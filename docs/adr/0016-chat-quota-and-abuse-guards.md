# 夜宴的额度与滥用防护

夜宴把 DeepSeek 的 key 留在 chat 服务里，但 `/chat` 是公开入口；如果只按「请求次数」限流，三个人一桌的一轮会调用三次模型，长上下文又比短问题贵得多，单靠 100 轮/天挡不住额度被刷。这个决策把防护拆成四层：先证明「是真实访问」，再限制单客户端频率，最后用全局预算兜底。

## 决策

### 1. 入场：必须有真实访问记录

- 请求必须带浏览器指纹，且该指纹在 `ViewLog` 里有记录（访问过文章）。
- 指纹不能凭空伪造；但指纹仍可被复用，所以它只是第一道门槛，不是安全边界。

### 2. 单客户端公平使用（Web 层，内存）

- 同一指纹同时只允许一条流；同一 IP 最多三条并发流。超过返回 `BUSY`。
- 每小时最多 30 次请求（指纹和 IP 各自计数）。
- 每日额度按「宾客数」扣点：单聊 1 点，两人桌 2 点，三人桌 3 点。默认每个指纹/IP 每天 100 点，即 100 次单聊或 33 次三人桌。
- 消息上限：用户单条 2,000 字符；assistant 单条 20,000 字符；历史总长 60,000 字符；最多 200 条历史；一桌最多 3 位。
- 这些计数是内存态，重启会清零；它们负责公平使用，真正的额度兜底在下一层。

### 3. 全局硬预算（Chat 服务，可持久化）

- 每次请求先按「最坏情况」估算字符数：每位宾客的系统提示词 + 完整历史 + 前面宾客按 `max_tokens` 估算的发言 + 自己的输出上限。
- 从当日全局预算里原子预留；预算不够直接返回 `SERVICE_DAILY_LIMIT`，不会调用上游。
- 请求结束后按实际输入/输出字符数结算，多退少补。
- 默认 `CHAT_DAILY_BUDGET_CHARS=5,000,000`，大约是 60 次单聊或 20 次三人桌；按自己的额度调整。
- 全局并发默认 6，超过返回 `SERVICE_BUSY`；每日请求上限 `DEEPSEEK_DAILY_LIMIT=1000` 作为第二道兜底。
- 当日预算状态写入 `CHAT_STATE_FILE`（Docker 挂载 `chat_data` 卷），进程重启不会把已花的额度清零。

### 4. 输出与上下文上限

- 单聊 `max_tokens=1400`，群聊每位 `max_tokens=900`，输出成本有上限。
- 群聊每轮最多 3 次上游调用，且历史总长只有 60k 字符；再长的对话应该换一桌，而不是无限堆历史。
- 预算估算使用 3 字符/token 的保守系数，实际结算按字符数回填。

### 错误码与 UI

- `BUSY`：同一指纹/IP 已有流在跑。
- `SERVICE_BUSY`：全局并发已满。
- `DAILY_LIMIT`：单客户端每日点数用完。
- `SERVICE_DAILY_LIMIT`：全局预算或每日请求上限用完。
- 页面显示 `Quota 已用 / 100`；选桌时显示「每轮 N 点额度」。请求在真正开始流式输出前被拒时，用户消息会退回输入框，不占客户端额度显示。

## 代价与已知限制

- 单客户端的指纹/IP 计数是内存态；进程重启会重置。全局预算状态是持久化的，所以重启不会让额度无限恢复。
- 指纹可以被复用，IP 可以轮换；轮换者最终会撞到全局预算和全局并发。
- 预算是「估算字符数」，不是 DeepSeek 的精确账单；它的目标是防止额度被刷完，不是财务对账。如果以后要精确到 token，可以解析上游 `usage` 并改用 token 预算。
- 没有引入 CAPTCHA / Turnstile。如果出现持续攻击，优先在 Cloudflare/WAF 层加人机验证，或临时调低 `CHAT_DAILY_BUDGET_CHARS` / `CHAT_MAX_CONCURRENCY`。
- 如果要多实例共享单客户端额度，需要把 Web 层的内存计数迁到 SQLite（例如 `ChatUsage` 表）或 Redis；当前单实例部署不需要。

## 考虑过的方案

- **只按请求次数限流**：三人桌一轮调用三次，等于把额度放大三倍；放弃。
- **只按 IP 限流**：代理池可以绕开；必须有全局预算兜底。
- **把人物提示词和 key 放前端**：客户端可被篡改，key 会泄露；放弃。
- **现在就上 Turnstile**：对个人站点的正常读者摩擦太大；先保留为攻击时的应急选项。
