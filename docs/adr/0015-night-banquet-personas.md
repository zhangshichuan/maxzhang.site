# 夜宴：把树洞改成可选的已蒸馏人物圆桌

`/chat` 原本是单一「树洞」倾听者。现在改成「夜宴」：用户从 14 位已蒸馏人物中选 1 位对谈，或选 2–3 位开一桌；每位宾客按顺序发言，能看见前面宾客说过什么，也可以互相反驳。

## 决策

- 保留 `/chat` 路由与本地会话机制，模块名与导航改为「夜宴 / Night Banquet」。
- 人物提示词改编自 [alchaincyf/nuwa-skill](https://github.com/alchaincyf/nuwa-skill) 的公开示例（MIT），只保留身份、心智模型、决策启发式、表达方式和盲区；去掉工具调用、调研工作流与案例索引等运行时无关内容。
- 提示词放在 `apps/services/chat/personas/*.md`，由 Go 服务 `go:embed` 加载；网页只保留名单、领域、短评等展示信息，不把提示词打进客户端 bundle。
- 单聊和群聊共用一条事件流：`guest_start` → `delta` → `guest_end` → `done`。群聊由 chat 服务串行编排：一位宾客一次 DeepSeek 调用，后面的人能看到前面的发言（其他宾客的消息以 `【姓名】` 前缀转成 user 角色）。
- 一桌最多 3 位。群聊每轮最多 3 次上游调用，单次请求总超时 180 秒；每位宾客的回答上限比单聊短。
- 网页按「桌子」（排序后的宾客组合）+ 日期保存会话，最多保留 3 天；换桌不会清掉另一桌。发送时只带最近 200 条、15 万字符以内的上下文，避免群聊无限变贵。
- 页面始终展示「所有宾客都是基于公开资料提炼的 AI 视角，不是本人，也不代表本站立场」。系统提示词另带共同安全底线。
- 群聊顺序默认是用户的选择顺序；用户点名某位宾客时，该宾客仍按选择顺序出现，但所有宾客都能看到点名内容。

## 原因

- 单一树洞的「只倾听」定位已经稳定，但用户希望有更主动、更有观点的对话；名人圆桌把「和谁聊」变成产品的一部分。
- 单次调用让模型同时扮演多人，容易出现声音趋同、格式漂移和解析脆弱；逐位调用更接近真实饭桌，也能准确标注发言人。
- 把人物提示词留在服务端，既能控制上下文和成本，也避免客户端被篡改或绕过。

## 代价

- 群聊成本与延迟是单聊的 N 倍（N = 宾客数），因此上限设为 3，并对群聊回答设更短的 token 上限。
- 人物提示词是公开资料的二手提炼，存在时效、误读和「公开表达 ≠ 真实想法」的局限；必须在 UI 和提示词里明确标注。
- 旧树洞提示词（只倾听、不评判）不再作为独立角色使用；如果以后需要，可作为第 15 位特殊宾客重新接入。

## 考虑过的方案

- **保留树洞 + 新增独立页面**：两个入口、两套会话与限额，定位分裂，放弃。
- **一次调用让模型输出多个 `【姓名】` 段落**：更便宜，但多人声音容易趋同，流式解析也脆弱，放弃。
- **把提示词放网页端并传给 Go**：前端 bundle 变大，且服务端无法阻止任意 system prompt，放弃。
