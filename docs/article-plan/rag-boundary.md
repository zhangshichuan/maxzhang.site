# RAG 的边界：幻觉、检索与评估

## 读者与承诺

读者：已经做过 LLM demo，正在把 RAG 推进到真实业务里的产品经理和工程师。

读完应该能：

1. 判断一次“答错了”到底发生在检索、上下文组装还是生成阶段。
2. 设计一套最小但有效的 RAG 评估集，而不是只看几个 demo 问题。
3. 决定什么时候该用 RAG，什么时候应该用长上下文、工具调用、微调，或者直接拒答。

## 核心主张

RAG 不是幻觉的解药，而是一套证据系统。它把“模型不知道”变成“系统有没有找到证据、有没有把证据放进上下文、模型有没有忠于证据”三个可检查的问题。

如果检索没有拿到正确证据，后面的生成越流畅，错误越难发现。所以优化顺序应该是：先评估检索，再评估忠实性，最后才调 prompt。

## 结构与论证

### 1. 开场：一个“看起来很对”的错误回答

场景：客服机器人引用了一条不存在的退款政策，语气确定，格式完整，用户信了。

要写清楚：

- 这不是单纯的“模型胡编”，而是证据链在某一环断了。
- 错误答案的流畅度与正确性无关；RAG 的价值是让错误可以被定位。

### 2. 幻觉不是一种问题，而是三类失败

- **知识缺失**：模型参数里没有这个知识，也没有检索到。
- **检索失败**：知识在库里，但召回没拿到，或拿到了错误版本。
- **生成不忠实**：证据在上下文里，模型仍然回答了与证据冲突的内容。

补充一个常被忽略的维度：**问题理解失败**。用户问的是“今年”，检索却按“所有年份”召回。它可以归入检索失败，但值得单独提醒。

关键句：不要把三类问题都归因于“模型能力不够”，否则会一直换模型，却不修检索和评估。

### 3. RAG 的完整管线

按数据流拆成六段，每段都给出失败信号：

1. 解析与切分：PDF 表格、标题层级、代码块、版本信息。
2. 索引：稀疏检索（BM25）、稠密向量、混合检索、元数据过滤。
3. 查询理解：改写、实体识别、时间/权限过滤。
4. 召回：top-k、阈值、去重、版本选择。
5. 重排与上下文组装：rerank、顺序、冲突处理、引用标注。
6. 生成：忠实性约束、引用、拒答。

要强调：RAG 不是“向量数据库 + prompt”，而是一条每一段都可能丢证据的管线。

### 4. 向量召回与 BM25 的分工

用一张表说明：

| 场景 | 更适合 | 原因 |
| ---- | ------ | ---- |
| 语义改写、同义表达 | 向量召回 | 不依赖字面重合 |
| 产品型号、错误码、人名 | BM25 | 稀有词和精确匹配更稳 |
| 长文档、口语问题 | 混合检索 | 两种信号互补 |
| 多语言/跨语言 | 向量或多语言模型 | 字面匹配失效 |

要写清楚 hybrid search 的基本做法：并行召回 → 分数归一化或 RRF → 去重 → rerank。不要写成“向量一定比 BM25 先进”。

### 5. 评估：先评估检索，再评估生成

检索指标：

- Recall@k：正确文档有没有进入候选集。
- MRR / nDCG：正确文档排得够不够靠前。
- Context precision / recall：送进模型的上下文是否相关、是否覆盖答案。

生成指标：

- Faithfulness：回答是否被上下文支持。
- Answer relevance / correctness：回答是否解决问题。
- Citation accuracy：引用是否真的对应证据。
- Abstention：没有证据时是否敢说“不知道”。

端到端指标：

- 任务成功率、人工抽检通过率、平均延迟、单次成本。

评估集：

- 从真实用户问题里采样，覆盖简单事实、跨文档、时间敏感、无答案、权限受限、冲突证据。
- 先做 50–100 条 golden set，比一上来追求自动化评测更有效。
- LLM-as-judge 只能做规模化初筛，关键样本必须人工复核。

### 6. 常见失败模式

结合 Seven Failure Points 的框架，映射到管线：

- 内容缺失：库里根本没有答案。
- 召回遗漏：正确文档没有进入 top-k。
- 上下文遗漏：召回了但被截断或排序挤掉。
- 提取失败：答案在文档里，但模型没有抽出来。
- 格式错误：要求 JSON，输出了自然语言。
- 粒度错误：答案太泛或太具体。
- 不完整：多跳问题只回答了第一跳。

每个失败模式给出一个可观测信号和修复方向。

### 7. 什么时候不该用 RAG

用决策表比较：

| 需求 | 更适合的方案 |
| ---- | ------------ |
| 私有知识、需要引用 | RAG |
| 文档很短、问题集中 | 长上下文 |
| 固定输出风格/格式 | 微调或结构化输出 |
| 需要实时数据/执行动作 | 工具调用 |
| 知识不存在或权限不足 | 拒答/转人工 |
| 高频、低延迟、答案稳定 | 缓存/规则/传统检索 |

关键句：RAG 适合“知识在外部、答案需要证据”的问题，不适合所有“模型答得不好”的问题。

### 8. 收尾：一张检查清单

- 先问：答案应该来自哪份证据？
- 再问：这份证据有没有被召回、被放进上下文、被正确引用？
- 最后问：没有证据时，系统会不会拒答？
- 评估集是否覆盖无答案、冲突证据和时间敏感问题？
- 是否把检索指标和生成指标分开看？
