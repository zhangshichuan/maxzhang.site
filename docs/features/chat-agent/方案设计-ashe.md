# Chat Agent 方案设计

## 1. 背景与目标

当前项目的 `/chat` 已有基础聊天入口，但现有实现本质上只是将消息转发给外部接口，缺少站点自身知识库、来源引用、范围约束和可展示的 RAG 能力。

本次重构目标不是继续做一个泛化聊天页，而是把 `/chat` 做成一个面向个人品牌与技术内容的智能客服：

- 能回答与 Max Zhang 个人介绍相关的问题
- 能回答与站内文章内容相关的问题
- 能回答与技术方向、项目经验、学习路径相关的问题
- 能基于知识库做相关文章推荐
- 能对无关问题拒答，避免“万能 AI”形态
- 能体现 LangChain RAG 的工程实践，作为求职作品展示

## 2. 产品定位

产品定位：

“基于 Next.js 16 + LangChain 的个人知识库智能客服，支持双语问答、来源引用、相关文章推荐和范围内拒答。”

相比电商客服流程，本项目保留“客服 Agent”的骨架，但替换业务语义：

- 商品基础信息 -> 个人介绍、技术栈、项目背景
- 商品导购推荐 -> 文章推荐、学习路径推荐、技术选型建议
- 售后与质保 -> 仅回答知识库可支持的问题
- 库存/物流插件 -> 暂不实现，替换为站内检索工具
- 多语言支持 -> 使用现有中英文内容和 `next-intl`

## 3. 用户场景

### 3.1 个人背景问答

示例问题：

- 你目前的技术方向是什么？
- 你做过哪些 AI 应用相关项目？
- 你为什么适合 AI 应用工程师岗位？

### 3.2 文章问答

示例问题：

- 你写过哪些关于 RAG 的文章？
- 你在文章里如何解释 LangChain？
- 有没有关于 Node.js 性能优化的内容？

### 3.3 内容推荐

示例问题：

- 如果我想学 LLMOps，你推荐先看哪些文章？
- 我准备面试后端开发，应该先看哪些内容？
- 能给我推荐几篇关于 LangChain 和 RAG 的文章吗？

### 3.4 边界控制

示例问题：

- 帮我预测明天比特币价格
- 帮我写一份劳动仲裁材料

对于站点知识库范围外问题，系统应明确拒答，并引导用户提问与个人介绍、文章内容或技术主题相关的问题。

## 4. 核心能力

### 4.1 知识库问答

基于站点本地内容构建知识库，回答以下范围内问题：

- 个人介绍
- 工作经历
- 技术栈
- 项目背景
- 已发布文章内容
- 与这些内容直接相关的技术总结与推荐

### 4.2 来源引用

每次回答都尽量附带来源，至少包括：

- 来源标题
- 来源类型
- 对应页面链接或文章 slug

这样可以明确证明回答来自站内知识，而不是模型自由发挥。

### 4.3 相关文章推荐

当问题涉及某个技术主题时，在回答后附带 2 到 3 篇相关文章，增强站内浏览转化。

### 4.4 双语支持

- 中文问题优先检索中文知识库并用中文回答
- 英文问题优先检索英文知识库并用英文回答
- 当当前语言数据不足时，可回退到另一语言内容，但应优先保留当前语言体验

### 4.5 拒答机制

系统需要具备范围判断能力：

- 与站点内容强相关 -> 正常回答
- 与站点内容弱相关但可推荐文章 -> 简答并推荐内容
- 与站点内容无关 -> 拒答并给出可提问方向

## 5. 非目标

本阶段不做：

- 电商订单、物流、库存类插件能力
- 多平台客服渠道接入
- 复杂长期记忆
- 外部联网检索
- 通用型工具调用平台
- 追求“什么都能答”的泛化 AI 助手

## 6. 知识源设计

当前项目已经具备较好的本地知识源，可直接复用。

### 6.1 文章知识

来源：

- `articles/zh/*`
- `articles/en/*`
- `src/features/posts/queries/posts.ts`

提取内容：

- 标题
- 摘要
- 标签
- 分类
- 正文
- slug
- locale
- 页面 URL

### 6.2 个人介绍知识

来源：

- `messages/zh.json`
- `messages/en.json`
- `src/features/about/components/about-page.tsx`

提取内容：

- 角色定位
- 地区
- 个人描述
- 工作经历
- 教育经历
- 技术栈
- 兴趣点
- 社交链接

### 6.3 项目背景知识

来源：

- `README.md`
- `README.zh.md`
- `ARCHITECTURE.md`

提取内容：

- 项目目标
- 技术栈
- 架构分层
- 内容组织方式
- 当前项目定位

## 7. 文档建模策略

建议将知识库拆成 3 类文档，而不是简单把所有文本拼在一起。

### 7.1 profile 文档

用于承载个人信息：

- 自我介绍
- 工作经历
- 教育经历
- 技术栈

### 7.2 post 文档

用于承载文章内容：

- frontmatter
- 摘要
- 正文切片

### 7.3 project 文档

用于承载项目与架构说明：

- README
- 架构设计说明

### 7.4 metadata 设计

每个 chunk 建议统一带上以下元信息：

- `type`: `profile` | `post` | `project`
- `locale`
- `title`
- `slug`
- `url`
- `tags`
- `category`
- `sourcePath`

这些 metadata 直接决定后续是否容易做：

- 当前语言优先检索
- 相关文章推荐
- 来源卡片展示
- 不同知识源分路召回

## 8. RAG 架构设计

### 8.1 总体流程

建议首版采用“轻 Agent、重 RAG”的结构：

1. 接收用户问题
2. 识别问题语言
3. 识别问题类型
4. 从对应知识源检索相关片段
5. 组装提示词生成回答
6. 返回答案、来源和相关文章

这个阶段不必一开始就追求复杂工作流，先把检索质量、引用和边界控制做扎实。

### 8.2 问题分类

问题可分为：

- `profile`: 关于个人经历、技术栈、求职方向
- `post`: 关于文章内容、某个技术主题
- `project`: 关于本站项目本身
- `recommendation`: 让系统推荐文章或学习路径
- `out_of_scope`: 明显超出站点内容范围

分类用途：

- 控制检索范围
- 控制提示词
- 控制返回结构

### 8.3 检索策略

建议首版优先做可控方案：

- profile 问题：优先检索 `profile`
- project 问题：优先检索 `project`
- post / recommendation 问题：优先检索 `post`
- 混合问题：允许跨类召回

召回步骤建议：

1. 先按 locale 过滤
2. 再按 type 限制检索范围
3. 取 top-k chunks
4. 组装 sources

### 8.4 生成策略

系统提示词建议强调：

- 仅基于提供的知识片段回答
- 知识不足时明确说明不知道
- 优先简洁回答
- 输出语言跟随用户问题
- 尽量给出站内来源
- 不编造不存在的经历、项目和文章

### 8.5 输出结构

首版服务端建议统一返回：

```ts
interface ChatAgentResponse {
  answer: string
  sources: Array<{
    title: string
    type: 'profile' | 'post' | 'project'
    url: string
    slug?: string
  }>
  relatedPosts: Array<{
    title: string
    slug: string
    url: string
    summary: string
  }>
  locale: string
}
```

这个结构比纯文本流更适合前端展示作品感，也方便后续测试。

## 9. LangChain 集成建议

### 9.1 首版目标

LangChain 在本项目中的主要职责：

- 文档抽象
- 文本切片
- embeddings 封装
- retriever 封装
- prompt 编排
- 输出结构化结果

### 9.2 适合引入的模块

可优先引入：

- `Document`
- text splitter
- embeddings
- vector store
- retriever
- prompt template

### 9.3 不建议一开始就上复杂 Agent

如果首版直接做多工具 Agent、复杂工作流和深层记忆，很容易把精力消耗在框架调试而不是结果质量上。

更好的策略是：

- 第一期做稳定 RAG
- 第二期再做 tool calling 和 query rewrite

## 10. 与现有项目结构的集成方式

项目已经有明确分层，聊天能力应遵循现有架构，不要把逻辑堆进页面或 server action。

建议目录方向如下：

```text
app/[locale]/chat/page.tsx

src/features/chat/
  components/
  model/
  queries/
  services/
  server-actions/

src/server/
  ai/
  knowledge/
```

### 10.1 页面层

`app/[locale]/chat/page.tsx`

职责：

- 路由入口
- 组装聊天页面

### 10.2 feature 层

`src/features/chat/components`

职责：

- 输入框
- 消息列表
- 来源卡片
- 推荐文章展示

`src/features/chat/server-actions`

职责：

- 作为前端直接调用入口
- 参数校验
- 调用 service

`src/features/chat/services`

职责：

- 问题分类
- 检索编排
- 调用 LLM
- 输出结果结构化

### 10.3 server 层

`src/server/knowledge`

职责：

- 读取本地知识源
- 构建 Documents
- 切片
- 初始化向量检索

`src/server/ai`

职责：

- 模型客户端封装
- embeddings 封装
- 提示词模板管理

## 11. UI 设计建议

`/chat` 不建议只是一个空白聊天框，而应有明显的“个人技术客服”定位。

### 11.1 首页态建议

显示：

- 标题：例如“Max Zhang AI 客服”或“个人知识库助手”
- 简短说明：可回答文章、项目、个人介绍相关问题
- 预设问题按钮

推荐预设问题：

- 你擅长哪些技术方向？
- 推荐几篇关于 RAG 的文章
- 你做过哪些 AI 相关项目？
- LangChain 为什么值得学？

### 11.2 消息区建议

回答消息可分区展示：

- 回答正文
- 来源
- 相关文章

相比纯文本气泡，这样更能体现 RAG 产品特征。

## 12. 约束与风格规则

建议在系统规则中明确以下限制：

- 仅回答与 Max Zhang、本网站文章、项目介绍相关的问题
- 超出知识库范围时拒答
- 回答尽量简洁
- 优先引用来源
- 中文问题用中文答，英文问题用英文答
- 不伪造经历、项目、技能、链接

## 13. 为什么这个方案适合作为求职作品

这个方案比做一个通用聊天窗口更适合作为作品展示，因为它同时覆盖了：

- LangChain RAG 基础能力
- 本地知识库建模
- 多语言内容检索
- 可解释性输出
- 产品边界控制
- 与现有 Next.js 项目的真实集成

面试时可重点讲：

- 为什么知识源要分 `profile` / `post` / `project`
- 为什么先做 RAG 再做 Agent
- 如何避免幻觉
- 如何通过 metadata 支撑来源引用和相关推荐
- 如何在现有分层架构中落地 AI 功能

## 14. 首版结论

首版应聚焦在以下结果：

- 替换现有 `/chat` 外部转发逻辑
- 接入本地知识源
- 完成基于 LangChain 的 RAG 回答
- 输出来源和相关文章
- 支持双语和拒答

这样可以较快形成一个完整、可演示、可继续迭代的 AI 求职项目基础版本。
