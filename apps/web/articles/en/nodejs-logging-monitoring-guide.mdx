## 1. Logging Isn't "Printing." It's Your Surveillance System.

Let's get one thing straight.

`console.log("hello")` is not logging.

That's printing. Like scribbling something on a sticky note and tossing it. Gone the moment you close the terminal. Good luck finding it later.

Real logging is structured. Persistent. Searchable. It's not a few lines you threw in while debugging. It's infrastructure you deploy alongside your application.

Here's an analogy.

You run a 24-hour convenience store. One night you count the register and find you're 500 bucks short.

What do you do?

If you installed security cameras, you pull up the footage. Ten minutes later, you know who took it, when, and how.

No cameras? You stare at the ledger helplessly and eat the loss.

Your application logs are that security footage. They just sit there recording. On normal days, they're a power-hungry lump of metal in the corner. On bad days, they're your savior.

But here's the thing most people never think about.

**The quality of your footage determines how fast you can find the problem.**

Are your cameras shooting 4K with night vision, or did you grab the cheapest 480P webcam off AliExpress? Does your footage keep for a month or does it overwrite itself every three days? When something goes wrong, can you search by timestamp, or do you have to watch the entire tape from the beginning?

These are the questions your logging system needs to answer. Not "do I have logs" — "are my logs any good?"

### What Logging Can Do, And What It Can't

A lot of beginners think logs are magic. Something broke? Check the logs. User behavior analysis? Check the logs. Performance tuning? Check the logs.

Logs can do a lot. But they have a clear boundary.

What they CAN do:

- Capture a snapshot of an error — who, when, what endpoint, what parameters, what went wrong
- Reconstruct a request's full path — if you included a requestId
- Count how many times a specific error occurred — if you're using structured logs
- Audit trail — "what did this user do in the last 24 hours?"

What they CAN'T do:

- **Tell you why something broke.** Logs record facts, not analysis. You have to connect the dots yourself.
- **Alert you that something is broken.** Logs are passive. An error happens, and if you don't go looking for it, you'll never know. That's what alerting systems are for.
- **Analyze performance bottlenecks.** "Why is this API 200ms slower than last week?" Logs can tell you which services were called, but not where the time went. That's distributed tracing territory.
- **Detect slow memory leaks.** Logs can look perfectly fine while your heap creeps upward toward an OOM. That's metrics monitoring territory.

One sentence: logs give you **raw materials**, not a **finished meal**.

## 2. How Logging Actually Lands in Node.js — From console to File Streams

Alright. Enough theory. Let's talk code.

### stdout and stderr Are Two Different Roads

In Node.js, `console.log` and `console.error` go through completely different pipes.

`console.log` writes to **stdout** (standard output).
`console.error` writes to **stderr** (standard error).

What does this mean in practice? You can separate them at the command line:

```bash
# stdout to one file, stderr to another
node app.js > normal.log 2> error.log

# pipe only stdout to grep, let stderr still print to screen
node app.js 2>/dev/null | grep "success"
```

Normal info out the front door. Errors out the back. This isn't some Node.js invention — Unix settled this decades ago. Once you understand it, you can do some elegant things in your shell.

But most Node.js developers go their entire careers without using this distinction. They just know `console.log` and dump everything into it, then wonder why their logs are a mess.

### The console API Is Packed With Gems

I used to only use `console.log` too. Then one day I was debugging a callback hell nested seven layers deep, and I discovered that the `console` object has a bunch of tools that can save your hairline.

**Print variable names and values together** — one of the most practical uses of ES6 object shorthand:

```javascript
const userId = 'u_123'
const orderId = 'ord_456'
const amount = 99.9

// The old way:
console.log('userId:', userId, 'orderId:', orderId, 'amount:', amount)

// The new way:
console.log({ userId, orderId, amount })
// { userId: 'u_123', orderId: 'ord_456', amount: 99.9 }
```

Dozens of characters saved, no alignment headaches. Once you use this for a week, going back to string concatenation feels like wiping your ass with sandpaper.

**Table printing** — absolutely clutch for array data.

```javascript
console.table([
  { name: 'Alice', role: 'admin', status: 'active' },
  { name: 'Bob', role: 'user', status: 'inactive' },
  { name: 'Carol', role: 'user', status: 'active' },
])
```

Your terminal draws a perfectly aligned table. Rows and columns. You can spot Bob's inactive status instantly instead of scanning through a wall of JSON.

**Stack tracing** — `console.trace()`:

```javascript
function validateOrder(order) {
  if (!order.items) {
    console.trace('Who the hell passed in an empty order?')
    throw new Error('Empty order')
  }
}

function processCheckout(data) {
  validateOrder(data.order)
}

function handleRequest(req) {
  processCheckout(req.body)
}
```

Trace prints the full call chain — `handleRequest → processCheckout → validateOrder`. Stick a trace inside a function that's called from seven layers deep, and you instantly know who's calling you. No need to hunt through dozens of import chains.

**Performance timing** — `console.time()` and `console.timeEnd()`:

```javascript
console.time('DB query')
const users = await db.query('SELECT * FROM users WHERE status = ?', ['active'])
console.timeEnd('DB query')
// DB query: 234.56ms
```

No manual `Date.now()` math. And you can nest them — wrap the whole request in `time('total')` and sprinkle smaller `time('userQuery')`, `time('orderQuery')` inside. Crystal clear.

**Conditional assertion** — `console.assert()`:

```javascript
const userCount = await db.query('SELECT COUNT(*) FROM users')
console.assert(userCount > 0, 'The user table is empty, something is very wrong')
// Only logs when the assertion FAILS
```

This is fantastic during development — you assume a condition always holds true, and if it ever doesn't, you know immediately.

**Hierarchical grouping** — `console.group()` and `console.groupEnd()`:

```javascript
console.group('DB operations')
console.log('Querying user table...')
console.group('SQL details')
console.log('SELECT * FROM users WHERE id = ?')
console.groupEnd()
console.log('Returned 1 row')
console.groupEnd()
```

The terminal shows indented nesting. Expand when you need details, collapse when you don't.

**Deep object inspection** — `console.dir()`:

```javascript
const deepObj = {
  level1: { level2: { level3: { value: 'bottom' } } },
}

// console.log might truncate at level 2
console.dir(deepObj, { depth: null, colors: true })
// depth: null means "show me everything, don't hold back"
```

These APIs aren't meant for production. They're for your development workflow. But the thing is — a lot of people don't even know they exist. Knowing them versus not knowing them is approximately a 3x difference in debugging speed.

### Writing Logs to Files — Streams vs Brute Force appends

In development, console is fine. In production, logs must be persisted to disk. Server restarts and your bug evidence is gone.

The mistake every beginner makes:

```javascript
import fs from 'node:fs'

function log(message) {
  fs.appendFile('app.log', message + '\n', () => {})
}

// Called everywhere in your business logic
app.post('/order', async (req, res) => {
  log('Starting order creation')
  const order = await createOrder(req.body)
  log('Order created: ' + order.id)
  res.json(order)
})
```

Every single `appendFile` call:

1. Opens the file
2. Writes to the end
3. Closes the file

Your endpoint gets hit 1000 times per second. That's 1000 open-write-close cycles per second. The operating system hates you. And there's a limit to how many files can be open simultaneously — you might start seeing "too many open files" errors.

The right way is a **writable stream**:

```javascript
import fs from 'node:fs'

const logStream = fs.createWriteStream('app.log', { flags: 'a' })

function log(message) {
  logStream.write(message + '\n')
}

// Gracefully close on exit
process.on('SIGINT', () => {
  logStream.end()
  process.exit(0)
})
```

A stream is like a garden hose. The file is connected at one end and stays open. You pour water in at your end. It accumulates in a buffer first, then flushes to disk in batches. You don't reconnect the hose for every cup of water.

One nuance: `write()` returns `false` when the internal buffer is full. In high-throughput scenarios, you need to wait for the `drain` event:

```javascript
function safeWrite(stream, data) {
  if (!stream.write(data)) {
    stream.once('drain', () => stream.write(data))
  }
}
```

But honestly — most Node.js apps don't hit this threshold. Just knowing it exists is enough for now.

### A Concept That Confuses Everyone: inodes

Alright, there's one Linux-level thing you need to understand. It directly affects your log rotation experience.

Every file on Linux has an inode number.

```bash
ls -i app.log
# 1234567 app.log
```

The inode stores the file's metadata (permissions, size, timestamps) and pointers to the actual data blocks on disk. The filename is just a label — the real identity is the inode number.

Think of it like this: your house has a street address. The inode is that address. The filename is whatever nickname you saved in your delivery app — "Sarah's place." You can change "Sarah's place" to "Leave at door," but the street address doesn't change. The delivery driver still finds it.

What does this mean for logging?

When you run `rm app.log` to delete a log file that a running process is actively writing to — the filename disappears from the directory listing. But the inode lives on. The process still holds the file descriptor and keeps writing data. Disk space won't be freed until every file descriptor pointing to that inode is closed.

This is why log rotation can't just "delete and recreate." You have to rename `app.log` to `app-2026-03-10.log`, let the process keep writing to the same inode, then signal the process to open a new file.

We'll come back to inodes when we talk about log rotation.

## 3. What Production Logs Should Actually Look Like

### Request Logging: Miss One Field and You Might As Well Not Bother

Every HTTP request — 200 or 500 — must leave a log entry. This is non-negotiable.

But log what?

A lot of people's request logs look like this:

```
GET /api/users/123 200
```

That's the equivalent of your security camera catching a dark blur. You know someone was there. You don't know who, how long they stayed, or what they did.

A proper request log should contain at minimum:

```
timestamp   — when
method      — GET/POST/PUT/DELETE
url         — full request path
status      — what status code was returned
duration    — how long it took
ip          — who's making the request
userId      — which authenticated user
traceId     — global trace ID for this request
```

The code is straightforward:

```javascript
app.use((req, res, next) => {
  const start = Date.now()

  res.on('finish', () => {
    console.log(
      JSON.stringify({
        timestamp: new Date().toISOString(),
        method: req.method,
        url: req.originalUrl,
        status: res.statusCode,
        duration: Date.now() - start,
        ip: req.ip,
        userId: req.user?.id,
        traceId: req.headers['x-trace-id'],
      }),
    )
  })

  next()
})
```

Notice the `res.on('finish', ...)`. Don't log right after `next()`. At that point, your business logic might not have finished executing, the status code isn't set yet, and your duration will be wrong. The `finish` event fires after the response is fully sent.

### External Service Call Logging: Your Service Is Not an Island

Your Node.js app almost certainly calls other backend services.

Who did you call? What parameters? How long did it take? What came back? You need to log all of it. Otherwise, when a user says "the site is slow," you're just guessing which link in the chain is dragging.

```javascript
async function callBackend(url, params) {
  const start = Date.now()
  const requestId = crypto.randomUUID()

  try {
    const res = await axios.post(url, params, {
      headers: { 'X-Request-ID': requestId },
      timeout: 5000,
    })

    const duration = Date.now() - start

    console.log(
      JSON.stringify({
        type: 'backend_call',
        requestId,
        service: url,
        duration,
        status: res.status,
        timestamp: new Date().toISOString(),
      }),
    )

    return res.data
  } catch (err) {
    const duration = Date.now() - start

    console.error(
      JSON.stringify({
        type: 'backend_error',
        requestId,
        service: url,
        duration,
        error: err.message,
        timestamp: new Date().toISOString(),
      }),
    )

    throw err
  }
}
```

Notice I log `duration` in both success AND failure paths. Why? Because sometimes failures aren't timeouts — the downstream service immediately returns an error. A short duration tells you "it's not a network issue, look at the business logic."

### Business Logging: Record State Transitions at Key Nodes

Request logs say "someone hit this endpoint." Business logs say "what actually happened."

Take order creation. You need three states:

**Start** — "Someone is placing an order." Order ID, product, quantity, price.

**Success** — "Order placed." Final price.

**Failure** — "Order failed." Why? Out of stock? Payment timeout? Validation error?

All three logs share the same order ID. Search that ID when something goes wrong, and the entire story unfolds before you.

```javascript
async function createOrder(data) {
  const orderId = generateOrderId()

  console.log(
    JSON.stringify({
      type: 'business',
      action: 'order_start',
      orderId,
      productId: data.productId,
      quantity: data.quantity,
      totalPrice: data.totalPrice,
    }),
  )

  try {
    const stockOk = await checkStock(data.productId, data.quantity)
    if (!stockOk) {
      console.log(
        JSON.stringify({
          type: 'business',
          action: 'order_failed',
          orderId,
          reason: 'stock_insufficient',
        }),
      )
      throw new Error('Out of stock')
    }

    const order = await saveOrder(orderId, data)

    console.log(
      JSON.stringify({
        type: 'business',
        action: 'order_success',
        orderId,
        totalPrice: data.totalPrice,
      }),
    )

    return order
  } catch (err) {
    console.error(
      JSON.stringify({
        type: 'business',
        action: 'order_error',
        orderId,
        error: err.message,
      }),
    )
    throw err
  }
}
```

Beginning, middle, end. Cause and effect. Logs like this make 3 AM debugging feel less like archaeology and more like reading a timeline.

### Error Handling — The Most Valuable Logs Live Inside try/catch

A few traps worth calling out.

**Trap one: Promise.reject won't be caught by synchronous try/catch.**

```javascript
// This does NOTHING
try {
  Promise.reject(new Error('something broke'))
} catch (err) {
  console.error(err) // never executes
}

// You must await or .catch()
await Promise.reject(new Error('something broke')) // try/catch works
Promise.reject(new Error('something broke')).catch((err) => console.error(err))
```

**Trap two: You think you've handled it, but your process is running naked.**

The most dangerous scenario isn't having no try/catch — it's having try/catch that doesn't cover everything. Maybe you wrapped your Express routes but forgot a global fallback. An unawaited Promise rejects somewhere, the unhandledRejection event fires, and you're not listening for it. The error gets swallowed into the void.

You need global backstops:

```javascript
// Last line of defense
process.on('unhandledRejection', (reason, promise) => {
  console.error(
    JSON.stringify({
      type: 'unhandled_rejection',
      message: reason?.message || reason,
      stack: reason?.stack,
      timestamp: new Date().toISOString(),
    }),
  )
  process.exit(1)
})

process.on('uncaughtException', (err) => {
  console.error(
    JSON.stringify({
      type: 'uncaught_exception',
      message: err.message,
      stack: err.stack,
      timestamp: new Date().toISOString(),
    }),
  )
  process.exit(1)
})
```

Node.js officially recommends exiting the process after catching an uncaught exception. The program state might be unreliable by that point. The best you can do is capture the crime scene before you pull the plug.

### Log Levels — This Judgment Call Saves Your Sleep at 3 AM

Too many people log everything as `info`. Or everything as `error`. This is the same as having no levels at all — you can't tell urgent from trivial.

From lowest to highest:

**trace** — Finest granularity. Code execution paths, more detailed than debug. Almost never enabled in production. Only used when chasing the most bizarre, inexplicable bugs.

**debug** — Development-time info. `SELECT * FROM users WHERE id = ?` stuff. Turn it off in production.

**info** — Normal business flow. Order created. User logged in. File uploaded. This is the main melody of your logs.

**warn** — Something's off, but not dead yet. DB connection pool at 85%. P99 latency hit 2 seconds. Worth noticing. Not fatal.

**error** — Something actually broke. Request failed. Exception caught. Business logic failure. Needs fixing, but the process is still running.

**fatal** — The ship is going down. Database completely unreachable. Out of memory. Process is about to exit. This is the last log that process will ever write.

A judgment framework: at 3 AM, if you got paged for this log, would you have to get out of bed?

| Level         | Action                               |
| ------------- | ------------------------------------ |
| trace / debug | Keep sleeping                        |
| info          | Roll over, keep sleeping             |
| warn          | Squint at it, probably keep sleeping |
| error         | Sit up                               |
| fatal         | Launch yourself out of bed           |

### Structured Logging: Why JSON

Imagine this. It's a weekend hobby project. One server. String-based logs. Looks nice enough:

```
[2026-03-10 10:00:00] INFO: user_123 logged in successfully
```

No problem.

Fast forward three years. That hobby project is now your main gig. Fifty servers. Billions of log entries per day. You pipe them all into ELK.

Now you want to find every log for user_123. You type `user_123` into Kibana.

Tons of results come back — some from the userId field, some from log message bodies that happen to contain `user_123`, some from query parameters in URLs the user happened to visit.

You can't get precise results.

This is where JSON saves you:

```json
{
  "timestamp": "2026-03-10T10:00:00.000Z",
  "level": "info",
  "message": "user logged in successfully",
  "userId": "user_123",
  "ip": "192.168.1.100",
  "requestId": "req_abc789"
}
```

Search `userId: "user_123"` in Kibana. Exact match. Nothing else.

That's the power of structured logging. It lets you **ask questions** instead of **guess riddles**.

### Three Iron Rules — They've Saved a Lot of People's Asses

**Rule one: A logging function must never throw.**

Logging is infrastructure. Infrastructure can't collapse on itself.

```javascript
// Stupid
function log(msg) {
  if (!msg) throw new Error('Message is empty')
  console.log(msg)
}

// You forgot to pass a message, and now the log function itself blows up the caller.
// Congratulations, you've made everything worse.
```

The right way: wrap the internals in try/catch and swallow everything. If logging fails, the business must continue. You can write the logging error to stderr as a last resort, but never let it affect the main flow.

**Rule two: Logging must have zero side effects.**

You can't modify an object's fields just because you're logging it.

```javascript
// Wrong
function logUser(user) {
  console.log(user)
  user.lastLogged = new Date() // side effect!
  await db.save(user)          // you're logging, why are you writing to the database?
}
```

Logging and business logic are two separate things. The security camera doesn't rearrange products on the convenience store shelves.

**Rule three: Sanitize sensitive data.**

Passwords. Phone numbers. ID numbers. Bank cards. Tokens. The only form these should appear in your logs is `***`.

```javascript
const SENSITIVE = ['password', 'token', 'secret', 'apiKey']

function sanitize(obj) {
  const clean = { ...obj }
  for (const key of SENSITIVE) {
    if (clean[key]) {
      clean[key] = clean[key].length > 10 ? clean[key].slice(0, 5) + '...' + clean[key].slice(-5) : '***'
    }
  }
  return clean
}
```

Picture this: a junior ops person copies an error log and pastes it into the company-wide group chat. Two hundred people now see a plaintext password. This isn't a technical problem anymore. It's a security incident.

## 4. Log Rotation — Don't Let Logs Eat Your Entire Disk

### What Happens Without Rotation

Your app.log grows 500MB a day.

3.5GB after a week. 15GB after a month. 45GB after three months.

One Wednesday at 3 AM — the disk fills up. Your Node.js process tries to write a log line, gets back "No space left on device." The process crashes. User service goes down. Your phone buzzes.

Log rotation means splitting that one infinitely-growing file into smaller, time-based or size-based chunks, then cleaning up the old ones. It protects your disk space.

### Two Strategies

**By time.**

```
app-2026-03-08.log
app-2026-03-09.log
app-2026-03-10.log
app.log   ← currently active
```

Every night at midnight, rename the current `app.log` to include the date, create a fresh `app.log`, and keep writing. Retain the last 30 days.

Good for applications with stable log volume.

**By size.**

```
app-001.log  (100MB)
app-002.log  (100MB)
app-003.log  (80MB)  ← currently active
```

When a file hits 100MB, rotate it out. Keep the last 50 files.

Good for applications with unpredictable log volume.

### Two Rotation Methods (With Traps People Fall Into)

**The create method** (rename):

1. Rename `app.log` to `app-2026-03-10.log`
2. Create a new `app.log`

The trap: the process still holds the old inode. It keeps writing to `app-2026-03-10.log`. Your new `app.log` receives nothing.

The fix: after renaming, send the process a signal — like SIGUSR2 — telling it to close the old file and open a new one.

**The copytruncate method** (copy then truncate):

1. Copy the contents of `app.log` to `app-2026-03-10.log`
2. Truncate the original `app.log` to zero bytes

The advantage: the process keeps writing to the same inode. No signal needed. The downside: there's a tiny window between copy and truncate where in-flight writes might be lost.

### logrotate Configuration

On Linux, this is handled by a tool called `logrotate`. Most distros ship with it:

```bash
# /etc/logrotate.d/myapp

/var/log/myapp/*.log {
    daily           # rotate every day
    rotate 30       # keep 30 days
    compress        # gzip old logs to save space
    delaycompress   # don't compress yesterday's log (you might need it today)
    missingok       # don't error if the log file doesn't exist
    notifempty      # don't rotate empty files
    create 0640 myapp myapp   # permissions for new files
    sharedscripts   # run postrotate once for all matched files

    postrotate
        kill -USR2 $(cat /var/run/myapp.pid)
    endscript
}
```

The `kill -USR2` in `postrotate` is how you tell your Node.js process to reopen log files. Your process needs to listen for it:

```javascript
process.on('SIGUSR2', () => {
  logStream.end()
  logStream = fs.createWriteStream('app.log', { flags: 'a' })
})
```

## 5. When Terminal Logs Become Fun — CLI Beautification

This chapter isn't about production. It's about making your development experience better. But a good dev experience makes you more willing to write good logs.

### chalk: Color Your Terminal

```javascript
import chalk from 'chalk'

console.log(chalk.red('Error message'))
console.log(chalk.green('Operation successful'))
console.log(chalk.yellow('Warning: memory at 85%'))
console.log(chalk.bold.blue('Bold and blue'))

// Template literals
console.log(chalk`{red Failed} {green Success} {yellow Warning}`)
```

When your terminal is a wall of white text, you don't notice the one red error line. Add color, and your eyes catch it automatically.

### progress: Progress Bars

```javascript
import ProgressBar from 'progress'

const bar = new ProgressBar('Downloading [:bar] :percent ETA: :etas', {
  total: 100,
  width: 30,
})

const timer = setInterval(() => {
  bar.tick()
  if (bar.complete) {
    clearInterval(timer)
    console.log('\nDownload complete')
  }
}, 100)
```

### inquirer: Interactive CLI

```javascript
import inquirer from 'inquirer'

const answers = await inquirer.prompt([
  { type: 'input', name: 'name', message: 'What is your name?' },
  {
    type: 'list',
    name: 'env',
    message: 'Select environment:',
    choices: ['dev', 'staging', 'production'],
  },
  { type: 'confirm', name: 'confirm', message: 'Proceed?', default: false },
])
```

### commander.js: CLI Framework

```javascript
import { Command } from 'commander'

const program = new Command()
program.name('myapp').description('My tool').version('1.0.0')

program
  .command('serve')
  .description('Start server')
  .option('-p, --port <number>', 'port', 3000)
  .action((opts) => console.log(`Server running on port ${opts.port}`))

program.parse()
```

chalk, inquirer, commander — combine these three and you're a CLI artist. Even for internal tools, the gap between pleasant and painful is the gap between your coworkers loving you and hating you.

## 6. Log Aggregation — When You Have More Than One Server

### A Soul-Searching Question

You now have 10 servers. Each one has its own `app.log`.

A user reports: "I couldn't place an order yesterday at 3 PM." How do you investigate?

SSH into every single machine and grep?

By the time you've finished the third server, your boss has already tagged you in the chat five times. After all ten — half an hour's gone. The user has switched to a competitor.

This is why you need **centralized log management**. All logs from all servers aggregated in one place. One search box. Results in seconds.

Sounds like something only big companies need, right?

Wrong. Even with just two servers, you should centralize. Because when something breaks across two machines, the back-and-forth alone is already frustrating enough.

### ELK: The Three-Piece Suite

ELK is an acronym for three open-source tools:

**Elasticsearch** — Storage and search. A distributed database optimized for text search. You dump JSON into it, and it retrieves from billions of records in milliseconds.

**Logstash** — Processing pipeline. A data refinery. Takes raw logs from Filebeat, parses them, filters them, transforms them. Parses timestamps into standard format. Flattens nested JSON. Masks sensitive fields.

**Filebeat** — Collector. A tiny agent installed on every server. Stupidly lightweight. Does one thing: watches log files for new content, reads it, ships it to Logstash.

And one more that's not in the acronym but is essential:

**Kibana** — Visualization and search UI. Your browser-based dashboard for searching logs, building charts, and creating dashboards.

The data flow:

```
Your Node.js app → writes JSON to app.log
                         ↓
                  Filebeat detects new content
                         ↓
                  Logstash parses & filters
                         ↓
                  Elasticsearch stores & indexes
                         ↓
                  Kibana displays & searches
```

### Stand One Up in Five Minutes

Docker Compose gets you running locally:

```bash
git clone https://github.com/deviantony/docker-elk.git
cd docker-elk
docker-compose up -d
# Browser to http://localhost:5601
```

That's it. Your personal project can have a full logging platform. Don't think "this is for later" — it's literally five minutes away.

### What Library to Use on the Node.js Side

Two choices:

**Pino** — Fast. Roughly 10x faster than Winston. JSON output by default, zero config. If you don't need to simultaneously output to five different places, Pino is your pick.

**Winston** — Full-featured. Transport plugins for days — file, console, Elasticsearch, HTTP, MongoDB. Whatever output target you can think of, there's a transport for it.

```javascript
import pino from 'pino'

const logger = pino({
  level: process.env.LOG_LEVEL || 'info',
  base: { service: 'user-service' },
  timestamp: pino.stdTimeFunctions.isoTime,
})

logger.info({ userId: 'user_123' }, 'User logged in')
// {"level":30,"time":"2026-03-10T10:00:00.000Z","pid":1234,"service":"user-service","userId":"user_123","msg":"User logged in"}
```

Pino isn't fast because of dark magic. It's fast because it does less — more efficient serialization, no fancy formatting overhead. Less is more.

My recommendation: start with Pino. Understand what logging actually means first, then decide if you need Winston.

### How to Use Kibana

Once logs are in Elasticsearch, Kibana is your control panel.

Step 1: Create an "index pattern" — tell Kibana where your logs live. Usually `myapp-*` since you're creating daily indices like `myapp-2026.03.10`.

Step 2: Pick the time field, typically `@timestamp`.

Step 3: Search:

```
level: "error"                          → all errors
userId: "user_123"                      → everything this user did
level: "error" AND userId: "user_123"   → combined
@timestamp: [2026-03-09 TO 2026-03-10]  → time range
method: "POST" AND NOT status: 200      → all failed POSTs
```

This is a hundred times better than grep. grep searches for "lines containing this string." Kibana searches for "this field equals this value." The former matches accidentally. The latter is surgical.

You can also build dashboards:

- Error count per hour, line chart
- P50 / P90 / P99 latency distribution
- Top 10 most common error messages
- Request volume timeline

One big screen showing everything beats scrolling through a wall of logs any day.

## 7. Sentry — Make Errors Come Find You

### Logs Are Security Cameras. Sentry Is an Alarm.

Logs are passive. They're the surveillance tape. You don't look at it unless something's wrong.

Sentry is active. It's the alarm. Someone kicks in the door, the siren goes off immediately.

Specifically: you embed Sentry's SDK in your code. Whenever an uncaught exception occurs, the SDK automatically packages the error scene — stack trace, user info, request parameters, browser, OS version — and ships it to Sentry's server. The server deduplicates, aggregates, and notifies you via email, Slack, Discord, whatever.

Key capabilities:

**Automatic aggregation.** 1000 users hit the same bug? That's one Issue in Sentry, not 1000 notifications. Your phone doesn't turn into a vibrator.

**Source Maps.** Production code is minified — variables become a, b, c, everything's on one line. Sentry supports uploading source maps, which map error stacks back to your real filenames and line numbers. This feature has saved me more times than I can count.

**Automatic context collection.** User IP. Browser. OS. Current URL. Request parameters. You don't add any of this manually. The SDK grabs everything it can get its hands on.

### Integration Is A Few Lines

```bash
npm install @sentry/node
```

```javascript
import * as Sentry from '@sentry/node'

Sentry.init({
  dsn: 'https://your-dsn@sentry.io/project-id',
  environment: process.env.NODE_ENV || 'development',
  tracesSampleRate: process.env.NODE_ENV === 'production' ? 0.1 : 1.0,
})

// With Express, one line is enough
Sentry.setupExpressErrorHandler(app)
```

Every exception not caught by your try/catch blocks — Express's error handler grabs it, Sentry SDK automatically reports it.

Manual reporting is just as simple:

```javascript
try {
  await chargeUser(userId, amount)
} catch (err) {
  Sentry.captureException(err, {
    tags: { userId, action: 'charge' },
    extra: { amount, paymentMethod: 'alipay' },
  })
  throw err // report it, then keep throwing so upstream handlers can deal with it
}
```

### Self-Hosted vs Cloud

Sentry offers a free cloud tier. They also provide an open-source self-hosted version.

Cloud: zero maintenance, works immediately. Free tier covers small projects. The downside is your data lives on their servers.

Self-hosted: you control everything. But you need 8GB+ RAM. You need to handle upgrades. You need to maintain PostgreSQL, Redis, Kafka, and a bunch of other dependencies.

Most people's answer: start with the cloud. By the time your project is big enough to justify self-hosting, you'll know exactly whether you need it.

## 8. What Logging Doesn't Solve — The Three Pillars of Observability

I feel like I have to spell this out clearly.

Are logs a silver bullet?

Hell no. Not even close.

There are problems where you can dig through every log ever written and still not find the answer. Not because you didn't dig deep enough — because the answer was never in the logs to begin with.

### What Logs Are Good At

- Finding a specific user's specific operation
- Reconstructing a request's full journey (if you added traceId)
- Counting how many times an error type occurred
- Audit trails — "who did what to this data, and when"

### What Logs Are Bad At

**Slow performance degradation.**

Last week your API's average response time was 50ms. This week it's 80ms. Next month it'll be 150ms.

No errors anywhere in the logs. Everything's tagged `info`. The service looks perfectly healthy. But users are already feeling the slowness.

This kind of problem needs **metrics monitoring**. Collect P99 latency once per minute. Plot it on a line chart. The curve either goes up or it doesn't. You see it immediately.

**Cross-service bottleneck identification.**

A request comes in: gateway 10ms → user service 30ms → order service 100ms → payment service 2000ms.

Logs are scattered across four services. How do you know payment is the culprit?

You need **distributed tracing**. One traceId threaded through every service. Jaeger or SkyWalking draws each span's duration as a waterfall chart. Which span is longest? It's right there.

**Memory leaks.**

GC pauses get more frequent. Heap memory creeps upward. Individual log lines look completely normal — no errors, no stack traces. Two months later, on some random Tuesday at 3 AM: OOM.

You need **metrics monitoring** tracking the memory curve continuously. A curve that's been trending up for a month — that's your signal.

### The Three Pillars

Modern observability stands on three pillars. Miss one, and you're limping.

| Pillar  | Answers                  | Tools               |
| ------- | ------------------------ | ------------------- |
| Logs    | "What happened?"         | ELK, Loki           |
| Metrics | "Is the system healthy?" | Prometheus, Grafana |
| Traces  | "Why is it slow?"        | Jaeger, SkyWalking  |

Logs give you detail. Metrics give you trends. Traces give you bottlenecks.

These three don't replace each other. They complement each other. Like visiting a doctor — logs are your subjective description ("my stomach hurts"), metrics are your lab results ("blood pressure 130, heart rate 90"), and traces are the CT scan ("there's inflammation in the gastric lining").

## 9. A Judgment Framework For Yourself

Alright. By now you should understand what logging is about. But understanding and actually using it are two different things.

Here's a simple set of questions. Next time you add a log line to your project, ask yourself these:

**Question 1: Will this log help me at 3 AM?**

It's 3 AM. You've been paged. Can you locate the problem using only this log line?

If not — what's missing? User ID? Request parameters? Downstream service response? Duration? Add it.

**Question 2: Can I still search this log ten minutes from now?**

That `console.log` you threw into the terminal — gone when the server restarts. If you need this log line tomorrow morning, it has to be persisted. Either to a file, or straight into ELK.

**Question 3: Can this log connect to other logs?**

A single request in your system might cross API gateway → user service → order service → payment service. If order service throws an error, can you trace back through the requestId to see what happened in user service? Can you see what happened at the payment step?

No requestId? This log is an island.

**Question 4: Is there plaintext sensitive data in here?**

Passwords. Tokens. ID numbers. Bank cards. Check. Confirm there's none. Make it a habit: scan your log output before every push.

**Question 5: Is the log level right?**

Is debug turned off in production? Are you logging something as error that should be info? Are you logging something as info that should be warn?

**Question 6: How fast will I know something is wrong?**

Logs won't tell you on their own. Do you have Sentry for real-time alerts? Grafana for metrics dashboards? Distributed tracing set up?

**Question 7: Do I really need this much complexity?**

Not every project needs the ELK + Sentry + Prometheus full stack. Single-server hobby project? Pino + logrotate is plenty. Ten-server business? Add ELK. User base growing, errors increasing? Add Sentry. When you start doing performance optimization, you'll naturally know it's time for Prometheus and Jaeger.

**Don't deploy everything at once. Start with the thing that hurts most.**

## A Few Last Words

Logging, at the end of the day, is an investment.

You spend two hours now — swap out your logging library for Pino, output JSON, configure logrotate, spin up Docker ELK. Six months from now, on some random 3 AM, you locate the problem in ten minutes, fix it, and go back to sleep.

You take the shortcut now — random `console.log` lines, no log levels, everything dumped into one undifferentiated blob. Six months from now, on some random 3 AM, you stare at a wall of meaningless text and fight with it until sunrise.

The difference is that one 3 AM.

Don't wait until you need it to discover that you've been recording static this whole time.

Your logs are your security footage. Nobody watches it on a normal day. But when things go wrong, it's the last thing you have to hold onto. Record it well. Your future self will thank you.
