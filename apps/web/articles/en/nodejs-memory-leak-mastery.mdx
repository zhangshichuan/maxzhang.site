## First, You Gotta Know What Memory Looks Like

Let's get low-level for a minute. V8, the JavaScript engine shared by Chrome and Node.js, manages memory like a warehouse manager with OCD.

### The Stack: A Sticky Note in Your Hand

You're at a restaurant and the server scribbles on a pad: "Table 3, Kung Pao chicken, one bowl of rice." Customer leaves, that page gets torn off, the pad stays the same.

The stack is that pad.

```javascript
const name = 'John'
const age = 25
const isStudent = true
```

These things are small and certain. Use and toss. The OS handles it, you don't have to think about it. But it has one fatal flaw: **it's tiny**. You can't register an entire warehouse on a sticky note.

### The Heap: The Back Warehouse Nobody Wants to Clean

Big stuff — objects, arrays, Buffers, closures — all goes into the heap. Plenty of room, but nobody tidies up for you. That's where the Garbage Collector (GC) earns its keep.

```javascript
const user = { name: 'John', age: 25 } // heap
const scores = [98, 97, 100, 99] // heap
const buffer = Buffer.alloc(1024 * 1024) // heap, 1MB

function createCounter() {
  let count = 0 // this count lives on the heap too — the closure is holding it
  return () => ++count
}
```

Crucial insight: **variables on the stack are remote controls pointing to the heap**. Lose the remote, and whatever it was pointing at becomes garbage — unreachable by anyone.

### What's Inside the Heap

V8 slices the heap into five zones, like a warehouse split into produce, dry goods, and cold storage:

| Zone               | Official Name  | What Goes There                     | Personality                  |
| ------------------ | -------------- | ----------------------------------- | ---------------------------- |
| New Space          | New Generation | Freshly created short-lived objects | Small but cleaned frequently |
| Old Space          | Old Generation | Long-lived objects like caches      | Large but cleaned lazily     |
| Large Object Space | —              | Objects over a size threshold       | Skips regular GC             |
| Code Space         | —              | Compiled machine code               | Mostly ignore it             |
| Map Space          | —              | Object shape metadata               | V8's internal bookkeeping    |

New Space and Old Space are the two you actually need to watch. Think of them like a hotel's front desk versus the deep storage room:

- New Space = lobby: people come and go, swept daily
- Old Space = dusty shelves in the back: stuff sits there for months

Objects in New Space that survive two GC cycles get "promoted" to Old Space. An honorable retirement — but it also means they're harder to clean up.

## GC Isn't Magic, It's a Janitor

What does GC actually do? In one sentence: **it starts from a set of "definitely alive" root objects, follows every reference chain to mark everything reachable as "alive," then reclaims the rest.**

But here's the problem: if GC scanned the entire heap every time, your app wouldn't respond to anything during the sweep. That's how early V8 worked — "Stop the World." Everything freezes while I clean.

Not anymore. Modern V8 uses three clever tricks:

- **Incremental marking**: Don't scan all at once. Batch it out, weave it between your business logic. Like folding laundry while binge-watching a show — neither one gets blocked.
- **Concurrent marking**: Hire help. Spawn helper threads to scan alongside the main thread. The main thread keeps serving requests.
- **Parallel scavenging**: Once marking's done and it's time to clean, everyone pitches in to toss the trash.

The result? GC pauses went from "users noticeably feel the lag" to "you can't perceive it." Sub-millisecond territory.

### How New Space Gets Cleaned: Scavenge

Most objects in New Space are born and die fast. So V8 uses a brutal method: only move the living, ignore the dead.

Imagine a doormat that's too dirty. You get a new one. Transfer everything useful from the old mat to the new one. Throw the old mat away. Roles swap.

New Space is split into two equal halves: From and To. New objects land in From. When From gets full:

1. Copy surviving objects from From into To
2. From and To swap identities
3. All space in the old From is freed

Why is this brutal? **It doesn't clean the dead — it only moves the living.** Dead things vanish into nothing. And since most objects in New Space die young, there aren't many survivors. The copy is blazing fast.

### How Old Space Gets Cleaned: Mark-Sweep + Mark-Compact

You can't pull that move on Old Space. Too much stuff, too big. Moving it all would bankrupt you. So V8 goes old-school:

1. **Mark**: Starting from roots, walk every reference. Tick the living.
2. **Sweep**: Walk the entire space. Recycle everything without a tick.

But there's a catch: after sweeping, memory looks like it's been chewed up by a dog. Holes everywhere. A large object can't find a contiguous slot to fit into. So V8 occasionally kicks off **Mark-Compact** — shuffle all living objects to one side, squeeze out the holes, free everything past the boundary.

Compacting is expensive. V8 only does it when fragmentation gets bad enough.

### Oilpan: The 2026 New Toy

Here's a headache: some things in Node.js aren't JavaScript's responsibility. C++ objects backing `Buffer`, Native Addon memory — these used to live in a jurisdictional gray zone. Nobody cleaned them. That's where a lot of mysterious leaks came from.

In 2026, Node.js introduced **Oilpan** — a dedicated GC for C++ objects that coordinates with the main V8 GC. Those weird "external memory leaks" (where the `external` metric inexplicably climbs to several gigs) are now drastically reduced.

**Boundary: What Oilpan doesn't solve?**

It won't fix your code logic. If you wrote an infinitely-growing Map, Oilpan can't help you. It cleans up C++ objects that are "eligible for collection but nobody was collecting them" — not the mess in your JavaScript code.

## Five Ways to Die: Classic Memory Leak Scenarios

Alright, you've got the fundamentals. Now let's look at the scenarios that have actually bitten people in production. Don't skip to solutions — understand how the problem happens first. You can't cure a disease without understanding the cause.

### Scenario One: Closures — They Have a Memory

Closures are the most beautiful and most dangerous thing in Node.js. Beautiful because they "remember" the outer function's environment. Dangerous for exactly the same reason.

```javascript
function createLeakingClosure() {
  const hugeBuffer = Buffer.alloc(1024 * 1024 * 10) // 10MB

  return () => {
    // I only want the first byte of hugeBuffer
    // But the closure remembers the entire 10MB
    console.log(hugeBuffer[0])
  }
}

const leak = createLeakingClosure()
// 10MB gone. You don't "need" hugeBuffer anymore, but the closure doesn't know that.
```

Think of a closure as a photograph. You took a group photo and you only want your Aunt Lucy's face. But you can't extract just her face — you have to keep the entire photo. Same deal: the function inside the closure references one variable in the outer environment, so it has to keep the **entire outer environment** alive.

**How to think about this problem:**

Always ask: is this closure going to be held long-term? If yes, does anything it references contain large objects? Grab just what you need, kill the closure when you're done, or null out the big stuff manually.

```javascript
function createSafeClosure() {
  let hugeBuffer = Buffer.alloc(1024 * 1024 * 10)

  return () => {
    if (!hugeBuffer) return
    console.log(hugeBuffer[0])
    hugeBuffer = null // explicitly release
  }
}
```

### Scenario Two: EventEmitters — Waiters Who Won't Leave

Node.js runs on events. The EventEmitter is the backbone. But if you add a listener and never remove it — add a hundred, never remove them — add ten thousand — your process gets drowned in listeners.

```javascript
import { EventEmitter } from 'node:events'

const globalEmitter = new EventEmitter()

export async function handleRequest(req, res) {
  const onData = (data) => {
    console.log('received:', data)
  }

  globalEmitter.on('update', onData) // listener attached

  res.end('OK')
  // Forgot to remove it! Every request adds a new listener
  // 1000 requests = 1000 onData functions
  // Each onData might still reference request context
}
```

Picture this: you run a restaurant. Every time a customer walks in, you station a waiter next to them. Customer finishes and leaves — the waiter just stands there. A hundred customers come. A hundred waiters plant themselves, unmoving. Eventually the restaurant is packed with waiters and there's no room for new customers.

**Three ways out:**

```javascript
// Option one: remember to clean up
res.on('finish', () => {
  globalEmitter.off('update', onData)
})

// Option two: one-and-done
globalEmitter.once('update', (data) => {
  console.log('received:', data)
})

// Option three (recommended): AbortController — one kill switch, all gone
const controller = new AbortController()

emitter.on('data', handleData, { signal: controller.signal })

// When the request ends
controller.abort() // every listener bound to this signal gets wiped
```

### Scenario Three: Timers — The Signal That Never Stops

`setInterval` is the godfather of leaks. You create a timer, it runs forever unless you tell it to stop.

```javascript
function startTask(data) {
  const timer = setInterval(() => {
    process.send(data.status)
  }, 1000)
  // timer isn't saved, isn't cleared
}

startTask({ status: 'Task 1' })
startTask({ status: 'Task 2' })
// ...called 100 times
// 100 timers ticking simultaneously, 100 data objects unrecoverable
```

Like hiring 100 couriers to deliver hourly. Later you don't need that many couriers, but you forgot to cancel. They keep showing up. They keep ringing the bell.

Fixes: track the timer ID and clear it, use the new `signal`-aware API, or switch to recursive `setTimeout` — let it stop naturally when conditions are no longer met.

```javascript
// AbortController approach
const controller = new AbortController()

setInterval(() => process.send(data.status), 1000, { signal: controller.signal })

// When you're done
controller.abort()
```

### Scenario Four: Streams — Doors Left Open

Streams are gorgeous for large files. But forget to close one, and file descriptors and buffers leak.

```javascript
import fs from 'node:fs'

function processFile(filePath) {
  const stream = fs.createReadStream(filePath)

  stream.on('data', (chunk) => {
    processChunk(chunk)
  })
  // If something breaks mid-stream, the stream isn't destroyed
  // File descriptor stays open, buffer stays in memory
}
```

Like walking into a building, opening 50 doors to grab stuff, halfway through deciding you're in the wrong room, and moving on to open more doors. Doors keep piling up. You forgot to close the old ones. Eventually every door in the building is open.

Fixes: use `for await...of` or `pipeline`, which auto-close on errors. Or attach an `AbortController`.

```javascript
async function processFileSafely(filePath) {
  const stream = fs.createReadStream(filePath)

  try {
    for await (const chunk of stream) {
      await processChunk(chunk)
    }
  } catch (error) {
    stream.destroy()
  }
}
```

`pipeline` is even less work:

```javascript
import { pipeline } from 'node:stream/promises'
import { createGzip } from 'node:zlib'

async function compressFile(input, output) {
  try {
    await pipeline(fs.createReadStream(input), createGzip(), fs.createWriteStream(output))
  } catch (error) {
    // pipeline auto-closes all streams. you don't lift a finger.
  }
}
```

### Scenario Five: SSR Singleton Cache — The Server-Side Time Bomb

This is the most overlooked and most dangerous one. In SSR frameworks like Next.js and Nuxt.js, module-level variables are shared across all requests.

```javascript
// lib/auth.js — something your coworker wrote, at module scope
const userCache = new Map() // lives from process start to process death

export async function getUserData(userId) {
  if (userCache.has(userId)) return userCache.get(userId)

  const data = await fetchUserData(userId)
  userCache.set(userId, data) // shit, it only grows!
  return data
}
```

A Node.js process doesn't refresh like a browser tab. It runs for days, weeks, months. This `userCache` grows from day one and nobody ever cleans it.

First user visits? Add one entry.
Ten-thousandth user? Ten thousand entries.
Hundred thousand? Hundred thousand.
Eventually OOM, process dies, restart, repeat.

Caching is "trade space for time." But if you don't set a space limit, you're not trading — you're borrowing from a loan shark.

**Fixes:**

```javascript
// Option one: LRU cache, auto-evicts the oldest
import { LRUCache } from 'lru-cache'

const userCache = new LRUCache({
  max: 500,
  ttl: 1000 * 60 * 10, // 10-minute auto-expiry
})

// Option two: Redis — decoupled from process lifecycle
import { createClient } from 'redis'

const redis = createClient()

export async function getUserData(userId) {
  const cached = await redis.get(`user:${userId}`)
  if (cached) return JSON.parse(cached)

  const data = await fetchUserData(userId)
  await redis.setEx(`user:${userId}`, 600, JSON.stringify(data))
  return data
}
```

One iron rule: **in SSR, never store user-scoped data at module level.** Either discard it immediately or give it a hard capacity limit and expiration.

## Two New Weapons: Your Cleanup Automation

The good news: Node.js itself has been evolving. Some tools make resource management an order of magnitude simpler.

### AbortController: One Switch to Rule Them All

You don't need to memorize different cleanup APIs for different resource types anymore. Before: EventEmitter uses `off()`, timers use `clearInterval()`, Streams use `destroy()`, Fetch uses... wait, also `AbortController`. Remembering all these APIs itself consumed mental RAM.

Modern `AbortController` unifies everything:

```javascript
import { EventEmitter } from 'node:events'
import { setTimeout } from 'node:timers/promises'
import { Readable } from 'node:stream'

const controller = new AbortController()
const { signal } = controller

// Listeners
emitter.on('data', handler, { signal })

// Timers
setTimeout(5000, 'Time!', { signal })

// Streams
Readable.from([1, 2, 3], { signal })

// Request ends — flip the master switch, everything's gone
res.on('finish', () => {
  controller.abort()
})
```

Core idea: `controller.abort()` — one line, every resource bound to that signal gets cleaned up. You go from "remember every individual lock" to "flip one master breaker."

**Boundary: What AbortController doesn't solve?**

It solves the "forgetting to clean up" problem. But if you don't even know which resources need cleaning, it can't help you. It's a cleanup remote — it doesn't replace your judgment about _when_ resources should be released.

### FinalizationRegistry: Leak Early-Warning Radar

This API doesn't prevent leaks. It helps you **discover** them.

The idea is dead simple: tell V8 "If this object gets garbage collected, let me know." If you don't hear anything for a while, the object is still alive — possibly leaked.

```javascript
const registry = new FinalizationRegistry((heldValue) => {
  console.warn(`Object "${heldValue}" was collected normally`)
})

function createSession(userId) {
  const session = {
    id: Math.random().toString(36).slice(2),
    userId,
    data: Buffer.alloc(1024 * 1024),
  }

  registry.register(session, `Session_${session.id}`)
  return session
}

let session = createSession('UserA')
session = null // drop the reference

// If things are normal, GC runs and you see the console.warn
// If you wait and hear nothing, someone's still holding onto session
```

**Warning:** FinalizationRegistry callbacks are not guaranteed to fire. GC runs on its own schedule, and the process might exit before it gets around to it. This is a development-time probe — don't build critical production logic on it.

## How to Hunt Down a Leak: From Observation to Pinpoint

Now you know what leaks look like. But your service is running, memory's climbing — how do you find it?

### Step One: Confirm It's Actually a Leak

Not every memory uptick is a leak. Sometimes GC just hasn't gotten to it yet.

```bash
node --expose-gc app.js
```

```javascript
if (global.gc) {
  console.log('Before GC:', process.memoryUsage().heapUsed)
  global.gc() // force a full GC cycle
  console.log('After GC:', process.memoryUsage().heapUsed)
}
```

- Memory drops significantly after GC → no leak, just normal fluctuation
- Memory stays basically the same → **confirmed leak**

### Step Two: Snapshots and Comparison

Like a detective photographing a crime scene, you take one snapshot when memory is clean, let things run, take another, and see what grew.

```bash
node --inspect app.js
```

Open Chrome, go to `chrome://inspect`, switch to the Memory panel:

1. Take a snapshot right after startup
2. Simulate user traffic or load-test for a few minutes
3. Take another snapshot
4. Switch to **Comparison** view
5. Sort by Delta (increase)

Watch for these types blowing up:

- `(closure)` count skyrocketing → closure leaks
- `EventListener` multiplying → listener leaks
- `Buffer` accumulating → buffer leaks
- `Timeout` / `Immediate` growing → timer leaks

Two snapshot metrics you need to know:

- **Shallow Size**: how big the object itself is. Not counting what it references.
- **Retained Size**: the object + everything it references. This is the number that matters — it tells you how much memory gets freed if you delete this object.

### Step Three: Monitor the Curve

```javascript
setInterval(() => {
  const mem = process.memoryUsage()
  console.log({
    heapUsed: `${Math.round(mem.heapUsed / 1024 / 1024)}MB`,
    heapTotal: `${Math.round(mem.heapTotal / 1024 / 1024)}MB`,
    rss: `${Math.round(mem.rss / 1024 / 1024)}MB`,
    external: `${Math.round(mem.external / 1024 / 1024)}MB`,
  })
}, 10000)
```

A healthy memory curve looks like a sawtooth — GC periodically reclaims, memory bounces up and down.

A leaking curve is monotonic — it only goes up. A diagonal line, no teeth.

### Step Four: The Production Black Box

In production you can't casually stop the service to grab snapshots. That's where Diagnostic Reports come in.

```bash
node \
  --report-on-fatalerror \
  --report-on-signal \
  --report-signal=SIGUSR2 \
  app.js
```

When you OOM-crash, a report is auto-generated. What's inside? Heap distribution, resource limits, JS and C++ stack traces, all libuv handles. Getting that report is like getting the surveillance footage of the crime scene — you don't need to reproduce the problem. The evidence is already saved.

Trigger manually:

```bash
kill -USR2 <pid>
```

## Don't Memorize — Ask Yourself These Questions

I'm not going to end with a "summary." Summaries are how authors outsource the thinking. Here's a set of questions instead. Answer them honestly. If you can, you actually understand this stuff.

**Code level:**

1. Will this closure be held long-term? Does anything it references contain large objects?
2. This EventEmitter listener — when does it get removed?
3. This timer — when does it stop? Is there a code path where it never gets cleared?
4. Will this Stream close on the error path, not just the happy path?
5. This module-level Map / Set / Array — does it have a capacity limit and an expiry?
6. Can I consolidate cleanup into one `AbortController` instead of scattered individual calls?

**Investigation level:**

1. After forcing GC, is memory still high? If not, it's not a leak.
2. Comparing two snapshots — which object types are growing?
3. Is the memory curve sawtooth or diagonal-up?
4. Confirmed with external tools (clinic.js, heapdump)?
5. Production environment configured with Diagnostic Reports?

**Monitoring level:**

1. Is Prometheus tracking `nodejs_heap_used_bytes`?
2. Are alert thresholds set? (e.g., 20% growth sustained for 15 minutes)
3. Is there a warning before hitting the container memory limit?
4. Have you run a 4+ hour load test to see the long-term curve?

If you can answer every one of these, you don't need to memorize anything. If some make you think "huh, never thought about that" — that's what you tackle next week.

---

Here's the thing about memory leaks: once you truly understand them, they stop being mysterious. At their core, it's just "something you don't need anymore, but someone's still holding onto it." GC can only clean up garbage it can no longer find. Give something a permanent reference, and GC can't touch it.

Good code habits aren't about "remember to clean up every type of resource." They're about "write cleanup next to creation." Creation and destruction should be managed in the same place. If every middleware has a rogue `setInterval`, every handler has a naked `EventEmitter.on`, you'll never keep track of what needs cleaning. Consolidate them under one controller and clear them with a single shot.

That's it. You should be able to go fix that service that crashes every three days now.
