> This isn't a documentation translation. This is a postmortem. I'm writing down every mistake I made building three enterprise NestJS projects, every line of code that survived production, every realization that came at 2am staring at a screen.

It was 2am. I sent a message to the company group chat: "Don't deploy. The database field type changed. Frontend hasn't synced yet."

The moment I hit send, I knew I wasn't sleeping that night.

What happened was simple. A backend dev changed an endpoint — `userId` went from `number` to `string`. Seemed trivial. Just a type, right? But the frontend code had `number` annotations everywhere. TypeScript compiled fine during build — you're getting JSON, type annotations don't participate in runtime validation at all.

Two hours after the deploy, users started reporting bugs. Payment records wouldn't load. Profile pages threw errors. Took forever to trace it back to this one type mismatch.

Fuck.

I've been through this too many times. And it's not your fault — it's how frontend-backend collaboration works in the traditional stack. Type information evaporates at the API boundary. Backend changes a return type, frontend doesn't know, the bug lies dormant until production.

That's why I bet on full-stack TypeScript. Not because I chase shiny new toys — because I got burned by type gaps one too many times.

This article is everything I figured out. From config to deploy. From monolith to microservices. No documentation translation, no abstract "best practices." Every conclusion has scars behind it.

You don't need to read it all at once. Pick the part that's hurting you right now.

## One: When You're Done With Type Mismatches

Let me start with something you can use next week.

tRPC does one thing: it auto-derives backend types to the frontend. No shared interface files to maintain manually. No syncing across teams. Backend is the source of truth — frontend follows automatically.

```typescript
// Backend
const appRouter = router({
  userById: publicProcedure.input(z.string()).query(({ input }) => {
    return { id: input, name: 'John', email: 'john@example.com' }
  }),
})

export type AppRouter = typeof appRouter
```

```typescript
// Frontend — nothing to write
const user = await trpc.userById.query('abc-123')
// user is auto-inferred as { id: string; name: string; email: string }
```

Backend changes a return field? Frontend build breaks immediately. Never reaches runtime.

But tRPC isn't a magic bullet. Here's what it doesn't solve:

- You need to talk to external systems (third-party APIs, mobile apps) — tRPC's protocol isn't universal
- Your frontend is React Native / Flutter / Swift — tRPC won't work
- Your team hates abstraction layers — forcing tRPC will just create resentment

That's where Zod comes in. It's a runtime validation library that also derives TypeScript types:

```typescript
import { z } from 'zod'

const CreateUserSchema = z.object({
  username: z.string().min(3).max(20),
  email: z.string().email(),
  age: z.number().min(0).max(150),
})

type CreateUserDto = z.infer<typeof CreateUserSchema>

const result = CreateUserSchema.safeParse(req.body)
if (!result.success) {
  return { code: 400, errors: result.error.flatten() }
}
```

TypeScript types vanish after compilation. Zod is your last line of defense — any user input, any external API response, must pass through it.

NestJS's `class-validator` + `class-transformer` do the same job. Zod's advantage: no decorator classes needed, one schema file shared across projects.

One rule to remember: **compile-time type checking + runtime schema validation. Miss either and you're asking for trouble.** Types aren't decoration. They're body armor.

## Two: The NestJS Mental Model — See the Whole Board First

First time you open the NestJS docs — Module, Controller, Provider, Decorator, Dependency Injection — your brain goes blank. Normal. Mine did too.

Then it clicked: NestJS isn't an Express upgrade. It's an architectural framework. Express gives you bricks — build however you want. NestJS gives you reinforced concrete — there are rules, but follow them and it'll hold a hundred floors.

### 2.1 Three Paradigms in One Framework

NestJS has three programming paradigms running simultaneously.

**OOP** — the skeleton. Modules, controllers, services are all classes. Inherit, encapsulate, polymorph.

```typescript
export abstract class BaseCrudService<T> {
  constructor(protected readonly repository: Repository<T>) {}

  async findAll(): Promise<T[]> {
    return this.repository.find()
  }

  abstract validateCreate(dto: unknown): T
}
```

**FP** — pipes and interceptors as composition. A request flows through layers of Pipes, each doing one thing, composed together.

**FRP** — RxJS handling async streams. We'll get to this later. For now just know those `pipe()` calls everywhere aren't decoration — they're actually composing async operations.

You don't need to master all three at once. OOP is mandatory — understand classes and DI. FP and FRP can come later.

### 2.2 AOP: The Restaurant's Accounting System

AOP sounds abstract. Let me tell you a story.

You go to a restaurant. Order, eat, pay — that's the "business logic."

But there's a rule: every transaction, no matter who or what was ordered, gets logged to the accounting system. This "accounting" has nothing to do with eating, but every table triggers it. That's a cross-cutting concern.

In your backend, these cross-cutting concerns are everywhere: logging, authentication, desensitization, unified error formatting. If you write this code inside every controller method, 60% of your business code becomes monitoring, auth, logging, sanitization — how the hell do you maintain that?

NestJS handles this with four mechanisms:

| Mechanism    | What it does                      | Restaurant analogy             |
| ------------ | --------------------------------- | ------------------------------ |
| Middleware   | Before the request enters routes  | Health check at the door       |
| Guards       | Decides if the request gets in    | Security checking your badge   |
| Interceptors | Before and after method execution | Logging every dish ordered     |
| Pipes        | Validation and transformation     | Kitchen inspecting ingredients |
| Filters      | After an exception is thrown      | Complaint handling process     |

AOP isn't mystical. It's just pulling "stuff every request needs but isn't business logic" out of your business code.

### 2.3 Dependency Injection: Why Everything Gets "Passed In"

In Express you write:

```typescript
app.get('/users', (req, res) => {
  const db = new Database()
  const userService = new UserService(db)
  res.json(userService.findAll())
})
```

You new it. You pass it. You manage its lifecycle.

In NestJS:

```typescript
@Controller('users')
export class UserController {
  constructor(
    private readonly userService: UserService,
    private readonly auditService: AuditService,
  ) {}

  @Get()
  findAll() {
    return this.userService.findAll()
  }
}
```

Where does `userService` come from? Nobody new'd it.

Answer: **NestJS's IoC container new'd it and injected it into your constructor.**

Why? Three reasons:

1. **Testable** — inject a fake `UserService` in tests, no real database needed
2. **Decoupled** — Controller depends on Service's interface, not implementation. Swap implementations without touching Controller
3. **Lifecycle** — you don't worry about singleton vs request-scoped. The container handles it

It feels weird at first. After a week, going back to `new Database()` feels wrong. Like getting used to running water and then having to draw from a well.

### 2.4 Decorators: Sticky Notes on Your Code

A decorator is just a function called at class/method/property definition time. NestJS uses them to declare metadata without touching your code:

```typescript
function Injectable(): ClassDecorator {
  return (target: any) => {
    Reflect.defineMetadata('design:paramtypes', [UserRepository], target)
    // Container reads this, knows to inject UserRepository
  }
}
```

The ones you'll use: `@Module()`, `@Controller()`, `@Injectable()`, `@Get()`, `@Post()`, `@Param()`, `@Body()`, `@UseGuards()`.

You can write your own:

```typescript
export const CurrentUser = createParamDecorator(
  (data: unknown, ctx: ExecutionContext) => {
    return ctx.switchToHttp().getRequest().user
  },
)

@Get('profile')
getProfile(@CurrentUser() user: User) {
  return user
}
```

### 2.5 Layer Responsibilities — Iron Rules

```
AppModule
├── AuthModule
│   ├── AuthController  → routing layer
│   ├── AuthService     → business logic layer
│   └── UserModule      → sub-module
├── ConfigModule
├── DatabaseModule
└── CacheModule
```

- **Controller**: receives requests, calls Service, returns response. **Never write business logic. Ever.**
- **Service**: pure business logic. Called by Controllers, other Services, even microservices.
- **Module**: organizational unit — declares what controllers and services it has, what it imports and exports.

I've seen too many projects with 200 lines of SQL in a Controller. That's not a NestJS problem — it's not understanding the framework's design intent.

## Three: Making Your App Alive in Different Environments

An enterprise project can't have one config. Dev connects to local DB, production to RDS. Dev logs to console, production to Elasticsearch.

Screw up config management and production incidents are just a matter of time.

### 3.1 Environment Variables Done Right

```bash
pnpm add @nestjs/config
```

```typescript
@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,
      envFilePath: [`.env.${process.env.NODE_ENV || 'development'}`, '.env'],
      validationSchema: validationSchema,
    }),
  ],
})
export class AppModule {}
```

`isGlobal: true` matters. Without it, each of your 20 modules needs its own `imports: [ConfigModule]`. It'll drive you insane.

File priority: earlier in the array wins. `NODE_ENV=production` reads `.env.production` first, `.env` as fallback.

### 3.2 Joi Startup Validation — Fail Fast

Worst case scenario: deploy to production, run for an hour, then discover a missing env var. Your app shouldn't silently run with `undefined` — it should blow up at startup.

```typescript
import * as Joi from 'joi'

const validationSchema = Joi.object({
  NODE_ENV: Joi.string().valid('development', 'production', 'test').default('development'),
  PORT: Joi.number().default(3000),
  DATABASE_HOST: Joi.string().required(),
  DATABASE_PORT: Joi.number().default(5432),
  DATABASE_USER: Joi.string().required(),
  DATABASE_PASSWORD: Joi.string().required(),
  DATABASE_NAME: Joi.string().required(),
  REDIS_HOST: Joi.string().required(),
  REDIS_PORT: Joi.number().default(6379),
  JWT_SECRET: Joi.string().min(32).required(),
  JWT_EXPIRES_IN: Joi.string().default('7d'),
})
```

Forgot `DATABASE_PASSWORD`? App immediately yells: `"DATABASE_PASSWORD" is required` — fails at startup, not hours later when DB connections fail. That's a safe failure.

## Four: Logging — Your Black Box in Production

Once you're live, logs are everything you depend on. Bug? Look at logs. Slow? Look at logs. Under attack? Look at logs.

I started with `console.log`. Fine in dev. In production — logs had everything and nothing at the same time. No structure. Searching one user's actions means scrolling hundreds of lines.

### 4.1 Why Pino

| Solution        | Throughput | Structured   | Use case                |
| --------------- | ---------- | ------------ | ----------------------- |
| Pino            | Extreme    | Native JSON  | Production first choice |
| Winston         | Medium     | Needs config | Complex transport needs |
| NestJS built-in | Low        | Weak         | Demos, local dev        |

Pino's fast because it's async and uses optimized schema serialization instead of `JSON.stringify`. At high QPS the difference is massive.

```bash
pnpm add nestjs-pino pino-http pino-pretty
```

```typescript
LoggerModule.forRoot({
  pinoHttp: {
    transport:
      process.env.NODE_ENV !== 'production' ? { target: 'pino-pretty', options: { colorize: true } } : undefined,
    level: process.env.NODE_ENV === 'production' ? 'info' : 'debug',
    autoLogging: false,
    serializers: {
      req: (req) => ({
        method: req.method,
        url: req.url,
        // Never log headers or body — passwords end up in logs
      }),
    },
  },
})
```

### 4.2 How to Log Properly

```typescript
// Wrong — string interpolation
this.logger.info(`User ${email} created successfully`)

// Right — context as first object argument
this.logger.info({ userId: user.id, email: dto.email }, 'User created successfully')
```

Why? Log systems search structured data infinitely faster than string-matching. Searching `email: "xxx"` is exact. Searching "User xxx created" is regex-scraping strings.

Three rules: block sensitive fields at the serializer, put context in the structured object, keep the message string for human reading only.

### 4.3 If You're Already on Winston

```typescript
WinstonModule.forRoot({
  transports: [
    new transports.Console({/* ... */}),
    new transports.DailyRotateFile({
      filename: 'logs/error-%DATE%.log',
      level: 'error',
      maxFiles: '30d',
    }),
  ],
})
```

Winston's fine. Just not as fast. Under 1000 QPS, the difference barely matters. Use what your team knows.

## Five: Filters, CORS, Prefix — Foundation Work

These configs touch every request. Get them right from the start.

### 5.1 Unified Error Response Format

What frontend devs hate most: same endpoint returns `{ data: ... }` on success and `{ statusCode: 400, message: '...' }` on failure — two different shapes, two different parsing paths.

```typescript
@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
  catch(exception: HttpException, host: ArgumentsHost) {
    const ctx = host.switchToHttp()
    const response = ctx.getResponse<Response>()
    const request = ctx.getRequest<Request>()
    const status = exception.getStatus()
    const exceptionResponse = exception.getResponse()
    const message =
      typeof exceptionResponse === 'string' ? exceptionResponse : (exceptionResponse as any).message || 'Unknown error'

    response.status(status).json({
      code: status,
      message,
      timestamp: new Date().toISOString(),
      path: request.url,
    })
  }
}

@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost) {
    const ctx = host.switchToHttp()
    const response = ctx.getResponse()
    const request = ctx.getRequest()
    this.logger.error({ err: exception, url: request.url, ip: request.ip }, 'Uncaught exception')
    response.status(500).json({
      code: 500,
      message: 'Internal server error',
      timestamp: new Date().toISOString(),
      path: request.url,
    })
  }
}
```

Frontend always gets the same shape: `{ code, message, timestamp, path, data? }`. They just check `code`. Done.

### 5.2 CORS and Prefix

```typescript
app.enableCors({
  origin:
    process.env.NODE_ENV === 'production'
      ? ['https://yourdomain.com']
      : ['http://localhost:3000', 'http://localhost:5173'],
  credentials: true,
})

app.setGlobalPrefix('api', { exclude: ['health'] })
```

Production CORS must be a whitelist. `origin: '*'` with `credentials: true` is a broken config waiting to bite you.

### 5.3 API Versioning

```typescript
app.enableVersioning({
  type: VersioningType.URI,
  defaultVersion: ['1'],
})

@Controller({ path: 'users', version: ['1', '2'] })
export class UserController {
  @Get()
  findAll() {}

  @Version('2')
  @Get('stats')
  getStats() {}
}
```

`/api/v1/users` is the old endpoint. `/api/v2/users/stats` is the new one. Clients migrate gradually. You don't need to beg everyone to upgrade simultaneously.

## Six: Build and Test — Make CI Not Suck

### 6.1 SWC: Rust-Powered Compilation

NestJS defaults to `tsc`. Fine locally. CI/CD crawls. SWC can cut compilation time to 1/10th.

```bash
pnpm add -D @swc/cli @swc/core
```

```json
{
  "compilerOptions": {
    "builder": "swc",
    "typeCheck": true,
    "deleteOutDir": true
  }
}
```

`typeCheck: true` is critical — SWC compiles, doesn't type-check. Turn it off and type errors silently pass through to production.

### 6.2 Vitest: An Order of Magnitude Faster Than Jest

Jest is good. Just slow. Vitest uses esbuild for transforms, native ESM, crushes on speed.

```bash
pnpm add -D vitest @swc-node/register unplugin-swc
```

The classic NestJS test pattern — TestingModule creates an isolated container:

```typescript
describe('UserService', () => {
  let service: UserService

  const mockRepository = {
    find: vi.fn(),
    findOne: vi.fn(),
    save: vi.fn(),
  }

  beforeEach(async () => {
    const module = await Test.createTestingModule({
      providers: [UserService, { provide: getRepositoryToken(User), useValue: mockRepository }],
    }).compile()

    service = module.get<UserService>(UserService)
  })

  it('should return all users', async () => {
    const mockUsers = [{ id: 1, name: 'John' }]
    mockRepository.find.mockResolvedValue(mockUsers)
    const result = await service.findAll()
    expect(result).toEqual(mockUsers)
    expect(mockRepository.find).toHaveBeenCalledTimes(1)
  })
})
```

Inject mock Repository. No real database. Tests run fast, so you write more of them.

## Seven: Caching — A Restaurant Needs a Fridge

A cacheless app is like a restaurant without a fridge. Every customer means buying fresh ingredients, washing, chopping, cooking from scratch. Traffic spikes and the kitchen (database) collapses.

### 7.1 Redis Client Choice

| Solution                | Pros                             | Cons               |
| ----------------------- | -------------------------------- | ------------------ |
| ioredis                 | Native Promise, great clustering | Slightly larger    |
| node-redis (v4+)        | Official maintenance             | Less intuitive API |
| @nestjs-modules/ioredis | NestJS native integration        | Thicker wrapper    |

I recommend ioredis — its API fits real-world scenarios better, cluster config is simpler.

```bash
pnpm add @nestjs-modules/ioredis ioredis
```

```typescript
RedisModule.forRoot({
  type: 'single',
  url: `redis://:${process.env.REDIS_PASSWORD}@${process.env.REDIS_HOST}:${process.env.REDIS_PORT}`,
  options: {
    maxRetriesPerRequest: 3,
    retryStrategy(times) {
      return Math.min(times * 50, 2000)
    },
  },
})
```

### 7.2 Two-Level Cache: LRU + Redis

Redis is fast but still goes over the network. Dictionary tables, config items — frequently accessed, rarely changed — add an in-memory LRU layer for another magnitude of performance.

```typescript
const memoryCache = createKeyv('cache-manager://store/memory', {
  max: 1000,
  ttl: 60000,
})

const redisCache = createKeyv({
  store: new KeyvRedis({
    url: `redis://:${process.env.REDIS_PASSWORD}@${process.env.REDIS_HOST}:${process.env.REDIS_PORT}`,
  }),
})

CacheModule.register({
  stores: [memoryCache, redisCache], // Check memory first, then Redis
  isGlobal: true,
})
```

### 7.3 Two Iron Rules

**One: always actively invalidate cache after writes.** Don't rely on TTL expiry.

```typescript
async updateUser(id: number, dto: UpdateUserDto) {
  const result = await this.userRepo.update(id, dto)
  await this.cacheManager.del(`user:${id}`)
  return result
}
```

**Two: keep a bypass switch.** Debugging needs direct DB access:

```typescript
async findById(id: number, useCache = true): Promise<User | null> {
  const cacheKey = `user:${id}`
  if (useCache) {
    const cached = await this.cacheManager.get<User>(cacheKey)
    if (cached) return cached
  }
  const user = await this.userRepo.findOne({ where: { id } })
  if (user) await this.cacheManager.set(cacheKey, user, 60000)
  return user
}
```

That `useCache` parameter has saved me many times.

## Eight: Sending Email — Don't Roll Your Own

Registration verification, password resets, notifications. Every enterprise app sends email.

I've seen a team set up a dedicated email server. Within a month, every outgoing email landed in spam. No IP warmup, no reputation, ESPs rejecting everything. This is not your business's problem to solve.

### 8.1 Provider Choice

| Provider          | Pros                          | Cons                    |
| ----------------- | ----------------------------- | ----------------------- |
| AWS SES           | Cheap, great AWS integration  | Strict approval process |
| Mailgun           | Nice API, high deliverability | Small free tier         |
| SendCloud         | Good domestic delivery (CN)   | Bad internationally     |
| Nodemailer (self) | Full control                  | Maintenance hell        |

For most cases: **AWS SES + Nodemailer as transport**:

```bash
pnpm add @nestjs-modules/mailer nodemailer @aws-sdk/client-ses
```

```typescript
MailerModule.forRoot({
  transport: {
    SES: new SES({
      region: process.env.AWS_REGION,
      credentials: {
        accessKeyId: process.env.AWS_ACCESS_KEY_ID!,
        secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY!,
      },
    }),
  },
  defaults: { from: '"System" <noreply@yourdomain.com>' },
  template: {
    dir: path.join(__dirname, '..', 'templates', 'emails'),
    adapter: new HandlebarsAdapter(),
    options: { strict: true },
  },
})
```

### 8.2 Never Block Users on Email Failure

```typescript
async sendWelcomeEmail(to: string, username: string) {
  try {
    await this.mailerService.sendMail({ to, subject: 'Welcome', template: 'welcome', context: { username } })
    this.logger.info({ to }, 'Welcome email sent')
  } catch (error) {
    this.logger.error({ err: error, to }, 'Welcome email failed')
    // Email failure is not registration failure — dead-letter to a retry queue
  }
}
```

**Never block a user's business flow because an email failed.** Log it. Queue it for retry. User registering and getting a 500 because of an email is a terrible experience.

## Nine: Database and ORM — The Chapter Where Mistakes Cost the Most

This is the most fucking important chapter. Wrong ORM choice is the most expensive mistake in the whole project. Wrong database architecture, by the time you realize it, you can't go back.

### 9.1 ORM Choice

| ORM      | Strengths                                | Weaknesses                                     |
| -------- | ---------------------------------------- | ---------------------------------------------- |
| TypeORM  | Best NestJS support, decorator style     | Weak type inference, controversial APIs        |
| Prisma   | Excellent type safety, strong migrations | Extra abstraction layer, opaque generated code |
| Mongoose | MongoDB de facto standard                | MongoDB only                                   |
| MikroORM | Modern design, good inference            | Smaller community than TypeORM                 |

**Recommendation**: relational databases (PG/MySQL), new projects — **Prisma**. Team already comfortable with NestJS decorator style — **TypeORM** is fine. MongoDB — **Mongoose**, no debate.

### 9.2 TypeORM Integration

```typescript
TypeOrmModule.forRootAsync({
  imports: [ConfigModule],
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({
    type: 'postgres',
    host: config.get<string>('DATABASE_HOST'),
    port: config.get<number>('DATABASE_PORT'),
    username: config.get<string>('DATABASE_USER'),
    password: config.get<string>('DATABASE_PASSWORD'),
    database: config.get<string>('DATABASE_NAME'),
    entities: [User, Role, Permission],
    synchronize: config.get('NODE_ENV') !== 'production',
    logging: config.get('NODE_ENV') === 'development',
    extra: { max: 20, idleTimeoutMillis: 30000, connectionTimeoutMillis: 2000 },
  }),
})
```

**`synchronize: true` in production is a disaster.** It auto-modifies table schemas. One wrong config and it drops columns, loses data. I've warned so many teams — some listened, some paid the tuition first.

### 9.3 Multi-Database — Multi-Tenant

```typescript
@Injectable()
export class MultiDatabaseService implements OnApplicationShutdown {
  private dataSources = new Map<string, DataSource>()

  async getDataSource(tenantId: string): Promise<DataSource> {
    if (this.dataSources.has(tenantId)) {
      const ds = this.dataSources.get(tenantId)!
      if (ds.isInitialized) return ds
    }
    const tenantConfig = await this.loadTenantConfig(tenantId)
    const dataSource = new DataSource({
      type: 'postgres',
      host: tenantConfig.host,
      port: tenantConfig.port,
      username: tenantConfig.username,
      password: tenantConfig.password,
      database: tenantConfig.database,
      entities: [User, Order],
      synchronize: false,
    })
    await dataSource.initialize()
    this.dataSources.set(tenantId, dataSource)
    return dataSource
  }

  async onApplicationShutdown() {
    for (const [tenantId, ds] of this.dataSources) {
      if (ds.isInitialized) await ds.destroy()
    }
  }
}
```

Distinguish two concepts:

1. **ORM connection pool**: TypeORM internally manages multiple connections to the same DB (pooling)
2. **DataSource Map**: your hand-managed multi-DB router (tenant routing)

They're not the same thing. One pools, one routes.

### 9.4 Prisma Integration

```bash
pnpm add prisma @prisma/client
npx prisma init
```

```prisma

  provider = "postgresql"
  url      = env("DATABASE_URL")

  provider = "prisma-client-js"

```

```typescript
@Global()

  providers: [PrismaService],
  exports: [PrismaService],
})
export class PrismaModule {}

@Injectable()

  async onModuleInit() {
```

Prisma's schema file IS your database documentation. Change the schema, run `prisma migrate dev`, auto-generate migration files. Everyone on the team can read the database structure — no reverse-engineering from code.

### 9.5 Connection Pool Formula

PostgreSQL defaults to max 100 connections. 5 Pods at `max: 20` = 100, perfect. 5 Pods at `max: 50` = 250 — exceeds limit, new connections rejected.

Formula: `max = (DB max connections / service instances) × 0.8`. Leave 20% headroom for admin operations.

## Ten: RxJS — Treat Async as Collections

Lots of people complain about RxJS in NestJS: "My Promises work fine, why learn this?"

I thought the same. Then one requirement changed my mind.

A search box: debounce input, skip duplicate values, cancel old requests on new input. Traditional approach:

```typescript
let timer: NodeJS.Timeout
inputElement.addEventListener('input', (e) => {
  clearTimeout(timer)
  timer = setTimeout(() => search(e.target.value), 300)
})
```

Three operations and the code is already messy. Add "cancel previous request" and "deduplication" — it becomes unreadable.

RxJS:

```typescript
fromEvent(inputElement, 'input')
  .pipe(
    map((e) => e.target.value),
    debounceTime(300),
    distinctUntilChanged(),
    switchMap((keyword) => this.searchService.search(keyword)),
  )
  .subscribe((results) => this.displayResults(results))
```

Declarative. Debounce, deduplicate, cancel old — three pipe operators. Think of RxJS as "Lodash for async events."

### 10.1 DB Disconnect Retry

```typescript
findByIdWithRetry(id: number) {
  return from(this.userRepo.findOne({ where: { id } })).pipe(
    retry({
      count: 3,
      delay: (_, retryCount) =>
        new Promise((resolve) => setTimeout(resolve, Math.pow(2, retryCount - 1) * 1000)),
    }),
    catchError((error) => {
      console.error('Retries exhausted, query failed', error)
      return throwError(() => new Error('Service temporarily unavailable'))
    }),
  )
}
```

What this does: query DB → on failure retry 3 times → exponential backoff (1s/2s/4s) → exhausted, degrade with error. Without RxJS you'd need a for loop, a pile of try-catches, manual timers.

## Eleven: Authentication — Where You Get Hacked

Auth is the front door. Do it wrong and data leaks, privilege escalation, session hijacking all queue up waiting for you.

### 11.1 Three Lines of Defense: Validation

```bash
pnpm add class-validator class-transformer
```

```typescript
export class RegisterDto {
  @IsEmail({}, { message: 'Invalid email format' })
  email: string

  @IsString()
  @MinLength(8)
  @MaxLength(32)
  @Matches(/^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)/, { message: 'Password requires upper, lower, and digit' })
  password: string

  @IsString()
  @MinLength(1)
  @MaxLength(20)
  username: string
}
```

```typescript
app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,
    forbidNonWhitelisted: true,
    transform: true,
    transformOptions: { enableImplicitConversion: true },
  }),
)
```

`whitelist: true` is a security requirement. Without it, attackers can stuff arbitrary fields into requests. Someday a forgotten field will enable privilege escalation.

### 11.2 Passport + JWT

```bash
pnpm add @nestjs/passport passport @nestjs/jwt passport-jwt passport-local
pnpm add -D @types/passport-jwt @types/passport-local
```

```typescript
@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor(private readonly configService: ConfigService) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      ignoreExpiration: false,
      secretOrKey: configService.get<string>('JWT_SECRET'),
    })
  }

  async validate(payload: JwtPayload): Promise<User> {
    const user = await this.userService.findById(payload.sub)
    if (!user) throw new UnauthorizedException('User not found')
    if (!user.isActive) throw new UnauthorizedException('User is disabled')
    return user
  }
}
```

### 11.3 Guard vs Middleware

Middleware doesn't know what comes after `next()`. Guards have `ExecutionContext` — they know which Controller, which method, what decorators:

```typescript
@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {
  constructor(private readonly reflector: Reflector) {
    super()
  }

  canActivate(context: ExecutionContext): boolean | Promise<boolean> | Observable<boolean> {
    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
      context.getHandler(),
      context.getClass(),
    ])
    if (isPublic) return true
    return super.canActivate(context)
  }
}

export const IS_PUBLIC_KEY = 'isPublic'
export const Public = () => SetMetadata(IS_PUBLIC_KEY, true)

@Public()
@Post('register')
async register(@Body() dto: RegisterDto) { }

// Global registration
providers: [{ provide: APP_GUARD, useClass: JwtAuthGuard }]
```

### 11.4 Argon2 — The Only Answer for Password Hashing

```bash
pnpm add argon2
```

```typescript
async hashPassword(password: string): Promise<string> {
  return argon2.hash(password, {
    type: argon2.argon2id,
    memoryCost: 65536,
    timeCost: 3,
    parallelism: 4,
  })
}

async verifyPassword(hash: string, password: string): Promise<boolean> {
  return argon2.verify(hash, password)
}
```

Stop using bcrypt. Argon2 won the 2015 Password Hashing Competition. It resists both GPU and ASIC attacks. OWASP's top recommendation. Configurable memory cost — brute-force cost multiplies drastically.

### 11.5 Response Desensitization — Passwords Never Leave the Server

```typescript
@Entity()
export class User {
  @PrimaryGeneratedColumn() id: number

  @Column() @Exclude()
  password: string

  @Column() name: string
}

@UseInterceptors(ClassSerializerInterceptor)
@Get('profile')

}
```

Add `@Exclude()` to your Entity. Set it and forget it. The three lines you should never skip.

## Twelve: Authorization — What You Can Do Matters More Than Who You Are

Authentication says "who you are." Authorization says "what you can do." Mix them together and when you need multiple roles and fine-grained permissions, if-else statements are scattered across dozens of files.

### 12.1 RBAC — Covers 80%

Define roles → assign permissions to roles → assign roles to users.

```typescript
@Entity()
export class Permission {
  @PrimaryGeneratedColumn() id: number
  @Column({ unique: true }) name: string // 'user:create', 'user:read'
}

@Entity()
export class Role {
  @PrimaryGeneratedColumn() id: number
  @Column({ unique: true }) name: string // 'admin', 'editor'
  @ManyToMany(() => User, (user) => user.roles) users: User[]
}
```

```typescript
export const RequirePermissions = (...permissions: string[]) =>
  SetMetadata(PERMISSIONS_KEY, permissions)

@Injectable()
export class PermissionGuard implements CanActivate {
  async canActivate(context: ExecutionContext): Promise<boolean> {
    const requiredPermissions = this.reflector.getAllAndOverride<string[]>(PERMISSIONS_KEY, [
      context.getHandler(),
      context.getClass(),
    ])
    if (!requiredPermissions) return true
    const { user } = context.switchToHttp().getRequest()
    const userPermissions = await this.authService.getUserPermissionNames(user.id)
    return requiredPermissions.some((perm) => userPermissions.includes(perm))
  }
}

@RequirePermissions('user:create', 'user:read')
@Post()
createUser(@Body() dto: CreateUserDto) { }

// Order matters — JWT first, permissions second
providers: [
  { provide: APP_GUARD, useClass: JwtAuthGuard },
  { provide: APP_GUARD, useClass: PermissionGuard },
]
```

### 12.2 CASL — Covers the Other 20%

RBAC can't handle "users can only edit their own posts" or "department leads only see their department's reports." CASL steps in:

```bash
pnpm add @casl/ability
```

```typescript
export function defineAbilityFor(user: User) {
  const { can, build } = new AbilityBuilder(AppAbility)

  if (user.roles?.some((r) => r.name === 'admin')) can('manage', 'all')
  if (user.roles?.some((r) => r.name === 'editor')) {
    can(['create', 'read', 'update'], 'Article')
    can('delete', 'Article', { authorId: user.id }) // only their own
  }
  if (user.roles?.some((r) => r.name === 'viewer')) {
    can('read', 'Article', { status: 'published' }) // only published
  }

  return build()
}

const ability = defineAbilityFor(currentUser)
if (!ability.can('update', subject('Article', { authorId: 5 }))) {
  throw new ForbiddenException('No permission to edit this article')
}
```

CASL's essence: conditional abilities like `{ authorId: user.id }`. Pure RBAC can't do this. RBAC and CASL aren't alternatives — they complement each other.

### 13.2 Bull Message Queue

Scheduled tasks are fine for simple periodic work. Heavy async — sending emails, image processing, report generation — belongs in a queue:

```bash
pnpm add @nestjs/bull bull
```

```typescript
BullModule.forRoot({
  redis: { host: process.env.REDIS_HOST, port: parseInt(process.env.REDIS_PORT || '6379'), password: process.env.REDIS_PASSWORD },
})
BullModule.registerQueue({ name: 'email' }, { name: 'thumbnail' })

// Consumer
@Processor('email')
export class EmailProcessor {
  @Process('welcome')
  async handleWelcomeEmail(job: Job<{ to: string; username: string }>) {
    await this.mailService.sendWelcomeEmail(job.data.to, job.data.username)
  }

  @OnQueueFailed()
  onFailed(job: Job, error: Error) {
    console.error(`Email job failed: ${job.id}, ${error.message}`)
  }
}

// Producer
async register(dto: RegisterDto) {
  const user = await this.createUser(dto)
  await this.emailQueue.add('welcome', { to: user.email, username: user.username }, {
    attempts: 3,
    backoff: { type: 'exponential', delay: 2000 },
    removeOnComplete: true,
  })
  return user
}
```

Bull solves three problems: decoupling (registration and email are separate concerns), load leveling (big promo surge gets queued), retries (auto-retry on failure).

## Fourteen: Microservices — Don't Split Too Early

Everything so far was monolith. When your project outgrows it — team conflicts, DB crumbling, deploys blocking each other — THEN consider microservices.

But microservices aren't a silver bullet. Split wrong and they're worse than the monolith.

### 14.1 Distributed vs Microservices — Not the Same Thing

- **Distributed**: a system split into multiple nodes communicating over the network. This is "how to deploy."
- **Microservices**: one implementation of distributed — split by business boundaries, independent deploy, independent database. This is "how to split."

The key is business boundaries, not deployment topology.

### 14.2 How to Split — Three Dimensions

| Dimension   | Approach                       | Examples                                     |
| ----------- | ------------------------------ | -------------------------------------------- |
| By business | Business domains               | User service, Content service, Order service |
| By function | Horizontal shared capabilities | Auditing, Notifications, File storage        |
| By resource | Access patterns and load       | Search (high-frequency), Reports (batch)     |

### 14.3 Microservice Communication

**gRPC (recommended)** — HTTP/2 + Protocol Buffers + strong contracts:

```protobuf
// proto/user.proto
service UserService {
  rpc FindOne (UserById) returns (User) {}
}
```

```typescript
// Server
@GrpcMethod('UserService', 'FindOne')
async findOne(data: { id: number }): Promise<User> {
  return this.userService.findById(data.id)
}

// Client
@Client({
  transport: Transport.GRPC,
  options: { package: 'user', protoPath: join(__dirname, '../proto/user.proto'), url: 'localhost:50051' },
})
private client: ClientGrpc
```

Proto files MUST be shared between services — extract to a separate npm package or git submodule. Copying them around leads to version mismatches. You'll pay for that someday.

**Redis Pub/Sub** — event-driven, better decoupling:

```typescript
this.eventBus.emit('user.registered', { userId: user.id, email: user.email })

@EventPattern('user.registered')
async handleWelcomeEmail(data: { userId: number; email: string }) {
  await this.mailService.sendWelcome(data.email)
}
```

### 14.4 Timeout and Degradation

```typescript
this.userServiceClient.send('user.findOne', { id: 5 }).pipe(
  timeout(3000),
  retry({ count: 2, delay: (_, retryCount) => timer(retryCount * 1000) }),
  catchError((error) => {
    if (error instanceof TimeoutError) {
      return of({ id: 5, name: 'Unknown User', _fallback: true })
    }
    throw error
  }),
)
```

Microservice calls: timeout, retry, degradation — all three, no exceptions. Downstream dying is downstream's problem. Upstream must not follow.

### 14.5 Service Governance

| Function            | Tools                  |
| ------------------- | ---------------------- |
| Service registry    | Consul / Etcd / Nacos  |
| API gateway         | Kong / Traefik / Nginx |
| Distributed tracing | SkyWalking / Jaeger    |
| Log aggregation     | ELK / Loki             |
| Monitoring & alerts | Prometheus + Grafana   |

Microservices aren't just splitting code into services. Governance infrastructure has to keep up. That's when it's actually microservices.

```
│   ├── api-gateway/
```

### 14.7 Local Dev — Multipass + K3s

You can't deploy to a cluster every time you debug. Set up a lightweight local K8s:


```yaml
# k8s/user-service.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
spec:
  replicas: 3
  template:
    spec:
      containers:
        - name: user-service
          image: your-registry/user-service:latest
```

`livenessProbe` and `readinessProbe` are mandatory. One checks if the process is alive, the other if it can take traffic.

## Fifteen: Questions to Ask Yourself Next Time

I'm not giving you a summary. Summaries are useless. Here's a set of questions — ask yourself these every time you make a decision. The answers will guide you.

**Architecture:**

1. Does this service really need splitting? Solo developer? Don't split yet.
2. After splitting, how much latency was added? How's data consistency?
3. Does the team have bandwidth to maintain Consul, K8s, distributed tracing?

**Database:**

1. Is `synchronize` off? (This isn't a discussion — the answer is always "off")
2. Did you calculate pool size? `instances × max > DB limit`?
3. Cache invalidation strategy: immediate purge or TTL-based?

**Security:**

1. Are you using Argon2 for passwords?
2. Do any API responses contain password fields? If unsure, add a global SerializeInterceptor.
3. Is whitelist on? If not, go turn it on right now.

**Reliability:**

1. Do microservice calls have timeout configured?
2. Can email failures block user operations?
3. Are sensitive fields logged anywhere?

One last thing — the thing I most want to tell you after three years of scars:

**Don't start with microservices.** Build the monolith first. NestJS's greatest strength isn't making microservices easy — it's that when your monolith is ready to split, you just wrap a Service as a microservice endpoint and change the caller to a ClientProxy. Business logic barely changes. That's what "built for splitting" actually means.

Priority order:

1. Config + logging + error handling (foundation)
2. Database + caching + auth (business core)
3. Message queues + microservices (architecture extension)

Validate each layer in production before moving to the next. Don't rush.

Now go check if `synchronize: true` is still on in your code. If it is, fix that first. Everything else can wait.
