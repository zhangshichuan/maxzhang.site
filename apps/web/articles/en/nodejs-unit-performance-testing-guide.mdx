> A testing guide for regular developers. No fluff. Just stuff you'll actually use.

It was 3 a.m. when my phone rang.

Not a friend. Not a wrong number. It was PagerDuty.

I squinted at the screen — CPU slammed against the ceiling, memory leaking like a sieve, error rate at 40%. The first thought that crossed my mind wasn't a plan. It was: crap. I changed that endpoint yesterday. It worked fine on my machine.

I dug through logs, commits, the one line that killed it. Turned out a teammate refactored a shared utility function — changed the input validation logic — and my module went belly up. Nobody caught it. Because nobody wrote tests.

I fixed the issue, pushed the hotfix, watched the graphs turn green, and lay there in the dark, eyes open, wired on adrenaline. You know what I asked myself?

Why the hell didn't I write tests?

If you've had that moment, or you'd like to avoid having it, this article is for you. I'm not here to sell you testing dogma. I'm here to tell you, as one tired developer to another, how tests let you sleep at night.

---

## Let's be honest about what tests actually do

A lot of people have the wrong idea about testing.

Some think tests "prove my code is correct." Wrong. Tests tell you where your code is probably wrong. Others think tests are a formality you tick off after writing code. Also wrong. Tests are a letter to your future self. Six months from now, you won't remember what you were thinking. The tests will.

And then there's the 100% coverage crowd. Look. 100% coverage doesn't mean zero bugs. It just means every line got executed. That's it. You can have 100% coverage and still have a garbage codebase.

Tests solve one thing: **trust**.

When you change a line of code, do you feel confident clicking "deploy"? Or do you hold your breath and mumble "should be fine" under it? If it's the second one, you're gambling. Stop gambling.

Here's what tests concretely give you:

**They stop regressions.** You fix A, B breaks. Classic. Automated tests catch this before merge, not at 3 a.m.

**They save debugging time.** A failed assertion tells you what went wrong and where. Compare that to `console.log(response, 'response ===================>')` scattered across fifteen files.

**They make refactoring possible.** You've been staring at that 500-line function for three months. You know you can do better. But you're scared. Because you don't know what depends on it. Tests give you a safety net. You restructure, you run the tests, they pass, you breathe.

**They document behavior.** Code comments rot. Nobody updates them. But tests? Tests fail when things change. They force themselves to stay current. Read the tests, and you'll understand what a function actually does — not what someone claimed it does in a comment from 2022.

Here's an analogy: you're renovating a house. The plumber runs pipes inside the walls, then the drywall goes up. Do you wait until the walls are painted to check if the pipes leak? Of course not. You test before you seal. Unit tests are that pressure check — done while you can still see everything.

## Part 1: Unit Tests — the bottom layer that holds everything up

### What counts as a unit test?

You take the smallest useful piece of your code, and you check it in isolation.

Usually that's a function. Sometimes a method. Rarely an entire module.

The word is _isolation_. If your test needs a database connection, an API call, or a Redis cache, it's not a unit test anymore. That's an integration test. Different beast. Different purpose.

Unit tests are like plugging in a toaster at the factory. You check if it toasts. You don't ship it to someone's kitchen first and then find out.

### Why bother? Let me show you the math.

Maybe you think "my logic is simple, it doesn't need tests." Or "writing tests takes too long, I'll just deploy and see."

Look at this:

| Stage of discovery         | Cost to fix  |
| -------------------------- | ------------ |
| While coding               | 1x           |
| During unit testing        | 1x - 10x     |
| During integration testing | 10x - 50x    |
| During QA                  | 50x - 200x   |
| In production              | 200x - 1000x |

A bug found in production costs 200 times more than one found while you're still typing. And the cost isn't just money. It's your time. Your morale. That phone call at 3 a.m.

The real value of unit tests is **feedback loop speed**. You just wrote the function. The logic is still warm in your brain. A test catches a mistake, you fix it in two minutes. Wait a month, and you won't even remember why you used a `Map` instead of an `Object`.

### The AAA pattern: it's a sandwich

No need to overthink this. Every test has three layers:

1. **Arrange**: set up the stuff you need. Data, mocks, dependencies.
2. **Act**: call the damn function.
3. **Assert**: check if you got what you expected.

Bread. Meat. Bread. That's it.

### Let's write one

Say you've got a simple calculator module:

```javascript
// math.js
export function add(a, b) {
  return a + b
}

export function subtract(a, b) {
  return a - b
}

export function multiply(a, b) {
  return a * b
}

export function divide(a, b) {
  if (b === 0) {
    throw new Error('Division by zero')
  }
  return a / b
}
```

Here's the test file. Watch the AAA structure:

```javascript
// math.test.js
import assert from 'node:assert'
import { add, subtract, multiply, divide } from '../math.js'

describe('Calculator module', () => {
  describe('add()', () => {
    it('should return the sum of two positive numbers', () => {
      // Arrange
      const a = 2
      const b = 3
      const expected = 5

      // Act
      const result = add(a, b)

      // Assert
      assert.strictEqual(result, expected)
    })

    it('should handle negative numbers', () => {
      assert.strictEqual(add(-1, 1), 0)
      assert.strictEqual(add(-5, -3), -8)
    })

    it('should handle zero', () => {
      assert.strictEqual(add(0, 0), 0)
      assert.strictEqual(add(5, 0), 5)
    })

    it('should handle decimals', () => {
      assert.strictEqual(add(0.1, 0.2), 0.3)
    })
  })

  describe('divide()', () => {
    it('should throw when divisor is zero', () => {
      assert.throws(() => divide(10, 0), /Division by zero/)
    })
  })
})
```

Run it:

```
Calculator module
  add()
    ✓ should return the sum of two positive numbers
    ✓ should handle negative numbers
    ✓ should handle zero
    ✓ should handle decimals
  divide()
    ✓ should throw when divisor is zero

5 passing (15ms)
```

Fifteen milliseconds. Five tests. Every future change to this module now has a guardrail.

The divide-by-zero case is the important one. When you're writing the function, your brain is in the "happy path." You're thinking about what happens when things go right. But the test forces you to think: what if the caller passes zero? What if they pass a string? What if they pass `undefined`? Writing tests makes you a better API designer — not because of some abstract principle, but because you literally have to confront the edge cases.

### What makes a test good? Remember FIRST.

Not all tests are useful. A bad test is worse than no test — it gives you false confidence.

**Fast.** Unit tests must be fast. You'll have hundreds of them. If each one takes two seconds, you'll stop running them. And unrun tests are useless.

**Independent.** Each test stands alone. Test B should not depend on Test A passing first. Don't chain them. Don't share mutable state between them. If one fails, the others should still run.

**Repeatable.** Same result every time. Mock anything time-dependent. Mock anything network-dependent. Your tests shouldn't fail just because it's a Tuesday.

**Self-Validating.** The result must be unambiguous — pass or fail. No "output a report for the tech lead to review." If a human has to interpret the result, it's not a test.

**Timely.** Write the test right after writing the code. Not a week later. A week later you've already moved on, and writing tests feels like homework you forgot to turn in.

### Coverage: 80% is fine. Stop chasing 100.

Coverage tells you what percentage of your code got exercised by tests. Four common metrics:

| Metric        | What it means                          | Example                                         |
| ------------- | -------------------------------------- | ----------------------------------------------- |
| **Statement** | Was this line executed?                | `if (x) { thing(); }` — never true? not covered |
| **Branch**    | Were both paths of each if-else taken? | Need true and false paths both hit              |
| **Function**  | Was every function called?             | Don't leave orphan functions                    |
| **Line**      | Was every line executed?               | Similar to statement coverage                   |

A typical coverage report looks like:

```
File          | % Stmts | % Branch | % Funcs | % Lines
 math.js      |   85.71 |       75 |     100 |   85.71
 user.js      |   90.00 |       80 |     100 |   90.00
```

`math.js` has 85.71% statement coverage and 75% branch coverage. That means 25% of conditional paths are untested. There could be bugs lurking there.

Is higher always better? **Hell no.**

I've seen teams write `expect(1 + 1).toBe(2)` just to push a number from 98% to 100%. That's not testing. That's theater. The number looks good in a dashboard, but your edge cases are still untested and your error handling is still a fantasy.

My rule of thumb:

- Core business logic: aim for 80%+.
- Edge cases and error paths: must be covered.
- Simple getters/setters, boilerplate: skip them.
- Never write a meaningless assertion just to game a number.

### Choosing a framework: Mocha vs Jest vs Vitest

Node.js has three serious testing frameworks. Here's the quick comparison:

| Feature            | Mocha                           | Jest           | Vitest                             |
| ------------------ | ------------------------------- | -------------- | ---------------------------------- |
| Assertions         | Bring your own (Chai)           | Built-in       | Built-in                           |
| Mocking            | Needs Sinon                     | Built-in       | Built-in                           |
| Parallel execution | Needs config                    | Automatic      | Automatic (Vite-native, very fast) |
| ESM                | Needs config                    | Mostly works   | Native                             |
| TypeScript         | Needs config                    | Built-in       | Built-in                           |
| Best for           | Legacy projects, control freaks | React projects | Vue/Vite, new projects             |

Shortcut: if you're starting a new project, use Vitest. If you're on React, Jest. If you need maximum configurability or you're maintaining something older, Mocha.

Here they are in action.

#### Mocha + Chai + Sinon: the old-school combo

Mocha is just a test runner. You bolt on Chai for assertions, Sinon for mocking. Flexible? Yes. Annoying to set up? Also yes.

```javascript
// api.js
import axios from 'axios'

export async function fetchUser(userId) {
  const response = await axios.get(`/api/users/${userId}`)
  return response.data
}
```

```javascript
// api.test.js
import { expect } from 'chai'
import sinon from 'sinon'
import axios from 'axios'
import { fetchUser } from './api.js'

describe('fetchUser', () => {
  let stub

  beforeEach(() => {
    stub = sinon.stub(axios, 'get')
  })

  afterEach(() => {
    stub.restore()
  })

  it('should return user data', async () => {
    const mockUser = { id: 1, name: 'Alice' }
    stub.resolves({ data: mockUser })

    const result = await fetchUser(1)

    expect(result).to.deep.equal(mockUser)
    expect(stub.calledOnce).to.be.true
    expect(stub.calledWith('/api/users/1')).to.be.true
  })

  it('should reject when user not found', async () => {
    const error = new Error('Request failed with status 404')
    error.response = { status: 404 }
    stub.rejects(error)

    await expect(fetchUser(999)).to.eventually.be.rejected
  })
})
```

#### Jest: zero-config, React-first

Jest gives you everything out of the box — assertions, mocking, coverage, watch mode. It was built by Facebook and integrates beautifully with React.

```javascript
// user.js
export function createUser(name, email) {
  if (!name || !email) {
    throw new Error('Name and email are required')
  }
  return {
    id: Date.now(),
    name,
    email,
    createdAt: new Date().toISOString(),
  }
}
```

```javascript
import { createUser } from './user.js'

describe('createUser', () => {
  test('should return a user object with id, name, email', () => {
    const user = createUser('Alice', 'alice@example.com')

    expect(user).toHaveProperty('id')
    expect(user).toHaveProperty('name', 'Alice')
    expect(user).toHaveProperty('email', 'alice@example.com')
    expect(user).toHaveProperty('createdAt')
  })

  test('should throw when name is empty', () => {
    expect(() => createUser('', 'test@example.com')).toThrow('Name and email are required')
  })

  test('should throw when email is empty', () => {
    expect(() => createUser('Alice', '')).toThrow('Name and email are required')
  })
})
```

#### Vitest: the new kid, blazing fast

Vitest is Jest-compatible but runs on Vite underneath. The startup time and hot module reload experience are leagues ahead. If your build tool is Vite, there's zero reason not to use it.

```javascript
// arrayUtils.js
export function filterByStatus(items, status) {
  return items.filter((item) => item.status === status)
}

export function groupByCategory(items) {
  return items.reduce((acc, item) => {
    const key = item.category
    if (!acc[key]) acc[key] = []
    acc[key].push(item)
    return acc
  }, {})
}
```

```javascript
// arrayUtils.test.js
import { describe, it, expect } from 'vitest'
import { filterByStatus, groupByCategory } from './arrayUtils.js'

describe('Array utilities', () => {
  const items = [
    { id: 1, status: 'active', category: 'A' },
    { id: 2, status: 'inactive', category: 'A' },
    { id: 3, status: 'active', category: 'B' },
  ]

  describe('filterByStatus', () => {
    it('should filter by status', () => {
      const result = filterByStatus(items, 'active')
      expect(result).toHaveLength(2)
      expect(result.every((item) => item.status === 'active')).toBe(true)
    })

    it('should return empty array when no match', () => {
      const result = filterByStatus(items, 'deleted')
      expect(result).toHaveLength(0)
    })
  })

  describe('groupByCategory', () => {
    it('should group by category', () => {
      const result = groupByCategory(items)
      expect(result).toHaveProperty('A')
      expect(result).toHaveProperty('B')
      expect(result.A).toHaveLength(2)
      expect(result.B).toHaveLength(1)
    })
  })
})
```

### Async tests and lifecycle hooks

Most real-world code is async — database queries, API calls, file reads. All frameworks support `async/await` out of the box:

```javascript
it('should fetch users asynchronously', async () => {
  const users = await getUsers()
  expect(users).to.be.an('array')
  expect(users.length).to.be.greaterThan(0)
})
```

Lifecycle hooks let you set up and tear down before and after tests:

```javascript
describe('Database tests', () => {
  before(async () => {
    // Runs once before all tests
    await db.connect()
  })

  after(async () => {
    // Runs once after all tests
    await db.close()
  })

  beforeEach(() => {
    // Runs before each test — keeps them independent
    db.clear()
  })

  it('should create a user', async () => {
    const user = await db.users.create({ name: 'Test User' })
    expect(user.id).to.exist
  })
})
```

### Mocking and Stubbing: you don't need the real thing

The hardest part of unit testing isn't writing assertions. It's isolating dependencies.

Your order-processing function depends on: a database, a cache, a payment gateway, an SMS API, and probably a third-party service you don't even control. If every test called the real thing:

1. It'd be slow. Database queries add up.
2. It'd be flaky. The external API goes down, your test fails — but your code is fine.
3. You can't test error paths. How do you make Stripe actually return "card declined" on demand?

Enter mocks and stubs.

**The difference matters:**

- **Stub**: replaces a function, returns a preset value. Like copying answers from the back of the textbook.
- **Mock**: replaces a function _and_ tracks how it was called — how many times, with what arguments. Like hiring a stunt double who also writes you a report afterward.

Here's a practical example:

```javascript
// userService.js
export async function getUserWithPosts(userId) {
  const user = await fetchUser(userId)
  const posts = await fetchPosts(userId)
  return { user, posts }
}
```

```javascript
// userService.test.js (Jest)
import { getUserWithPosts } from './userService.js'
import { fetchUser, fetchPosts } from './api.js'

jest.mock('./api.js')

describe('getUserWithPosts', () => {
  beforeEach(() => {
    jest.clearAllMocks()
  })

  it('should return user with their posts', async () => {
    // Stub return values
    fetchUser.mockResolvedValue({ id: 1, name: 'Alice' })
    fetchPosts.mockResolvedValue([{ id: 1, title: 'First post' }])

    const result = await getUserWithPosts(1)

    expect(result.user.name).toBe('Alice')
    expect(result.posts).toHaveLength(1)

    // Verify calls
    expect(fetchUser).toHaveBeenCalledWith(1)
    expect(fetchPosts).toHaveBeenCalledWith(1)
  })

  it('should propagate API errors', async () => {
    fetchUser.mockRejectedValue(new Error('Network error'))

    await expect(getUserWithPosts(1)).rejects.toThrow('Network error')
  })
})
```

With mocking, you can simulate success, failure, empty data, timeouts — every pathological scenario — without actually breaking anything.

## Part 2: Performance Testing — can your system take the heat?

### Unit tests check correctness. Performance tests check survival.

Unit tests ask: does this function return the right value?

Performance tests ask: will this entire system collapse under load?

Picture this: you build a car. Unit tests verify the wheels turn, the brakes stop, the steering works. Performance testing is taking it onto the highway at 120 km/h for eight hours straight, watching the temperature gauge, and hoping the engine doesn't catch fire.

Performance tests simulate real traffic and measure four things:

- **Response time**: how long does a request wait? Not the average — look at P50, P90, P99. The slowest 1% of your users matter most.
- **Throughput (TPS/QPS)**: how many requests per second can you handle?
- **Resource usage**: CPU, memory, disk, network. What's getting maxed out?
- **Error rate**: how many requests just fail?

It answers the brutal questions:

- How many concurrent users can you serve? 100? 1,000? 10,000?
- Will you crash during the holiday sale?
- Is memory slowly creeping up over time? (That's a leak.)
- After a traffic spike, does the system recover or stay broken?

### There are four kinds of performance tests, not one

People say "let's do a load test" like it's one thing. It's not. Each type serves a different purpose.

#### Type 1: Baseline Test

**What it does**: runs under low load to establish a "normal" performance profile. You run this after every release and compare. If the numbers got worse, your last commit introduced a regression.

**How to run it**: single or few users, 5-10 minutes.

**What to check**: average response time for a single user, baseline resource consumption.

#### Type 2: Load Test (Capacity Test)

**What it does**: this is what most people mean by "load testing." You gradually increase concurrent users until you find the breaking point — the **performance inflection point** where response times spike or errors skyrocket.

**When to do it**: before a big sale, before launching a new feature, anytime you want to know your system's ceiling.

**How to run it**: ramp up step by step. Start at 10 users, add more every 30 seconds, watch the metrics. When latency jumps from 200ms to 2 seconds in one step — that's your ceiling.

**What to check**: maximum TPS, response time distribution at each concurrency level, where the inflection point lives.

#### Type 3: Endurance Test (Stability Test)

**What it does**: runs at ~80% capacity for a long time — 8 hours, 24 hours, even 7 days. The goal is to catch slow-burn problems: memory leaks, connection leaks, GC thrashing.

**When to do it**: your service is supposed to run 24/7. You claim your code is fine. Run it for three days and watch the memory graph. If it's sloping upward, you've got a leak.

**What to monitor obsessively**:

- Memory trend: is it creeping up? That's a leak.
- CPU trend: stable, or spiking periodically? Spikes might mean a batch job or cron is misbehaving.
- Handle count: is it growing? You're not closing connections.
- GC frequency: if the garbage collector is running more and more often, your memory management is in trouble.
- Error logs: are they slowly accumulating?

#### Type 4: Stress Test (Spike Test)

**What it does**: simulates a sudden traffic burst — like the moment tickets go on sale and everyone hits refresh at once.

**When to do it**: flash sales, ticket launches, or any scenario where traffic can spike 10x in seconds.

**How to run it**: from normal load, instantly jump to peak load, hold for a few seconds, drop back down. Two things to watch: did you survive the spike? Did you recover after?

### When performance testing is non-negotiable

Not every project needs all four types. But these scenarios? Skip testing at your own risk:

| Scenario                    | Why you can't skip it                                                   |
| --------------------------- | ----------------------------------------------------------------------- |
| New application launch      | Your estimate of "how much traffic we'll get" is almost certainly wrong |
| High-frequency core service | Payments, orders, flash sales. Downtime equals money                    |
| Major events                | Black Friday, concert ticket sales. Not load testing is gambling        |
| Architecture changes        | Microservice split, database migration. Performance will change         |
| Long-running services       | Memory leaks don't show up in a five-minute test                        |

Real stories:

- An e-commerce platform skipped load testing before Singles' Day. Their database melted in the first minute. Twenty minutes of downtime.
- A bank upgraded their system and didn't endurance-test it. Memory leak after three days. Transactions lost.
- A ticketing system crashed during peak demand. Millions in lost revenue.

These teams weren't incompetent. They were complacent.

### A performance test is a process, not a command

Don't just type `artillery run` and call it done. Think first.

**Step 1: Set targets.** What TPS do you need? What P95 response time? What error rate? If you don't know, talk to the product people. Testing without a target is jogging without a destination.

**Step 2: Build a traffic model.** What do your users actually do?

- 80% browsing products
- 15% placing orders
- 5% searching

Design your test script to match these proportions. Use realistic data distributions — not `"username": "test"`. Production data looks nothing like your test data.

**Step 3: Pick a tool.** (Covered next.)

**Step 4: Set up monitoring.** The load tool tells you "it's slow." It doesn't tell you _why_. Set up Prometheus + Grafana for system metrics. Better yet, add APM to trace individual requests.

**Step 5: Execute.** Start slow, ramp up gradually. Don't slam it. Watch every step. Mark anomalies.

**Step 6: Analyze and report.** Compare against targets. Find the bottleneck. Recommend fixes. If you didn't hit targets, optimize and retest. If you did, archive the results as your new baseline.

### Tool choice: Artillery vs k6

Two tools dominate the Node.js performance testing landscape.

#### Artillery: YAML-driven, dead simple

Artillery uses YAML for test scenarios. It takes five minutes to learn. And it's genuinely good.

```bash
npm install -g artillery
```

Basic config:

```yaml
# test.yml
config:
  target: 'http://localhost:3000'
  phases:
    - duration: 60
      arrivalRate: 20
      name: 'Sustained load'

scenarios:
  - name: 'Get users'
    flow:
      - get:
          url: '/api/users'
          capture:
            - json: '$.data[0].id'
              as: 'userId'
      - get:
          url: '/api/users/{{ userId }}'
```

```bash
artillery run test.yml
```

The output gives you request count, mean response time, P95, P99 — everything you need in a clean table.

Advanced features include CSV-driven parameterization, think time (simulating a user staring at the page), and built-in assertions:

```yaml
config:
  target: 'http://my-api.com'
  phases:
    - duration: 300
      arrivalRate: 20
      rampTo: 50
  payload:
    path: 'users.csv'
    fields:
      - 'userId'
      - 'token'
    order: 'random'

scenarios:
  - name: 'Full user flow'
    flow:
      - post:
          url: '/api/auth/login'
          json:
            userId: '{{ userId }}'
            token: '{{ token }}'
          capture:
            - json: '$.token'
              as: 'authToken'
          expect:
            - statusCode: 200
      - think: 2
      - get:
          url: '/api/users/me'
          headers:
            Authorization: 'Bearer {{ authToken }}'
```

#### k6: JavaScript scripting, Go-powered

k6's runtime is Go, so it's fast. The scripting language is JavaScript, so it's accessible. It's a beautiful combination.

```bash
# macOS
brew install k6

# Linux
curl -s https://github.com/grafana/k6/releases/latest/download/k6-latest-linux-amd64.deb -o k6.deb
sudo dpkg -i k6.deb
```

Minimal script:

```javascript
import http from 'k6/http'
import { check, sleep } from 'k6'

export const options = {
  stages: [
    { duration: '1m', target: 10 }, // ramp up to 10 users over 1 minute
    { duration: '3m', target: 10 }, // hold at 10 for 3 minutes
    { duration: '1m', target: 0 }, // ramp down to 0 over 1 minute
  ],
  thresholds: {
    http_req_duration: ['p(95)<500'], // P95 must stay under 500ms
    http_req_failed: ['rate<0.01'], // error rate must stay under 1%
  },
}

export default function () {
  const res = http.get('http://localhost:3000/api/users')
  check(res, {
    'status is 200': (r) => r.status === 200,
  })
  sleep(1)
}
```

```bash
k6 run script.js
```

The output is a live terminal dashboard — TPS, latency, errors. Watching it in real time as you ramp up is weirdly satisfying. You'll know exactly when your system hits the wall.

k6 can pipe data into InfluxDB and Grafana for beautiful real-time dashboards. Run the test, open Grafana, and watch the curves climb. When the inflection point hits, you'll see it.

#### How I choose:

- Simple HTTP endpoints, team prefers YAML over JS — Artillery.
- Complex scenario orchestration, custom metrics, CI/CD integration — k6.
- Both are easy. You can learn either in an afternoon.

### Add APM: find out _where_ it's slow

Your load test says "P95 is 850ms, way too slow." Now what? You stare at logs, guessing.

APM traces every request from entry to exit, breaking down the time spent at each step:

- API Gateway: 10ms
- Your Node.js service: 50ms
- Database query: 800ms

Ah. It's not your code. It's a missing index.

Common APM tools:

| Tool                       | Type        | Notes                                       |
| -------------------------- | ----------- | ------------------------------------------- |
| New Relic                  | Commercial  | End-to-end tracing, expensive but complete  |
| Datadog                    | Commercial  | Cloud-native, strong integrations           |
| Elastic APM                | Open source | Tied to the ELK stack                       |
| Prometheus + OpenTelemetry | Open source | Fully self-hosted, free but labor-intensive |

If you're just starting out, use the free tier of New Relic or Datadog. Get the workflow working. Worry about self-hosting later.

### Performance testing checklist

Before every test, run through this:

**Pre-test prep**

- [ ] Define performance targets (TPS, response time, error rate) — never start without targets
- [ ] Prepare realistic test data — fake data gives fake results
- [ ] Match the test environment to production as closely as possible — hardware differences will lie to you
- [ ] Deploy monitoring — running a test without monitoring is like driving with your eyes closed
- [ ] Review test scripts — a broken script generates meaningless numbers

**During testing**

- [ ] Start at low load, ramp up gradually
- [ ] Watch metrics at every step — find the inflection point
- [ ] Record every anomaly — you'll need them later
- [ ] Run multiple times to verify consistency — rule out flukes

**Post-test analysis**

- [ ] Compare results against targets — pass or fail
- [ ] Locate the bottleneck — what's the slowest thing
- [ ] Produce optimization recommendations — what to fix, in what order
- [ ] Archive results as a baseline — so the next release has something to compare against

## Part 3: Put Your Tests in CI/CD

### Running tests locally isn't enough

You might ask: "I already ran the tests on my machine. Why put them in CI?"

Because you're not the only person on the team. Someone else merges a change. Your module breaks. You don't notice because you haven't pulled latest. But CI notices — and it stops the broken code at the merge gate.

CI-based testing gives you three things:

- **A gate**: if tests fail, the PR can't merge. Quality floors, enforced automatically.
- **Visibility**: every push runs the tests. You know instantly if something broke.
- **Freedom**: stop running the full test suite locally. CI handles it. You read the results.

### GitHub Actions setup

Drop this in `.github/workflows/test.yml`:

```yaml
name: Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  unit-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-node@v3
        with:
          node-version: '18'
          cache: 'npm'
      - run: npm ci
      - run: npm test
      - uses: codecov/codecov-action@v3
        with:
          file: ./coverage/lcov.info

  performance-test:
    runs-on: ubuntu-latest
    needs: unit-test # only run if unit tests pass
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-node@v3
        with:
          node-version: '18'
      - run: npm ci
      - run: npm run start:prod &
      - run: npx k6 run tests/performance.js
```

Notice `needs: unit-test` on the performance test job. If the unit tests fail, there's no point load-testing broken code.

## A Judgment Framework to Take with You

I'm not going to summarize everything I just wrote. You don't need a summary. You need a set of questions you can ask yourself each time you face a testing decision.

**For unit tests:**

1. Is this function on a critical path? If it breaks, does production break? — If yes, test it.
2. Have I thought about the edge cases? — Probably not. Writing the test will force you to.
3. Would I feel confident changing this code and hitting deploy right now? — If no, you need tests.
4. I hit 85% coverage. Are the remaining 15% actually important? — If not, stop chasing. The number is a mirage.
5. What framework am I using? — Vite project? Vitest. React? Jest. Legacy? Mocha. Don't overthink it.

**For performance tests:**

1. How many users will hit my system? Is there a peak? — Ask the product team. If there's a peak, load test.
2. When should I test? — Before launch. Before a big event. After architecture changes. These three are mandatory.
3. Which type? — Baseline every release. Load test before launch. Endurance for 24/7 services. Stress for flash-sale scenarios.
4. Which tool? — Simple: Artillery. Complex: k6.
5. Where is it slow? — The tool tells you _that_ it's slow. APM tells you _where_.

**For process:**

1. Are tests running in CI? — If not, your local tests are decorative.
2. Can a PR merge if CI fails? — If yes, your CI is decorative.
3. Where are the results from the last load test? — If you can't find them, this test was a waste of time.

Testing isn't a ceremony. It's how you build trust in your system — not trust based on hope, but trust based on evidence. Every green checkmark is one less thing that can wake you up at 3 a.m.

Write the tests. Not for your manager. For the version of you who wants to sleep through the night.
