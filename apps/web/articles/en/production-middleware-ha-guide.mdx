It's 3 AM. Your phone buzzes.

You squint at the screen. `PostgreSQL connection refused`.

Your brain goes blank, then starts spinning. Is the primary down? Did the replica take over? Did we lose data? Are users seeing error pages or just nothing?

You drag yourself upright and open your laptop. You've been here before. We all have.

This article is for that moment. Not to give you config files — you can look those up. It's to wire the mental model into your head. So next time shit hits the fan, you have a map, not a panic attack.

---

## It starts with a crash

Say you're running a SaaS platform. Nothing exotic. Requests come in through Nginx, hit your Node.js backend, which talks to PostgreSQL and Redis. You've got BullMQ as your job queue. Everything runs on K3s.

One afternoon, the PostgreSQL primary's disk fills up. The process goes down hard.

Users start seeing timeouts. Then Redis Sentinel fails too — because that same machine was hosting one of your Sentinel nodes, and you only deployed two Sentinels total.

Classic domino effect.

In the postmortem, you realize every layer had a single point of failure. But nobody told you how those single points are wired together. Nobody told you how much you can actually trust that "automatic failover."

Let's fix that. Layer by layer.

## PostgreSQL: your database is more fragile than you think

### When it dies, it stays dead

PostgreSQL doesn't fail over on its own. It's a process that executes SQL. It crashes, it's gone. End of story.

So you give it a sidekick.

### Streaming replication: first, don't lose data

PG replication runs on the WAL — Write-Ahead Log.

The WAL isn't magical. Think of it like Git's commit log. Every change you make, Git records the change before modifying the file. PG does the same: every write operation hits the WAL first, then the data files.

The WAL records are binary, page-level changes. Not SQL statements. They say "change tuple 3 on page 6 from state A to state B." This means the replica doesn't need to re-parse SQL, re-run index lookups, or re-check constraints. It just modifies memory pages directly. Replay on the replica is actually much faster than the original write on the primary.

Three latency metrics you need to know:

- `write_lag`: time for WAL bytes to reach the replica's network buffer
- `flush_lag`: time for those bytes to hit disk on the replica
- `replay_lag`: time for the replica to apply changes — this is when queries can actually see the data

**`replay_lag` is the one that matters.** It determines whether your replica can take over traffic.

If replay_lag is huge — for instance, the primary just ran a transaction that touched 5 million rows and generated 2GB of WAL — your replica is wheezing behind it. If the primary dies right then and you fail over, those unreplayed records are gone.

### Synchronous replication: zero data loss, at a price

PG supports two modes:

**Asynchronous** (default): Primary returns success to the client as soon as it writes WAL, then sends it to the replica later. If the primary crashes, you might lose a few seconds of data.

**Synchronous**: Primary waits for the replica to confirm the WAL is on disk before returning success to the client. Zero data loss.

Sounds perfect, right?

Shit, the price is steep. If the synchronous replica goes down or has network problems, the primary can't write anymore. Your entire write path blocks until timeout. Your API goes down with it.

The real-world compromise: **1 synchronous + N asynchronous** replicas. You get zero-loss guarantees for that one synchronous replica. If it dies, PG automatically degrades to asynchronous mode. When it comes back and catches up, PG promotes it back to synchronous. This is the best balance between "no data loss" and "keep serving traffic."

### How replication actually runs: WAL Sender and WAL Receiver

The primary runs a `WAL Sender` process. The replica runs a `WAL Receiver` and a `Startup` process.

Here's the flow:

1. The replica connects and says: "Give me WAL starting from LSN `0/1A000000`."
2. The primary forks a WAL Sender. It reads WAL files from `pg_wal/`, starting at that LSN, packs records into replication messages, and streams them over TCP.
3. The replica's WAL Receiver writes them to its local `pg_wal/` directory.
4. The replica's Startup process reads from local WAL files and applies changes to the data directory.
5. Once caught up, it enters **streaming mode** — every new WAL record on the primary is sent immediately, no waiting for a full 16MB segment.

If the replica is brand new or has been disconnected too long, it first does **file-based catch-up** (copying entire 16MB WAL segments), then switches to streaming once caught up.

Rebuilding a replica from scratch with `pg_basebackup`:

1. Connect to primary, create a replication slot ("keep WAL from this point forward")
2. Make a physical backup of data files over the replication protocol (a tar archive)
3. The replica restores that tar into its own data directory
4. On startup, it reads `backup_label` to learn the starting LSN
5. Starts WAL Receiver, begins replay from that LSN
6. Catches up, switches to streaming

### Automatic failover: Patroni enters the room

Replication alone isn't enough. When the primary dies, someone has to run `pg_ctl promote` on a replica. At 3 AM, you don't want to be that someone.

**Patroni** is a Python agent that sits next to every PG node.

It works like this:

1. Every Patroni instance writes heartbeats and its current LSN position to etcd
2. etcd holds a "leader lock" — whoever holds it is the primary
3. The primary's Patroni renews the lock periodically (TTL mechanism)
4. Primary dies → lock TTL expires, lock is released
5. Other Patroni instances notice the lock is free → election begins
6. The replica with the highest LSN grabs the lock → runs `pg_ctl promote` to become the new primary
7. Other replicas automatically follow the new primary

The whole thing takes 10-30 seconds. Enough time for you to sit up in bed.

Critical detail: **etcd itself must be highly available.**

etcd runs on the Raft consensus protocol. Minimum 3 nodes. A write requires confirmation from a majority. Lose 1 node (3 becomes 2): cluster works fine. Lose 2 (3 becomes 1): cluster becomes read-only, data is safe but you can't make changes.

So your etcd needs at least 3 nodes, and those 3 nodes must not all live on the same physical machine. One machine dies, etcd is gone, Patroni can't fail over. You're back to 3 AM manual promotion.

### Connection pooling: PgBouncer

PostgreSQL forks a process per client connection. Each process eats around 5-10MB of memory. Deploy 10 app pods, each opening 100 connections, that's 1,000 connections = 5-10GB of memory. Before serving a single request.

**PgBouncer** is a connection multiplexer. Hundreds of short-lived app connections get funneled through a handful of long-lived PG connections. PG only ever has to deal with those few.

How does PgBouncer itself stay highly available? Deploy 2 instances. Put both addresses in your app's connection string. One dies, the app falls over to the other.

### Backups: the last line of defense

When automatic failover fails — and eventually, it will — you have backups.

Standard approach: **full backup + continuous WAL archiving**.

- `pg_basebackup` for a weekly full backup
- WAL continuously archived to S3 or MinIO

This gives you PITR: Point-in-Time Recovery. You can restore to any moment in the past. RPO depends on WAL archiving frequency, typically tens of seconds.

Don't confuse backups with HA. Backups save your data. HA saves your service. 3 minutes of downtime gets you angry users. Data loss gets you sued.

## Redis: it's fast, but don't trust it with your life

Redis's problem is the opposite of PostgreSQL's.

PG's problem is "it won't fail over by itself." Redis's problem is "it will fail over, but it might lose data while doing it."

### Three ways to run Redis

- **Standalone**: dev environments only. Running standalone Redis in production is like driving on the highway without a seatbelt.
- **Master-replica + Sentinel**: small to medium data (under a few dozen GB per node), read-heavy workloads. This is the most common production setup.
- **Cluster**: data bigger than a single machine's memory, needs sharding. Splits 16,384 hash slots across multiple masters. Each master holds a fraction of the data. Scale up and down by migrating slots.

### Sentinel mode: how leader election works

Sentinel is a separate process, deployed alongside your Redis nodes. It stores no data. It does exactly three things:

**1. Monitoring.** Pings master and replicas every second. If a node doesn't respond within `down-after-milliseconds` (typically 30 seconds), Sentinel declares it "subjectively down."

**2. Voting.** One Sentinel thinking the master is dead isn't enough. A majority of Sentinels must agree before declaring it "objectively down."

You're probably wondering: why the majority requirement?

Consider this: a network hiccup, not a real crash. Sentinel-1 can't reach the master, marks it down. If it fails over right then, Sentinel-2 and Sentinel-3, still connected, see a different master. Congratulations, you just created a split-brain. Two masters, each accepting writes, data diverging in two directions. When you try to merge them later, you'll be crying into your keyboard.

The quorum exists to prevent false positives from network partitions. Without majority agreement, no failover.

**3. Failover.** Elect a new master → redirect all replicas to follow it → notify clients of the new address.

Minimum 3 Sentinels, deployed on different physical machines. Otherwise one machine dies, all Sentinels die, and nobody's left to trigger failover when the master goes down.

### How clients discover the new master

Your app doesn't connect directly to Redis. It connects to Sentinel. Client libraries like ioredis have built-in Sentinel support:

```typescript
const redis = new Redis({
  sentinels: [
    { host: 'sentinel-1', port: 26379 },
    { host: 'sentinel-2', port: 26379 },
    { host: 'sentinel-3', port: 26379 },
  ],
  name: 'mymaster',
})
```

After failover, the client briefly fails, then auto-reconnects to the new master. A few requests may fail in between. Your application code needs retry logic.

### Cluster mode: failover without Sentinel

When data exceeds single-machine memory, storing full copies on every node is wasteful. Cluster mode splits the dataset:

```
Master 1 owns slots 0-5460
Master 2 owns slots 5461-10922
Master 3 owns slots 10923-16383
```

On write: `CRC16(key) % 16384` determines the slot, which determines the master.

Cluster doesn't need Sentinel. Nodes monitor each other via the **Gossip protocol**. Each node periodically picks a few random peers and exchanges state info: who's alive, who owns which slots.

Gossip's strength: fully decentralized, no single point. Weakness: failure detection is slower than Sentinel's (seconds vs milliseconds).

### Persistence: can you actually trust Redis with your data?

Does Redis lose data on restart? Depends on what you configured.

- **RDB**: periodic snapshots. Dump the entire in-memory dataset to disk every N minutes. Simple, low performance impact. But you can lose up to N minutes of data. RPO of 5 minutes is typically unacceptable in production.
- **AOF**: append every write command to a log file. Configurable fsync interval — every second is the sweet spot for performance vs safety. RPO: up to 1 second. Redis replays the AOF on restart. Production must-have.
- **Hybrid**: RDB as the base, AOF for increments. Redis 4.0+ recommendation. The AOF file won't grow infinitely — periodically, Redis writes a full RDB snapshot, then appends only subsequent changes.

```conf
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes
```

Three lines. Add them to every production Redis config.

But here's the thing: Redis persistence is not designed for "guaranteed no data loss." It's an in-memory database. Persistence is a nice-to-have, not the foundation. If your business requires "once written, never lost," use PostgreSQL.

Redis's niche: **blazing fast, tolerable sub-second data loss windows.** Counters, caches, sessions, leaderboards — losing a few seconds is fine. User balances? That goes in PostgreSQL. Don't fool yourself.

## BullMQ: your job queue runs on Redis, and that's okay

BullMQ is the go-to job queue in the Node.js ecosystem. It lives entirely in Redis.

People ask: "Is it safe to run a message queue on Redis? What if Redis goes down?"

Let's break this down.

BullMQ's data structures all sit in Redis:

- `wait` (list): jobs waiting to be processed
- `active` (list): jobs currently being worked on
- `completed` (set): finished jobs
- `failed` (set): failed jobs
- `delayed` (zset): jobs scheduled for later
- `stalled` (set): jobs that stopped sending heartbeats

If Redis loses these keys, your queue is empty. So BullMQ's HA boils down to: **Redis HA + stalled detection**.

You've already set up Redis with Sentinel or Cluster. That part we've covered.

### Stalled detection: your jobs survive worker crashes

This is BullMQ's most important internal mechanism.

Your worker is a K3s pod. It picks up a job from `wait`, the job moves to `active`, and the worker starts executing. During execution, the worker sends periodic heartbeats.

If the pod crashes, heartbeats stop. BullMQ scans the `active` list. If a job has been sitting there longer than `lockDuration` (say, 30 seconds) without a heartbeat, it's marked stalled and moved back to `wait`. Another worker picks it up.

Two critical knobs:

- `lockDuration`: how long without a heartbeat before the job is considered stalled
- `stalledInterval`: how often to scan for stalled jobs

Set them too high, and stalled jobs sit for a long time before being retried. Set them too low, and long-running jobs get falsely marked as stalled. Tune them based on your actual job execution times.

### How far does this architecture hold up?

Redis on Sentinel for automatic failover. Workers on K3s Deployments with replicas for automatic pod replacement. Stalled detection as the safety net. Three layers.

But the worst case: the entire Redis cluster goes down simultaneously. Maybe all 3 Sentinels are on the same physical machine, and that machine dies. BullMQ goes completely dark.

This is an extreme scenario. Multi-AZ deployment reduces the probability further. But you need to be aware of this tail risk.

BullMQ fits the pattern of: **jobs can tolerate brief delays, but cannot be permanently lost.** If you need "message absolutely never lost" semantics with strong guarantees, you want Kafka or RabbitMQ with durable queues.

## What happens when K3s itself dies

K3s is a lightweight Kubernetes distribution. It ships with embedded etcd. Minimum 3 server nodes for HA.

### The control plane and data plane are separate things

The single most important thing to understand about K3s HA: **when the control plane goes down, your already-running pods don't care.**

The control plane — K3s servers, including the API server and etcd — handles scheduling new pods and managing cluster state. But once a pod is scheduled onto an agent node, kubelet runs independently on that agent, maintaining the pod's lifecycle.

Services too — traffic forwarding uses iptables rules, enforced by the Linux kernel, with zero dependency on the API server.

So:

- 1 server down (etcd: 3 → 2): cluster is fine. You can schedule, deploy, delete as usual.
- 2 servers down (etcd: 3 → 1): can't schedule new pods, can't modify any resources. But existing pods keep running. Existing Services keep forwarding traffic.

This is the most elegant thing about Kubernetes: the decoupling of control plane and data plane.

### Actual deployment

3 server nodes. Agent nodes as many as you need. Put a TCP load balancer in front of the servers (HAProxy or Nginx, doesn't matter). Agents connect to the API server through the LB. Any server dies, the LB drops it.

```bash
# First server: initialize etcd cluster
curl -sfL https://get.k3s.io | sh -s - server --cluster-init

# Second and third servers: join the etcd cluster
curl -sfL https://get.k3s.io | sh -s - server \
  --server https://server-1-ip:6443 --token <token>

# Agents: connect through the load balancer
curl -sfL https://get.k3s.io | \
  K3S_URL=https://lb.example.com:6443 \
  K3S_TOKEN=<token> sh -
```

### Redundancy at every layer

Production K3s needs redundancy at multiple layers:

| Layer         | How                                                     |
| ------------- | ------------------------------------------------------- |
| Control plane | 3 servers + embedded etcd + front LB                    |
| Worker nodes  | Multiple nodes + pod affinity rules                     |
| Pods          | Deployment replicas + liveness/readiness probes         |
| Service       | iptables/ipvs rules (kernel-level, no process to crash) |
| Ingress       | Nginx Ingress multi-replica                             |
| Storage       | PVC + Longhorn distributed block storage                |
| Middleware    | Independent HA mechanisms (covered above)               |

Each layer is an independent failure domain. Lose one, the others stay up.

## Load balancing: the layer that can't die

### L4 vs L7

Traffic forwarding in K3s comes in two layers:

**L7 Ingress**: routes by hostname and path. Terminates TLS. Can do rate limiting and rewriting. Deployed as a multi-replica Deployment. Has processes — can crash — so you need replicas.

**L4 Service**: TCP/UDP load balancing. Maintained by kube-proxy as iptables rules. Here's the key — there is no process. Just iptables rules in the Linux kernel. No process means nothing to crash. A K3s Service is more reliable than any user-space load balancer you'll ever write.

That's why K8s Services almost never fail. As long as the kernel is alive, traffic flows.

### What if you're on bare metal

If you're in the cloud, the cloud provider's LoadBalancer Service provisions a cloud load balancer automatically (AWS ELB, GCP LB, etc.). The providers handle HA for you.

If you're in your own data center, you need Keepalived + a floating IP:

Two physical load balancer machines. One holds a Virtual IP (VIP). They exchange heartbeats over the VRRP protocol. The primary dies, the backup seizes the VIP in 1-3 seconds. Clients always connect to the VIP and don't know the backend changed.

VRRP is old tech. It's been around for over two decades. It's boring, it's battle-tested, and it works.

## Consul: etcd's service-discovery cousin

Consul's own HA works basically the same as etcd's — Raft consensus, 3-5 node cluster, majority confirmation for writes.

The leader handles writes and replicates to followers. The leader dies, the remaining nodes elect a new one. 3 nodes, tolerate 1 failure.

What Consul adds on top is health checking.

Consul monitors registered service instances. An instance goes unhealthy → health check fails → Consul removes it from the DNS result set. Clients resolve service addresses through Consul DNS and automatically get only healthy instances.

This creates an automatic eviction pipeline:
Instance goes bad → Consul health check fails → DNS entry removed → client traffic never reaches the bad instance

All automatic. The caveat: your application code needs retries and circuit breakers. Consul tells you which instances are healthy. It doesn't handle what happens when your call to a healthy instance fails anyway. That's on you.

## Kafka: when BullMQ isn't enough

BullMQ handles most job queue scenarios well. But if you need "messages absolutely cannot be lost" semantics, look at Kafka.

Kafka's HA centers on **ISR — In-Sync Replicas**.

A topic has multiple partitions. Each partition has multiple replicas. One replica is elected the leader. Writes go to the leader, which replicates to followers.

Key point: not every follower is eligible to become leader. Only followers whose sync lag is within the configured threshold are in the ISR set. When the leader dies, the new leader is chosen only from the ISR — guaranteeing no data loss.

### The acks parameter: how safe do you need to be?

| acks     | What it means                                               | Safety                                         |
| -------- | ----------------------------------------------------------- | ---------------------------------------------- |
| 0        | Fire and forget. Don't even wait for the leader to receive. | Data loss possible                             |
| 1        | Leader acknowledges the write.                              | Data loss if leader crashes before replication |
| all (-1) | All ISR replicas confirm before acknowledging.              | Maximum                                        |

For maximum reliability, use `acks=all`. Tradeoff: higher write latency. This is the trade you make.

Kafka and BullMQ aren't competing. They solve different problems.

BullMQ: Redis-based, lightweight, job queue. Ideal for "process and mark done" job models. Your AI video generation pipeline lives here.

Kafka: own storage engine, append-only message log. Ideal for "multiple consumers with independent offsets" streaming scenarios. Event-driven architectures, data pipelines, log aggregation — these go to Kafka.

## Multi-AZ: when the whole building loses power

### Three tiers of failure domains

Get the terminology straight first:

- **Same AZ, multiple replicas**: multiple machines in the same data center. Protects against single machine failure. This is table stakes. Everyone should do this.
- **Cross-AZ deployment**: multiple data centers in the same city. Protects against a single data center losing power, network, or air conditioning. Latency between AZs: 1-3ms over dedicated lines.
- **Multi-region active-active**: different cities. Protects against city-level disasters. Latency: 20-50ms.

### The database cross-AZ pain point

Same-city cross-AZ latency is 1-3ms. PG master-replica sync is totally feasible. Put your replica in another AZ, fail over if the primary's AZ goes down.

Cross-city latency of 20-50ms is a different beast. With synchronous replication, every write waits for the cross-city replica to confirm. Your API response times just got 20-50ms worse. So cross-city can only be asynchronous.

This is the fundamental tension of multi-region: **consistency vs latency.**

If your use case is AI video generation and P99 latency tolerance is 200ms, the extra milliseconds from cross-AZ don't matter. If you're processing payments, 50ms of added latency is a real problem.

### Practical priorities for small to medium teams

Start with same-AZ HA: multiple nodes, multiple replicas, automatic failover. This covers 99% of failures you'll actually encounter.

Cross-AZ disaster recovery is your next step. You don't need real-time cross-AZ failover. At minimum, keep an async read replica in another AZ so you can restore if your primary AZ goes completely dark.

Multi-region active-active is a luxury. Most companies don't need it and can't afford to operate it.

## A framework you can actually use

This article isn't meant to be memorized. Next time you're evaluating a piece of middleware, run through these questions:

**1. What happens when it crashes?**

- Does it fail over by itself? If not, you need Patroni / Sentinel / K8s Deployments.
- Is it already clustered? Check whether the consensus protocol still has a majority.

**2. Can data be lost?**

- Async replication? You might lose the last few seconds.
- Sync replication? No data loss, but you pay for it in performance.
- Is persistence enabled? AOF? Raft log? WAL archiving?

**3. Is failure detection trustworthy?**

- One node saying something is down isn't enough. You need majority agreement to prevent split-brain.
- Are the detection nodes themselves HA? (3 Sentinels, 3 etcd nodes)

**4. How do we recover?**

- Do we have backups? (What's the RPO?)
- How long does recovery take? (What's the RTO?)
- Can replicas catch up automatically after reconnecting?

**5. Can we tolerate the worst case?**

- Are all control plane nodes on the same physical machine?
- Are all Sentinels in the same AZ?
- Acceptable probability × acceptable consequences = resources you should invest.

Run these five questions against any middleware, and you'll know exactly where you stand. You don't need to memorize configs. You just need to think.
