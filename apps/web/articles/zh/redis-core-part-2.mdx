### 背景

上篇讲完数据结构，你知道了 Redis 为什么快。但"快"有一个代价：Redis 默认把数据放在内存里，进程一退出，数据就没了。很多团队第一次遇到 Redis 重启是在一个平静的下午——有人执行了 `FLUSHALL`，或者运维升级了 Redis 版本，然后缓存全部消失，数据库被请求打穿，页面白屏。

更隐蔽的问题是高可用：Redis 单实例挂了，不只是缓存失效，分布式锁、排行榜、限流器全部跟着停摆。你可以在重启后把数据找回来，但"找回来之前"的每一秒，业务都在裸奔。持久化决定"重启后还剩什么"，高可用决定"挂了以后谁来顶上"。

这一篇讲 Redis 可靠性的两张王牌：持久化（RDB 与 AOF）和高可用（主从复制、哨兵、集群）。读完你能回答三个问题：我的 Redis 重启会丢多少数据？主节点挂了多久能恢复？数据量大了怎么水平扩展？这些都是上生产前必须想清楚的。

先建立一个统一的视角：持久化和高可用解决的是两个不同的"丢"——持久化解决"进程重启后数据还在"，高可用解决"机器挂了之后服务不断"。两者可以独立存在：只开持久化，重启不丢数据但宕机期间业务停摆；只做高可用，故障转移很快但主从都重启时数据可能全丢。生产环境的完整方案是"持久化兜底 + 复制冗余 + 哨兵自动切换"三层叠加，缺一层，都会在某个事故场景里暴露。

还有一个组织层面的现实：Redis 的可靠性配置通常是"上线时一次性设置"，之后很少有人再碰。这意味着初次配置的正确性至关重要——`appendonly yes` 少写一行，可能半年后的某次重启才被发现。把持久化和高可用配置写进部署模板和 checklist，而不是依赖每个开发者记得，是团队工程化的一部分。

本篇结构：RDB → AOF → 混合持久化 → 主从复制 → 哨兵与集群 → 选型表和陷阱 → 进阶方向。建议在测试环境完整演练一遍"kill 主节点"和"重启恢复"，可靠性不是读出来的，是练出来的。

### 核心原理

#### 第一层：RDB——全量快照

RDB 是 Redis 默认的持久化方式：按配置的时间间隔（比如 60 秒内 1000 次写）把内存数据生成一个二进制快照文件（dump.rdb）。恢复时直接加载快照，速度极快，文件体积也比 AOF 小。

RDB 的生成依赖 fork：主进程 fork 出子进程，子进程把内存快照写入磁盘，主进程继续服务。因为 Linux 的写时复制（COW），fork 瞬间不复制全部内存，但后续主进程每修改一个内存页，就会复制一页——所以写密集时 RDB 生成会带来瞬时内存和磁盘开销。fork 本身也有成本：实例内存越大，fork 越慢，大实例上可能阻塞数百毫秒。

RDB 的致命短板是"丢数据窗口"：两次快照之间的所有写操作都会丢。默认配置下可能丢几十秒甚至几分钟的数据。所以 RDB 适合"可以接受少量丢失"的场景（缓存），不适合"必须完整恢复"的场景（订单、余额）。

#### 第二层：AOF——追加式命令日志

AOF（Append Only File）把每次写命令追加到日志文件，恢复时重放命令。它把丢失窗口从"两次快照之间"缩小到"一次 fsync 之间"，取决于 `appendfsync` 策略：`always` 每条命令 fsync，最安全但最慢；`everysec` 每秒 fsync，最多丢 1 秒数据，是默认推荐；`no` 交给操作系统，性能最好但可能丢几秒。

AOF 的代价是文件无限增长，所以需要重写（rewrite）：用 BGREWRITEAOF 把当前内存状态压缩成最小命令集，类似"合并日志"。Redis 7.0 引入了多部分 AOF 和 manifest 管理，重写更安全、重启加载更快。

工程上的推荐是混合持久化：AOF 打开 + RDB 作为 AOF 重写的基础。Redis 4.0 之后支持 `aof-use-rdb-preamble`，AOF 文件头部是 RDB 快照、尾部是增量命令——兼顾 RDB 的加载速度和 AOF 的低丢失。生产环境默认配置应该是混合模式，而不是二选一。

AOF 重写还有一个"触发时机"的权衡：`auto-aof-rewrite-percentage`（默认 100）和 `auto-aof-rewrite-min-size`（默认 64MB）决定什么时候自动重写。触发太频繁浪费 CPU，触发太晚 AOF 文件过大、加载变慢。监控 AOF 文件大小和重写耗时，把重写安排在低峰期，是 Redis 运维的日常功课。

持久化还有一个"加载优先级"的细节：Redis 启动时，如果同时有 RDB 和 AOF，优先加载 AOF（数据更新）；AOF 文件损坏时，可以用 `redis-check-aof` 修复（截断尾部损坏部分），但会丢失尾部数据。备份策略上，RDB 文件要定期复制到异地（对象存储），AOF 不适合直接备份（实时变化）。把"启动恢复顺序"和"备份恢复流程"写进运维手册，事故时不用现想。

#### 第三层：主从复制——读的扩展与数据冗余

主从复制解决两个问题：数据冗余（从节点有完整副本）和读扩展（读请求打到从节点）。复制过程分两段：全量同步（主节点生成 RDB 传给从节点）和增量同步（复制积压缓冲区的命令流）。

复制的几个关键细节：从节点默认只读，写请求要打到主节点；复制是异步的，主从之间可能有毫秒级延迟，强一致读场景要注意；`repl-backlog-size` 太小会导致从节点断线后被迫全量重同步；主从版本要一致或从节点不低于主节点，否则可能复制失败。

主从复制的"全量同步"是性能事件：主节点要 fork 生成 RDB 传给从节点，期间内存和磁盘开销上升。从节点数量多或数据量大时，多个全量同步叠加会拖垮主节点——实践中"从节点的从节点"（链式复制）可以分散压力。还有一个安全细节：主从之间的连接要配置认证（requirepass + masterauth），否则公网环境会被未授权复制。

复制还有一个"读写分离的一致性"问题：从节点读到的数据可能比主节点旧（毫秒到秒级）。对"刚写入立即读"的业务，从节点可能返回旧值——这类读必须走主节点。用 `WAIT` 命令可以等从节点确认同步，但会阻塞，只在关键场景用。读写分离的收益（读扩展）和风险（读旧数据）要按业务场景权衡，不要无脑全站读写分离。

主从复制本身不提供故障转移：主节点挂了，从节点不会自动上位。这就是哨兵（Sentinel）的职责。

#### 第四层：哨兵与集群——自动故障转移与水平扩展

哨兵是一个独立进程，监控主从节点状态，主节点失联时自动把一个从节点提升为主节点，并通知客户端新主节点地址。哨兵要至少三个实例（奇数）才能形成多数派决策，防止"脑裂"——网络分区时，两个分区各自以为自己是主，数据就会分裂。

哨兵模式下，客户端通过哨兵获取当前主节点，主节点变更后需要重新获取。连接池和重试逻辑要处理"连接被拒/只读"的过渡期。脑裂的残余风险依然存在：主节点没死但网络分区，新主上位，旧主恢复后带着分区期间的新写入——Redis 官方用 `min-replicas-to-write` 参数缓解：主节点在失去多数从节点时拒绝写入，宁可不可用也不分裂。

集群（Cluster）解决的是水平扩展：数据按哈希槽（16384 个槽）分布到多个主节点，每个主节点配从节点。客户端根据 key 计算槽位，请求被重定向（MOVED/ASK）到正确节点。集群的代价是多键操作受限（跨槽的 `MGET`、事务、Lua 不保证原子），以及部分节点故障时相关槽位不可用。

集群还有一个容易被忽视的"数据迁移期"问题：在线扩缩容时，槽位在节点间迁移，客户端会收到 ASK 重定向，多一次往返；迁移窗口内，跨槽命令和某些一致性保证会临时变化。生产实践是把扩容放在低峰期，先用 `redis-cli --cluster rebalance` 在测试集群演练一遍，再在正式集群执行。集群不是"加个节点就完事"的银弹，它是一套需要运维纪律的分布式系统。

最后补一个高可用和持久化的组合细节：哨兵在故障转移后，新主节点的持久化配置必须和原主节点一致——如果新主节点没开 AOF，一次重启照样丢数据。高可用解决"切换"，持久化解决"切换后的数据安全"，两者要一起验收：模拟主节点宕机，确认新主节点上线、数据完整、客户端自动重连，才算一套可用的架构。

### 实战应用

#### 模式速查：方案选型表

| 场景                     | 方案                    | 理由              |
| ------------------------ | ----------------------- | ----------------- |
| 纯缓存，可接受重启丢数据 | RDB                     | 简单、加载快      |
| 缓存 + 少量丢失容忍      | 混合持久化              | 低丢失 + 快速恢复 |
| 数据必须尽量不丢         | AOF everysec + RDB 混合 | 最多丢 1 秒       |
| 读多写少                 | 主从复制                | 从节点分担读      |
| 主节点挂了要自动恢复     | 哨兵（3 节点）          | 自动故障转移      |
| 数据量大、单机扛不住     | 集群                    | 按槽位水平分片    |

#### 陷阱与正确做法

**陷阱一：持久化全关。** 反面案例：开发环境 Redis 不配持久化，上线时忘了改，一次重启缓存全部清空，数据库被打穿。正确做法：生产至少开混合持久化；缓存类数据也要有"重建预案"，不能指望内存永续。

**陷阱二：AOF everysec 还觉得慢。** 反面案例：误以为 `always` 才安全，每条命令 fsync，写性能掉一个量级。正确做法：`everysec` 是安全性和性能的平衡点；真不能丢的数据，靠复制 + 确认机制（WAIT）而不是让每个写都 fsync。

**陷阱三：哨兵只部署一个。** 反面案例：哨兵单实例，它挂了就没人监控主节点，故障转移形同虚设。正确做法：哨兵至少 3 个实例，分布在不同机器；客户端配置全部哨兵地址，任一个能连上就行。

**陷阱四：集群里用多 key 命令。** 反面案例：业务里 `MGET` 多个 key，集群模式下随机跨槽，命令直接报错。正确做法：用哈希标签（`{user:42}:cart`）让相关 key 落在同一槽；或拆分请求在客户端聚合；事务和 Lua 只对同槽 key 生效。

**陷阱五：主从延迟导致读到旧数据。** 反面案例：写主读从，刚写入就查，读到旧值，业务判断"写入失败"。正确做法：强一致读走主节点；从节点延迟用 `INFO replication` 的 `master_repl_offset` 监控，超过阈值告警；必要时用 WAIT 确认从节点同步。

**陷阱六：AOF 重写和快照同时触发。** 反面案例：高峰时段 AOF 重写和 RDB 快照同时进行，fork 两次，内存和磁盘双双告急，主节点阻塞。正确做法：错开定时任务窗口，用 `aof-rewrite-incremental-fsync` 和合理的 `auto-aof-rewrite-percentage` 控制重写频率；监控 `latest_fork_usec`，fork 耗时超过阈值就要考虑拆分实例或降配。

**陷阱七：备份只在本机。** 反面案例：RDB 文件存在同一台机器的磁盘上，机器损坏时备份一起消失。正确做法：定期把 RDB/AOF 文件同步到对象存储（S3/COS），保留多版本；恢复演练要真实执行一次"从备份重建实例"，确认备份不是摆设。

### 进阶思考

持久化与高可用组合起来，就是 Redis 生产架构的全貌：主节点承载写，从节点承载读和备份，哨兵管故障转移，集群管水平扩展。继续深入有三个方向。

一是读写分离的一致性边界：从节点延迟不可避免，哪些读可以接受延迟、哪些必须读主，要在业务层显式声明；不要"无脑读写分离"，热点 key 读从节点可能放大延迟问题。二是容量规划：单实例内存建议不超过物理内存的一半（给 fork 和 AOF 重写留余量），超过就分片；`maxmemory` 和淘汰策略必须配置，否则内存打满 Redis 直接拒绝写入。三是运维自动化：持久化文件的备份（快照 + 异地）、故障转移演练（主动 kill 主节点看哨兵反应）、版本升级流程（从节点逐个升级再切换），都要写成可重复的剧本。

学习路径：先在一个测试环境搭"主从 + 哨兵"最小架构，手动 kill 主节点观察故障转移过程；再打开 AOF 和 RDB 混合模式，重启实例验证恢复速度和丢失量；最后用 redis-cli 的 `--cluster create` 搭一个三主三从集群，跑一遍跨槽命令看报错。中篇到这里，下篇进入缓存策略与分布式锁——把 Redis 的"可靠性"用在业务正确性上。

如果只记一句话：Redis 的可靠性不是某个开关，而是一套"持久化 + 复制 + 哨兵/集群 + 备份演练"的组合拳。每一个环节单独看都很简单，但它们之间互相依赖——持久化决定恢复数据，复制决定切换时的副本，哨兵决定切换本身，备份决定灾难恢复。生产事故里 90% 的 Redis 数据丢失，都能回溯到这套组合拳里缺了一环。

再补一个"故障演练"的清单：季度演练一次主节点宕机（看哨兵切换时长和数据完整性）、半年演练一次整机宕机（看备份恢复流程）、上线前演练一次网络分区（看脑裂防护是否生效）。演练不是"走过场"，每次演练后要产出"发现的问题 + 改进项"——可靠性体系的成熟度，靠演练次数而不是文档页数衡量。

还有一个"客户端视角"的提醒：高可用是服务器的事，也是客户端的事——客户端要有正确的重试和超时（连接新主节点、处理 MOVED/ASK 重定向、区分"可重试"和"不可重试"错误）。很多故障转移"成功"但业务仍报错，是因为客户端没有正确跟随新的主节点。把客户端的故障转移测试写进集成测试，高可用才算闭环。

再补一段"哨兵 vs 集群"的选型细化：哨兵适合"单主多从、数据量单机装得下"的场景，它解决"主节点挂了自动切换"，不解决"数据量超过单机"；集群适合"数据量超过单机"的场景，它用分片解决问题，但引入多键限制和运维复杂度。选型判断顺序：数据量会不会超单机？会，直接集群；不会，哨兵更简单。不要"因为集群更高级"就跳过哨兵——简单性本身就是架构价值。

还有一个"持久化和高可用的联动测试"：故障转移后，新主节点的数据是否完整，取决于"主从复制延迟 + 持久化配置"——如果从节点落后主节点太多，切换就会丢数据。用 `INFO replication` 监控 `master_repl_offset` 差距，把"复制延迟"纳入告警，是 Redis 高可用的最后一公里。故障转移能"切"是一回事，切换后"数据不丢"是另一回事，两者都要验证。

最后补一段"恢复时间目标（RTO）"的设定：Redis 故障的恢复时间由三层决定——哨兵发现故障的时间（秒级）、新主节点接管的时间（秒级）、数据恢复的时间（看持久化）。给业务设一个明确的 RTO（比如 30 秒），然后反向设计每一层的超时和配置——没有 RTO 的可靠性设计，是"尽力而为"的另一种说法。

再补一段"数据丢失的三种场景"：Redis 的数据丢失不只发生在"进程崩溃"——还有三种常见场景：`FLUSHALL` 误执行（人为）、主从切换时从节点落后（复制延迟）、淘汰策略误删（maxmemory 设置不当）。每种场景的防御不同：FLUSHALL 用权限和审计（禁止生产执行）、切换丢数据用复制延迟监控、淘汰误删用合理的 maxmemory 和淘汰策略。把"数据丢失"按场景分类，防御才有针对性——"做好持久化"只是四分之一。

还有一个"容量和备份"的联动：Redis 备份（RDB）的恢复不是"拷回去就能用"——恢复时的内存需求和运行时的内存需求相同，备份机/恢复机的规格要按"峰值内存"规划，否则恢复过程中 OOM。恢复演练的意义就在于此：不是"备份能下载"，而是"备份能在目标机上跑起来"。把"恢复规格"写进备份文档，灾难恢复才不会卡在最后一步。

最后补一段"监控指标清单"：Redis 生产监控至少要有——内存（used_memory/碎片率）、连接（connected_clients 和 maxclients 比例）、命中率（keyspace_hits/misses）、复制（master_repl_offset 差距）、持久化（lastsave 时间、AOF 重写状态）、慢命令（slowlog 数量和耗时）。六个维度覆盖"容量、连接、效率、可靠"四个方向，接进告警后，Redis 的大部分问题都能在用户感知前被发现。

再补一句"中篇的收尾"：持久化让你"数据不丢"，复制让你"有冗余"，哨兵让你"自动切换"，集群让你"装得下"——四件事合起来，才是 Redis 的"生产形态"。但请记住，这套体系不是配置出来的，是演练出来的：只有亲手 kill 过主节点、重启过实例、恢复过备份，你才算真正拥有了它。文档给你知识，演练给你信心。

再补一句"给明天的行动"：今天就在测试环境做一次"主节点宕机演练"——kill 主节点，计时哨兵切换，验证客户端重连，记录数据完整度。一次演练半小时，但它会暴露你在文档里永远发现不了的配置问题。可靠性的差距，就是演练次数和文档页数的差距。

如果只记一句话：Redis 的可靠性不是某个开关，而是一套"持久化 + 复制 + 哨兵/集群 + 备份演练"的组合拳。每一个环节单独看都很简单，但它们之间互相依赖——持久化决定恢复数据，复制决定切换时的副本，哨兵决定切换本身，备份决定灾难恢复。生产事故里 90% 的 Redis 数据丢失，都能回溯到这套组合拳里缺了一环。
