### 背景

大多数团队的数据库成长路径是：上线时 SQL 都能跑，三个月后开始有慢查询，半年后索引越来越多但有些永远用不上，一年后遇到死锁和"查询突然变慢"。每次都是"加个索引试试""重启一下试试"，没有人真正回答过：为什么这条 SQL 没走索引？为什么事务隔离级别改了行为就变？为什么表越用越大？

这些问题的答案都藏在 PostgreSQL 的底层机制里：MVCC 决定数据怎么存、锁怎么协调；B-tree 索引决定查询怎么加速；事务隔离级别决定并发下你看到什么。不懂原理时，数据库调优是玄学；懂了原理后，大部分问题看一眼执行计划就能定位。

这篇文章是 PostgreSQL 系列的上篇，讲三块地基：存储与 MVCC、索引原理、事务与锁。实战部分给出一套慢查询排查路径和索引设计规则。下篇讲 pgvector 向量检索。读完上篇，你会理解"为什么加了这个索引就快了"，而不是只会照着模板建索引。

还有一个值得先建立的认知：PostgreSQL 不是"另一个 MySQL"。它们的 SQL 大体兼容，但事务模型、索引实现、复制方式和运维工具都不同——用 MySQL 的直觉去调 PostgreSQL，会踩不少隐性坑。比如 MySQL 的 InnoDB 用聚集索引（主键决定物理顺序），PostgreSQL 的表是堆表、索引独立存储；比如 MySQL 的默认隔离级别是可重复读，PostgreSQL 是读已提交。这些差异不是小事，它们决定了你在什么场景下会遇到什么问题。

这个系列的定位是"实战原理"：不贴大段源码，但会把机制讲到你能够推理的程度。数据库面试里最常见的"为什么这条 SQL 慢"，本质上都是执行计划和索引原理的问题；而生产事故里最常见的"数据库突然变慢"，多半是膨胀、锁等待和统计信息过期。两类问题，这篇文章都会覆盖。

### 核心原理

#### 第一层：MVCC——读不阻塞写，写不阻塞读

PostgreSQL 用多版本并发控制（MVCC）实现并发读写：每行数据有 `xmin`（创建它的事务 ID）和 `xmax`（删除它的事务 ID），事务读取数据时，根据自己事务的快照判断"这一行对我可见吗"。因为旧版本和新版本可以并存，读操作不需要锁，写操作也不需要等读——这是 PostgreSQL 高并发读写的根基。

MVCC 的直接代价是"膨胀"：更新一行不是覆盖，而是插入新版本，旧版本留在页面里等清理。负责清理的是 VACUUM：它回收死元组占用的空间，更新统计信息，防止事务 ID 回卷。不理解 VACUUM，你会在"表越来越大、查询越来越慢"里打转——这不是数据泄露，是旧版本没清理。

工程上关于 VACUUM 的三条常识：自动 VACUUM 默认开启但要在负载低时跑；长事务会阻止清理（事务结束前，它还可能看到旧版本）；膨胀严重时用 `VACUUM FULL` 或 `pg_repack` 重建表。判断膨胀的 SQL 是查 `pg_stat_user_tables` 的 `n_dead_tup` 和 `n_live_tup` 比例。

MVCC 还有一个"事务 ID 回卷"的隐藏炸弹：事务 ID 是 32 位整数，会循环使用；如果 VACUUM 没有及时冻结（freeze）旧事务 ID，数据库会进入"紧急模式"甚至拒绝写入。这是 PostgreSQL 最可怕的运维事故之一，但预防很简单——保持自动 VACUUM 开启、监控 `age(datfrozenxid)`、对超大表定期手动 VACUUM。理解 MVCC，不只是理解"读不阻塞写"，还包括"清理是生命线"。

和 MVCC 配套的还有一个"快照"概念：每个事务看到的是"某个时刻的数据库状态"。事务 ID 和快照的组合，决定了"我能看到哪些行"。长事务持有旧快照，意味着旧版本不能被清理——所以"长事务"在 PostgreSQL 里不只是资源问题，还会让整个表膨胀。监控 `pg_stat_activity` 里超过阈值的事务，是 PostgreSQL 运维的必修课。

#### 第二层：B-tree 索引——为什么最左前缀、为什么失效

PostgreSQL 默认索引是 B-tree，适合等值、范围、排序。理解 B-tree 索引，关键是理解"索引是有序的目录"：查询时先走目录定位，再回表拿整行。索引不是越多越好，每条索引都有写入成本和存储成本。

联合索引（`(a, b, c)`）的三条规则：最左前缀——查询必须从第一个字段开始用，`WHERE b = 1` 用不上这个索引；范围之后失效——`WHERE a = 1 AND b > 2 AND c = 3` 中 `c` 的等值条件在 `b` 的范围条件之后，无法继续用索引；覆盖索引——索引包含查询需要的所有列时，不用回表，`EXPLAIN` 里出现 `Index Only Scan` 就是命中。

索引失效的四个高频场景：隐式类型转换（`WHERE varchar_col = 123` 会禁用索引，因为要转类型）；函数包裹列（`WHERE lower(name) = 'max'` 走不了普通索引，需要表达式索引）；`LIKE '%xxx'` 前导通配符；`OR` 拆分条件导致优化器选择全表扫。排查时先 `EXPLAIN` 看执行计划，再决定是改 SQL 还是加索引，不要凭直觉。

索引的选择性（selectivity）也是理解索引的一把钥匙：一个列的去重值越多，选择性越高，索引的价值越大。`性别` 这种只有两个值的列，索引选择性低，优化器常常宁可全表扫——这是"我建了索引为什么不生效"的另一个高频原因。真正值得建索引的是高选择性的过滤列、外键列和排序列；低选择性列要靠组合索引或位图思路解决，而不是单列索引硬上。

索引的"写入成本"也值得量化：每条索引都让 INSERT/UPDATE 变慢（要维护索引结构），所以"多建索引"不是免费的。一张表上 5 个索引和 15 个索引，写入性能可以差一倍。工程原则是"按查询建索引、按写入控数量"：新索引上线前，先想清楚它服务哪条查询，并用 `pg_stat_user_indexes` 定期清理从未被使用的索引。

还有一个高级索引类型值得知道：GIN 索引用于全文搜索（tsvector）、数组和 JSONB 的包含查询；BRIN 索引适合"物理顺序和时间顺序一致"的超大表（日志表）。大多数场景 B-tree 就够，但知道 GIN/BRIN 的存在，遇到搜索和日志类查询时你不会只会建 B-tree。

索引的选择性（selectivity）也是理解索引的一把钥匙：一个列的去重值越多，选择性越高，索引的价值越大。`性别` 这种只有两个值的列，索引选择性低，优化器常常宁可全表扫——这是"我建了索引为什么不生效"的另一个高频原因。真正值得建索引的是高选择性的过滤列、外键列和排序列；低选择性列要靠组合索引或位图思路解决，而不是单列索引硬上。

#### 第三层：事务与隔离级别——并发下你看到什么

事务保证 ACID，但隔离级别决定"并发事务之间能互相看到什么"。PostgreSQL 的默认级别是读已提交（Read Committed）：每个语句开始时取一次快照，同一事务里两次查询可能看到不同数据。可重复读（Repeatable Read）在事务开始时取快照，整个事务看到一致视图——这是报表、对账类逻辑的正确选择。

隔离级别的经典陷阱是"以为可重复读就没有并发问题"：可重复读解决的是"读一致性"，不解决"写冲突"——两个事务同时更新同一行，后提交的会收到"could not serialize access due to concurrent update"错误。工程上的处理是重试：检测到序列化冲突，回滚重试整个事务，而不是当成数据库故障。

锁与死锁是另一块：行锁在事务提交/回滚时释放，长事务等于长锁；死锁由数据库检测并回滚其中一个事务。减少死锁的实践：多个表的更新按固定顺序、事务尽量短、大事务拆小。死锁不可怕，可怕的是"不知道有死锁"——`log_min_messages` 打开死锁日志，是排查的第一步。

锁的"等待链"是排障的核心：`pg_locks` 和 `pg_stat_activity` 配合，能看出"谁在等谁的锁"。经典场景是"一条 UPDATE 卡住"——上游事务没提交，下游都在等它。排查顺序：找到卡住的查询 → 查它等待的锁 → 找到持锁事务 → 判断是"业务需要"还是"泄漏"。ORM 的长事务（连接池里没提交）是持锁大户，监控 `idle in transaction` 连接是标准手段。

隔离级别的选择还有一个"业务正确性"视角：读已提交适合"每次都看最新数据"的场景；可重复读适合"事务内一致快照"（报表、对账）；串行化（Serializable）提供最强保证但性能代价大，只在确实需要时才用。不要无脑用最高的隔离级别——隔离级别的选择是"一致性需求 vs 并发性能"的权衡，不是"越安全越好"。

#### 第四层：查询计划——让数据库告诉你它怎么干

`EXPLAIN ANALYZE` 是 PostgreSQL 最实用的调优工具：它实际执行 SQL 并输出每步的耗时、行数估计和实际行数。读执行计划的核心是看三件事：有没有全表扫描（Seq Scan）应该走索引；估计行数和实际行数差异大不大（统计信息过期）；哪个节点耗时最长（通常是嵌套循环里反复扫描）。

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 42;
```

调优的顺序是：先看执行计划确认瓶颈，再检查统计信息（`ANALYZE`）、索引设计、SQL 写法，最后才考虑改表结构（冗余字段、汇总表）。数据库调优 80% 的问题在执行计划里已经写明答案，只是很多人没养成"先 EXPLAIN 再动手"的习惯。

执行计划里还有几个高频词汇要会读：`Nested Loop`（对每一行去另一个表查一次，小表驱动大表没问题，大表没索引就是灾难）、`Hash Join`（把一张表哈希进内存再匹配，通常比嵌套循环快）、`Sort`（排序没走索引时会出现，大数据量排序很贵）、`Bitmap Index Scan`（索引选择性不高时，先拿位图再回表）。看到这些词，你能判断"数据库为什么选了这个方案"，也能理解"加索引为什么能改变选择"。

执行计划还有一个"估计 vs 实际"的对比技巧：`EXPLAIN` 显示估计行数，`EXPLAIN ANALYZE` 显示实际行数。两者差异大（比如估计 100 行实际 10 万行），说明统计信息过期或查询写得太复杂——先 `ANALYZE` 更新统计，再看计划是否改变。统计信息是优化器的"眼睛"，眼睛瞎了，再好的索引也用不对。

#### 检查清单：慢查询治理流程

| 步骤 | 动作         | 工具                        |
| ---- | ------------ | --------------------------- |
| 1    | 找出慢 SQL   | pg_stat_statements          |
| 2    | 看执行计划   | EXPLAIN ANALYZE             |
| 3    | 检查统计信息 | ANALYZE                     |
| 4    | 检查索引设计 | pg_stat_user_indexes        |
| 5    | 检查锁等待   | pg_locks / pg_stat_activity |
| 6    | 检查表膨胀   | n_dead_tup 比例             |
| 7    | 验证优化效果 | 前后耗时对比                |

七步走完，慢查询治理就从"碰运气"变成了"流程化"。

### 实战应用

#### 模式速查：慢查询排查路径

| 步骤          | 动作                            | 判断依据                 |
| ------------- | ------------------------------- | ------------------------ |
| 1. 找到慢 SQL | `pg_stat_statements` 按耗时排序 | 最耗时的前 10 条         |
| 2. 看执行计划 | `EXPLAIN (ANALYZE, BUFFERS)`    | Seq Scan？行数估计偏差？ |
| 3. 检查索引   | 是否命中、是否覆盖、是否失效    | Index Scan 还是 Seq Scan |
| 4. 检查统计   | `ANALYZE` 更新统计信息          | 估计 vs 实际行数差异     |
| 5. 检查锁     | `pg_locks` 看阻塞链             | 谁锁了谁，等了多久       |
| 6. 检查膨胀   | `pg_stat_user_tables`           | n_dead_tup 占比过高      |

#### 陷阱与正确做法

**陷阱一：索引凭感觉加。** 反面案例：每遇到一条慢查询就加一个索引，一年后几十个索引，写入变慢、磁盘膨胀，很多索引从没用过。正确做法：用 `pg_stat_user_indexes` 查索引使用率，长期未使用的索引删除；新索引先建在 staging 验证执行计划再上线。

**陷阱二：忽略隐式类型转换。** 反面案例：`WHERE phone = 13812345678`，phone 是 varchar，PostgreSQL 把列转成数字，索引失效，全表扫。正确做法：参数类型和列类型保持一致（`'13812345678'`），或建对应类型的索引；类型混用是"索引明明存在却不生效"的头号原因。

**陷阱三：长事务不提交。** 反面案例：连接池里一个事务开着几小时（ORM 事务没提交、长轮询包在事务里），VACUUM 无法清理，表膨胀到几十 GB。正确做法：事务保持短小，ORM 里显式提交/回滚；监控 `pg_stat_activity` 里 `state = 'idle in transaction'` 的连接，超过阈值告警。

**陷阱四：隔离级别选错。** 反面案例：报表逻辑用读已提交，两次查询之间数据变化导致数字对不上，业务侧"修"了半天以为是 bug。正确做法：对账、报表、需要一致快照的逻辑用可重复读；写冲突用重试机制兜底，而不是降低隔离级别。

**陷阱五：`LIMIT` 大偏移量。** 反面案例：分页用 `OFFSET 100000`，数据库要扫过前十万行再丢弃，越翻越慢。正确做法：用"键集分页"（`WHERE id > last_id ORDER BY id LIMIT 20`），或基于游标的分页，让每页查询都走索引定位。

**陷阱六：删除数据不回收空间。** 反面案例：`DELETE FROM logs WHERE ...` 删了几百万行，磁盘占用没降，因为 MVCC 的死元组要等 VACUUM 才回收。正确做法：大批量删除后手动 `VACUUM (VERBOSE)` 或 `VACUUM FULL`；按时间分区的表直接 `DROP PARTITION`，秒级释放空间，是日志类数据的最优解。

**陷阱七：连接池参数和事务长度不匹配。** 反面案例：连接池设置了 10 分钟空闲超时，但业务里存在"查询 + 慢处理 + 再查询"的长事务，连接被池回收时事务还在跑，数据库端事务悬挂。正确做法：连接池的超时和数据库的 `idle_in_transaction_session_timeout` 一起配置；事务边界在代码里明确，避免把外部调用包进数据库事务。

### 进阶思考

PostgreSQL 的地基理解之后，值得深入三个方向。一是分区表：按时间分区的日志表、订单表，让查询只扫对应分区（partition pruning），是"数据量大到单表扛不住"的标准解法；注意分区键要匹配查询条件，否则还是全扫。二是并行查询：`max_parallel_workers_per_gather` 让大查询用上多核，但小查询上并行反而有调度开销，要按查询类型区分。三是 WAL 与复制：WAL 是崩溃恢复和流式复制的基石，理解它才能理解"同步复制为什么慢、异步复制为什么会丢数据"——这是下篇 pgvector 和后续高可用实践的基础。

学习路径：先把你项目里最慢的三条 SQL 拿出来，逐一 `EXPLAIN ANALYZE` 并记录瓶颈；再给每张核心表做一次索引审计（哪些在用、哪些没用）；最后在测试环境故意制造一次死锁，打开日志看数据库怎么处理。数据库调优没有银弹，但"先看执行计划、再动索引、最后改结构"这个顺序，能让你少走 90% 的弯路。

实践时给自己定三条验收线：每条慢查询都能说出"瓶颈在哪个节点"；每张核心表的索引都有使用率数据支撑；每个事务都明确"为什么是这个隔离级别"。三条线过了，你的 PostgreSQL 认知就不再依赖"网上教程说加索引"这种二手经验，而是能自己从执行计划里读出答案。

结语：PostgreSQL 是"可推理的系统"，它的每个行为都有原因——慢有执行计划，锁有等待链，膨胀有死元组。学会读这些信号，你就从"数据库用户"变成了"数据库使用者"：前者遇到问题求助，后者自己定位。上篇的地基打牢，下篇 pgvector 的向量检索就不会让你觉得是另一个世界。

再补一个"日常体检"的清单：每周花十分钟看四个数字——慢查询数量（pg_stat_statements）、死元组比例（膨胀）、连接数（是否接近上限）、长事务数量（idle in transaction）。四个数字正常，数据库大概率健康；任何一个异常，就是本周的运维任务。数据库不是"出事了才管"，是"每周体检"。

最后补一段"和开发协作"的建议：数据库的变更（加索引、改表结构）应该和代码一样走评审——写一份"变更说明"（为什么、影响什么、怎么回滚），让懂数据库的人 review 后再执行。很多数据库事故不是"技术不行"，而是"变更没评审"。把数据库变更纳入代码评审流程，是成本最低的数据库治理手段。

再补一段"连接池的正确姿势"：应用侧的连接池（PgBouncer 或应用内池）和数据库侧的 `max_connections` 要配套设计——连接池防的是"应用创建太多连接打爆数据库"，不是"数据库连接数越多越好"。常见事故是"连接池 200、数据库 max_connections 100"，应用一启动就报 too many connections。设计原则：应用连接数 < 数据库上限，且每个应用实例的连接数按实例数分摊。

最后补一段"从慢查询到架构"的进阶视角：单条 SQL 优化到极限后，如果业务还是慢，就要看架构——是不是查询该走缓存（Redis）、该走搜索（ES）、该改异步（消息队列）、该换存储（对象存储/列存）。数据库是"最后一道防线"，不是"唯一的数据方案"。上篇的调优让你把数据库用到位，架构层让你知道什么时候该"绕开数据库"——两件事合起来才是数据层的完整能力。

再补一段"PostgreSQL 生态的延伸"：学会了 PostgreSQL 核心，你的知识能自然延伸到它的生态——PostGIS（地理）、pgvector（向量，下篇）、Citus（分布式）、TimescaleDB（时序）、逻辑复制与变更捕获（Debezium）。这些扩展共享同一个内核心智（MVCC、事务、SQL），学一个核心，扩展都是"加字段"的难度。这也是"选择一个成熟数据库"的长期收益——生态和社区会持续放大你的投入。

最后补一段"运维与开发的协作界面"：数据库的运维和开发之间需要一张"接口表"——连接串怎么给、迁移谁执行、备份谁负责、慢查询谁看、权限谁申请。接口表写清楚，开发和运维就不会互相甩锅；没有接口表，一次"谁改的表结构"就能吵一天。把"数据库接口表"写进团队文档，比任何技术方案都能更快地改善数据库相关的协作效率。

再补一句"上篇的收尾"：PostgreSQL 的三块地基（MVCC、索引、事务）你已经学完，加上查询计划，你已经有了"自己推理数据库行为"的能力。下篇的 pgvector 会在这个基础上展开，但即使你不做向量检索，上篇的能力也足够你应付日常的慢查询、锁等待和膨胀问题。数据库不是黑盒，你现在有了打开它的钥匙。

再补一句"给行动的建议"：今天拿一条你项目里最慢的 SQL，跑一遍 `EXPLAIN ANALYZE`，写下瓶颈节点和优化计划。一个动作，把"我读过数据库原理"变成"我会读数据库执行计划"——这一步，就是用户和工程师的区别。

实践时给自己定三条验收线：每条慢查询都能说出"瓶颈在哪个节点"；每张核心表的索引都有使用率数据支撑；每个事务都明确"为什么是这个隔离级别"。三条线过了，你的 PostgreSQL 认知就不再依赖"网上教程说加索引"这种二手经验，而是能自己从执行计划里读出答案。

最后记住一个心态：PostgreSQL 不是你代码的"外部黑盒"，它是一套可以推理的系统。每个查询都有执行计划，每个慢查询都有原因，每个锁都有持有者——只要你愿意花十分钟读它给你的信息。这个系列的上篇到这里，下篇我们进入 pgvector，把向量检索接到同一套数据库里。
