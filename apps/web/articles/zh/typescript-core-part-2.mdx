### 背景

上篇讲完底层逻辑，你大概已经能看懂 `keyof`、`typeof`、联合和泛型。但打开项目里的类型文件，你还会遇到另一批东西：`Partial<Config>`、`Pick<T, K>`、`ReturnType<typeof fn>`，以及一些长得像"天书"的自定义类型——里面全是 `T extends ... ? ... : ...` 和 `infer`。

这些不是语言特性展览，是真实需求逼出来的。配置对象要部分更新，接口响应要统一包装，事件名要能被编译器检查，函数返回类型要自动推导——每个场景都需要一种"类型的函数"：输入一个类型，输出另一个类型。工具类型就是 TypeScript 官方预置的类型函数，类型体操就是你按同样规则自己写的类型函数。

这一篇的目的很直接：让你能读懂项目里 90% 的类型代码，并且有能力写出自己需要的工具类型。中篇只讲三块：内置工具类型怎么用、条件类型和 `infer` 怎么工作、模板字面量类型能干什么。看完你会发现，类型体操不是炫技，是让类型跟着业务走的正常手段。

在深入之前，先回答一个心态问题："类型体操是不是只有写库的人才需要？"答案是否定的。日常项目里，你迟早会遇到这些需求：接口的字段要按权限裁剪、表单的错误类型要跟着字段走、配置对象要保留字面量类型、事件名要能被编译器检查。这些需求的共同点是"类型要根据输入变化"，而"根据输入变化"就是工具类型和条件类型的本职。你可以不成为类型体操选手，但读懂它们，是绕过 `as any` 的唯一路径。

还有一个学习顺序的建议：先会用，再懂原理。内置工具类型先用起来（`Partial`、`Omit`、`Record`），用出疑问了再去看手写实现——"为什么 Partial 能把这些字段变可选"这个问题，会自然把你引向映射类型和 `keyof`。从使用到原理的顺序，比从原理到使用更容易坚持，也更符合工程师的认知习惯。

举个具体的例子。你的表单状态是 `{ name: string; email: string; age: number }`，用户每改一个字段只提交一部分，接口的更新模型是 `Partial<FormState>`；你的事件总线有 `click`、`input`、`submit` 三种事件，想用 `Record<EventName, Handler>` 约束每个事件的处理函数签名；你的 API 层想统一返回 `{ data: T; error: string | null }`，让调用方拿到 `T` 而不是任何类型。这三件事靠手写具体类型会写三遍，用工具类型各写一行。类型函数的存在意义，就是让"类型层面的复用"和"值层面的复用"拥有同等的地位。

再看一个反面例子，感受"没有工具类型"的世界：某项目里表单更新函数写了五个重载，分别处理"只改 name""只改 email""只改 age""改 name 和 email""改 email 和 age"，新增一个字段就要再加两个重载。用 `Partial<FormState>` 一行替代后，五个重载变成一句 `Partial<FormState>`，新增字段零成本。这就是类型函数复用的价值——它消灭的不是语法，是组合爆炸。

### 核心原理

#### 第一层：内置工具类型——先会用，再问为什么

所有内置工具类型都是"类型函数"，输入类型、输出类型。日常用到频率最高的十个，按用途分成四组。

第一组是"改属性"：`Partial<T>` 把所有属性变成可选，`Required<T>` 把可选变成必填，`Readonly<T>` 把所有属性变成只读。配置对象、表单状态、不可变数据都会用到。

第二组是"选属性"：`Pick<T, K>` 从 T 里挑出 K 这些键，`Omit<T, K>` 排除 K 这些键。接口返回给前端时不想暴露内部字段，`Omit` 一行解决。

第三组是"造对象"：`Record<K, V>` 用键联合 K 和值类型 V 构造对象，是定义"枚举到配置"映射的最快方式。

第四组是"集合运算"：`Exclude<T, U>` 从 T 里排除 U，`Extract<T, U>` 保留交集，`NonNullable<T>` 去掉 `null | undefined`。

```ts
type Config = { url: string; retries?: number }
type PartialConfig = Partial<Config> // url 和 retries 都可选
type PublicUser = Omit<User, 'passwordHash'>
type StatusMap = Record<'pending' | 'done' | 'failed', string>
type NoNull = NonNullable<string | null | undefined> // string
```

这十个工具类型不是要背的，用两个月自然就记住了。真正值得理解的是它们背后的三个原语：`keyof`、索引访问类型 `T[K]`、映射类型 `[K in keyof T]`。`Partial` 的手写版本就是这三个原语的组合：

```ts
type MyPartial<T> = {
  [K in keyof T]?: T[K]
}
```

看懂这一行，工具类型就不是黑盒了：遍历 T 的所有键，每个键的值保持原类型，属性加上可选标记。

映射类型还有两个容易混淆的细节：`-?` 修饰符和 `readonly` 修饰符。`Partial<T>` 本质是给每个属性加 `?`，`Required<T>` 本质是 `-?`（去掉可选标记），`Readonly<T>` 是加 `readonly`，`-readonly` 则去掉只读。这些修饰符可以组合，比如 `type Mutable<T> = { -readonly [K in keyof T]: T[K] }`。理解修饰符的加减法，内置工具类型在你眼里就不再是"二十个黑盒"，而是一套可推导的规则。

`keyof` 和映射类型还有一个搭配技巧：`keyof any` 的类型是 `string | number | symbol`，当你想写"任意键"的约束时（`K extends keyof any`），它比 `string` 更准确——因为对象的键本来就可以是数字和 symbol。这个细节在实现通用工具类型时经常出现，记住它能少踩一个"为什么 symbol 键被漏掉"的坑。

映射类型还有两个容易混淆的细节：`-?` 修饰符和 `readonly` 修饰符。`Partial<T>` 本质是给每个属性加 `?`，`Required<T>` 本质是 `-?`（去掉可选标记），`Readonly<T>` 是加 `readonly`，`-readonly` 则去掉只读。这些修饰符可以组合，比如 `type Mutable<T> = { -readonly [K in keyof T]: T[K] }`。理解修饰符的加减法，内置工具类型在你眼里就不再是"二十个黑盒"，而是一套可推导的规则。

`keyof` 和映射类型还有一个搭配技巧：`keyof any` 的类型是 `string | number | symbol`，当你想写"任意键"的约束时（`K extends keyof any`），它比 `string` 更准确——因为对象的键本来就可以是数字和 symbol。这个细节在实现通用工具类型时经常出现，记住它能少踩一个"为什么 symbol 键被漏掉"的坑。

映射类型还有两个进阶能力：键名重映射（`as`）和键值过滤。`{ [K in keyof T as K extends 'id' ? never : K]: T[K] }` 可以把特定键从结果中剔除，等价于手写 `Omit` 的底层实现。日常写业务代码很少需要直接造映射类型，但读懂它们，遇到"为什么这个工具类型行为不一样"时就不会懵。

#### 第二层：条件类型与分发——类型世界的 if/else

条件类型的语法是 `T extends U ? X : Y`，含义是"如果 T 能赋值给 U，结果是 X，否则是 Y"。它和泛型约束长得像，但作用完全不同：约束是在入口挡住不合格的类型，条件类型是在出口按输入计算结果。

```ts
type IsString<T> = T extends string ? true : false
type A = IsString<'hello'> // true
type B = IsString<number> // false
```

条件类型最反直觉的是分发（distributive）：当 `T` 是一个裸类型参数时，TypeScript 会把联合类型的每个成员分别代入计算，再把结果合并成联合。这是"为什么结果和我预期不一样"的头号来源。

```ts
type ToArray<T> = T extends unknown ? T[] : never
type R1 = ToArray<string | number> // string[] | number[]（分发）

type ToArrayNoDistribute<T> = [T] extends [unknown] ? T[] : never
type R2 = ToArrayNoDistribute<string | number> // (string | number)[]（不分发）
```

第一行结果是 `string[] | number[]`，第二行是 `(string | number)[]`。差别在于 `[T]` 把裸类型参数包进了元组，分发机制就停用了。什么时候需要停用？当你希望把整个联合当做一个整体处理，而不是拆开逐项处理时。

分发的另一个隐藏规则和 `never` 有关：`never` 是空联合，条件类型对它分发时不会产生任何分支，结果直接是 `never`。这解释了为什么 `Exclude<T, never>` 这类写法会得到 `T` 本身，也解释了为什么"结果莫名变成 never"往往是输入里混进了空类型。排查时把输入拆开，逐个成员测试，比盯着输出猜快得多。

条件类型还有一个容易被忽视的能力：它是"类型级逻辑"的载体，可以组合出复杂的类型分支。比如"如果 T 是数组就取元素类型，否则返回 T 本身"——`T extends Array<infer U> ? U : T`。再比如"如果 T 是函数就取返回类型"——`T extends (...args: any[]) => infer R ? R : never`。当你发现自己在业务代码里反复写同一类"按输入分形状"的判断时，就是把它抽成条件类型的时候。

#### 第五层：条件类型高级模式——infer 与递归的组合拳

条件类型和 `infer` 组合，可以解决一类非常实际的问题：从复杂类型里"提取"信息。除了 `ReturnType` 和 `Unwrap`，还有三个高频模式值得掌握。

第一个是"取 Promise 数组的元素类型"：`type ArrayElement<T> = T extends Promise<infer U>[] ? U : never`，配合 `Promise.all` 的结果类型使用。第二个是"取函数的第一个参数类型"：`type FirstArg<T> = T extends (arg: infer A, ...rest: any[]) => any ? A : never`，常用于事件处理函数和依赖注入场景。第三个是"从联合类型中提取特定形状"：`type ExtractByKind<T, K extends string> = T extends { kind: K } ? T : never`，在事件总线、消息系统里按类型筛选事件。

这些模式的共同套路是"extends + infer + 递归"三件套：用 `extends` 匹配形状，用 `infer` 提取片段，必要时递归深入。掌握这个套路，你会发现自己能"读懂"几乎所有第三方库的类型声明——它们 90% 都是这三件套的组合。

#### 第六层：递归类型的实战边界

递归类型是类型体操里"收益最高也最危险"的部分。收益在于它能表达"任意深度"的结构（树、嵌套对象、Promise 链）；危险在于递归深度有上限，滥用会导致"Type instantiation is excessively deep"。

实战中最常用的是 `DeepPartial` 和 `DeepReadonly`：把嵌套对象的所有层都变成可选/只读。它们的写法是"先处理当前层，再递归处理属性值"：

```ts
type DeepPartial<T> = {
  [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K]
}
```

写递归类型有三条纪律：第一，终止条件必须清晰（基本类型、函数、数组要单独处理，否则无限递归）；第二，深度控制在三层以内，超过三层考虑拍平数据结构而不是继续递归；第三，递归类型要配注释说明"递归到哪里停"。遵守这三条，递归类型是利器；违反，它就是编译性能的定时炸弹。

条件类型还有一个容易被忽视的能力：它是"类型级逻辑"的载体，可以组合出复杂的类型分支。比如"如果 T 是数组就取元素类型，否则返回 T 本身"——`T extends Array<infer U> ? U : T`。再比如"如果 T 是函数就取返回类型"——`T extends (...args: any[]) => infer R ? R : never`。当你发现自己在业务代码里反复写同一类"按输入分形状"的判断时，就是把它抽成条件类型的时候。

#### 第五层：条件类型高级模式——infer 与递归的组合拳

条件类型和 `infer` 组合，可以解决一类非常实际的问题：从复杂类型里"提取"信息。除了 `ReturnType` 和 `Unwrap`，还有三个高频模式值得掌握。

第一个是"取 Promise 数组的元素类型"：`type ArrayElement<T> = T extends Promise<infer U>[] ? #### 第六层：递归类型的实战边界

递归类型是类型体操里"收益最高也最危险"的部分。收益在于它能表达"任意深度"的结构（树、嵌套对象、Promise 链）；危险在于递归深度有上限，滥用会导致"Type instantiation is excessively deep"。

实战中最常用的是 `DeepPartial` 和 `DeepReadonly`：把嵌套对象的所有层都变成可选/只读。它们的写法是"先处理当前层，再递归处理属性值"：

```ts
type DeepPartial<T> = {
  [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K]
}
```

写递归类型有三条纪律：第一，终止条件必须清晰（基本类型、函数、数组要单独处理，否则无限递归）；第二，深度控制在三层以内，超过三层考虑拍平数据结构而不是继续递归；第三，递归类型要配注释说明"递归到哪里停"。遵守这三条，递归类型是利器；违反，它就是编译性能的定时炸弹。

#### 第三层：infer——从类型里提取类型

`infer` 是条件类型里的模式匹配：在 `extends` 的右边声明一个"待推断"的位置，TypeScript 会从输入类型里把那一部分抠出来。官方 `ReturnType` 就是标准范例：

```ts
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never

type Fn = (a: number, b: string) => boolean
type R = MyReturnType<Fn> // boolean
```

`infer R` 相当于说"不管这个函数返回什么，把它存到 R 里"。`infer` 只能出现在条件类型的 extends 子句中，而且通常配合递归使用。取 Promise 里的值类型是另一个高频场景：

```ts
type Unwrap<T> = T extends Promise<infer U> ? Unwrap<U> : T
type A = Unwrap<Promise<Promise<number>>> // number
```

这里 `Unwrap` 递归调用自己，直到不再满足 `Promise` 形状。递归类型能解决"嵌套结构取类型"的问题，但也要付出编译性能的代价：深度超过 TypeScript 的限制会直接报"类型实例化过深"。

递归条件的边界要想清楚：什么时候该停？大多数递归类型以"不再是目标形状"为终止条件，但有些类型（比如 `DeepPartial`）会递归到对象的最底层，遇到函数、数组、基本类型才停。数组元素和对象属性都要单独处理，否则会出现"递归不下去或者绕回来"的死循环。项目里递归类型超过两层，就值得写注释说明终止条件，否则三个月后没人敢改。

#### 第四层：模板字面量类型——把字符串变成类型约束

模板字面量类型用反引号声明，`${}` 里可以放字面量联合或类型。它能做的事，是把"字符串拼写错误"从运行时错误变成编译错误。

```ts
type EventName = `on${'Click' | 'Change' | 'Input'}`
const good: EventName = 'onClick' // 合法
const bad: EventName = 'onclick' // 报错

type Route = `/${string}`
const home: Route = '/home' // 合法
const wrong: Route = 'home' // 报错：必须以 / 开头
```

内置的 `Capitalize`、`Uncapitalize`、`Uppercase`、`Lowercase` 都是模板字面量的配合工具，比如把 `'click'` 变成 `'Click'` 再拼出事件名。这套能力在表单字段名映射、组件事件命名、路由类型上非常有用，但不要过度——类型约束的事件名一旦超过十几个，维护成本会明显上升。

模板字面量类型和 `as const`、`satisfies` 是黄金组合：先用 `as const` 把配置对象变成字面量类型，再用 `satisfies` 检查它符合某个宽类型，最后用模板字面量派生出事件名联合。三段各管一件事——保留字面量、检查形状、派生约束，比在一处写死二十个字符串好维护得多。

模板字面量还有一个进阶用法：把"命名规范"变成类型约束。比如日志级别 `'info' | 'warn' | 'error'` 和前缀拼成 `type LogEvent = `log:${Level}``，任何写错的事件名都在编译期暴露；再比如国际化 key 用 `type I18nKey = `${'home' | 'about'}.${string}``，防止拼错翻译键。这类约束的成本是"字符串字面量的可组合性"——它让字符串不再是任意的，而是有结构的。

### 实战应用

#### 模式速查：真实场景对应的类型写法

| 场景         | 写法                         | 说明                         |
| ------------ | ---------------------------- | ---------------------------- |
| 配置部分更新 | `Partial<Config>`            | 函数参数只改一部分配置       |
| 隐藏内部字段 | `Omit<User, 'passwordHash'>` | 对外 DTO 安全裁剪            |
| 状态码到文案 | `Record<Status, string>`     | 联合键映射，漏键编译报错     |
| 事件名约束   | 模板字面量 `on${Event}`      | 拼错事件名直接编译失败       |
| 函数返回类型 | `ReturnType<typeof fn>`      | 改函数签名，消费端自动跟着变 |
| Promise 解包 | `Unwrap<T>`                  | 嵌套 Promise 层层取类型      |

表里每一行的共同点：类型都是从"真实数据形状"派生出来的，而不是拍脑袋写死的。配置对象有部分更新需求，所以用 `Partial`；用户对象有内部字段不能暴露，所以用 `Omit`；状态码是有限集合，所以用 `Record` 加联合键。选工具类型的思路是"先看数据怎么流，再选类型怎么切"，反过来先选类型再迁就数据，写出来的类型往往和业务对不上。

#### 陷阱与正确做法

**陷阱一：分发没关掉。** 反面案例：写 `type Filter<T> = T extends string ? never : T`，拿 `string \| number` 代入，以为会得到整个联合类型，结果 `string` 被拆出去只剩 `number`——其实这正是 `Exclude` 的实现，但很多人没意识到自己在用分发。正确做法：明确自己要不要分发；要整体处理时用 `[T]` 包一层。

**陷阱二：infer 位置理解错。** 反面案例：想提取 Promise 类型却写了 `T extends Promise<infer U>`，输入是 `Promise<string> \| number`，结果一半分支是 `never`。正确做法：先用 `extends` 收窄输入，再递归处理联合的每个成员。

**陷阱三：Omit 大对象导致编译变慢。** 反面案例：对几十个字段的大类型反复 `Omit`、`Pick`，每次都在生成新的映射类型，项目 `tsc` 越来越慢。正确做法：公共类型只定义一次，派生类型控制在两层以内；性能敏感的地方用 `interface` 组合代替深层工具类型。

**陷阱四：模板字面量过度设计。** 反面案例：给所有路由、事件、表单字段都做字面量类型，一个字符串变化要改五个类型定义。正确做法：只在"拼错代价高"的边界用（公共事件名、路由前缀），内部细节让普通 `string` 通过。

补充一个实战里最常见的选择题：接口返回的 `status` 字段，用字面量联合（`'pending' | 'done' | 'failed'`）还是普通 `string`？答案是字面量联合——后端枚举一变，编译期就能发现所有漏处理的分支，配合判别联合的穷尽检查，比运行时 if 判断可靠得多。

#### 实战演练：实现一个 DeepPartial 并评测

把中篇的知识串成一个练习：手写 `DeepPartial`，然后对比它和内置 `Partial` 的行为差异。

```ts
type DeepPartial<T> = {
  [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K]
}

interface Order {
  id: number
  customer: { name: string; address: { city: string } }
}

const patch: DeepPartial<Order> = {
  customer: { address: { city: 'Shanghai' } },
}
```

对比 `Partial<Order>`：它只把第一层变可选，`customer.address` 仍然是完整类型；`DeepPartial` 让每一层都变可选，这正是"部分更新嵌套对象"的真实需求。评测时给自己三个问题：它处理数组吗？（上面这个版本会把数组也递归成对象，需要额外分支）它处理函数吗？（`typeof function` 是 `'function'`，所以 `extends object` 不匹配，这个版本恰好安全）它编译快吗？（深度超过三层就要警惕）。三个问题答完，你对递归类型的理解就超过大多数"复制粘贴 DeepPartial"的开发者了。

**陷阱五：把 infer 当万能。** 反面案例：一个函数返回类型被 `infer` 层层剥开，报错时看不到原始类型，只能靠 IDE 悬停一层层展开。正确做法：infer 只在"提取必要片段"时使用，提取结果给一个名字清晰的类型别名；过度嵌套的 infer 是类型可读性的杀手。

**陷阱六：内置工具类型和手写混用，风格不统一。** 反面案例：一半代码用 `Partial`，一半用自己写的 `MyPartial`，行为还有细微差别（比如没处理 symbol 键），排查时反复确认"到底是哪个"。正确做法：能用内置就用内置，手写工具类型放在统一目录并导出，禁止"同名不同实现"。

**陷阱七：为了"一行搞定"牺牲可读性。** 反面案例：一个 200 字符的条件类型写在一行里，没有换行、没有注释，三个月后没人敢动。正确做法：复杂类型按"输入 → 分支 → 输出"拆成多行，每层分支写注释；类型代码和业务代码一样需要格式化，`prettier` 对 TS 类型同样生效。

落地时给自己三条验收线：项目里的自定义工具类型不超过 10 个；每个工具类型都有注释说明用途和终止条件；第三方库暴露的复杂类型，你能用一句话说清它做什么。三条线过了，中篇的工具类型就算真正内化了。

### 进阶思考

类型体操的边界要自己划清楚。判断标准很简单：这段类型代码，新同事三分钟内能看懂吗？如果不能，优先拆成带注释的小工具类型，或者干脆放弃。类型体操的目的是让业务数据形状清晰，不是展示语言能力。

值得继续深入的方向有三个。一是 `satisfies` 操作符：它既检查值是否符合某个类型，又保留值自身的精确字面量类型，是 `as const` 的更好替代。二是 const 类型参数（`<const T>`）：让函数参数自动保留字面量类型。三是递归条件类型：`DeepPartial`、`DeepReadonly` 这类工具，理解递归边界和性能限制。

练习路径：type-challenges 从中级题开始，重点刷 `infer` 和条件类型分组；然后读你项目依赖里 `@types` 包的源码，看真实世界的工具类型怎么写。下篇我们讲工程化：tsconfig 严格配置、类型检查流程、以及怎么让一套类型体系在团队里真正落地，而不是只在个人项目里成立。

最后给一条判断标准：当你想写一个自定义工具类型时，先问自己三句话——这个类型要解决什么问题？它会不会被三个以上的地方复用？如果只是用一次，直接写具体类型是不是更清晰？三句话都通过再动手，类型体操才不会变成自嗨。工具类型的本质是"类型层面的抽象"，抽象的价值在于复用，不复用的抽象只会增加阅读负担。

再补一个进阶方向：类型级编程的"性能意识"。条件类型的分发、递归的深度、`Omit` 对大对象的展开，都会影响 `tsc` 的速度。项目大之后，一两个"昂贵的工具类型"就可能让全量类型检查慢上几十秒。排查方法是隔离法：把工具类型逐个注释掉，跑 `tsc --extendedDiagnostics` 对比时间，找到最贵的那一个，然后重写或拍平。类型体操的终点不是"越复杂越好"，而是"刚好够用且编译快"。

最后送一句中篇的总结：工具类型是把"类型层面的重复"消灭掉的手段，条件类型和 `infer` 是它的发动机，递归是它的变速箱，模板字面量是它的仪表盘。四个部件组合起来，你就能造出项目需要的任何"类型函数"。下篇进入工程化，把这些能力放到 tsconfig、CI 和 API 层的真实环境里检验。
