### 背景

把 Redis 接进项目很容易：读的时候先查缓存，没有就查数据库再写回。但上线后你会陆续遇到三种"缓存事故"：某个不存在的 key 被疯狂查询，数据库被打穿（穿透）；热点 key 过期的一瞬间，上千个请求同时重建缓存（击穿）；大量 key 同时过期，数据库瞬时压力暴涨（雪崩）。每种事故都有经典解法，但解法之间还有坑。

另一个高频翻车点是分布式锁。`SETNX` 加锁、`DEL` 解锁，看起来十分钟能写完；线上却可能出现"锁没设过期时间，持有者挂了锁永远不释放""删锁删掉了别人的锁""主从切换后锁丢失"等事故。分布式锁的正确性，藏在每一个细节里。

这一篇是 Redis 系列的收尾，讲两块业务最常用的能力：缓存策略（三大故障 + 一致性）和分布式锁（正确实现 + 边界条件）。读完你会得到一张"场景 → 方案"的决策表，而不是零散的命令片段。

在进入机制之前，先明确一个判断标准：缓存和锁都是"优化手段"，不是"业务需求本身"。缓存引入的是"数据可能不一致"的新复杂度，锁引入的是"分布式系统可能分裂"的新风险——如果业务不需要这个优化，就别加。很多团队的问题不是"缓存没做好"，而是"把缓存当成了万能药"：该用数据库的地方用缓存，该用幂等设计的地方用锁，结果系统的脆弱点从数据库转移到了 Redis。

另一个现实是：缓存和锁的坑，绝大多数不是 Redis 的问题，而是"使用姿势"的问题。Redis 提供的是原语（SETNX、EXPIRE、Lua），业务怎么组合它们、怎么处理边界，决定了系统的正确性。所以这一篇的重点不是 Redis 命令，而是"组合逻辑"——三大故障的防御组合、一致性的取舍组合、锁的七个细节组合。

本篇结构：三大故障（穿透/击穿/雪崩）→ 一致性方案 → 分布式锁的演进（七个细节）→ 场景决策表与陷阱 → 进阶方向。建议结合你自己的项目，给每个缓存 key 问一遍"如果它挂了/过期了/不存在会怎样"。

### 核心原理

#### 第一层：缓存三大故障——穿透、击穿、雪崩

缓存穿透：查询一个数据库中也不存在的 key，缓存永远没机会命中，请求全部打到数据库。解法是空值缓存（把 null 也缓存几十秒）和布隆过滤器（在缓存前判断 key 是否存在）。

缓存击穿：某个热点 key 过期后，大量并发请求同时发现缓存未命中，一起冲进数据库重建。解法是互斥重建（只允许一个请求重建，其他请求等待）和逻辑过期（key 永不过期，值里带过期时间，异步刷新）。

缓存雪崩：大量 key 在同一时段过期，或 Redis 整体不可用，请求全部落到数据库。解法是过期时间加随机抖动（`TTL + random`）、多级缓存（本地缓存兜底）、以及 Redis 高可用（上篇的哨兵/集群）防止"整体不可用"。

三者的判断口诀：穿透是"查不存在"，击穿是"查热点"，雪崩是"查很多"。解法可以组合：布隆过滤器防穿透，互斥重建防击穿，随机过期防雪崩——一套完整的缓存防御体系，三件都要有。

三大故障的防御还要考虑"降级路径"：缓存全挂时，应用应该返回什么？直接查库是最差的降级（数据库会被打穿）；返回旧数据（本地缓存或最后成功的结果）是中间方案；返回默认值/友好错误是最简单的方案。降级策略要在架构设计时就定，而不是事故发生时现想——事故时人的判断力会下降 50%。

还有一个"缓存预热"的实践：活动开始前，把热点数据提前写入缓存（而不是等用户请求触发）。预热可以避免"活动开始瞬间缓存未命中 + 数据库打穿"。预热脚本要幂等、可重跑，预热完成后用监控确认缓存命中率。缓存不只是"被动加速"，也可以是"主动规划"。

#### 第二层：缓存与数据库的一致性

缓存一致性的核心问题是"先更新数据库还是先更新缓存，删除还是写入"。最常用的模式是 Cache Aside：读时缓存未命中就查库写缓存；写时先更新数据库，再删除缓存（而不是更新缓存）。

为什么删除而不是更新？因为更新缓存会引入"两个写者写不同数据"的竞争，而删除缓存让下次读取自然重建。为什么先更新数据库再删缓存？因为先删缓存再更新数据库，可能有一个请求在删除后、更新前读到旧值并写回缓存，缓存被旧数据污染。

更严格的场景（数据一致性要求高）可以用"延迟双删"：更新数据库后删缓存，延迟几百毫秒再删一次，兜住并发窗口。或者用订阅数据库 binlog（如 Canal/Debezium）异步删缓存，让缓存失效和业务代码解耦。工程上要先认清需求：绝大多数业务能接受"短暂不一致"，追求强一致的缓存设计，复杂度会指数上升。

一致性的"业务容忍度"值得量化：商品标题晚几秒更新，用户无感；库存晚几秒更新，可能超卖；余额晚几秒更新，就是事故。把业务按"一致性敏感度"分级——内容类用 Cache Aside + 删除，库存/余额类走强一致（数据库事务 + 缓存失效 + 补偿）。一致性方案不是统一的，而是按业务分级设计的。

还有一个"缓存更新 vs 删除"的细节补充：删除缓存比更新缓存安全，但删除有"缓存击穿"风险（删除瞬间大量请求重建）。解法是"逻辑过期"：缓存永不过期，值里带过期时间，读到时发现过期就异步重建（并加互斥锁），用户拿到旧数据但接口不阻塞。这个模式适合"可以接受短暂旧数据"的高并发读场景。

#### 第三层：分布式锁——正确实现的七个细节

分布式锁的正确实现，可以从"最简单、有缺陷"逐步演进到"可用的版本"。第一步：`SETNX key value` 加锁，`DEL` 解锁——缺陷是没设过期时间，持有者崩溃锁永不释放。

第二步：`SET key value NX EX 10` 原子地加锁并设过期时间——解决"忘了过期"，但引入新问题：业务执行超过 10 秒，锁自动过期，另一个进程拿到锁，两个"持有者"同时存在。

第三步：看门狗续期。Redisson 等客户端默认会启动后台线程，在锁快过期时自动续期，业务完成再释放。续期让"锁的存活"和"业务的执行"绑定，是生产可用的关键。

第四步：释放时校验持有者。`DEL` 之前先比较 value 是不是自己的唯一标识（UUID），防止"删掉别人刚拿到的锁"。这个校验必须用 Lua 脚本保证原子性：先 GET 比较，再 DEL。

第五步：主从切换下的锁丢失。主节点加锁成功但还没复制到从节点，主节点挂了，从节点上位，锁丢失，另一个进程拿到同一把锁。RedLock（向多个独立节点加锁）试图解决，但被分布式系统社区广泛批评——它的正确性依赖不现实的假设。务实的选择是：接受"极端情况下锁可能失效"，让业务侧有幂等兜底，而不是追求完美的锁。

分布式锁还有一个业务语义问题值得单独说：锁保护的是"临界区"，而临界区往往涉及数据库、消息队列等外部系统——锁拿到之后，操作可能失败、可能超时、可能部分成功。真正可靠的方案是"锁 + 幂等 + 事务"三层：锁负责"尽量串行"，幂等负责"重复执行无副作用"，事务负责"要么全成要么全败"。把业务正确性全部押在锁上，是分布式系统里最危险的设计假设之一。

再补充一个实践细节：锁的 key 命名和过期时间要可观测。锁 key 带业务前缀（`lock:order:pay:123`）、value 带持有者标识（UUID + 实例 ID）、过期时间按"最坏执行时间"设置并配续期。线上排查"死锁"时，`SCAN lock:*` 能看到所有持锁者；锁释放日志和持有时间要记录，超长持锁直接告警——锁的问题，90% 能在日志里定位。

### 实战应用

#### 模式速查：场景 → 方案决策表

| 场景     | 方案                               |
| -------- | ---------------------------------- |
| 防穿透   | 空值缓存 + 布隆过滤器              |
| 防击穿   | 互斥重建 / 逻辑过期                |
| 防雪崩   | TTL 随机抖动 + 多级缓存            |
| 读多写少 | Cache Aside + 删除缓存             |
| 强一致写 | 延迟双删 / binlog 订阅             |
| 分布式锁 | SET NX EX + UUID + 续期 + Lua 释放 |

#### 陷阱与正确做法

**陷阱一：锁不设过期时间。** 反面案例：`SETNX` 加锁后进程崩溃，锁永远不释放，所有请求阻塞。正确做法：`SET key value NX EX 10` 原子加锁；再配合续期，防止业务超时锁被误释放。

**陷阱二：删锁不校验持有者。** 反面案例：进程 A 的锁过期后进程 B 拿到锁，A 执行完 `DEL` 把 B 的锁删了，两个进程同时执行临界区。正确做法：value 存唯一标识，释放用 Lua 脚本"先比较再删除"，保证原子性。

**陷阱三：缓存重建没有互斥。** 反面案例：热点 key 过期，1000 个请求同时查库重建，数据库连接打满。正确做法：重建加分布式锁或本地互斥，只让一个请求重建，其他请求短暂等待后读新缓存。

**陷阱四：TTL 全部相同。** 反面案例：所有缓存 TTL 都是 10 分钟，每到整点数据库被同时打穿。正确做法：TTL 加随机抖动（±20%），让过期时间分散；批量生成的缓存按批次错开。

**陷阱五：缓存雪崩时没有降级。** 反面案例：Redis 整体不可用时，所有请求直接查库，数据库扛不住。正确做法：多级缓存（本地缓存兜底）、限流降级（返回旧数据或默认值）、以及高可用架构（上篇）三管齐下。

**陷阱六：分布式锁的 key 范围太粗。** 反面案例：所有订单的支付锁都用同一个 key，一个慢事务阻塞所有订单的支付。正确做法：锁的粒度要和临界区匹配——按订单 ID、按用户 ID 细分；锁粒度太细会浪费 Redis 调用，太粗会放大阻塞，实际取舍要在压测里验证。

**陷阱七：续期和业务生命周期脱节。** 反面案例：业务代码里手动续期，忘记在异常路径停止续期，锁永远不释放。正确做法：用 Redisson 这类客户端管理续期（看门狗自动续、自动停）；手写续期时用 `try/finally` 保证释放，并把续期循环的退出条件和业务完成绑定。

### 进阶思考

缓存策略的终点，是"一致性、可用性、成本"三者之间明确的取舍。继续深入有三个方向。

一是多级缓存：本地缓存（Caffeine/进程内） + Redis + 数据库，热点 key 在本地命中，Redis 命中，最后才到数据库；本地缓存要解决"更新传播"问题，可以用版本号或消息通知失效。二是限流与保护：Redis 的 `INCR + EXPIRE` 实现固定窗口限流，Lua 实现滑动窗口或令牌桶；限流不只是防攻击，也是缓存重建和降级时的最后防线。三是 Redis 7 的新能力：`CLIENT CACHING`、函数（Functions）替代 Lua 脚本、`redis-cli --cluster` 的改进——新特性在降低复杂场景的实现成本。

学习路径：先把项目里的缓存代码做一次"三大故障体检"——每个 key 问一遍"不存在会穿透吗？热点会击穿吗？同时过期会雪崩吗？"；再写一个带续期和唯一标识的分布式锁工具类，跑一遍并发测试；最后模拟一次 Redis 宕机，验证降级路径是否真的生效。缓存和锁是 Redis 业务价值的最后一公里——数据结构决定性能，策略决定正确性。

最后给一个全局视角：Redis 三篇（数据结构、可靠性、缓存与锁）合起来，是"一台内存服务器从原理到业务"的完整路径。上篇回答"快从哪来"，中篇回答"稳怎么保证"，下篇回答"对如何达成"。技术选型和架构设计时，这三问缺一不可——只快不稳，业务不敢用；只稳不快，没必要用 Redis；快稳但用错，事故比慢还可怕。把三篇的判断标准串起来，Redis 在你手里就不是黑盒，而是一台可以推理的机器。

再补一个"和业务场景联动"的练习：挑你项目里一个真实功能（比如"文章阅读量"），设计它的完整 Redis 方案——用什么结构（String 计数器）、过期策略（TTL 多久）、一致性（先写库还是先写缓存）、降级（Redis 挂了怎么办）。一个功能设计下来，你会把三篇的知识全部串起来，比单独复习三遍都有效。

最后补一段关于"Redis 的边界"的话：Redis 适合"热数据、低延迟、结构化访问"，不适合"冷数据、大容量、复杂查询"——它是一台内存服务器，不是数据仓库。业务里"什么放 Redis、什么放数据库、什么放搜索引擎"的边界想清楚，Redis 才会被用在它最强的地方。技术选型的成熟，不是"会用更多工具"，而是"知道每个工具的边界"。

再补一段"缓存和测试"的实践：缓存逻辑（击穿/穿透/雪崩的防御）要能被测试覆盖——用单元测试验证"缓存未命中时只重建一次"（击穿防护）、"空值也会缓存"（穿透防护）、"TTL 有随机抖动"（雪崩防护）。测试缓存逻辑的难点是"时间"，用可注入的时钟（clock）让测试可控。缓存防御不是"上线后看效果"，是"上线前测正确"。

还有一个"锁的降级"设计：分布式锁本身也可能不可用（Redis 挂、网络分区）——业务要定义"拿不到锁怎么办"：拒绝请求（安全优先）、降级为本地锁（弱一致）、放行并靠幂等兜底（可用性优先）。三种降级对应三种业务：支付用拒绝，活动发放用幂等放行，内部任务用本地锁。锁的降级策略要写进设计文档，而不是事故时临时决定。

最后补一段"缓存和锁的监控"：缓存要看命中率（低于 80% 要排查）、重建次数（击穿信号）、过期分布（雪崩信号）；锁要看持锁时长（超长告警）、等待队列（锁竞争信号）、释放成功率（泄漏信号）。没有监控的缓存和锁，是"黑盒里的正确性"——看起来没事，出事就是大事。把这两类指标加进现有监控体系，是下篇落地的最低要求。

再补一段"缓存一致性方案的选型矩阵"：一致性需求从低到高——内容型（标题、描述）用 Cache Aside + 删除，可接受分钟级不一致；交易型（库存、价格）用"数据库事务 + 缓存失效 + 重试"；强一致场景（余额）干脆不缓存或只做本地兜底。把每个缓存 key 标注"一致性等级"，架构评审时按等级检查方案是否匹配——最怕的是"所有 key 用同一套方案"，要么过度设计要么欠设计。

还有一个"缓存和日志"的联动：缓存事故（穿透、击穿、雪崩）的排查依赖日志——缓存未命中、重建触发、降级生效，都要有结构化日志（带 key、耗时、原因）。没有这些日志，事故后只能猜"当时发生了什么"。把"缓存关键路径打日志"写进规范，事故复盘才有材料——可观测性是正确性的前提。

最后补一段"三篇的总复习"：用一张纸把 Redis 三篇串起来——数据结构（上）回答"用什么存"，持久化/高可用（中）回答"怎么不丢"，缓存/锁（下）回答"怎么用对"。再补两个横切主题：安全（requirepass、网络隔离、禁用危险命令）和可观测（INFO、slowlog、监控告警）。一张纸写满，你的 Redis 知识体系就闭环了——剩下的，是实践把它变成肌肉记忆。

再补一段"性能优化的最后一步"：缓存命中率、锁等待时间、命令延迟都优化完了，如果 Redis 还是慢，检查"网络往返"——客户端和 Redis 之间的 RTT（毫秒级）在"N 次命令"的循环里会放大（100 次往返 = 100 × RTT）。解法是管道（pipeline）和批量命令（MGET/MSET），把 N 次往返变成 1 次。Redis 的性能瓶颈往往是"往返次数"而不是"命令本身"——这条经验，值回整篇文章。

最后补一句"和数据库的边界"：Redis 是"加速层"，数据库是"事实层"，两者不是竞争而是配合——缓存让热点读变快，数据库保证数据可靠，消息队列让变更异步传播。架构成熟的标志是"每一层只做自己擅长的事"：Redis 不存必须持久化的数据，数据库不扛全部读流量，消息队列不背业务状态。把边界守住，Redis 的价值才会最大化。

再补一句"给行动的建议"：今天给项目里最热的一个 key 设计完整方案——结构、TTL、穿透/击穿/雪崩防护、降级路径、监控指标，五项各写一行。一个 key 设计下来，三篇的知识就串起来了。Redis 不是学完的，是用完的。

最后给一个全局视角：Redis 三篇（数据结构、可靠性、缓存与锁）合起来，是"一台内存服务器从原理到业务"的完整路径。上篇回答"快从哪来"，中篇回答"稳怎么保证"，下篇回答"对如何达成"。技术选型和架构设计时，这三问缺一不可——只快不稳，业务不敢用；只稳不快，没必要用 Redis；快稳但用错，事故比慢还可怕。把三篇的判断标准串起来，Redis 在你手里就不是黑盒，而是一台可以推理的机器。
