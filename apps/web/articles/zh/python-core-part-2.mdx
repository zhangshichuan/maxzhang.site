### 背景

上篇讲完数据模型，你已经能写出干净的脚本。但脚本变成服务，还差一整套工程设施：同事克隆仓库后怎么跑起来？依赖版本谁来锁定？谁能保证提交的代码没有低级错误？测试跑在谁的机器上？发布到服务器时为什么 `import` 报错？

这些问题在 JavaScript 生态里早就有了标准答案（package.json、lockfile、CI），Python 生态过去一直各自为政：`pip install` 直接污染全局环境，`requirements.txt` 不锁传递依赖，测试靠 `print` 调试，部署靠"我本地能跑"。现在这些问题都有了解法：`uv` 统一环境管理，`pyproject.toml` 声明项目元数据，`pytest` 做测试，`mypy` 查类型，Docker 固定运行时。

这篇是 Python 系列的下篇，从零搭一个"能长期维护"的项目骨架：环境与依赖、代码质量、测试、CI、部署。每一步都讲清楚它在防什么，而不是让你背命令。

先给一个宏观视角：Python 工程化在过去十年经历了三次迭代。第一代是 `virtualenv` 加 `requirements.txt`，解决"环境隔离"，但依赖树不可复现；第二代是 `pipenv`/`poetry`，引入锁文件概念，但性能和生态各有问题；第三代是 `uv`，用 Rust 重写解析和安装，把"建环境、装依赖、锁版本、跑命令"合并成一条命令。理解这条演进线，你就知道现在该用什么——不是"哪个工具最潮"，而是"哪个工具把可复现这件事做完整了"。

还有一个容易被忽略的前提：工程化工具只是载体，真正要改变的是"习惯"。装了 uv、写了 pyproject、配了 CI，但如果团队还是"本地跑一下就算测过"，一切照旧。下篇的每一节都问同一个问题：这个环节，能不能让机器替我保证？能，就自动化；不能，就写进规范并由 CI 强制。工具负责执行，规范负责兜底。

下篇的阅读路线建议按"环境 → 质量 → 测试 → CI → 部署"的顺序，每一节都在上一节的基础上加一道保险。你可以先只做前三节（uv + ruff/mypy + pytest），这已经能让个人项目脱胎换骨；CI 和部署是团队项目再上的台阶。不要一次全上，分阶段落地，每阶段跑通再进下一阶段。

举一个真实的崩溃现场：某团队在 `requirements.txt` 里写 `requests>=2.20`，半年后新同事 `pip install` 解析到 requests 2.32，其中某个传递依赖的行为变化导致生产环境偶发超时。排查两天，最后定位到"本地和线上依赖版本不一致"。这类事故的根源不是某个人粗心，而是环境声明不完整：没有锁文件，"可复现"就是一句空话。工程化的第一步，就是把"跑起来"从运气变成确定性。

再举一个测试的案例。某项目的测试只在开发者本地跑，CI 里没有测试步骤。一次重构改了数据库模型的字段名，本机因为缓存没触发问题，部署后线上查询全部报错。问题不在测试写得差，而在于测试根本没有成为流程的一部分——本地跑过的测试、没人保证其他人也跑过。工程化的本质，是把"我检查过了"变成"系统检查过了"。

### 核心原理

#### 第一层：uv——环境、依赖、锁文件一把抓

Python 工程化的第一个痛点就是环境。`uv` 的核心命令只有几个：`uv init` 初始化项目，`uv add` 加依赖，`uv sync` 按锁文件装环境，`uv run` 在项目环境里执行命令。

````
```bash
uv init myapp
cd myapp
uv add fastapi uvicorn
uv add --dev pytest mypy ruff
uv run python -c "import fastapi; print(fastapi.__version__)"

关键产物是 `pyproject.toml` 和 `uv.lock`。`pyproject.toml` 声明"直接依赖"和项目元数据，`uv.lock` 锁定完整的依赖树——包括每个传递依赖的精确版本和哈希。有了锁文件，任何人 `uv sync` 得到的都是同一个环境，"我本地能跑"这句话才不再成立。

为什么不能只用 `pip install -r requirements.txt`？因为 `requirements.txt` 只锁直接依赖，传递依赖的版本是解析时决定的。今天解析和三个月后解析，可能得到两棵不同的依赖树。`uv.lock` 把整棵树（含每个包的哈希）冻结下来，配合 `--frozen` 安装，任何环境的依赖树都逐字节一致。这也是 CI 和 Docker 构建能放心的前提。

还要回答一个更基础的问题：为什么需要虚拟环境？因为 Python 包默认装进系统目录，两个项目需要不同版本的 Django 时就会互相覆盖。虚拟环境的本质是"每个项目一个隔离的包目录"，`uv` 把创建、激活、装包合并成了几条命令，让隔离变成默认行为而不是额外步骤。新人问"为什么我 pip 装的东西另一个项目用不了"，答案就是虚拟环境——它在保护你。


#### 第五层：测试策略——从"跑得通"到"跑得对"

测试的价值不在数量，在"置信度"：一组测试能不能让你放心重构？工程化的测试策略包含四个层次。

第一层是单元测试：只测一个模块、一个函数，不碰数据库和网络。它们快、稳定，是 CI 的主力。第二层是集成测试：连接真实数据库、真实文件系统，验证"模块之间合起来对不对"。第三层是端到端测试：从 API 入口到数据库落库，模拟真实用户路径，数量少但覆盖关键流程。第四层是契约测试：验证"我调用的外部服务接口没变"——外部 API 的 schema 变化，契约测试会第一时间报警。

四层的比例建议是 7:2:0.5:0.5，越往上越慢越贵。很多团队的测试只有一层（全是"单元测试"其实在连数据库），或者只有端到端（慢到没人跑）。正确的策略是"分层互补"：单元测试抓逻辑错误，集成测试抓协作错误，端到端抓用户路径，契约测试抓外部变化。

#### 第六层：部署流水线——从构建到上线的完整链路

部署不是"把代码传到服务器"，而是一条可重复、可回滚的流水线。完整的链路是：构建（build）→ 测试（test）→ 打包（package）→ 发布（publish）→ 部署（deploy）→ 验证（verify）。

每一步的产物都要"不可变"：构建产物带版本号或 commit SHA，镜像 tag 不可覆盖，部署记录写进发布日志。回滚不是"重新跑一遍旧流程"，而是"切回上一个不可变产物"——所以不可变标签是回滚的前提。

部署策略上，最简单的是"停机部署"（维护窗口），升级是"滚动更新"（逐个替换实例），再高级是"蓝绿"（新旧并存切流量）和"金丝雀"（先放 5% 流量观察）。对大多数内部服务，滚动更新加健康检查就够；对用户敏感的服务，金丝雀是标准答案。部署流水线的验收标准只有一条：出问题时，一键回滚到上一个版本，且数据不丢。









#### 第二层：pyproject.toml——项目的唯一声明文件

旧的 `setup.py` 加 `requirements.txt` 加 `Pipfile` 三套并存的时代结束了。现代 Python 项目所有声明都收进 `pyproject.toml`：项目信息、依赖、构建系统、甚至 lint 和格式化配置。

````

```toml
[project]
name = "myapp"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["fastapi>=0.115"]

[project.optional-dependencies]
dev = ["pytest", "mypy", "ruff"]

[tool.ruff]
line-length = 100

一个文件说清楚"这是什么项目、需要什么、怎么检查"，新成员克隆下来十分钟就能进入开发状态。

`pyproject.toml` 里还有一块容易被忽略的配置：`[build-system]` 声明构建后端（hatchling、setuptools、flit），`[project]` 声明元数据和依赖，`[tool.*]` 放各工具的配置。好处是工具链配置不再散落在 `.flake8`、`mypy.ini`、`setup.cfg` 里，换工具就是改一个文件。Python 打包生态花了十年才统一到这个标准，新项目不要再开历史倒车。

目录布局也值得较真：`src/myapp` 这种"src 布局"要求代码必须安装后才能 import，从根目录直接跑测试会因为模块找不到而失败——这个"麻烦"恰恰是特性，它逼所有入口（测试、脚本、服务）走同一条已安装的路径，避免"本地能跑、打包后 import 失败"的经典事故。小脚本无所谓，要发布的项目一律 src 布局。

#### 第三层：质量门禁——format、lint、typecheck、test

代码质量不能靠自觉，要靠可以重复执行的命令。推荐的最小组合是：`ruff` 做格式化和 lint，`mypy` 做类型检查，`pytest` 做测试。三个命令全部写进 pyproject 的脚本别名：

```

```bash
uv run ruff check .
uv run ruff format --check .
uv run mypy src
uv run pytest

`ruff` 的价值是消灭"风格争论"：行宽、导入顺序、未使用变量，机器说了算。`mypy` 的价值是让上篇讲的类型提示真正起作用——它检查 `User \| None` 有没有被正确处理，`Any` 有没有在边界泄漏。测试用 `pytest` 而不是 `unittest`：`fixture`、参数化、断言重写，写起来舒服得多。

```

```python
import pytest

@pytest.mark.parametrize('a,b,expected', [(2, 3, 5), (0, 0, 0)])
def test_add(a, b, expected):
    assert add(a, b) == expected

测试不是数量游戏，是分层游戏。单元测试只测一个模块，快、稳、无副作用；集成测试连真实数据库和外部 API，慢但更接近真相；端到端测试最少，覆盖最关键的用户路径。三层比例大约 7:2:1，全塞进单元测试会漏集成问题，全堆端到端测试会让 CI 慢到没人等。`fixture` 的作用是管理每层测试的准备与清理：数据库会话、临时目录、Mock 客户端，都在 fixture 里声明，测试函数保持干净。

fixture 的作用域（scope）是测试速度的关键：`function` 级每个测试新建，隔离最好但最慢；`session` 级整个测试会话复用，最快但共享状态有风险。数据库连接、缓存客户端用 `session` 级，临时目录、Mock 用 `function` 级，组合使用才能兼顾速度与隔离。测试的"确定性"比"覆盖率"更重要——一个每次跑结果不同的测试，比没有更糟。

mypy 值得多花两句话：默认配置只查显式标注的代码，`--strict` 才要求全项目无遗漏。刚迁移的项目开 `--strict` 会爆出几百个错误，正确的策略是"新代码严格、旧代码渐进"：先跑 `mypy --strict` 收集基线，用 `# type: ignore` 带注释压住存量，再每周清理一批。mypy 的回报不是现在，而是三个月后重构时，编辑器替你挡住了所有类型错位。

#### 第四层：CI 与部署——让门禁自动执行

本地命令再全，不跑也是摆设。CI 的第一原则：每次 push 都跑同一套质量门禁。GitHub Actions 的 job 可以这样组织：

```

```yaml
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v6
      - run: uv sync --frozen
      - run: uv run ruff check .
      - run: uv run mypy src
      - run: uv run pytest

`uv sync --frozen` 表示必须按锁文件安装，锁文件过期直接失败——依赖漂移在源头被拦住。

CI 里还有一个容易漏掉的维度：Python 版本矩阵。项目声明 `requires-python = ">=3.11"`，但线上跑 3.11、本地跑 3.13，行为可能不同。用矩阵同时在 3.11 和 3.13 上跑测试，能提前暴露"新版本语法、旧版本不支持"这类问题。版本矩阵会让 CI 时间翻倍，但它的价值是让"支持范围"这句话有测试背书，而不是拍脑袋。

部署方面，Docker 是标准答案。镜像构建的关键是分层缓存：先复制 `pyproject.toml` 和 `uv.lock` 安装依赖，再复制源码，这样依赖没变时能复用缓存层。

```

```dockerfile
FROM python:3.12-slim
COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev
COPY src ./src
CMD ["uv", "run", "uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8000"]

部署还有两个容易被忽略的细节。一是健康检查：容器编排（K8s、Docker Compose）靠 `/healthz` 判断实例是否就绪，没有健康检查的部署等于盲人开车。二是环境变量注入：密钥走 Secret 或部署平台的变量管理，绝不写进镜像或代码仓库。镜像只包含代码和依赖，任何环境相关的差异都在运行时注入——这是"一个镜像到处跑"的前提。

生产部署还有一个"发布即验证"的原则：部署完成后，流水线必须自动验证（健康检查通过、冒烟接口 200、关键指标正常），验证失败自动回滚。不要"部署完就下班"，让验证交给监控；人只负责看结果，机器负责执行和回滚。

### 实战应用

#### 模式速查：标准项目结构

```

myapp/
├── pyproject.toml
├── uv.lock
├── src/
│ └── myapp/
│ ├── **init**.py
│ ├── main.py
│ └── services/
├── tests/
│ ├── conftest.py
│ └── test_main.py
├── .github/workflows/ci.yml
└── Dockerfile

`src/` 布局（而不是根目录放包）能防止"从仓库根目录 import 测试代码"这类隐藏依赖，是 Python 打包的推荐实践。

这套结构的核心原则是"命令可复现、失败可定位"：任何人、任何机器，跑同一组命令得到同一组结果。新同事入职的第一天，克隆仓库、`uv sync`、跑一遍测试，十分钟进入开发状态，而不是先折腾半天环境。项目结构不是审美问题，是团队效率问题。

#### 落地清单：从零到可交付的十步

把下篇的内容压缩成一张十步落地清单，可以直接贴在项目文档里：

| 步骤 | 动作             | 验收标准                 |
| ---- | ---------------- | ------------------------ |
| 1    | `uv init` 初始化 | pyproject.toml 存在      |
| 2    | `uv add` 装依赖  | uv.lock 入库             |
| 3    | 配 ruff          | `ruff check .` 通过      |
| 4    | 配 mypy          | `mypy src` 无错误        |
| 5    | 写 pytest        | 覆盖率 > 70%             |
| 6    | 建 CI            | push 自动跑四件套        |
| 7    | 写 Dockerfile    | 多阶段构建，镜像 < 200MB |
| 8    | 配健康检查       | `/healthz` 返回 200      |
| 9    | 建 staging       | 自动部署 + 冒烟          |
| 10   | 建回滚           | 一键回滚到上一版本       |

十步做完，一个"能长期维护"的 Python 服务就成型了。每一步都有明确的验收标准，团队进度可度量。

这十步的节奏建议：第一周完成 1-5 步（个人项目脱胎换骨），第二周完成 6-8 步（CI 和 Docker），第三周完成 9-10 步（staging 和回滚）。不要试图一天做完——工程化是习惯的养成，不是任务的堆砌。每完成一步，跑一遍全流程验证"没把上一步弄坏"，再进下一步。

调试体验也值得优化：把 `uv run` 包装成 `make` 或 `just` 命令（`make lint`、`make test`），团队成员不需要记住每个工具的参数；`pyproject.toml` 里配置 pytest 的 `testpaths` 和 mypy 的 `files`，让默认行为就是全量检查。工程化的目标不是造更多命令，而是让正确的命令成为最省力的选择。

还有两个容易忽略的细节。一是 `.gitignore` 必须包含 `.venv`、`__pycache__`、`.pytest_cache`、`.mypy_cache`——把虚拟环境和缓存提交进仓库，等于让每个克隆者下载一堆与代码无关的文件。二是提交前跑一遍完整的四件套（ruff、mypy、pytest、格式检查），而不是只跑自己改的那部分——全量检查的成本几秒，漏检的代价可能是几个小时。

#### 陷阱与正确做法

**陷阱一：全局 pip 安装。** 反面案例：`pip install requests` 装进系统 Python，换个项目版本冲突，`pip list` 变成垃圾场。正确做法：每个项目一个虚拟环境，`uv sync` 一把装齐。

**陷阱二：锁文件不提交。** 反面案例：`uv.lock` 被 gitignore，同事各自解析出不同版本，线上 bug 无法复现。正确做法：锁文件必须入库，CI 用 `--frozen` 强制一致。

**陷阱三：测试只跑 happy path。** 反面案例：只测正常流程，异常分支、空数据、超时全都不测，重构一次崩一片。正确做法：用 `pytest.raises` 测异常，用参数化覆盖边界值，把"坏输入"当一等公民。

**陷阱四：Docker 里装开发依赖。** 反面案例：`uv sync` 不带 `--no-dev`，镜像里塞进 pytest 和 mypy，体积翻倍还多出攻击面。正确做法：生产镜像只装运行依赖，开发工具留在 CI 里。

**陷阱五：测试依赖真实网络。** 反面案例：单元测试直接请求真实第三方 API，CI 网络波动导致测试随机红，没人敢改相关代码。正确做法：外部依赖用 fixture 注入 fake 客户端，或使用 `respx`、`httpx.MockTransport` 拦截请求；需要真实服务的测试单独打标记，只在专门的集成 job 里跑。

**陷阱六：Docker 构建上下文过大。** 反面案例：`.dockerignore` 没配，`node_modules`、`.venv`、`.git` 全被 COPY 进构建上下文，镜像几百 MB，构建慢还泄露文件。正确做法：`.dockerignore` 排除 `.venv`、`__pycache__`、`.git`、缓存目录；构建上下文只含必要文件。

**陷阱七：环境变量靠人传。** 反面案例：部署时手动在平台上填几十个环境变量，漏一个线上才爆。正确做法：环境变量模板入库（`.env.example`），部署平台从配置中心或 Secret 自动注入；启动时用 Pydantic Settings 校验必填项，缺失立即失败。

### 进阶思考

这套骨架解决的是"项目从一个人变成一个团队"的问题，但还有三个方向值得继续深入。

一是构建与发布：用 `hatchling` 或 `uv build` 打 wheel，配合 `twine` 发到私有仓库。理解 sdist 和 wheel 的区别，是 Python 包作者的门槛。二是异步架构：FastAPI + `asyncio` 下，阻塞调用（`requests`）会卡住整个事件循环，必须用异步客户端或线程池，这是 Python 服务性能的分水岭。三是性能剖析：`cProfile` 和 `py-spy` 找热点，`memory_profiler` 找内存增长，别再凭感觉优化。

学习路径：把 uv 的文档读一遍（半小时），用这套骨架重写一个你手头的小脚本，再跑一次 `mypy` 把所有 `Any` 清零。工具是死的，习惯是活的——Python 工程化的终点，是你不再依赖"我本地能跑"这句话。

如果团队规模再大一点，值得把"质量门禁"升级成"发布门禁"：CI 里加依赖漏洞扫描（`uv audit` 或 osv-scanner）、构建产物校验、以及 staging 自动部署。工程化的终点不是工具最多，而是每个环节都有明确的守卫者——代码提交由 CI 守卫，发布由流水线守卫，线上由监控守卫。Python 的工程化能力过去被低估，现在这套工具链已经完整，缺的只是执行的纪律。

最后总结下篇的路线：环境（uv）解决"能跑"，质量（ruff/mypy/pytest）解决"跑得对"，CI 解决"每次都跑"，部署解决"安全上线"，监控解决"上线后放心"。五件事环环相扣，缺一环，前面的投入都会打折扣。Python 工程化不是某一个工具的胜利，而是这套"可复现 + 可验证 + 可回滚"习惯的胜利。

可复现是工程化的核心概念：环境可复现、依赖可复现、命令可复现、发布可复现、回滚可复现。凡是"只能在我机器上跑"的东西，都是工程化的敌人。把每一个"我本地能跑"改写成"任何人 `uv sync` 后都能跑"，你的项目就从个人作品变成了团队资产——这是上下两篇合起来最想传递的一句话。

"什么时候算完成"的判断标准：当你的项目里出现这些现象——新同事克隆后十分钟跑起来、CI 红了没人敢合并、发布记录有据可查、回滚一键完成、监控面板上有健康度——工程化就算落地了。工具清单会过时，但这五个现象不会。用现象验收，而不是用工具清单验收，是团队工程化真正成熟的标志。

回顾整个下篇，主线只有一条：把"我以为没问题"变成"系统证明没问题"。环境有锁文件证明一致，质量有命令证明达标，测试有 CI 证明通过，部署有镜像证明可复现。单看每一条命令都很简单，难的是把它们串成一条不许跳过的流水线——跳过一次，就会跳第二次，然后回到"我本地能跑"的旧世界。

测试覆盖率要配套"有效性"一起看：覆盖率 90% 但全是 happy path，价值有限；覆盖率 70% 但覆盖了边界和异常，价值更高。有效的覆盖策略是"按风险分配"——支付、权限、数据一致性相关的逻辑必须覆盖异常路径，工具函数可以放宽。给覆盖率设阈值（比如 80%）之前，先确认"测的是正确的东西"——覆盖率是结果指标，不是目标。

CI 的 Python 版本矩阵还有一个"最低版本"的纪律：`requires-python` 声明支持范围，但测试矩阵至少要覆盖"最低支持版本"和"最新稳定版本"两个端点——只测最新版本，等用户报"旧版本跑不起来"就晚了。Python 版本的生命周期（EOL）要跟踪，EOL 版本到期后更新矩阵并提升最低版本。版本矩阵的维护是"支持承诺"的落地，不是 CI 配置的装饰。

依赖审计（`uv audit`、osv-scanner、pip-audit）应该成为 CI 的固定环节：依赖漏洞扫描在每次提交时跑，高危漏洞（critical/high）让流水线失败，中低危进入"限期修复"队列。依赖是供应链攻击的主要入口（投毒、抢注、依赖混淆），审计不能靠"上线前扫一次"，要进 CI 持续跑。把依赖审计和镜像扫描一起放进流水线，供应链安全才算闭环。

测试「覆盖率」的解读：覆盖率 90% 但全是 happy path，价值有限；70% 但覆盖边界和异常，价值更高。按风险分配覆盖——支付、权限、一致性相关逻辑必须覆盖异常路径，工具函数可以放宽。给覆盖率设阈值前，先确认「测的是正确的东西」——覆盖率是结果指标，不是目标。

CI 的「版本矩阵」：`requires-python` 声明支持范围，测试矩阵至少覆盖「最低支持版本」和「最新稳定版本」两端——只测最新版，等用户报「旧版本跑不起来」就晚了。跟踪 Python 版本的 EOL，到期后更新矩阵并提升最低版本。版本矩阵的维护是「支持承诺」的落地，不是 CI 配置的装饰。
