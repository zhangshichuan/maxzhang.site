### 背景

2025 年，几乎所有 LLM 应用团队都在讨论两个缩写：MCP（Model Context Protocol）和 A2A（Agent2Agent）。网上有人把 MCP 吹成"AI 的 USB-C"，有人说 A2A 是 MCP 的替代品，还有人把 skills、subagent、function calling 全部混在一起讲。结果就是：概念越看越多，落地时不知道该接哪个。

这些混乱的根源是"层级"没分清。MCP 解决的是"模型怎么调用工具"——一个统一协议，让任何模型都能接入任何工具；A2A 解决的是"智能体怎么和智能体协作"——一个企业里的多个 AI 智能体，怎么发现彼此、派发任务、交换结果。一个是"手"，一个是"同事"，不是同一层的东西，也就不存在谁替代谁。

这篇文章把 MCP 和 A2A 分开讲清楚：各自的架构、核心概念、典型场景，最后给一张"什么时候用哪个"的决策表。读完你能在架构评审会上说清楚：我们的应用要接工具，用 MCP；要让多个智能体协作，再考虑 A2A——而不是把两个协议捆在一起拍脑袋。

在深入之前，先给一个"为什么现在才需要协议"的背景：2024 年之前，LLM 应用大多是"单模型 + 单工具集"的玩具架构，直接调 API 就够了；2025 年之后，工具数量、智能体数量、供应商数量都上来了，每个应用都接十几个工具、多个模型平台，硬编码适配的成本开始超过协议本身。MCP 和 A2A 的出现，本质上是"集成数量爆炸"之后的标准答案——就像 USB-C 出现之前，每台设备都有自己的充电线。

还要提醒一点：这两个协议都是"规范 + SDK 生态"的组合，规范本身很短，真正影响你的是生态的成熟度。2025 年 MCP 的 SDK、调试工具、云服务支持已经相当成熟，A2A 还在早期。选型时除了看协议能力，还要看"团队能拿到多少现成实现和排障工具"——协议再标准，没有工具支撑，落地成本一样高。

本篇结构：MCP 架构与设计取舍 → A2A 的任务模型 → 两者分层关系 → 选型决策表与陷阱 → 生态演进方向。建议边读边画"我的应用里模型/工具/智能体分别在哪一层"。

### 核心原理

#### 第一层：MCP——模型与工具的通用插口

MCP 的架构是典型的三角色模型：Host 是模型运行的应用（Claude Desktop、IDE、自建 Agent 平台），Client 是 Host 内部与 Server 建立连接的组件，Server 是暴露工具/资源/提示词的一方。模型通过 Host 与 Server 通信，不需要知道每个工具的实现细节。

MCP 定义了三种原语：Tools（模型驱动的执行，模型决定何时调用）、Resources（应用驱动的上下文，Host 决定注入什么数据）、Prompts（预定义的可复用提示词模板）。三种原语分别回答"模型能做什么、模型能看到什么、模型该怎么开场"，组合起来就是一个完整的"模型与外部世界交互"的契约。

传输层面，MCP 基于 JSON-RPC 2.0，支持 stdio（本地进程通信）和 Streamable HTTP（远程服务）。会话流程是固定的：initialize 协商能力 → 双方确认 → 正常消息交换 → 可选的通知机制。协议细节（分页、取消、采样、MCP 扩展）在实现时才会碰到，理解"统一消息格式 + 能力协商"这个骨架就够了。

MCP 的消息流还有一个"生命周期"的概念：连接建立后，Client 和 Server 通过 initialize 交换能力（支持哪些原语、哪些扩展），之后的每次工具调用都是标准的 request/response。断开重连时，客户端要重新 initialize——所以 Server 要做到"无状态"（除了必要的会话信息），否则重连后状态错乱。协议实现者最常踩的坑是"在 initialize 之前就处理工具调用"和"响应格式不符合 JSON-RPC 2.0"，用官方 SDK 能避开大部分。

MCP 的扩展机制（采样、roots、资源订阅）还在快速演进：采样让模型可以反向调用宿主能力，roots 让 Server 知道宿主的工作目录，资源订阅让客户端监听资源变化。生产实现时，不要一次性上全部扩展——先跑通核心三原语，扩展按需启用。协议的演进期，兼容性测试比功能开发更重要。

#### 第二层：MCP 的设计取舍——为什么是它

在 MCP 之前，每个模型平台都有自己的工具调用格式（OpenAI function calling、Anthropic tools、各框架的 tool schema），工具开发者要为每个平台写一遍适配。MCP 的价值是把"工具描述"和"调用协议"标准化：写一个 MCP Server，任何 MCP 兼容的 Host 都能用。

这个取舍的代价也很真实：协议层增加了一层抽象，调试要查 JSON-RPC 消息，版本演进要兼容（MCP 规范仍在快速变化，从早期 draft 到 2025 年的稳定版，接口有过调整）。对"只接一个平台"的简单场景，直接 function calling 反而更轻；MCP 的优势在"工具要被多个平台复用"时才开始兑现。

安全是 MCP 落地的核心议题：工具是"能执行动作"的，一个写文件的工具、一个发消息的工具，暴露给模型就意味着模型拿到了这个权限。MCP 协议本身不解决授权——谁允许模型调用什么工具，由 Host 和 Server 的配置决定。工程实践是"工具白名单 + 人工确认 + 敏感操作二次授权"，把模型的工具权限当成 API 权限一样管理。

MCP 的调试体验也值得提前知道：协议消息是 JSON-RPC，用 MCP Inspector 可以像看 HTTP 请求一样看每次工具调用的请求和响应，包括参数、错误、时序。排查"模型为什么调错了工具"时，先看 Inspector 的调用记录，再看提示词和工具描述——大多数工具误调用，是工具描述写得不清楚，而不是模型的问题。

工具的"描述"质量在 MCP 里被放大：模型根据描述决定"这个工具能帮我干什么、参数怎么填"。写工具描述时，要写"什么时候用、参数含义、返回值结构、失败时会怎样"，而不是一行注释。把工具描述当成"给模型看的 API 文档"来写，是 MCP Server 质量最重要的因素。

#### 第三层：A2A——智能体之间的协作协议

A2A 由 Google 于 2025 年发布，解决的是"多个智能体如何协作"。它的核心概念包括：Agent Card（智能体的能力清单，类似"名片"）、Task（一次任务，有状态、可跟踪）、Artifact（任务产出的文件或结构化数据）、Message（智能体之间的通信内容）。

A2A 的工作流是：客户端智能体发现另一个智能体的 Agent Card → 创建 Task 并发送消息 → 目标智能体执行并回报状态 → 产出 Artifact 交付结果。它支持长任务（几秒到几小时）、流式更新（部分结果先返回）、人机协作（需要时升级给人类）。简单说，A2A 把"智能体之间"的通信和任务管理标准化了。

#### 第四层：MCP 与 A2A 的关系——分层而不是竞争

最清晰的类比：MCP 是"模型操作系统"里的设备驱动，A2A 是"企业应用网络"里的服务协议。一个智能体内部，用 MCP 接工具（查数据库、调 API、发邮件）；多个智能体之间，用 A2A 派任务（订单智能体把任务交给物流智能体）。

实际架构里两者经常叠加：一个 A2A 智能体，内部用 MCP 工具完成自己的任务；任务结果通过 A2A 传给下一个智能体。把它们当成"不同层级的标准"，而不是"二选一"，架构讨论立刻就清晰了。2025 年的生态里，两者的边界还在演化（agent skills、subagent 协议也在争夺注意力），但分层思维不会过时。

A2A 的任务模型还有一个和普通 API 调用不一样的地方：它是"长任务优先"的。Task 有状态（submitted、working、completed、failed）、可跟踪、可轮询，支持流式中间结果——这针对的是"智能体干活可能要几分钟甚至几小时"的现实。设计 A2A 集成时，不要把 Task 当成同步 RPC：客户端应该接受异步状态更新，而不是阻塞等待。

Agent Card 是 A2A 里的"服务发现"机制：每个智能体发布一张卡片，声明自己能做什么、接受什么输入、产出什么格式。这听起来像微服务的注册中心，但粒度是"能力"而不是"接口"——调用方按能力匹配智能体，而不是硬编码地址。企业里智能体多了之后，这张卡片就是"谁能帮我干什么"的目录。

A2A 的安全模型也值得单独讲：智能体之间互相信任是最大的风险。A2A 规范支持认证（OAuth 2.0）和授权，但企业落地时还要加"任务级权限"——一个智能体派发给另一个智能体的任务，要能追溯到发起人和授权范围。把 A2A 当成"内部 API 网关"来治理：谁发布 Agent Card、谁可以调用、任务日志保留多久，都要有明确规则。

#### 检查清单：Agent 集成选型与落地

| 检查项   | 通过标准                  |
| -------- | ------------------------- |
| 层级     | 分清工具层/智能体层       |
| 协议     | MCP/A2A/原生按场景选      |
| 工具描述 | 每个工具文档化            |
| 权限     | 工具白名单 + 二次授权     |
| 可观测   | 调用日志、任务状态追踪    |
| 版本     | SDK 锁定、兼容性测试      |
| 治理     | Agent Card 发布与审计规则 |

七项过完，Agent 集成就有了"生产心智"。

### 实战应用

#### 模式速查：选型决策表

| 场景                | 选择                  | 理由                         |
| ------------------- | --------------------- | ---------------------------- |
| 模型要调用内部 API  | MCP Server            | 统一工具接入，多 Host 复用   |
| 模型要读文件/数据库 | MCP Resources/Tools   | 结构化上下文注入             |
| 多个智能体分工协作  | A2A                   | 任务派发、状态跟踪、结果交付 |
| 智能体内部用工具    | MCP                   | A2A 不解决"模型接工具"       |
| 只接一个平台        | 原生 function calling | 少一层抽象，更轻             |

#### 陷阱与正确做法

**陷阱一：把 MCP 和 A2A 当二选一。** 反面案例：架构评审会上争论"用 MCP 还是 A2A"，最后选了 MCP 却没解决智能体协作需求。正确做法：先问"是模型接工具还是智能体接智能体"，前者 MCP，后者 A2A，两者可以共存。

**陷阱二：工具权限不设防。** 反面案例：MCP Server 暴露了"执行任意 SQL"的工具，模型在一次对话里误操作删了生产表。正确做法：工具按最小权限设计，写操作默认禁止或人工确认；敏感工具单独鉴权；Server 端记录完整调用日志。

**陷阱三：上下文无脑全注入。** 反面案例：把整个代码库、全部文档做成 MCP Resources，模型上下文爆炸，回答质量下降、成本飙升。正确做法：按任务动态注入——先检索再注入，用小模型或搜索先定位，再只把相关片段给主模型。

**陷阱四：协议版本不锁定。** 反面案例：MCP Server 和 Client 用了不同版本的协议实现，能力协商失败，线上偶发连接错误。正确做法：SDK 版本固定并纳入依赖锁定；升级协议前在测试环境做兼容性矩阵。

**陷阱五：把 A2A 当内部函数调用。** 反面案例：两个服务之间高频同步调用也用 A2A 建 Task，协议开销远大于直接 HTTP。正确做法：A2A 用于"真正独立的智能体/长任务"；进程内或同服务内的调用直接用函数，不要为了"先进"套协议。

**陷阱六：工具描述敷衍。** 反面案例：MCP Server 里工具描述只有一句话，模型经常用错参数、选错工具，调试时还以为是模型不行。正确做法：给每个工具写"用途 + 何时用 + 参数说明 + 失败行为"，像给新人写 API 文档一样；工具描述的质量直接决定 Agent 的准确率。

**陷阱七：没有观测 Agent 的每一次调用。** 反面案例：Agent 在测试环境表现正常，生产里工具调用失败、任务超时，全靠用户截图反馈才知道。正确做法：给 MCP 调用和 A2A 任务加日志与链路追踪——每次工具调用的入参、出参、耗时、错误都记录下来，配合任务状态流转图，让 Agent 行为可回放、可审计。

### 进阶思考

2025 年的 Agent 生态还在快速演化，但可以看清两条主线：一是"工具标准化"——MCP 正在成为模型接工具的事实标准，云厂商、IDE、企业软件都在适配；二是"智能体互联"——A2A 与微软的 Agent Framework、各厂商的 MCP 扩展在争夺"智能体之间"的标准。对企业来说，正确的策略不是押注某一个，而是把"协议适配层"做成可替换的：内部抽象一层，接 MCP 还是 A2A 是配置问题，不是架构问题。

值得深入的方向有三个。一是安全与治理：Agent 平台的工具权限、审计日志、沙箱隔离，是 Agent 从 demo 到生产最大的门槛；二是可观测性：Agent 的每一步工具调用、任务状态、token 消耗都需要链路追踪，MCP 生态正在补这块；三是多 Agent 的编排模式：单一复杂 Agent vs 多个专业 Agent 协作，前者简单但能力有限，后者灵活但状态管理复杂——没有银弹，按业务复杂度选型。

学习路径：先搭一个最小的 MCP Server（暴露一个查询工具），用 MCP Inspector 调试协议消息；再读 A2A 规范的 Agent Card 和 Task 模型，用官方 demo 跑一次跨智能体任务；最后画一张你自己应用的"工具/智能体分层图"，标注哪些用 MCP、哪些用 A2A、哪些用原生调用。协议会更新，但"分层"和"边界"这两个问题，每个 Agent 架构都要先回答。

最后给一个判断框架：任何新协议出现时，先问三个问题——它解决哪一层的集成问题（工具层还是智能体层）？它的生态里有没有调试工具和成熟 SDK？如果它明天消失，我的抽象层能不能无损替换？用这三个问题过滤，MCP、A2A 以及未来任何新协议，都不会再让你陷入"该不该上车"的焦虑。

结语：MCP 和 A2A 是 2025 年 Agent 工程化的两个坐标轴——MCP 横向连接"模型与工具"，A2A 纵向连接"智能体与智能体"。它们的成熟度不同、生态不同，但都指向同一个方向：让 AI 集成从"点对点硬编码"走向"标准化、可组合、可治理"。理解这两个协议，你就站在了 Agent 架构的正确起点上。

再补一个"未来演进"的观察：Agent 生态的下一个争夺点是"技能（skills）"和"子智能体（subagents）"——它们解决的是"一个智能体内部怎么组织复杂能力"，和 MCP/A2A 解决的外部集成问题互补。2025 年的共识正在形成：工具层用 MCP、智能体间用 A2A、智能体内部分层用 skills/subagent。把这四层画在一张图上，Agent 架构的全貌就清晰了。

最后补一段"投资策略"的建议：协议生态还在早期，企业不要过早押注单一实现。正确的做法是"抽象层先行"——内部定义自己的"工具接口"和"智能体接口"，MCP/A2A 只是这些接口的标准适配器之一。这样无论生态怎么洗牌，你的架构都能以最小代价跟随，而不是被某一个协议的兴衰绑架。

再补一段"可观测性"在 Agent 场景的落地方案：MCP 的每次工具调用、A2A 的每个任务，都要有日志和追踪——工具名、入参、出参、耗时、错误码、token 消耗，全部结构化记录。Agent 的行为是"模型决策驱动的"，不可复现性比传统程序高得多，日志几乎是唯一的排障手段。把"Agent 行为日志"当作审计数据保留（至少 90 天），既是排障需要，也是合规要求。

还有一个"成本治理"的提醒：Agent 的 token 消耗是新的成本中心——工具调用失败会重试，重试会重复消耗 token；上下文越塞越多，单次调用成本随对话增长。工程实践是"失败快速返回"（工具错误信息精简）、"上下文裁剪"（只保留最近 N 轮）、"成本告警"（单会话 token 超阈值告警）。Agent 的工程化，一半是正确性，一半是成本控制。

最后补一段"安全红线"清单：Agent 能访问的工具和智能体，都按"最小权限"授权——工具白名单、智能体白名单、数据范围限制、操作审计；敏感操作（支付、删除、发消息）强制人工确认；Agent 的 prompt 注入防护（外部输入不直接拼进系统提示词）。Agent 比传统程序有更大的"动作空间"，安全设计要从"接口级"升级到"行为级"。

再补一段"从 demo 到生产的差距"：很多人 demo 里用 MCP 接了一堆工具，感觉很顺；上生产才发现问题成串——鉴权谁做、限流谁做、工具并发怎么控制、模型乱调用怎么办、任务挂起怎么处理。MCP/A2A 的协议只解决"通信"，生产要补的是"治理"：身份、权限、限流、审计、超时、重试、可观测。把"生产化清单"当作接入协议的第二个项目来做，demo 和生产的差距才不会成为上线时的惊吓。

最后补一段"架构师的 checklist"：画 Agent 架构图时，标出四类边界——工具边界（MCP Server 提供什么）、智能体边界（A2A Agent 负责什么）、权限边界（谁能调用什么）、数据边界（哪些数据能进模型上下文）。四类边界都清楚，架构评审就能通过；任何一类模糊，就是未来事故的温床。Agent 工程化，本质是"把边界画清楚"的工程。

再补一段"和现有系统的集成"：MCP/A2A 不是要推翻现有架构，而是给现有系统加一层"AI 接入层"——你的 API 已经存在，包一层 MCP Server 就变成"模型可调用的工具"；你的服务已经存在，包一层 A2A 适配器就变成"可协作的智能体"。集成的关键是"适配层"而不是"重写"：让现有系统保持原样，在边界上加协议适配，是成本最低、风险最小的 Agent 落地路径。

最后补一句"工程师的行动建议"：本周就可以做一个小实验——用官方 SDK 写一个 MCP Server（暴露你的一个内部 API），用 MCP Inspector 调试，再让模型调用它。一个下午的动手，比十篇文章更能让你理解协议的"形状"。理解之后，你自然会知道你的项目该在哪个边界接 MCP、在哪个边界考虑 A2A——实践是最好的老师。

再补一句"本文的收尾"：MCP 和 A2A 都还很年轻，规范在变、生态在长，但"分层、边界、治理"这三个词不会变。工具层、智能体层、权限层、数据层，每层画清楚，Agent 架构就立住了。协议会迭代，你的架构能力会沉淀——这是这篇想送给你的长期资产。

最后给一个判断框架：任何新协议出现时，先问三个问题——它解决哪一层的集成问题（工具层还是智能体层）？它的生态里有没有调试工具和成熟 SDK？如果它明天消失，我的抽象层能不能无损替换？用这三个问题过滤，MCP、A2A 以及未来任何新协议，都不会再让你陷入"该不该上车"的焦虑。
