### 背景

上篇解决了"组件在哪渲染"，下篇解决"数据从哪来、什么时候过期"。这两件事是 Next.js 项目里最大的困惑来源：同样的 `fetch`，有时构建时执行一次，有时每次请求都执行；改完数据库，页面怎么都不刷新；`revalidate` 设了，好像有时生效有时不生效。

根源是 Next.js 有不止一层缓存：Full Route Cache 缓存整个页面 HTML，Data Cache 缓存 `fetch` 的结果，Router Cache 在客户端缓存导航过的路由，`revalidatePath` 和 `revalidateTag` 负责精准失效。不理解这些层级，配置缓存就是撞运气。

这一篇把数据获取、缓存和失效讲成一张地图：`fetch` 的语义、静态与动态渲染的切换、Server Actions 怎么写、部署时要注意什么。读完你能回答"数据多久更新一次"这个问题，而不是靠试。

在深入之前，先给一个最重要的心智模型：Next.js 的缓存不是一个开关，而是一组嵌套的层。从外到内是：CDN 缓存（部署平台的）、Full Route Cache（整页 HTML）、Data Cache（数据获取结果）、Router Cache（客户端导航缓存）。请求到达时，任何一层命中都会跳过后面的层；任何一层失效，都只是那一段需要重新计算。理解"哪一层在起作用"，是配置缓存的第一步。

这篇文章的结构：先讲 fetch 的两种语义，再讲数据库查询怎么缓存，然后讲 Server Actions 与失效，最后讲部署形态。实战部分给一张决策表和一组高频陷阱。读完你能画出一张"我的页面数据新鲜度表"——这是数据获取工程化的核心产出。

再给一个心态提醒：缓存配置不是"一次调好永久生效"，而是"随业务变化持续调整"的。数据更新频率变了、页面结构变了、部署方式变了，缓存策略都要重新审视。把缓存当成"显式契约"而不是"隐式魔法"，每次改动都问一句"这会改变哪一层缓存的行为"，你就不会在缓存问题上反复踩坑。

先描述一个典型事故：内容团队更新了一篇文章，线上首页半小时不刷新；运维加了 `revalidate: 60`，页面开始随机变慢；有人改成 `no-store`，缓存没了，数据库压力翻倍。每一步都是"治标"，因为没有人画过缓存地图——不知道哪一层在缓存、哪一层在失效，所有调整都是盲调。数据获取的工程化，第一步就是给每个页面画一张"数据新鲜度"表。

另一个常见误区是把缓存当成"性能优化"，可有可无。实际上缓存直接决定用户体验和成本：静态页面的 CDN 命中率决定首屏速度，Data Cache 决定数据库压力，Router Cache 决定导航流畅度。不配置缓存，应用也能跑，但每一分性能都是在烧服务器资源和用户耐心。理解缓存不是选修课，是 App Router 的必修课。

### 核心原理

#### 第一层：fetch 的两种语义——缓存还是实时

App Router 给 `fetch` 增加了缓存选项，默认行为取决于页面是否动态。关键的两个选项是：

```ts
// 缓存并定时失效（ISR 的数据层）
const res = await fetch('https://api.example.com/posts', {
  next: { revalidate: 3600 },
})

// 每次请求都拿最新
const res = await fetch('https://api.example.com/posts', {
  cache: 'no-store',
})
```

`revalidate: 3600` 表示数据缓存一小时后过期，过期后下一次请求触发重新验证，页面继续显示旧数据直到新数据生成。`cache: 'no-store'` 表示完全跳过 Data Cache，每次请求都访问源。

理解规则：一个页面只要调用了动态 API（`cookies()`、`headers()`、`searchParams`）或使用了 `no-store`，整条渲染路径就会变成动态渲染，Full Route Cache 失效。静态和动态不能在同一层混着来，这是"为什么我的页面突然不缓存了"的最常见原因。

这里的"污染"是渐进式的：一个静态页面加了 `cookies()`，整页变动态；一个动态页面删了 `cookies()`，也不会自动变回静态（构建时决定）。所以"这个页面到底静态还是动态"不是运行时的属性，而是构建时分析的结果——排查时看 `next build` 输出的路由表，每个路由后面会标注 `ƒ Dynamic` 或 `○ Static`。这个标注是最权威的答案，比代码里找动态 API 快得多。

#### 第五层：三种数据获取方式的选型

App Router 里数据获取有三种方式，选错会直接导致性能或架构问题。

第一种是服务端组件内直接获取：`await fetch()` 或直接查库，代码在服务端执行，结果序列化给客户端。适合"页面初始化就要的数据"，是默认首选。第二种是客户端获取（`useEffect` 或 TanStack Query）：适合"用户操作后才需要"的数据，或需要实时刷新的数据。第三种是 Server Actions：适合"写操作"（表单提交、按钮触发），配合 `revalidatePath` 刷新页面数据。

选型的判断顺序：数据在首屏吗？在，用服务端获取；不在且需要交互，用客户端获取；是写操作，用 Server Action。还有一种混合：首屏用服务端获取，后续交互用客户端获取同一份数据——注意这里的"同一份"要在两端定义同一套类型和端点，避免两个数据源漂移。

数据获取还有一个"瀑布流"陷阱：组件 A 等数据，组件 B 依赖 A 的数据，串行等待让页面慢上加慢。解法是"并行获取"——用 `Promise.all` 同时发起互不依赖的请求，或用 Suspense 让独立的数据块并行渲染。检查瀑布流的方法：看 Network 时间线里请求是不是一条直线串行，是的话就要并行化。

#### 第六层：缓存调试方法论——从"猜"到"看"

缓存问题最怕"猜"。三个调试工具按顺序用，能覆盖 90% 的缓存问题。

第一，看构建输出：`next build` 的路由表标注了每个路由是静态还是动态，先确认"预期"和"实际"是否一致。第二，看请求头：浏览器 Network 里请求的响应头会显示缓存状态，Vercel 部署会带 `x-nextjs-cache` 头（`HIT`/`MISS`/`STALE`），自托管可以自己加类似标记。第三，看日志：`next start` 的日志会显示路由是 `PRERENDER`（静态）还是 `RENDER`（动态），配合 `unstable_cache` 的日志能定位数据层缓存。

调试的通用流程：先确认"哪一层缓存应该生效"，再逐层验证"它是否生效"，最后定位"在哪一层断了"。用日志和响应头说话，不要靠"感觉页面没变"来猜——页面没变可能是 Router Cache、CDN、浏览器缓存、Data Cache 四者中任何一个在起作用。

再往深一层说，动态渲染不一定是坏事，关键是"动态的范围"要可控。整页动态和局部动态的成本完全不同：整页动态意味着每次请求都重新执行所有组件，数据库查询、第三方调用全部重复；局部动态意味着只有客户端小组件每次重新获取，服务端骨架仍然走缓存。工程上优先保证"页面壳子"静态，把动态限制在真正需要实时的区域，这是 Next.js 性能优化的第一原则。

排查"页面为什么是动态的"，有一个标准动作：在 `page.tsx` 里逐行检查有没有 import 动态 API。`cookies()` 经常被隐藏在某个工具函数或第三方封装里，从 `next/headers` 引入的每一处都要追到源头。很多团队以为"我没调用 cookies，为什么页面是动态的"，最后发现是某个日志中间件调用了 `headers()`——这类隐性依赖是缓存问题里最磨人的一类。

#### 第二层：数据库访问——不经过 fetch 的缓存

直接查数据库（Prisma、SQLAlchemy、pg）的代码不经过 Data Cache，因为 Data Cache 只包裹 `fetch`。想让数据库页面也有 ISR 效果，需要手动加缓存层：

```ts
import { unstable_cache } from 'next/cache'

const getPosts = unstable_cache(
  async () => {
    return db.post.findMany()
  },
  ['posts'],
  { revalidate: 300 },
)
```

`unstable_cache` 把任意异步函数的结果缓存进 Data Cache，标签名用于后续精准失效。这是"数据库查询也想缓存"的标准答案。

`unstable_cache` 的缓存键默认包含函数参数和依赖，但有几个使用细节：函数体内不能访问 `cookies()`、`headers()` 等动态 API，否则每次都会重新执行；返回对象必须是可序列化的；标签名要遵循"资源类型 + 标识"的命名约定（比如 `posts:list`），否则后续失效时只能靠猜。缓存函数的最佳实践是"纯函数化"：所有输入通过参数传入，所有输出只依赖参数，这样缓存语义才清晰。

数据库查询缓存还有一个团队协作层面的大坑：每个开发者在不同地方各写各的缓存，标签不统一、`revalidate` 时间不一致，页面之间数据互相打架。正确的做法是把"缓存策略"收敛到数据访问层：项目里只有一个 `getPosts` 函数，缓存逻辑写在函数内部，调用方不感知。业务代码里出现裸的 Prisma 查询是 review 红线——数据访问必须经过带缓存策略的统一入口。

#### 第三层：Server Actions 与缓存失效

Server Actions 是写在服务端的异步函数，表单或事件可以直接调用，不需要单独的 API 路由。写完后最重要的一步是失效缓存：

```ts
'use server'
import { revalidatePath, revalidateTag } from 'next/cache'

export async function createPost(formData: FormData) {
  const post = await db.post.create({ data: ... })
  revalidateTag('posts')   // 失效所有带 posts 标签的缓存
  revalidatePath('/blog')  // 或者按路径失效
  return post
}
```

`revalidatePath('/blog')` 让该路径的 Full Route Cache 失效；`revalidateTag('posts')` 让所有带 `posts` 标签的数据缓存失效。两者的区别是：路径级失效影响页面，标签级失效影响数据。写变更操作后不调用失效函数，页面就永远显示旧数据——这是"我改了数据库页面没变"的头号原因。

失效粒度选哪个，取决于页面和数据的对应关系。一个页面只依赖一类数据，`revalidatePath` 简单直接；一个页面聚合了多个数据源，`revalidateTag` 更精准——只失效变化的那一类，其他缓存保留。实践中团队容易犯的错是"两个都用"，结果一次写入触发全站失效，缓存形同虚设。规则应该是：数据入口统一打标签，变更时只失效相关标签；路径失效只在"页面本身的结构变了"时使用。

标签命名是失效体系的地基：`posts:list`、`posts:detail:{id}`、`user:{id}`，一套可预测的命名规范让"哪个变更失效哪个标签"一目了然。反之，标签随便起（`data`、`cache1`），三个月后没人知道该失效谁，最终只能全站 `revalidatePath('/')`。把标签命名写进团队规范，和数据库索引命名同等重要。

Server Actions 的幂等性：表单可能被重复提交（用户双击、网络重试），Action 要能容忍重复执行。做法是给操作加唯一标识（订单号、请求 ID），数据库层用唯一约束兜底；`useActionState` 的 pending 状态只能减少重复，不能消灭重复——真正的防线在服务端。

Server Actions 的错误处理也值得单独说：服务端抛错默认返回 `{ error: string }`，客户端可以用 `useActionState` 拿到并渲染；不要为了"用户体验"把错误吞掉，表单校验失败、权限不足、写库失败要区分对待。权限校验必须在 Action 内部重新做一遍，不能依赖客户端传过来的判断结果——Server Action 本质是 API，暴露给浏览器的入口都要当公共接口对待。

#### 第四层：部署形态——Vercel 与自托管的差别

Vercel 上很多能力开箱即用：Image Optimization、ISR、边缘缓存。自托管时这些能力需要自己补齐：图片优化需要独立的 sharp 处理或换成 CDN 服务，ISR 的 on-demand 失效需要持久化存储，边缘函数需要额外的运行时。

自托管部署的核心决策是 `next start` 加反向代理，注意 `output: 'standalone'` 会生成最小化的 server 目录，镜像体积从几百 MB 降到几十 MB：

```js
// next.config.ts
const nextConfig = {
  output: 'standalone',
}
```

Dockerfile 里只复制 `.next/standalone`、`.next/static` 和 `public`，再用 Nginx 或 Caddy 做反向代理和静态资源缓存。

自托管还有一个常被忽略的点：`next start` 是单进程的，多实例部署需要自己管理进程数和负载均衡；`next.config` 里的实验开关和 Node.js 版本兼容性也要在部署前验证。Vercel 帮你处理的那些事（进程管理、日志、监控、证书），自托管都要自己补齐——不是不能做，而是要知道成本在哪里。小流量项目用 Docker 单实例加反向代理就够了，流量上来再考虑多实例和共享缓存。

部署环境还有一个和缓存直接相关的细节：环境变量和构建期数据。`NEXT_PUBLIC_*` 变量在构建时被打进 bundle，改它必须重新构建；服务端环境变量在运行时读取，改它可以只重启。理解"哪些是构建期、哪些是运行期"，能避免"改了环境变量页面没变"的困惑。同理，ISR 的 `revalidate` 时间在构建时确定，运行时修改配置不会改变已构建页面的行为。

### 实战应用

#### 模式速查：数据获取决策表

| 场景                        | 做法                                 | 缓存行为            |
| --------------------------- | ------------------------------------ | ------------------- |
| 文章列表，可接受 5 分钟延迟 | `unstable_cache` + `revalidate: 300` | Data Cache 定时刷新 |
| 用户个性化首页              | 动态渲染 + `no-store`                | 每次请求实时        |
| 后台管理提交表单            | Server Action + `revalidatePath`     | 提交后立即刷新      |
| 第三方 API 限流             | `fetch` + `revalidate: 3600`         | 缓存一小时          |
| 构建时不变内容              | 默认静态                             | 构建时生成一次      |

给这张表配一个实战练习：拿你手上的博客应用，给首页、文章页、用户页各画一张"数据新鲜度"表——数据从哪来、缓存多久、谁触发失效。画完你会发现，多数页面的答案其实是"默认静态"和"每次请求"两种，真正需要精细配置的只有中间那类。把这张表写进 README，新同事就不会再乱改缓存配置。

#### 检查清单：缓存配置 Review 清单

每次改缓存配置，过一遍这张清单：

| 检查项     | 通过标准                              |
| ---------- | ------------------------------------- |
| 缓存层     | 明确是哪一层缓存（Route/Data/Router） |
| 新鲜度承诺 | "多久更新一次"能一句话回答            |
| 失效路径   | 每个写操作都有对应的失效调用          |
| 标签命名   | 遵循统一规范，可预测                  |
| 动态污染   | 静态页面没被动态 API 污染             |
| 调试证据   | 构建输出/响应头/日志验证过            |
| 降级方案   | Redis 挂了/数据库慢了页面表现可控     |

七项全过，缓存配置才算"可解释"。把这张清单放进 PR 模板，缓存问题就不会再靠"试"来解决。

#### 陷阱与正确做法

**陷阱一：revalidate 设了但页面不更新。** 反面案例：`fetch` 设了 `revalidate: 60`，但页面调用了 `cookies()`，整个路由变成动态渲染，Data Cache 失效但 Full Route Cache 从不生效。正确做法：先确认页面是否被动态 API 污染，把个性化逻辑拆到独立的客户端组件里。

**陷阱二：变更后忘了失效缓存。** 反面案例：Server Action 写库成功，页面列表还是旧的，刷新也没用，因为 Router Cache 在客户端缓存了导航历史。正确做法：写操作后调用 `revalidatePath` 或 `revalidateTag`；如果数据在客户端被缓存，用 `router.refresh()` 强制刷新。

**陷阱三：自托管图片全部 400。** 反面案例：部署到自建服务器后 `<Image>` 全部报错，因为 Image Optimization 的 sharp 依赖没装。正确做法：安装 `sharp` 依赖，或把 `images.unoptimized` 打开并交给 CDN。

**陷阱四：把密钥写进客户端组件。** 反面案例：数据库连接串出现在 `"use client"` 文件引用的模块里，构建后被写进浏览器 bundle。正确做法：所有含密钥的代码只被服务端组件导入，客户端需要的数据通过 props 或 Server Function 传递。

**陷阱五：缓存配置散落在每个页面。** 反面案例：每个页面自己写 `revalidate`，数字各不相同，数据层还绕过缓存直接查库，导致同一份数据在页面上显示不同步。正确做法：缓存策略收敛到数据访问函数，页面层只声明"静态/动态"，不碰具体秒数；所有失效走统一的标签体系。

**陷阱六：把 ISR 当实时数据用。** 反面案例：库存、价格这类高频变化数据用 `revalidate: 60`，页面仍显示一分钟前的价格，用户下单时才发现价格变了。正确做法：时效敏感的数据走动态渲染或客户端实时获取；ISR 只用于"延迟可以接受"的内容型数据。

**陷阱七：所有数据都走客户端 fetch。** 反面案例：页面初始化数据用 `useEffect` 拉取，首屏先是空壳、再 loading、再内容，SEO 也拿不到内容。正确做法：首屏数据走服务端组件获取；客户端 fetch 只留给"用户操作触发的数据"。

**陷阱八：缓存降级没有预案。** 反面案例：数据库变慢时，页面直接报错，因为每个请求都实时查库。正确做法：内容型页面保留"最后成功缓存"作为降级（stale-while-revalidate），数据库抖动时用户看到旧内容而不是错误页。

### 进阶思考

缓存体系是 Next.js 的上限所在，也是它最值得花时间的部分。三个进阶方向：一是按需重新验证（on-demand revalidation）：配合 webhook，CMS 发布内容后立即失效对应页面，而不是等 `revalidate` 到期。二是 `Instrumentation` 和运行时配置：自托管环境下把 ISR 的缓存存到共享存储（如 S3），多实例部署时缓存才能一致。三是性能排查方法论：用 `next dev --turbo` 加速开发，用 `next build` 的输出清单检查每个路由的渲染类型，用 RSC Payload 的大小判断服务端组件是否真的在减少包体积。

容易忽视的运维视角：缓存失效是有传播延迟的。`revalidate` 到期后，下一次请求触发后台重新生成，期间用户看到的还是旧版本——这意味着"更新后立即生效"和"定时刷新"是两种不同的承诺，别混为一谈。如果你的业务要求"发布即生效"（新闻、活动页），必须用按需失效或动态渲染；能接受"最多延迟一个刷新周期"，才适合 `revalidate`。把承诺和机制对齐，缓存才能成为契约而不是事故源。

最后总结下篇的路线：fetch 语义决定数据层缓存，unstable_cache 扩展数据库缓存，Server Actions 决定写后失效，部署形态决定缓存一致性。四个环节环环相扣，任何一环配置错位，都会表现为"页面数据不对"——但排查路径永远是"先看构建输出，再看响应头，最后看日志"。数据获取的工程化，本质是让"数据多久更新一次"这个问题在每个页面都有明确答案。

承诺是理解缓存的核心概念：缓存的本质是你对用户和系统的承诺——这个页面多久更新一次，这个数据多久重新拉取。承诺写清楚（代码可读）、可验证（构建输出/日志）、可失效（revalidate 机制），缓存就从玄学变成了工程。下篇开始，我们会离开框架层，进入 shadcn/ui、Tailwind 等组件与样式主题——同样的"承诺"思维依然适用。

团队协作的建议：数据获取和缓存最容易产生"隐性知识"——某个页面为什么这么配缓存，往往只在写它的人脑子里。把这些决策写进代码注释（`// revalidate 3600：内容团队每小时更新，可接受一小时延迟`）和 README 的"数据新鲜度表"，把隐性知识变成显式文档。团队越大，这套文档的价值越高——它不是给新人看的，是给三个月后的自己看的。

最后给一个"缓存心态"的总结：不要把缓存当成"优化手段"，要当成"系统契约"。契约的一方是"数据新鲜度承诺"（多久更新一次），另一方是"成本和延迟"（缓存多久省多少资源）。每次配置缓存，都是在两个方向之间做显式权衡：承诺越新鲜，成本越高；承诺越宽松，用户看到旧数据的风险越大。把权衡写清楚，缓存配置就不再是"抄别人的数字"，而是"基于自己业务的决策"。

实操动作：给你的项目建一张"缓存地图"文档，列出每个页面/数据源的三列——数据来源、缓存策略、失效时机。这张地图放在 README 或 docs 里，每次改缓存先改地图再改代码。三个月后，新同事（和三个月后的你）看到地图，五分钟就能理解整个系统的数据新鲜度设计，不需要翻代码猜。文档的投入是半小时，省下的是无数次"为什么页面是旧的"的排查。

最后用一个比喻收束：缓存体系像冰箱——不同的食材有不同的保质期（revalidate 时间），不同的区域温度不同（Route/Data/Router 各层），过期食材要定期清理（失效机制），停电了要有应急预案（降级方案）。管理缓存和管理冰箱一样，不是"买回来就完事"，而是"持续维护"：知道每样东西放哪、什么时候过期、坏了怎么处理。希望这篇下篇能帮你把项目的"缓存冰箱"整理得井井有条。

数据获取的终极原则只有一句：让"数据多久更新一次"成为每个页面都能明确回答的问题。静态页面答"构建时"，内容页答"每小时"，用户页答"每次请求"，后台页答"提交后立即"。答不上来，就是缓存配置还没想清楚。学习路径：读官方文档 Caching 章节，然后把你项目里每一个 `fetch` 和 Server Action 都标上缓存语义。
