### 背景

星期二下午，你合上电脑准备下班，PM 在群里喊："线上崩了！！！"你本地跑得好好的，为什么线上不行？版本不同、依赖不同、系统库不同、环境变量不同——"我本地是好的"这句话，是每个工程师职业生涯里说过最多也最心虚的谎话。

Docker 解决的是这个问题的根源：把"运行环境"本身变成可以打包、复制、校验的产物。镜像里不光有你的代码，还有操作系统层、运行时、依赖、配置。任何一台装了 Docker 的机器，跑同一个镜像，得到的就是同一个环境。

这篇文章是 Docker·K8s 系列的上篇，只讲 Docker 单机层：镜像和容器是什么关系、分层存储怎么工作、网络和数据卷怎么用、Dockerfile 怎么写才专业。中篇讲 Kubernetes 的核心对象，下篇讲存储、扩缩容和本地开发。

在进入机制之前，先破除两个迷思。迷思一："Docker 就是虚拟机。"容器和虚拟机最大的区别在于共享内核：虚拟机每个实例都带一个完整操作系统，启动按分钟算；容器只是宿主上的受限进程，启动按毫秒算。迷思二："Docker 能解决所有环境问题。"它解决的是"运行环境一致"，解决不了"配置不一致"——环境变量、数据库地址这些运行时差异，恰恰是部署事故的第二大来源。理解 Docker 的能力边界，和学会它的命令同等重要。

还有一个战略层面的视角：Docker 之所以成为云原生的事实标准，不是因为"容器技术"本身多神奇，而是它让"构建、分发、运行"三个环节第一次有了统一的交付物。以前交付代码、文档、部署手册，现在交付镜像——一个不可变、可签名、可回滚的产物。这个转变改变的不只是运维流程，还有整个软件的交付哲学。

本篇文章的结构：先讲镜像与容器的关系，再讲分层存储和 Dockerfile，然后讲多阶段构建、网络与数据卷，最后给一组实战命令、陷阱和进阶方向。每一节都可以单独查阅，但建议按顺序读一遍——后面的概念都建立在前面的基础上。

### 核心原理

#### 第一层：镜像与容器——模板与实例

镜像是只读模板，容器是镜像的运行实例。一个镜像可以启动多个容器，每个容器有独立的文件系统写入层、进程空间和网络栈。类比：镜像是类，容器是对象；镜像是光盘母盘，容器是刻录出来的可写副本。

理解"只读 + 可写层"对排障很重要：容器运行时对文件系统的所有修改都发生在最顶层的可写层，容器删除后这层随之消失。所以"进容器改个配置"是临时行为，正确姿势永远是改镜像或挂载卷。`docker commit` 可以把运行中的容器固化成新镜像，但强烈不推荐——它把"运行时状态"混进了"构建产物"，镜像不可复现，团队会失去对版本的控制。

镜像的命名与标签也有一套约定：`仓库名:标签`（如 `myapp:1.0.3`），标签应该不可变——每次构建用新 tag（git SHA 或版本号），而不是覆盖 `latest`。`latest` 的语义是"最新"，但"最新"在部署记录里无法追溯，回滚时不知道回到哪。生产环境的铁律：不用 latest，用不可变 tag。

镜像的存储布局同样值得了解：多个镜像共享底层只读层，相同的基础镜像层只在磁盘上存一份。这意味着"基础镜像不换、只改应用层"的构建策略，不仅能复用构建缓存，还能节省磁盘空间。反过来，经常换基础镜像（比如每次都用 `latest`）会破坏层共享，磁盘占用和拉取时间同时上升。

````
```bash
docker build -t myapp:1.0 .     # 从 Dockerfile 构建镜像
docker run -d -p 8080:80 myapp:1.0   # 启动容器，映射端口
docker ps                       # 查看运行中的容器
docker logs -f myapp            # 看日志
docker exec -it myapp sh        # 进入容器调试

容器不等于轻量虚拟机。虚拟机虚拟化硬件，容器只是受限的进程：共享宿主内核，靠 namespace 隔离资源、cgroup 限制用量。这也是容器启动快（秒级）、密度高（一台机器跑几十个）的原因。

#### 第二层：镜像分层——为什么构建快、复用高

Dockerfile 的每一行指令生成一个只读层，层与层之间做内容寻址缓存。构建时，某一层没变，它和它后面的缓存可以直接复用——这是"只改代码重新构建只要几秒"的原因。

层缓存是把双刃剑。好处是构建快，坏处是"缓存毒化"：一条高频变化的指令（比如 `COPY . .`）放在依赖安装之前，会让它之后的所有层全部失效，构建时间从几秒退化到几分钟。反过来，如果一条不稳定的命令（`apt-get update` 不带固定版本）长期命中缓存，又会把旧包固化进镜像。工程上的折中：依赖类指令尽量提前且固定版本，源码类指令放在最后；需要强制刷新缓存时用 `--no-cache` 或调整指令顺序。

Dockerfile 的"最佳实践"远不止顺序问题，还有几条硬规则：每条指令尽量只做一件事（可读、可缓存）；`RUN` 里多条命令用 `&&` 连接并清理缓存（减少层数和体积）；固定基础镜像版本（不用 `latest`）；优先用官方镜像和轻量基础（`alpine`、`slim`、distroless）；`.dockerignore` 排除无关文件。把这些规则写进团队模板，新服务开箱即符合规范。

还有一个和"开发体验"相关的细节：`docker compose` 的 `build` 配置支持 `target` 指定多阶段中的某一阶段——开发环境构建到 dev 阶段（带热更新工具），生产环境构建到 prod 阶段（只留产物）。一套 Dockerfile，两个环境目标，避免"开发和生产两套构建文件"的维护成本。


````

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile
COPY . .
RUN pnpm build
CMD ["pnpm", "start"]

上面的顺序是刻意的：先复制依赖清单再安装依赖，最后复制源码。源码每次变化，前面的层仍然命中缓存，只有最后几层重建。如果把 `COPY . .` 放在安装依赖之前，任何文件改动都会导致依赖重装，构建时间从几秒变成几分钟。

层数不是越少越好，但层数多会让镜像变大、拉取变慢。实践中把构建产物和运行依赖分开（多阶段构建），是控制体积的标准做法。

#### 第三层：多阶段构建——编译和运行分离

多阶段构建用多个 `FROM`，前几阶段编译，最后只拷贝产物到干净的运行镜像：

```

```dockerfile
# 阶段一：编译
FROM node:20-alpine AS builder
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile
COPY . .
RUN pnpm build

# 阶段二：运行
FROM node:20-alpine
WORKDIR /app
COPY --from=builder /app/.output ./.output
ENV NODE_ENV=production
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]

最终镜像里没有源码、没有 node_modules、没有编译器，只有运行必需的文件。前端项目从 1GB 降到 100MB 以内，靠的就是这个。

多阶段构建还有一个安全收益：运行阶段只暴露最小依赖，攻击者即使打进容器，也找不到源码、没有包管理器、没有 shell（如果用 distroless 基础镜像）。镜像瘦身不只是"省存储"，是"缩小攻击面"。配合固定基础镜像版本和定期漏洞扫描（`docker scout`），镜像供应链才能算安全。

镜像安全还有一个容易被忽视的环节：构建缓存里的旧层可能包含已删除的敏感文件。CI 里构建镜像后，不要把缓存长时间保留在共享 runner 上；敏感信息（密钥、token）绝不通过 `ARG` 或 `ENV` 写进镜像——用运行时注入。镜像会分发到很多机器，镜像里的每一层都是"公开的"，安全审查要按"镜像可能被任何人拿到"的标准来做。


#### 第四层：网络与数据卷——容器间的通信和持久化

容器默认网络隔离。常用模式有三种：`bridge` 网络让同网络的容器用服务名互访；`host` 网络直接用宿主机端口；`none` 完全隔离。

网络是容器排障的重灾区，三个高频问题值得提前知道。一是"容器里 localhost 为什么连不上数据库"：容器内 localhost 是容器自己，不是宿主机，访问宿主机服务要用 `host.docker.internal`（Docker Desktop）或宿主机 IP。二是端口映射的绑定地址：`-p 127.0.0.1:8080:80` 只监听本机，`-p 8080:80` 会暴露到所有网卡，云服务器上后者等于裸奔。三是容器间通信优先走自定义网络而不是 `--link`——`--link` 已废弃，自定义网络提供 DNS 服务名解析，容器重启后 IP 变了也不用改配置。

数据卷还有一个"为什么数据还是丢了"的经典场景：挂载的是容器内路径，但忘了把数据库的数据目录挂出来——比如 PostgreSQL 默认把数据放在 `/var/lib/postgresql/data`，只挂 `/data` 当然丢。挂卷前先查应用的默认数据目录，`docker inspect` 看实际写入路径，比事后恢复数据便宜得多。命名卷比绑定挂载更推荐：它由 Docker 管理位置和权限，跨平台行为一致，而绑定挂载依赖宿主机路径，在 CI 和 Mac/Windows 之间经常出现路径差异。



```

```bash
docker network create mynet
docker run --network mynet --name api myapp
docker run --network mynet --name web -p 80:80 webapp
# web 容器里可以直接访问 http://api:8080

容器删除后文件系统也没了。要持久化数据，用数据卷（volume）或绑定挂载：数据库、上传文件、日志必须挂卷，否则重启即丢。

```

```bash
docker volume create pgdata
docker run -v pgdata:/var/lib/postgresql/data postgres:16

### 实战应用

#### 模式速查：日常命令

| 场景           | 命令                                 |
| -------------- | ------------------------------------ |
| 构建并打标签   | `docker build -t myapp:1.0 .`        |
| 启动并映射端口 | `docker run -d -p 8080:80 myapp:1.0` |
| 查看日志       | `docker logs -f <容器名>`            |
| 进入容器       | `docker exec -it <容器名> sh`        |
| 清理无用资源   | `docker system prune`                |
| 多服务编排     | `docker compose up -d`               |

日常使用记住一个原则：`docker run` 只适合调试，多服务环境一律用 `docker compose`。compose 文件把网络、卷、端口、环境变量声明在一起，`docker compose up -d` 一条命令拉起整套环境，`docker compose down` 一条命令清理。本地开发和 CI 用同一份 compose，环境差异才能压到最小。

排障时还有一组"三连"动作：`docker logs` 看输出，`docker inspect` 看配置和状态，`docker exec` 进容器看现场。遇到"容器一直重启"，先 `docker logs` 看退出原因，再 `docker inspect` 查 `RestartCount` 和 `OOMKilled`——大部分启动失败都能在这三步里定位，不用翻文档。

#### 检查清单：Dockerfile 上线前自检

| 检查项   | 通过标准             |
| -------- | -------------------- |
| 基础镜像 | 固定版本，非 latest  |
| 层缓存   | 依赖指令在源码前     |
| 多阶段   | 运行镜像无构建工具   |
| 用户权限 | 非 root 运行         |
| 安全     | 无密钥，镜像可审计   |
| 体积     | 记录构建后大小并监控 |
| 健康检查 | 配置了 HEALTHCHECK   |

七项过完，镜像才算"可上线"。



#### 陷阱与正确做法

**陷阱一：COPY 顺序错误导致缓存失效。** 反面案例：`COPY . .` 放在依赖安装前，每次改动全量重装。正确做法：先复制依赖清单，装完依赖再复制源码，利用分层缓存。

**陷阱二：容器以 root 运行。** 反面案例：生产镜像默认 root，被攻破后容器内权限等于宿主管理权。正确做法：`USER node` 切换到非特权用户，文件权限配合调整。

**陷阱三：数据不挂卷。** 反面案例：数据库容器没挂卷，`docker rm` 后数据全没。正确做法：所有有状态数据用 volume 或 bind mount，并在 compose 文件里声明。

**陷阱四：镜像里塞构建工具。** 反面案例：单阶段构建，镜像里全是编译器、包管理器、源码，体积巨大且暴露源码。正确做法：多阶段构建，运行镜像只留产物。

**陷阱五：镜像 tag 用 latest。** 反面案例：生产环境 `image: myapp:latest`，无法确认线上跑的是哪个版本，回滚无门。正确做法：用不可变 tag（git SHA 或语义化版本），发布记录可追溯；latest 只留给本地开发。

**陷阱六：数据卷权限问题。** 反面案例：容器以非 root 用户运行，但挂载的宿主机目录属于 root，写入时报 permission denied，应用启动失败。正确做法：挂载目录的所有权对齐（chown 或命名卷），或调整容器用户的 UID 与宿主机一致；数据库镜像尤其常见，先确认数据目录可写再启动。

还有一个实战技巧：`docker compose` 的 `depends_on` 只保证启动顺序，不保证依赖就绪——数据库容器起来了不代表端口能连。配合 healthcheck（`pg_isready`）和 `condition: service_healthy`，才能让应用等数据库真正就绪再启动。这个细节在本地"偶尔连不上"和 CI "随机失败"里反复出现，是 compose 排障的第一课。

### 进阶思考

Docker 单机掌握之后，自然的问题是"多台机器怎么办"：谁来调度、谁来保证重启、谁来滚动更新。这就是 Kubernetes 的领域，也是本系列中篇的主题。

值得先深入的两个单机方向：一是 `docker compose` 作为本地开发的标准编排——数据库、缓存、消息队列一条命令拉起，配合 volume 挂载热更新；二是镜像供应链安全——`docker scout` 扫描漏洞、固定基础镜像 digest、签名校验，把"依赖安全"纳入 CI。

再补两个进阶主题。一是镜像瘦身的系统方法：不只靠多阶段构建，还有 `--squash`、distroless 基础镜像、按架构分离（`--platform`）、压缩层。瘦身到极致不是目的，目的是减少拉取时间、存储成本和攻击面——三者都随体积线性增长。二是容器安全的纵深：非 root 用户、只读根文件系统（`read_only: true`）、capabilities 最小化、`--security-opt no-new-privileges`，一层层收窄容器权限。安全不是某一个开关，是默认收敛的配置组合。

第三个值得深入的方向是容器编排的前置认知：单机 Docker 熟练之后，你自然会遇到"多台机器怎么管"的问题。K8s 不是"更大的 Docker"，它是一套完全不同的抽象——Pod、Deployment、Service 这些概念，需要在"声明式"的心智模型下理解。中篇会从零讲起，但如果你现在就开始思考"镜像怎么分发到多台机器、容器挂了谁来重启"，你已经站在正确的起跑线上了。

学习路径的最后一段：用 compose 搭一个"应用 + 数据库 + 缓存"的本地环境，把 Dockerfile 改成多阶段构建并对比体积，再给镜像配 HEALTHCHECK 和漏洞扫描。这些练习做完，Docker 单机层就过关了——中篇见。

"什么时候 Docker 不是答案"的判断：单进程应用（一个二进制、无依赖）直接用 systemd 管理可能更简单；需要访问宿主机特殊硬件（GPU、USB）或深度内核能力时，容器会引入额外复杂度。容器适合"多依赖、多实例、需要一致环境"的应用，不适合"本来就很简单的进程"。选型不是"有容器就高级"，而是"容器是否真的降低了你的运维复杂度"。

关于文档的建议：把团队常用的 Docker 命令和镜像规范写进 README，新成员克隆仓库后先读"容器规范"再动手。镜像构建、标签约定、健康检查、安全要求，这些知识如果不沉淀成文档，就会变成"只有老成员知道"的隐性经验——文档化的成本是半小时，省下的是无数次"为什么你的镜像能跑我的不能"的对话。

"学习验收"的标准：学完 Docker 上篇，你应该能独立完成三件事——给一个 Node/Python 项目写出多阶段 Dockerfile；用 compose 搭起"应用 + 数据库"的本地环境；用日志和 inspect 定位一次"容器反复重启"的问题。三件事都能独立完成，Docker 单机层才算真正过关，可以放心进入 Kubernetes。

迁移到容器后，用三个数字衡量收益——部署时间（分钟级变秒级）、环境搭建时间（小时级变分钟级）、故障恢复时间（重装系统变重启容器）。如果三个数字没有明显改善，说明容器化只是"换了运行方式"而没有"改变交付方式"——真正的容器化收益，来自"镜像即交付物"的流程变革，而不是容器本身。

镜像的推送和拉取也是一条需要设计的链路：私有仓库（Harbor、GitHub Container Registry）要配置认证和访问控制，CI 构建的镜像推送到仓库，生产环境从仓库拉取。镜像的"来源可信"是供应链安全的一部分——用不可变 tag 加签名（cosign），部署前校验镜像指纹，防止"仓库被投毒"。镜像签名看起来是"额外步骤"，但它是"线上跑的镜像 = CI 构建的镜像"这个等式成立的唯一保证。

`docker compose` 在本地开发里还有一个经常被忽略的能力：它可以定义"开发专属服务"（数据库、缓存、消息队列）和"应用服务"分离，通过 `profiles` 按需启动。开发环境用 compose 拉起依赖，生产环境用 K8s 部署应用——两套环境共享镜像，但编排方式不同，这正是"镜像一致、编排分离"的标准形态。把"compose 管依赖、K8s 管应用"写进团队约定，环境差异会大幅减少。

容易被忽略的细节：容器的时间同步和日志时区。容器默认继承宿主内核时间，但日志的时间戳格式要统一（UTC 还是本地时间），否则跨时区排障时"对时间"就能浪费半小时。日志输出到 stdout/stderr（而不是文件），由日志收集器统一采集——这是"容器只做一件事"原则的延伸：应用不关心日志去哪，日志管道负责收集和转发。

如果把这一篇浓缩成一句话：容器是"可复制的运行环境"，镜像分层和多阶段构建让复制既快又小，网络和数据卷让复制出来的环境真的能用。单机层的每个概念，到 Kubernetes 里都会以更抽象的形态出现——中篇的 Pod 就是"一个或多个容器 + 共享网络和存储"的组合，你在 Docker 里理解的卷和网络，直接映射到 PVC 和 Service。打好单机地基，再往上走才不会悬空。

学习路径：读完官方 Dockerfile 最佳实践文档，把项目改成多阶段构建并记录体积变化，再用 compose 搭一个"应用 + PostgreSQL + Redis"的本地环境。容器不是虚拟机，理解这一点，后面的 Kubernetes 才不会跑偏。

最后给一条判断"是否真的会 Docker"的验收线：不看文档，能独立回答三个问题——我的镜像为什么比预期大？我的容器为什么起不来？我的数据为什么重启就丢？三个问题都能在五分钟内定位原因，Docker 单机层的功夫才算到家。这三个问题分别对应镜像分层、启动日志与健康检查、数据卷——也就是本文反复强调的三条主线。


镜像仓库的安全基线也：私有仓库开启访问认证，CI 推送用最小权限的机器人账号，生产环境拉取用只读凭据；镜像扫描（漏洞、密钥、恶意软件）接入 CI，高危镜像禁止推送。镜像一旦发布就不可变——覆盖同一个 tag 等于篡改历史，回滚和审计都会失效。把「镜像不可变 + 来源可验证」写进发布规范，供应链安全才不是口号。

容器资源限制是单机稳定性的底线：`docker run` 用 `--memory` 和 `--cpus` 限制容器用量，compose 里用 `deploy.resources.limits` 声明；没有限制的容器可以吃光整台机器，一个内存泄漏就能拖垮所有邻居。限制要基于压测数据设置（先不加限制观察峰值，再加 30% 余量），而不是拍脑袋。资源限制不是性能优化，是故障隔离。

日志的「标准输出」约定：容器应用把日志写到 stdout/stderr，由日志收集器统一采集——应用不写日志文件，因为容器文件系统是临时的，日志文件会随容器消失。配合结构化日志（JSON 格式），日志收集器可以直接解析字段，排障时按 trace_id 检索。容器改变了日志的「归属」：日志属于管道，不属于容器。


镜像「标签策略」语义化版本（1.2.3）适合对外发布，git SHA 适合 CI 内部追溯，两者可以同时打（`myapp:1.2.3` 和 `myapp:sha-abc123`）。`latest` 标签只留给本地开发，生产环境一律用不可变标签——不可变标签是「部署可回滚、镜像可审计」的前提，这是镜像管理最便宜也最重要的一条规则。

compose 的「健康检查」`docker compose` 的 `healthcheck` 可以在容器内执行检查命令（如 `curl -f http://localhost:3000/healthz`），配合 `depends_on.condition: service_healthy` 让依赖服务就绪后再启动应用。没有健康检查的 compose 环境，应用经常「数据库还没就绪就启动」然后反复重试——健康检查是本地环境和生产环境共用的一套就绪协议。


`.dockerignore` 的价值它决定「哪些文件进入构建上下文」——`node_modules`、`.git`、`dist`、`*.log` 都不该进，否则每次构建都要传输大目录，镜像还可能泄露源码和密钥。`.dockerignore` 是 Dockerfile 的「白名单思维」：默认排除一切，按需放行。


容器是「可复制的运行环境」——这句话值得反复咀嚼，它是 Docker 所有实践的起点。
```
