### 背景

用 Deployment 和 Service 把服务跑起来之后，真正的生产问题才刚开始：域名怎么进来？HTTPS 证书谁管？数据库数据存在哪里？流量涨了怎么自动加副本？每个 Pod 能吃多少资源？这些问题不解决，集群只是"多台机器上的 Docker"。

这一篇是 Docker·K8s 系列的收尾，覆盖三层：入口层（Ingress 与 TLS）、状态层（PVC 与有状态应用）、规模层（资源配额与 HPA），最后给出本地开发的标准姿势——用 k3d 在笔记本上跑一个完整的集群。

在展开之前，先回答一个常见的疑问："这些是不是运维才需要懂？"答案是否定的。开发者写出 Deployment 和 Service 之后，域名、存储、资源、扩容这些决策就会追上来：你的服务要不要暴露公网？数据放 PVC 还是对象存储？内存限制写多少？HPA 阈值设多少？每个问题都影响应用架构——比如"无状态设计"直接决定你能不能轻松扩容，"配置外置"直接决定你换环境要不要改镜像。K8s 不是运维的专属领域，它是应用架构的一部分。

这个系列到收尾，很多读者会问："我什么时候才需要真的上 K8s？"一个诚实的回答：单机部署够用就别上。K8s 解决的是"多机器、多服务、频繁发布"的组合问题，它的复杂度是真实存在的。但当你的服务数量、发布频率、故障恢复需求跨过某个阈值后，手工运维的复杂度会超过 K8s 本身的复杂度——这个拐点每个团队不同，判断标准是"你花在部署上的时间是不是每周都在增长"。

本篇的结构：入口层（Ingress 与 TLS）→ 状态层（PVC/StatefulSet）→ 规模层（资源/HPA）→ 本地开发（k3d），最后是生产检查清单、陷阱和进阶方向。三篇合起来，是从"docker run"到"生产集群"的完整路径。

### 核心原理

#### 第一层：Ingress——统一入口与 TLS

Service 是集群内部的负载均衡，Ingress 是集群对外的入口：按域名和路径把请求路由到不同 Service，并在入口层终结 HTTPS。

Ingress 和 Service 的分工值得再强调一遍：Service 负责集群内的稳定访问，Ingress 负责集群外的路由。没有 Ingress 时，你可以用 NodePort 或 LoadBalancer 暴露服务，但每个服务都要占一个端口或一个负载均衡器，域名、路径、TLS 全要手动管。Ingress 把"外部流量策略"收敛到一份配置里：一个 Ingress 对象可以按 host 分域名、按 path 分服务、统一挂证书，入口层的变更不需要动任何 Service。

TLS 证书的管理是 Ingress 最容易被低估的部分。手动上传证书意味着要盯过期时间，证书一过期整站白屏。cert-manager 把这件事变成声明式的：你创建一个 `Certificate` 资源，它自动向 Let's Encrypt 申请、续期、把证书写进 Secret，Ingress 引用 Secret 即可。接线方式是通过 Ingress 注解（`cert-manager.io/cluster-issuer`）声明证书策略，集群里统一配置 issuer，业务团队只写一行注解。

Ingress 的性能和可靠性也值得关注：Ingress Controller 是集群流量的咽喉，它挂了，所有外部访问都断。生产环境要给 Controller 预留资源、配置多副本、监控它的 QPS 和延迟。常见事故是"证书续期失败但没告警"和"Controller 版本升级后注解不兼容"——把这两项加进监控和发布检查，入口层才算稳。

还有一个"南北向 vs 东西向"的概念区分：Ingress 管南北向（外部 → 服务），Service 管集群内的东西向（服务 → 服务）。微服务之间的大量调用是东西向，走 Service 和 mTLS；只有用户流量是南北向，走 Ingress。区分清楚，网络策略（NetworkPolicy）才能写对——默认拒绝东西向、只放行必要路径，是零信任的基础。

TLS 证书的管理是 Ingress 最容易被低估的部分。手动上传证书意味着要盯过期时间，证书一过期整站白屏。cert-manager 把这件事变成声明式的：你创建一个 `Certificate` 资源，它自动向 Let's Encrypt 申请、续期、把证书写进 Secret，Ingress 引用 Secret 即可。接线方式是通过 Ingress 注解（`cert-manager.io/cluster-issuer`）声明证书策略，集群里统一配置 issuer，业务团队只写一行注解。

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp
spec:
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: myapp
                port:
                  number: 80
```

Ingress 本身是规范，实际干活的是 Ingress Controller（Nginx、Traefik、云厂商的 ALB）。证书管理用 cert-manager：它监听 Ingress 的注解，自动申请并续期 Let's Encrypt 证书，TLS 从"手动上传证书"变成"声明一下就行"。

#### 第二层：持久化存储——PVC 与 StorageClass

普通 Pod 的文件系统是临时的。持久化用 PersistentVolumeClaim（PVC）声明"我要多大、什么访问模式"，StorageClass 负责真正分配底层存储：

这里最容易混淆的三个概念：PV（PersistentVolume）是"存储资源"本身，PVC 是"存储资源的申请单"，StorageClass 是"存储资源的工厂"。开发者平时只写 PVC，集群管理员配置 StorageClass，动态供给（Dynamic Provisioning）会自动创建底层 PV。本地开发（k3d）用 local-path，云上根据场景选云盘、EBS、EFS——存储类型的选择直接影响性能和成本，这不是写代码能解决的问题。

存储性能还有一个"IOPS 和延迟"的选型维度：云盘的 IOPS 决定数据库的吞吐上限，EFS/CFS 这类网络文件系统延迟更高但支持多节点共享。选型的判断标准是"访问模式"：单节点独占（数据库）用块存储，多节点共享（日志、上传目录）用文件存储，海量非结构化（图片、备份）用对象存储。存储选型错了，后面迁移的代价是"数据搬迁 + 停机窗口"。

备份策略不要依赖存储本身：PVC 数据要定期备份到对象存储（数据库用 `pg_dump` 类工具，文件用同步工具），备份要验证"能恢复"而不是"备份成功"。K8s 生态里 Velero 是标准方案：备份集群资源 + PVC 数据到对象存储，恢复时可以重建整个命名空间。每季度做一次真实的恢复演练——备份的价值只在恢复时兑现。

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
```

在 Deployment 里把 PVC 挂进容器路径，数据就不随 Pod 重建丢失：

```yaml
spec:
  containers:
    - name: postgres
      volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: postgres-data
```

有状态应用（数据库、消息队列）除了存储，还需要稳定的网络身份和有序启停，这超出 Deployment 的能力，用 StatefulSet。StatefulSet 给每个副本固定名字（`pg-0`、`pg-1`）和固定 PVC，是"集群内数据库"的标准答案。

StatefulSet 的使用有一条重要提醒：它解决的是"身份稳定"，不是"数据备份"。集群内跑数据库，备份、恢复、故障切换仍然要自己负责——建议用 `pg_dump` 定时备份到对象存储，或直接用云厂商的托管数据库。很多团队在 K8s 里跑 PostgreSQL 最后都被"运维负担"劝退，不是因为技术上不行，而是因为备份和升级的复杂性被低估了。

还有一个现实建议：新项目尽量用云厂商托管数据库（RDS、TDSQL），把数据库运维外包；只有"必须自托管"（数据合规、成本、定制）时才用 StatefulSet。K8s 上跑有状态服务是"能力"，但不是"默认选择"——默认选择是托管服务，除非有明确理由。这个决策能省下团队大量凌晨时间。

#### 第三层：资源配额与自动扩缩容

不给 Pod 设资源限制，是生产事故的温床：一个失控的 Pod 能把整台节点的内存吃光。每个容器都应该声明 `requests`（调度依据）和 `limits`（硬上限）：

`requests` 和 `limits` 的语义要分清：`requests` 是调度器做"能不能放"的依据，`limits` 是运行时"最多能用多少"的约束。`requests` 设得过高会浪费节点资源，设得过低会导致节点超卖；`limits` 不设则可能 OOM 整台节点。还有一个微妙点：`requests` 设 100m、`limits` 设 500m，CPU 可以用突发到 500m，但内存不能超过 limits——CPU 可压缩、内存不可压缩，内存超限就是 OOMKilled。

资源配额的确定方法不是拍脑袋，而是"压测 + 监控"：先在无 limits 的情况下跑压测，看真实峰值（`kubectl top`、监控面板），再按峰值加 30% 余量设置 requests/limits。每季度重新评估一次——业务增长、代码变化都会改变资源画像。资源配额是"活的配置"，不是"上线时填一次"。

节点层面还有两个配套机制：ResourceQuota（命名空间级总量限制，防止一个团队耗尽集群）和 LimitRange（命名空间级默认值，防止有人忘配）。生产集群建议三层都配：容器级 limits、命名空间级 ResourceQuota、节点级水位告警。缺一层，就会有人把集群资源吃光。

`requests` 和 `limits` 的语义要分清：`requests` 是调度器做"能不能放"的依据，`limits` 是运行时"最多能用多少"的约束。`requests` 设得过高会浪费节点资源，设得过低会导致节点超卖；`limits` 不设则可能 OOM 整台节点。还有一个微妙点：`requests` 设 100m、`limits` 设 500m，CPU 可以用突发到 500m，但内存不能超过 limits——CPU 可压缩、内存不可压缩，内存超限就是 OOMKilled。

```yaml
spec:
  containers:
    - name: app
      resources:
        requests:
          cpu: 100m
          memory: 256Mi
        limits:
          cpu: 500m
          memory: 512Mi
```

自动扩缩容用 HorizontalPodAutoscaler：监控 CPU 或自定义指标，副本数在最小和最大之间自动调整：

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
```

HPA 依赖 metrics-server 提供指标，而且扩容有冷却时间——流量突增时不会立刻到位，所以"HPA + 提前扩容 + 弹性测试"要一起做。

HPA 的扩容逻辑还有两个容易被忽略的细节：一是扩容是"期望副本数 = 当前副本数 × 当前指标/目标指标"的乘法，指标翻倍副本就翻倍，指标暴涨可能导致副本数瞬间打满上限；二是缩容有更长的冷静期（默认 5 分钟），防止抖动导致副本频繁增减。生产实践上，把 `behavior` 配置成"扩容快、缩容慢"，再配合压测验证从 2 副本扩到 10 副本的真实耗时，避免流量高峰时 HPA 来不及反应。

弹性还有一个"容量规划"的前置问题：HPA 能把副本数从 2 扩到 20，但节点数不够，新 Pod 永远 Pending。集群级的弹性（Cluster Autoscaler 或云厂商的节点池伸缩）要和 HPA 配套：先算"单节点能放几个 Pod、峰值需要几个节点"，配置节点池的最小/最大范围。没有节点级弹性的 HPA，是"纸上弹性"。

弹性的验收方式只有一种：压测。用 k6 或 wrk 打流量，观察 HPA 扩副本、节点扩容、请求成功率三条曲线，确认"流量涨 → 副本涨 → 节点涨 → 延迟可控"的链路真实成立。弹性演练和故障演练一样，应该定期做，而不是上线当天做一次。

HPA 的扩容逻辑还有两个容易被忽略的细节：一是扩容是"期望副本数 = 当前副本数 × 当前指标/目标指标"的乘法，指标翻倍副本就翻倍，指标暴涨可能导致副本数瞬间打满上限；二是缩容有更长的冷静期（默认 5 分钟），防止抖动导致副本频繁增减。生产实践上，把 `behavior` 配置成"扩容快、缩容慢"，再配合压测验证从 2 副本扩到 10 副本的真实耗时，避免流量高峰时 HPA 来不及反应。

#### 第四层：本地开发——k3d 与 Kind

本地开发跑完整集群的最佳工具是 k3d：它在 Docker 里跑一个轻量 K3s 集群，一条命令起来，配置、Ingress、PVC 全部真实生效，再也不用"线上才发现的 YAML 错误"。

```bash
k3d cluster create dev --port 8080:80@loadbalancer
kubectl apply -f k8s/
```

镜像通过 `k3d image import myapp:dev` 或配置 registry 打进集群。开发时配合 `telepresence` 或端口转发，让本地进程"假装"在集群里，联调体验接近生产。

k3d 之外，`kind` 也是常用选择：kind 用 Docker 容器模拟节点，适合 CI 里跑"K8s 集成测试"；k3d 基于 K3s，资源占用更小、自带 Ingress 和负载均衡，适合日常开发。两者的共同价值是"把 K8s 环境本地化"，让 YAML 的语法错误、探针配置错误、PVC 挂载错误在提交前就暴露——这类错误在线上发现的成本，是本地发现的十倍以上。

本地集群还有一个"配置同步"的实践：把 `k8s/` 目录放在仓库里，本地 k3d 和 CI 的 kind 集群用同一份配置，只有"环境差异"通过 Kustomize overlay 或 Helm values 区分。这样"本地能跑 = CI 能跑 = 生产接近"，环境漂移被压到最小。配置漂移是分布式系统事故的头号来源，本地和线上用同一套声明，是成本最低的防线。

### 实战应用

#### 模式速查：生产部署检查清单

| 项目   | 检查点                         |
| ------ | ------------------------------ |
| 入口   | Ingress 域名、TLS 证书自动续期 |
| 存储   | 有状态服务挂 PVC，备份策略     |
| 资源   | 所有容器配 requests/limits     |
| 扩缩容 | HPA 配置、压测验证扩容速度     |
| 配置   | 敏感信息走 Secret，不写镜像    |
| 可观测 | 日志、指标、Trace 接入         |

检查清单的使用方式不是"部署前看一眼"，而是"每项都要有证据"：证书有 `kubectl get certificate` 验证，存储有 `kubectl get pvc` 看 Bound 状态，资源有 `kubectl top` 看真实用量，扩缩容有压测报告。没有证据的检查项等于没检查。建议把这份清单写进发布模板，每次发布前逐项打勾，而不是依赖某个人"记得"。

清单之外，发布本身也要自动化：CD 流水线（GitHub Actions、GitLab CI）在测试通过后自动 `kubectl apply`，配合 rollout 状态等待和失败回滚，发布从"人肉操作"变成"流水线动作"。人的角色从"执行者"变成"审批者"——发布前看 diff，发布后看指标，手不再碰集群。

#### 检查清单：生产集群上线检查

| 检查项 | 通过标准                     |
| ------ | ---------------------------- |
| 入口   | Ingress 域名 + TLS 自动续期  |
| 存储   | PVC Bound，备份策略落地      |
| 资源   | 容器、命名空间、节点三层配额 |
| 弹性   | HPA + 节点池压测通过         |
| 安全   | Secret 加密、网络策略生效    |
| 可观测 | 指标/日志/告警接入           |
| 发布   | 流水线 + 回滚演练过          |

七项全过，集群才算"生产就绪"。

清单之外，发布本身也要自动化：CD 流水线（GitHub Actions、GitLab CI）在测试通过后自动 `kubectl apply`，配合 rollout 状态等待和失败回滚，发布从"人肉操作"变成"流水线动作"。人的角色从"执行者"变成"审批者"——发布前看 diff，发布后看指标，手不再碰集群。

#### 陷阱与正确做法

**陷阱一：PVC 的 accessMode 选错。** 反面案例：多副本应用需要共享读写，却用 `ReadWriteOnce`，第二个副本挂载失败。正确做法：单写多读场景用 `ReadWriteMany` 或改用对象存储；数据库用 StatefulSet 而不是共享存储。

**陷阱二：limits 设太小导致 OOMKilled。** 反面案例：Node.js 应用内存峰值 400MB，limits 设 256Mi，Pod 反复被杀。正确做法：先不加 limits 跑压测，观察真实峰值，再按峰值加 30% 余量设置。

**陷阱三：HPA 依赖不存在的指标。** 反面案例：配了自定义指标但没装 Prometheus Adapter，HPA 永远 Unknown，副本数不动。正确做法：先用 CPU 指标跑通，再逐步加自定义指标。

**陷阱四：本地和线上 YAML 两套。** 反面案例：本地 docker-compose 一套配置，线上 K8s 另一套，环境差异反复咬人。正确做法：本地也用 k3d 跑同一套 K8s 清单，compose 只留给单机工具类服务。

**陷阱五：Ingress 配了但不生效。** 反面案例：`kubectl apply` 了 Ingress，访问域名还是 404，最后发现集群里根本没装 Ingress Controller。正确做法：先确认控制器存在（`kubectl get pods -n ingress-nginx`），再检查 Ingress 的 `className` 和注解是否匹配；本地 k3d 记得用 `--port 8080:80@loadbalancer` 把端口映射出来。

**陷阱六：Secret 明文提交进 Git。** 反面案例：YAML 里直接写数据库密码，推到公共仓库，几分钟内被扫描机器人拿走。正确做法：Secret 用云厂商密钥管理或 Sealed Secrets 加密，仓库里只有密文；配合 External Secrets Operator 从 Vault/云 KMS 同步到集群。

### 进阶思考

系列三篇走完了从 `docker run` 到生产集群的完整路径，剩下的是深度和广度两个方向。

深度上，值得研究的有三个：一是网络模型——CNI（Calico、Cilium）如何实现 Pod 到 Pod 通信，Cilium 的 eBPF 数据面为什么成为新标准；二是调度器——节点亲和性、污点与容忍，怎么让"有状态服务不能乱跑"；三是 GitOps——用 ArgoCD 或 Flux 把 K8s 清单也放进 Git，集群状态由 Git 驱动，回滚和审计天然成立。

广度上，云厂商的托管服务（EKS、ACK、TKE）把控制面复杂度外包，但应用层概念完全一样。理解裸集群再上托管集群，能少踩很多"云厂商抽象层"的坑。

最后给一个心态上的提醒：K8s 的学习曲线陡，但大部分陡峭来自"概念太多"，而不是"单个概念难"。把对象分成三类记忆——工作负载（Pod、Deployment、StatefulSet）、访问（Service、Ingress）、配置与状态（ConfigMap、Secret、PVC）——每个类别记住"它回答什么问题"，再遇到新对象时先归类，学习速度会快很多。三篇系列到这里，你已经有了完整的骨架，剩下的深度交给实践。

如果你只带走一个概念，带走"声明式"：告诉系统你要什么，而不是怎么做到。这个思想从 Docker Compose 到 K8s 到 Terraform 一路贯穿，是整个云原生世界的通用语言。理解了它，以后看到任何新工具（ArgoCD、Crossplane、Pulumi），你都会发现它们在做同一件事——把运维从手工操作变成可版本化的声明。

最后给三篇做一个收束：Docker 篇解决"运行环境一致"，K8s 中篇解决"服务如何声明和自愈"，下篇解决"入口、状态和规模"。三篇合起来，是你从"在服务器上手动跑容器"到"用声明管理一套集群"的完整跃迁。学习路径的终点不是读完这三篇，而是用 k3d 搭一个真实项目，让它经受一次故障演练（kill 节点、断存储、压流量）——经历过故障的集群，才是你真正理解的集群。

最后补一句关于"云原生"的话：云原生不是"把服务跑在 K8s 上"，而是"以声明、弹性、可观测为默认设计"。K8s 只是这套思想的载体之一——Serverless、边缘计算、GitOps 都在往同一个方向走。理解了声明式、弹性、可观测这三条原则，你就拥有了理解云原生所有新工具的坐标系，而不会被某个具体产品的营销牵着走。

学习路径：用 k3d 起一个带 Ingress、PVC、HPA 的完整演示集群，部署一个数据库加两个无状态服务，再写一个 GitOps 仓库把清单管起来。Kubernetes 不是终点，它是"声明式基础设施"这套思想最成熟的载体。
