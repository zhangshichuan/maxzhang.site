### 背景

你打开一个 Next.js 项目，发现目录结构和印象里的完全不一样：没有 `pages/api`，多了一堆 `layout.tsx`、`loading.tsx`、`error.tsx`，组件默认是服务端组件，`useState` 一写就报错，还要加 `"use client"`。网上教程各说各话，有人说 RSC 是未来，有人说它把简单问题复杂化了。

混乱的根源只有一个：Next.js 13 之后的 App Router 换了一套心智模型。旧模型是"整个页面在服务端渲染，需要交互的地方挂 JavaScript"；新模型是"组件级别决定渲染位置——能静态就静态，能服务端就服务端，只有需要交互的叶子组件才进客户端"。

这一篇讲 App Router 的核心：四种渲染模型分别是什么、文件约定如何驱动路由和状态、服务端组件和客户端组件的边界在哪里。下篇讲数据获取、缓存与部署。读完上篇，你会理解项目里每个文件的职责，而不是照着模板抄。

在深入之前，先给一个学习心态：App Router 的文档很长，但真正核心的概念只有三个——渲染模型（静态/动态/ISR）、文件约定（layout/page/loading/error）、组件边界（服务端/客户端）。把这三个概念想清楚，剩下的都是细节。很多人的困惑来自"每个 API 都要学"，其实你只需要先掌握"页面是怎么渲染的、文件放哪、组件在哪边跑"这三件事。

另一个提醒：Next.js 版本迭代很快，网上很多教程基于旧版本，API 已经变了。学习时以官方文档为准，看文章先看发布时间和 Next.js 版本号。本文基于 App Router 的稳定特性，不涉及实验性 API——实验性的东西留给尝鲜，生产项目用稳定能力。

还有一个更实际的信号：你面试或者带新人的时候，几乎绕不开"这个页面是静态还是动态？数据在哪一层获取？为什么这个组件报 hydration 错误？"。App Router 把这些问题变成了日常开发的一部分，模板能解决一时，理解才能解决一直。这篇文章的目标，就是让你把"为什么"补齐——每个文件为什么存在、每个边界为什么这么划、每次报错为什么发生。

先给一个规模上的参照：同一个博客应用，Pages Router 版本是"页面级"思维——每个页面决定自己渲染方式；App Router 版本是"组件级"思维——页面里的每个模块都可以有自己的渲染和缓存策略。前者适合小站点，后者为大型应用的分层优化铺路。选型不是赶时髦，而是看你的应用是否真的需要"组件级"的粒度。

### 核心原理

#### 第一层：四种渲染模型——先分清"什么时候渲染"

Next.js 的页面最终只可能是四种渲染方式之一：静态生成（SSG）、服务端渲染（SSR）、增量静态再生成（ISR）、客户端渲染（CSR）。

静态生成在构建时把 HTML 生成好，CDN 直接缓存，性能最好，适合内容基本不变的文章、文档、营销页。服务端渲染在每次请求时生成 HTML，适合需要个性化数据但没有实时性要求的场景。ISR 是静态生成加定时失效：构建时生成，`revalidate` 到期后后台重新生成，适合数据变化不频繁的页面。客户端渲染是浏览器里用 `fetch` 拿数据，适合需要实时交互、完全依赖用户操作的场景。

App Router 下，默认行为是"能静态就静态"：没有动态 API（`cookies()`、`headers()`、`searchParams` 等）的页面，构建时直接静态化。理解这一点，很多"为什么我的页面是构建时的旧数据"的困惑就解开了。

静态生成还有一个隐含的工程红利：构建时就能发现渲染错误。静态页面在 `next build` 时执行，数据库连接失败、组件抛错都会在构建期暴露，而不是等到用户访问。动态渲染的错误则要等运行时——这也是为什么"尽量静态"不只是性能策略，还是可靠性策略。把能静态的页面都静态化，你的构建日志就是第一道测试网。

#### 第五层：路由组与动态路由——目录即架构

App Router 的目录结构不只是文件组织，它就是路由架构本身。除了 layout/page/loading/error 这些约定文件，还有三个高频结构值得单独讲。

路由组（Route Groups）用括号目录表达"共享布局但不产生 URL 段"：`app/(marketing)/page.tsx` 和 `app/(shop)/page.tsx` 可以分别有独立 layout，但 URL 都是根路径。它适合"同一个域名下多套视觉体系"的场景——官网、后台、移动端布局各一套。

动态路由（Dynamic Routes）用方括号表示参数：`app/blog/[slug]/page.tsx` 对应 `/blog/hello`，参数通过 `params` 拿到。可选参数用双括号 `[[slug]]`，catch-all 用 `[...slug]`。动态路由的静态化靠 `generateStaticParams` 列出所有路径，构建时生成全部页面；没有列出的路径，在动态渲染模式下按需生成。

并行路由（Parallel Routes）用 `@slot` 组织同一页面里的多个独立区域：`app/dashboard/@analytics/page.tsx` 和 `@users` 可以在同一个 layout 里并行渲染，各自独立 loading/error。它的价值是"页面分区解耦"——一个区域报错不影响另一个区域。拦截路由（Intercepting Routes）用 `(.)`、`(..)` 前缀实现"点击进入详情但保留列表页状态"的模态体验。这两个是高级特性，新手阶段先了解存在即可。

判断一个页面是静态还是动态，有两条硬规则：有没有调用动态 API，有没有使用 `no-store` 或动态函数。只要有，整条渲染路径变成动态；没有，构建时就静态化。实践中"内容型页面 + 少量个性化"的组合最常出错：把个性化数据获取放在服务端组件里，整个页面被拖成动态。解法是把个性化部分拆到独立的客户端组件，静态骨架保持缓存。

#### 第二层：文件约定——路由由文件系统驱动

App Router 用目录和文件名表达路由与页面状态，核心约定有六种：

| 文件            | 职责                                                |
| --------------- | --------------------------------------------------- |
| `layout.tsx`    | 嵌套布局，切换子路由时保留，可包裹 `header`、侧边栏 |
| `page.tsx`      | 路由对应的页面内容                                  |
| `loading.tsx`   | 路由切换时的 Suspense 占位                          |
| `error.tsx`     | 路由段的错误边界                                    |
| `not-found.tsx` | 404 页面                                            |
| `route.ts`      | 同路径的 API 端点（替代旧的 `pages/api`）           |

````
```tsx
// app/blog/[slug]/page.tsx
export default async function BlogPostPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params
  const post = await getPost(slug)
  return <article>{post.content}</article>
}

`page.tsx` 可以直接是异步函数，因为默认就是服务端组件，可以在服务端直接读数据库、调内部函数。`params` 在较新版本里是 Promise，需要 `await`——这是迁移时最常见的报错来源。

layout 的嵌套是 App Router 最大的结构红利：根 layout 放全局样式和字体，路由组 layout 放导航，详情页 layout 放面包屑。切换子路由时，父 layout 不重新渲染，浏览器只更新变化的部分。路由组（`(marketing)`、`(shop)`）用括号目录组织共享 layout，不产生 URL 段；`route.ts` 与 `page.tsx` 可以共存，一个路径同时提供页面和 API。

#### 第三层：服务端组件与客户端组件——边界在哪

RSC 的核心规则只有两条：默认是服务端组件，只有加 `"use client"` 的模块才是客户端组件。

服务端组件能做的事：直接访问数据库、读取文件系统、调用内部服务函数，这些代码不会打包进浏览器，密钥和逻辑都不泄露。客户端组件能做的事：`useState`、`useEffect`、事件处理、浏览器 API。判断标准很简单——这个组件需要交互状态吗？需要，就是客户端组件；只是展示数据，就留在服务端。

组件边界可以嵌得很细：一个 `page` 是服务端组件，读取数据后把结果传给内部的客户端交互组件（如筛选器、表单），服务端负责数据、客户端负责交互，各管一段。

````

```tsx
// app/products/page.tsx（服务端）
export default async function ProductsPage() {
  const products = await getProducts()
  return <ProductFilter initialProducts={products} />
}

// ProductFilter（客户端）
;('use client')
export function ProductFilter({ initialProducts }) {
  const [keyword, setKeyword] = useState('')
  // 只在客户端做筛选
}

还有一个常见误区："use client" 是模块级指令，文件里所有组件都会变成客户端组件。所以最佳实践是每个客户端组件单独一个文件，服务端组件 import 它时保持自己的服务端身份。传 props 时也要注意：函数和 Date 对象不能从服务端组件传给客户端组件（RSC 序列化限制），需要传可序列化的数据，再在客户端做转换。这些边界踩过一遍就记住了，但提前知道能省一天调试。

组件边界的判断还有一个实用清单：需要 `useState`/`useEffect` 吗？需要事件处理吗？需要浏览器 API 吗？需要就标客户端；只是展示数据、处理逻辑（计算、格式化、访问数据库），留在服务端。如果你发现一个"客户端组件"其实只用到了 `useState` 之外的普通函数，把它拆回服务端——客户端组件数量越少，包体积越小、首屏越快。

#### 第六层：中间件与路由守卫——请求级逻辑放哪里

Next.js 的中间件（middleware.ts）在请求到达页面之前执行，适合做：重定向（登录检查、A/B 测试）、地区/语言识别、请求头修改、基础限流。它运行在边缘运行时（Edge Runtime），不能用 Node.js 全部 API，也不能读数据库（需要外部服务）。

```

```ts
// middleware.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function middleware(request: NextRequest) {
  const token = request.cookies.get('token')
  if (!token && request.nextUrl.pathname.startsWith('/dashboard')) {
    return NextResponse.redirect(new URL('/login', request.url))
  }
  return NextResponse.next()
}

export const config = {
  matcher: ['/dashboard/:path*'],
}

中间件的使用边界很重要：它适合"粗粒度"的请求级判断（有没有登录、要不要重定向），不适合"细粒度"的业务校验（这个用户能不能看这条数据）——后者必须放在页面或 Server Action 里做，因为中间件拿不到完整的用户上下文，且绕过中间件的直连（直接请求 API 路由）不会经过它。安全边界永远在数据访问层，不在中间件。

路由守卫还有一个 Next.js 特有的细节：客户端导航（`<Link>`）不经过完整的服务器请求，所以中间件的重定向在客户端导航时可能"滞后"。需要客户端侧拦截时，用布局组件里的逻辑配合中间件，双保险。

#### 第七层：RSC Payload 与包体积——服务端组件的隐藏收益

服务端组件最大的隐藏收益是包体积：它的渲染结果以序列化数据（RSC Payload）传给浏览器，而不是把组件代码打进 JS bundle。一个包含大量逻辑的服务端组件，浏览器可能只需要下载几百字节的渲染结果，而不是几十 KB 的 JavaScript。

这意味着"逻辑放服务端"不只是安全和性能问题，还是包体积问题。检查方法：打开浏览器 Network，看页面加载的 JS 文件大小；如果某个页面 JS 明显偏大，检查是不是有组件不该标 `"use client"` 却被标了。把"use client 边界"作为性能 review 的常规检查项，比任何打包优化都有效。

流式渲染（Streaming）和 RSC 是配套的：`loading.tsx` 和 `Suspense` 让慢数据块不阻塞整页。工程上的最佳实践是"首屏必须数据不放 Suspense，可延迟数据放 Suspense"——首屏先到，次要内容边到边渲染。用户感知的加载时间，比"整页等待"快一倍不止。

还有一个容易忽略的点：客户端组件里 import 的库会进入浏览器包，服务端组件里 import 的库不会。判断一个库该在哪边引入，先问"它运行在服务端还是客户端"：数据库驱动、加解密、模板渲染在服务端；动画库、图表库、日期选择器在客户端。把"误入客户端包"的库移回服务端，是 Next.js 项目最省力的瘦身手段。


#### 第四层：metadata 与流式渲染——开箱的工程能力

页面 SEO 信息用 `export const metadata` 声明，Next.js 自动生成 `<title>`、`<meta>`、`og:` 标签，不需要手动改 `head`。动态页面的 metadata 用 `generateMetadata` 异步生成。

流式渲染是 App Router 的另一项默认能力：`loading.tsx` 提供 Suspense 边界，慢的组件可以先显示骨架屏，快的组件先到达浏览器，用户感知到的首屏时间大幅缩短。配合 `Suspense` 包裹独立数据块，可以做到"页面框架秒开，数据块逐步填充"。

metadata 的动态版本 `generateMetadata` 支持读取 params 和 searchParams，是博客、商品详情页的标配；生成失败时可以调用 `notFound()` 触发 404。Suspense 的粒度决定了流式渲染的体验：整页一个 Suspense 等于没有流式，每个数据块独立 Suspense 才能边到边渲染。工程上把"首屏必须的数据"放在页面主体，把"可延迟的数据"（评论、推荐）放进 Suspense，用户感知的加载时间能差出一倍。

### 实战应用

#### 模式速查：项目结构决策表

| 场景                     | 推荐做法                 | 说明                    |
| ------------------------ | ------------------------ | ----------------------- |
| 内容型页面（博客、文档） | 静态生成                 | 构建时生成，CDN 缓存    |
| 个性化但不实时           | SSR 动态渲染             | 请求时读取用户信息      |
| 数据每小时变化           | ISR + `revalidate: 3600` | 后台定时重生成          |
| 表单和交互               | 客户端组件               | `"use client"` 叶子组件 |
| 全局导航                 | `layout.tsx`             | 子路由切换不重渲染      |
| API 端点                 | `route.ts`               | 与页面同路径组织        |

这些文件约定不是装饰：Next.js 在构建期扫描目录，把每个约定文件挂到对应的生命周期。删掉 `loading.tsx`，路由切换立刻回到整页等待；漏建 `not-found.tsx`，404 就用默认样式。约定的价值是"零配置的工程能力"，代价是文件必须放对位置——这是项目结构 review 的第一条规则。

#### 检查清单：新页面开发流程

写一个新页面时，按这个流程走，能避免大部分 App Router 的坑：

| 步骤 | 动作               | 检查                   |
| ---- | ------------------ | ---------------------- |
| 1    | 确定路由和布局归属 | layout/page 放对目录   |
| 2    | 判断渲染模型       | 静态/动态/ISR 明确     |
| 3    | 拆分组件边界       | 客户端组件独立文件     |
| 4    | 数据获取位置       | 服务端获取，props 下发 |
| 5    | 加 loading/error   | 慢区域包 Suspense      |
| 6    | 配 metadata        | 标题/描述/OG 完整      |
| 7    | 检查动态 API       | 静态页面没被污染       |

七步走完，页面的渲染、体验、SEO 都齐了。这份清单写进团队 PR 模板，比口头提醒可靠得多。

还有个实用技巧：并行路由（`@slot`）和拦截路由（`(.)`）能实现"同页面弹窗"和"返回保留上下文"这类高级交互，但它们的优先级低于上面六个约定，且对目录命名敏感。新手阶段先跳过，等基础约定全部熟练后再碰，否则容易把目录结构搞乱。

#### 陷阱与正确做法

**陷阱一：把整个页面标成客户端组件。** 反面案例：从模板复制 `"use client"` 到 `page.tsx`，数据获取、密钥、大依赖全部打进浏览器包，首屏被拖垮。正确做法：默认保持服务端，只有交互叶子组件加 `"use client"`。

**陷阱二：在客户端组件里用 `useEffect` 拿数据。** 反面案例：`useEffect(() => fetch('/api/...'))` 导致先渲染空壳、再请求、再渲染，还要自己处理 loading 和错误。正确做法：数据获取放服务端组件，或使用服务端函数（Server Functions）作为入口。

**陷阱三：`params` 忘记 await。** 反面案例：把 `params` 当同步对象用，部署后才报错，因为本地开发和生产模式对 Promise 的处理不同。正确做法：`const { slug } = await params`，并给 props 标注正确类型。

**陷阱四：metadata 写在客户端组件里。** 反面案例：`export const metadata` 出现在带 `"use client"` 的文件里，构建直接报错。正确做法：metadata 只从服务端组件导出，页面级 metadata 放在 `page.tsx`。

**陷阱五：忽略 hydration 一致性。** 反面案例：组件在渲染顶层直接读 `window` 或调用 `Date.now()`，服务端渲染和客户端渲染输出不一致，报"Text content does not match server-rendered HTML"。正确做法：浏览器 API 放进 `useEffect` 或事件回调；渲染结果依赖客户端环境的，先用 `mounted` 状态占位，再渲染真实内容。

**陷阱六：目录结构混乱。** 反面案例：所有页面平铺在 `app/` 下，layout 重复写，路由组没用，改一次导航改十个文件。正确做法：按"路由组 + 领域"组织目录，共享布局抽 layout，页面按领域分组；目录结构 review 时看"每个 layout 是否真的被复用"。

**陷阱七：忽略 `not-found` 和错误边界。** 反面案例：动态路由访问不存在的 slug，直接渲染空页面或 500，用户一脸懵。正确做法：数据不存在时调 `notFound()` 触发 404 页面；页面级错误用 `error.tsx` 兜底，避免整站白屏。

### 进阶思考

渲染模型理解之后，Next.js 最值得深挖的是缓存体系：Full Route Cache、Data Cache、Router Cache 三层缓存各管什么，失效条件是什么，`fetch` 的 `revalidate` 和 `no-store` 分别影响哪一层。这是下篇的主题，也是"为什么我的页面数据是旧的"的完整答案。

第二个方向是 Server Actions：表单提交不再需要单独写 API 路由，直接调用服务端函数，配合 `useActionState` 和 `revalidatePath` 做乐观更新。它让"表单"这个最常见场景的代码量减少一半，但也引入了新的安全考量——权限校验必须在服务端做。

第三个方向是流式渲染和 RSC Payload 的性能含义：服务端组件不传 JavaScript 只传序列化后的组件树，这是 Next.js 包体积控制的关键。检查方式是在浏览器 Network 里看 RSC 请求的响应体，如果发现大段组件代码被打进客户端包，说明 "use client" 的边界划得太靠上——这条检查应该写进性能 review 清单。

最后是缓存体系的预告：Full Route Cache 缓存页面 HTML，Data Cache 缓存 fetch 和 unstable_cache 的结果，Router Cache 缓存客户端导航过的路由，三者失效条件不同，很容易混。一张实用的速查表是：页面内容变了用 `revalidatePath`，数据变了用 `revalidateTag`，客户端缓存用 `router.refresh()`。下篇我们会把这张表展开成完整的决策树。学习路径：读官方 App Router 文档的 Rendering 和 Routing 两章，把项目里每一个 `"use client"` 都问一遍"真的需要吗"。

心态建议：App Router 的学习曲线不是陡，而是"反直觉"——它把很多以前需要框架决策的事（渲染、缓存、数据获取）变成了默认约定。当你觉得"为什么它不按我想的来"时，先假设默认行为是对的，再去查文档确认。绝大多数困惑，最后都落在"默认静态"和"服务端优先"这两条设计选择上。

上篇到这里结束，最值得记住的默认方向是"服务端优先"：默认在服务端渲染、默认在服务端拿数据、默认静态化，只有需要交互时才下沉到客户端。这个默认方向，是 App Router 所有设计的总纲——顺着它写，代码自然又快又安全；逆着它写，你会和框架一路打架。

实践建议：学完上篇后，把你项目里现有的一个页面用 App Router 重写一遍——先画目录结构，再定渲染模型，再拆组件边界。重写一个页面，比读十篇教程都管用。中篇我们会进入数据获取与缓存，把"页面怎么渲染"延伸到"数据怎么流动"。

最后给一个判断"是否理解上篇"的自测：能一句话说出你项目里每个页面的渲染模型吗？能说出每个 `"use client"` 文件为什么需要客户端吗？能说出 layout 和页面组件的数据流吗？三个问题都能答上，上篇合格；答不上，回去重读对应章节。自测比"感觉学会了"可靠得多。

学习资源层面的建议：Next.js 官方文档的 Learn 教程（App Router 章节）是唯一推荐从头读完的资料，它用一个真实项目把目录、渲染、数据获取、Server Actions 全部串一遍。读完后回到你自己的项目，你会突然看懂很多"模板里抄来但不知道为什么"的代码。教程是地图，项目是实地，两者结合才是完整的学习闭环。

关于"要不要升级 Next.js"的话：新版本带来的不只是新 API，还有默认行为的变化（比如渲染模型的调整、缓存语义的演进）。升级前先读 release notes 里的 breaking changes，用 staging 环境跑一遍全量回归；不要把"升级"当成"换 API"，要当成"换行为模型"。理解了上中下三篇的机制，你就有能力评估每次升级的影响面——这是长期使用 Next.js 最重要的能力之一。

回顾上篇全文，主线是"三层决策"：第一层，页面用哪种渲染模型（静态/动态/ISR）；第二层，目录和约定文件怎么组织（layout/page/loading/error/route group）；第三层，组件放服务端还是客户端（use client 边界）。每一层决策都有明确的判断标准，而不是"看心情"。三层想清楚，App Router 的 80% 问题都不会发生——剩下的 20%，是中篇要讲的数据获取与缓存。

最后，给你一个"最小行动"：今天就把你项目首页的渲染模型确认一遍——打开 `next build` 的输出，看它标的是 `○ Static` 还是 `ƒ Dynamic`，然后问自己"这是我预期的吗"。如果答案是否，说明你对页面行为的理解还有盲区，正好用上篇的知识去排查。一个页面一个页面地确认下来，你对项目的心智模型就和框架一致了。


路由缓存（Router Cache）的行为：客户端导航过的页面会被缓存，返回时「秒开」但可能不新鲜——`router.refresh()` 可以强制刷新当前路由的数据，适合「从详情页返回列表页要看到最新数据」的场景。理解 Router Cache 的「缓存 + 手动刷新」机制，你就不会在「为什么返回后数据是旧的」上困惑——这和中篇的缓存体系是同一套心智模型。
```
