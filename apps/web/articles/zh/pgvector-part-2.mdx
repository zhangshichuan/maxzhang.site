### 背景

大模型应用（RAG、语义搜索、推荐）都需要一种能力：给定一个向量，找到"最相似"的一批向量。专用向量数据库（Milvus、Weaviate、Qdrant）很强大，但对多数团队来说，引入一个新组件意味着新的运维、新的学习曲线、新的数据同步管道——为了一个功能，搭一套基础设施，值不值？

pgvector 提供了一条"低增量"路线：它是 PostgreSQL 的扩展，在熟悉的表里加一列向量类型，建一个索引，写一条 SQL 查询。业务数据、元数据、向量可以放在同一张表里，事务、备份、权限全部复用 PostgreSQL 的能力。对"已经用 PostgreSQL"的团队，这是向量检索性价比最高的起点。

这篇文章讲 pgvector 的实战：向量类型怎么用、IVFFlat 和 HNSW 两种索引的原理与参数、相似度度量怎么选、过滤条件怎么写才不会拖垮性能，以及从 RAG 场景出发的落地建议。下篇开始我们会进入 Kafka/RabbitMQ 等消息队列主题，但向量检索这套"近邻搜索"的思维会继续有用。

先给一个场景定位：pgvector 最适合"已有 PostgreSQL、向量数据量在千万级以内、查询 QPS 中等"的团队。它不是性能最强的向量库，但它是"从 0 到 1"成本最低的——不需要新运维、不需要新语言、不需要数据同步。当你的业务验证了"向量检索真的有用"之后，再评估是否值得迁移到专用向量库，这个顺序比一开始就上重型组件务实得多。

另一个常见疑问是"向量数据库是不是必须的"。答案取决于你的瓶颈：如果 PostgreSQL 加 pgvector 后查询延迟、召回率、扩展性都能满足，它就不是必须的；如果向量数据达到亿级、需要实时写入和高并发搜索，专用库的优势才会体现。选型的关键是先量化需求，再选工具——而不是先选工具，再让需求去迁就。

本篇结构：向量类型与存储 → IVFFlat/HNSW 索引原理 → 相似度度量 → 过滤查询 → RAG 落地步骤与陷阱 → 进阶方向。建议在测试库灌入真实数据后对比"有索引 vs 无索引"的查询计划。

### 核心原理

#### 第一层：向量是什么，pgvector 怎么存

向量是浮点数数组，由 embedding 模型生成——文本、图片、用户行为都可以编码成向量，语义越相近，向量距离越近。pgvector 提供 `vector` 类型，声明维度后存储：

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE documents (
  id bigserial PRIMARY KEY,
  content text,
  embedding vector(1536)
);
```

维度由模型决定：OpenAI 的 text-embedding-3-small 是 1536 维，BGE 系列常见 768 或 1024 维。同一张表里的向量维度必须一致，否则插入报错。维度越高，存储和计算成本越大，但语义表达能力通常越强——选模型时要在"效果"和"成本"之间做权衡。

pgvector 的存储是"标准 PostgreSQL 数据"：支持事务、备份、复制。这意味着向量数据和业务数据可以一起管理，不需要额外的同步管道。这也是它最大的卖点——不是性能最强，而是集成成本最低。

#### 第二层：两种索引——IVFFlat 与 HNSW

没有索引的向量查询是全表扫描：计算每一行和查询向量的距离，再排序取 Top N。数据量到百万级后，这个操作慢到不可接受。pgvector 提供两种索引加速近邻搜索。

向量索引和传统 B-tree 的思维方式完全不同：B-tree 用"有序"加速精确查找，向量索引用"近似图/倒排"加速最近邻查找。这也是为什么向量查询的结果叫"近似"——索引为了速度牺牲了精确性，换来的是百万级数据下毫秒级的响应。理解这个 trade-off，你才能接受"召回率"这个指标，并学会用参数去平衡速度和精度。

IVFFlat 的"桶"还有一个聚类质量的问题：索引构建时用 K-means 聚类，聚类质量取决于数据分布和 `lists` 参数。如果数据是"增量灌入"的（先建索引再不断插入），聚类会逐渐失真，召回率下降——解决方法是定期重建索引（`REINDEX`）。HNSW 对增量插入更友好（图结构动态维护），所以"数据持续增长"的场景默认选 HNSW 更省心。

IVFFlat（倒排文件）：把向量空间划分成若干"桶"（lists 参数），查询时只搜索最近的几个桶。它的特点是：构建快、内存占用低，但"召回率"依赖 lists 参数和数据的分布；必须在数据有一定量之后构建（lists 建议 = 行数 / 1000），否则聚类质量差。

HNSW（分层小世界图）：构建一张多层的近邻图，查询从顶层逐层下降。它的特点是：查询精度和速度通常优于 IVFFlat，但构建更慢、内存占用更高。参数 `m`（每层最大连接数）和 `ef_construction`（构建时探索的候选数）越大，质量越好、成本越高；查询时 `hnsw.ef_search` 控制每次查询的探索范围。

选型建议：数据量几十万以下、追求构建速度，用 IVFFlat；数据量大、查询精度敏感，用 HNSW。两种索引都是"近似"搜索（ANN），结果不是精确的 Top N——这是所有向量索引的共性，业务上要接受"近似"。

#### 第三层：相似度度量——L2、内积、余弦

pgvector 支持三种距离：L2 欧氏距离（`vector_l2_ops`）、内积（`vector_ip_ops`）、余弦距离（`vector_cosine_ops`）。距离越小越相似。

```sql
SELECT id, content, embedding <=> $1 AS distance
FROM documents
ORDER BY embedding <=> $1
LIMIT 10;
```

`<=>` 是余弦距离，`<->` 是 L2，`<#>` 是负内积。选哪种取决于 embedding 模型：很多模型（OpenAI）建议用余弦，有些模型（Cohere）用内积更合适——先查模型的官方建议，不要凭感觉。

一个重要细节：HNSW 索引必须和距离类型匹配（`vector_cosine_ops` 对应余弦）。索引的 `ops` 选错，查询会退化成全表扫描。余弦距离下，向量是否归一化不影响排序结果，但影响索引效率；官方建议对余弦用归一化向量配合内积索引，可以提升性能。

相似度度量的选择还影响"业务阈值"：用余弦时，`distance < 0.2` 表示非常相似，`0.5` 以上基本不相关；用 L2 时，阈值含义完全不同。上线前要基于真实数据标定阈值（用评测集画"距离 vs 相关性"曲线），而不是拍脑袋写一个数字。阈值写错，检索结果的"感觉"会差很远。

#### 第四层：过滤查询——元数据过滤的正确姿势

真实场景很少只按向量搜：还要过滤"用户自己的文档""最近 30 天""某个分类"。pgvector 支持在 SQL 里直接加 WHERE：

```sql
SELECT id, content
FROM documents
WHERE user_id = 42 AND embedding <=> $1 < 0.8
ORDER BY embedding <=> $1
LIMIT 10;
```

性能的关键是"过滤和索引的关系"：pgvector 的 ANN 索引不支持"先按条件过滤再近邻搜索"，它是先找全局近邻再应用过滤。如果过滤条件很严格（比如 1000 万行里只有 100 行属于 user_id=42），索引找到的 Top N 可能全部被过滤掉，查询结果为空或不准确。

解法有三种：把高频过滤字段作为"部分索引"的键（PostgreSQL 14+ 支持 `CREATE INDEX ... WHERE`）；用"聚类 + 分区"让每个分区的数据在语义上更集中；或者在应用层分桶（按用户/租户分别建索引）。理解"ANN 索引 + 过滤"的组合限制，是 pgvector 生产化的核心功课。

过滤和近邻搜索的关系还有一个进阶理解：过滤条件的"选择性"决定了策略。选择性高（1000 万里只有 100 行匹配）时，索引预过滤（pre-filter）会失效，需要"按桶检索"或把过滤条件变成向量的一部分；选择性低（1000 万里有 900 万行匹配）时，普通过滤基本不影响结果。设计时先统计每个过滤字段的选择性，再决定是"索引内过滤"还是"应用层过滤"，这是从 demo 走向生产的关键一步。

再补充一个和多租户相关的模式：每个租户的数据量不大时，可以为每个租户建独立的分区或独立索引，查询时 `WHERE tenant_id = ?` 直接命中对应分区；租户数量多但每个租户数据少时，反过来用全局索引 + 租户过滤。两种模式没有绝对优劣，取决于"租户数量 vs 每租户数据量"的比例——这是 RAG 类 SaaS 应用最常见的架构决策。

### 实战应用

#### 模式速查：RAG 落地步骤

| 步骤        | 动作                         | 注意                   |
| ----------- | ---------------------------- | ---------------------- |
| 1. 选模型   | 确定 embedding 模型和维度    | 维度影响存储和速度     |
| 2. 建表     | `vector(维度)` 列 + 元数据列 | 维度必须一致           |
| 3. 灌数据   | 文档切片后生成向量入库       | 切片大小影响检索粒度   |
| 4. 建索引   | HNSW + 匹配的距离 ops        | 先灌数据再建索引       |
| 5. 查询     | 向量相似度 + 元数据过滤      | 验证过滤下的召回率     |
| 6. 混合检索 | 向量 + BM25 融合             | 提高关键词场景的准确率 |

#### 陷阱与正确做法

**陷阱一：不建索引就上线。** 反面案例：测试环境几千行数据全表扫也快，上线后百万行，查询秒级超时。正确做法：数据量达到万级就建 ANN 索引；用 `EXPLAIN` 确认走的是 `Index Scan using ..._hnsw` 而不是 `Seq Scan`。

**陷阱二：HNSW 参数照抄。** 反面案例：把 `m=16, ef_construction=64` 用到百万级数据，召回率不达标，业务反馈"搜不到"。正确做法：用小样本离线评测 `ef_search` 和召回率的关系；生产查询的 `hnsw.ef_search` 独立调，兼顾延迟和效果。

**陷阱三：维度不一致。** 反面案例：切换 embedding 模型后旧的 1536 维数据和新的 768 维数据混在同一列，插入报错或查询异常。正确做法：模型版本写进表结构或元数据；切换模型时重建向量列，并保留旧索引到迁移完成。

**陷阱四：过滤条件拖垮召回。** 反面案例：按租户过滤的查询结果经常为空，用户以为"没数据"。正确做法：用部分索引或分桶策略；过滤字段的选择性高时，考虑把过滤条件也编码进向量（拼接语义字段）或走专用向量库。

**陷阱五：忽略向量归一化。** 反面案例：余弦距离模型没有归一化，索引选择错误，查询精度和速度都不理想。正确做法：按模型文档处理归一化；使用 `vector_cosine_ops` 时确认查询语句的算子与索引一致。

**陷阱六：切片策略拍脑袋。** 反面案例：所有文档固定 500 字切片、无重叠，跨段落的问题搜不到答案，召回率惨不忍睹。正确做法：按文档结构（标题、段落）切片，配合 10%-20% 重叠；对切片质量做离线评测（检索命中率），而不是只看"能搜到东西"。

**陷阱七：上线后从不评测。** 反面案例：索引建完、demo 跑通就上线，模型更新、数据分布变化后召回率悄悄下降，业务"感觉搜不准"但拿不出数据。正确做法：建一套带标注的评测集（query → 期望文档），每次索引重建或模型升级后跑一遍 recall@k；把评测结果写进发布记录，让"搜索质量"可度量、可回归。

### 进阶思考

pgvector 适合"PostgreSQL 已经存在、向量量级可控"的团队；当数据量到千万级、查询 QPS 很高、需要复杂的过滤和混合检索时，专用向量数据库的优势才会显现。选型不是"谁技术更强"，而是"新增组件的运维成本能不能抵消性能收益"。

值得深入的方向有三个。一是混合检索（Hybrid Search）：向量检索擅长语义，BM25 擅长精确关键词，把两者结果融合（RRF 或加权）能显著提升 RAG 的准确率——PostgreSQL 的全文检索（tsvector）可以和 pgvector 在同一张表上做，这是"一个数据库搞定混合检索"的实用方案。二是 RAG 的质量工程：chunk 大小、重叠、检索后的 rerank（用 cross-encoder 精排）、上下文压缩，这些环节对回答质量的影响往往比向量库选型更大。三是向量索引的运维：HNSW 构建是 CPU/内存密集操作，导入大语料时要规划窗口和资源；索引重建要验证召回率不回退。

学习路径：先用 `pgvector` 官方 demo 跑通"建表 → 灌向量 → 查询"全流程；再在你的 PostgreSQL 里给真实业务数据建 HNSW 索引，比较索引前后的延迟；最后实现一个"向量 + BM25"的混合检索并评测召回率。向量检索是数据层的新基建，但它的工程化套路——索引、评测、过滤、混合——和传统数据库调优一脉相承。

最后总结 pgvector 的定位：它把向量检索从"新组件"降级成了"一个扩展"，让团队用熟悉的 SQL 和数据管理方式进入语义搜索。它的边界也清晰——大规模、高并发、复杂过滤时，专用向量库是下一步。技术选型最怕的不是"选错"，而是"不知道边界在哪"：知道 pgvector 什么时候够用、什么时候该换，比盲目追新更值钱。

结语：向量检索正在成为数据层的"标配能力"，就像索引和事务一样。pgvector 让 PostgreSQL 团队以最低成本获得这个能力，而理解它的索引、度量和过滤机制，是正确使用的前提。上篇的 PostgreSQL 基础和这篇的向量知识合起来，你的数据层就同时拥有了"关系查询"和"语义检索"两种能力——这是 2025 年后数据架构师的基本功。

再补一个"混合检索"的落地细节：向量 + BM25 的融合不是简单的"结果相加"，常用 RRF（Reciprocal Rank Fusion）把两个排名的倒数名次相加，或者用权重线性融合。融合前要归一化两边的分数，否则一个尺度会把另一个淹没。混合检索的评测用"两种单路 vs 融合"的召回率对比——融合不是自动更好，要用数据验证。

最后补一段"向量检索的运维"提醒：向量列会让表变大（1536 维 float 每行约 6KB），备份、恢复、迁移的时间和存储都会增加；HNSW 索引构建是 CPU/内存密集操作，导入大语料时要有窗口规划。把"向量数据量"纳入容量规划和成本预估，向量检索才不会在上线后给运维"惊喜"。

再补一段"评测集的建设"：向量检索的质量评测不是"感觉搜得准"，而是"有标注、可量化"——准备 100-200 条"查询 → 期望结果"的标注对，计算 recall@k（前 k 条里命中期望的比例）。评测集要覆盖正常查询、同义表达、长尾查询三类，每次改模型、改索引、改参数都跑一遍。没有评测集的向量检索优化，是"在黑暗中调旋钮"——你以为在变好，其实在过拟合。

还有一个"embedding 模型的选择"提醒：向量检索的效果 80% 取决于 embedding 模型，而不是向量库——模型维度、训练数据、是否支持中文，直接决定召回率。选模型时看"领域适配"（代码搜索用代码模型、中文语义用中文模型），不要默认用最大的模型（成本高、维度高、收益未必）。模型版本要锁定（embedding 模型更新会改变向量空间，旧索引可能失效），升级模型要重建索引并评测。

最后补一段"pgvector 和专用向量库的分工"：同一套系统里可以共存——热数据（近期、高频）用 Redis 或专用向量库，全量数据用 pgvector 兜底；简单查询走 pgvector，复杂过滤和超高 QPS 走专用库。把向量检索也做成"分层缓存"（热索引 + 冷索引），而不是"一个库包打天下"，是数据量增长后的自然演进。

再补一段"中文语义检索的落地细节"：中文向量检索的坑比英文多——中文分词粒度影响 embedding 效果、同义词（笔记本/电脑）影响召回、数字和英文缩写（RAG/AI）需要特殊处理。实践上"向量 + BM25 混合"对中文特别有效：向量兜语义，BM25 兜精确词，RRF 融合后中文场景的召回率通常提升明显。做中文 RAG 的团队，混合检索不是"可选项"而是"默认项"。

最后补一段"从检索到回答的完整链路"：向量检索只是 RAG 的一环，完整的链路是"查询改写（把用户问题变成检索 query）→ 检索（向量 + BM25）→ 重排（rerank 精排）→ 组装上下文 → 生成回答"。检索质量影响上限，但重排和上下文组装同样决定回答质量——很多"检索到了但回答不对"的问题，出在重排和组装，不在向量库。把 RAG 当"系统工程"而不是"向量库选型"，效果才会真正上来。

再补一段"索引参数的调优方法"：HNSW 的 `ef_search` 是查询时的"探索广度"——越大召回越好但越慢，调优方法是"固定数据量，扫描 ef_search（10-500），画"召回率 vs 延迟"曲线，取拐点"。IVFFlat 的 `lists` 同理（按行数/1000 起步，用 `probes` 调查询精度）。参数调优要有"评测集 + 曲线"，不是拍脑袋——这是向量检索和传统数据库调优最不一样的地方：参数空间更大，必须用数据说话。

最后补一句"向量检索的长期演进"：pgvector 在不断进化（HNSW 支持、量化、流式索引），专用向量库也在卷性能——选型的天平会随时间变化。工程上最好的策略是"抽象层先行"：把"检索接口"抽象出来（`search(query, filter, top_k)`），底层用 pgvector 还是专用库是配置。这样无论生态怎么演进，你的应用都能以最小成本切换——工具会变，接口是长期资产。

最后总结 pgvector 的定位：它把向量检索从"新组件"降级成了"一个扩展"，让团队用熟悉的 SQL 和数据管理方式进入语义搜索。它的边界也清晰——大规模、高并发、复杂过滤时，专用向量库是下一步。技术选型最怕的不是"选错"，而是"不知道边界在哪"：知道 pgvector 什么时候够用、什么时候该换，比盲目追新更值钱。
