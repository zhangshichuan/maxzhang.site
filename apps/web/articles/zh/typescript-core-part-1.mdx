### 背景

项目从 JavaScript 迁到 TypeScript，前两周很爽：补全、重构、到处都有类型提示。第三周开始难受——接口返回的数据要一个个定义类型；两个看起来一样的类型不能互相赋值；泛型报错像天书；"Type 'string | undefined' is not assignable to type 'string'" 这种报错每天见；遇到搞不定的地方，一个 `as any` 解决问题，然后这个 any 顺着调用链传染，整个文件又变回 JavaScript。

这不是你不行。TypeScript 的类型系统有自己的底层逻辑，没搞懂它，所有类型写法都像在背咒语：为什么 `interface` 之间能互相赋值而有的 `class` 不能？为什么 `T extends object` 有时收不住？为什么 `typeof` 和 `as const` 要一起用才能得到字面量类型？这些问题的答案指向同一个根源：TypeScript 用的是结构化类型系统，类型本质上是一组约束，而不是一张名字标签。

更扎心的是，这些坑会变成团队负债：code review 里满屏 `as any`，注释写着"暂时先这样"，三个月后没人敢动那段代码；新同事看不懂类型报错，只能照着错误信息试错。你刷过 type-challenges，见过 `infer`，但回到项目里还是只会写 `interface` 和 `: string`。

这篇文章是 TypeScript 系列的上篇，只讲底层逻辑：类型到底是什么、推断怎么工作、联合与交叉怎么组合、泛型怎么设计、类型怎么收窄。中篇讲工具类型与类型体操，下篇讲工程化和真实项目落地。读完上篇，你至少能看懂以前看不懂的类型报错，也能写出不再依赖 any 的接口。

为什么值得花时间理解这些底层逻辑？因为类型不是"给编译器看的形式主义"，它是一张免费的测试网。类型系统能抓到的错误——传错参数、漏处理空值、字段拼错、分支漏掉——如果在编译期被拦住，就不需要写单元测试、不需要等用户反馈、不需要在凌晨三点查日志。一个类型体系健康的项目，重构时改一个字段名，所有引用点一起报错；一个 `as any` 泛滥的项目，改字段名只能靠全局搜索。前者是编译器在帮你，后者是你一个人在扛。

还有一个常被低估的收益：类型是"可执行的文档"。接口返回什么、函数接受什么、状态机有哪些分支，类型定义写得清楚，新同事看类型比看注释更快、比翻文档更准，而且不会过期——注释会忘记更新，类型不会，因为编译器逼它同步。这篇上篇打底，中篇和下篇的所有技巧，都是在这套底层逻辑上长出来的。

再给一个"先有鸡还是先有蛋"的提醒：很多人想等"项目稳定了再补类型"，但类型系统的价值恰恰在项目不稳定的时候最大——需求频繁变化时，改一个字段名，类型系统能帮你找出所有受影响的地方；等代码库膨胀到十万行再补类型，光是把 `any` 清完就要几个月。正确的时机是"第一天就开 strict"，而不是"以后再说"。类型债和业务债一样，拖得越久，利息越高。

### 核心原理

#### 第一层：类型是约束，不是标签

大多数语言用名义类型：类型是类名，只有继承关系才允许赋值。TypeScript 用的是结构化类型：只要形状对得上，类型就兼容，跟它叫什么名字无关。

```ts
interface Point {
  x: number
  y: number
}

interface Coordinate {
  x: number
  y: number
}

const p: Point = { x: 1, y: 2 }
const c: Coordinate = p // 合法，形状相同
```

把类型想成合同而不是名字：`Point` 合同上写着"必须有 x 和 y 两个 number"，`Coordinate` 合同内容一样，所以两份合同可以互换。这也解释了为什么 `interface` 之间能互相赋值，而含私有成员的 `class` 不能——两个 class 只要没有 `private`/`protected`，形状相同依然兼容；一旦出现私有成员，只有同一个类自己内部能赋值。私有成员就像合同上的防伪水印：形状一样不算数，必须有"同一个来源"的身份证明。

TypeScript 选择结构化而不是名义，是为了让 JavaScript 生态无缝迁移：一个函数只要形状对得上，就能接住任何来源的对象，不用为了类型去改第三方库。这个取舍贯穿整个语言，理解它，你就能接受很多"看起来宽松"的赋值规则。

结构化类型带来两条推论。一是宽不能赋给窄：`{ x, y }` 不能赋给要求 `{ x, y, z }` 的变量，缺字段就是违约。二是对象字面量会被额外检查（freshness）：直接写 `{ x: 1, y: 2, extra: true }` 赋给 `Point` 会报错，但先把整个对象赋给一个变量再传，多余属性检查就放行了。知道这两条，大部分"为什么报错"都有了解释。

结构化类型还解释了一个让很多新手困惑的现象：为什么"第三方库的对象"能直接传进你的函数，即使它们没有声明实现你的接口？因为只要形状匹配，TypeScript 就认为它们兼容。这个特性让"鸭子类型"（长得像鸭子就是鸭子）变成了编译期检查，也让 mock 测试变得极其容易——测试里手写一个和接口形状一致的对象，就能替代真实的复杂依赖，不需要继承、不需要代理。

```ts
const extra = { x: 1, y: 2, extra: true }
const ok: Point = extra // 合法，多余属性检查只对字面量生效
```

#### 第二层：推断、联合与交叉——类型就是集合

类型推断的规则很简单：变量初始化时的值决定它的类型；字面量默认被拓宽——`const s = 'a'` 的类型是 `string`，除非写 `as const` 才保留 `'a'`。真正需要花时间理解的是联合（union）和交叉（intersection）：联合是"或"，交叉是"且"。

```ts
type A = { name: string } | { id: number } // 满足其一即可
type B = { name: string } & { id: number } // 两个都要满足
```

联合类型对应集合的并集：你拿到 `A` 时，编译器不知道它到底是哪个分支，所以只允许你访问两个分支共有的属性；要访问分支特有属性，必须先收窄。交叉类型对应交集：`B` 必须同时满足两边，属性会合并；如果两边对同一个属性给出了冲突的类型，交叉会退化成 `string & number` 这种不可满足的类型——遇到这种报错，把名字拆开看就能发现是哪个字段互相打架。

收窄是联合类型能用的关键：`typeof`、`in`、`instanceof`、判别联合都可以让编译器在分支内缩小范围。日常最常见的联合其实是 `T | null | undefined`：先 `if (x == null)` 把空值排除，再用 `typeof`、`in` 继续缩小，比层层嵌套 `if (x !== null)` 清晰得多。其中判别联合是实战价值最高的模式，用一个字面量字段当"标签"，再配一个 `never` 兜底做穷尽检查：

```ts
type Event = { kind: 'click'; x: number; y: number } | { kind: 'input'; value: string }

function assertNever(x: never): never {
  throw new Error('unexpected: ' + JSON.stringify(x))
}

function handle(e: Event) {
  switch (e.kind) {
    case 'click':
      return e.x // 这里只有 click 分支，完全类型安全
    case 'input':
      return e.value
    default:
      return assertNever(e) // 以后新增分支忘了处理，这里直接编译报错
  }
}
```

穷尽检查是判别联合的隐藏福利：新加一个事件类型，编译器会逼你在 `switch` 里补上分支，而不是让漏掉的分支在运行时静默出错。

收窄还有一个经常被忽略的运算符：`in`。`'name' in obj` 不仅能做运行时判断，还能让 TypeScript 在分支里收窄对象类型——这是处理"联合类型里不同分支有不同字段"的利器。再配合 `typeof` 处理基本类型、`instanceof` 处理类实例、`Array.isArray` 处理数组，你手上就有一套完整的收窄武器库。判别的顺序也有讲究：先排空值（`null`/`undefined`），再排宽泛类型，最后排具体分支，收窄逻辑和人的思考顺序一致，代码才读得顺。

#### 第三层：泛型——把约束写成参数

泛型不是"类型变量"四个字能概括的，它是"以类型为参数写约束"。核心用法就三个：占位（`T`）、约束（`T extends ...`）、默认值（`T = ...`）。

```ts
function first<T>(arr: T[]): T | undefined {
  return arr[0]
}

// 约束：保证 T 有 length 属性
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b
}

// 默认值：不传类型参数也有兜底
function create<T = string>(): T {
  return {} as T
}
```

`T extends { length: number }` 不是"T 继承某个类"，而是"T 必须满足这个形状"。所以 `longest('abc', 'def')` 合法（string 有 length），`longest(1, 2)` 直接报错。

泛型的另一面是它会让错误信息变长。报错时优先看"不满足约束"那一行，而不是底下几百行的类型展开；大部分泛型报错都能拆成同一个原因：输入形状不满足 `T extends X` 这条约束。把报错当约束的反馈，而不是天书。

泛型最经典的组合是 `keyof`：既要约束键名，又要保持键和值的对应关系。

```ts
function getValue<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key]
}

const age = getValue({ name: 'max', age: 18 }, 'age') // age: number
const bad = getValue({ name: 'max', age: 18 }, 'nope') // 编译报错
```

这里 `K extends keyof T` 把键限制在对象的真实键上，`T[K]` 让返回值跟着键走。写错键名在编译期就暴露，改键名后所有调用点一起报错，这就是泛型"保持对应关系"的威力。什么时候才需要加泛型？就是这种需要对应关系的时候；如果只是换个地方用同一个类型，直接用具体类型更简单。

泛型和"重载"的关系也值得理清：TypeScript 的函数重载（overload signature）适合"同一函数在不同参数组合下有不同返回类型"，但实现复杂、文档效果差；泛型通常能覆盖 90% 的需求，而且类型推导更自然。看到一个用三个重载签名实现的函数，先想想能不能用泛型加条件类型替代——大多数情况下能，而且调用方体验更好。

#### 第四层：类型空间与值空间——两条平行的世界

`type`、`interface`、`keyof`、`T extends` 生活在类型空间；`const`、`function`、`class` 的值生活在值空间。`class` 比较特殊，同一个名字同时占两个空间：值空间里它是构造函数，类型空间里它是实例类型。但你不能在类型空间用值，也不能在值空间用类型。

```ts
class User {
  constructor(public id: string) {}
}

type U = User // 类型空间：实例类型
const u = new User('1') // 值空间：构造函数
```

两座桥里最常用的是 `typeof`：它把值转成类型。`keyof` 取出对象键的联合，索引访问类型 `T[K]` 取出某个键的类型，这两件工具是所有类型体操的地基。

```ts
const obj = { name: 'max', age: 18 }
type Keys = keyof typeof obj // 'name' | 'age'
type Name = (typeof obj)['name'] // string

function fetchUser() {
  return { id: 1, name: 'max' }
}
type Fetched = ReturnType<typeof fetchUser> // 从函数推导出返回类型
```

理解了这两个空间，再看 `typeof import('./x')`、`as const`、`ReturnType<typeof fn>` 这些写法，就不再是咒语。注意 `typeof` 只能用在标识符或值上，不能直接写 `typeof { name: 'x' }`——先赋给变量，再取它的类型。

#### 第五层：satisfies、as const 与索引签名——三个高频武器

上篇的最后一层，补三个日常开发里几乎每天都会碰到的实用武器。

`as const` 把字面量"冻结"成最精确的类型：`const config = { env: 'prod' } as const` 之后，`config.env` 的类型是 `'prod'` 而不是 `string`。它常用于配置对象、事件名、路由表——让"枚举值"在不用 enum 的情况下也能享受字面量类型的保护。

`satisfies` 是 TypeScript 4.9 引入的检查操作符：它要求值"满足"某个类型，但保留值自身的精确类型。经典场景是配置校验：

```ts
type Config = { env: 'dev' | 'prod'; debug: boolean }

const config = {
  env: 'prod',
  debug: true,
} satisfies Config
// config.env 的类型是 'prod'，而不是被拓宽成 string
```

如果用 `: Config` 标注，`config.env` 会被拓宽成 `'dev' | 'prod'`；用 `satisfies`，既能通过校验，又保留 `'prod'` 字面量——两全其美。

索引签名（index signature）用于"键不固定但值类型统一"的对象：`Record<string, number>` 或 `{ [key: string]: number }`。它的价值在于约束"字典"的值类型，代价是放弃对具体键的检查——所以索引签名对象要配合 `as const` 或白名单，避免"拼错键名还编译通过"。

这三个武器组合起来，是日常类型设计的最小工具箱：`as const` 保留字面量，`satisfies` 校验形状，索引签名约束字典。上篇的底层逻辑加上这层工具箱，你已经有能力独立设计项目里 90% 的类型了。

#### 第六层：读类型报错——把编译器当老师

类型报错是新手最大的挫败源，但它其实是编译器在告诉你"哪里违约了"。学会读报错，等于学会和编译器对话，这一层单独拿出来讲，因为它比任何 API 都更影响你的日常体验。

三类最高频的报错要形成条件反射。第一类：`Type 'X' is not assignable to type 'Y'`——形状不匹配，往下看"Property 'z' is missing"这一行，缺字段就是答案。第二类：`Property 'x' does not exist on type ...`——类型太宽或太窄，通常是联合类型没收窄，或者对象类型根本没有这个字段。第三类：`Type instantiation is excessively deep`——递归类型太深，回去检查递归的终止条件，或者用 `// @ts-expect-error` 临时隔离再修。

报错信息很长时不要慌：从第一行开始读，找到"不满足约束"的那一句，答案通常在报错的前三分之一。另一个实用技巧是把复杂类型拆开测试——`type A = ...; type B = ...` 逐层验证，哪一层报错，问题就在哪一层。编译器不会冤枉你，它只会诚实地告诉你契约没对齐，读懂了就是免费的老师。

#### 第七层：类型擦除与运行时边界

上篇的最后一课，是认清类型系统的"权力边界"：TypeScript 的类型只在编译期存在，编译成 JavaScript 后全部被擦除。这意味着三件事。

第一，类型不能当运行时判断用。`if (x instanceof User)` 里的 `User` 如果是 interface，编译后这段代码会直接报错——interface 是纯类型，运行时不存在。要做运行时判断，要么用 `class`，要么写类型守卫，要么用 zod 这类校验库。第二，类型安全不等于运行时安全：`as User` 只是告诉编译器"相信我"，数据在运行时可能完全不是这个形状，所以"边界校验"是类型系统的必要补充。第三，装饰器等元编程能力依赖实验性开关，和类型擦除的交互容易出坑，团队里要提前约定使用范围。

认清这条边界，你就不会犯"用类型当运行时判断"的错，也不会把类型系统吹成万能。TypeScript 的价值是把"能静态检查的错误"提前到编译期，剩下的运行时错误，交给守卫、校验和测试——三者各管一段，才是完整的安全网。

### 实战应用

#### 模式速查：常见场景的类型写法

| 场景       | 推荐写法                                                         | 说明                               |
| ---------- | ---------------------------------------------------------------- | ---------------------------------- |
| API 响应   | 判别联合 `{ ok: true; data: T } \| { ok: false; error: string }` | 成功失败分两个分支，调用处自动收窄 |
| 配置对象   | `as const` + `satisfies Config`                                  | 保留字面量类型，又不会越界         |
| 事件处理   | 判别联合 `{ kind, payload }`                                     | `switch` 里自动收窄 + 穷尽检查     |
| 组件 props | `interface` 继承 + 泛型                                          | 可扩展、可复用                     |
| 表单状态   | `FormState<T>` + `Partial<T>`                                    | 部分字段更新不用 as 断言           |

下面的模式来自真实项目的沉淀，可以直接抄。API 响应是最值得先改造成判别联合的场景：

```ts
type ApiResult<T> = { ok: true; data: T } | { ok: false; error: string }

function handleResult<T>(r: ApiResult<T>) {
  if (r.ok) {
    r.data // 这里 T 可用，类型安全
  }
}
```

如果后端返回错误码而不是布尔值，把 `ok` 换成 `code` 的联合也一样——关键是让编译器能靠一个字段区分分支，而不是在多个字段之间猜。

#### 陷阱与正确做法

**陷阱一：any 泄漏。** 反面案例：函数参数写成 `any`，返回值被推断成 `any`，调用链上所有类型保护全部失效，报错从源头消失，重构时全靠命。正确做法：边界处用 `unknown` 兜底，用类型谓词或运行时校验收窄；给边界函数写显式返回类型，让 any 止步于入口。

**陷阱二：as 滥用。** 反面案例：`response.data as any as Foo`，把编译期错误全部按下，运行时字段对不上就炸，还查不到原因。正确做法：先用 zod 或手写校验确认数据形状，再断言；至少要 `as unknown as Foo` 并写注释说明为什么这里安全。校验失败时返回错误路径，配合判别联合的错误类型，前端能直接按字段渲染报错。

**陷阱三：泛型过度设计。** 反面案例：一个函数挂五个类型参数，约束层层嵌套，调用方看不懂，写错一个参数报错一屏幕。正确做法：先写具体类型，出现重复再抽泛型；约束能窄则窄，用不上泛型就别用。

**陷阱四：类型谓词写错返回类型。** 反面案例：`function isFoo(x: unknown): boolean { return 'foo' in x }`——返回 `boolean` 不会收窄，后面照样要再断言。正确做法：返回 `x is Foo`，编译器才会在 `if` 分支内缩小类型。

**陷阱五：interface 和 type 混着用。** 反面案例：一个团队一半 `interface` 一半 `type`，同一个概念两种写法，互相替换还偶尔踩到"为什么 type 不能合并"的坑。正确做法：对外公共 API 用 `interface`（支持声明合并、继承语义稳定），内部组合和工具类型用 `type`，一条规则定死，review 时不用争论。

**陷阱六：用 `any` 绕过而不是定位问题。** 反面案例：`const data: any = JSON.parse(raw)`，之后所有字段访问都失去类型保护，一个拼写错误在运行时才爆炸。正确做法：JSON.parse 的结果先用类型守卫或 zod 校验，再断言成具体类型；`any` 只在"迁移期临时过渡"时出现，且必须带 TODO 注释和清理计划。

**陷阱七：类型谓词写得不严谨。** 反面案例：`function isUser(x: unknown): x is User { return typeof x === 'object' }`——校验太宽，任何对象都被当成 User，字段缺失照样崩溃。正确做法：类型谓词必须逐字段校验（`'id' in x && typeof x.id === 'string'`），谓词是"运行时和编译期的桥梁"，宽一寸，后面就多一分危险。

落地时给自己定三条验收线：每个外部数据入口都有类型守卫或 schema 校验；新增代码里 `any` 数量为零；每个联合类型都有明确的收窄路径。三条线同时守住，上篇讲的底层逻辑就算真正落地了，而不是停留在"能看懂报错"。

用一个完整的例子串一遍：假设你在写登录接口，后端返回 `{ token: string, user: { id: number, name: string } }`。第一层，定义 `LoginResponseSchema`（或用类型守卫）确认返回形状；第二层，定义 `LoginResponse = { token: string; user: User }` 让后续代码享受类型安全；第三层，`token` 只存在内存变量里，不写进 localStorage 以外的全局状态；第四层，`user` 传给组件时用 `Pick<User, 'id' | 'name'>` 控制暴露面。四层下来，这个接口从入口到 UI 全程类型安全，任何一个字段变化都在编译期暴露。

**陷阱八：把类型当成"别人的事"。** 反面案例：自己写的函数参数全是 `any`，类型错误全部转嫁给调用方，别人调你的代码还要自己猜。正确做法：公共函数必须有显式签名；"写类型"是交付的一部分，和写注释、写测试同等重要。

#### 实战演练：从零设计一个带类型的 API 层

把上篇的知识串成一个完整练习：给一个"获取用户资料"的接口设计类型层。

第一步，定义数据形状：`type User = { id: number; name: string; email: string }`。第二步，定义接口响应：`type ApiResponse<T> = { data: T } | { error: { code: string; message: string } }`——用判别联合而不是裸的 `data`，让调用方必须处理失败分支。第三步，写请求函数：`async function getUser(id: number): Promise<ApiResponse<User>>`，内部用 zod 或守卫校验 `JSON.parse` 的结果，校验失败返回 `{ error: ... }` 而不是抛 `as` 出来的假类型。第四步，消费端用 `if ('data' in resp)` 收窄，拿到 `resp.data` 时就是真正的 `User`。

四步走完，你会注意到一件事：类型定义在最前面，实现跟在后面——这就是"类型优先"的写作顺序。数据形状没想清楚之前不写实现，实现阶段几乎不用再改类型。这个顺序，是上篇所有底层逻辑在真实项目里最直接的体现。

再给一张高频场景的速查表，覆盖日常 80% 的"要不要写类型"决策：

| 场景       | 做法                       | 理由                 |
| ---------- | -------------------------- | -------------------- |
| 函数参数   | 显式类型 + 尽量用接口/联合 | 调用方靠签名自文档化 |
| 函数返回值 | 显式返回类型               | 防止实现悄悄改变契约 |
| 组件 props | interface + 可选标记       | 可扩展、可继承       |
| 事件/状态  | 判别联合 + 穷尽检查        | 漏分支编译期暴露     |
| 外部数据   | 守卫/schema 校验后断言     | 类型和运行时一致     |
| 内部推导   | 让编译器推断               | 少写、不重复         |

这张表的核心逻辑只有一句：**边界显式，内部推断**。外部进来的数据（API、存储、配置）显式定义和校验，内部的中间变量交给推断——既不啰嗦，又不失安全。

### 进阶思考

类型体操不是炫技。工具类型（`Partial`、`Record`、`Pick`、`Omit`）能读懂就够日常用了，自己造条件类型时记住一条核心规则：裸类型参数在条件类型里会自动分发（distributive），这是大多数"为什么结果和我预期不一样"的根源。类型体操也有成本：可读性和编译速度。一段类型代码如果三分钟才能看懂，它可能不值得；优先让业务数据的形状清晰，而不是追求"一行类型解决所有问题"。

```ts
type ToArray<T> = T extends unknown ? T[] : never
type R = ToArray<string | number> // string[] | number[]，而不是 (string | number)[]
```

值得再往下走的方向有三个。一是 branded type：`type UserId = string & { __brand: 'UserId' }`，让用户 ID、订单 ID、商品 ID 不再互相乱传，代价只是创建时多一次断言。二是模板字面量类型：``type Route = `/${string}` `` 能把路由、事件名从字符串拼写错误变成编译错误。三是类型检查性能：少写深递归类型、少对大对象用 `Omit`、避免 `any` 让推断失控，这三条能让大项目 `tsc` 快一个量级。

```ts
type UserId = string & { __brand: 'UserId' }
const uid = 'abc' as unknown as UserId // 只有创建点需要断言
function getUser(id: UserId) {
  // id 不会和订单 ID 混用
}
```

动手方面有个立竿见影的建议：在 tsconfig 里打开 `noUncheckedIndexedAccess`，它会逼你处理 `arr[i]` 可能为 `undefined` 的情况。这个选项带来的报错一开始很烦，但它能提前拦住一半的运行时错误，比任何类型体操都值。

学习路径也清楚：先精读官方 Handbook 的类型操作章节，再刷 type-challenges 的 easy 和 medium 题，接着读 Effective TypeScript 第二版，最后挑一个周末翻翻项目里 node_modules 的 `@types` 包源码，看别人怎么设计公共类型。中篇我们会把工具类型、条件类型和模板字面量全部拆开讲，下篇讲 tsconfig、项目引用和真实 API 层怎么落地。

最后回答一个很多人问过的问题："用 TypeScript 是不是一定比 JavaScript 好？"答案取决于你是否真的用它的类型系统。把类型当成"可选的装饰"，项目会退化成"带类型标注的 JavaScript"，该踩的坑一个不少；把类型当成"先于实现的契约"，你会发现自己写代码的顺序都变了——先想清楚数据形状，再写实现。这个顺序的转变，比任何语法技巧都重要，也是这三篇系列真正想传递的东西。

如果只允许你带走一个概念，带走"类型是约束"：类型不是标签，不是装饰，不是编译器的负担，而是你对自己代码的承诺——"这个值一定是这个形状"。承诺越多，运行时意外越少。上篇到这里结束，中篇我们进入工具类型与类型体操，把这些承诺变成可复用的工具。

从今天开始，你可以做一个最小的改变：打开你项目里 `any` 最多的一个文件，把每个 `any` 替换成 `unknown`，然后看着编译器逼你把类型收窄。第一次会有点痛，但你会发现自己对数据形状的理解在变清晰——这就是上篇全部内容的实践起点。

最后补一个学习心态：TypeScript 的知识是"螺旋上升"的，第一次读官方文档可能半懂，刷题又半懂，回到项目再半懂——但每一次半懂都比上一次多懂一层。不要指望一遍学完，给自己定一个节奏：每两周集中解决一类问题（这周联合类型，下周泛型），比一次读完整本手册有效得多。上篇结束，中篇见。

再强调一次上篇的主线：所有技巧都从"类型是约束"出发——结构化类型定义兼容规则，联合与交叉定义集合，泛型定义对应关系，收窄定义安全使用。把这四条刻进脑子，遇到任何类型问题，先问"这是哪条规则在起作用"，答案往往自己就出来了。这是上篇能给你的、比任何 API 都持久的东西。
