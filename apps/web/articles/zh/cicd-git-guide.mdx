### 背景

几乎每个团队都经历过这样的发布夜：功能开发完了，但没人记得部署步骤；测试只在本地跑过，合并后 CI 才爆出失败；线上出了问题，回滚靠"翻聊天记录找上一个镜像 tag"。发布不是技术难题，却成了每周最紧张的时刻——问题不在代码，在流程。

流程问题的根源是"人肉执行 + 口头约定"：手动跑命令、手动记步骤、手动决定能不能上线。CI/CD 要做的不是"自动化一切"，而是把每个环节的决策变成可重复、可审计的机制：提交有规范，合并有门禁，测试有流水线，部署有策略，回滚有按钮。

这篇文章把"从提交到上线"拆成三层：Git 协作规范（代码怎么进仓库）、CI 门禁（合并前谁把关）、CD 部署（上线怎么安全）。读完你能搭出一套自己的流水线，也能回答"为什么需要 CI"这个问题——不是赶时髦，是让发布从事故现场变成例行公事。

先给一个量化视角：DORA 研究把"部署频率、变更前置时间、变更失败率、恢复时间"作为软件交付的四个核心指标，而它们全部由 CI/CD 流程直接决定。手动发布团队的部署频率以周计、恢复时间以小时计；流水线团队的部署频率以天计甚至以小时计、恢复时间以分钟计。差距不是个人能力，而是"流程是否把正确的事固化成默认路径"。

另一个常被低估的是"发布恐惧"的组织成本：因为发布要开评审会、要熬夜、要写长长的检查单，团队会本能地攒批量、压周期，结果一次发布包含几百个变更，出了问题根本无法定位。CI/CD 的核心收益不是快，而是"小步、频繁、可回滚"——把发布拆小，每个变更的失败半径就小。

本篇结构：Git 工作流（代码怎么进仓库）→ CI 门禁（合并前谁把关）→ CD 部署（上线怎么安全）→ 实战模式与陷阱 → GitOps 与进阶。每节都围绕同一个问题：这个环节能不能让机器替我保证？

### 核心原理

#### 第一层：Git 工作流——代码怎么进仓库

Git 工作流的争议很多，但工程上可以收敛成两条主线：主干开发（trunk-based）和特性分支（feature branch）。主干开发是所有人都往 main 上合，靠小步提交和特性开关控制风险，适合 CI/CD 成熟、发布频繁的团队；特性分支是每个需求开分支、PR 评审后合入，适合需要代码评审和版本管控的团队。

无论选哪种，几条底线是一致的：main 永远可部署（broken main 是事故不是常态）、PR 必须过 CI 才能合、提交信息遵守规范（`feat:`、`fix:`、`chore:` 等 Conventional Commits）。提交规范不只是"好看"，它是变更日志、版本号和回滚定位的数据源——`git log` 能按类型筛选，`release-please` 能自动生成 changelog，全依赖提交信息的一致性。

分支保护是 Git 工作流的最后一道锁：在托管平台（GitHub/GitLab）上设置"main 禁止直接 push、PR 必须通过检查和 review"。保护规则把"口头约定"变成"平台强制"，谁也不能绕过。团队里如果有人问"为什么不能直接 push"，答案不是流程官僚，而是"直接 push 等于没有 review、没有 CI、没有留痕"。

还有一个和 Git 工作流配套的实践：PR 要小。一个 PR 的理想状态是"一次变更、一个主题、能独立发布"；超过 500 行的 PR 大概率是多个需求混在一起，review 质量下降，回滚时也会连带无关变更。拆 PR 的技巧是"按发布单位拆"而不是"按文件拆"——每个 PR 合并后 main 都处于可发布状态，这是主干开发的前提。

代码评审本身也要有明确的标准：看什么、不看什么。格式问题交给 lint 和格式化工具，逻辑正确性、边界处理、安全问题才是人看的重点。把 review 清单写进 PR 模板（"变更了什么、为什么、怎么验证、影响面"），评审从"通读代码"变成"核对清单 + 重点阅读"，效率和质量同时提升。

还有一个 Git 细节值得养成的习惯：提交信息写"为什么"而不是"改了什么"。"fix bug" 和 "fix: 修复订单重复支付（原因：支付回调幂等键缺失）"在半年后的 git log 里是完全不同的体验。Conventional Commits 不只是格式规范，它是变更日志和回滚定位的数据源——提交信息是写给未来排查事故的人看的。

#### 第二层：CI 门禁——合并前谁把关

CI 的核心不是"跑命令"，而是"把质量门禁自动化"。一个健康的 CI 流水线至少包含四道门：lint（风格和静态问题）、类型检查（TypeScript/mypy 等）、单元测试、构建验证。四道门全部通过，代码才允许合并。

````
```yaml
# .github/workflows/ci.yml
name: CI
on:
  pull_request:
  push:
    branches: [main]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm test
      - run: pnpm build

CI 工程化的几个关键细节：依赖缓存（`actions/cache` 缓存 pnpm store，安装时间从分钟级降到秒级）、并行 job（lint、test、build 互不依赖就并行跑）、失败即中断（任何一步失败，流水线红，不得用 `|| true` 吞掉）、超时保护（每个 job 设超时，防止挂起的任务占满队列）。

还有一个容易被忽略的点：CI 要和本地环境一致。`pnpm install --frozen-lockfile` 保证按锁文件安装，`packageManager` 字段固定 pnpm 版本，Node 版本用 `.nvmrc` 或 actions 显式指定。"本地能过、CI 挂了"的 90% 原因，是本地和 CI 的工具链版本不一致。

测试的确定性也值得单独强调：CI 里跑测试，最怕的是"偶发失败"。测试用了真实网络、依赖了执行顺序、留下了共享状态，都会产生偶发失败。工程实践是"测试必须能单独运行、重复运行、并行运行"——这条标准写进测试规范，比事后修 flaky 测试便宜得多。CI 的 retry 可以缓解噪音，但真正的解法是让测试具备确定性。

CI 还有一个组织层面的作用：它是团队质量的"共同基线"。新人写的代码好不好，先看 CI 过不过；老代码能不能动，看测试覆盖了多少。没有 CI 的团队里，质量靠"老手把关"；有 CI 的团队里，质量靠"机制兜底"——两者可以并存，但后者可扩展得多。

CI 的缓存策略也值得细化：依赖缓存（pnpm store、npm cache）能大幅缩短安装时间，但缓存 key 必须包含锁文件哈希——锁文件变了缓存自动失效，否则测试会跑在旧依赖上。另一个细节：CI 的 job 要设超时（比如 15 分钟），挂起的 job 会占满 runner 队列，让所有人的反馈都变慢。



#### 第三层：CD 部署——上线怎么安全

CI 负责"能不能合"，CD 负责"怎么上线"。最朴素的 CD 是"合并到 main 自动部署到生产"，但直接对生产 `kubectl apply` 或 `ssh deploy` 风险很高。工程化的部署至少要有：环境分层（staging 先验证、生产后上）、部署策略（滚动/蓝绿/金丝雀）、回滚机制（一键回到上一个版本）。

````

```yaml
jobs:
  deploy:
    needs: check
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t myapp:${{ github.sha }} .
      - run: docker push registry.example.com/myapp:${{ github.sha }}
      - run: kubectl set image deployment/myapp app=registry.example.com/myapp:${{ github.sha }}
      - run: kubectl rollout status deployment/myapp --timeout=5m

部署策略的选择：滚动更新（rolling）是默认，逐个替换实例，服务不断；蓝绿部署（blue-green）新旧两套并存，切流量瞬间完成，回滚就是切回去；金丝雀（canary）先放 5% 流量，观察指标再全量。策略没有绝对好坏，取决于"切换成本和回滚成本"的权衡——数据库 schema 变更过的版本，回滚不是切流量那么简单，这类问题要在发布流程里提前设计。

部署还有一个常被忽略的环节：验证。流水线不是"部署完成就结束"，而是要跑冒烟测试、检查健康检查接口、观察错误率和延迟指标。最好的验证方式是把"发布后观察"做成流水线的一步：部署后等待 N 分钟，如果错误率超过阈值自动回滚。人肉盯发布只能盯一次，流水线可以盯每一次。

数据库变更和代码发布的关系，是 CD 里最需要提前设计的环节。经典的"expand-and-contract"流程：第一步加新列/新表（兼容旧代码），第二步发布新代码（使用新结构），第三步删旧列/旧表（等旧代码全部下线）。把数据库迁移和代码发布解耦成三步，才能避免"代码回滚了数据库怎么办"的死锁。

#### 检查清单：发布流水线设计检查

| 检查项 | 通过标准                  |
| ------ | ------------------------- |
| 门禁   | 合并前 lint/测试/构建全绿 |
| 产物   | 不可变 tag，可追溯        |
| 环境   | staging 先于生产验证      |
| 策略   | 滚动/蓝绿/金丝雀明确      |
| 验证   | 发布后自动冒烟 + 指标观察 |
| 回滚   | 一键回滚，数据兼容        |
| 数据库 | expand-and-contract 流程  |
| 审计   | 部署记录自动生成          |

八项过完，发布流程才算"可上生产"。


### 实战应用

#### 模式速查：流水线结构速查表

| 阶段         | 动作                         | 门禁                   |
| ------------ | ---------------------------- | ---------------------- |
| push 分支    | 跑 lint + 单测               | 快速失败，开发者自己看 |
| 开 PR        | 跑 lint + 单测 + 类型 + 构建 | 合并必须全绿           |
| 合并 main    | 构建镜像 + 推 registry       | 镜像带 commit SHA      |
| 部署 staging | 自动部署 + 冒烟测试          | 验证通过才继续         |
| 部署生产     | 金丝雀/滚动 + 指标观察       | 失败自动回滚           |

#### 陷阱与正确做法

**陷阱一：CI 吞错误。** 反面案例：`pnpm test || true`，流水线永远绿，测试坏了三个月没人发现。正确做法：每一步失败都让 job 失败；确需容忍的步骤（如可选报告）单独标记，明确说明为什么容忍。

**陷阱二：密钥写进仓库。** 反面案例：`.env` 提交到 Git，几分钟后密钥被扫描机器人扒走。正确做法：密钥只放 CI 的 Secrets 和部署平台的变量管理；仓库里只有 `.env.example`；一旦发现密钥泄露，立即轮换而不是删除提交。

**陷阱三：部署脚本不可回滚。** 反面案例：发布脚本只做"更新"，没有记录上一个版本，出问题只能"找历史镜像"。正确做法：每个发布产物带不可变 tag（commit SHA），部署记录写进发布日志，回滚命令是一个固定的 `rollback` 脚本，而不是考古。

**陷阱四：staging 和生产配置漂移。** 反面案例：staging 用 SQLite、生产用 PostgreSQL，测试通过上线就挂。正确做法：staging 尽量复刻生产（数据库引擎、依赖版本、环境变量结构），至少保证"配置差异清单"是显式维护的。

**陷阱五：缓存毒化。** 反面案例：CI 缓存不设失效策略，依赖更新后缓存里还是旧版本，测试在旧依赖上通过。正确做法：缓存 key 包含锁文件哈希，锁文件变了缓存自动失效；关键依赖的更新在 CI 里强制全量安装一次。

**陷阱六：环境和密钥混在一起。** 反面案例：测试环境的密钥和生产环境同一个变量名，一次误操作把测试配置发到生产。正确做法：环境配置按 environment 隔离，密钥按环境分别管理；生产密钥只有发布 job 能读，普通 PR 连读的权限都没有。

**陷阱七：流水线没有超时和并发限制。** 反面案例：一个 job 挂起后占用整个 runner，多个 PR 同时触发导致队列堆积，CI 反馈时间从五分钟涨到一小时。正确做法：每个 job 设超时（`timeout-minutes`），关键路径限制并发（`concurrency` 取消旧版本的重跑），runner 资源按需扩容——CI 的速度本身就是团队效率的一部分。

### 进阶思考

CI/CD 的下一站是 GitOps：把"部署动作"也变成"仓库里的声明"。ArgoCD 或 Flux 持续监听 Git 仓库，仓库里的 K8s 清单一变，集群自动收敛。回滚就是 revert 一次提交，审计就是看 git log，部署的每一步都有版本——这套模型把"流水线"和"基础设施"统一成了同一个事实来源。

值得深入的方向还有三个。一是供应链安全：依赖锁定（lockfile）、漏洞扫描（`pnpm audit`/osv-scanner）、镜像签名（cosign）和 SBOM 生成，让"你部署的东西"可以验证。二是发布工程：把数据库迁移、特性开关、金丝雀指标观察纳入发布流程，解决"代码回滚了数据库怎么办"这类经典难题。三是度量：部署频率、变更前置时间、失败率、恢复时间（DORA 四指标），让 CI/CD 的改进有数据可依。

学习路径：先把你项目最耗时的发布步骤写成一个 GitHub Actions 工作流（构建 + 测试 + 部署），再逐步加分支保护和 staging 环境，最后用 ArgoCD 或一个简单的 CD 脚本把生产部署自动化。记住一句话：CI/CD 的终点不是"没人操作"，而是"每个操作都可解释、可回滚、可审计"。

判断标准：你的流水线是"给人看的"还是"给系统用的"？如果每次发布还要人手动确认十几个步骤、翻聊天记录找镜像 tag，说明流水线只是把命令写进了 YAML，流程还是人肉的。真正的 CI/CD 应该让"发布"变成一次确认动作——输入只有一个"发布版本"，剩下的由流水线保证。

从今天开始，你可以做一个最小改造：把"构建 + 测试 + 部署"中最常出错的三个手动步骤写进一个脚本或工作流，先不追求全自动化。跑通一次，你就能感受到"机器记得步骤"和"人记得步骤"的差别——这个差别，就是 CI/CD 所有价值的起点。

结语：CI/CD 不是"运维的事"，它是整个研发团队的事。开发者负责写门禁（测试、lint、类型检查），运维负责写部署（策略、回滚、监控），两者在流水线里汇合。一个团队从"手动发布"走向"流水线发布"，改变的不仅是发布速度，还有发布心态——从"每次发布都紧张"变成"每次发布都例行"。这个心态转变，是工程成熟度最真实的指标。

"从零开始"的最小路径：如果你的团队还没有任何 CI，不要一次上全套——本周先做一件事：把"构建 + 测试"写进 GitHub Actions，push 就自动跑。跑通后加"分支保护"（main 必须过 CI 才能合），再加"构建镜像 + 部署 staging"。每一步都小到一周能完成，三个月后回头看，你会发现流程已经在不知不觉中完整了。

关于"度量"的话：CI/CD 的改进要有数据支撑——部署频率、失败率、恢复时间、构建时长，四个数字每月复盘一次。没有度量的流程改进是"感觉"，有度量的才是"工程"。把四个数字贴进团队周会，你会发现讨论从"我觉得""他应该"变成了"数据显示"——这个转变，比任何工具都更能推动工程文化。

"安全流水线"的实践：CI/CD 是攻击者的高价值目标（拿到流水线权限等于拿到发布权限）。安全基线包括：流水线密钥用 Secrets 管理且最小权限、runner 隔离（不共享生产凭据）、依赖扫描（pnpm audit/osv-scanner）、镜像签名（cosign）、发布审批（生产环境 require review）。流水线安全不是"运维的事"，它是"供应链安全"的核心环节——一次流水线入侵，等于一次全站投毒。

CI 不是替代本地检查，而是兜底本地检查——理想节奏是"本地跑得飞快（lint + 单测）、CI 跑得全面（类型 + 集成 + 构建）、发布跑得谨慎（staging + 金丝雀）"。三层各有职责，别让 CI 承担"本应该本地发现"的慢反馈，也别让本地承担"本应该 CI 保证"的全量检查。分层清晰，开发体验和工程质量才能同时在线。

CI/CD 配置本身就是团队最重要的运维文档——每个 job 做什么、为什么做、失败怎么办，都要能在 YAML 里读懂。工程实践是"流水线即文档"：job 名用业务语言（`test-unit` 而不是 `job-3`）、关键步骤加注释、失败处理显式声明（`continue-on-error` 只在明确原因时用）。流水线是团队"怎么交付"的固化表达，它的可读性决定了流程的可维护性。

四个 DORA 指标（部署频率、变更前置时间、变更失败率、恢复时间）不只是"看"，还要设目标——比如"部署频率从每周一次到每天一次""恢复时间从 2 小时到 30 分钟"。目标要小步调（一个季度一个指标），达成后庆祝并设下一个。流程改进的本质是"习惯的重塑"，习惯靠节奏，不靠口号。

测试在 CI 里的分层，值得用一张金字塔说清楚：底层是单元测试（几百个、毫秒级、覆盖纯逻辑），中层是集成测试（几十个、秒级、覆盖模块协作），顶层是端到端测试（几个、分钟级、覆盖核心用户路径）。CI 的策略是"每次提交跑底层、PR 跑中层、合并后跑顶层"——把最慢的测试放在最不频繁的环节，开发反馈速度和质量保障才能同时成立。

分支策略的选择还有一个"发布节奏"的维度：如果你的产品需要"随时可发布"（SaaS、App 后端），主干开发加特性开关是正解——所有代码合入 main，未完成的功能用开关隐藏；如果你的产品是"版本制交付"（发版给客户安装），release 分支加 hotfix 流程更合适。分支策略不是"哪个先进"，而是"匹配你的发布模型"——选错分支策略的代价，是每次发布都要处理一堆"这个分支该不该包含这个提交"的纠结。

流水线的"产物可追溯"是审计和排障的基础：每个发布版本要能回答三个问题——这个版本由哪个 commit 构建？用了哪些依赖版本？通过了哪些测试？解决方式是"构建产物带元数据"（commit SHA、依赖锁文件哈希、测试报告链接），并把这些元数据写进发布记录。没有可追溯性的发布，出问题时的第一步（定位版本）就要靠猜。

合并冲突是 Git 绕不开的，但冲突可以最小化——小 PR（冲突面小）、频繁同步（main 更新就 rebase）、模块边界清晰（少改同一文件）。真的冲突了，别慌：`git diff` 看双方意图，按"保留谁、合并什么"逐段决策，必要时找对方确认。冲突不是"代码打架"，是"两个人同时改了同一处的信息"——处理冲突的能力，和写代码的能力同等重要。

从提交规范到分支保护，从 CI 门禁到部署回滚——这一整套流程的终极目的，是让"发布"从"高风险动作"变成"日常动作"。当发布变得日常，团队就敢于小步快跑；敢于小步快跑，问题就能在最小范围内暴露。这就是 CI/CD 送给团队最珍贵的礼物：把恐惧换成节奏。


构建缓存的设计：依赖缓存（pnpm store、npm cache、Go module cache）能大幅缩短安装时间，但缓存 key 必须包含锁文件哈希——锁文件变了缓存自动失效，否则测试跑在旧依赖上。缓存命中率要监控，缓存长期不命中说明 key 设计有问题。缓存是 CI 速度的杠杆，也是「测试环境不一致」的隐患源，key 设计要同时兼顾速度和正确性。

发布的「审批门」也：生产发布可以由环境保护规则控制——指定审批人、限定发布窗口、要求特定 job 成功。审批不是流程官僚，它是「高风险变更的多一双眼睛」：发布清单、回滚计划、验证计划三样齐全才能点批准。把审批做成「有清单的确认」，比「口头说一声就发」安全得多。

流水线的「失败通知」：CI 失败要在第一时间通知到提交者，而不是等全量跑完才看到红。通知的分层：提交失败通知提交者，主分支失败通知全组，发布失败通知值班。通知要带「失败原因 + 日志链接」，让收到通知的人能直接开始排查，而不是先问「哪个 job 挂了」。


流水线的「可观测性」每个 job 的耗时、缓存命中率、测试通过率、部署成功率都要有记录，形成趋势。CI 变慢是团队效率的隐形杀手——「构建从 5 分钟涨到 20 分钟」通常不是某一次变更造成的，而是依赖、测试、缓存策略的持续劣化。用趋势图发现劣化，比等到「没人愿意跑 CI」再治理便宜得多。


流水线还有一个「默认安全」的原则：失败默认阻止（fail closed），而不是「失败了也放行」。`continue-on-error` 只用在「非关键步骤」（如可选报告），关键门禁（测试、构建、安全扫描）失败必须红。默认安全的流水线，偶尔会误伤「其实没关系」的失败，但换来的是「红了一定有问题」的确定性——这个确定性比省一次重跑值钱。
```
