### 背景

你所在的团队要做一次云平台决策：海外业务选 AWS，国内合规要求选腾讯云，或者两边都有。开会时大家各说各话——"AWS 生态全""腾讯云便宜""阿里云文档多"——但没有一个人能说清楚：这两朵云到底差在哪，迁移成本有多大，账单会不会失控。

这种困惑很正常，因为云厂商的差异不在"能做什么"，而在"怎么叫、怎么配、怎么收费"。EC2 和 CVM 是同一个东西的两个名字，S3 和 COS 也一样，但控制台路径、权限模型、计费项却各有一套。如果只按"功能对得上"来迁移，上线后账单和运维方式都会给你惊喜。

这篇文章把两朵云的核心服务逐项对照，给出选型决策表，再讲透迁移、权限和成本这三个最容易出事的环节。目标不是让你成为任一家的专家，而是让你在选型会上能问出正确的问题：这朵云的服务和我的架构匹配吗？迁移要动多少代码？月底账单会不会爆？

还有一个经常被忽视的现实：云平台的决策往往是"历史决定"而不是"技术决定"。公司早期选了腾讯云，后来出海想加 AWS；或者老板在 AWS 峰会上听了演讲，回来要求全栈迁移。工程师能做的，不是争论"谁更好"，而是把两边的能力、成本和迁移工作量量化成表，让决策基于事实而不是感觉。这篇文章提供的对照表和检查清单，就是用来干这件事的——它不会替你选，但会让你选得有依据。

本篇的结构：核心服务对照（翻译表）→ 计算与存储选型 → 权限模型 → 账单与成本 → 实战选型表和陷阱 → 多云与进阶方向。按"先懂抽象、再懂差异、最后懂成本"的顺序，读完后你能独立完成一次云平台评估。

还有一个学习心态：不要把"云平台"当成一个需要精通的大系统，把它当成"一组可以按需租用的 API"。每个服务（计算、存储、数据库）都有清晰的边界和计费方式，你不需要全部精通，只需要在架构需要时选对。云平台的知识是"地图式"的——知道有什么、去哪查，比背下所有细节更有用。

### 核心原理

#### 第一层：核心服务对照——同一件事，两套名字

云计算的基石服务其实高度同构，先建立一张"翻译表"：

| 能力         | AWS        | 腾讯云                      |
| ------------ | ---------- | --------------------------- |
| 云服务器     | EC2        | CVM                         |
| 对象存储     | S3         | COS                         |
| 关系数据库   | RDS        | CDB（云数据库 MySQL/TDSQL） |
| 容器编排     | EKS / ECS  | TKE                         |
| 函数计算     | Lambda     | SCF                         |
| 负载均衡     | ALB / NLB  | CLB                         |
| 对象存储 CDN | CloudFront | CDN                         |
| 消息队列     | SQS / SNS  | CMQ / TDMQ                  |

名字不同，但抽象层几乎一致：计算实例、块存储、对象存储、托管数据库、容器集群、函数计算。选型的核心不是"哪家更强"，而是"你的团队熟悉哪套操作习惯、目标市场在哪、合规要求是什么"。AWS 在全球化网络和生态深度上领先，腾讯云在国内备案、微信生态、中文文档和本地支持上有优势，这些差异比单个服务的 benchmark 重要得多。

选型时还要看"配套生态"：AWS 的 IAM、CloudFormation、CloudWatch、S3 生态自成一体，腾讯云的 CAM、Terraform 支持、CLS、COS 也成体系。选一家，意味着你进入它的整个生态——迁移成本不只是服务对服务，还有工具链、权限模型、监控体系的整体迁移。评估时把"生态配套"列成清单，比对比单个服务规格更有意义。

还有一个经常被忽略的维度：合规与备案。国内业务要求 ICP 备案和等保，数据要留在境内；出海业务要考虑 GDPR、数据主权和区域合规。腾讯云对国内备案流程更熟，AWS 对国际合规（SOC2、ISO27001）更完整。合规不是"上云后再说"，而是选型的前置条件——选错了区域和厂商，业务上线后才发现不合规，返工成本极高。

#### 第二层：计算与存储——从虚拟机到 Serverless 的选型阶梯

计算选型有一个清晰的阶梯：物理机（极少数）→ 虚拟机（EC2/CVM）→ 容器（EKS/TKE）→ Serverless（Lambda/SCF）。每上一层，你放弃的控制权越多，换来的运维负担越少。

虚拟机适合"迁移第一站"：架构不变，先上云再说。容器适合已经做好的应用打包：镜像即交付物，配合 K8s 生态获得扩缩容和自愈。函数计算适合事件驱动和突发流量：按调用次数计费，冷启动是主要代价。选型判断标准是"你的负载形状"：稳定长跑用虚拟机或容器，尖峰突发用 Serverless，两者混合也完全正常——网关层用函数，业务层用容器，是云原生架构的常见组合。

存储选型同样分三层：对象存储（S3/COS）存文件、图片、备份，按量计费、无限扩展；块存储（EBS/CBS）挂给虚拟机当系统盘和数据盘，性能稳定；文件存储（EFS/CFS）做多实例共享，适合日志和上传目录。对象存储是云上最便宜的持久化方案，也是几乎所有应用的默认选择——静态资源、数据库备份、日志归档，先问"能不能放对象存储"，再问其他方案。

计算实例还有一个"规格陷阱"：选型时只看 CPU 核数，忽略了内存比例、网络带宽、突发性能（burstable）限制。同样的 2 核 4G，标准型、突发型、高 IO 型的实际能力差别很大。云厂商的实例类型文档里，"性能基线"和"突发上限"要仔细看——突发型实例平时性能打折，峰值才恢复，不适合持续高负载。选型表里加一列"用途标签"（计算型/内存型/IO 型），比只看价格更靠谱。

Serverless 的选型也有一个认知纠偏：函数计算不是"零成本"，是"按调用计费"——高频低延迟的调用，函数计算的成本可能高于常驻实例；低频突发、事件驱动才是它的主场。判断标准是"调用频率 × 单次耗时 × 冷启动容忍度"：低频突发用函数，高频稳定用容器。Serverless 和容器不是替代关系，是"负载形状不同"的两种工具。

#### 第三层：权限模型——IAM/CAM 是一切的边界

云上事故里，权限过宽造成的比例远超想象：账号密码泄露、子账号是管理员、密钥硬编码在仓库里。AWS 的 IAM 和腾讯云的 CAM 解决同一个问题：谁（身份）能对什么（资源）做什么（操作）。

权限设计的三条铁律：一是最小权限，每个服务角色只给需要的操作，不用 `AdministratorAccess` 图省事；二是密钥隔离，访问密钥（AccessKey）只发到有需要的服务，代码仓库和镜像里绝不出现明文密钥；三是定期审计，用云厂商的访问审计（CloudTrail/CloudAudit）查"谁在什么时候干了什么"，权限变更走审批。

权限模型的"主体"也要分清楚：人是身份（IAM 用户），程序是身份（服务角色），密钥是凭证（AccessKey）。现代实践是"人走 SSO/临时凭证，程序走服务角色"——长期密钥的数量应该趋近于零。每次在代码里看到硬编码的 AK/SK，都应该当成安全事件处理：立即轮换，并排查泄露路径。

权限还有一个"职责分离"的设计：开发角色和生产角色分开，生产资源的删除权限只有运维审批后可用；密钥的创建要审计，权限的变更要通知。云平台的权限事故（误删生产库、密钥泄露）大多是"一个人拥有太多权限"造成的——权限的最小化不只是安全要求，也是操作事故的预防手段。

身份体系还有一个现代演进：从"长期密钥"转向"临时凭证"。容器和函数运行时用服务角色（Service Role）自动获取临时凭证，本地开发用短期令牌，长期密钥的数量应该趋近于零。谁还在代码里写死 AK/SK，谁的账号就是下一个泄露点。

#### 第四层：账单与成本——云上最大的隐藏陷阱

云账单失控不是"用量太大"，而是"计费项没看懂"。最容易爆的四个计费项：公网流量（出网按 GB 计费，CDN 回源和跨区域流量都算）、对象存储请求次数（读写请求按次数计费，小文件海量访问能吃掉大笔钱）、快照和备份存储（删除实例不删快照，快照费用悄悄滚）、托管服务的闲置资源（没人用的开发实例 24 小时在跑）。

成本控制的标准动作：预算告警（月度预算的 50%/80%/100% 三级告警）、标签体系（按项目/环境/负责人打标签，账单按标签拆分）、闲置资源巡检（一周没流量的实例自动下线）、存储生命周期（日志 30 天后转归档存储，90 天后删除）。云厂商都有成本优化工具（AWS Cost Explorer、腾讯云成本分析），但工具只是报表，真正省钱的是"资源必须有主、有生命周期"的管理制度。

账单的另一个隐藏面是"预留与按量的博弈"。长期稳定的负载（数据库、核心服务）用包年包月或预留实例，通常能省 30% 到 50%；弹性负载（测试环境、批处理）用按量计费，避免为闲置付费。两种模式不是二选一，而是按资源画像混合：稳定资源包年，弹性资源按量，再配合自动关机策略（非工作时间停掉开发实例），账单能肉眼可见地降下来。成本优化的本质不是"省"，而是"让每一笔钱对应到明确的价值"。

成本治理还有一个组织层面的机制：把"成本"写进每个服务的"责任书"。谁创建资源，谁负责它的生命周期和预算；谁的资源没标签，谁的成本无法归属。云成本失控很少是"单价贵"，多是"没人认领的资源在持续产生费用"——标签、预算、责任到人，三件事比任何优化工具都有效。

### 实战应用

#### 模式速查：典型场景选型表

| 场景       | AWS 方案             | 腾讯云方案       | 要点                           |
| ---------- | -------------------- | ---------------- | ------------------------------ |
| 静态网站   | S3 + CloudFront      | COS + CDN        | 零服务器，流量成本是唯一变量   |
| Web API    | EKS + ALB            | TKE + CLB        | 容器化是两家的共同推荐路径     |
| 关系数据库 | RDS（Aurora）        | TDSQL-C          | 托管库省运维，但别选冷门引擎   |
| 定时任务   | Lambda + EventBridge | SCF + 定时触发器 | 按次计费，适合低频任务         |
| 文件上传   | S3 预签名 URL        | COS 临时密钥     | 直传对象存储，不经过应用服务器 |
| 日志分析   | S3 + Athena          | CLS（日志服务）  | 先归档再查询，成本低一个量级   |

#### 陷阱与正确做法

**陷阱一：按"功能名对得上"做迁移。** 反面案例：EC2 迁 CVM 时只改镜像，没检查磁盘类型、网络计费、地域差异，上线后性能差 30% 还找不到原因。正确做法：迁移前做一次"能力清单"对照——实例规格、磁盘 IOPS、带宽计费模式、可用区、镜像兼容性逐项核对，先跑影子流量再切正式流量。

**陷阱二：公网流量费用失控。** 反面案例：对象存储不挂 CDN，前端直接读源站，每月流量费上万。正确做法：静态资源一律走 CDN，数据库、内网服务之间走内网地址，出网流量按"必要出网"原则审计；跨区域同步数据前先算流量账。

**陷阱三：权限一给就是管理员。** 反面案例：为了调试方便给子账号绑了 AdministratorAccess，泄露后攻击者能删库、改账单、开矿机。正确做法：子账号按角色最小授权，生产资源用服务角色，密钥一律临时凭证；把"权限越大责任越大"写进团队规范。

**陷阱四：选了冷门地域或引擎。** 反面案例：数据库选了无托管的自建方案，或选了团队没人会运维的冷门引擎，迁移时找不到参考、出问题时没人能救。正确做法：地域选"目标用户最近 + 合规允许"的交集；数据库优先托管服务的主流引擎，把"好招人"也当成选型条件。

**陷阱五：备份只做"全量快照"。** 反面案例：每天全量快照，恢复时才发现快照保留周期太短、没有跨地域容灾。正确做法：备份分层——本地快照保 7 天、跨地域备份保 30 天、核心数据定期导出到对象存储并设置不可变（WORM）；每季度做一次真实恢复演练，恢复速度比备份频率更重要。

**陷阱六：忽略可用区（AZ）设计。** 反面案例：所有实例和数据库都在同一个可用区，可用区故障（电力、网络）时业务整体宕机。正确做法：核心服务至少跨两个可用区部署，数据库用多 AZ 高可用；从第一天就按"单可用区会挂"来设计。

**陷阱七：网络和安全组规则过宽。** 反面案例：安全组放行 0.0.0.0/0 到数据库端口，等于把数据库暴露在公网。正确做法：安全组默认拒绝，按"谁需要访问谁"逐条放行；数据库、Redis 只允许内网和特定 IP；公网只暴露必要的 Web 端口。

**陷阱八：镜像和快照不清理。** 反面案例：每次发布生成新镜像/快照，旧的永不删除，存储费用悄悄涨。正确做法：镜像和快照设置保留策略（保留最近 N 个版本），定期清理；用云厂商的镜像生命周期功能自动化。

#### 检查清单：上云迁移评估表

| 检查项   | 通过标准                 |
| -------- | ------------------------ |
| 合规     | 区域、备案、数据主权明确 |
| 能力对照 | 每个依赖服务有替代方案   |
| 网络规划 | VPC/子网/安全组设计完成  |
| 权限     | 最小权限、无硬编码密钥   |
| 成本     | 预算告警 + 标签体系就绪  |
| 备份     | 多层级备份 + 恢复演练过  |
| 容灾     | 跨可用区/跨地域方案明确  |

七项全过，迁移方案才算"可评审"。

### 进阶思考

云平台的下一层，是"多云和可移植性"的博弈。全用一家，能吃到最好的集成和折扣，但会被锁定；全用两家，成本翻倍且运维复杂度剧增。务实的路线是"分层多云"：无状态应用层保持可移植（容器镜像 + Terraform），有状态服务（数据库、对象存储）留在主云，把可移植性投资花在真正会迁移的部分。

值得深入的方向有三个：一是基础设施即代码，用 Terraform 管理云资源，环境从"控制台点出来的"变成"代码声明的"，可 review、可审计、可重建；二是 FinOps，把成本责任人落到每个服务负责人，预算、标签、闲置清理变成日常节奏而不是季度运动；三是云厂商的原生高级服务（托管 K8s、Serverless 数据库、AI 服务），它们省下的运维时间，往往比"迁移省下的账单"更值钱。

学习路径：先用免费额度在两朵云各搭一个最小环境（对象存储 + 静态网站），感受控制台和计费差异；再写一份 Terraform 配置把环境重建一遍；最后给自己设一个成本预算，跑一个月的真实流量看账单。云平台的知识更新极快，但"选型看架构、权限看边界、账单看流量"这三条原则，长期不变。

最后给一个心态建议：不要试图"精通"每一朵云。云平台的控制台和文档量级，任何个人都不可能全部掌握；聪明的做法是掌握"抽象层"（计算、存储、网络、权限、账单）和"迁移路径"，具体按钮和命令按需查文档。你在 AWS 上学会的 VPC、IAM、S3 概念，90% 能平移到腾讯云——平台会变，云计算的思维模型不会。

结语：云平台选型不是"选最好的云"，而是"选最合适的组合"——国内市场腾讯云，出海加 AWS，两者可以并存（分层多云）。真正重要的不是牌子，而是你是否具备"用云的正确姿势"：架构按抽象层设计、权限按最小化收敛、成本按责任到人管理。姿势对了，换哪朵云都是迁移；姿势不对，用哪朵云都是事故。

"多云落地"的现实建议：不要一开始就双云跑同一套业务（成本翻倍、运维翻倍）；先用"主云 + 灾备云"的形态（主云承载业务，备份数据同步到备云），跑通后再评估"无状态层双活"。多云的价值在"谈判筹码"和"容灾兜底"，不在"同时用两套"——把云厂商当"可替换的供应商"，而不是"必须二选一的信仰"。

"云技能"的学习路径：先精通一个抽象层（计算或存储）在一朵云上的完整操作，再对照另一朵云找"翻译表"；每学一个新服务，先画"它属于哪个抽象层、和已知服务的对应关系"，而不是从头学。云平台的知识是"一法通、万法通"——抽象层是法，控制台是万，掌握了法，万只是时间问题。

上云的本质是"用可控的运营成本换弹性和运维外包"——自建机房适合"长期稳定、数据主权要求极高、团队有运维能力"的场景；上云适合"业务波动大、不想养运维团队、需要快速扩展"的场景。2025 年大多数团队没有自建的理由，但"数据必须留在境内指定位置"这类硬约束，仍然会让自建或私有云成为唯一答案。决策时把"合规约束"放在第一位，成本和技术排后面。

云平台的价值不在"省了服务器采购"，而在"让基础设施成为可编程的 API"——用 Terraform 声明资源、用 CI/CD 自动发布、用监控自动伸缩。上云只是第一步，"用云的姿势"才是分水岭：把云当"远程机房"用（手动点控制台），你只省了硬件；把云当"API"用（代码管理一切），你才拿到云原生的全部收益。

收尾：无论你最终选了 AWS、腾讯云还是混合，这篇文章想留给你的不是"选哪家"的答案，而是"怎么选"的方法——抽象层对照、合规前置、成本责任化、迁移可回滚。云平台会不断出新服务，账单会不断变化，但"用抽象思考、用边界控制、用数据决策"这套方法不会过时。带着方法上路，选哪朵云都能走得稳。

第一，给现有云账号开"预算告警"（本月费用的 80% 提醒）；第二，检查一次"是否有硬编码密钥在仓库里"（有就立即轮换）；第三，用 Terraform 把一台测试实例的配置写成代码。三件事加起来不超过半天，但它们会立刻改变你对云的"使用姿势"——从"控制台点击者"变成"云原生工程师"。

VPC/私有网络的「三层子网」规划：公网子网放负载均衡和入口，内网子网放应用，数据子网放数据库（不暴露公网）；子网间用安全组和网络 ACL 双层控制。数据库只允许应用子网访问，Redis 同理——「数据库暴露公网」是最常见的云安全事故，几乎都源于「没有子网规划」。VPC 设计在项目初期做，比事后补安全层便宜一个量级。

成本「归属」的机制：所有资源强制打标签（项目/环境/负责人），没有标签的资源不允许创建（用组织策略强制），账单按标签拆分。成本归属清晰后，「谁的费用在涨」一目了然，优化责任才能落到人。标签是成本治理的地基，比任何 FinOps 工具都先要建起来。

云上「灾备」的落地路径：先做「备份」（数据定期备份到对象存储并异地），再做「恢复演练」（每季度从备份恢复一次），最后做「容灾」（跨可用区/跨地域的自动切换）。大多数团队只需要「备份 + 恢复演练」就够——容灾的复杂度远高于收益，除非业务有明确的 RTO/RPO 要求。

云上「账号体系」的隔离生产、开发、测试用独立账号（或独立的组织单元），权限和账单天然隔离；跨账号的资源访问用角色切换（AssumeRole），而不是共享密钥。账号隔离的代价是管理复杂度上升，但它把「生产事故影响面」和「权限爆炸半径」都控制住了——云账号的边界，就是安全边界。
