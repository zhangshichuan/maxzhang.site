### 背景

上中两篇解决了"会不会写类型"的问题，这一篇解决"类型怎么活下来"的问题。现实里最常见的场景是：个人项目类型干净，一进团队项目就全是 `any`；`strict` 没开，`null` 满天飞；`tsc` 编译要跑两分钟，大家宁愿 `as any` 也不想等；CI 不跑类型检查，类型报错只在 IDE 里出现，合代码的人根本不知道。

这不是某个人偷懒，是工程机制没建起来。类型安全不是个人觉悟，是流程、配置和工具链共同作用的结果。个人英雄式的"我写得规范"撑不过三个月，只有把检查固化到流程里，类型体系才能长期存活。

另一个现实是：团队里真正能写复杂类型的人通常只有一两个，其他人靠自动补全和复制粘贴。这不是类型体系的失败，而是设计信号——公共类型必须简单到"不用想就能用"，复杂类型应该被封装在底层，业务代码里只出现 `User`、`Order`、`ApiResult<T>` 这种一眼能懂的名字。工程化的目标不是让每个人都成为类型专家，而是让非专家也踩不到类型坑。

这篇是 TypeScript 系列的下篇，讲四件事：tsconfig 怎么开才叫严格、类型检查怎么进 CI、API 边界怎么保证类型和运行时一致、以及构建性能怎么抢救。看完你就能搭出一套"类型不容易烂掉"的工程底座。

先给一个反面参照：一个三年前的项目，`strict` 没开，`any` 遍布数据层，CI 只跑 lint 不跑类型检查，每次重构都要靠"全局搜索调用点 + 肉眼确认"。后来想升级框架，光是把 `null` 相关的报错修完就花了两周，期间还上线了一个"用户资料偶发为空"的 bug。类型工程不是锦上添花，是项目长期维护的承重墙——墙没砌好，后面每一次改动都在还债。

另一个现实是：团队里真正能写复杂类型的人通常只有一两个，其他人靠自动补全和复制粘贴。这不是类型体系的失败，而是设计信号——公共类型必须简单到"不用想就能用"，复杂类型应该被封装在底层，业务代码里只出现 `User`、`Order`、`ApiResult<T>` 这种一眼能懂的名字。工程化的目标不是让每个人都成为类型专家，而是让非专家也踩不到类型坑。

所以下篇的立场很明确：不追求"每个人都会写复杂类型"，追求"每个人都被机制保护"。机制包括配置、脚本、CI、review 规则，它们不依赖某个人的水平，而依赖系统的设计。这正是"工程化"和"个人能力"的分水岭——个人能力会流失，机制不会。

### 核心原理

#### 第一层：tsconfig 的严格开关，每一个都在堵一类 bug

很多人以为开了 `strict: true` 就万事大吉，其实 `strict` 只是第一道门。真正决定项目类型质量的是一组更细的开关。

`strict` 家族包含 `strictNullChecks`、`noImplicitAny`、`strictFunctionTypes` 等，其中 `strictNullChecks` 是价值最大的一个：它让 `null` 和 `undefined` 成为显式类型，逼你在使用前处理空值。`noImplicitAny` 则禁止"猜出来的 any"——函数参数没写类型就是错误，而不是静默通过。

`strict` 之外，还有三个高频开关。`noUncheckedIndexedAccess` 让 `arr[i]` 和 `obj[key]` 的结果带上 `undefined`，逼你处理"下标可能越界"；`exactOptionalPropertyTypes` 区分"属性缺失"和"属性值为 undefined"，防止用 `undefined` 伪造可选属性；`noImplicitOverride` 要求重写父类方法时显式写 `override`，防止父类改了签名子类还蒙在鼓里。

```json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true
  }
}
```

这些开关刚打开时会冒出一批报错，那是历史债务显形，不是坏事。正确姿势是开一次、修一批，而不是开开关关。

开严格模式的顺序也有讲究。推荐从 `strictNullChecks` 开始：它的报错最多，但语义最清楚，修完立刻能拦住一半的空值崩溃。然后是 `noImplicitAny`，把所有"猜出来的 any"改成显式类型或 `unknown`。最后再开 `noUncheckedIndexedAccess` 和 `exactOptionalPropertyTypes`，这两个报错虽然烦，但每一条都对应一个真实的运行时错误。一次全开容易让团队产生"严格模式 = 痛苦"的错觉，分批开反而能建立信心。

还有一个配置细节常被忽略：`lib` 和 `target` 决定了你能用哪些语法和类型 API。`target` 管编译输出，`lib` 管类型环境（`DOM`、`ES2022` 等）。团队统一配置 `target` 和 `lib`，避免"我的机器能用、CI 报错"的怪问题；`moduleResolution` 用 `bundler`（Vite 项目）或 `node16`，和打包工具对齐。配置漂移是类型工程里最隐性的一类问题，它不像 `any` 那么显眼，但造成的困惑一点不少。

#### 第五层：类型测试——给类型写测试

类型也是代码，代码就要有测试。TypeScript 生态里最轻量的类型测试方式是 `@ts-expect-error`：它断言"下一行应该报错"，如果下一行没有报错，编译器反过来报错。

```ts
const user: User = { id: 1, name: 'max' }
// @ts-expect-error 缺少 email 应该报错
const bad: User = { id: 1, name: 'max' }
```

`@ts-expect-error` 的价值是"把类型契约固化成测试"：工具类型的行为、判别联合的收窄、泛型的约束，都能用"哪行代码应该报错"来验证。配合 `expectTypeOf`（vitest 提供），可以断言"这个变量的类型是 X"：

```ts
import { expectTypeOf } from 'vitest'

const result = getValue({ name: 'max', age: 18 }, 'age')
expectTypeOf(result).toEqualTypeOf<number>()
```

类型测试的粒度不需要细到每个函数，重点覆盖：公共 API 的类型契约、工具类型的边界行为（输入联合、输入 never、嵌套结构）、以及"重构后类型仍兼容"的回归保护。有了类型测试，改一个类型定义时，你不再只靠 IDE 报错，而是有一套可以跑进 CI 的断言。

#### 第六层：monorepo 与共享类型——让契约跨包流动

项目大了之后，类型通常要跨包共享：API 层的类型给前端用，领域类型给多个服务用。monorepo 里最朴素的做法是"类型包"：一个 `packages/types` 专门导出共享类型，其他包依赖它。

```json
{
  "name": "@app/types",
  "exports": { ".": "./src/index.ts" },
  "types": "./src/index.ts"
}
```

共享类型的三个纪律：第一，类型包只放类型和纯函数，不放运行时逻辑，避免前端打包时引入后端依赖；第二，类型的变更按"兼容性"分级——新增可选字段是兼容变更，改必填字段是破坏变更，破坏变更要同步改所有消费方；第三，跨包类型检查用项目引用或统一 `tsc` 跑全量，防止"每个包各自检查、合起来才报错"。类型包是"团队契约"的载体，它的治理规则，比代码本身更重要。

开严格模式的顺序也有讲究。推荐从 `strictNullChecks` 开始：它的报错最多，但语义最清楚，修完立刻能拦住一半的空值崩溃。然后是 `noImplicitAny`，把所有"猜出来的 any"改成显式类型或 `unknown`。最后再开 `noUncheckedIndexedAccess` 和 `exactOptionalPropertyTypes`，这两个报错虽然烦，但每一条都对应一个真实的运行时错误。一次全开容易让团队产生"严格模式 = 痛苦"的错觉，分批开反而能建立信心。

#### 第二层：类型检查必须成为构建和 CI 的一环

类型检查最大的敌人是"只在本地跑"。Vite 构建默认不做类型检查，esbuild 转译直接丢类型，所以 `pnpm build` 通过不代表类型正确。解决办法是把 `tsc --noEmit` 显式加进构建脚本和 CI。

```json
{
  "scripts": {
    "build": "tsc --noEmit && vite build",
    "typecheck": "tsc --noEmit"
  }
}
```

CI 里加一个独立的 typecheck job，和 lint、test 并行跑。这样类型错误在合并前就暴露，而不是等到部署之后。要注意 `tsc --noEmit` 的退出码：任何类型错误都应该让流水线失败，不要用 `|| true` 吞掉。

比 CI 更早的一道闸门是 pre-push 钩子：`husky` 配合 `lint-staged`，只在暂存文件上跑类型检查，几百毫秒就能拦住低级错误。CI 是兜底，pre-push 是体验，两道闸门都不应该省。还要注意类型检查的"范围"：`tsc --noEmit` 默认检查整个项目，大项目里可以用 `--incremental` 配合 `tsBuildInfoFile` 让重复检查变快，但不要为了速度把检查范围缩小到"只查改动的文件"——那会让跨文件类型错误漏网。

CI 里还可以加一个"类型债度量"：每周统计 `tsc` 报错数量和 `any` 出现次数，画一条趋势线。类型债和代码债一样，不度量就不会改善；有了趋势线，团队能看到"这周新增了多少 any""存量错误在下降还是上升"，把类型质量变成可讨论的数字，而不是某个人对某个人说"你类型写得不好"。

#### 第三层：API 边界——类型和运行时必须一致

类型系统只在编译期存在，运行时拿到的数据不会自带类型。接口返回、`localStorage` 读取、环境变量、WebSocket 消息，这些边界如果只靠 `as` 断言，类型就变成了谎言。

正确的边界模式是"校验后断言"：先用运行时校验（手写守卫或 zod）确认数据形状，再让类型系统接管。手写类型守卫是最轻量的方式：

```ts
function isUser(value: unknown): value is User {
  return typeof value === 'object' && value !== null && 'id' in value && typeof value.id === 'string'
}

const raw: unknown = await fetchUser()
if (!isUser(raw)) throw new Error('invalid user payload')
// 从这里开始，raw 就是 User
```

环境变量同理：不要 `process.env.API_URL as string`，定义一个 `Env` 类型加校验函数，缺失变量在启动时立刻报错，而不是运行到一半才变成 `undefined`。

这里要强调一个容易误会的点：运行时校验和类型系统的关系不是"二选一"，而是"两段接力"。校验函数负责确认"数据真的是这个形状"，类型系统负责在确认之后提供自动补全和编译期保护。用 `as` 跳过校验，等于让第二段在没有第一段的情况下运行；只校验不写类型，又放弃了第二段的所有收益。工程上的标准做法是：外部数据入口统一过一层 `parse` 函数，内部代码只消费已确认的类型。

API 层的类型设计还有一个和"版本演进"相关的细节：接口返回的结构会变，前端和后端的发布节奏不同，怎么保证过渡期不崩？实践中用"宽松解析、严格使用"：解析时允许未知字段（不 reject 多余字段），使用前只依赖"已确认存在的字段"；新增字段先做成可选，等所有消费方升级后再转必填。这条规则让类型和部署节奏解耦，是前后端并行开发的润滑剂。

#### 第四层：构建性能——类型安全不能以慢为代价

项目大了之后，`tsc` 从几秒涨到几分钟，团队就会开始绕开类型检查。性能问题的根源通常是三个：大型第三方类型（特别是 `@types` 依赖树）、深层的工具类型体操、以及每次全量检查没有增量。

解法分三层。第一层是增量：`tsc --noEmit --incremental`，配合 `tsBuildInfoFile`，让重复检查只处理变化的部分。第二层是项目引用（project references）：把代码拆成多个 `tsconfig` 子项目，公共类型单独编译，减少重复检查。第三层是"类型卫生"：避免对大对象反复 `Omit`，避免无界递归类型，避免 `any` 让推断扩散。

项目引用还有一个容易忽略的收益：它强制你梳理模块边界。公共包、业务包、测试包各有一个 `tsconfig`，依赖方向清晰，编译顺序由 `references` 声明，误依赖在编译期就报错。代价是配置文件变多、初次配置有学习成本，但项目超过五万行之后，这笔投入几乎必然回本。

构建性能还有一个"类型卫生"层面的杀手：`as` 和 `any` 会打断类型推断链。一个函数的返回类型如果被 `as` 断言成具体类型，它的调用方就无法从实现推导类型，类型信息在调用链上衰减。反过来，显式的返回类型和干净的推导链，能让 `tsc` 的类型缓存更有效。性能优化不只是配置，也是代码风格——类型卫生做得好的项目，`tsc` 通常不会慢。

### 实战应用

#### 模式速查：工程配置速查表

| 场景        | 配置或做法                           | 收益                          |
| ----------- | ------------------------------------ | ----------------------------- |
| 空值处理    | `strictNullChecks`                   | 强制显式处理 null/undefined   |
| 下标越界    | `noUncheckedIndexedAccess`           | 数组取值变成 `T \| undefined` |
| 构建前校验  | `tsc --noEmit && vite build`         | 构建失败先于部署              |
| CI 类型门禁 | 独立 typecheck job                   | 合并前拦截类型错误            |
| API 数据    | 类型守卫或 zod 校验                  | 类型和运行时一致              |
| 编译提速    | `--incremental` + project references | 增量检查、减少重复编译        |

这张表不是配置清单，是事故清单：每一行都对应一种真实的线上失败。空值没处理，接口在高峰期偶发崩溃；构建不查类型，重构的破坏在部署后才被发现；环境变量靠 `as`，配置缺失时服务带着坏状态运行。落地时建议先做一次"类型体检"：打开 `tsc --noEmit`，把报错按文件统计，前十个文件通常贡献了 80% 的错误，先集中修它们，收益最大。

#### 实战演练：给一个遗留项目做类型化改造

把下篇的知识串成一个可执行的改造方案。假设你接手一个 5 万行、`strict` 未开、`any` 遍地的前端项目，按四步推进。

第一步，立机制：开 CI typecheck job、装 `@typescript-eslint/no-explicit-any` 规则、写"新增代码禁止 any"的团队规范。机制先行，改造才有保障。第二步，开严格开关：先开 `strictNullChecks`，用一周修完报错；再开 `noImplicitAny`，把隐式 any 改成显式类型或 `unknown`。第三步，从边界收口：给 API 层、localStorage、环境变量加 schema 校验和类型守卫，让"外部数据"先安全起来，内部代码的 any 会因为输入变清晰而自然减少。第四步，消化存量：按文件统计 any 数量，从少到多逐文件清理，每周一个文件，三个月清完。

四步的关键是"机制先行、边界优先、存量渐进"——不要第一天就想着把所有 any 清零，那样只会打击士气。类型化改造是一场马拉松，但每一步都有可度量的成果：报错数量、any 数量、CI 绿率。

给这个演练配一张"类型体检清单"，改造过程中逐项打勾：

| 检查项      | 通过标准                                          |
| ----------- | ------------------------------------------------- |
| strict 开关 | `strict: true` 且报错数为 0                       |
| 新增代码    | `no-explicit-any` 规则开启，新增 any 为 0         |
| 外部边界    | API/localStorage/env 全部有校验                   |
| CI 门禁     | typecheck job 必须全绿才能合并                    |
| 类型测试    | 公共契约有 `@ts-expect-error`/`expectTypeOf` 断言 |
| 类型债趋势  | 每月 any 数量下降，报错数不反弹                   |

这张清单的价值是"可验收"：每一项都有明确的通过标准，改造进度不再是"感觉差不多了"，而是"六项里过了四项"。把它贴进项目文档，改造就不会半途而废。

#### 陷阱与正确做法

**陷阱一：strict 开了就再也不管。** 反面案例：打开 `strict` 后报错太多，项目组用 `// @ts-ignore` 压掉，半年后 ignore 注释比业务代码还多。正确做法：开严格模式时固定一个"清理期"，按模块分批修复；`@ts-ignore` 必须带理由注释并限定范围。

**陷阱二：CI 里吞类型错误。** 反面案例：typecheck 命令后面加 `\|\| true`，流水线永远绿，类型烂了三个月没人发现。正确做法：让 `tsc --noEmit` 的退出码直接决定 job 成败；本地 pre-push 钩子再兜一层。

**陷阱三：只信构建不信类型。** 反面案例：用 Vite 构建，以为构建通过就类型安全，结果 `vite build` 根本不查类型。正确做法：构建脚本显式串 `tsc --noEmit`，谁都不能跳过。

**陷阱四：边界数据全靠 as。** 反面案例：接口返回 `as User`、环境变量 `as string`、localStorage `as Config`，运行时字段缺失时崩溃在页面深处。正确做法：所有"外部进入"的数据走校验函数，校验失败快速失败。

**陷阱五：类型检查和构建混在同一个命令里。** 反面案例：`"build": "tsc && vite build"`，类型错误时构建直接中断，开发者的反馈是"构建失败了"而不是"这里有类型错误"，问题定位慢半拍。正确做法：拆成 `typecheck` 和 `build` 两个命令，CI 里分开跑，本地开发时只跑 `typecheck`，反馈又快又准。

**陷阱六：把 any 当"项目历史遗留"放任不管。** 反面案例：`eslint` 规则允许 `any`，code review 没人提，一年后统计发现 `any` 出现 800 次，类型系统形同虚设。正确做法：把 `@typescript-eslint/no-explicit-any` 设为 error，新增 `any` 必须带理由注释；每个季度跑一次 `tsc --noEmit --pretty false` 统计报错趋势，让"类型债"可度量。

**陷阱七：类型测试没人写。** 反面案例：工具类型和公共 API 改了行为，只有 IDE 报错，CI 没有类型断言，回归全靠人工。正确做法：公共类型配 `@ts-expect-error` 和 `expectTypeOf` 断言，跑进 CI；类型测试的覆盖范围对标"公共 API 的契约"，不需要覆盖所有内部推导。

**陷阱八：共享类型包变成垃圾场。** 反面案例：`packages/types` 里堆了所有业务的 interface，几百个类型互相依赖，改名一个字段全站编译失败。正确做法：类型包只放"跨包共享的契约"，业务内部类型留在各自包内；类型包按领域拆分（`@app/api-types`、`@app/domain-types`），而不是一个大杂烩。

### 进阶思考

类型体系落地的最后一步，是让它成为团队默认行为而不是额外负担。三件事值得做：一是在 AGENTS.md 或 CONTRIBUTING 里写明类型规范（公共 API 用 interface、边界必须校验、禁止裸 any）；二是在 code review 里把"新增 any"当 review blocker；三是定期跑一次类型审计，统计 `any` 数量趋势，而不是追求一次性清零。

更进一步的工程方向有三个。一是 monorepo 下的 project references 和类型共享，让多个包之间类型不重复编译。二是 `tsc --watch` + IDE 的 TS Server 调优，减少大型项目的编辑卡顿。三是关注 TypeScript 每年的新特性（const 类型参数、`satisfies`、ECMAScript 装饰器），它们在不断降低类型体操的成本。

到这里，TypeScript 系列三篇讲完了：上篇是底层逻辑，中篇是工具类型，下篇是工程落地。三个层面缺一不可——不懂逻辑写不对，不会工具写不深，不建机制活不长。接下来按 Skill Matrix 的顺序，我们会进入 Python、Go 等语言主题，每篇都保持同样的结构：背景、核心原理、实战应用、进阶思考。

回头看你最初的项目，可能已经被 `as any` 包围。不要急着全面清理——先搭好"类型检查进 CI"的机制，再把新增代码的 `any` 清零，最后用一个季度逐步消化存量。类型的价值不是一天兑现的，但只要闸门立住了，代码库会自己往安全的方向漂移。这是工程和手艺的区别：手艺靠个人，工程靠机制。

如果只允许你记住一件事，记住这句：类型安全是流程属性，不是个人属性。一个人再自律，也挡不住一百次"先 as 一下明天改"；但只要 CI 里有一道 `tsc --noEmit` 的闸门，明天的类型债就不会再增加。这也是本系列从底层逻辑一路讲到工程落地的原因——知道怎么用类型，只是起点。

最后做一个三篇的收束：上篇的底层逻辑让你"看得懂"，中篇的工具类型让你"写得出"，下篇的工程机制让你"活得了"。三者的关系像盖楼——地基（逻辑）、建材（工具）、施工规范（工程），缺一不可。很多团队只学了语法，没有工程规范，楼盖到一半就塌了；也有团队只建规范，开发者看不懂类型，规范形同虚设。TypeScript 的完整实践，是这三层同时在线。

从今天开始，你可以做一个最小的行动：打开 `tsconfig.json`，确认 `strict: true` 和 `noUncheckedIndexedAccess: true`；如果没开，开起来，然后修第一批报错。这个动作花不了半小时，但它会让你的项目从此不再产生新的类型债——这是三篇系列能给你的最后一份礼物。

最后回答一个总被问的问题："花在类型上的时间值吗？"答案是：前期每写十行类型，后期能省一百行调试。类型系统不是开发速度的敌人，它是"把错误留在编译期"的杠杆——一次类型错误在编译期被发现，成本是三十秒；在线上被发现，成本是几个小时加一次事故报告。三篇系列讲完，希望你下次写代码时，第一反应是"这个数据是什么形状"，而不是"先跑起来再说"。

还想补一句关于"工具"的提醒：类型工程的工具在快速进化——`tsc` 的增量编译、语言服务的内存优化、各种类型测试框架，都在降低类型体系的维护成本。不要因为"以前类型很难维护"就拒绝它，2025 年的工具链已经让类型工程从"奢侈品"变成了"日用品"。三篇系列是地基，工具是脚手架，真正的大楼，要靠你在项目里一砖一瓦地盖。
