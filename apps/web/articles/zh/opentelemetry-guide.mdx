### 背景

你的系统有 Prometheus 看指标、ELK 看日志、Jaeger 看链路，三个系统各自工作。出问题时，指标说"支付接口慢了"，日志里有几条错误，链路图却找不到对应的 trace——因为三个系统没有统一的关联 ID，谁也串不起谁。排查一小时，一半时间花在"对时间戳、猜请求"上。

这就是可观测性的"割裂问题"：信号多不等于可观测。OpenTelemetry（简称 OTel）的出现就是为了解决割裂：它定义了一套统一的数据模型（trace、metric、log）、一套标准的采集架构（SDK + Collector）和一个中立的传输协议（OTLP），让所有信号带着同一个 trace ID 流向后端。你选哪个后端（Jaeger、Tempo、Datadog）都可以，数据格式不再被厂商锁定。

这篇文章讲 OTel 的核心机制：三大信号各回答什么问题、SDK 和 Collector 怎么分工、上下文怎么跨服务传播、采样策略怎么设计，最后是一套从零接入的落地步骤。目标不是介绍工具列表，而是让你理解"统一可观测性"到底统一了什么。

先破除一个常见误解：OTel 不是"又一个监控产品"，它不存数据、不画图表，它做的是"数据采集和传输的标准层"。你可以把 OTel 理解成可观测性世界的 HTTP 协议——后端（Tempo、Datadog、自建）是网站，OTel 是浏览器和服务器之间那个统一的协议。这也意味着，选 OTel 不等于选后端，你的存储和展示层仍然要自己决定。

另一个现实是：完全"零成本"接入不存在。自动插桩能覆盖 HTTP、数据库、消息队列等 80% 的场景，但自定义业务打点、异步上下文传播、采样调优仍然需要投入。这篇文章的目的，就是让你知道"成本花在哪、值不值"——大多数团队的可观测性问题，不是工具不够多，而是数据没有统一，OTel 恰好治这个病。

还有一个"谁来做"的组织问题：可观测性建设跨所有服务，没有平台团队牵头，就会变成"每个服务各自为政"（命名不统一、采样不一致、后端五花八门）。推荐的组织方式：一个平台团队负责 Collector、标准、后端，各业务团队负责接入；平台团队出文档和模板，业务团队照模板接入。可观测性是"平台能力"，不是"业务副业"。

本篇结构：三大信号（trace/metric/log）→ 架构（SDK/Collector/OTLP）→ 上下文传播 → 采样 → 落地步骤与陷阱 → 进阶方向。建议按顺序读，架构部分决定了后面所有决策。

还有一个"从哪开始"的建议：先接 trace（链路），因为它最能暴露"服务之间的依赖和瓶颈"；再补 log 关联（trace ID 进日志）；最后完善 metric 和告警。不要第一天就想三件套全上——每加一个信号都要配套"命名规范 + 存储容量 + 告警规则"，一次全上是运维灾难。

### 核心原理

#### 第一层：三大信号——一个请求的三副面孔

OTel 定义三类信号，对应可观测性的三个问题：trace 回答"请求经过了哪些环节、每环节花了多久"，metric 回答"系统整体在什么状态"（QPS、错误率、延迟分布），log 回答"某个具体事件发生了什么"。

它们不是三个独立的系统，而是同一件事的三个视角。一条 trace 告诉你"支付接口花了 2.7 秒，其中 2.5 秒在等第三方"，对应的 metric 告诉你"过去五分钟支付接口的 P99 在涨"，对应的 log 告诉你"这次超时的具体请求参数和错误码"。OTel 让三个视角共享同一个 trace ID，从指标异常点进去，能直接跳到链路和日志——这是"可观测"和"有监控"的分水岭。

数据模型上，trace 由 Span 组成，每个 Span 有名称、开始/结束时间、属性和父 Span 引用；metric 是带时间戳的数值序列，支持 Counter、Gauge、Histogram 三种基本类型；log 是结构化事件，要求时间戳、级别、消息体，并推荐携带 trace/span ID。理解这三个模型，比记 API 重要——所有语言 SDK 都是这三个模型的实现。

三类信号的写入路径也值得分清：trace 和 log 通常由应用 SDK 直接产生，metric 一部分由 SDK 产生、一部分由 Collector 从基础设施（节点、容器）采集。Collector 还支持从 Prometheus exporter、StatsD、Fluent Bit 等已有来源接收数据并转换成统一模型——这意味着存量系统的数据不用推翻重来，可以渐进汇入 OTel 管道。

三大信号还有一个"关系"问题：它们不是三个平行的数据流，而是通过"资源（resource）"和"上下文（context）"关联起来的。同一个服务实例的所有信号共享一组资源属性（服务名、版本、主机），同一条请求的信号共享 trace ID。有了这两层关联，"指标异常 → 点进 trace → 跳到日志"的下钻路径才成立——这是统一可观测性真正的价值。

资源属性（resource attributes）的命名规范值得提前定：服务名（service.name）、版本（service.version）、环境（deployment.environment）、主机（host.name）是四大基础属性。命名不统一（同一个服务叫"order-service"和"order_svc"两个名字），跨服务关联会断。把资源属性的命名规范写进团队标准，和代码规范同等重要。

还有一个"信号质量"的概念：OTel 的数据模型统一了"格式"，但没统一"质量"——span 的命名、属性的语义、日志的结构化程度，都影响数据的可用性。工程上要给"打点质量"定标准：span 名用"动词 + 资源"（`GET /orders/{id}` 而不是 `handleRequest`）、属性用语义约定（semantic conventions）、日志必须有 trace_id。格式统一是第一步，语义统一才是真正可用的可观测性。

三类信号的写入路径也值得分清：trace 和 log 通常由应用 SDK 直接产生，metric 一部分由 SDK 产生、一部分由 Collector 从基础设施（节点、容器）采集。Collector 还支持从 Prometheus exporter、StatsD、Fluent Bit 等已有来源接收数据并转换成统一模型——这意味着存量系统的数据不用推翻重来，可以渐进汇入 OTel 管道。

#### 第二层：架构——SDK 与 Collector 的分工

OTel 的采集架构分两层：应用内的 SDK 负责产生信号，应用外的 Collector 负责接收、处理、转发。SDK 通常用自动插桩（Auto Instrumentation）接入：Java Agent、Python 的 `opentelemetry-instrument`、Node 的 `@opentelemetry/auto-instrumentations-node`，不用改业务代码就能给 HTTP、数据库、消息队列自动打点。

Collector 是整个架构的枢纽：它接收各服务的 OTLP 数据，做批处理、采样、过滤、脱敏，再转发到后端。Collector 存在的意义有两个：一是解耦——应用只认 OTLP，后端怎么换都行；二是集中治理——采样率、脱敏规则、数据丢弃都在 Collector 配，不用逐个服务改。

```yaml
# collector.yaml（简化）
receivers:
  otlp:
    protocols:
      grpc:
      http:
processors:
  batch:
  memory_limiter:
    check_interval: 1s
    limit_percentage: 80
exporters:
  otlp:
    endpoint: tempo:4317
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlp]
```

#### 第三层：上下文传播——trace ID 怎么跨服务走

链路追踪最难的部分不是打点，是"跨服务把同一个 trace ID 传下去"。OTel 用 W3C 标准的 `traceparent` HTTP 头：网关生成 trace ID，传给服务 A，A 调 B 时把 header 透传，B 调 C 时继续透传——整条链上的 Span 全部挂到同一个 trace 下。

传播依赖每个中间环节都"接住并转发"header：HTTP 客户端、消息队列（把 traceparent 写进消息头）、定时任务（手动注入上下文）。最容易断的地方是异步边界：线程池、消息队列、后台任务，如果上下文没有显式传播，trace 会在某个环节"断掉"，链路图从那里开始变成孤岛。

自动插桩解决了 80% 的传播问题（HTTP、DB、消息客户端都有现成实现），剩下的 20%——自定义异步任务、手动构造的 HTTP 调用——需要手动用 `context` API 传播。落地时值得做一次"链路完整性检查"：挑几条典型请求，确认 trace 从入口到数据库全程不断。

传播机制还有一个细节：不是只有 HTTP 才传播。消息队列（Kafka、RabbitMQ）的消息头、gRPC 的 metadata、进程内的线程池切换，都需要显式或自动地传递上下文。判断标准是"链路在哪里断，就在哪里补传播"——一个简单的经验是：把一条请求从用户到数据库的完整调用链画出来，标出每一段用什么机制传 trace ID，缺了哪段，就是将来链路断掉的位置。

还有一个"传播与安全"的细节：traceparent 头是客户端可控的，恶意用户可以伪造 trace ID。不要信任 trace ID 做鉴权或审计——它只用于关联观测数据。服务端可以限制 trace ID 的格式和长度，防止超长 header 的滥用。可观测性和安全是两个系统，不要混在一起。

异步边界的传播还有一个"批处理"的坑：一个批次处理 100 条消息，如果整个批次只带一个 trace ID，100 条消息的耗时全部算在一个 trace 里，无法区分单条慢在哪。正确做法是"每条消息一个子 span"，批次只是父 span——让"批量"和"单条"的观测粒度分开。

还有一个"传播与安全"的细节：traceparent 头是客户端可控的，恶意用户可以伪造 trace ID。不要信任 trace ID 做鉴权或审计——它只用于关联观测数据。服务端可以限制 trace ID 的格式和长度，防止超长 header 的滥用。可观测性和安全是两个系统，不要混在一起。

传播机制还有一个细节：不是只有 HTTP 才传播。消息队列（Kafka、RabbitMQ）的消息头、gRPC 的 metadata、进程内的线程池切换，都需要显式或自动地传递上下文。判断标准是"链路在哪里断，就在哪里补传播"——一个简单的经验是：把一条请求从用户到数据库的完整调用链画出来，标出每一段用什么机制传 trace ID，缺了哪段，就是将来链路断掉的位置。

#### 第四层：采样策略——全量采集是灾难

高流量系统全量采集 trace，存储成本会迅速失控。采样不是"要不要做"的问题，而是"怎么做"的问题。OTel 支持两种采样：头部采样（head sampling）在请求入口按固定比例决定采不采，简单但会漏掉"少数慢请求"；尾部采样（tail sampling）在 Collector 里等请求结束后按特征决定，能精准保留错误和慢请求，但需要缓存和延迟。

工程上的推荐组合：入口按 10% 固定采样，错误和慢请求通过尾部采样规则提高到 100% 保留；指标和日志不全量采样（指标按聚合、日志按级别过滤）。采样的目标是"保留足够多的异常样本，控制总量"——你的目标是排障，不是收集全宇宙的 trace。

采样还有一个和存储成本同样重要的维度：采样影响延迟分析的准确性。按 10% 采样后，P99 延迟的估算会带明显误差——你看到的"慢请求"可能只是采样噪声。解法是"低采样 + 直方图兜底"：trace 低比例采样用于深挖单请求，metric 用直方图全量统计延迟分布，两者互补，既省钱又不失真。

采样的工程治理还要考虑"按服务差异化"：核心服务（支付、登录）采样率高一些（比如 50%），边缘服务（日志、推荐）低一些（1%）。同一个服务里，按路径差异化——关键接口全采，静态接口低采。采样策略是"数据价值"的显式表达，应该由业务团队和平台团队一起定，而不是统一一个数字。

采样还有一个"多后端"的协调问题：如果 trace 进一个后端、log 进另一个后端，两者的采样策略不一致会导致"有 log 没 trace、有 trace 没 log"。解法是让采样决策统一（Collector 决定），或者接受"采样不一致"并把它设计进查询路径（先按 trace 查，缺失的用 log 兜底）。

最后补一个"采样与 SLA"的关系：采样率不是随意定的，它和你的排障承诺挂钩——"承诺任何错误都能查到 trace"，采样率就必须保证错误全采；"只承诺抽样排查"，低采样就够。把采样率写进可观测性 SLA，团队对"能不能查到那次请求"有明确预期，而不是事后才发现"被采掉了"。

采样还有一个和存储成本同样重要的维度：采样影响延迟分析的准确性。按 10% 采样后，P99 延迟的估算会带明显误差——你看到的"慢请求"可能只是采样噪声。解法是"低采样 + 直方图兜底"：trace 低比例采样用于深挖单请求，metric 用直方图全量统计延迟分布，两者互补，既省钱又不失真。

### 实战应用

#### 模式速查：从零接入的落地步骤

| 步骤            | 动作                              | 验证                   |
| --------------- | --------------------------------- | ---------------------- |
| 1. 起 Collector | 部署 OTel Collector，配好导出后端 | Collector 健康检查通过 |
| 2. 接一个服务   | 自动插桩 + OTLP 导出              | 后端能看到 trace       |
| 3. 打通传播     | 确认 HTTP header 透传             | 跨服务链路完整         |
| 4. 加日志关联   | 日志 SDK 注入 trace ID            | 日志能跳 trace         |
| 5. 配采样       | 入口固定采样 + 异常全采           | 存储量可控             |
| 6. 建告警       | 指标告警 + 链路下钻               | 告警能追到根因         |

#### 陷阱与正确做法

**陷阱一：只接 trace 不接 log。** 反面案例：链路图画得漂亮，但 span 里没有业务上下文，慢请求查不到参数和错误。正确做法：trace、metric、log 一起接，至少让日志带上 trace ID，形成"指标 → 链路 → 日志"的下钻路径。

**陷阱二：采样率乱设。** 反面案例：全部服务 100% 采集，存储爆掉后一刀切到 1%，错误请求也全丢了。正确做法：分层采样——正常流量低比例、错误和慢请求高比例；采样决策在 Collector 统一做，不要每个服务各设各的。

**陷阱三：Collector 单点部署。** 反面案例：一个 Collector 实例扛所有流量，它挂了全站可观测性消失。正确做法：Collector 多副本 + 负载均衡，或 sidecar 模式（每节点一个）；Collector 的数据丢失要有降级策略（本地队列 + 重试）。

**陷阱四：在代码里硬编码后端地址和密钥。** 反面案例：OTLP endpoint 和 token 写进环境变量但没脱敏，日志里泄露。正确做法：Collector 配置走配置管理，密钥走 Secret；应用只配置本地的 OTLP 地址（通常是 localhost），后端地址统一在 Collector 层管理。

**陷阱五：异步边界不传播上下文。** 反面案例：消息消费者处理消息时没有继承生产者的 trace ID，整条业务链路断成两截。正确做法：消息头携带 traceparent，消费端用 `context` API 恢复；后台任务同理，把上下文从触发点传入任务。

**陷阱六：把敏感数据打进 span 属性。** 反面案例：span 里记录完整 SQL、用户邮箱、token，日志系统里明文可查，合规审计时全部暴露。正确做法：属性只放必要且脱敏的数据（用户 ID 而不是邮箱、SQL 摘要而不是全文）；Collector 配置属性过滤器，统一做脱敏，防止某个服务漏配。

**陷阱七：后端容量没跟着数据量走。** 反面案例：接入一个月后 trace 量翻倍，后端磁盘打满，采集直接被拒，可观测性在事故当天失效。正确做法：上线前按预估 QPS × 采样率 × 平均 span 数估算存储量，给后端配置容量告警；用保留期策略（trace 保留 7 天、指标保留 30 天）控制总成本。

### 进阶思考

OTel 的长期愿景是"可观测性的标准化"：就像 HTTP 统一了 Web 协议，OTLp 统一了遥测数据的采集和传输。对团队来说，这意味着可观测性投入不再绑定某个厂商——今天用 Tempo，明天换 Datadog，SDK 和打点代码一行不用改。

值得深入的方向有三个。一是持续剖析（Continuous Profiling）：把 CPU/内存 profiling 也变成常驻信号，和 trace 关联，回答"这段慢代码到底慢在哪一行"；OTel 生态正在把它纳入统一模型。二是 eBPF 零侵入观测：不需要改应用代码就能看到网络、系统调用级别的数据，补上应用层探针的盲区，适合"接不了 SDK"的存量系统。三是和告警体系结合：把"可观测性数据"变成"告警上下文"，告警消息里直接带 trace 链接和指标截图，缩短 MTTR。

学习路径：先用官方 demo（`opentelemetry-demo`）跑起一个带 trace 的微服务示例，理解数据流；再给你项目的一个服务接自动插桩，确认链路完整；最后配 Collector 和采样，把存储量控制在预算内。可观测性的建设是渐进的——从一个服务开始，把链路打通，再逐步扩大覆盖，比一次全量接入靠谱得多。

最后补一个组织层面的建议：可观测性需要"负责人"而不是"志愿者"。全链路打通涉及每个服务的改动和协作，没有明确责任人，事情会停在"demo 能跑"阶段。建议由一个平台团队负责 Collector 和标准（命名规范、采样策略、脱敏规则），各业务团队负责自己服务的接入；标准的统一比工具的选型更难，也更重要——工具可以换，标准换了就要重新打点。

结语：OTel 的价值不在"多一个工具"，而在"少一层重复"。以前每个后端厂商都有自己的 SDK 和格式，换厂商等于重新打点；OTel 之后，打点一次，后端随便换。对团队来说，这意味着可观测性投入变成"资产"而不是"负债"——投资 OTel 是在投资数据的可迁移性。可观测性不是监控的升级，是数据基础设施的一部分，这句话值得每个平台团队记住。

最后给一个"验收"标准：你的可观测性体系"可用"的标志不是"面板上有数据"，而是三个问题的答案——出问题时，能在 5 分钟内定位到服务/环节/根因吗？告警消息里能直接跳转链路和日志吗？换后端厂商时，需要改业务代码吗？三个答案都是"能"，说明 OTel 的投入兑现了；任何一个是"不能"，就还有一段路要走。

行动清单：本周用一个服务接自动插桩，确认跨服务链路完整；下周把日志和 trace 关联（trace_id 进日志）；月底前配好分层采样和容量监控。可观测性的建设没有终点，但第一步必须是"让一条真实请求的链路从头到尾可追踪"。

最后补一段"告警的最后一公里"：可观测性的终点不是"能看到"，而是"能及时知道并快速定位"——告警规则要基于 SLO（错误率、延迟、可用性），而不是"CPU 超 80%"这种噪音；告警消息要带"链路链接 + 日志查询 + 最近变更"三个上下文。一条好的告警，是"事件 + 上下文 + 入口"的组合，让值班的人不用打开三个系统才能开始排查。把告警质量当成可观测性的验收标准，比"数据多全"更重要。

再补一句全文的收束：OTel 的统一、三大信号的关联、上下文的传播、采样的治理——这套体系的最终目的只有一个：让"系统为什么慢了/挂了/错了"成为一个可以在几分钟内回答的问题。可观测性不是监控面板的堆砌，而是一种"系统可被提问"的能力。你为这个能力做的每一分投入，都会在下一个凌晨三点的告警里连本带利地还给你。
