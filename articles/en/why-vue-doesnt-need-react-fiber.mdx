User types "r" — half a second — "r" appears. Types "e" — another pause. Your CPU is pinned at 100%. You've checked the network tab, profiled the JavaScript execution, ruled out infinite loops. The code is correct. The data lives in memory. But every keystroke lands like a telegram from 1920.

You're using the latest React. You've followed every best practice. useMemo here. useCallback there. React.memo wrapped around everything like bubble wrap. Still. Lagging.

"Vue doesn't need Fiber."

You nod. You've heard these words before. You kind of know what they mean. But when you stop to actually think about it — you realize you don't know what Fiber is. Or why one framework needs it and the other doesn't. Or whether "not needing Fiber" is a flex or a confession.

## Your page isn't slow. It's blocked.

Let's start from zero. Why is that search box lagging?

Your first guess: "The network requests are too slow."

Nope. The data came back ages ago. It's sitting in memory. You're just filtering and rendering.

Second guess: "Infinite loop in a useEffect? Wrong dependency array?"

Nope. React Profiler shows everything completing. Render functions return correct values. DOM updates correctly.

"So what the fuck is lagging?"

The browser's main thread is choked by a single massive task. And your framework is the one that put it there.

Here's how the browser works. It has a main thread. One. Single. Like a maître d' at a packed restaurant — this one person handles everything. Guests arriving (DOM events). People asking about the menu (user input). The kitchen calling out orders (rendering). The bar running tabs (animation frames). The phone ringing (network callbacks).

All of it queues up. One line. One worker.

Normally, each task is tiny. A click fires, an event handler runs, state updates, some DOM changes — maybe 3 milliseconds total. The queue moves so fast you never perceive it. You think things are happening simultaneously — but they're just dequeuing faster than your eye can track.

Then a monster task lands. A 12-course tasting menu with paired wines. Five hundred individual operations. The maître d' drops everything.

During those 500 operations:

- Someone rings the bell at the entrance — queued.
- Someone at the counter asks about a bill — queued.
- The kitchen calls out the next course — queued.
- The phone rings — queued.

Everything piles up behind this one behemoth.

For the user, those 500 operations might take 200 milliseconds. Human perception of delay kicks in around 100ms. Past 200ms, you feel it. Past 500ms, the page feels dead.

This is main thread blocking. And old React — pre-Fiber React — was a virtuoso at producing it.

Old React's logic was brutally simple. State changed? Re-render the entire component tree. Run every render function. Build a brand new virtual DOM from scratch. Diff it against the old one — node by node, prop by prop. Find every difference. Apply to the real DOM. All in one synchronous, unbroken sweep. No checkpoints.

Ten components on the page? Fine. Five milliseconds. Five hundred components? You're going to feel it. 500 render calls, 500 virtual nodes created, 500 nodes diffed. Maybe 150 milliseconds of dead silence from your page.

"But virtual DOM diffing is already an optimization," you say. "It's faster than touching the real DOM."

Correct. But here's the distinction everyone misses: optimizing total work and optimizing blocking duration are two completely different problems.

React's virtual DOM diff reduces total work — fewer real DOM operations, batched updates, minimal change sets. Great. But no matter how small the total work becomes, if it all executes synchronously in one shot on the main thread, it blocks. If the block exceeds human perception threshold, the user feels lag.

So React's real problem isn't "how do we make the diff faster." It's "how do we stop the diff from monopolizing the main thread." First question is about algorithm. Second is about scheduling. Different beasts entirely.

That's why Fiber exists.

## What Fiber actually does: moving furniture, piece by piece

In 2017, the React team released a new architecture called Fiber. Not an incremental tweak. A near-total rewrite of the reconciliation engine.

Why "Fiber"? Like dietary fiber. Like optical fiber. Something you can split into thinner and thinner strands without losing the whole.

Before Fiber, React's rendering was monolithic. One indivisible chunk. Like a moving company that insists on carrying the entire sofa in one trip. Can't set it down mid-haul — the sofa tips. If someone calls your name, they wait until the sofa reaches the truck.

Fiber disassembles the sofa.

Carry the cushions first. Set them down. Drink water. Check your phone. Carry the armrests. Someone knocks on the door — answer it, come back. Carry the frame. Now the sofa is on the truck. Piece by piece. Interruptibly.

In technical terms: Fiber chops a single render cycle into countless micro-tasks. Each micro-task executes in 1-2 milliseconds. After every micro-task, React pauses and asks the browser: "Anything urgent? User click something?"

If yes, React shelves the current rendering, handles the user interaction, then returns to the exact point where it paused and resumes.

Three mechanisms make this possible.

---

**Time slicing** is the easiest to grasp.

Watching a two-hour movie. Old React: you must watch in one sitting. No pausing. No bathroom breaks. No phone calls. Your body is the screen's hostage until credits roll.

Fiber: the movie is split into 30-second chunks. After each chunk, the player pauses. "Continue? Or check on something else first?" You can walk away. Handle an interruption. Return to the exact same second of the film.

React is the player. Each slice is 1-2 milliseconds. After each slice, React checks: "Should I yield the main thread?"

**Priority scheduling** is an ER triage system.

Patient clutching his chest? Straight to the front. Patient with a sprained ankle? Wait your turn. Everyone agrees — priority hierarchies are obvious when lives are on the line.

React marks user clicks and keystrokes as "chest pain" — max priority. Background rendering, data prefetching — those are "sprained ankle." Low priority. High priority always preempts low.

**Interruptible rendering** is the natural consequence. If work is chunked and prioritized, pausing and resuming becomes the default behavior.

---

But behind all of this is a data structure choice that matters more than it first appears.

React abandoned tree-based traversal of the component hierarchy. It switched to a **linked list**.

Why? Trees are typically traversed via recursion. And recursion has a fatal limitation: once you enter a recursive call, you cannot stop until the entire call stack unwinds. There is no "pause halfway through a recursion." The stack must complete.

Linked list traversal doesn't have this problem. You maintain a single variable — a pointer to the current node. Want to pause? Save the pointer. Walk away. Want to resume? Load the pointer. Keep going.

In Fiber, every component becomes a Fiber node with three pointers:

```javascript
const fiber = {
  type: 'div', // component type
  props: { className: 'container' },
  child: childFiber, // pointer to first child
  sibling: nextFiber, // pointer to next sibling
  parent: parentFiber, // pointer back to parent
}
```

`child`, `sibling`, `parent`. Three pointers transform a hierarchical tree into a flat, walkable path. Traversal: follow `child` down, `sibling` across, `parent` up. At any point, save the current Fiber, walk away, resume from that exact Fiber later.

This is like reading a book. Recursion is "I must finish this chapter in one sitting." The linked list is "I'm on page 47, paragraph 3. Let me bookmark it and pick it up tomorrow."

This bookmark mechanism is the foundation of everything Fiber offers. Without it, time slicing is meaningless — you can slice, but you can't resume. Without it, priorities can't interrupt rendering — there's no way to save your place.

Above the linked list sits the Scheduler. It maintains the priority queue — the ER triage system. It pulls tasks during browser idle moments, executes micro-chunks, and checks for new high-priority work after each chunk.

Fiber operates in two distinct phases:

**The Render phase** (also called Reconciliation). This phase is interruptible. React walks the Fiber tree, compares old and new nodes, identifies what needs updating. All computation here is "pure" — no side effects. It can be abandoned at any moment and restarted without consequences.

**The Commit phase.** This phase is NOT interruptible. React takes all the changes calculated during the Render phase and applies them to the real DOM in one shot. Real DOM manipulation can't be halfway done — the user would see a broken UI. Good news: the Commit phase is usually very fast because the Render phase already figured out the exact minimal change set.

Put the heavy work in the interruptible phase, keep the lightweight work in the non-interruptible phase — that's the complete Fiber secret to perceived performance.

## The gifts Fiber brought along

Fiber was built to fix jank. But the interruptibility it introduced unlocked two capabilities nobody planned for: **Suspense** and **concurrent mode**.

Suspense tackles the "waiting for async data" problem.

Before Suspense, every data-fetching component looked like this:

```jsx
function ProductPage({ productId }) {
  const [product, setProduct] = useState(null)
  const [loading, setLoading] = useState(true)
  const [error, setError] = useState(null)

  useEffect(() => {
    setLoading(true)
    fetchProduct(productId)
      .then(setProduct)
      .catch(setError)
      .finally(() => setLoading(false))
  }, [productId])

  if (loading) return <LoadingSpinner />
  if (error) return <ErrorDisplay error={error} />
  return <ProductDetails product={product} />
}
```

Loading state. Error state. Data-ready state. Manual juggling in every async component. Plus waterfall loading — child data arrives but parent data hasn't, so nothing renders anyway.

Suspense inverts this entirely:

```jsx
<Suspense fallback={<LoadingSpinner />}>
  <ProductDetails id={productId} />
  <RelatedProducts id={productId} />
</Suspense>
```

The contract: "Show the spinner until everything inside this boundary resolves. Then swap in real content, all at once."

The wild part: if the user navigates away before data loads, React can cancel in-flight requests. No wasted bandwidth. No wasted renders. This cancellation works because Fiber can always interrupt — if a render branch is abandoned, Fiber just stops processing it.

**Concurrent mode** goes further. It lets React prepare multiple UI versions simultaneously.

User types "react tutorial" — fourteen keystrokes. Old React: fourteen full renders. Each render can block the next keystroke's input handling. Typing feels like wading through wet concrete.

Concurrent mode: user types "r" — React starts rendering results for "r," marked low priority. User types "e" — React abandons "r" render, starts "re." User types "a" — abandons "re," starts "rea."

Throughout, the input never stutters because rendering never actually blocks it. React discards intermediate renders like a worker who drops half-finished tasks the moment a new instruction arrives. User stops. React renders the final query.

`startTransition` is the API. `useDeferredValue` is its companion — it creates a "deferred version" of a value. The immediate version updates instantly for input responsiveness. The deferred version lags behind for rendering. The input always feels instant. The results can take their time.

```jsx
import { useState, startTransition } from 'react'

function SearchResults({ query }) {
  const [results, setResults] = useState([])

  const handleSearch = (newQuery) => {
    startTransition(() => {
      fetchResults(newQuery).then(setResults)
    })
  }

  return (
    <div>
      <input onChange={(e) => handleSearch(e.target.value)} />
      <SlowList results={results} />
    </div>
  )
}
```

`startTransition` tells React: "This can wait. User input takes priority."

React 19 added: the **auto-optimizing compiler**.

Before React 19, you manually decided when to use `useMemo`, `useCallback`, `React.memo`. The APIs were simple. Knowing _when_ — that was the nightmare. Thousands of developers spent countless hours debating whether a particular memoization actually helped.

React Compiler ends the debate. It analyzes your JavaScript at build time and inserts caching automatically. The rules are straightforward: if a variable's value comes entirely from props or state and isn't mutated locally — cache it. If a function's return value depends only on props or state and has no side effects — cache it. As long as you follow React's basic rules (no direct state mutation, no raw DOM manipulation), the compiler can safely auto-optimize.

```jsx
// What you write (React 19)
function ProductList({ products, onSelect }) {
  const sorted = [...products].sort((a, b) => b.price - a.price)
  const handleSelect = (p) => onSelect(p)

  return sorted.map((p) => <ProductItem key={p.id} product={p} onSelect={handleSelect} />)
}

// What the compiler effectively produces:
// function ProductList({ products, onSelect }) {
//   const sorted = useMemo(() => [...products].sort(...), [products])
//   const handleSelect = useCallback((p) => onSelect(p), [onSelect])
//   ...
// }
```

No more "should I memoize this" existential crises.

## Here's what Fiber absolutely does NOT do

This is the part almost everyone gets wrong. It's also the key to understanding why Vue doesn't need Fiber.

Fiber does not make rendering faster.

Sit with this. Fiber never speeds up rendering. The total amount of work — render functions called, virtual nodes created and diffed, real DOM updated — that total doesn't shrink. Sometimes it grows slightly, because chunking and context-switching have overhead.

Fiber changes not how much work there is. Fiber changes whether that work can be interrupted.

Construction site. 100 bricks. East end to west end.

**Without Fiber**: carry all 100 in one trip. No setting them down. No water. No phone. Someone calls your name — they wait. If that someone is a user clicking save — frozen page.

**With Fiber**: carry 5 at a time. After each batch, stop. Drink water. Check for interruptions. Carry the next 5. Total brick-moving time? Roughly identical. Maybe a tiny bit longer due to pause-and-resume overhead.

The difference: between any two batches, you're available. Someone calls — you respond within seconds. The user never feels the page is dead.

Fiber's value: not speed. Responsiveness. Not lower total work. Lower blocking probability.

Now flip the scenario.

What if you only need to move 3 bricks?

Three bricks fit in one hand. No chunking needed. No pauses. You walk, done in 2 seconds. Even if someone calls at the exact wrong moment — 2 seconds is imperceptible.

Building an elaborate "chunk-and-check-and-bookmark" system for 3 bricks is pure waste. It adds overhead. It solves a problem you don't have.

If your rendering workloads are already small enough that they never block the main thread longer than human perception threshold — Fiber is pointless.

This is the entire thesis of Vue's architecture. Everything that follows flows from this one insight.

## Vue's approach: kill the problem at the source

React says: "Rendering might be heavy, so let's make it interruptible."

Vue says: "Let's make rendering so light it never needs interrupting."

Sounds like marketing. But it's backed by a concrete mechanism: the reactive dependency graph.

The apartment building analogy, told properly.

20-story building. 200 units. Bulletin board in the lobby.

**React's way:**

Manager posts a notice. Gets on the PA: "ATTENTION ALL RESIDENTS. BULLETIN BOARD UPDATED. PLEASE COME CHECK FOR RELEVANT INFORMATION."

200 people troop downstairs. Each reads the notice. Each decides: "Does this affect me?" 170 find it doesn't — wasted a trip, wasted the reading. 30 find relevant info — take action.

The manager (setState) doesn't track who cares about what. The manager shouts. The residents (components) each run their own investigation (render → diff → decide).

**Vue's way:**

On move-in day, Vue knocks on every door with a clipboard.

"What kinds of bulletin board announcements interest you?"

Resident A: "I care about 3rd floor renovation notices. And 5th floor lost items."
"Noted."

Resident B: "I care about power outage announcements."
"Noted."

Vue builds a comprehensive interest map.

Week later, a 3rd floor renovation notice goes up. Vue checks the map. Only Resident A cares. Vue knocks on Resident A's door alone: "Renovation notice on 3rd floor. Check it when you can."

Resident B never knows anything happened. No trip downstairs. No reading. Zero overhead — it wasn't their concern.

In Vue's world: the interest map = reactive dependency graph. Knocking on one door = targeted component update. Never knowing = unaffected components untouched.

This is why Vue's update cost is inherently low. 100 components on the page. Only 2 depend on the data that changed. Vue updates those 2. The other 98 are _never touched_. Their render functions don't fire. Their virtual DOM isn't created.

React, by contrast, re-runs all 100 and lets them figure it out themselves.

Vue doesn't need Fiber — not because it secretly implemented an alternative interruption mechanism. It doesn't need Fiber because it never generates workloads heavy enough to require interruption. The problem Fiber solves simply doesn't arise in Vue's architecture.

## Show me the code: how both handle a single update

Analogies are nice. But looking at actual code makes the difference sharper.

A simple state: a user object with name and age. Two spots on the page — one displays name, one displays age.

**React version:**

```jsx
function UserProfile() {
  const [user, setUser] = useState({ name: 'Alice', age: 25 })

  const updateAge = () => {
    setUser({ ...user, age: user.age + 1 })
  }

  return (
    <div>
      <NameDisplay name={user.name} /> {/* only depends on name */}
      <AgeDisplay age={user.age} /> {/* only depends on age */}
      <button onClick={updateAge}>Age +1</button>
    </div>
  )
}

const NameDisplay = React.memo(({ name }) => {
  console.log('NameDisplay rendered')
  return <span>{name}</span>
})

const AgeDisplay = React.memo(({ age }) => {
  console.log('AgeDisplay rendered')
  return <span>{age}</span>
})
```

You click "Age +1". `user.age` changes. New user object. UserProfile re-renders.

NameDisplay receives `name` — still `'Alice'`. React.memo's shallow comparison passes. NameDisplay skips rendering. AgeDisplay receives new `age`. Renders.

Seems fine. But notice: **you had to manually add React.memo to NameDisplay to prevent its unnecessary re-render.** If you forgot, NameDisplay would render anyway — producing an identical virtual DOM, which the diff would then discard. Render wasted.

React 19's compiler auto-adds the memo. But the underlying mechanism hasn't changed: React doesn't _know_ that NameDisplay doesn't depend on age. It infers it by comparing props.

**Vue version:**

```vue
<script setup>
import { reactive } from 'vue'

const user = reactive({ name: 'Alice', age: 25 })

const updateAge = () => {
  user.age++ // Direct mutation. No new object needed.
}
</script>

<template>
  <div>
    <span>{{ user.name }}</span>
    <!-- only tracked against name -->
    <span>{{ user.age }}</span>
    <!-- only tracked against age -->
    <button @click="updateAge">Age +1</button>
  </div>
</template>
```

You click "Age +1". `user.age++` triggers Proxy set trap.

Vue checks its dependency graph: only `{{ user.age }}` previously read `age`. Vue updates just that one `<span>`. The `{{ user.name }}` binding is never even considered — needs no React.memo, no compiler, nothing.

Vue precisely _knows_ that the name binding doesn't depend on age — because it recorded the dependency when `{{ user.name }}` was first read. It doesn't infer. It knows.

This is why Vue's update cost is naturally low. Not because it renders faster. Because it renders less.

## Push and Pull: the two words that explain everything

If you only remember two words from this entire article, make them these. Push and Pull.

**React is Pull.**

Data changes. The framework itself doesn't know which components need updating. Its philosophy: "I don't know who depends on what. So I'll wake everyone up and let them figure it out."

Company-wide Slack message. HR posts a policy update. 500 people get pinged. 500 open the link. 480 find it doesn't apply to them. But they already spent the time reading.

Pull mode: data producers don't track consumers. Consumers actively "pull" what they need. The system doesn't push — it broadcasts "something changed" and lets consumers pull.

**Upside of Pull**: simpler implementation. No dependency graph to maintain. Your component is a pure function — state and props in, UI out. State changed? Re-call the function. Functional. Elegant. This is React's DNA.

**Downside of Pull**: massive potential for wasted work. Running 500 components when only 3 changed is wasteful. Enough waste on a complex page blocks the main thread — which is why React needs Fiber. Fiber doesn't eliminate the waste. Fiber schedules around it.

**Vue is Push.**

Data changes. The framework knows exactly who needs to be notified. It actively pushes updates to the affected components. Unaffected components are never interrupted.

Smart notification system. Policy update goes only to relevant departments. Everyone else keeps working.

Push mode: the system tracks who depends on what. When data changes, the system pushes notifications precisely.

**Upside of Push**: extremely low waste. Only components that actually depend on changed data get updated. Light rendering means low blocking probability means no need for Fiber.

**Downside of Push**: implementation complexity. You need a reactive system that silently intercepts every property read (recording who read what) and every property write (notifying who depends on it). Proxy makes this easier in Vue 3, but it's still a non-trivial subsystem.

A real-world analogy to make it stick:

**Pull mode** is a bulletin board in the office kitchen. Want to know if anything relevant was posted? Walk over and check. Some people walk over, read everything, find nothing — wasted trip. But the benefit: HR doesn't need to know everyone's interests.

**Push mode** is phone notifications. Only messages that concern you trigger a ping. You never need to check proactively. But the prerequisite: the system needs to know who you are and what you care about. That's an additional registration system.

**The big-picture insight:**

React chose "simple implementation." It bet that the functional model — re-run pure functions on every state change — is conceptually elegant and "fast enough." Then it poured enormous engineering effort (Fiber, Diff optimization, React Compiler) into making "fast enough" actually fast enough.

Vue chose "optimal runtime performance." It bet that a capable reactive system can eliminate wasteful work at the source. Then it poured enormous engineering effort (Proxy reactivity, compile-time optimization, dependency graph maintenance) into making that system invisible to developers.

Two paths. React goes from simple to complex. Vue goes from complex to simple. In typical business applications, they arrive at performance levels so close that users can't tell them apart.

## React's "state management trap" — and what it tells you

Here's a real-world confusion that trips up nearly every React developer at some point. It's related to Fiber but not directly — worth its own section.

New React developers often think:

"Wait — if I store a big state object at the root component and pass props down, and a component at level 5 changes a tiny nested property inside that state... doesn't that trigger a re-render of the ENTIRE tree from the root? That's terrifying."

This fear leads people to:

- Scatter state across dozens of child components (making state a nightmare to reason about)
- Wrap everything in React.memo indiscriminately (adding complexity without real benefit)
- Jump to third-party state libraries thinking they'll "avoid" re-renders

**The truth is more nuanced.**

React's re-renders are component-level, not "whole tree." And there are mechanisms controlling which components actually need to re-render.

First: when state changes, React does walk down from the component that owns that state. But whether a child re-renders depends on whether its props changed. By default, even with identical props, React will still re-render children (this is a known React behavior) — but the virtual DOM they produce will be identical. The diff phase will then find "nothing changed" and skip real DOM operations.

`React.memo` prevents those unnecessary re-renders — it makes a component skip rendering when props haven't changed. React 19's compiler automates this.

Second, and more importantly: **selectors**.

If you use Zustand, Redux, or similar state libraries, what triggers a re-render isn't "the store changed." It's "the value returned by your selector changed."

```javascript
// ❌ Bad: selecting too much
function PostItem() {
  const { posts, comments, user, settings } = useStore()
  // Any field change triggers re-render, even if PostItem only shows posts
}

// ✅ Good: precise selection
function PostItem({ postId }) {
  const post = useStore((state) => state.posts.find((p) => p.id === postId))
  // Only re-renders when this specific post changes
}
```

React does NOT re-render the entire tree just because state lives at the root. It re-renders the components whose selected data changed. The precision of your selection determines how much re-rendering happens.

And Vue? Vue never asks you to think about selectors. Proxy records reads at the individual property level — "this component read `user.age`" — and notifies with that granularity. You get precision by default. You don't have to craft selectors. The framework is already the most precise selector possible.

## Virtual DOM: same term, opposite approaches

React and Vue both claim to use a "virtual DOM." But that's like two people saying "I cook" — one is making dinner, the other is running a pottery kiln. Same word. Completely different activity.

React's virtual DOM is **global reconciliation**.

State changed? Create an entirely new virtual DOM tree from scratch. Diff it against the old one — every node, every prop, every child list. Find every difference. Apply changes to the real DOM.

Sounds brute-force. But it's smart brute-force. Naive tree diffing is O(n³) — n nodes in each tree, each must find a match in the other, then handle moves. React cuts it to O(n) with two heuristics:

**Heuristic one: different element types imply entirely different subtrees.** `<div>` to `<ul>`? React doesn't even look at the children. Tears down the whole subtree. Rebuilds. This assumption isn't always correct, but in practice it almost never harms. Think about it — if a div turns into a ul, the internal structure is almost certainly completely different. Continuing to deep-diff would be wasteful.

**Heuristic two: `key` props identify list items across reorders.** Without keys, React guesses by position. With keys, React tracks identity. A node with `key="abc"` that moved from position 3 to position 7 — same node. Just repositioned. No destruction. No recreation.

Two heuristics drop diffing from O(n³) to O(n). Brilliant engineering. But O(n) is still linear. 1000 nodes, only 1 changed — React walks all 1000 to confirm "only 1 changed."

Vue's virtual DOM is **surgical precision**.

The reactive system already knows whose data changed. Vue goes directly to that component. Does a local, scoped update inside that one component. Applies to the DOM. Other components? Their virtual DOM subtrees are never even created.

Consider a dashboard component.

React: main panel's counter goes from 5 to 6. React re-renders the entire dashboard (sidebar, header, footer, main panel). Creates a new virtual DOM for everything. Starts diffing from the root. Sidebar — no changes, skip. Header — no changes, skip. Footer — no changes, skip. Finds the counter. Updates the DOM.

Vue: same counter, 5 to 6. Vue's reactive graph says: only the counter display component depends on this value. Goes directly there. Updates the DOM binding. Sidebar, header, footer — never even considered.

Both correctly updated the counter. React walked a whole tree. Vue touched one node.

And Vue has compile-time optimization. Its templates are compiled at build time. The compiler separates **static** (never-changing HTML) from **dynamic** (data bindings that might update):

```vue
<template>
  <div class="container">
    <h1>Product List</h1>
    <!-- ^^ Static. Created once. Reused forever. -->
    <div v-for="p in products" :key="p.id">
      {{ p.name }}: {{ p.price }}
      <!-- ^^ Dynamic. Only these bindings are tracked. -->
    </div>
  </div>
</template>
```

The compiled output hoists `<h1>Product List</h1>` — instantiated once, never touched again. Only the `v-for` loop and its dynamic bindings are continuously tracked. React's JSX compiles to `createElement` calls — runtime work every single time, even when the output is identical.

These two compiler approaches are converging, slowly. React Compiler analyzes runtime behavior patterns — "which values should be cached?" Vue's template compiler analyzes static structure — "which code paths never need re-execution?" The former is more flexible, handling complex JSX logic. The latter is more precise, outright skipping static sections. Both head toward the same destination: handle everything predictable at compile time, leaving only the truly dynamic for runtime.

## Why React is obsessed with immutability

This isn't directly about Fiber. But understanding it rounds out the picture.

Why can't you just do `user.age = 26` in React? Why the eternal `setUser({...user, age: 26})`?

Because React detects change through **reference identity**:

```javascript
// React's internal logic, simplified
if (Object.is(oldState, newState)) {
  // Same reference → "nothing changed" → skip render
} else {
  // Different reference → "something changed" → re-render
}
```

This is a direct consequence of the Pull model. React can't intercept `user.age = 26`. It has no idea what happened inside your object. The only tool it has: "Is the reference new? Yes or no?"

If you mutate `user.age = 26` directly, `user` is still the same object, same reference. `Object.is(user, user)` → `true` → "nothing changed" → no re-render. You changed the value. The page didn't change. Bug.

So immutability isn't just React being opinionated about functional programming — though that's part of the story. It's a practical necessity of the Pull model. Without the ability to detect internal changes, you need the wrapper to be different: a fresh reference.

There's another layer too: immutability naturally supports undo/redo and time-travel debugging. Every `setState` produces a new object. The old one still exists. Store them in an array — you can jump to any historical state anytime. Redux DevTools' time-travel debugging works precisely because of this property.

Mutable objects overwrite their history. You can only see the current state — all intermediate steps are gone.

Vue doesn't need this. Vue's Proxy hooks catch every property access and mutation:

```javascript
state.user.age = 26
// Proxy set trap fires instantly. Vue knows:
//  1. user.age: 25 → 26
//  2. Components A and B previously read user.age
//  3. Notify A and B → update their DOM bindings
```

Vue lets you mutate directly because it can sense mutations the moment they happen.

A mental model that sticks:

React is a Polaroid camera. Every shot produces a discrete, immutable photograph. To capture change, take a new photo. The old one still exists — you can stack them and flip through history. Time-travel debugging works because every state is a preserved snapshot.

Vue is a whiteboard. You erase the old number. Write a new one. Same board. Different content. But a stenographer records every edit: "3:42 PM, whiteboard A, line 3: 5 → 6." No stack of snapshots. But precision and efficiency.

Snapshots give you history. Whiteboards give you directness. In most business apps, you don't need time-travel debugging. You need "change data, UI updates, that's it." Vue bets harder on "that's it."

## When Vue hits a wall

Vue isn't magic. There are scenarios where it genuinely struggles. But its solutions look nothing like Fiber.

**Scenario: massive data lists.**

100,000 rows. No framework creates 100,000 DOM nodes in 16ms. Physics doesn't negotiate.

Vue's answer isn't "make rendering interruptible." It's "don't render 100,000 rows."

Virtual scrolling. Only render rows visible in the viewport. Maybe 25 rows. The other 99,975 exist as data, not as DOM:

```vue
<script setup>
import { ref } from 'vue'
import { useVirtualList } from '@vueuse/core'

const items = ref(
  Array.from({ length: 100000 }, (_, i) => ({
    name: `Item ${i}`,
    value: Math.random(),
  })),
)

const { list, containerProps, wrapperProps } = useVirtualList(items, {
  itemHeight: 50,
  overscan: 5,
})
</script>

<template>
  <div v-bind="containerProps" style="height: 400px; overflow: auto;">
    <div v-bind="wrapperProps">
      <div v-for="{ data, index } in list" :key="index">{{ data.name }}: {{ data.value.toFixed(2) }}</div>
    </div>
  </div>
</template>
```

This isn't optimizing how rendering executes. It's changing what you render. Don't need to interrupt rendering if you're not rendering.

**Scenario: expensive computations.**

If a component crunches a 10,000-item array — sorting, filtering, aggregating — that's main thread work. Framework-independent.

Vue's arsenal:

- `computed` auto-caches. Dependencies unchanged? Returns previous result. No recomputation.
- `v-memo` directive freezes template regions until specified values change.
- Web Workers — offload heavy computation to a separate thread entirely.

```vue
<template>
  <div>
    <span v-for="item in list" :key="item.id" v-memo="[item.name, item.count]">
      {{ item.name }}: {{ item.count }}
    </span>
  </div>
</template>
```

None of this is Fiber-style interruptible rendering. But each solves the problem in its own domain.

**Vue 3.4+ and Vapor Mode.**

Vue's latest optimization push is called Vapor Mode — inspired by Solid.js. It compiles templates directly into DOM manipulation code, skipping the virtual DOM entirely for static parts. The traditional Vue pipeline is "reactive data → virtual DOM → real DOM." Vapor Mode short-circuits to "reactive data → real DOM." The middle layer is removed.

If Vapor Mode reaches maturity, Vue's performance jumps another tier. The "does Vue need Fiber?" question becomes even more irrelevant — Vue isn't even running a virtual DOM anymore, so what would Fiber interrupt?

## Are the two frameworks converging?

A question worth asking: are React and Vue heading toward the same place?

In some ways, yes.

React 19's compiler does what Vue's template compiler has always done — compile-time optimization — though the mechanisms differ significantly. Vue's Vapor Mode is learning from Solid.js's "skip the virtual DOM" approach, which actually takes Vue _further_ from React's model, closer to Solid.

Both have borrowed from each other. React Hooks were clearly inspired by Vue's Composition API (though the implementation mechanism is completely different). Vue's `v-memo` gives developers a React.memo-like manual control — allowing explicit "only re-render when..." semantics.

But their deepest divergence cannot converge. That divergence is how they detect change: Pull vs Push.

React cannot suddenly become Push mode. That would mean rewriting the entire core, abandoning functional philosophy, breaking ecosystem compatibility. Vue cannot suddenly become Pull mode. That would mean abandoning the reactive system — Vue's single most differentiating advantage.

So they'll converge on the periphery — compile optimization, developer experience, SSR capabilities. But their cores will remain distinct.

What does this mean for you? You don't need to worry about which one "wins." Both will win. They'll just win in different scenarios.

## A judgment framework you can actually use

Enough theory. Here's something practical.

Next time someone asks you "React or Vue?" — don't answer directly. Ask them five questions. By the fifth question, they'll have their own answer.

### Question 1: How interaction-dense is your app, really?

This determines whether main thread blocking is a genuine concern in your context.

Display-heavy apps — tables, dashboards, cards, charts, read-only data views — where interactions are mainly clicks, pagination, scrolling. Single update workloads are naturally small. Vue's precise updates excel: only the tiny slice of UI that depends on changed data updates. Almost zero waste.

Interaction-dense apps — drag-and-drop editors, canvas tools, high-frequency live input with previews, complex animations touching many UI regions simultaneously. Here, the main thread genuinely can block. Fiber's priority scheduling genuinely prevents stutter.

But ask honestly: is your app Figma? Or is it an admin dashboard?

Ninety percent of business apps are display-heavy. Don't pay for a problem you don't have.

### Question 2: What mental model fits your team?

This matters more than performance. In typical apps, the rendering performance gap between Vue and React is invisible to users. But mental model differences shape every single day of development.

Vue is **implicit and automatic**. Define reactive data. Use it in templates. Change it. Vue handles tracking, propagation, DOM updates. You don't need to understand Proxy to write performant Vue components.

React is **explicit and manual** — trending toward automatic with React 19. You need to understand state lifting, re-render triggers, memoization timing. The compiler reduces the manual burden, but understanding React's update mechanics remains valuable.

Team that prefers "things just work" → Vue.
Team that prefers "everything is explicit" → React.

### Question 3: Batteries included or build your own?

Vue's official ecosystem — Vue Router, Pinia, Vite, VueUse, Vitest — is cohesive and pre-integrated. You rarely debate "which routing library should I use?" The official choice is solid.

React's ecosystem is broader but more fragmented. State management: Redux Toolkit, Zustand, Jotai, Recoil, Valtio — each with different philosophies. Routing: React Router, TanStack Router. Data fetching: TanStack Query, SWR.

Endless choices. But choosing requires evaluation. Some love curating their stack. Some find it exhausting.

### Question 4: Whose problem does Fiber actually solve?

Use this question for interviews and for your own understanding.

Fiber solves a problem React created. The Pull model's "state change → re-run everything" strategy generates rendering workloads that can block the main thread. Fiber mitigates the symptoms — making blocking less likely through time slicing and priority scheduling.

Vue prevents the problem. Reactive tracking means rendering workloads are light from the start. Light workloads → no blocking → no need for Fiber.

The metaphor that survives every explanation:

Two students. Same exam.

Alex partied all semester. Night before the exam: all-nighter. Coffee. Energy drinks. Without stimulants (Fiber), Alex collapses.

Sam studied consistently. Night before: bed at 10 PM. No coffee needed. The concept "I need something to stay awake" doesn't apply.

Both pass. But "why doesn't Sam need coffee?" isn't about coffee being bad. Sam doesn't need coffee because Sam doesn't have the problem coffee solves — staying awake through a forced all-nighter.

### Question 5: How special is your app?

Don't let extreme-case blog posts scare you. "10,000 rows rendered." "100 keystrokes per second." "800 components animating simultaneously." How often do these actually appear in your codebase?

For most business apps, the real bottleneck isn't framework rendering. It's undebounced network requests. Unoptimized images. Uncached computations. Overstuffed bundles.

Vue and React — in normal apps doing normal things — the rendering performance gap is invisible to the human eye. What users actually feel is your product design and engineering discipline. Not whether your framework can interrupt a diff.

## Quick answers to common questions

**Q: Is Vue 3's Composition API related to Fiber in any way?**

Zero relationship. Composition API is a code organization pattern — extracting scattered logic into reusable functions. It solves "logic reuse." Fiber solves "rendering scheduling." Their problem domains don't touch. Think of Composition API as Vue's version of Hooks — except its reactive foundation makes it more flexible (no dependency arrays, no re-execution problems).

**Q: Will Vue ever introduce something like Fiber?**

Vue core team has said "no plans." Not because they can't. Because they don't need to. Vue 3's reactivity system makes updates efficient enough that Fiber would add complexity with almost no benefit. Like buying coffee for someone who never stays up late — coffee is great, but useless for them.

But Vue keeps evolving. `v-memo` (Vue 3.2) lets you manually freeze template regions. Vapor Mode (Vue 3.4+) skips virtual DOM for static parts. Both share Fiber's spirit — "don't do unnecessary work." But the approaches are fundamentally different.

**Q: Aren't Svelte and Solid.js even more efficient than Vue?**

Svelte and Solid represent a third path: extreme compile-time optimization.

Svelte determines at compile time exactly which DOM nodes each data change affects. Almost no diff at runtime. Solid goes further — its reactivity tracking is almost entirely resolved at compile time.

Tradeoffs exist: larger compiled output, harder debugging for complex scenarios, smaller ecosystems. Vue balances compile-time optimization with runtime flexibility — more flexible than Svelte, more efficient than React.

Not "better." Different points on the tradeoff spectrum.

**Q: Does React 19's compiler level the playing field?**

It narrows the gap significantly. One of React's historical pains — manual memoization — is largely automated now. But the fundamental architectural difference remains: React is still Pull mode, Vue is still Push mode. The compiler reduces wasted work but doesn't eliminate the Pull model's need for Fiber in interaction-dense scenarios.

In typical business apps, React 19 + Compiler is fast enough that users can't tell the difference. In extreme real-time scenarios (Figma-level complexity), Fiber's priority scheduling remains React's unique advantage — an upside dividend of the Pull model.

## Before you close this tab

You probably noticed. This article never tells you which framework to use.

That's not laziness. That's honesty.

React and Vue represent two competing engineering philosophies fighting in the same arena:

One says: "Keep the framework simple. If performance becomes an issue, we'll give you tools to fix it (Fiber, Compiler, Concurrent Mode)."

The other says: "Make the framework handle complexity internally so your code is naturally fast. The hard work is invisible to you (reactive tracking, compile-time optimization)."

Both philosophies produced great frameworks. Both are still evolving, still absorbing each other's best ideas. React got a compiler. Vue got Vapor Mode. The gap keeps narrowing.

But back to you — 3 AM you, staring at that frozen search box.

You don't need a better framework. You need to understand what your current framework is doing for you, and what it's making you pay in return.

If you take only two things from this article, take these two questions. Apply them to any new technology you evaluate:

**One: How does it detect change?**

React: you call setState. Explicit.
Vue: Proxy intercepts. Implicit.

**Two: After detecting change, how much unnecessary work does it do?**

React: re-runs the entire component tree, then diffs to find what actually changed. Lots of potentially unnecessary work. Fiber schedules around that waste.
Vue: only updates components that depend on the changed data. Almost no unnecessary work. No Fiber needed — not because Fiber is bad, but because the problem Fiber solves doesn't arise.

Internalize these two questions. Interviewers can't stump you. Blog posts can't mislead you. And you'll never again sit at 3 AM, staring at a lagging search box, not knowing why.

You'll already know.

Speaking of which — is that search box still broken?

If yes. Maybe it's not your code.
Maybe your tool is making you solve a problem it created.
