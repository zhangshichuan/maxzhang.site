## 1. Why Does Everything Fall Apart Under Load?

Let me tell you a story.

You open a tiny restaurant. Hire one chef. She can cook one dish at a time. Then a hundred customers walk in at once. Her hands are shaking. The order slips pile up. Customers at the back start yelling. Some walk out. The chef finally snaps — "I quit" — throws her apron down and leaves.

A website is exactly the same. One server is that one chef. When traffic spikes:

- Everything gets slower, like those shaking hands
- Eventually it crashes — throws you a 502 and walks out
- The user sees a blank page, a spinner, an error screen

**High concurrency is a bunch of people showing up at the exact same second.** The core problem is dead simple: do more work, in less time, with limited resources, and don't fuck up the data.

Think about a flash sale: 100K people refreshing the product page, 50K clicking "buy," 30K submitting orders, 20K completing payment. All within seconds. One weak link in the chain and the whole experience is ruined.

### You're trying to do three things at once

| Goal       | What it means                      | Real metric                               |
| ---------- | ---------------------------------- | ----------------------------------------- |
| **Fast**   | Every extra second costs you users | 99% of requests under 200ms               |
| **Much**   | Serve thousands simultaneously     | 100K+ requests per second                 |
| **Stable** | Can't keep crashing                | Less than 52 minutes of downtime per year |

These three things are interconnected. Go faster, you can handle more. Handle more, you might slow down. You have to balance them.

### The system doesn't grow up overnight

Nobody runs a marathon the day they're born.

```
Monolith → add machines + load balancing → read/write split DB → add caching → split into microservices → containerize → multi-DC active-active
```

- **Monolith**: All the code bundled together, one machine
- **Add machines**: Can't keep up, buy more servers, use a load balancer to spread requests
- **Read/write split**: Database is the bottleneck now, separate reads from writes
- **Caching**: Hot data goes in memory, stop asking the database for everything
- **Microservices**: The codebase is a mess, split by function into independent services
- **Containerization**: Too many services, need proper orchestration
- **Multi-DC**: One data center isn't enough, replicate globally

Each stage solves the bottleneck of the previous stage. Don't jump straight to multi-DC active-active — that's for Taobao-scale traffic. We'll start from the beginning.

## 2. Spread the Load — Load Balancing

### 2.1 You bought more servers. Now what?

You added three servers. Here's the question: when a request comes in, which one handles it?

If nobody's at the door directing traffic, all requests still hit the first server. Servers two and three are sunbathing while number one is on fire.

**A load balancer is the person at the door.** She doesn't cook. She just guides customers to the chef with the shortest queue.

Real load balancing isn't one layer — it's several, working together:

```
User → DNS (returns IP of nearest DC) → LVS (layer 4 forwarding, blazing fast) → Nginx (layer 7, understands request paths) → API Gateway (auth, rate limiting) → your app
```

**DNS layer** — the outermost. Returns different IPs when resolving the domain. Problem: it has no idea if a server is alive. One machine goes down, DNS keeps sending users there. So DNS usually works with CDN — cache static assets (images, CSS, JS) on edge nodes close to the user. Physical proximity cuts latency from 300ms to 50ms.

**LVS layer** — works at the transport layer (layer 4). No protocol parsing. Just IP and port forwarding. Extremely fast. Perfect as the first gatekeeper. Config looks like:

```bash
# One virtual IP, three real servers behind it
ipvsadm -A -t 192.168.1.100:80 -s rr
ipvsadm -a -t 192.168.1.100:80 -r 10.0.0.1:80 -m
ipvsadm -a -t 192.168.1.100:80 -r 10.0.0.2:80 -m
ipvsadm -a -t 192.168.1.100:80 -r 10.0.0.3:80 -m
```

LVS has three modes. DR mode (Direct Routing) is the fastest — it only changes MAC addresses, not IP addresses, so packets barely touch the LVS machine itself. Downside: all servers must be on the same subnet. NAT mode works across subnets, but all traffic flows through LVS, making LVS itself a potential bottleneck.

**Nginx layer** — layer 7 load balancing. It can read HTTP, understand which path the user wants, and route precisely. If LVS is a highway toll booth, Nginx is the city traffic control center — "Going to /api/order? Lane 2. /static/image.jpg? Straight to CDN, don't crowd the backend."

```nginx
upstream backend {
    least_conn;  # whoever has fewest active connections gets the next request
    server 10.0.0.1:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 10.0.0.2:8080 weight=2 max_fails=3 fail_timeout=30s;
    server 10.0.0.3:8080 backup;  # backup, sits idle until all primaries fail
    keepalive 32;
}

server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://backend;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_connect_timeout 5s;
        proxy_next_upstream error timeout http_500 http_502 http_503;
        proxy_next_upstream_tries 3;
    }
}
```

A few details worth noting: `least_conn` is dynamic, suits long-connection scenarios. `weight` is meritocracy — the 8-core machine gets more traffic, the 2-core gets less. `max_fails=3 fail_timeout=30s` is health checking — three consecutive failures and the server is ejected for 30 seconds. `backup` means standby — it just sits there until all primaries are dead.

**API Gateway layer** — the bouncer for microservices. Authentication (who are you?), rate limiting (how many requests per second?), service discovery (where's the service you need?). You use gRPC, client speaks HTTP? Gateway translates. Your data is scattered across three services? Gateway aggregates it.

```javascript
// Simple rate limiter: 1000 requests per IP per minute
import rateLimit from 'express-rate-limit'
import RedisStore from 'rate-limit-redis'

const limiter = rateLimit({
  store: new RedisStore({ sendCommand: (...args) => redisClient.sendCommand(args) }),
  windowMs: 60 * 1000,
  max: 1000,
  handler: (req, res) => {
    res.status(429).json({ error: 'Too many requests. Take a breather.' })
  },
})

app.use('/api/order', limiter)
```

### 2.2 Which server gets the request? Load balancing algorithms

Algorithms are the rules for "who's next." Two categories: **static** (ignores server state) and **dynamic** (watches server state).

#### Static algorithms

**Round Robin** — fairest of them all. 1-2-3-4-1-2-3-4, around and around.

```javascript
class LoadBalancer {
  constructor(servers) {
    this.servers = servers
    this.currentIndex = 0
  }
  getNextServer() {
    const server = this.servers[this.currentIndex]
    this.currentIndex = (this.currentIndex + 1) % this.servers.length
    return server
  }
}
```

**Weighted Round Robin** — the strong carry more weight. 8-core machine gets weight 8, 2-core gets weight 2. Slightly more complex code but the idea is simple: bigger muscles, heavier load.

**IP Hash** — same IP always goes to the same server. Why? Session stickiness. The user logs in, their session data lives in the server's memory. Next request goes to a different server — no session, forced re-login.

```javascript
import crypto from 'node:crypto'

function ipHash(ipAddress, serverList) {
  const hash = crypto.createHash('md5').update(ipAddress).digest('hex')
  const hashInt = parseInt(hash.substring(0, 8), 16)
  return serverList[hashInt % serverList.length]
}
```

Same IP, same hash every time, same server every time. Heads up: this is tied to the number of servers. Add or remove one, and almost every IP's routing changes.

**Consistent Hashing** — IP Hash on steroids. Mainly used for distributed caches.

Here's the problem: you've got 3 Redis servers caching user data. One day a server dies, or you scale to 4. With regular hashing (modulo), almost every cache key gets remapped — because the divisor changed from 3 to 4. All caches invalidate. All requests hit the database. Database: dead.

Consistent hashing uses a ring to solve this. Servers take positions on the ring. Data keys also land on the ring. Walk clockwise — the first server you encounter is where the data belongs. Add or remove a server, only the data in the adjacent ring segment needs to move.

```javascript
class ConsistentHash {
  constructor(nodes = [], virtualNodes = 150) {
    this.virtualNodes = virtualNodes
    this.ring = new Map()
    this.sortedKeys = []

    nodes.forEach((node) => this.addNode(node))
  }

  _hash(key) {
    const hash = crypto.createHash('md5').update(key).digest('hex')
    return parseInt(hash.substring(0, 8), 16)
  }

  addNode(node) {
    for (let i = 0; i < this.virtualNodes; i++) {
      const hashValue = this._hash(`${node}:${i}`)
      this.ring.set(hashValue, node)
      this.sortedKeys.push(hashValue)
    }
    this.sortedKeys.sort((a, b) => a - b)
  }

  removeNode(node) {
    for (let i = 0; i < this.virtualNodes; i++) {
      const hashValue = this._hash(`${node}:${i}`)
      this.ring.delete(hashValue)
      this.sortedKeys = this.sortedKeys.filter((k) => k !== hashValue)
    }
  }

  getNode(key) {
    if (this.ring.size === 0) return null
    const hashValue = this._hash(key)
    // Binary search: first position on the ring >= hashValue
    let low = 0,
      high = this.sortedKeys.length - 1
    while (low <= high) {
      const mid = Math.floor((low + high) / 2)
      if (this.sortedKeys[mid] >= hashValue) high = mid - 1
      else low = mid + 1
    }
    if (low === this.sortedKeys.length) low = 0 // wrap around
    return this.ring.get(this.sortedKeys[low])
  }
}
```

`virtualNodes` is the key. Each physical node occupies 150 spots on the ring, not just one. More virtual nodes, more even distribution. Without them, you might get "server A owns half the ring, server B gets a sliver" — terrible.

#### Dynamic algorithms

**Least Connections** — send the request to the server with the fewest active connections. Perfect for long-lived connections: WebSockets, chat apps, streaming. Don't bother using this for short-lived HTTP — connections open and close so fast the number is meaningless.

### 2.3 What happens when a server dies? Health checks

You wouldn't send a customer to a dead chef. But the code doesn't know — you have to tell it.

Two approaches:

**Active checks**: the load balancer pings each backend every few seconds. "Hey, you alive?" Alive means stay in rotation. Dead means eject. Typically an HTTP probe — `GET /health` returns 200. `rise=2` means it takes two consecutive successes to mark a server healthy again. `fall=5` means five consecutive failures before declaring it dead. This prevents flapping.

**Passive checks**: don't probe proactively, watch actual responses. A request returns 500 — note it down. Enough consecutive failures, eject. Simpler to implement, but has a delay — some users already saw errors before the server gets pulled.

Use both. Passive as first line of defense — catches problems as they happen. Active as safety net — detects dead servers even when there's no traffic.

Passive in Nginx is trivial: `server 10.0.0.1:8080 max_fails=3 fail_timeout=30s;`. Active needs the `nginx_upstream_check_module`.

Sometimes you need more than "is the process alive" — you need "is the database connected, is Redis responding, is there disk space?" That's what application-layer health endpoints are for:

```javascript
app.get('/health', async (req, res) => {
  const healthcheck = {
    uptime: process.uptime(),
    status: 'OK',
    timestamp: Date.now(),
    checks: {},
  }

  try {
    healthcheck.checks.database = mongoose.connection.readyState === 1 ? 'up' : 'down'
    await redisClient.ping()
    healthcheck.checks.redis = 'up'
    const diskSpace = await checkDiskSpace('/')
    healthcheck.checks.disk = diskSpace.free / 1024 / 1024 / 1024 > 10 ? 'up' : 'warning'
  } catch (error) {
    healthcheck.status = 'error'
    return res.status(503).json(healthcheck)
  }

  if (healthcheck.checks.database === 'down' || healthcheck.checks.redis === 'down') {
    return res.status(503).json(healthcheck)
  }

  res.json(healthcheck)
})
```

### 2.4 The load balancer itself can't be a single point of failure

Wait — doesn't the load balancer itself become a single point of failure? Yep.

So you make it HA. Use Keepalived to create a virtual IP (VIP) that floats between two Nginx instances. Primary Nginx dies, VIP automatically drifts to the backup. Users don't notice — they've always connected to the virtual IP, they have no idea who's behind it now.

At global scale, GSLB (Global Server Load Balancing) routes users to the nearest data center. User in Beijing? Beijing origin. User in New York? Frankfurt origin. Physical distance is something code can't compensate for.

### What load balancing doesn't solve

It doesn't fix application-level problems. Your code does a full table scan per request — ten servers will still get crushed. It doesn't solve data consistency — multiple requests hitting different servers, how do you prevent overselling inventory? That's a database and business-layer problem. And it can't handle a genuine traffic tsunami — if your instantaneous QPS is 1000x normal and you only have three servers, load balancing just makes all three die at exactly the same elegant moment.

## 3. Node.js and the Single-Thread Problem — Damn, 8 Cores, Using 1

Node.js has this annoying design: single-threaded by default. Not a bug, a choice. It uses an event loop for async I/O, which spares you the entire shitshow of multi-threaded programming — locks, deadlocks, race conditions. You never touch them.

But the price:

1. **8-core CPU, using 1 core.** You buy an 8-core server. Node.js runs. You open htop. One core at 100%. Seven cores — crickets.
2. **Process crashes, whole service is gone.** Unlike Java with thread isolation — one thread dies, others survive. Node.js process dies, it's over.

### The Cluster Module: DIY multi-process

Node.js ships with the `cluster` module to handle this. The master process forks N child processes. Each child independently handles requests. The OS kernel distributes incoming connections (socket sharing).

```javascript
import cluster from 'cluster'
import { cpus } from 'os'

if (cluster.isPrimary) {
  const numCPUs = cpus().length
  for (let i = 0; i < numCPUs; i++) {
    cluster.fork()
  }
  // Child died? Auto-restart.
  cluster.on('exit', (worker, code, signal) => {
    console.log(`Process ${worker.process.pid} died, restarting`)
    cluster.fork()
  })
} else {
  // This is a child process. Start your server normally.
  http
    .createServer((req, res) => {
      res.end(`You got process ${process.pid}`)
    })
    .listen(3000)
}
```

Critical detail: `cluster.on('exit')` with auto-restart. Production must have this. Otherwise a process silently dies at 3 AM and you never know.

### Graceful shutdown — don't cut off requests mid-flight

A brutal `kill -9` interrupts requests being processed. User gets `ECONNRESET` — confused and pissed. Database transactions half-written — dirty data.

Graceful shutdown flow: receive shutdown signal → stop accepting new connections → finish existing requests → close database connections → exit.

```javascript
class GracefulShutdownManager {
  constructor(server, options = {}) {
    this.server = server
    this.timeout = options.timeout || 10000
    this.connections = new Set()
    this.pendingRequests = 0
    this.isShuttingDown = false

    this.server.on('connection', (socket) => {
      if (this.isShuttingDown) {
        socket.destroy()
        return
      }
      this.connections.add(socket)
      socket.on('close', () => this.connections.delete(socket))
    })

    this.server.on('request', (req, res) => {
      this.pendingRequests++
      res.on('finish', () => {
        this.pendingRequests--
        if (this.isShuttingDown && this.pendingRequests === 0 && this.connections.size === 0) {
          console.log('All requests finished. Safe to exit.')
          process.exit(0)
        }
      })
    })
  }

  shutdown() {
    if (this.isShuttingDown) return
    this.isShuttingDown = true
    this.server.close()

    setTimeout(() => {
      console.error('Graceful shutdown timed out. Forcing exit.')
      process.exit(1)
    }, this.timeout)
  }
}

// Listen for signals
const manager = new GracefulShutdownManager(server)
process.on('SIGTERM', () => manager.shutdown()) // Docker/K8s stop
process.on('SIGINT', () => manager.shutdown()) // Ctrl+C
```

Honestly, don't write your own cluster management, graceful shutdown, log rotation, and monitoring. PM2 does it all:


The `health_check` config is gold — PM2 hits your health endpoint every 30 seconds. One failure, it notes. Two failures, it restarts. No external monitoring needed — PM2 keeps itself alive.

### What this doesn't solve

Cluster doesn't solve shared state. Multiple processes — how do they share memory? Share counters? It only solves "one process handles more requests." State is still per-process. For shared state, you need Redis or a database.

PM2 doesn't fix bugs. Auto-restart is a bandage, not a cure. You have a memory leak — PM2 will keep restarting, but the bug is still there. Fix the code.

## 4. Caching — Stop Walking to the Warehouse Every Time

### 4.1 Why caching saves your ass

The database is the slowest thing in your system. Not because it's slow in absolute terms — but relative to memory.

- Reading from memory: microseconds
- Reading from a database: milliseconds to tens of milliseconds
- Reading from disk: even slower

That's a thousand-fold difference. If you can keep hot data in memory ahead of time, your system's capacity jumps by orders of magnitude.

**Caching = trading space for time.** Keep frequently used stuff on your desk. Stop walking to the warehouse next door for every little thing.

### 4.2 Caching is layered

Not one layer — several. The closer to the user, the faster. But also harder to keep consistent:

```
Browser Cache → CDN → Nginx Cache → Local Memory → Redis → Database
```

- **Browser**: Fastest. Static assets read locally, zero network requests. Just set proper Cache-Control headers.
- **CDN**: Static assets cached on edge nodes near the user. Physical proximity rules.
- **Nginx**: Cache full-page or API responses. Good for infrequently-changing endpoints.
- **Local memory**: In-process cache, microseconds. But each process has its own copy — inconsistent.
- **Redis**: Distributed cache. All processes share the same data.
- **Database**: Source of truth. Slowest, but most reliable.

### 4.3 Redis in practice — the right caching patterns

Let's look at real code. This RedisCache class implements the key patterns:

```javascript
class RedisCache {
  constructor(options = {}) {
    this.client = createClient({
      url: `redis://${options.host || 'localhost'}:${options.port || 6379}`,
      password: options.password,
      database: options.db || 0,
    })
    this.prefix = options.prefix || 'cache:'
    this.defaultTTL = options.defaultTTL || 3600
    this.client.connect().catch(console.error)
  }

  async get(key) {
    const data = await this.client.get(`${this.prefix}${key}`)
    return data ? JSON.parse(data) : null
  }

  async set(key, value, ttl = this.defaultTTL) {
    const data = JSON.stringify(value)
    await this.client.set(`${this.prefix}${key}`, data, { EX: ttl })
  }

  async del(key) {
    await this.client.del(`${this.prefix}${key}`)
  }

  // This is the pattern you'll use most: return cached value,
  // otherwise fetch from DB, cache it, then return.
  // Built-in mutex prevents cache stampedes.
  async remember(key, ttl, callback) {
    let value = await this.get(key)
    if (value !== null) return value

    const lockKey = `lock:${key}`
    const locked = await this.client.set(lockKey, 'locked', { NX: true, EX: 10 })
    if (locked) {
      try {
        value = await this.get(key) // double-check
        if (value !== null) return value
        value = await callback()
        await this.set(key, value, ttl)
        return value
      } finally {
        await this.client.del(lockKey)
      }
    } else {
      await new Promise((resolve) => setTimeout(resolve, 100))
      return await this.get(key)
    }
  }
}
```

The `remember` pattern is what you'll reach for in business logic. One line for cache-or-fetch:

```javascript
const user = await cache.remember('user:1001', 1800, async () => {
  return await db.query('SELECT * FROM users WHERE id = ?', [1001])
})
```

### 4.4 The three classic cache problems

Caching gives you performance but introduces three new problems. Each can wreck your database.

**Cache Penetration** — querying an ID that doesn't exist. Nobody caches it (because it doesn't exist), so every request punches through to the database. A malicious attacker can weaponize this to kill your DB.

Fix: cache null values. Even a non-existent ID gets cached with a sentinel value (`NULL_VALUE`), expiring in 5 minutes. Next query for the same ID returns the cached null instead of hitting the database.

**Cache Breakdown (Hotspot Expiry)** — a super-hot key (like the homepage featured products) expires. Instantly, thousands of concurrent requests realize the cache is gone and all charge the database simultaneously. Database: I have one waiter and you sent a stadium.

Fix: mutual exclusion lock. Only let one request go to the database to rebuild the cache. Everyone else waits. The `lock` logic inside `remember` above does exactly this.

**Cache Avalanche** — massive batch of caches expire at the exact same time. Like after a system restart where you warmed the cache with identical TTLs. The clock strikes, everything goes poof.

Fix: add random jitter to TTLs. Instead of exactly 3600 seconds, set 3600-4000 random. They won't all expire simultaneously. Also, for hot data, use "never expire + background async refresh" — the cache never auto-deletes, but when it's close to stale, silently refresh it.

### What caching doesn't solve

Caching doesn't solve data consistency. You update the database, the cache still holds the old value — users see stale data. This is the "cache-database dual-write inconsistency" problem, which deserves its own article.

Caching doesn't improve write performance. If your bottleneck is heavy writes (logging, event tracking, payment records), caching can't help — you need async writes via message queues.

## 5. The Database — The Last Wall

When caching fails, every request — warranted or not — lands on the database. It has to hold.

### 5.1 Read/Write Splitting — let replicas handle reads

Most workloads are read-heavy. A news site: 99% reading articles, 1% publishing. E-commerce: browsing products far outweighs purchases.

Read/write splitting is simple: one primary for writes, multiple replicas for reads. Data replicates from primary to replicas. Write pressure stays the same, read pressure is shared across replicas.

PostgreSQL uses Streaming Replication: the primary pushes WAL (Write-Ahead Log) to replicas, which replay the logs to stay in sync.

Primary config: `wal_level = replica`, `max_wal_senders = 10`, `hot_standby = on`. Create a replication user, then replicas use `pg_basebackup` to pull a full snapshot and start tailing the primary's logs.

Middleware (pgpool-II) handles automatic routing: SELECT goes to replicas, INSERT/UPDATE/DELETE goes to primary. The middleware itself needs HA — if it dies, all routing is gone.

### 5.2 After 5 million rows per table

Once a single table grows large enough, no amount of indexing keeps queries fast. Time to shard.

**Horizontal partitioning**: split rows across tables. A users table hash-partitioned into 4 — `users_0` through `users_3`. PostgreSQL 10+ native partitioning handles routing automatically. You insert into `users`, PG figures out which partition. You query `users`, PG scans the relevant partitions.

**Vertical partitioning**: split columns across tables. User profile becomes `user_basic` (ID, username, email) and `user_detail` (avatar, bio, settings). Frequently-used vs rarely-used fields separated, reducing per-row data size.

PostgreSQL native partitioning:

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    username VARCHAR(50),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) PARTITION BY HASH (id);

CREATE TABLE users_0 PARTITION OF users FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE users_1 PARTITION OF users FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE users_2 PARTITION OF users FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE users_3 PARTITION OF users FOR VALUES WITH (MODULUS 4, REMAINDER 3);
```

Query and insert against the parent table `users`. PostgreSQL handles the routing. You don't need `id % 4` logic in your application.

### 5.3 Connection pooling — establishing connections is slow

Creating a database connection involves: TCP handshake, SSL handshake, authentication, initialization parameters. Tens of milliseconds. If every request opens a new connection, the database spends most of its time saying hello instead of doing work.

Connection pooling: pre-establish a pool of connections. Requests grab one, use it, return it. Reuse, don't destroy.

```javascript
import pg from 'pg'

const pool = new pg.Pool({
  host: 'localhost',
  port: 5432,
  user: 'postgres',
  database: 'myapp',
  max: 50, // max 50 connections
  min: 5, // always keep at least 5
  idleTimeoutMillis: 60000, // release idle connections after 60s
  connectionTimeoutMillis: 10000, // wait max 10s for a connection
  statement_timeout: 30000, // single query max 30s
  ssl: process.env.NODE_ENV === 'production' ? { rejectUnauthorized: false } : false,
})
```

Connections aren't infinite. The database can only handle so many concurrent connections. 50 is already a lot — more and context switching overhead starts hurting overall throughput. When you genuinely need more concurrency, don't add connections. Add replicas.

### What database optimization doesn't solve

Read/write splitting doesn't solve write bottlenecks. Your writes are too heavy — the primary is still alone on writes. You need sharding or async writes via message queues.

Sharding doesn't solve complex cross-shard queries. `SELECT * FROM users ORDER BY created_at LIMIT 100` — after sharding, you need to fetch 100 from each shard and merge-sort. Complexity goes from O(N log N) to O(N²). When you genuinely need these queries, use a dedicated search engine (Elasticsearch) or aggregate at the application layer.

## 6. Don't Deploy Everything at Once — Canary Releases

### 6.1 How many times have you yolo-deployed?

Ten full deployments, nine are fine. But that one time —

Two in the morning. Code goes live. The new version has a hidden N+1 query you missed. Database connection pool instantly saturated. Entire site down. Users screaming. You roll back frantically, but it's already been 10 minutes.

If those 10 minutes happened during a flash sale, the losses are measured per second.

**Canary releases: test on a tiny slice of users first.** If nothing breaks, expand. Like miners sending a canary into the shaft — bird lives, miners follow. Bird dies, everyone runs.

### 6.2 Three common strategies

| Strategy   | How it works                                                    | When to use                 |
| ---------- | --------------------------------------------------------------- | --------------------------- |
| Canary     | New version gets 10% traffic, observe, expand to 50%, then 100% | Core services, high risk    |
| Blue-Green | Two complete environments, old and new. Verify new, then switch | Tolerate brief interruption |
| Rolling    | Replace instances one at a time, e.g., 2 out of 10 at a time    | Stateless services          |

Canary is safest and most common. Nginx does it with weights:

```nginx
upstream backend {
    # Old version 90%
    server old-v1:8080 weight=45;
    server old-v2:8080 weight=45;
    # New version 10%
    server new-v1:8080 weight=5;
    server new-v2:8080 weight=5;
}
```

For finer control — route specific users (internal test accounts, specific IPs) to the new version:

```nginx
set $backend "backend";
if ($http_cookie ~* "canary=1") {
    set $backend "backend_canary";
}
location / {
    proxy_pass http://$backend;
}
```

Set a `canary=1` cookie for yourself, and you can validate the new version in production. Everyone else unaffected.

### 6.3 Feature Flags — don't deploy, toggle

Sometimes you want to test a feature without deploying new code. Feature flags let you embed a switch in your code and flip it live.

```javascript
class FeatureToggle {
  async getFeature(featureName, userId) {
    const config = await this.getConfig(featureName)
    if (!config.enabled) return false

    switch (config.strategy) {
      case 'percentage':
        // Hash user ID: 10% of users see the new feature
        return this._hash(userId) % 100 < config.percentage
      case 'userList':
        // Whitelist
        return config.users.includes(userId)
      default:
        return config.enabled
    }
  }

  _hash(str) {
    let hash = 0
    for (let i = 0; i < str.length; i++) {
      hash = (hash << 5) - hash + str.charCodeAt(i)
      hash = hash & hash
    }
    return Math.abs(hash)
  }
}
```

Configuration lives in Redis. Change it anytime, takes effect in 5 seconds. Rollback is flipping a switch — zero code changes.

### What canary releases don't solve

Canary releases don't guarantee the new version is bug-free. They limit blast radius — 10% of users affected is better than 100%. You still need testing, code review, and load testing.

Feature flags left too long turn your codebase into spaghetti. `if (flag1 && flag2 || flag3)` nested three deep — six months later, nobody remembers which flag is on or off. Set expiration dates on flags. Clean them up regularly.

## 7. You Can't Manage What You Can't See — Monitoring

### 7.1 No monitoring is like driving blindfolded

The system runs fine. But do you really know it?

- How many database connections are open right now? About to max out?
- That one API's P99 latency has been creeping up, from 200ms to 2 seconds — did you notice?
- 3 AM, Redis memory is nearly full — do you know?

An unmonitored system is a car with no dashboard. You only know you're out of gas when you're already stopped on the highway.

### 7.2 Monitoring in four layers

**Collection layer**: gather metrics from every component. Node.js app exposes `/metrics`. Database via PostgreSQL Exporter. Host via Node Exporter. All feeding Prometheus.

**Storage & Alerting layer**: Prometheus as time-series database, AlertManager for notifications. Prometheus scrapes every endpoint every 15 seconds.

**Visualization layer**: Grafana dashboards. CPU, memory, QPS, error rate, slow queries — all visualized. When something's wrong, you don't need to read logs. Grafana curves tell you the rough direction.

**Notification layer**: Slack, email, SMS, PagerDuty. 3 AM outage — don't wait for users to tell you. Let your phone ring first.

### 7.3 Instrumenting your code

```javascript
import promClient from 'prom-client'

const register = new promClient.Registry()
promClient.collectDefaultMetrics({ register }) // default: CPU, memory, event loop lag

// Custom metrics
const httpRequestDuration = new promClient.Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration',
  labelNames: ['method', 'route', 'status_code'],
  buckets: [0.1, 0.3, 0.5, 0.8, 1, 3, 5, 10],
})

const httpRequestTotal = new promClient.Counter({
  name: 'http_requests_total',
  help: 'Total HTTP requests',
  labelNames: ['method', 'route', 'status_code'],
})

register.registerMetric(httpRequestDuration)
register.registerMetric(httpRequestTotal)

// Middleware
app.use((req, res, next) => {
  const start = Date.now()
  res.on('finish', () => {
    const duration = (Date.now() - start) / 1000
    httpRequestDuration.labels(req.method, req.route?.path, res.statusCode).observe(duration)
    httpRequestTotal.labels(req.method, req.route?.path, res.statusCode).inc()
  })
  next()
})

// Expose metrics endpoint
app.get('/metrics', async (req, res) => {
  res.set('Content-Type', register.contentType)
  res.end(await register.metrics())
})
```

Prometheus alert rules:

```yaml
groups:
  - name: alerts
    rules:
      - alert: HighErrorRate
        expr: rate(http_requests_total{status_code=~"5.."}[5m]) > 0.1
        for: 5m
        labels: { severity: critical }
        annotations:
          summary: 'Error rate above 10%'
          description: 'Five-minute error rate is spiking. Go look.'

      - alert: HighResponseTime
        expr: histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m])) > 2
        for: 5m
        labels: { severity: warning }
        annotations:
          summary: 'P95 response time over 2 seconds'
          description: 'Endpoints are slowing down. Check for slow queries or cache invalidation.'

      - alert: ServiceDown
        expr: up{job="nodejs"} == 0
        for: 1m
        labels: { severity: critical }
        annotations:
          summary: 'Service is DOWN!'
```

Note `for: 5m` — alert only if the condition persists for 5 minutes. This prevents false alarms from momentary spikes. Getting woken up at 1 AM by a false alert is the absolute worst.

### What monitoring doesn't solve

Monitoring tells you "there's a problem." It doesn't tell you "here's how to fix it." The curve goes up, you know which layer (app vs. database), but the specific slow query, the exact memory leak — that takes your experience and investigation. Monitoring is the eyes. Fixing is the hands.

And monitoring itself doesn't prevent problems. It helps you catch them early, but things will still break. That's why monitoring and self-healing (auto-restart, auto-scaling) go together.

## 8. Weigh It Yourself — A Few Questions to Carry With You

That's everything I wanted to share. But I'm not going to give you a summary — you just read it all, you don't need me to repeat it.

Instead, here's a set of questions. Think of them as a measuring tape — next time you face a new project or a new system, you can size it up yourself.

### Question 1: Where's your actual bottleneck?

Don't deploy the whole arsenal blindly. Locate the bottleneck first. Open your monitoring dashboard. Watch four things: CPU, memory, network, disk. Whichever curve spikes first — that's your bottleneck.

- CPU pegged first → add app instances, more workers
- Memory full first → find the leak, add cache, evict infrequently-accessed data
- Network slow first → CDN, reduce payload, compress
- Disk IO saturated first → caching, reduce database queries

Don't optimize a place that isn't slow. CPU at 20% and you're adding machines? Pure waste.

### Question 2: What's your traffic now? What will it be in a year?

Ten thousand vs. a million — two orders of magnitude apart. The solutions are completely different.

- DAU < 10K: monolith + single DB + Nginx reverse proxy. That's enough. Really.
- DAU 10K-100K: add Redis caching, database read/write split, PM2 clustering. Don't jump to microservices yet.
- DAU 100K-1M: sharding, microservice decomposition, async via message queues. Complexity rises, but you genuinely need it.
- DAU 1M+: multi-DC active-active, full-link load testing, service mesh. At this scale, architectural complexity itself is a resource you have to manage.

### Question 3: How much downtime can you tolerate?

- 5 minutes is totally fine → single-server deployment, manual restart if it dies. Simple is good.
- Not even 1 minute → high availability (failover, auto-recovery). Complexity doubles. Cost doubles.
- Not even 1 second → multi-DC active-active. The cost isn't 2x. It's 10x. Data consistency, network latency, operational burden — all explode.

Most companies can honestly tolerate 5 minutes. Don't chase "zero downtime" prestige and end up with a mountain of redundancy you don't need — that's all money and technical debt.

### Question 4: Are you protecting "everything works" or "core functions work"?

On Singles' Day, Taobao's entire transaction chain is protected to the extreme — ordering, payment, inventory deduction — none can fail. But "My Orders" can lag a few seconds or even temporarily disappear, and users will tolerate it.

This is called **degradation**. Core path gets every safeguard. Non-critical features can auto-degrade or shut off during peak load. Does your system have this line drawn?

### Question 5: How many machines and how much money?

Technology choices eventually hit a wall called cost. Redis Cluster costs way more than single-instance Redis. Multi-DC active-active bandwidth bills are counted in terabytes. Kubernetes cluster management isn't free either — you need people who can operate it.

Start with the minimum to run stable, then add gradually as you grow. Premature optimization is the root of all evil — I've verified this across dozens of systems. Every single time, it holds true.
