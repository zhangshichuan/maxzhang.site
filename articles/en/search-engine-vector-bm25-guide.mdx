## The Day I Searched for Something and Everything Went Wrong

A while back, I searched my notes for `OOM Killer`.

The search system I had built was pure vector retrieval — the kind that tries to "understand what you mean." I hit Enter and waited for it to pull up my note on the Linux kernel mechanism that kills processes when memory runs out.

The top three results?

- "Out of memory error debugging guide"
- "What to do when your process gets killed"
- "Container resource exhaustion handling"

These documents were semantically adjacent to OOM. Sure. But goddammit — the note I wrote about OOM Killer didn't use the phrase "out of memory" even once. It used the exact term `OOM Killer`. And my search system, in its infinite wisdom, fed me everything that _felt_ related while skipping the one note with the literal search term in its title.

That's the most infuriating thing about vector search. It's too smart. Smart enough to gloss right over the keywords staring you in the face.

So I added BM25 as a fallback. Same query, same system. The `OOM Killer` note shot straight to number one. Because BM25 doesn't give a damn about "understanding." It counts words.

That experience forced me to re-examine — start to finish — what a real search engine should actually look like. Here's everything I figured out along the way.

---

## Layer One: What You're Actually Asking the Machine to Do

Every time you hit Enter in a search box, four things happen behind the scenes. Doesn't matter if it's ChatGPT's search, Notion's doc search, or a RAG pipeline you built yourself. The skeleton is the same:

```
You type "nginx stream proxy_bind config"
    │
    ▼
┌─────────────────────────────┐
│  1. Turn your query into     │
│     a vector                 │
│     (768 floating-point      │
│      numbers)                │
└─────────────┬───────────────┘
              │
              ▼
┌─────────────────────────────┐
│  2. Vector Recall (primary)  │
│     Find the K most similar  │
│     document vectors via     │
│     HNSW. Milliseconds.      │
└─────────────┬───────────────┘
              │
              ▼
       Top score < threshold?
       ├── Yes ──▶ BM25 Fallback
       │          (inverted index + keyword match)
       │
       └── No ──▶ Use vector results directly
              │
              ▼
┌─────────────────────────────┐
│  3. Merge + Deduplicate      │
│     Combine both result      │
│     sets, remove duplicates  │
└─────────────┬───────────────┘
              │
              ▼
┌─────────────────────────────┐
│  4. Rerank                   │
│     A heavier model re-scores│
│     the candidates.          │
│     Top 10 returned.         │
└─────────────┬───────────────┘
              │
              ▼
         Results to you
```

Four steps. But every step hides a mountain of engineering decisions.

You might wonder: why split recall and rerank? Why two passes instead of one? Isn't four stages over-engineering?

It isn't. You'll see why in a minute.

## Layer Two: Vector Recall — How It "Understands" You

### First, appreciate how wild this actually is

Imagine you run a Q&A system with tens of thousands of technical docs.

Someone asks: "How to drop weight fast?"

A traditional search engine would split the query into words — "how," "drop," "weight," "fast" — then hunt for documents containing those words.

Here's the problem.

Your knowledge base contains an article titled "Most Effective Weight-Loss Methods." It doesn't contain the word "drop" anywhere. It doesn't have "fast" as a standalone word. A traditional engine scans this document and says: irrelevant.

Seriously. Look at those two sentences. Are they talking about the same thing?

This is where vector recall earns its keep: **"How to drop weight fast" and "Most effective weight-loss methods" share almost no vocabulary, but after encoding, their vectors sit right next to each other in 768-dimensional space.**

Next to each other. That's the part that matters.

### What the hell "768-dimensional space" actually means

You hear "768-dimensional vector" all the time, but almost nobody explains what it actually is. Let me try.

"768 dimensions" isn't mystical. It's an array of length 768, each slot holding a float.

Take "The cat eats fish." Feed it through BERT. What comes out looks like this:

```
[0.52, -0.13, 0.89, 0.01, ..., -0.32]   ← 768 numbers total
```

Now imagine it as a coordinate point in 768-dimensional space.

A 2D coordinate is `(x, y)`. Two numbers.

A 768D coordinate is `(v₁, v₂, v₃, ..., v₇₆₈)`. 768 numbers.

In 2D space, you can see whether two points are close. In 768D space, you can't — but a computer can compute it.

"Pets enjoy eating fish" — encode it. Those 768 numbers will, as a whole, sit close to the 768 numbers for "The cat eats fish."

"Flights from Beijing to Shanghai" — encode it. Those 768 numbers will be in a completely different neighborhood.

That's it. That's the entire mechanism.

### A single text → a vector, shape always `(768,)`. What about multiple texts?

Here's something people confuse constantly.

A single text's vector is always one-dimensional — a flat list, shape `(768,)`.

If you feed three sentences at once, the output isn't three separate vectors. It's a single `(3, 768)` two-dimensional array. Three 768-dim vectors stacked together.

In deep learning, these multi-dimensional data structures are all called **tensors**. The hierarchy:

| Dims | Name   | Example                                                                         |
| ---- | ------ | ------------------------------------------------------------------------------- |
| 0D   | Scalar | `5` — just a number                                                             |
| 1D   | Vector | `[1, 2, 3, 4]`, shape `(4,)`. The text vector you just saw lives here           |
| 2D   | Matrix | `[[1, 2], [3, 4]]`, shape `(2, 2)`. Batch-encoding 3 sentences gives `(3, 768)` |
| 3D   | Tensor | A color image is `(224, 224, 3)`: height × width × RGB channels                 |
| 4D   | Tensor | A 10-second video at 30fps is `(300, 224, 224, 3)`                              |

Back to search: an image is a 3D tensor inside the model. A video is 4D. But what lands in the vector database is always a compressed one-dimensional vector. ResNet squishes an image into `(2048,)`. VideoBERT squishes a video into `(4096,)`.

Once compressed, text, images, and video all become the same format: a flat array of floats. Search "a cat" and you might get cat photos back — because the text vector and the image vector got mapped into the same semantic space.

So here's the core distinction: **during model processing**, you keep the high-dimensional structure (spatial, temporal, color channels) to capture the richest features. **During storage and retrieval**, everything gets flattened to one dimension — because vector databases only know fixed-length flat arrays. They don't care whether the vector came from text, an image, or a video.

### Millions of vectors. How do you find the nearest ones fast?

Alright. You have 100 million documents. All encoded. All stored. User enters a query — you encode that too.

Problem: find the K document vectors nearest to the query vector.

If you compute distance one by one — 100 million distance calculations per search. Latency explodes. Completely unusable.

This is what **ANN (Approximate Nearest Neighbor)** search solves. The current king is **HNSW (Hierarchical Navigable Small World)**.

Let me explain it with roads.

You're in a new city trying to find a restaurant:

- Top layer: highways. Cross the entire city fast, get near the target area.
- Next layer: main roads. Narrow down to a specific neighborhood.
- Bottom layer: local streets. Navigate to the exact doorstep.

HNSW works exactly like this. Top layers have few nodes with long edges (like highways). Lower layers get progressively denser with shorter edges (like small streets). During search, you ride the highways first, rapidly approach the target zone, then switch to local streets for precision.

Result: you only need to visit a tiny fraction of all nodes. No full scan.

Latency? Single-digit to low-double-digit milliseconds. Totally online-ready.

### Vector recall's fatal flaw — it guesses too much

The biggest problem with vector recall is the side effect of its greatest strength: **too much semantic sensitivity.**

Search "RTX 4090 graphics card." What do you actually want? Odds are you want documents that literally contain the text "RTX 4090."

But the vector model thinks these are close in meaning:

- "NVIDIA flagship GPU"
- "High-end gaming card recommendations"
- "Ada Lovelace architecture deep dive"

Semantically, all relevant. But your intent was exact keyword matching. In this scenario, semantic generalization becomes nothing but noise.

And here's the killer — the vector model can't tell you it's unsure. The similarity scores might all be mediocre, but it'll still return them. And the results will be completely orthogonal to what you wanted.

You need another player on the field.

## Layer Three: BM25 — The Stubborn One. Semantically Illiterate.

### Think of it as a guy who just counts words

BM25 doesn't care about "meaning." Its logic is one sentence: **the more a query's terms appear in a document, and the rarer those terms are across the entire collection, the higher the score.**

Two things to notice:

1. Rarer terms get higher weight per hit. "RTX4090" — appears in maybe three documents. A single hit is massive. "the," "is," "of" — appear in every document hundreds of times. A hundred hits mean almost nothing.

2. More occurrences in a single document help, but with diminishing returns. A term appearing 100 times versus 50 times barely changes the score. This is one of BM25's improvements — it prevents long documents from winning by keyword spamming.

This is TF-IDF thinking, evolved. BM25 fixes the original TF-IDF's bugs — like long documents getting unfairly penalized, or the absurdity of a term appearing 20 times scoring twice as high as 10 times.

### It owns one scenario absolutely

Go back to my failed search at the beginning.

Searching `OOM Killer`, BM25 does what? It splits the query into the tokens `OOM` and `Killer`, hits the inverted index, and finds documents containing both. If a document contains the exact phrase "OOM Killer," bonus points.

It will never return "Out of memory error" — because those tokens simply aren't in there.

**For exact matching on rare terms, proper nouns, config parameters, commands, version numbers — BM25 is a hundred times more reliable than vector recall.**

That's why your search system cannot be vector-only.

### BM25 is not Elasticsearch. Let me say this once and never again.

Alright, I need to nail this down because people confuse these constantly. It drives me nuts.

**BM25 is an algorithm.** A mathematical formula proposed by Stephen Robertson in 1994. It belongs to the probabilistic retrieval model family. You open a Python script, `pip install rank-bm25`, and you're running it in a dozen lines. It's a function — input: query and document. Output: a score.

**Elasticsearch is a product.** A distributed search engine built on Apache Lucene. Since version 5.0, ES defaults to BM25 as its scoring algorithm. But under the hood, it runs far more than just that formula — tokenizers, inverted indexes, distributed document routing, aggregations, highlighting. None of those have anything to do with BM25.

So when someone tells you "we use BM25," listen politely. 99% of the time they mean "we use Elasticsearch or Solr or Lucene with BM25 scoring inside."

And another classic: "the inverted index is part of BM25."

No. Just no.

The inverted index is a data structure. Turn to the index page at the back of a book — that page _is_ an inverted index. "Quantum mechanics, page 34." It saves you from flipping through every page to find a term.

BM25 is a scoring function that runs on top of that data structure. "Use the book's index to find all pages containing 'quantum mechanics,' then score each page."

The inverted index is the hammer. BM25 is the swing. Not the hammer and the toolbox.

## Layer Four: Fallback — Not a Spare Tire. A Seatbelt.

### What "fallback" actually means

"Fallback" is a bad word. It sounds like a last resort — a backup plan you fire only when the main thing breaks.

In many real search systems, BM25 and vector recall run **in parallel.**

What does that mean?

Every query hits both paths simultaneously. Vector retrieval returns one batch of results. BM25 returns another. Both sets get merged, deduplicated, and fed together into the reranker. Exact-match signals and semantic-match signals all flow into the final decision. Nobody has priority. Nobody is the backup.

So why still call it a "fallback"?

Because vector recall has two specific scenarios where it drops the ball. When it does, BM25 is underneath, catching you, keeping you from returning nothing.

### Vector recall's Achilles heels

Two scenarios:

**One: the query is too short or too vague.** User types `bug`. What kind of bug? Code defect? Insect? Listening device? The vector model guesses. Similarity scores are low across the board.

**Two: the query is stuffed with hyper-specific proper nouns and parameters.** "nginx 1.27.3 stream module proxy_bind configuration" — holy shit. The vector model has almost certainly never seen this exact combination during training. Recall quality tanks.

The fallback logic is a single conditional:

```python
def search(query):
    vector_results = vector_search(query)
    if vector_results.top_score < THRESHOLD or len(vector_results) == 0:
        return bm25_search(query)
    return vector_results
```

Top vector score below a preset threshold? Switch to BM25. That's it.

### How to pick the threshold — no, it's not derived from a formula

Nine out of ten people, the first time they encounter this design, ask: "Is there a formula for this threshold?"

Answer: **there isn't. You find this number by iterating.**

Here's the process:

**Step one: build labeled data.** Gather real user queries. Manually label which documents are relevant for each query. This step is the most painful. It's also the one that makes or breaks everything downstream.

**Step two: plot the distribution.** Run vector recall on all queries. For each query, record the similarity scores of the relevant documents. Draw a histogram.

You'll see something like:

```
Similarity Range    % of relevant docs
─────────────────────────────────────
0.8 - 1.0           ████████████████  40%
0.7 - 0.8           ██████████████    35%
0.6 - 0.7           ████████          15%
0.5 - 0.6           ████              7%
0.4 - 0.5           ██                3%
```

Those numbers are made up. They're just to show you the shape of the thinking.

**Step three: pick a quantile.** If 90% of relevant documents score above 0.55, set the threshold somewhere around 0.5–0.55. In practice, cosine similarity thresholds tend to land between 0.4 and 0.6.

**Step four: launch, then keep tuning.** Offline distributions can't capture real user behavior. Once live, watch your fallback trigger rate, click-through rate, and zero-result rate. Those are the real signals. Iterate.

One more thing — **different businesses need different thresholds.**

E-commerce product search: lower the threshold. Showing too many results beats showing none. A user who sees zero results leaves.

Medical literature search: raise the threshold. Showing irrelevant results is more dangerous than showing fewer. Hand a doctor a paper that looks relevant but isn't? You're asking for trouble.

## Layer Five: Reranking — The Finals

### Why you can't do precision in the first pass

Your document corpus might hold ten million documents. The recall stage (vector + BM25) has a millisecond-level time budget. Its job: fish out a few hundred candidates from ten million — without missing the good ones.

The goal is coverage.

Once you're at the rerank stage, you're down to a few hundred candidates. Now you can bring out a heavier, more precise model. Score each one carefully. "Which one is truly the best match for this query?"

The goal is precision.

If you try to run the rerank model at the recall scale, a single math problem will humble you:

Cross-Encoder processes one document in roughly 10–50ms. Multiply by ten million documents. Fifty thousand to two hundred eighty thousand seconds. Search once, wait half a day.

That is not workable.

So you have to split.

|                 | Recall                       | Rerank                       |
| --------------- | ---------------------------- | ---------------------------- |
| Candidate count | Millions to billions         | Dozens to hundreds           |
| Latency budget  | Milliseconds                 | Hundreds of milliseconds     |
| Model           | Simple (dual encoder / BM25) | Heavy (Cross-Encoder / GBDT) |
| Goal            | Don't miss                   | Get the top ones right       |

This architecture isn't an ideal design. It's the compromise that scale and latency shove down your throat.

### Which rerank model to use

**Cross-Encoder.** Best quality. Slowest speed.

Concatenate query and document. Feed them into BERT together. The two texts cross-interact from the very first layer. Attention mechanisms in every layer look at both sides. Output: a single relevance score.

This thing catches subtle stuff — negations, conditionals, word order. "The system does not require a restart" and "The system requires a restart" look almost identical to a dual encoder. A Cross-Encoder immediately tells them apart.

The price: every candidate requires a full forward pass. You can't precompute document vectors like you do with dual encoders. So you can only use it on a few hundred candidates.

**ColBERT and other late-interaction models.** A compromise.

Encode documents and queries independently first (cheap). Add a lightweight interaction step at the end (accurate). On many benchmarks, these get close to Cross-Encoder quality while running much faster.

**GBDT / LambdaMART.** Not deep learning.

Inputs go beyond vector similarity scores — BM25 scores, document publish date, historical CTR, author authority. All fair game. Interpretable. Easy to tune manually. If your business demands ranking logic that humans can understand and tweak, tree models beat neural nets.

Honestly, in real projects, **you almost never need to train a rerank model from scratch.** Grab `cross-encoder/ms-marco-MiniLM-L-6-v2` off HuggingFace. Fine-tune on your labeled data. That covers the vast majority of use cases.

## Layer Six: Chunking — If Your Foundation Is Crooked, the Tower Falls

### One bad case is worth a thousand arguments

I've seen too many people pour energy into picking embedding models and tuning rerankers while treating document chunking as an afterthought — "just split at 512 tokens and call it a day."

They don't even know what they're splitting.

Look at this:

> Original text: "The system uses PostgreSQL as the primary database because of its excellent concurrency control."

Hard-split by character count could give you:

- Chunk A: "The system uses PostgreSQL as the primary database because"
- Chunk B: "of its excellent concurrency control."

You think Chunk A and Chunk B produce good vectors?

Chunk A's sentence isn't finished. Chunk B has no subject — it reads like some random thing has excellent concurrency control. Both chunks carry crippled semantics. No embedding model can reconstruct the full meaning from half a sentence.

But split at the period — this single sentence becomes one chunk. Semantics intact. Vector accurate.

I don't exaggerate when I say: **chunking quality is this system's ceiling.** Screw up the chunking, and everything downstream — embedding, recall, reranking — is optimization on a broken foundation. Pointless.

### Three rules of thumb

**Split on semantic boundaries. Not fixed character counts.**

At minimum, respect sentence terminators and paragraph breaks. Semantic splitters from libraries like `text-splitter` work even better. Fixed token counts (e.g., 512) can be a safety cap — but they cannot be your only strategy.

**Add overlap between adjacent chunks.**

10%–20%. Prevents critical information from being sliced right at the chunk boundary — where half lives in one chunk and half in the other, and neither side retrieves well.

**Keep contextual metadata.**

Which document did this chunk come from? What's the document title? Which section? This data is incredibly valuable during reranking. Two chunks with similar scores? The one from a more authoritative document should rank higher. But you have to record this information first.

## Layer Seven: Embedding — Picking a Model Is Picking a Cost-Performance Ratio

### General-purpose or domain-specific?

If your documents are broad — news, Wikipedia, general Q&A — just use `text-embedding-3-large` or `bge-large-en`. Done. Don't overthink it.

But if your documents are specialized — medical papers, legal contracts, internal code docs — a general model's semantic space probably doesn't align well with your data. It hasn't seen your domain's vocabulary and relationships. Vector quality degrades.

Two paths: either fine-tune a general model on your domain data, or use a domain-specific model (like a BioBERT-based embedding variant).

### Bigger is better? Bullshit.

A 1024-dim model might beat a 768-dim one by 1–2% on precision. But storage and compute costs jump 30% or more.

At millions of documents, 30% is real money — more disks, more RAM, slower retrieval.

When choosing dimensions, open your cost spreadsheet. Don't just stare at benchmark tables from some paper. Cost-performance is the only engineering metric that matters.

### The most overlooked engineering trap — ongoing maintenance

Vectors aren't fire-and-forget.

Documents updated? Regenerate vectors. New documents arriving? Incrementally build indexes. Old documents deleted? Remove them from the vector database.

If this incremental sync pipeline isn't designed well, your search system will periodically start returning stale results. Consistency is the most neglected engineering cost in embedding pipelines.

## Layer Eight: The Inverted Index — How BM25 Gets That Fast

### Forward indexing is caveman logic

You have a thousand books. Find every one that mentions "quantum mechanics."

The forward-index approach: start at page 1 of book 1. Scan line by line. Through all thousand books. Then tell the user the answer.

That's not an algorithm. That's manual labor.

### The inverted index flips it

An inverted index doesn't record "what words are in each book." It records "which books contain each word."

Two parts:

**Term dictionary.** Every unique word that appears in the collection, stored in sorted order. Find a word: binary search. O(log N).

**Posting list.** Under each word, a list recording which documents it appears in, at which positions, and how many times.

Looks like this:

```
"cat" → [(doc_id=5, tf=2, positions=[10, 205]),
         (doc_id=23, tf=1, positions=[67]),
         (doc_id=108, tf=3, positions=[...])]

"dog" → [(doc_id=3, tf=1, positions=[89]),
         (doc_id=5, tf=1, positions=[150])]
```

### Where the speed comes from

Search "cat dog":

1. Look up "cat" in the term dictionary → get its posting list (all document IDs containing "cat").
2. Same for "dog" → another posting list.
3. AND logic → compute the **intersection** of both lists. OR logic → compute the **union**.
4. Score results with BM25. Sort. Return.

At no point does the system "scan every document." It's like walking into a library and, instead of flipping through shelves, opening the index at the back of a book, finding your keyword, and jumping to the right page.

Every serious full-text search engine on the planet runs on this principle.

### There's still room to squeeze

Lucene adds **skip lists** and **compression encodings** on top of posting lists.

Skip lists accelerate intersection of two large lists — think merge-sort on steroids. Compression reduces memory footprint — store more document IDs in fewer bytes.

Lucene and Elasticsearch push these optimizations to the industrial limit. Even at hundreds of billions of documents, a single keyword lookup stays in the low tens of milliseconds.

## Layer Nine: Offline Does the Heavy Lifting. Online Stays Lean.

You have to understand: a search engine runs on two completely independent timelines.

### Offline (invisible to users, always running in the background)

1. Documents arrive → split into chunks.
2. Each chunk goes through the embedding model → vectors generated.
3. Vectors written to the vector database → HNSW or IVF indexes built.
4. Inverted index built in parallel → for BM25.
5. Document updates → incremental sync across all indexes.

This is computationally heavy. Usually batch-processed on CPU or GPU clusters. No user requests touch this path, so latency doesn't matter. Focus is on throughput and consistency.

### Online (what you feel every time you hit Enter)

1. Receive query → vectorize it.
2. Vector recall (primary) + optional BM25 fallback.
3. Merge, deduplicate.
4. Rerank model scores the candidates.
5. Return Top N.

This path is brutally latency-sensitive. Search response over 200ms? Feels sluggish. Over 1 second? You're annoyed. Over 3 seconds? You've already opened a different product.

The two-tier principle, stated plainly: **everything that can be precomputed goes offline. The online path is stripped to its absolute minimum.**

## Layer Ten: What Happens When You Try to Merge Stages

You'll get the urge sometimes — "what if I combine these two steps? Save a round of computation."

Don't. I've done the math for you.

**Embedding + Recall merged.** "Encode and search simultaneously." A single BERT forward pass takes tens of milliseconds. Multiply by millions of documents. You'll be waiting until sunrise. Embedding must stay offline.

**Recall + Rerank merged.** Cross-Encoder takes 10–50ms per document. Ten million documents — 50,000+ seconds. Search once, wait over a dozen hours. Think your users will stick around?

**Chunking + Embedding merged.** One is mostly rule-based (CPU-bound). The other is neural network inference (GPU-bound). Merge them and both sides lose efficiency. Run them separately on their preferred hardware — both go faster.

These separations aren't architectural aesthetics. They exist because, at this scale and this latency budget, **you cannot avoid splitting them.**

## The End — Not a Summary. A Judgment Framework.

The entire search architecture, flattened out, is one funnel:

```
All documents (millions to billions)
    │
    ▼ Recall (milliseconds, broad coverage)
Hundreds of candidates
    │
    ▼ Rerank (hundreds of ms, high precision)
Top 10
```

Every layer answers the same question: **given the time I have, how do I make the results as useful as possible?**

But when you're building something yourself, stop asking "which model scores highest?" That's a 2018 question.

Ask yourself these three questions:

**1. What do your users actually search for?**

If they search "how to debug memory leaks" — vector recall works great.

If they search "RTX 4090 TDP specs" — BM25 is your savior.

Before doing anything else, spend half a day looking at real user query logs. The shape of your data should determine the shape of your system.

**2. What's your latency budget?**

User patience is a hard line. Work backward from it. How much time can you spend at each step? Can embedding be faster? Can you drop dimensions? Tweak HNSW layers? Shrink rerank candidates? These are all answers that fall out once you're working backward from latency.

**3. Do your documents change?**

If your documents are static (a published book, a snapshot), run embedding once and forget about it.

If your documents update frequently (a collaborative knowledge base), your incremental sync pipeline matters more than anything else. Teams that cheap out on this always pay for it later.

Let me close with a card catalog analogy:

- **Document chunking** — tearing a whole book into individually searchable index cards.
- **Embedding** — stamping each card with a set of machine-readable "understanding scores."
- **Vector recall** — "find the cards that feel most like what I described." Semantic matching.
- **BM25** — "find the cards that literally contain the words I said." Exact matching.
- **Rerank** — spread both stacks on the table, read each card carefully, pick the best 10.

A search engine isn't good because it topped some benchmark. It's good because — **under your data, your users, and your latency budget — it doesn't fall over.**

One last note on RAG.

RAG is essentially taking the document list from "recall + rerank" and handing it straight to an LLM for summarization and generation.

If you understand search, you already understand most of RAG.

The rest is the LLM's business.
