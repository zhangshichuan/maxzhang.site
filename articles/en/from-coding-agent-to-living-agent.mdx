Wednesday, 2:30 PM. I'm refactoring a legacy project's CI config when Lark pings me with a message.

Not a coworker. Not my boss. It's the Hermes Agent running on my $5 VPS:

> "Staging CI failed at 14:12. Cause: Prisma migration checksum mismatch — you manually edited a migration file last Thursday without regenerating the checksum. I've generated a fix commit. Want me to push it to fix/prisma-checksum?"

I replied with one word: "Push."

Thirty seconds later:

> "Done. By the way, this is the second checksum issue this month. Want me to add 'auto-regenerate checksum after Prisma migration edits' to your pre-commit hook skill? That way we catch it before CI does."

I froze for a second. Not because it fixed a bug — Claude Code can do that too. What got me was the second part: **it remembered last time, and it was proactively improving its own process.**

This isn't a tool. This is something that's getting smarter.

I picked up my phone, replied "Add it."

Then put the phone down and went back to CI refactoring. But my mind kept circling one question: what's the fundamental difference between this thing and the Claude Code I've been using for almost a year?

Claude Code can fix bugs too. It can write code — sometimes better than I can. But it has never — not once — proactively said "hey, you made this same mistake last time, want me to help you prevent it?"

Never.

Because it doesn't remember there was a "last time."

# I. The Goldfish Memory Era of Agents

Have you ever had this feeling — every time you open Claude Code or Cursor, you have to tell it again that "we use Prisma not TypeORM," "we use pnpm not npm," "our ESLint is flat config"?

You've told it a hundred times. On the hundred-and-first, it still asks.

Or worse: you spend two hours discussing an architecture decision with it, finally settling on BullMQ for async queues and Redis for pub/sub — not Kafka, because your team's scale doesn't justify that complexity. Three days later you open a new conversation, ask it to design another async pipeline — and it suggests Kafka.

What the hell.

It's not messing with you on purpose. It genuinely doesn't remember. Every new conversation is the Big Bang — day one of the universe. All your discussions, all your decisions, all your context evaporates the instant that session ends.

Claude Code is like this. Cursor is like this. Copilot is like this. They're all goldfish — seven seconds of memory. Actually, not even seven seconds — one session's worth of memory.

You might say: "But Claude Code has CLAUDE.md! Cursor has .cursorrules! I can write project info in there."

Yes, you can. But that's **you** maintaining memory, not the Agent itself. You have to write it manually, update it manually, ensure it stays consistent with your actual project state. When was the last time you updated CLAUDE.md? A month ago? Two months? Does it still reflect your current tech stack?

This is fundamentally a "who bears the maintenance cost" problem. Every mainstream Agent's answer right now is: you maintain it. I'll just do my best within the current session.

This leads to a question I find increasingly important:

**Should an AI Agent you've used for three months be different from one you just installed?**

If your answer is "obviously yes" — congratulations, you and Hermes's designers are thinking the same thing.

If your answer is "doesn't matter" — you probably haven't experienced the crushing feeling of explaining the same thing to an Agent for the hundredth time. Come back to this article when you have.

# II. Four Types of Agent, Four Species

Before diving into Hermes, let me put every Agent product on a single map so you can see where they each stand. Not to compare specs, but to show you — they're not even answering the same question.

## Task Execution Type: Manus and Its Ilk

Manus was the hot Agent of early 2025. Give it a complex task — "research all AI Agent frameworks' GitHub stars trends for 2026 Q1, generate a comparison report, export as PDF" — and it automatically breaks it into steps, opens a browser, searches data, generates charts, exports files.

Looks incredible the first time. That "the future is here" feeling.

But after your tenth or twentieth use, you notice something: **it starts from zero every single time.**

The first time you ask for competitive research, it spends ages figuring out to check GitHub for stars. The second time? Still ages. The tenth time? Still ages. It never learns from attempt one that "oh, this person wants competitive research — just hit the GitHub API directly."

Why? Because Manus's design philosophy is "perfect execution of one-shot tasks." Its goal is maximizing single-task success rate, not making your second use faster. These are different objectives.

What Manus solves: **one-shot automation of complex tasks.**

What Manus doesn't solve: **cross-task experience accumulation.**

This distinction is crucial. If your use case is "every task is different" (like a researcher with different directions daily), Manus might be enough. But if you're an engineer where 80% of your work is "similar but not identical" — initializing projects, writing CRUD, configuring CI, doing code reviews — you need an Agent that carries past experience into the next task.

## Coding Assistant Type: Claude Code, Cursor, Copilot

This category has a narrower positioning: **help you autocomplete, refactor, and debug while you're writing code.**

Claude Code is currently the strongest in this category. It can read your entire project, understand the architecture, then write stylistically consistent new code. Its context window is massive — it can ingest dozens of files at once. Cursor is similar but wrapped in an IDE shell with better interaction. Copilot is pure completion — not deep enough in reasoning.

The problem?

They're "stateless expert consultants." Every time you consult them, they give their full effort. But they don't remember what they helped you with last time. They don't know you abandoned GraphQL for tRPC last month. They don't know your team's convention of wrapping all API responses in a Result type — unless you wrote it in CLAUDE.md.

You can use `.cursorrules` or `CLAUDE.md` to manually stuff in some context. But that's you maintaining a "memory file" — the Agent itself doesn't have this capability.

And these files have a fatal flaw: **they're static.** What you write in doesn't auto-update. Decisions made last week? You have to manually edit the file. Forgot to update? The Agent makes decisions using stale information.

I'll admit Claude Code's "single-shot execution ability" is currently the strongest. Having it write code, refactor a module, solve a bug — it does better than Hermes. But "single-shot execution ability" isn't the only dimension that matters.

## Platform-Locked Type: Coze, Various Agent Platforms

The defining feature: **you build Agents on someone else's platform. Data belongs to them. Models belong to them. Runtime belongs to them.**

Upside: low barrier — drag and drop to build a "chatbot that talks to customers." For non-technical users, this might be the only option.

Downside: you're betting all your chips on someone else's table:

1. **Model lock-in.** Coze only runs ByteDance's models (or a limited set). Can't just say "today I want to try DeepSeek V4" and switch.
2. **Data lock-in.** All your conversation history, workflow definitions, knowledge base data — on their servers. Want to migrate? Good luck.
3. **No local deployment.** Can't run it on your own VPS, your own intranet. For security-sensitive scenarios (handling client code), that's a deal breaker.
4. **Their "memory" is fake.** What they call "long-term memory" is often just stuffing previous conversation summaries into the system prompt. That's not memory — it's stretching the context window.
5. **No growth.** These platforms' Agents don't become more attuned to you after three months. Their behavior is entirely determined by your defined workflow — if you don't change the workflow, their performance doesn't change.

I'm not saying these products have no value. They do — for specific scenarios (customer service bots, content pipelines, simple data processing), they're cost-effective. But they're not "personal Agents," they're "automation platforms."

## Self-Evolving Type: Hermes

Then there's Hermes.

What fundamentally separates it from the other three? One sentence:

**A Hermes you've used for three months and a freshly installed Hermes are completely different Agents. A Claude Code you've used for three months and a freshly installed Claude Code are identical.**

Hermes treats "growth" as its first design principle. Not a feature. Not a plugin. The foundation. The entire system architecture — from Skills to Memory to User Model to Nudge mechanism — is designed around one core objective: **making this Agent more useful as usage time increases.**

This is a fundamentally different design philosophy. Not "how to help you better complete this one task," but "how to become someone who understands you better through the process of helping you do things."

Let's peel it apart layer by layer.

# III. The Learning Loop: Hermes's Core Engine

Hermes's self-evolution isn't a "note-taking" feature. It's a complete closed-loop system. I'll break it into four layers.

## Layer 1: Skills — Automatic Crystallization from Experience

This is the most mind-blowing design in Hermes.

When you ask Hermes to complete a complex task — say, "migrate this Express project to Hono, keeping all API endpoints unchanged" — it doesn't just finish the job and call it a day. After completion, it looks back at its own trajectory (execution trace) and evaluates: was this task complex enough? Is there a reusable pattern in the steps I took?

If yes, it **automatically creates a Skill.**

A Skill isn't a dead prompt. It's a structured procedural memory containing: trigger conditions, execution steps, tool chains used, caveats, and pitfalls encountered in previous executions.

Here's a concrete example. Say you ask Hermes to do "Node.js project initialization" three times:

- First time: It asks you a bunch of questions — what framework? What ORM? Docker? What CI? Then fumbles through the setup.
- Second time: It notices a reusable pattern in the previous trajectory, automatically creates a "Node.js project initialization" Skill. This execution is 40% faster because it no longer needs to reason through every step from scratch.
- Third time: You tell it "last time the Dockerfile didn't have cache mount, add it." It updates the Skill. This time the generated project includes cache mount directly.

More crucially — **Skills self-improve during use.**

The first version of a Skill might be rough. But next time you trigger the same scenario, Hermes executes using that Skill, then reviews afterward: anything to optimize? Any new edge cases? Then it updates the Skill.

By the third execution, the Skill has been refined through two iterations.

It's like a new hire: fumbling through something the first time, but a smart person writes down lessons learned afterward. Second time, they review those notes first — faster, better. Third time, it's muscle memory.

Claude Code doesn't have this. Manus doesn't have this. Coze definitely doesn't.

And Hermes's Skills are compatible with the [agentskills.io](https://agentskills.io) open standard — you can download Skills from the community Skills Hub, and share your own. This means Skills aren't just personal accumulation, they're community accumulation.

## Layer 2: Memory — Not Context Stuffing, Actual Modeling

Hermes's memory system operates on multiple dimensions, each solving different problems:

**1. Factual Memory (Memory entries)**

"This project uses Prisma." "Team convention is Result-type wrapping for API responses." "The boss hates `any` types." "Deployment uses Docker + GitHub Actions, not Jenkins."

These are factual snippets the Agent proactively records. You don't need to say "remember this" — during conversations, it automatically judges which information deserves persistence.

What's the criteria? Roughly: would this information be useful in future conversations? If yes, store it. If it's one-off chat content ("nice weather today"), skip it.

These memories are stored in a local SQLite database, not stuffed into the context window. Only when relevant scenarios arise are they recalled into the current context. This means memory volume isn't limited by context window size — you can accumulate thousands of memories, only retrieving when needed.

**2. User Model**

This goes deeper. Hermes integrates Honcho's dialectic user modeling — it doesn't just remember what you said, it's trying to understand **what kind of developer you are.**

Do you prefer functional or OOP? Readability or performance? What commenting style do you hate? What's your tech-selection decision logic? Are you a "ship an MVP first then optimize" person, or a "won't start until the design is right" person?

These aren't explicitly stored as "Max likes functional programming." They're an implicit model built gradually through multiple interactions. The longer the relationship, the better it knows you.

Why does this matter? Because the same "help me design this module's architecture" request should produce different answers for a simplicity-seeking engineer versus a robustness-seeking one. The User Model lets Hermes give answers that match **your** thinking style, not a generic "best practice."

**3. Cross-Session Search (FTS5)**

"What was that SQLite WAL mode pitfall we discussed last week?"

Hermes uses SQLite's FTS5 full-text search to index all historical conversations. You can ask about previous discussions — it finds them, summarizes them, provides context.

This isn't "scrolling through chat logs." It's **turning past conversations into a queryable knowledge base.**

Think about it — your conversations with an Agent contain tons of valuable technical decisions, solution discussions, problem analyses. Before, these vanished after the chat. Now they become searchable, referenceable knowledge assets.

**4. Memory Lifecycle Management**

A point many overlook: memory isn't just "store everything, delete nothing."

Stale memory is more dangerous than no memory. If Hermes still "remembers" you used TypeORM three months ago, but you've actually migrated to Prisma — decisions based on stale memory will be wrong.

Hermes's Memory system has active management: when new information conflicts with old memory, it updates or replaces the old. Not simple appending — it's a living system with additions and removals.

## Layer 3: Nudge — Proactive Knowledge Persistence

A small but important design: Hermes **proactively reminds itself** to persist knowledge.

What does this mean? After a complex conversation ends, a normal Agent just... ends — context closes, everything vanishes. Hermes self-nudges as a conversation wraps up: hey, was there anything worth remembering in that discussion? Anything that should become a Skill? Any User Model updates needed?

This nudge mechanism means Hermes doesn't depend on users explicitly saying "remember this." It autonomously "leaves traces."

Why is this design so important? Because humans are lazy. You won't say "hey, remember this" after every conversation. Most of the time you just close the chat. If the Agent depends on you to trigger memory storage, 90% of valuable information gets lost.

The Nudge mechanism takes that responsibility off you and puts it on the Agent. You just use it normally; it handles the "learning" itself.

## Layer 4: Trajectory — Paving the Road for Next-Gen Models

This layer doesn't directly affect your experience, but it determines Hermes's long-term evolution path.

Hermes can record the complete execution trajectory of every task — including user requests, Agent reasoning, tool calls, intermediate results, final output. These trajectories can be used to:

1. Train better tool-calling models (Nous Research is doing this themselves)
2. Compress into training data so next-gen models "ship with" these capabilities
3. Local trajectory replay and debugging (you can review why the Agent made a wrong decision)

This means Hermes's evolution isn't just "single Agent instance evolution" — it's "entire model family evolution." The trajectories you produce using Hermes ultimately help Nous Research train better base models, which feed back into Hermes — a community-level learning flywheel beyond a single machine.

# IV. From OpenClaw to Hermes: Not an Upgrade, a Rebirth

If you follow the open-source Agent community, you might have heard of OpenClaw. It's Hermes's predecessor — an AI Agent that runs in the terminal, calls tools, has a persona, has basic memory.

Hermes's README still has a `hermes claw migrate` command for OpenClaw users to migrate. You can import your previous SOUL.md (persona), MEMORY.md (memory), skills, API keys, even messaging platform configs.

So why the "rebirth"? Wasn't OpenClaw good enough?

It wasn't bad — it just **wasn't answering a big enough question.**

OpenClaw's memory was a `MEMORY.md` file. You manually wrote things in it, the Agent read it. Skills were markdown files you created by hand — you had to decide what to abstract into a Skill, write the content yourself, decide when to trigger it. Persona was a `SOUL.md` — also manually maintained.

Does it work? Sure. But it's all **manually maintained.**

Manual maintenance means the burden is on you. You have to remember to update MEMORY.md, summarize Skills yourself, manage Persona yourself. Given enough time, you stop updating. I'd bet 90% of OpenClaw users updated MEMORY.md in the first month, then let it rot by month two.

Then those files become outdated waste paper. The Agent reads three-month-old MEMORY.md and makes decisions about a completely changed project. This is worse than having no memory — at least no memory doesn't actively mislead with wrong information.

What Hermes did: **turned manual maintenance into an automatic closed loop.**

|                    | OpenClaw                 | Hermes                                                     |
| ------------------ | ------------------------ | ---------------------------------------------------------- |
| Memory             | Manually write MEMORY.md | Auto-detect + proactive persistence + lifecycle management |
| Skills             | Manually create markdown | Auto-generate from trajectories + self-improve             |
| User understanding | A static SOUL.md         | Dialectic user modeling, continuously evolving             |
| Cross-session      | None                     | FTS5 full-text search + LLM summarization                  |
| Nudge              | None                     | Auto-triggered knowledge persistence                       |
| Skill sharing      | None                     | agentskills.io open standard                               |
| Model training     | None                     | Trajectory generation + compression                        |

This isn't "a few new features." It's going from "human-driven tool" to "self-driven system."

Analogy: OpenClaw is you carrying a notebook, writing notes after each task. Hermes is the notebook writing its own notes, organizing them, pulling them up when you need them, and periodically tearing out outdated pages.

This leap wasn't a sudden epiphany from Nous Research. If you look at Hermes's git log, you'll find that the densest commits during the OpenClaw-to-Hermes transition focused on three areas: Skills engine automation, Memory structured management, and Nudge mechanism introduction. All three consistently point to one goal — **automating away things humans used to have to do, one by one.**

First, Skills no longer needed manual writing. Then Memory no longer needed manual maintenance. Then even "reminding yourself to store things" got automated.

Each step reduces dependence on human intervention. Not because "automation is cool," but because **only by removing the burden of manual maintenance can the learning loop truly operate.** The moment a human forgets or gets lazy, the loop breaks. Only when the system does it itself can we guarantee "every interaction won't be wasted."

That's the key leap from "tool" to "system." Tools wait for you to operate them. Systems know what to do themselves.

# V. Why Not Manus

Let me be blunt.

Manus had its moment. "Manus-like" products exploded even more — every startup claiming "one sentence does everything," "fully automated workflow," "AI that replaces your team." From 2025 into early 2026, the space became a bloodbath. Every month a new product claimed to "surpass Manus" with increasingly impressive demo videos.

But after using them, my takeaway is: **they solve "automation" problems, not "personalization" problems.**

What's an "automation" problem? "Summarize these 50 PDFs into a table." "Turn this data into charts." "Research competitors for me."

These tasks share a trait: **they're stateless.** Anyone doing them produces roughly the same result. No need to understand "you" — your preferences, your history, your decisions.

Manus excels here. It's a great automation machine.

But "personalization" problems are entirely different. Let me give concrete examples:

- "Help me design this module's architecture" — requires knowing your tech stack, team size, performance requirements, your personal architecture preferences.
- "Help me refactor this code" — requires knowing your code style, patterns you hate, what you consider "clean."
- "Does this PR look problematic?" — requires knowing your team's code review standards, what you've historically focused on in reviews.
- "Help me write a reply to this client" — requires knowing your tone, your history with this client, what you've previously discussed.

These tasks share a trait: **the answer depends on "who you are."** Same question to different people, different optimal answers.

Manus can't do this. Because it doesn't remember you. Every time it's a fresh it meeting a fresh you.

And Manus has a more fundamental issue: **cloud-based black box.**

You can't see what it's doing. You don't know which webpage it opened, which button it clicked, what intermediate results it used. It operates in a cloud browser — you only see the final result, the intermediate process is opaque.

For developers, this is unacceptable. I need to know what my tools are doing. If it makes a mistake, I need to debug, reproduce, understand why. Black-box execution means you can only pray when things go wrong.

Hermes runs on your own machine. Every operation, every tool call, every decision process — visible. You can interrupt it, redirect it, correct it. It's transparent.

One last point: Manus is a commercial service with token quotas, pricing, and call limits. Hermes is open source (MIT license) — unlimited use with your own API keys calling any model. Long-term, which is more controllable?

# VI. Why Not Platform Products

Coze, Wenxin Agent, Tongyi Agent Studio, MiniMax's Agent platform, various startup "Agent platforms"... I've tried most to varying degrees.

Their shared problem in one phrase: **living under someone else's roof.**

## Model Freedom: None

On Coze you can only use ByteDance's models. On Wenxin, only Baidu's. Want to try DeepSeek V4 or Qwen3? Sorry, platform doesn't support it.

Why does this matter? Because LLM development moves too fast. Today's best model might not be in three months. If you're locked to a platform's models, you can only ever use "the best one this platform currently integrates," not "the best one currently available on the market."

Hermes's `hermes model` command — one tap, 200+ models. OpenRouter's full catalog, OpenAI, Anthropic, DeepSeek, Qwen, Nous's own models, even your local Ollama. Use Claude today, switch to DeepSeek tomorrow, try an open-source model the day after — zero lock-in.

## Data Freedom: None

Everything you accumulate on platforms — workflows, knowledge bases, conversation history, user profiles — stored on their servers. If pricing changes, policies shift, or (more realistically) the platform shuts down — your accumulation is gone.

From 2025 to 2026, how many AI startups folded? Countless. Do you dare build core workflows on a platform that might not exist next year?

Hermes keeps everything in `~/.hermes/` — SQLite database + local files. cp, backup, migrate anytime. Even if Nous Research dissolved tomorrow (unlikely, but hypothetically), your local Hermes still runs — just switch model providers.

## Environment Freedom: None

Their Agents run in their sandboxes. Can't operate your local filesystem, Git repos, Docker containers, SSH servers.

Hermes supports seven terminal backends:

1. **Local** — execute commands directly on your machine
2. **Docker** — execute in containers, security isolated
3. **SSH** — connect to remote servers
4. **Singularity** — HPC cluster scenarios
5. **Modal** — serverless, hibernates when idle, wakes on demand
6. **Daytona** — serverless dev environments, persistent workspaces
7. **Vercel Sandbox** — frontend project rapid prototyping

Run it wherever you want. Operate whichever server you want. This flexibility is something platform products can never give you.

## Real vs Fake Memory

I've tested several platforms' "long-term memory" features. Here's how they actually implement it:

1. Stuff summaries of previous N conversation turns into the system prompt
2. Store historical conversations in a vector database, do similarity search to recall "relevant" entries
3. Have the LLM generate a "memory summary" at the end of each conversation, stuff it into context next time

Their shared problem: **no structured memory management.** They don't know which memories are stale, don't understand priority between memories, don't know when to update versus delete. Result: context gets stuffed with a pile of "maybe useful, maybe outdated" text, and the model has to figure out what's currently valid — often getting it wrong.

Hermes's Memory is structured storage with active management. It knows which memories are factual, which are preference-based, which are stale and need updating. Each memory has a clear semantic type — not undifferentiated text fragments.

# VII. Hermes's Technical Architecture: How It Achieves All This

After all the "what it can do," let's discuss "how it does it." Not too deep — this isn't a source code analysis article — but you need the architectural picture to understand its boundaries.

## Agent Loop

Hermes's core is an Agent Loop:

```
User input → Model reasoning → Tool call → Result processing → Model reasoning → ... → Final reply
```

This loop itself isn't novel — all Agents follow this pattern. What's special about Hermes is the loop's "surrounding infrastructure":

- **Before entering the loop**: Recall relevant memories, check for available Skills, load User Model
- **During loop execution**: Record complete trajectory, support user interrupt and redirect anytime
- **After loop ends**: Nudge mechanism triggers, evaluating whether Memory/Skill/User Model needs updating

All this "surrounding infrastructure" collectively forms the learning loop.

## Gateway Architecture

Hermes isn't terminal-only. It has a Gateway process connecting various messaging platforms:

- Lark
- Discord
- Slack
- WhatsApp
- Signal
- Email

One Gateway process + one Agent process lets you talk to the same Agent from any platform. All platforms share the same Memory, same Skills, same User Model.

This means you discuss an architecture plan in your terminal, then ask on Lark "what was point three of that plan?" — it knows. Cross-platform continuity.

## 40+ Built-in Tools

Hermes ships with 40+ tools covering:

- File read/write, search
- Shell command execution
- Git operations
- Browser control
- Code analysis
- Network requests
- Plus MCP integration — any MCP Server plugs in seamlessly

The tool system is modular — use `hermes tools` to toggle specific toolsets. Don't want it touching your Git repo? Toggle off the git toolset.

Through MCP integration, you can connect any external service implementing the MCP protocol — a custom database query tool, an internal API gateway, even a Linux desktop control service. Hermes's tool ecosystem isn't closed; it's infinitely extensible.

## The Philosophy of Not Being Locked In

Hermes's overall architecture philosophy in one sentence: **nothing is hardcoded at any layer.**

- Model? Switch anytime. Claude today, DeepSeek tomorrow, local Ollama the day after.
- Platform? Add anytime. Lark, Discord, Slack, WhatsApp — one gateway process handles all.
- Tools? Toggle anytime. MCP lets you plug in any external capability.
- Backend? Swap anytime. From local to Docker to Modal, no config changes needed.
- Skills? Compatible with open standards. Community Skills on agentskills.io work out of the box.

This "not locked to any layer" design gives Hermes a lifespan far exceeding any platform product. Platform dies, you're done. If any single component layer of Hermes has issues, you swap that layer — everything else keeps working.

This matters because what you accumulate on Hermes — Skills, Memory, User Model — are long-term assets. These assets shouldn't be tied to any single vendor, model, or platform.

# VIII. Imagination: How It Can Live in Your Work

Theory and architecture done. Now let's open up imagination — a mature Hermes Agent you've used for three months, how can it weave into your daily work?

## Scenario 1: It Remembers Your Architecture Decisions

Thursday, 2 PM. You start a new microservice project. You tell Hermes: "Initialize the project skeleton."

It doesn't ask what framework, what ORM, what build tool. It generates: Hono + Prisma + Vitest + pnpm workspace + Docker Compose + GitHub Actions CI.

Why? Because three months ago, in a two-hour discussion, you walked through your team's tech stack selection logic with it. It remembers. Not just conclusions — reasons. "Hono because Express is too heavy, Fastify's plugin ecosystem isn't rich enough, Hono can run on Cloudflare Workers."

If you've since made new decisions — like last week saying "Prisma's migrations are garbage, let's try Drizzle next project" — it updated. Next project initialization uses Drizzle.

Can Claude Code do this? Yes — if you manually update CLAUDE.md with tech stack info every time. But will you?

## Scenario 2: Skills That Evolve

First time you ask Hermes to write a Dockerfile, it produces a standard multi-stage build. Works fine, but the image is big.

You discuss it, deciding to add `--mount=type=cache` for faster dependency installation plus a `.dockerignore` template. It updates its "write Dockerfile" Skill.

Second time you ask for a Dockerfile — cache mount and dockerignore included automatically.

Third time — it added a healthcheck too. Because last week in a different conversation you mentioned "all our services need a healthcheck endpoint." It cross-referenced that into the Dockerfile Skill.

Fourth time — it added `LABEL` tags too. Because your team recently started using a container registry for image management, needing version and commit hash labels. You only mentioned it in passing in a completely unrelated conversation, and it absorbed the information.

This is why I call it "self-evolving." You didn't say "always add healthcheck" or "always add LABEL." It abstracted the pattern from multiple interactions on its own.

## Scenario 3: A 24-Hour Colleague on Lark

Your Lark conversations with Hermes and your terminal conversations share the same Memory, same Skills, same User Model.

Tuesday, 10 AM — at the office terminal, you ask it for a code review.

Tuesday, 4 PM — you're out in a meeting, phone buzzes with a Lark message: "That PR from earlier has a potential N+1 query issue I missed. Specifically at `src/services/order.ts:142`, suggest using Prisma's `include` for eager loading. Want me to drop a comment?"

It doesn't wait for you to get back to your computer. It's continuously "alive" in the background. You leave; it keeps thinking. Thinks of something? Tells you through Lark.

This feeling is strange — somewhat like having a real colleague. You don't have to be sitting together, but they might say "hey, I just thought of something" at any time.

## Scenario 4: Cron Jobs in Natural Language

You say one sentence to Hermes: "Every Monday at 9 AM, check all new issues opened in our GitHub repo last week, categorize by priority, send to me."

Cron set. Every Monday at 9 AM, a neatly organized issue list arrives on Lark. And it knows your definition of "priority" — because you previously discussed issue classification criteria.

Want to add another? "Also, every Wednesday at 2 PM, check if staging has any P0 alerts." Done.

Want to change? "From now on, categorize issues by impact scope instead of severity — 'affects single user,' 'affects some users,' 'affects all users.'" Updated.

Manus can't do this — no concept of "persistent residency," it's one-shot. Platform products struggle too — their cron jobs usually only trigger predefined workflows, can't push messages to your own Lark.

## Scenario 5: Subagent Parallelism

This one's slightly advanced.

You say: "Do three things simultaneously — change Service A's log format to JSON structured logging, add rate limiting middleware to Service B, upgrade Service C's Dockerfile to Node 22."

Hermes doesn't do these serially. It spawns three subagents, each independently executing their task without interference. Reports results when done.

And each subagent accesses the same Memory and Skills — they know your code style, project conventions, previous pitfalls.

This parallelism is hugely useful in complex projects. No waiting one by one — fire off three tasks, grab a coffee, everything's done when you're back.

# X. Honest Boundaries: Where It Falls Short

I'm not writing an ad. Hermes has real problems. Let me be clear.

## Configuration Cost Isn't Low

Hermes is an open-source project, not a SaaS product. You configure providers yourself, choose models yourself, connect Lark/Discord/Slack yourself. For command-line-unfamiliar people, the barrier is real.

`hermes setup` has a wizard, but still assumes you know what an API key is, what a webhook is, what environment variables are. If you're a frontend developer who's never touched a VPS and doesn't know SSH — Hermes might not suit you right now.

That said, if you're this article's target reader (developer with some backend/DevOps experience), this configuration shouldn't be a problem. Half an hour to an hour tops.

## Model Capability Is the Ceiling

No matter how good Hermes's self-evolution gets, the underlying LLM ultimately executes tasks. If your model isn't smart enough (some small-parameter open-source models), then no matter how refined the Skills or rich the Memory, outputs will be problematic.

Skills can make an Agent "know what to do," but "doing it well" still depends on model reasoning capability. A 7B model could memorize all correct steps but still frequently err in execution — insufficient reasoning precision.

Best current combinations: Claude 3.5/4 or DeepSeek V4 as primary. Small models for daily rotation produce too many errors. Good news: switching models in Hermes costs nothing, so you can "use expensive models for important tasks, cheap models for simple ones."

## Open Source Roughness

9,000+ commits, 4,000+ issues — fast iteration also means many unpolished edges. Documentation sometimes lags code, certain Skills behave inconsistently with specific models, occasional weird state bugs.

Not a "works out of the box commercial product." More like "enormous potential requiring willingness to tinker." You need some hands-on ability, willingness to search issues, read docs, maybe even read source when hitting problems.

If you're the "doesn't work = uninstall" type — Hermes might disappoint. But if you're the "potential worth investing time into" type — you'll find after three months it becomes something you can't live without.

## The Learning Loop Needs Time

Day one of installing Hermes, experience isn't dramatically different from Claude Code. Might even be worse — Claude Code's single-shot reasoning is genuinely strong, while day-one Hermes has zero Skill accumulation and Memory.

Its advantage needs time — two weeks for initial feels, one month for obvious difference, three months and you can't go back.

This is counterintuitive. We're trained for instant gratification — install tool, expect immediate results. Hermes's value curve doesn't work that way. It's flat then exponential. First two weeks you might think "how is this different from just using Claude?" Persist to one month: "holy shit how did it know I wanted this?" Persist to three months: you'll wonder how you ever tolerated memory-less tools.

## Privacy and Security Considerations

Though Hermes runs locally, it still calls external LLM APIs. Your code snippets, architecture discussions, technical decisions — all sent as prompts to model providers.

If handling highly sensitive content (military, core financial algorithms), consider whether this is acceptable. Solution: use local models (Ollama + open-source), but this sacrifices some reasoning capability.

Hermes has a command approval mechanism (`hermes config set approval_mode`) — you confirm before every command execution. Recommended for sensitive projects.

# XI. Questions You Might Have

## "How are Hermes Skills different from CLAUDE.md?"

Fundamental difference: **who maintains it** and **can it evolve.**

CLAUDE.md is a static file. You write, Claude reads. You don't update, content stays stale forever. And CLAUDE.md only provides context to Claude's current conversation — it can't "trigger" specific behavioral patterns.

Hermes Skills are **dynamic, structured, triggerable, self-improving.** They auto-trigger in specific scenarios, execute complete workflows, and self-optimize after each execution based on results.

## "What if Claude gets persistent memory too?"

Likely. Anthropic is probably building it. ChatGPT already has "memory" (though weak).

But several differences:

1. Commercial products' memory lives on **their servers.** Your data isn't yours.
2. Their memory likely won't give you self-evolving Skills — Skills are a form of "delegation," letting the Agent decide how to do things. Commercial products will probably not be this aggressive for safety and controllability.
3. Model lock-in. Claude's memory only works with Claude. DeepSeek releases a better model? You can't migrate your Claude-accumulated memory. Hermes Memory is model-agnostic.

## "160k stars — legit? Not botted?"

Nous Research is a serious AI research institution, previously known for training open-source LLMs (the Hermes model series is theirs). 9,000+ commits, 600+ watchers, 26k forks, 5,000+ PRs. From code activity and community engagement, this isn't a "botted empty project."

Of course, star count only indicates "attention," not "quality." Whether it's good — you have to try yourself.

## "Should I use Hermes or keep using Claude Code?"

If your primary need is "strong coding assistance" — Claude Code is still better. Stronger single-shot reasoning, better IDE integration, zero setup cost.

If you want "an Agent that understands you, remembers you, works cross-platform, continuously evolves" — Hermes is currently the only option.

Best approach might be both: Claude Code for daily coding assistance, Hermes for long-term partner + automation + cross-platform. They don't conflict.

## "Can Skills go wrong? It modifies itself — what if it makes mistakes?"

Good question. Every "autonomous system" faces this — more autonomy means more risk of error.

Hermes's approach: every Skill modification is traceable. You can see all historical versions and rollback. During execution, you can set approval mode — it tells you "I'm about to use this Skill, okay?" before triggering.

In practice, Skills rarely "go wrong" — they improve based on successful trajectories. If last execution succeeded, improvements based on that experience are probably right. Problems arise from incorrect attribution based on "partially successful" trajectories. But this is rare and easily caught and corrected next use.

## "How's Hermes different from AutoGPT, MetaGPT?"

AutoGPT and MetaGPT were 2023-2024's "autonomous Agent" wave. Their goal: "given an objective, let the Agent decompose and complete it."

Problem: they didn't solve **reliability.** Having GPT-3.5/4 self-plan then self-execute had very high failure rates — frequently going off-track or stuck in loops.

Hermes is positioned differently. It's not "fully autonomous" — it's "progressively autonomous under human supervision." You can interrupt, redirect, correct anytime. Its autonomy level gradually increases with trust accumulation: initially you might approve every command, a month later you trust it and open more permissions.

And Hermes's focus isn't "autonomous completion of single complex tasks" (that's Manus/AutoGPT's approach) — it's "cross-temporal experience accumulation and capability evolution." Two completely different directions.

## "I'm in China — is the network situation convenient for Hermes?"

Hermes itself is locally installed. Installation needs access to GitHub and PyPI. After installation, main network requirement is LLM API calls.

If using Chinese models (DeepSeek, Qwen, MiniMax, Kimi, etc.), network is no issue — these model APIs are on domestic servers. Hermes can connect through OpenRouter or directly to their API endpoints.

If wanting Claude or GPT-4 — you'll need to solve network issues yourself. But that's not Hermes-specific; same for Claude Code.

# XIII. Decision Framework: When to Use What

After all that, here's a ruler for evaluating any new Agent product.

## Ask Yourself Three Questions

**1. Is this task one-off, or will it recur?**

One-off ("summarize this PDF") → Manus or Claude is plenty. No need for memory or growth.

Recurring ("project initialization every time," "weekly issue triage") → needs an Agent with Skill accumulation. Starting from zero every time is wasteful.

**2. Does this task need to understand "me"?**

Generic tasks not requiring personal understanding ("convert JSON to CSV") → any tool works.

Personalized tasks requiring understanding you ("design this module's architecture," "review this PR") → needs an Agent with Memory and User Model. Otherwise answers are "generic best practices," not "best approach for you."

**3. Do I care about data sovereignty and controllability?**

Don't care (personal casual use) → platform products are fine, less hassle.

Care a lot (company code, client data, tech decisions, compliance) → local deployment + open source. Hermes or self-built.

## A Decision Table

| Your Situation                                                 | Recommended Approach     |
| -------------------------------------------------------------- | ------------------------ |
| Occasional one-off Agent tasks                                 | Manus / ChatGPT / Claude |
| Daily coding with real-time assistance                         | Claude Code / Cursor     |
| Want a long-term partner that understands and evolves with you | Hermes                   |

| Want to tinker without writing code                            | Platform products        |
| Need strongest single-shot reasoning + don't care about memory | Claude Code              |
| Need memory + growth + cross-platform + local control          | Hermes                   |

This isn't about "who's better." It's about "what problem are you solving." Hammers for nails, screwdrivers for screws. Don't hammer screws, don't screwdrive nails.

# XIV. A Bigger Question

At this point, I want to step back for a larger thought.

From 2024 to now, the entire Agent space competes on one dimension: **single-task execution capability.** Who handles more complex tasks, who has higher success rates, who scores better on benchmarks. SWE-bench scores from 20% to 50% to 70%. Every product launch says "we solve XX% of GitHub issues."

That obviously matters. But I increasingly feel one dimension is severely overlooked: **time.**

Whether a tool is good isn't just about your first-time experience. It's about whether it becomes better after a year of use.

Word after a year is still Word. Vim after a year becomes an extension of your hand. Notion after a year becomes your external brain. iPhone after a year is no different from day one. But a Vim configuration trained over a year is worlds apart from default.

The difference? **Whether the system can grow with you.**

Vim's growth is manually configured — you add plugins, change keymaps, write snippets. Hermes's growth is automatic — use it normally, it evolves itself. If Vim could automatically observe your editing habits, auto-configure ideal shortcuts, auto-install plugins you likely need — that's what Hermes does in the Agent domain.

That's what Hermes is betting on. Not "being stronger than Claude Code on day one" — day one it's probably worse. It's betting that: **three months, six months, a year later, the "co-evolution" relationship it builds with you is something no "stateless Agent" can replicate.**

Is this the right bet? Nobody knows. Maybe future models will have native, infinite-length context windows, making external memory systems unnecessary. Maybe Claude ships persistent memory + self-improving skills tomorrow, ten times better than Hermes.

But at least today — May 2026 — Hermes is the only product seriously answering this question. Everyone else is competing on "execution power." Only it's competing on "growth."

And I believe long-term, "growth" matters more than "execution power." Because execution power improves universally with model progress (every Agent gets more capable), but growth is a **structural advantage** — it requires time to accumulate, and time cannot be skipped.

Think about it: if all models doubled in capability tomorrow — Hermes's advantage wouldn't disappear; it'd amplify. Stronger model + your three months of accumulated Skills and Memory = greater compounding effect. Model progress is shared by everyone, but your Skills and Memory belong only to you.

This is why I say Hermes points to a "completely different future" — it's not running faster on the existing track, it's opening a new one. On this track, time is the moat, usage is investment, and every conversation makes the future better.
