For a while, the first thing I did every morning was open the 800-line `user-profile.tsx`.

Eight hundred lines. One component. It had API calls, state management, form validation, analytics tracking, permission checks, date formatting, avatar cropping—you name it, it was in there. Every time a product manager walked over and said "add recent browsing history," or a designer said "make the avatar rounded," my stomach dropped. I knew I'd have to knead that entire blob from top to bottom again.

I'd read plenty of articles about design patterns. Honestly? Read them, forgot them. The UML diagrams were pretty. The C++ examples were standard. But I had no goddamn idea how to bring any of it back to my React project. What did the factory pattern have to do with me? Wasn't a singleton just a global variable? What the hell was the difference between observer and pub/sub?

Then one Friday night.

I was refactoring that 800-line component for the Nth time, cursing at my screen. Around the third hour, I just stopped. Stared at the monitor for a long time. What I was doing—splitting out that request hook—wasn't that the single responsibility principle? The pattern behind that extracted hook—wasn't that the factory pattern? That validation logic, written another way—wasn't that the strategy pattern?

Shit.

These design patterns were describing the exact garbage code I was writing.

They just used names I could never remember.

That was when it hit me: design patterns aren't something you memorize. They're something you suddenly recognize when you're standing in front of a pile of crap.

---

## Step Back for a Second

Let me give you an analogy. You're renovating a house. How to lay out the kitchen, where the plumbing goes, how far apart the outlets should be—you don't need to design any of this from scratch. Generations of builders already figured it out. You just follow the playbook.

That's what design patterns are.

They're battle-tested recipes that programmers have distilled over decades—"do it this way, and you probably won't screw it up."

**But they're not rules.**

This is the most critical distinction. Rules must be followed. Patterns don't have to be. Your code runs fine without the factory pattern. The sky doesn't fall if you skip the singleton. A design pattern is just someone saying—"Hey, I've been here before. Doing it this way felt right. Want to give it a shot?"

Understand this, and everything else follows.

## SOLID: Five Principles You've Probably Heard and Never Quite Understood

Before we dive into specific patterns, these five are unavoidable. Think of them as fundamentals—the specific moves vary, but the underlying principles are the same.

### OCP: The Open/Closed Principle

My first real encounter with OCP was a button component.

In my feral coding days, buttons looked like this:

```typescript
function Button({ type, children }) {
  if (type === 'primary') {
    return <button className="bg-blue-500 rounded px-4">{children}</button>
  } else if (type === 'danger') {
    return <button className="bg-red-500 rounded px-4">{children}</button>
  } else if (type === 'ghost') {
    return <button className="bg-transparent border rounded px-4">{children}</button>
  }
  return <button className="bg-gray-500 rounded px-4">{children}</button>
}
```

Every new color meant a new `else if`. A designer had a whim one day—"add a `success` green button"—and you'd open this function, jam in more code. Nested braces upon nested braces. And if you slipped while tweaking `primary` styles, `danger` could break too.

This is called being "open for modification."

OCP says the opposite: **open for extension, closed for modification.** In human language—when adding a feature, add new code, don't touch old code.

Here's what it looks like fixed:

```typescript
function Button({ variant = 'default', className = '', children, ...props }) {
  const base = 'px-4 py-2 rounded font-medium'
  const variants = {
    primary: 'bg-blue-500 text-white',
    danger: 'bg-red-500 text-white',
    ghost: 'bg-transparent border border-gray-300',
    default: 'bg-gray-100 text-gray-800',
  }
  return (
    <button className={`${base} ${variants[variant] || variants.default} ${className}`} {...props}>
      {children}
    </button>
  )
}
```

Now when a designer wants a `success` green button, you add one line to the `variants` object: `success: 'bg-green-500 text-white'`. Old code? Untouched.

**Analogy:** A burger joint cook. The boss says "add chicken burgers to the menu." What does he do? The dumb move is taking apart the beef burger machine and installing a "chicken-specific tube"—then next month, pork burgers require dismantling it again. The smart move: the machine has a "swap patty" slot. New meat, same machine.

Vue's `slot` mechanism is classic OCP thinking. You can stuff anything into a component's slot—the component itself never changes.

**When NOT to use it:** If your button only has two colors and no product manager will request a third in the next three years—if-else is fine. Abstracting because "maybe we'll extend later" is exactly what YAGNI warns us against.

### SRP: The Single Responsibility Principle

Easiest to understand, hardest to do.

Simple version: **One thing does one job.**

You walk into a tiny noodle shop. The owner kneads dough, stir-fries, takes money, and wipes tables—and the food tastes inconsistent and the shop can barely stay open. A real restaurant? The chef handles the kitchen, waiters take orders, the cashier manages the till. Clear roles.

Back to our 800-line `user-profile.tsx`:

```typescript
// A single function doing three people's jobs
function UserProfile({ userId }) {
  const [user, setUser] = useState(null)
  const [posts, setPosts] = useState([])

  useEffect(() => {
    fetchUser(userId).then(setUser)
    fetchPosts(userId).then(setPosts)
    trackPageView('profile', userId)  // Analytics tangled in here too
  }, [userId])

  return (
    <div>
      <Avatar src={user?.avatar} />
      <h1>{user?.name}</h1>
      <PostList posts={posts} />
    </div>
  )
}
```

What looks like "fetch user data and render" to one person is three jobs under SRP: fetching the user, fetching posts, rendering UI. Change the analytics logic and accidentally break a request parameter—that's collateral damage from muddled responsibilities.

After splitting:

```typescript
// Hook does only one thing: fetch user
function useFetchUser(userId: string) {
  const [user, setUser] = useState(null)
  useEffect(() => {
    fetchUser(userId).then(setUser)
  }, [userId])
  return user
}

// Another hook only handles analytics
function useTrackPageView(event: string, userId: string) {
  useEffect(() => {
    trackPageView(event, userId)
  }, [event, userId])
}

// Component only renders
function UserProfile({ userId }: { userId: string }) {
  const user = useFetchUser(userId)
  useTrackPageView('profile', userId)
  return <UserProfileUI user={user} />
}
```

Each piece worries about its own thing. Change analytics? Go to the analytics hook. No risk of breaking data fetching.

**When NOT to use it:** If your component is 30 lines, splitting it into three files adds cognitive overhead—don't. SRP is a guardrail against chaos, not a commandment demanding atomization.

### LSP: The Liskov Substitution Principle

The name itself is the most intimidating part. First time I heard "Liskov substitution," I assumed it was some mathematical theorem.

But it says something dead simple: **a child object should be able to replace its parent without screwing things up.**

The classic example:

```typescript
class Bird {
  fly(): string {
    return 'I flew away'
  }
}

class Duck extends Bird {
  fly(): string {
    return 'Flew away quacking' // Extended fly, but kept the contract
  }
}
```

A duck is a bird, it can fly—fine. What about a penguin?

```typescript
class Penguin extends Bird {
  fly(): string {
    throw new Error('I can't fucking fly!')  // Breaks the parent's contract
  }
}
```

The problem isn't that penguins can't fly. It's that **you shoved something that can't fly into an inheritance chain that promises flying.** Callers take any `Bird` subclass and call `.fly()` assuming it'll work. Then it blows up.

The fix: pull "can't fly" out of the chain.

```typescript
interface Animal {
  move(): string
}

class Duck implements Animal {
  move(): string {
    return 'Flew away'
  }
}

class Penguin implements Animal {
  move(): string {
    return 'Slid away on ice'
  }
}
```

LSP's real message: **a subclass can extend its parent's capabilities, but it cannot break the parent's existing contract.** Your dad promised "my son can drive." If you're blind, that's not your fault—your dad shouldn't have made that promise. Whoever put the wrong thing in the wrong chain violated LSP.

In frontend frameworks, class inheritance is rare (everyone uses composition now), but this principle shows up everywhere in type systems. If you define a `FormField` interface saying every field must have a `validate()` method, then every class implementing `FormField` must return a meaningful result from `validate()`—never throw.

**When NOT to use it:** Frontend barely uses class inheritance. If you're not using inheritance, this principle barely touches you. Don't force classes just because you learned LSP.

### ISP: The Interface Segregation Principle

"Don't force clients to depend on things they don't need."

Ever ordered delivery and been stuck with a combo meal—a rice bowl forcibly bundled with soup, a side dish, and milk tea—when all you wanted was the rice?

The `UserCard` component is exactly this:

```typescript
interface UserCardProps {
  name: string
  avatar: string
  email: string
  phone: string
  address: string // List page doesn't need this
  bio: string // List page doesn't need this
  lastLoginAt: string // List page doesn't need this
  permissions: string[] // List page doesn't need this
}
```

A simple user list page only needs `name` and `avatar`. But you have to work with this bloated Props interface—unless you write a separate one.

ISP says: **split into small interfaces, take what you need.**

```typescript
interface UserBasic {
  name: string
  avatar: string
}

interface UserContact {
  email: string
  phone: string
  address: string
}

interface UserProfile extends UserBasic, UserContact {
  bio: string
  lastLoginAt: string
  permissions: string[]
}
```

List pages use `UserBasic`. Detail pages use `UserProfile`. Nobody is force-fed anything.

**Analogy:** Buying a tool set. A good set has each tool standalone—buy what you need. A bad set is a plastic shell with fifteen screwdriver heads crammed inside—you have to buy the whole set for one head.

GraphQL's field-level queries are this principle applied to databases—the client says exactly what fields it wants, the server returns precisely those.

**When NOT to use it:** If your component only has one consumer, splitting Props interfaces is just self-indulgence. ISP only feels good when you have three or more consumers—one consumer, no isolation needed.

### DIP: The Dependency Inversion Principle

This one took me a long time to get.

It's called "dependency inversion," but just read it as **"depend on abstractions, not concretions."**

```typescript
// Hardcoded to MySQL
class UserService {
  private db = new MySQLDatabase()

  getUser(id: string) {
    return this.db.query(`SELECT * FROM users WHERE id = ${id}`)
  }
}
```

What's wrong? `UserService` is welded to `MySQLDatabase`. The day you want to switch to PostgreSQL, or use an in-memory database for tests—sorry, you're cracking open `UserService` to rewrite it.

DIP says: **`UserService` shouldn't depend on `MySQLDatabase`—both should depend on an abstract `Database` interface.**

```typescript
interface Database {
  query(sql: string): any
}

class MySQLDatabase implements Database {
  query(sql: string) {
    /* MySQL implementation */
  }
}

class PostgresDatabase implements Database {
  query(sql: string) {
    /* PostgreSQL implementation */
  }
}

class UserService {
  constructor(private db: Database) {} // Depends on interface, not implementation

  getUser(id: string) {
    return this.db.query(`SELECT * FROM users WHERE id = ${id}`)
  }
}

// Test with mock, production with MySQL—swap databases like swapping plugs
const service = new UserService(new MySQLDatabase())
```

**Analogy:** Your wall outlet. An appliance doesn't care whether the electricity behind the outlet comes from coal or hydro—it only cares about "give me 220V." The `Database` interface is the outlet spec; `MySQLDatabase` and `PostgresDatabase` are coal and hydro plants. The appliance (`UserService`) depends on the outlet spec (`Database` interface), not the power plant type.

In frontend, DIP's most common use case: your business logic hooks don't depend directly on axios—they depend on an abstract `HttpClient` interface. Switch between fetch, axios, or a built-in request method—you only change the injection point, never the business logic.

**When NOT to use it:** Your backend hasn't switched databases in three years, and there's no plan to. Abstraction isn't free—every layer of abstraction adds complexity. Only when you genuinely face "we might need to swap" does abstraction start paying for itself.

## Creational: Who Creates, and How

Creational patterns center on one question: **how do objects get produced, and how do you keep the production process under control?**

### Factory Pattern

You walk into McDonald's and say "one Big Mac meal." The cashier hands you a complete set—burger, fries, Coke, all packaged. You don't care which patty went in, how long the fries were fried, or how the syrup ratio was calibrated.

That's the factory pattern.

**The `new` operator is you walking into the kitchen and frying your own fries. A factory is you telling the counter one sentence and getting the finished product handed to you.**

In React, `React.createElement` is a classic factory:

```typescript
// Without factory—you manually new, worrying about parameters
const button = new VNode('button', { className: 'btn' }, ['Click me'])

// With factory—one call, done
const button = React.createElement('button', { className: 'btn' }, 'Click me')
```

jQuery's `$()` is also a factory. You pass a selector string, it returns a jQuery object—the entire creation process is wrapped inside `$()`.

The most common real-world scenario: creating different form fields based on type.

```typescript
interface FormField {
  type: 'text' | 'select' | 'datepicker'
  label: string
  value: any
}

class FormFieldFactory {
  static create(field: FormField) {
    switch (field.type) {
      case 'text':
        return new TextField(field)
      case 'select':
        return new SelectField(field)
      case 'datepicker':
        return new DatePickerField(field)
      default:
        throw new Error(`Unknown field type: ${field.type}`)
    }
  }
}
```

The backend returns JSON describing what fields to render. The frontend factory handles them all uniformly. Add a new field type? One line in the factory. Nothing else touched.

**When NOT to use it:** If you only have two field types, a two-line `switch` is fine—no separate factory class needed. The factory's value lies in "the creation logic is complex enough to warrant encapsulation."

### Singleton Pattern

A country has one president at a time.

Not that the president can't change—just that "there's only one person sitting in that seat at any given moment."

A singleton is your program's president.

```typescript
class ModalManager {
  private static instance: ModalManager
  private modalStack: string[] = []

  private constructor() {} // Note: private constructor

  static getInstance(): ModalManager {
    if (!ModalManager.instance) {
      ModalManager.instance = new ModalManager()
    }
    return ModalManager.instance
  }

  open(id: string) {
    this.modalStack.push(id)
  }

  close() {
    this.modalStack.pop()
  }

  get top(): string | undefined {
    return this.modalStack[this.modalStack.length - 1]
  }
}

// Everywhere in the app gets the same instance
const manager = ModalManager.getInstance()
manager.open('confirm-dialog')
```

The scenario is clear: global state management, modal managers, log collectors—these things only need one instance in a program.

Many people hear "singleton" and think "global variable." What's the difference? A singleton has a `getInstance` gate—whenever you fetch it, it guarantees only one exists. A global variable is a public square—anyone can drop something there, anyone can step on it.

**When NOT to use it:** Singletons are convenient, but they couple all your code to the same state. They're a nightmare for testing—you can't reset a singleton's state between tests. If your "global need" could actually be solved with Context or provide/inject, skip the singleton.

### Prototype Pattern

You have a precise architectural blueprint. You want to build 100 identical houses—not redraw the blueprint 100 times, but take this one blueprint and clone it 100 times.

```typescript
const baseConfig = {
  api: {
    baseURL: 'https://api.example.com',
    timeout: 5000,
    headers: { 'Content-Type': 'application/json' },
  },
  auth: {
    tokenKey: 'access_token',
    refreshEndpoint: '/auth/refresh',
  },
}

// Clone with tweaks
function createAppConfig(overrides: Partial<typeof baseConfig> = {}) {
  return deepMerge(baseConfig, overrides)
}

const testConfig = createAppConfig({
  api: { baseURL: 'https://test-api.example.com' },
})
```

JavaScript's `Object.create()` is native prototype pattern support—the new object takes the old object as its prototype chain.

```typescript
const animal = {
  speak() {
    return `${this.name} makes a sound`
  },
}

const dog = Object.create(animal)
dog.name = 'Dog'
dog.speak() // "Dog makes a sound"
```

`Object.create` doesn't call a constructor, doesn't copy properties—it just builds a prototype chain bridge between two objects.

**When NOT to use it:** The prototype pattern's advantage is speed (no constructor call), but the cost is implicit inheritance relationships between objects. When you need to clearly know what properties an object has, the prototype chain makes debugging painful. Most of the time, `Object.assign` or spread operator shallow copies are enough.

## Structural: How to Assemble Parts Into a Working Machine

Creational is about "producing parts." Structural is about "putting the parts together."

### Proxy Pattern

You visit a big company to meet the CTO. You don't just push open the office door—you go through the front desk first. The receptionist confirms your identity, logs your purpose, calls back to ask "are you available right now," and only then lets you through.

A proxy is the front desk in your code.

Vue 3's `reactive()` system is the most elegant example of the proxy pattern:

```typescript
const raw = { count: 0 }
const state = new Proxy(raw, {
  get(target, key) {
    console.log(`Someone is reading ${String(key)}`)
    track(target, key) // Collect dependencies
    return target[key]
  },
  set(target, key, value) {
    console.log(`Someone is setting ${String(key)} to ${value}`)
    target[key] = value
    trigger(target, key) // Notify dependencies
    return true
  },
})

state.count // Console: Someone is reading count
state.count = 1 // Console: Someone is setting count to 1
```

You use `state.count` thinking you're directly reading and writing an object. In reality, every read and write goes through the Proxy—this front desk that automatically signs you in (track) when you enter and notifies (trigger) when you leave. You never feel its presence, but it never stops working.

Lazy-loading images is another classic proxy use case:

```typescript
function lazyLoadImage(src: string): HTMLImageElement {
  const img = new Image()

  const proxy = new Proxy(img, {
    set(target, key, value) {
      if (key === 'src') {
        const observer = new IntersectionObserver((entries) => {
          if (entries[0].isIntersecting) {
            target.src = value // Load only when entering viewport
            observer.disconnect()
          }
        })
        observer.observe(target)
        return true
      }
      target[key] = value
      return true
    },
  })

  return proxy
}
```

**When NOT to use it:** Proxy has a performance cost. For simple value reads and writes, there's no need for a wrapper layer. Proxies add indirection—debugging reveals an extra Proxy handler in your call stack, making investigation harder.

### Decorator Pattern

You just bought a new phone. You don't like how slippery it is, so you put a case on it. The phone is still the same phone, all functions intact—but now it has something extra: drop protection.

That's the decorator: **don't modify the original object, just wrap it with new capabilities.**

TypeScript's experimental decorator syntax:

```typescript
function timeTrack(target: any, propertyKey: string, descriptor: PropertyDescriptor) {
  const original = descriptor.value
  descriptor.value = function (...args: any[]) {
    const start = performance.now()
    const result = original.apply(this, args)
    const end = performance.now()
    console.log(`[${propertyKey}] execution time: ${(end - start).toFixed(2)}ms`)
    return result
  }
  return descriptor
}

class ApiClient {
  @timeTrack
  async fetchUserData(userId: string) {
    return fetch(`/api/users/${userId}`).then((r) => r.json())
  }
}

const client = new ApiClient()
client.fetchUserData('123') // Console: [fetchUserData] execution time: 234.56ms
```

You didn't change `fetchUserData`'s source code, but you added timing capability to it. Like a phone case—the phone is still the same phone, but now it has an extra layer of protection.

In React, Higher-Order Components (HOC) are the React version of decorators:

```typescript
function withLoading<P>(Component: React.ComponentType<P>) {
  return function LoadingWrapper(props: P & { loading: boolean }) {
    if (props.loading) return <Spinner />
    return <Component {...props} />
  }
}

const UserListWithLoading = withLoading(UserList)
```

`UserList` knows nothing about loading states. We wrapped it with an HOC to add loading capability. The original component stays clean.

**When NOT to use it:** Too many decorators become an onion—layer after layer, all wrapping shells. If a component has auth, loading, error, and tracking HOCs simultaneously, debugging means remembering "which layer wrapped what." More than three decorators, and it's time to reconsider.

### Adapter Pattern

You travel to Japan with a Chinese charger. You get to the hotel and freeze—their outlets are two flat prongs, your charger is three-pronged, won't fit. You don't open up the charger and re-solder it. You buy an adapter.

An adapter is that converter.

The most common frontend scenario: backend API returns `snake_case`, frontend uses `camelCase`:

```typescript
// Backend returns
const apiResponse = {
  user_id: 123,
  first_name: 'Max',
  last_name: 'Zhang',
  created_at: '2026-03-23',
}

// Adapter
interface User {
  userId: number
  firstName: string
  lastName: string
  createdAt: string
}

class UserAdapter {
  static adapt(raw: typeof apiResponse): User {
    return {
      userId: raw.user_id,
      firstName: raw.first_name,
      lastName: raw.last_name,
      createdAt: raw.created_at,
    }
  }
}

const user: User = UserAdapter.adapt(apiResponse)
```

The benefit is clear—frontend code always uses `firstName`. If the backend format changes, you fix the adapter, not business code.

Another classic scenario: a third-party library's interface doesn't match your project's conventions. You use an old chart library whose `setData` takes `{x: number, y: number}[]`, but your project uses `{label: string, value: number}[]` everywhere. Write an adapter, and you don't need to convert at every call site.

**When NOT to use it:** If the backend format is stable and your project convention is to match backend field names—just use them directly, no adapter. Adapters add a layer of indirection and more code. They're only valuable when the "mismatch" pain is real.

### Facade Pattern

You pick up the TV remote and press the red button. The TV turns on. You don't care how the remote emits infrared, how the TV's power module starts up, or how the signal receiver decodes—you just know one button does the job.

The facade pattern is the remote control.

It provides **a simplified entry point that hides all the complex logic behind it.**

Vue's `computed` is a perfect facade example:

```typescript
const user = reactive({
  firstName: 'Max',
  lastName: 'Zhang',
  settings: {
    language: 'zh',
    timezone: 'Asia/Shanghai',
  },
})

// Without facade: manually concatenate every time
console.log(`${user.firstName} ${user.lastName}`)

// With facade: one property handles the concatenation behind the scenes
const displayName = computed(() => `${user.firstName} ${user.lastName}`)
console.log(displayName.value)
```

Complex form submission logic:

```typescript
// Without facade—caller must know all three steps
async function submitFormRaw() {
  const validated = await validateAll(formData)
  if (!validated.success) return showErrors(validated.errors)
  const sanitized = sanitizeInput(formData)
  const result = await api.submit(sanitized)
  if (result.error) return showErrorToast(result.error)
  showSuccessToast('Submitted successfully')
  router.push('/dashboard')
}

// With facade—one method, everything handled
class FormFacade {
  async submit() {
    const validated = await validateAll(this.data)
    if (!validated.success) return showErrors(validated.errors)
    const sanitized = sanitizeInput(this.data)
    const result = await api.submit(sanitized)
    if (result.error) return showErrorToast(result.error)
    showSuccessToast('Submitted successfully')
    router.push('/dashboard')
  }
}

// Caller only needs to know one step
await formFacade.submit()
```

The facade pattern's significance isn't about "encapsulation" (if that's all you see, every function is a facade). It's about **converging interactions with multiple subsystems into a single fixed entry point.** If the validation logic changes from `validateAll` to another library later, callers don't need to know—fix it inside the facade.

**When NOT to use it:** Facades easily become "god objects"—a class that does everything, circling back to our 800-line component problem. If your facade starts requiring 10 parameters to configure behavior, it's lost the meaning of "simplified entry point." The facade's advantage is simplicity, the cost is flexibility—you sealed the complexity inside the remote, but some people actually want to open the TV and tune it themselves.

## Behavioral: How Objects Talk to Each Other

Creational handles "creating people." Structural handles "forming teams." Behavioral handles "how people on the team shout to each other."

### Observer Pattern

You follow a WeChat official account. When they publish a new article, you receive it passively—you don't refresh every five minutes asking "did they post yet." They notify you.

The observer pattern is this logic: **one object (the account) maintains a list of followers and wakes each one up when its state changes.**

```typescript
class Subject {
  private observers: Array<(data: any) => void> = []

  subscribe(fn: (data: any) => void) {
    this.observers.push(fn)
    return () => {
      this.observers = this.observers.filter((o) => o !== fn)
    }
  }

  notify(data: any) {
    this.observers.forEach((fn) => fn(data))
  }
}

// Usage
const userStore = new Subject()

// Xiao Li subscribes to user changes
const unsubscribe = userStore.subscribe((data) => {
  console.log('Xiao Li received notification:', data)
})

userStore.notify({ name: 'Max', action: 'login' }) // Xiao Li receives notification
unsubscribe() // Xiao Li unsubscribes
```

Vue's reactivity system is built on the observer pattern at its core. A `computed` property is an observer—it subscribes to every `ref`/`reactive` it reads. When any dependency changes, `computed` receives a notification and recomputes.

React's `useEffect` also embodies observer thinking—the dependency array is your "subscription list," and the cleanup function is the "unsubscribe."

**When NOT to use it:** The observer pattern makes "notification" simple and "debugging" hard. When 20 observers respond to one event simultaneously, your call stack becomes a plate of spaghetti. And if one observer's callback triggers another notification, you can easily create an event loop. If you only have one receiver, use a callback—don't wrap it in the observer pattern.

### Pub/Sub Pattern

Reading this, you might be wondering: what the hell is the difference between observer and pub/sub?

Great question. They're too similar. I got confused the first time too.

The difference in one sentence: **in observer, the subject knows all its observers directly. In pub/sub, neither side knows the other—there's a third party in the middle called an "event hub."**

```typescript
class EventBus {
  private events: Map<string, Array<(data: any) => void>> = new Map()

  on(event: string, fn: (data: any) => void) {
    if (!this.events.has(event)) this.events.set(event, [])
    this.events.get(event)!.push(fn)
  }

  off(event: string, fn: (data: any) => void) {
    const fns = this.events.get(event)
    if (fns)
      this.events.set(
        event,
        fns.filter((f) => f !== fn),
      )
  }

  emit(event: string, data: any) {
    this.events.get(event)?.forEach((fn) => fn(data))
  }
}

// Usage—two strangers shouting through a middleman
const bus = new EventBus()

// Component A: I'm emitting this event, but I don't know who'll hear it
bus.emit('user-login', { userId: 123 })

// Component B: I'm listening for this event, but I don't know who's emitting it
bus.on('user-login', (data) => {
  console.log('Component B received login event', data)
})
```

**Analogy:** Observer is an official account pushing directly to followers (author → reader, direct relationship). Pub/sub is you placing an order on a shipping platform—the seller ships, the logistics company notifies you of arrival. The seller doesn't know you, you don't know the seller, but the platform (the "event hub") routes everything.

Vue 2's `$on` and `$emit` embody the pub/sub pattern. Sibling component communication without going through the parent component—an event bus handles it.

**When NOT to use it:** An event bus is a globally shared megaphone. Over time, you'll forget which components are listening to which events. When refactoring, you're terrified to delete an `emit` because it might affect an `on` hidden in some corner. If your component relationship is a clear parent-child tree, props + emit are much clearer than an event bus. Pub/sub is for loosely coupled cross-level communication—not a shortcut to bypass component structure.

### Strategy Pattern

You need to go from Beijing to Shanghai. Fly? High-speed rail? Drive? Each is a "strategy." You choose different strategies, but the destination doesn't change.

The strategy pattern separates "algorithm" from "context that uses the algorithm"—you have a single entry point like `formValidator`, but it selects different validation strategies based on field type.

```typescript
interface ValidationStrategy {
  validate(value: any): string | null
}

const strategies: Record<string, ValidationStrategy> = {
  isNonEmpty: {
    validate(value: string) {
      return value.trim() ? null : 'This field is required'
    },
  },
  isEmail: {
    validate(value: string) {
      return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(value) ? null : 'Invalid email format'
    },
  },
  isPhone: {
    validate(value: string) {
      return /^1[3-9]\d{9}$/.test(value) ? null : 'Invalid phone number'
    },
  },
  minLength: {
    validate(value: string, min: number = 6) {
      return value.length >= min ? null : `Minimum ${min} characters`
    },
  },
}

class FormValidator {
  private checks: Array<{ strategy: ValidationStrategy; value: any; params?: any }> = []

  add(value: any, name: string, params?: any) {
    const strategy = strategies[name]
    if (!strategy) throw new Error(`Unknown validation rule: ${name}`)
    this.checks.push({ strategy, value, params })
  }

  validate(): string | null {
    for (const { strategy, value, params } of this.checks) {
      const error = strategy.validate(value, params)
      if (error) return error
    }
    return null
  }
}

const validator = new FormValidator()
validator.add('13800138000', 'isPhone')
validator.add('a@b.com', 'isEmail')
validator.add('abc', 'minLength', 6)
console.log(validator.validate()) // "Minimum 6 characters"
```

Without the strategy pattern, how would you write this? A giant `if-else`:

```typescript
if (rule === 'isNonEmpty' && !value.trim()) return 'This field is required'
else if (rule === 'isEmail' && !isEmailRegex.test(value)) return 'Invalid email format'
else if (rule === 'isPhone' && !isPhoneRegex.test(value)) return 'Invalid phone number'
// Fifty lines later...
```

The product manager wants to add "ID number validation." Strategy pattern: add one entry to `strategies`. If-else pattern: find the right spot in that pile of conditionals, jam it in, pray you didn't break anything.

**When NOT to use it:** Only two strategies? Don't bother. If validation rules are just "required" and "email"—write them directly. Wrapping them in the strategy pattern is overengineering. The strategy pattern's value lies in "the number of strategies will keep growing."

### Iterator Pattern

No matter what remote you're holding—air conditioner, TV, set-top box—the "channel up" and "channel down" buttons work exactly the same way. Press once, next one. Whether it's cable TV signals or streaming behind the scenes, the operation is identical.

The iterator pattern is this: **no matter what data structure is behind you, the traversal method is unified.**

JavaScript's `Symbol.iterator` is built-in iterator support:

```typescript
const myIterable = {
  data: ['Page One', 'Page Two', 'Page Three'],
  [Symbol.iterator]() {
    let i = 0
    return {
      next: () => {
        if (i < this.data.length) {
          return { value: this.data[i++], done: false }
        }
        return { value: undefined, done: true }
      },
    }
  },
}

for (const item of myIterable) {
  console.log(item) // Page One / Page Two / Page Three
}
```

With `Symbol.iterator`, your custom object works with `for...of`, spread operator, destructuring—just like a native array.

Real-world scenario: traversing tree structures.

```typescript
class TreeNode {
  value: number
  children: TreeNode[]

  constructor(value: number, children: TreeNode[] = []) {
    this.value = value
    this.children = children
  }

  *[Symbol.iterator](): Generator<number> {
    yield this.value
    for (const child of this.children) {
      yield* child // Recursively iterate children—depth-first traversal
    }
  }
}

const tree = new TreeNode(1, [new TreeNode(2, [new TreeNode(4), new TreeNode(5)]), new TreeNode(3)])

for (const value of tree) {
  console.log(value) // 1, 2, 4, 5, 3
}
```

A tree, traversable with `for...of`. No matter how deep the tree is—the iterator handles depth-first traversal behind the scenes.

In frontend, the DOM's `NodeList`, `HTMLCollection`, `Map`, `Set`—all iterable. No matter how different their data structures are, you can traverse them all uniformly with `for...of`.

**When NOT to use it:** If you only need to traverse once, just use `array.forEach()`—no need to implement your own iterator. Iterators are valuable when you want to extract traversal logic from business logic, making traversal itself a reusable tool.

## Step Back: What the Whole Picture Looks Like

Pull everything together, and the world of design patterns is just three layers:

```

Creational (Who makes)
├── Factory: Order at the counter, don't walk into the kitchen
├── Singleton: Only one voice in the entire system
└── Prototype: Clone the blueprint, don't redraw it

Structural (How to assemble)
├── Proxy: The front desk screens for you
├── Decorator: Put on a phone case, functions untouched
├── Adapter: Swap the converter, both sides work
└── Facade: Here's a remote, don't worry about the complexity

Behavioral (How to communicate)
├── Observer: Follow an account, new posts auto-push
├── Pub/Sub: Two people shouting through the void, a middleman relays
├── Strategy: Fly or take the train, destination unchanged
└── Iterator: No matter the device, the channel button is the same

```

You don't need to memorize all 23 patterns. You just need to ask yourself three questions when facing a messy block of code:

**1. Is this a "who creates what" problem?**
— If yes, pick from Factory, Singleton, Prototype.

**2. Is this a "how to assemble objects" problem?**
— If yes, pick from Proxy, Decorator, Adapter, Facade.

**3. Is this a "how do objects notify and coordinate" problem?**
— If yes, pick from Observer, Pub/Sub, Strategy, Iterator.

If none of the three?

Then this place probably doesn't need a design pattern.

## FAQs — The Questions That Trip You Up

**Q: Do I need to memorize all 23?**

No. I've been writing frontend code for years, and before I write a strategy pattern, the words "strategy pattern" never cross my mind. I finish writing it, then suddenly realize—oh, that's the strategy pattern. You don't need to memorize. You need to look at a piece of code and recognize it: "that's observer," "that's adapter," "that's singleton." Names don't matter. Structure does.

**Q: How do I decide which pattern to use?**

Run the three questions above first. If you're still unsure—don't use one. Write traditional if-else and direct function calls. When the code starts hurting you, you'll naturally know where to extract a pattern.

**Q: Won't design patterns make the code more complex?**

Yes. Absolutely yes.

That's why there's YAGNI—You Aren't Gonna Need It. While the code is still simple, don't rush to introduce patterns. A 50-line utility function doesn't need a factory. Parent-child component communication doesn't need pub/sub.

Design patterns are the renovation crew you call after the code gets ugly—not gold leaf you apply to a bare concrete room.
