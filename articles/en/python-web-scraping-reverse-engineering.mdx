It's 2am. Your third coffee has gone cold. On the screen, Chrome DevTools' Network panel shows the login request payload, and it's gibberish — starts with `U2FsdGVkX1`, followed by hundreds of bytes of noise. You fire the same payload with `requests.post()`. The server sends back 403. You copy the exact raw bytes your browser sent, paste them, try again. Still 403.

You're sending the exact same thing. What the hell?

Welcome to lesson one in web scraping: **what you think you're sending is not what the browser is sending**. The gap between those two things is what this whole article is about.

From mid-2018 to late 2019, I was building a system to scrape insurance policy data. Sounds boring, right? Scrape insurance products, premium tables, coverage details. But every insurance site and broker platform had their own flavor of security. I knew the tools — Selenium, Scrapy, Pyppeteer — but there's an ocean between "knowing these tools exist" and "writing a scraper that runs for ten days without crashing."

This is a record of the trenches. Not a tutorial. Not best practices. Just what actually worked. Everything revolves around a real scenario: scraping insurance terms.

## You're Actually Dealing With Three Problems

Let me pull back and frame this. In 2018, if you wanted to scrape a site with even modest defenses, you were looking at three problems:

1. The login payload is encrypted, and you can't construct it yourself
2. The page content is JS-rendered — `requests.get()` gives you an empty shell
3. After 20 requests your IP gets blacklisted

These map to three core technical problems: **reverse-engineering encryption**, **browser simulation**, and **identity rotation**. They're not independent — solving encryption without a proxy gets you nowhere. Having a proxy without a Cookie pool still gets you banned. Solving all three but running on a single machine? You need distributed architecture.

Alright. Layer by layer.

## Chapter One: Login Is Harder Than You Think

### What You See vs. What You Can't Get

Picture yourself on an insurance product search portal's login page. You open DevTools, switch to the Network tab, type your username and password, hit login.

The request fires. The payload looks like this:

```json
{
  "data": "U2FsdGVkX1+...a long blob...",
  "timestamp": 1559347200,
  "sign": "a1b2c3d4e5f6..."
}
```

What the fuck is this? You never typed this.

Here's the truth: the frontend took your plaintext password the moment you clicked login and ran it through a gauntlet of operations. Usually some combination of:

| Algorithm  | What it did                  | What you do about it                                                   |
| ---------- | ---------------------------- | ---------------------------------------------------------------------- |
| MD5        | Hashed your password         | Rainbow table, or just replay the hash                                 |
| SHA-256    | Generated a signature        | Can't reverse, but you can replicate the signing process               |
| AES        | Encrypted the entire payload | Find the key and IV, then decrypt                                      |
| RSA        | Encrypted with a public key  | You won't get the private key, but you can encrypt with the public one |
| Base64     | Obfuscated it                | Just decode it — it's not encryption                                   |
| Custom XOR | A homegrown toy cipher       | A few test inputs reveal the pattern                                   |

Late 2018, real example from a site I was working on. The frontend did this:

```javascript
const encrypted = CryptoJS.AES.encrypt(
  JSON.stringify({ username, password }),
  CryptoJS.enc.Utf8.parse('some-hardcoded-key'),
  { mode: CryptoJS.mode.ECB, padding: CryptoJS.pad.Pkcs7 },
).toString()
```

The key was hardcoded in a webpack bundle. Once you found it, the Python equivalent is six lines:

```python
from Crypto.Cipher import AES
import base64, json

key = b'some-hardcoded-key'
cipher = AES.new(key, AES.MODE_ECB)
data = json.dumps({'username': 'user', 'password': 'pass'})
padded = data + chr(16 - len(data) % 16) * (16 - len(data) % 16)
encrypted = base64.b64encode(cipher.encrypt(padded.encode()))
```

Six lines. Looks easy.

The hellish part is: how do you find that key in fifty thousand lines of minified JS? How do you confirm it's ECB and not CBC? How do you verify that your Python output matches the browser's byte-for-byte? None of these are "just Google it" problems.

### When You Open DevTools and the Site Loses Its Mind

Then it gets worse. You open Chrome DevTools, ready to debug, and the page freezes — stuck on a `debugger` statement. You hit resume. Another one fires immediately. Infinite loop.

The site planted this:

```javascript
;(function () {
  setInterval(function () {
    debugger
  }, 100)
})()
```

The nastier ones use `Function("debugger")()` to generate it dynamically — so string search won't find it.

This is anti-debugging. It doesn't block you from accessing the page. It just makes debugging a torture device. Every 100 milliseconds, your flow gets shattered.

My toolkit for dealing with this:

1. **"Never pause here"**: Right-click the line number in Chrome DevTools and select it. Works for static `debugger` statements.

2. **Deactivate all breakpoints**: Click the pause icon with the slash in the Sources panel. Silences everything, including `debugger`. Simple and brutal.

3. **Hijack before it runs**:

```javascript
var _setInterval = window.setInterval
window.setInterval = function () {}
```

4. **Intercept at the proxy level**: Use mitmproxy or Fiddler to grab the JS file containing anti-debug code, strip out the `debugger` calls, and serve the modified version. This is the most reliable approach — the code gets altered before the browser ever sees it.

In practice, one insurance platform might simultaneously use `setInterval`-based `debugger` calls, scattered `Function("debugger")()` invocations, and a timer detecting whether DevTools is open. You shut them down one by one. Like peeling an onion where every layer wants to make you cry.

### Finding One Function in Fifty Thousand Lines of Garbage

Past the anti-debug traps, the real work begins.

You're hunting for an encryption function in an 18,000-line webpack bundle. The code is minified to one line. Variables are named `a`, `b`, `c`. You need a method, not luck.

Here was my workflow:

1. **XHR breakpoints**: In Sources → XHR/fetch breakpoints, add a breakpoint on the login URL. The instant the request fires, the call stack shows you exactly which functions executed before sending. This is the fastest way to locate encryption logic.

2. **Global keyword search**: `Cmd+Shift+F`, search for `encrypt`, `AES`, `CryptoJS`, `sign`, `md5`. Even in minified code, these strings usually survive.

3. **Trace up the call stack**: When a breakpoint hits, don't just stare at the current function. The function that calls the encryption function is often the one constructing the payload — understand it, and you're halfway there.

4. **Experiment in the Console**: Set a breakpoint before the encryption call, then in console, invoke the function with test inputs and observe the output. This is the stage where you confirm whether your understanding is correct — whether it's worth writing any Python at all.

Let me give you a concrete example. Early 2019, that insurance policy search platform. The login payload looked like:

```json
{
  "data": "U2FsdGVkX1+...",
  "timestamp": 1559347200,
  "sign": "a1b2c3d4e5f6..."
}
```

The `sign` field was `md5(timestamp + fixed_secret + encrypted_data)`. No sign? 403. Wrong sign? 403.

To get through this door, you had to:

1. Find where `sign` was computed in Sources (global search for `md5`)
2. Locate that fixed secret (it was the `btoa` result of some string — decode it in console)
3. Replicate the exact string concatenation order in Python

Tedious beyond belief. But by the tenth time I did this, a truth emerged: **most sites use the same few encryption libraries** — CryptoJS, JSEncrypt, jsrsasign. The techniques are similar. Once you have a debugging workflow, the rest is just putting in the hours.

## Chapter Two: The Identity Game

### Your IP Is Your Face

A scraper without a proxy is running naked. That's not a metaphor.

Datacenter IPs get rate-limited within minutes. Residential IPs last longer — but you only have one. One IP hitting hundreds of pages on the same site in quick succession looks nothing like human behavior to any fraud detection system.

The solution is to maintain a rotating pool of IPs. In 2018-2019, China's proxy market was absurdly fragmented. Here's what I encountered:

**Short-lived static IPs**: You pay for a batch of IPs. They're yours for 3-5 minutes, then recycled to the next customer. For most scraping projects, this is the best bang for your buck — rotation is fast, bandwidth is decent, costs are manageable. The catch: they're datacenter IPs, and some sites are ruthless about blocking them.

**Dynamic forwarding**: The provider doesn't give you an IP list. They give you a forwarding port. You send requests to their server, and they forward through their own rotating pool. Pay per request. Sounds great, right? At 0.3-0.5 yuan per page, scraping thousands of pages a day, the math falls apart instantly. Avoid for high-volume work.

**Tunnel proxies**: Subscription-based. Pay monthly, get an API, fetch IPs whenever you need them. IP quality is generally higher because the provider maintains the underlying pool infrastructure.

**Traffic-based billing**: Some providers charge by data volume, not IP count or request count. Buy 10GB of traffic, use as many IPs as you want within that quota. Way cheaper than per-request billing for high-payload scraping.

**What you actually care about when choosing a provider**:

- Can you select geography? For insurance policies, different provinces return different products
- Authentication: IP whitelist or username/password? Whitelist is simpler; password auth is more flexible across multiple servers
- IP quality: shared or dedicated? Dedicated always performs better but costs 2-3x more
- Extraction method: URL or SDK? URL is the most portable

There's also a dirt-cheap hack. If your budget is tight, in 2018 people used VPS instances (DigitalOcean, Vultr) and programmatically restarted network interfaces to get new IPs. About 30-90 seconds per swap, but nearly zero cost beyond the VPS itself. A backup option for low-frequency scraping.

### Roll Your Own Proxy Layer

If you already have a batch of IPs and want to manage them properly, the simplest approach in 2018 was Squid — specifically the `sameersbn/squid` Docker image.

Why build your own proxy layer? Because you want to **decouple proxying from scraping**. Your Python code shouldn't know or care how IPs rotate. It just sends requests to a local proxy, and the rotation happens upstream.

Deployment is one line:

```bash
docker run -d --name squid \
  --restart=always \
  -p 3128:3128 \
  -v /data/squid/cache:/var/spool/squid \
  sameersbn/squid:latest
```

Configuration has a few hard rules:

```
# Never use the default port — it gets scanned
http_port 0.0.0.0:9128

# Authentication is mandatory
auth_param basic program /usr/lib/squid/basic_ncsa_auth /etc/squid/passwords
auth_param basic realm proxy
acl authenticated proxy_auth REQUIRED
http_access allow authenticated

# Deny everything else
http_access deny all

# Scrapers don't need caching
cache deny all
```

Why this config:

- **Non-standard port**: 3128, 8080, 1080 — these default ports get scanned non-stop by bots probing the public internet. Using 9128 eliminates 90%+ of the noise.
- **Mandatory auth**: An open proxy on the public internet gets discovered and abused within hours. Basic auth with a strong random password stops most scanners.
- **Cloud security groups**: At the firewall level, only allow inbound connections from your scraper server's IP. Defense in depth — even if the password leaks, nobody can connect.

Squid doesn't natively support automatic upstream IP rotation. You need a rotation layer:

```python
import requests
import random

class ProxyPool:
    def __init__(self):
        self.proxies = []
        self.refresh_proxies()

    def refresh_proxies(self):
        resp = requests.get('https://provider-api.com/get-ips?num=50')
        self.proxies = resp.json()['data']

    def get_proxy(self):
        if not self.proxies:
            self.refresh_proxies()
        return random.choice(self.proxies)

    def request(self, url, **kwargs):
        proxy = self.get_proxy()
        return requests.get(
            url,
            proxies={'http': proxy['http'], 'https': proxy['https']},
            **kwargs
        )
```

The core insight: **solve proxy problems at the proxy layer. Don't make your scraper code carry that weight.** It's a separation-of-concerns principle, but in the scraping context it means: when your proxy pool breaks, you fix the proxy pool. Zero changes to scraper code.

## Chapter Three: Making a Browser Do Your Bidding

### When You Actually Need a Real Browser

Some login flows are nearly impossible to replicate with raw HTTP:

- Multi-step login wizards with CSRF tokens buried deep inside `<script>` tags
- CAPTCHAs that appear after login with opaque triggering rules
- Enterprise SSO redirect chains
- SMS or email verification code requirements

The pragmatic solution is to use a headless browser just for login. Complete the login, extract the cookies, and hand them to your Scrapy spider or requests session for everything else.

The browser handles thirty seconds of login. The next ten thousand page requests go through bare HTTP with those cookies.

```python
import asyncio
from pyppeteer import launch

async def login_and_get_cookies():
    browser = await launch(headless=True, args=['--no-sandbox'])
    page = await browser.newPage()

    await page.goto('https://broker.example-insurance.com/login')
    await page.type('#username', 'broker_account')
    await page.type('#password', 'broker_pass')
    await page.click('#login-btn')
    await page.waitForNavigation()

    cookies = await page.cookies()
    await browser.close()
    return cookies
```

Once you have the cookies, feed them into Scrapy. The rest of your pipeline never touches a browser. This "browser as gateway" pattern was one of the most practical advanced techniques of 2018.

### Your Mouse Is Snitching On You

By 2018, some insurance platforms had started analyzing mouse movement patterns. If your cursor goes from (0,0) to (500,300) in a straight line, that's clearly not a human hand.

The fix is Bezier curves to simulate human-like motion:

```python
import random
import asyncio
from typing import List, Tuple

def bezier_curve(p0, p1, p2, p3, steps=50):
    """Cubic Bezier — the math behind smooth curves"""
    points = []
    for t in [i / steps for i in range(steps + 1)]:
        x = ((1 - t) ** 3) * p0[0] + 3 * ((1 - t) ** 2) * t * p1[0] + \
            3 * (1 - t) * (t ** 2) * p2[0] + (t ** 3) * p3[0]
        y = ((1 - t) ** 3) * p0[1] + 3 * ((1 - t) ** 2) * t * p1[1] + \
            3 * (1 - t) * (t ** 2) * p2[1] + (t ** 3) * p3[1]
        points.append((x, y))
    return points

def generate_mouse_path(start, end, steps=60):
    cp1 = (
        start[0] + (end[0] - start[0]) * random.uniform(0.2, 0.4),
        start[1] + random.uniform(-50, 50)
    )
    cp2 = (
        start[0] + (end[0] - start[0]) * random.uniform(0.6, 0.8),
        end[1] + random.uniform(-50, 50)
    )
    path = bezier_curve(start, cp1, cp2, end, steps)

    # Humans overshoot and correct
    overshoot = (end[0] + random.uniform(-5, 10), end[1] + random.uniform(-5, 10))
    path.append(overshoot)
    path.append(end)
    return path

async def human_like_move(page, x, y):
    start = (random.randint(0, 200), random.randint(0, 200))
    path = generate_mouse_path(start, (x, y))
    for px, py in path:
        jx = px + random.gauss(0, 0.5)  # micro-tremors
        jy = py + random.gauss(0, 0.5)
        await page.mouse.move(jx, jy)
        await asyncio.sleep(random.uniform(0.005, 0.015))
```

This isn't perfect — advanced anti-bot systems also analyze timing patterns, scroll behavior, and UI interaction sequences. But it's a hell of a lot better than the straight-line approach most scrapers used at the time. Remember: this is an arms race. You'll never win permanently.

### Remote Debugging: The Underrated Trick

One of the most useful but least-discussed techniques of 2018: Chrome remote debugging.

Your scraper runs on a cloud server. Something goes wrong with the page, and you can't see what the browser is doing. The trick is to launch Chrome in debug mode on the server:

```bash
google-chrome \
  --headless \
  --remote-debugging-port=9222 \
  --no-sandbox \
  --user-data-dir=/tmp/chrome-profile
```

Then create an SSH tunnel from your local machine:

```bash
ssh -L 9222:localhost:9222 user@server
```

Open `chrome://inspect` in your local Chrome, and you get full DevTools control over the remote server's page — inspect elements, set breakpoints, watch network requests, all remote.

The magic of this: you can use a server in the target geographic region to fetch geo-restricted insurance pages, while debugging them with full DevTools from your laptop. Retrieval and debugging happen in the same environment, completing a closed loop.

## Chapter Four: The Data Came Back, But It's Encrypted

### The Double Encryption Nightmare

Some sites encrypt not just the request, but the response too. You fight your way through crafting the correct encrypted request, and what comes back is another blob of garbage. You have to decrypt it again to see the actual policy data.

This pattern shows up on insurance underwriting platforms, product comparison sites, claims management systems — anywhere structured data flows through internal APIs.

The reverse-engineering approach is the same as login encryption, just in reverse:

1. Set an XHR breakpoint on the API endpoint
2. Trigger a request
3. Trace up the call stack from the response handler
4. Find the `CryptoJS.AES.decrypt()` call

You'll typically find an interceptor like this:

```javascript
axios.interceptors.response.use(function (response) {
  if (response.data && response.data.encrypted) {
    var decrypted = CryptoJS.AES.decrypt(response.data.encrypted, CryptoJS.enc.Utf8.parse(KEY), {
      mode: CryptoJS.mode.CBC,
      iv: CryptoJS.enc.Utf8.parse(IV),
    })
    response.data = JSON.parse(decrypted.toString(CryptoJS.enc.Utf8))
  }
  return response
})
```

Once you have the algorithm, key, and IV, the Python side is a mirror operation:

```python
from Crypto.Cipher import AES
from Crypto.Util.Padding import unpad
import base64, json

def decrypt_response(encrypted_b64: str, key: str, iv: str) -> dict:
    cipher = AES.new(key.encode('utf-8'), AES.MODE_CBC, iv.encode('utf-8'))
    encrypted = base64.b64decode(encrypted_b64)
    decrypted = cipher.decrypt(encrypted)
    unpadded = unpad(decrypted, AES.block_size)
    return json.loads(unpadded.decode('utf-8'))
```

With the decryption function in hand, your data flow becomes: send request → get encrypted response → decrypt → get structured JSON → extract policy data.

An important discovery: **the decrypted API response is often far richer than what the page renders**. The rendered HTML might show 20 products with basic summaries per page. The decrypted JSON might contain complete policy documents — all clauses, riders, exclusion lists, premium breakdowns. You're getting more data than any human visitor can see.

## Chapter Five: Cookies Need Maintenance Too

### You're Not Just An IP, You're a "Person"

Changing IPs isn't enough. Many sites track sessions via cookies. Same cookie, too many requests in a short window, and you're flagged.

The solution is a cookie pool — register multiple accounts, log in, extract their cookies, store them, rotate.

**Mass account registration**: Use Puppeteer or Selenium to automate the signup flow. Email verification gets handled through temporary email services (Guerrilla Mail, 10-minute mail). Phone verification is the real bottleneck — you need SMS receiving platforms, and they're not cheap.

**Login and export cookies**: After registration, log in, extract cookies, and store them like this:

```json
{
  "account_id": "broker_1234",
  "cookies": [
    { "name": "sessionid", "value": "abc123...", "domain": ".example-insurance.com" },
    { "name": "csrftoken", "value": "xyz789...", "domain": ".example-insurance.com" }
  ],
  "created_at": "2019-06-15T10:30:00Z",
  "last_used": "2019-06-15T10:30:00Z",
  "status": "active"
}
```

### Cookies Die. You Need a Morgue.

Cookies expire. Sessions time out. The server might invalidate a session after 30 minutes of inactivity, or impose a fixed lifespan like 24 hours.

Keeping an operational cookie pool requires continuous monitoring:

```python
import time
import redis
import json

class CookiePool:
    def __init__(self, redis_client, min_pool_size=20):
        self.redis = redis_client
        self.min_pool_size = min_pool_size

    def get_cookie(self) -> dict:
        cookie_ids = self.redis.smembers('cookie_pool:active')
        if len(cookie_ids) < self.min_pool_size:
            self.trigger_refill()

        cookie_id = random.choice(list(cookie_ids))
        cookie_data = json.loads(self.redis.get(f'cookie:{cookie_id}'))
        cookie_data['last_used'] = time.time()
        self.redis.set(f'cookie:{cookie_data["account_id"]}', json.dumps(cookie_data))
        return cookie_data

    def validate_cookie(self, account_id: str) -> bool:
        cookie_data = json.loads(self.redis.get(f'cookie:{account_id}'))
        try:
            resp = requests.get(
                'https://www.example-insurance.com/api/account',
                cookies={c['name']: c['value'] for c in cookie_data['cookies']},
                timeout=5
            )
            return resp.status_code == 200
        except Exception:
            return False

    def trigger_refill(self):
        # Invoke your Puppeteer login script to replenish
        pass
```

The maintenance rhythm in practice:

- **Spot-check every 5 minutes**: Pick 5 random cookies, test them. If failure rate exceeds 20%, run a full sweep.
- **Full sweep every 30 minutes**: Test all cookies. Remove the dead ones.
- **Refill** when the pool drops below threshold: trigger the automated registration and login pipeline.
- **Rotate every request**: Simple random selection works — the key is not making any single session look anomalously active.

A few cookie attribute traps to watch for:

- `httpOnly`: When set to `true`, JavaScript can't access this cookie — but Python's `requests` library sends it anyway. Don't use JS-accessible cookies to judge what Python can send.
- `secure`: Only sent over HTTPS. Forget this during local debugging and you'll lose an hour cursing yourself.
- `expires`: The server often sets a shorter session timeout at the application layer. Don't trust this value blindly.

Rule of thumb: **treat every cookie as if it might expire after 15 minutes of inactivity**.

## Chapter Six: Distributed — When One Machine Isn't Enough

### Breaking the Problem Apart

By late 2019, I had settled on a layered architecture for scraping insurance policies.

Think of it as an assembly line:

```
Scheduler (when to crawl)
  ↓
Task Queue (what to crawl — Redis with URLs, priorities, retry counts)
  ↓
Worker Cluster (who crawls — multiple Scrapy instances sharing a queue)
  ↓
Proxy Pool (changing faces — Squid instances + upstream IP rotation)
  ↓
Cookie Pool (changing identities — Redis-managed with health checks and auto-refill)
  ↓
Target Website
  ↓
Data Pipeline (dedup → validate → store → index)
```

Each layer is independent. The proxy pool breaking doesn't affect the cookie pool. An empty cookie pool doesn't stop workers from picking up tasks. This decoupling means you won't get woken up at 3am by a single point of failure.

### Making Multiple Workers Share a Task Queue

Scrapy is inherently single-machine. But add `scrapy-redis`, and it can share request queues:

```python
# settings.py
SCHEDULER = "scrapy_redis.scheduler.Scheduler"
DUPEFILTER_CLASS = "scrapy_redis.dupefilter.RFPDupeFilter"
REDIS_URL = 'redis://localhost:6379/0'
REDIS_START_URLS_KEY = 'spider:start_urls'
```

With this config, push a URL into Redis from any machine:

```bash
redis-cli lpush spider:start_urls "https://www.example-insurance.com/policies/page/1"
```

Any idle worker grabs it. Simple. Stable. Horizontally scalable. Your job is just adding machines — each worker runs on its own server or Docker container, all pulling from the same Redis instance.

### Proxy Pool, Independently Managed

```python
# proxy_pool.py
import redis
import requests
import json
import time

class ProxyPoolManager:
    def __init__(self, redis_client):
        self.redis = redis_client
        self.refresh_interval = 180  # 3 minutes

    def refresh_proxies(self):
        resp = requests.get('https://proxy-api.com/get?num=50&format=json')
        proxies = resp.json()['proxies']
        pipe = self.redis.pipeline()
        for proxy in proxies:
            key = f"proxy:{proxy['ip']}:{proxy['port']}"
            pipe.setex(key, self.refresh_interval * 2, json.dumps(proxy))
        pipe.execute()

    def run(self):
        while True:
            try:
                self.refresh_proxies()
            except Exception as e:
                print(f"Proxy refresh failed: {e}")
            time.sleep(self.refresh_interval)
```

On the worker side, one job — grab a proxy from Redis:

```python
def get_random_proxy(redis_client) -> dict:
    keys = redis_client.keys('proxy:*')
    if not keys:
        return None
    key = random.choice(keys)
    return json.loads(redis_client.get(key))
```

Proxies and cookies are managed independently. Workers don't know where proxies come from or how cookies are maintained — they just request from the respective pools. It's a design subtraction, but its payoff is multiplicative.

### Storing Data Is Just Step One

Once you have millions of records, deduplication and retrieval become their own problems.

**Deduplication**: At the URL level, `scrapy-redis` handles it via Redis sets automatically. At the item level, you need your own:

```python
class DedupPipeline:
    def __init__(self, redis_client):
        self.redis = redis_client

    def process_item(self, item, spider):
        key = f"seen:{item['insurer']}:{item['policy_id']}"
        if self.redis.exists(key):
            raise DropItem(f"Duplicate: {item['policy_id']}")
        self.redis.setex(key, 86400 * 7, '1')
        return item
```

**Storage**: In 2018-2019, MongoDB was the default for scraped data. It handles unstructured data well, has good write throughput, and its document model naturally maps to insurance policies with their deeply nested structure — main clauses, riders, exclusions, cash value tables.

```python
from pymongo import MongoClient

class MongoPipeline:
    def __init__(self):
        self.client = MongoClient('mongodb://localhost:27017/')
        self.db = self.client['insurance_data']

    def process_item(self, item, spider):
        collection = self.db[spider.name]
        collection.update_one(
            {'_id': item['policy_id']},
            {'$set': dict(item)},
            upsert=True
        )
        return item
```

At million-record scale, switch to batch writes:

```python
class BatchMongoPipeline:
    def __init__(self):
        self.buffer = []
        self.batch_size = 100

    def process_item(self, item, spider):
        self.buffer.append(dict(item))
        if len(self.buffer) >= self.batch_size:
            self.flush(spider)
        return item

    def flush(self, spider):
        self.db[spider.name].insert_many(self.buffer)
        self.buffer.clear()

    def close_spider(self, spider):
        if self.buffer:
            self.flush(spider)
```

When MongoDB holds tens of millions of policy records, querying without an index is a nightmare. Create indexes on frequently queried fields — insurance type, premium, effective date. For time-series data (premium changes, new product launches), partition collections by day — makes deleting old data easy and keeps individual collection sizes manageable.

For ad-hoc analysis, use pandas:

```python
import pandas as pd
from pymongo import MongoClient

client = MongoClient()
cursor = client.insurance_data.policies.find(
    {'insurance_type': 'medical'},
    {'_id': 0, 'product_name': 1, 'premium': 1, 'coverage_amount': 1}
)
df = pd.DataFrame(list(cursor))
df['premium'] = pd.to_numeric(df['premium'])
print(df.describe())
```

For real-time dashboards, pipe data into Elasticsearch as it arrives — instant full-text search and aggregation across the entire dataset.

## Chapter Seven: Looking Back from 2026

It's been years since those records above. The fundamental principles haven't changed much — encryption is still encryption, cookies are still cookies — but the landscape has shifted in a few important ways.

### What Got Harder

**Bot detection leveled up massively**. Cloudflare, Akamai, DataDome now analyze TLS fingerprints (JA3/JA4), HTTP/2 frame patterns, Canvas/WebGL fingerprinting, even keystroke timing. A bare `requests.get()` with a fake User-Agent gets identified on protected sites almost instantly.

**CAPTCHAs went invisible**. reCAPTCHA v3 and hCaptcha score every page visit silently. You don't even see a challenge — if your score is too low, the site just returns garbage data. Getting past this requires browser-level simulation that passes all fingerprint checks.

**Data went mobile**. Many insurance services moved data into mobile apps with certificate pinning and obfuscated API protocols. Scraping these means either reverse-engineering the mobile app (Frida, objection, APK decompilation) or intercepting API traffic at the network layer (mitmproxy + certificate unpinning).

**Legal risk got more complicated**. GDPR, CCPA, and various data protection laws make the legal landscape murkier. A few landmark cases (hiQ v. LinkedIn, Van Buren v. US) clarified some boundaries, but overall it's still a gray area.

### What Got Easier

**AI-assisted reverse engineering**. In 2026, you can throw a chunk of obfuscated JS at an LLM and get a mostly-correct deobfuscated version in seconds. Not 100% accurate, but it saves 80% of the work. ChatGPT, Claude, and various Copilot integrations can recognize encryption patterns, suggest Python equivalents, and help reconstruct function logic.

**Headless browser reliability**. Playwright has mostly replaced Puppeteer as the default for browser automation. It supports multiple browsers (Chromium, Firefox, WebKit), has better auto-waiting, and is maintained by Microsoft. For JS-rendered scraping, Playwright + stealth plugins is the current best practice.

```python
# 2026-style browser scraping
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch(headless=True)
    context = browser.new_context(
        user_agent='Mozilla/5.0 ...',
        viewport={'width': 1920, 'height': 1080},
        locale='en-US',
    )
    page = context.new_page()
    page.goto('https://www.example-insurance.com')
    content = page.content()
    browser.close()
```

**Proxy infrastructure matured**. Residential proxy networks have improved dramatically. Bright Data, Oxylabs, Smartproxy now offer massive, high-quality residential IP pools. Prices have dropped significantly since 2018. But for high-concurrency scraping, datacenter proxies with careful rotation remain the economical choice if you're building it yourself.

**New tools emerged**:

- **Crawlee** (by Apify): A modern Python framework supporting both HTTP scraping and headless browser crawling, with built-in auto-scaling and proxy rotation.
- **ScrapeGraphAI**: An LLM-based scraper — describe the target data schema in natural language and it extracts structured data from HTML. Good for prototypes, but too slow and expensive for production pipelines.
- **Browserbase / Rebrowser**: Headless browser platforms as a service. They handle fingerprinting, proxy rotation, CAPTCHA solving. You pay a premium but skip the infrastructure work.

### What Hasn't Changed

**The core workflow**: You still need to understand encryption, manage proxies, handle cookies, and distribute work across workers. Tools change. Problems don't.

**Economies of scale**: If you're scraping millions of pages a month, building your own proxy pool, cookie pool, and distributed architecture is still cheaper than paying scraping SaaS. For small projects, SaaS tools have gotten good enough that DIY isn't worth it.

**JS reverse engineering as a core skill**: Even with AI assistance, you still need to understand what you're looking at. LLMs hallucinate. They'll suggest a decryption approach that sounds convincing but produces garbage. That ability to "verify byte-for-byte that your Python decryption matches the browser output" — that hasn't been automated yet.

**The cat-and-mouse game**: Sites add new anti-scraping measures. Scrapers develop new countermeasures. The cycle continues. The specific technologies evolve, but the underlying game is identical to 2018.

## You Don't Need to Memorize All This — But Ask the Right Questions

This article is the sum of everything I stepped in over two years. You don't need to remember every code snippet. But the next time you're staring down a defended website, run through these questions:

1. **Where's the encryption?** Login request? API response? Both? First figure out how many directions you need to reverse.

2. **How findable is the JS?** Webpack bundle or custom framework? Can you read it after formatting? Roughly how many lines?

3. **How many dimensions of identity rotation do you need?** Is IP rotation enough? Or are cookies also tracked? Do you need an account pool?

4. **Do you need a browser?** If the login flow is complex (multi-step, CAPTCHA, SSO), consider using a headless browser only for login. Everything else stays on raw HTTP.

5. **What's the scale?** A few hundred pages — one machine, raw requests. Tens of thousands — add a proxy pool and cookie pool. Millions — you need distributed architecture.

6. **Can you just buy a service?** What's the value of your project? What's the volume? If you're validating an idea, use a managed scraping service. If this is your core data pipeline, build the infrastructure.

7. **Have you weighed the legal risk?** Does the target site's robots.txt prohibit scraping? Are there terms of service restrictions? What's the purpose of the data you're collecting?

That's it. What worked in 2018 still mostly works in 2026. Tools evolve, techniques iterate, but the core principles don't change — understand what the browser is actually sending, replicate it faithfully, rotate your identity, distribute the load.

And honestly? That's what makes this fun. The day scraping becomes a completely "solved problem" is the day it stops being interesting.
