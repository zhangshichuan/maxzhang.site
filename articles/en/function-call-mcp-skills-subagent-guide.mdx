If you have been reading about AI agents lately — through Codex, Claude Code, Cursor, the OpenAI Agents SDK, or other agent frameworks — you have probably seen these terms over and over:

- `function call`
- `MCP`
- `A2A`
- `skills`
- `subagent`

They all relate to the same broad goal: making models do more than chat. But they are not the same kind of thing.

That is where a lot of confusion starts. Some people treat MCP as a more advanced version of function calling. Some treat A2A as a competitor to MCP. Some treat skills as just another name for tools. Some think subagents are basically multithreading with extra branding. None of those interpretations is quite right.

This article puts all five ideas back into the context where they emerged and explains them as a system: **why each one appeared, what problem it solves, what it does not solve, and how they fit together in real agent architectures.**

---

# The short version: these are not peer concepts

If you want the core idea first, here it is:

> `function calling` answers: how does a model request a concrete external action?
> `MCP` answers: how are external capabilities exposed to model systems through a standard protocol?
> `A2A` answers: how do different agents communicate and collaborate across systems using a standard protocol?
> `skills` answer: how does an agent reuse a stable way of working for a class of tasks?
> `subagents` answer: when one agent is not enough, how do you split work across multiple agents?

These ideas sit at different layers:

```text
User task
  ↓
Main agent reasoning and planning
  ↓
If the task is complex and needs delegation
  → subagents (within one system)
  → A2A (across different agent systems)
  ↓
If execution needs reusable working patterns
  → skills
  ↓
When interacting with the outside world
  → function calls / tools
  ↓
How those external capabilities are exposed
  → often through MCP
```

Put differently:

- `function calling` is about the invocation itself
- `MCP` is about standardized tool integration
- `A2A` is about standardized agent-to-agent communication
- `skills` are about reusable task expertise
- `subagents` are about task organization within a single system

Once you see that layering clearly, most of the confusion disappears.

# 1. Why plain chat-based LLMs were not enough

The earliest LLM products mostly looked like this:

```text
User asks a question
  ↓
Model generates text from context
  ↓
Returns an answer
```

That setup is powerful, but it has three built-in limitations.

## 1. The model knows things, but cannot directly touch the outside world

For example:

- "Check how many orders we processed today."
- "Assign this ticket to the backend team."
- "Pull this PR and run the tests."

The model itself cannot access your database, call internal APIs, or execute shell commands. At most, it can describe what should be done.

## 2. It can describe a process without actually performing it

Suppose a user says:

> Analyze this production incident and check the last 24 hours of error logs.

A pure chat model can produce a very confident troubleshooting plan:

1. Inspect the logs
2. Check alerts
3. Classify error patterns
4. Provide a conclusion

The problem is obvious: **it never actually looked at the logs.**

## 3. It can improvise, but it does not naturally execute stable workflows over time

Imagine you want a coding agent to consistently follow team conventions:

- read the code before editing
- prefer `rg` for search
- apply edits via patch
- run the smallest useful verification first
- in review mode, list findings before summary

If all of that lives only in ad hoc prompting, behavior drifts.

This is why agent systems evolved in layers. Function calling, MCP, A2A, skills, and subagents each emerged to solve a different part of that gap.

# 2. Function Calling: first solve "how does the model act?"

## 2.1 Where it came from

Before structured tool calling became standard, many teams built "action-taking" systems like this:

1. Ask the model to output some JSON
2. Parse the JSON in backend code
3. Decide whether it represents an action
4. Execute that action
5. Feed the result back to the model

For example:

```json
{
  "action": "get_weather",
  "city": "Shanghai"
}
```

This works, but only up to a point:

- output formats drift
- field names change unexpectedly
- argument types become unreliable
- validation is awkward
- model-to-model compatibility is weak

Function calling, or tool calling, emerged to solve exactly that. The idea is simple:

> Do not let the model freestyle something that merely looks like a tool invocation. Instead, let it choose from declared tools and produce arguments that conform to a schema.

## 2.2 What it solves

### 1. It gives the model a structured way to request external actions

Suppose you define:

```ts
getWeather(city: string, date?: string)
```

When the user says:

> Check tomorrow's weather in Shanghai.

The model can return something like:

```json
{
  "name": "getWeather",
  "arguments": {
    "city": "Shanghai",
    "date": "2026-04-15"
  }
}
```

That is very different from free-form text that your backend has to guess how to interpret.

### 2. It separates reasoning from execution

The model is responsible for:

- deciding whether a tool is needed
- selecting the right tool
- filling in the parameters

The host system is responsible for:

- actually executing the function
- validating arguments
- enforcing permissions
- handling retries, timeouts, and auditability

This separation matters. **The model is not the executor. It is the requester.**

### 3. It makes agent loops practical

A typical loop looks like this:

```text
User request
  ↓
Model chooses a function call
  ↓
Host executes it
  ↓
Result goes back to the model
  ↓
Model reasons again
  ↓
Final answer or another tool call
```

Without structured function calling, it is much harder to make the "reason → act → observe → reason again" loop reliable.

## 2.3 What it does not solve

Function calling is foundational, but it is not a complete agent system.

It does not solve:

- how tools are discovered or registered
- whether tools are local, remote, or shared
- how different applications reuse the same tool ecosystem
- long-horizon planning
- reusable task methodology
- delegation across multiple agents
- how different agents communicate with each other

So function calling is the starting layer, not the whole architecture.

## 2.4 A minimal example

Imagine an operations assistant with two functions:

```ts
getServiceStatus(serviceName: string)
restartService(serviceName: string)
```

The user says:

> Check whether `payment-service` is down, and restart it if needed.

The system might work like this:

```text
1. The model calls getServiceStatus("payment-service")
2. The system returns: status = unhealthy
3. The model calls restartService("payment-service")
4. The host executes the restart
5. The model summarizes the outcome for the user
```

Function calling solves the "how does the model request these actions?" part.

# 3. MCP: then solve "how do tools connect in a standard way?"

## 3.1 Where it came from

Once function calling became common, a new problem showed up:

**Where do these tools come from, how are they described, and how do multiple hosts reuse them?**

Suppose you have capabilities like:

- filesystem access
- Git operations
- database queries
- browser automation
- internal ticket APIs
- documentation search

The naive approach is to wire each one manually into every agent application. That quickly becomes messy:

- app A defines the database tools one way, app B does it differently
- your IDE assistant and your web agent duplicate the same integration logic
- tool descriptions diverge
- permission handling is inconsistent
- moving to a new host means rebuilding the tool layer again

This is the problem space where MCP appeared.

## 3.2 What MCP is

A practical way to think about MCP is:

> a standard protocol between model hosts and external capability providers

It is concerned with questions like:

- how external systems expose capabilities
- how hosts discover them
- how inputs and outputs are described
- how resources, prompts, and tools are surfaced in a unified way

If function calling answers "how does the model express a desire to use a tool?", MCP answers "how is that tool made available to model systems in the first place?"

## 3.3 What it solves

### 1. Standardized capability integration

Before protocol-level standardization, every host tends to define the same things repeatedly:

- tool name
- argument schema
- descriptive metadata
- execution wiring

MCP shifts that toward a cleaner model:

- an `MCP Server` exposes capabilities
- an `MCP Client` consumes them

For example, a Git-oriented MCP server might expose:

- `git_status`
- `git_diff`
- `git_log`
- `create_branch`

Any host that speaks MCP can then integrate that same capability surface.

### 2. It decouples tool providers from model hosts

This is one of the most important gains.

Without a standard protocol, architectures often look like this:

```text
Specific host application
  ↔ hard-coded tool integration
```

With MCP, the architecture becomes closer to:

```text
Agent host
  ↔ MCP Client
  ↔ MCP Server
  ↔ external system
```

That gives you:

- independently evolving tool servers
- reuse across multiple hosts
- easier enterprise standardization
- more centralized governance for permissions and auditing

### 3. It treats resources as first-class citizens, not just functions

Many people focus only on tools, but real agent systems also need access to:

- files
- documents
- tables
- prompt assets
- execution context

Part of MCP's value is that it provides a more unified way to surface those things rather than forcing everything into a "pretend function" shape.

## 3.4 MCP's evolution: from v1.0 to v2.0

Understanding MCP's version history reveals what level of problem it is actually solving.

### Phase one: MCP is born (2024-11-05)

The initial MCP spec defined two transport mechanisms:

- **stdio**: the client launches the MCP server as a subprocess and communicates over standard in/out. Ideal for local tools.
- **HTTP + SSE**: the server receives requests via HTTP POST and pushes responses and notifications via Server-Sent Events. Ideal for remote tools.

This version solved the core problem of "tools can be shared across hosts" and was quickly widely adopted. But it exposed several issues in production:

- **HTTP+SSE is firewall-unfriendly**: many enterprise firewalls and proxies struggle with persistent long-lived stream connections
- **Complex connection management**: maintaining both POST and SSE endpoints is fragile
- **No standard authentication**: access control for remote MCP servers is entirely up to individual implementors
- **No tool metadata**: hosts cannot distinguish read-only from destructive tools, forcing all-or-nothing permission models

### Phase two: MCP 2.0 (2025-03-26)

The March 2025 revision (often called "MCP 2.0" by the community) was a major update introducing four key capabilities:

**① Streamable HTTP replaces HTTP+SSE**

This is the most significant change. Streamable HTTP uses a single HTTP endpoint that supports both POST (client→server) and GET (server→client push), eliminating the need for dual endpoints. Think of it as a "bidirectional HTTP pipe" — both sides can send messages, all through standard HTTP requests:

- any HTTP-supporting firewalls and proxies work out of the box
- connections can be gracefully established and resumed
- session management via `Mcp-Session-Id` header
- broken streams can be resumed using `Last-Event-ID`

This change takes MCP from "fine for local/dev environments" to "truly production-ready for remote deployment."

**② OAuth 2.1 authorization framework**

With standardized authentication, enterprise MCP servers can have a unified permission model. MCP clients complete a standard OAuth flow on connection to obtain access tokens.

**③ Tool Annotations**

Each tool can carry metadata declaring its properties:

- `readOnlyHint`: whether the tool is read-only
- `destructiveHint`: whether it has destructive effects
- `idempotentHint`: whether repeated calls are safe
- `openWorldHint`: whether it accesses the open internet

This enables fine-grained authorization. Read-only tools can be auto-approved, destructive tools require user confirmation, and tools that access external networks require additional review.

**④ JSON-RPC Batching**

Clients can send multiple JSON-RPC calls in a single HTTP request, reducing round trips. For agent scenarios that make dense tool calls, batching significantly lowers latency.

### The logic behind the evolution

Looking back, MCP's evolution follows a clear arc:

```text
MCP v1.0 (2024-11)
  - stdio: solves "local tool reuse"
  - HTTP+SSE: solves "remote tool access"
  → Core question: can tools be shared across hosts?

MCP v2.0 (2025-03)
  - Streamable HTTP: makes remote access production-ready
  - OAuth 2.1: standardizes permission management
  - Tool Annotations: makes tool properties describable
  - JSON-RPC Batching: makes invocations more efficient
  → Core question: not just "can tools be shared", but "can they be managed, governed, and secured?"
```

MCP is not a static spec. It keeps answering more specific questions: "Can tools be shared? → Can sharing work in production? → Is production sharing secure and controllable?"

## 3.5 What it does not solve

MCP is infrastructure, not intelligence.

It does not:

- plan tasks for you
- decide when to call which tool
- write good prompts automatically
- split work across multiple agents
- handle agent-to-agent communication (that is what A2A does)

It standardizes integration. It does not replace orchestration or reasoning.

## 3.6 A helpful analogy

One simple analogy is:

- `function calling` is like dialing a number
- `MCP` is like having a standardized telecom network
- MCP v1.0 → v2.0 is like the telecom network evolving from "calls connect" to "caller ID, encryption, and plan management"

A phone number by itself does not create an interoperable system. But a communications protocol alone does not decide who to call or why.

## 3.7 Example: an internal enterprise assistant

Suppose your company has three systems:

- Jira
- Confluence
- an internal deployment platform

Without standardization, each AI product has to integrate all three separately.

With MCP, a platform team might build:

- `jira-mcp`
- `confluence-mcp`
- `deploy-mcp`

Then multiple hosts can reuse them:

- an IDE coding assistant
- a Slack-based support agent
- an internal web operations assistant

MCP turns tool integration from repeated app-specific work into a reusable capability layer.

Even better with MCP 2.0:

- `deploy-mcp` tools can be annotated with `destructiveHint: true`, so the assistant auto-requests user confirmation before triggering deploys
- all MCP servers share unified OAuth, so permission administration happens in one place
- even assistants in overseas offices connect cleanly to internal Streamable HTTP endpoints over standard HTTPS

# 4. Skills: solve "does the agent know how to work?"

## 4.1 Where they came from

As tool ecosystems got richer, another issue became obvious:

> Having tools is not the same as knowing how to use them well.
> Being able to call functions is not the same as reliably completing a task.

Take a bug-fixing workflow. Two agents might have access to the exact same tools:

- one edits code immediately and changes the wrong module
- another reads logs, traces the call path, inspects tests, and applies the smallest useful fix

The difference is not tool availability. It is working method.

That is what skills address.

## 4.2 What a skill really is: more than a prompt — it is a "context override"

A useful mental model is:

> a reusable packet of task-specific operating knowledge

A skill may include:

- task definition
- when to use it
- working steps
- behavioral constraints
- examples
- recommended tools
- common pitfalls

But if you stop there, you might think a skill is just "a really detailed prompt." That is not wrong, but it misses a crucial insight.

**Skills are fundamentally a mechanism of "context override."**

What does that mean? An LLM's behavior is largely determined by what sits in its context window. Normally, the context looks like:

```
system prompt + user messages + conversation history + tool definitions
```

When an agent activates a skill, it injects an entire **professional cognitive framework** into the context window — not just "what to do," but also "who you are right now," "what you should prioritize," "which traps to avoid," and "what your output should look like."

This framework effectively **overrides** the model's default behavior pattern, much like how a subclass method overrides a parent class's default implementation in object-oriented programming:

```text
Default LLM behavior (parent class):
  - general chat mode
  - casual solution suggestions
  - free-form output

After loading "code-fix" skill (subclass override):
  - read code before touching it
  - minimal change first
  - always verify after editing
  - output includes file paths and diffs
```

From this angle, skill and RAG have a key distinction:

- **RAG** injects *knowledge* — it tells the model "what the facts are"
- **Skill** injects *methodology* — it tells the model "how you should think and act right now"

Here is a concrete example. Suppose you create a code review skill:

```text
# Code Review Skill

## Identity
You are a code reviewer focused only on code quality. No pleasantries needed.
Do not comment on anything beyond code quality.

## Review Priorities
1. Logic errors and edge cases
2. Security vulnerabilities
3. Performance issues
4. Maintainability concerns

## Output Format
- List issues by severity
- Include file paths and line numbers
- Explicitly say "No issues found" when appropriate
- Do not put a change summary at the top
```

When an agent loads this skill, multiple things happen simultaneously:

1. **Identity override**: switches from "general assistant" to "code reviewer"
2. **Priority reshape**: focuses from "could mention anything" to "severity-ordered inspection"
3. **Output constraint**: locks from "free format" to "structured review report"
4. **Behavior boundary**: explicitly says "say no issues when there are none," preventing the urge to "find something no matter what"

None of this is achievable through external tools. Tools provide capability, not methodology. The value of a skill lies in solidifying methodology into an executable "behavior program" within the context.

## 4.3 Why context override matters

This layer is frequently underestimated, but it solves a very fundamental problem:

**LLMs are generalists. Tasks require specialization.**

A general-purpose LLM has immense breadth (trained on nearly all of human text), but precisely because it "knows a little about everything," it often shows "a little depth, not enough" or "knows how but can't execute consistently" on specific tasks.

The context override mechanism of skills enables the model to demonstrate **expert-level execution consistency** on specific tasks — without changing model parameters.

This consistency comes from the "soft constraint system" that a skill establishes in context:

- What to do first, what to do next → prevents step-skipping
- What can and cannot be done → prevents boundary-crossing
- How to handle problems → prevents getting stuck
- What the output should look like → prevents format drift

This is why a well-designed skill file often performs far better than a "long prompt saying the same thing" — a prompt is just "a sentence," while a skill systematically "sets up a working environment" inside the context.

## 4.4 What skills solve

### 1. They stabilize execution style for recurring tasks

For example, the code review skill above. Every time a code review is done, the agent's behavior stays consistent.

### 2. They reduce the repetition cost of complex prompting

Without skills, teams often keep rewriting giant prompts such as:

> You are a senior architect. First do this, then do that, watch out for these cases...

That does not scale well, and it is hard to share across a team.

Skills turn that knowledge into a reusable asset.

### 3. They bind domain knowledge and workflow together

Imagine a skill specifically for giving OpenAI API implementation guidance. It might encode rules like:

- prefer official documentation first
- avoid outdated parameters
- recommend models based on latency, cost, and capability tradeoffs
- favor official SDK-style examples

That is more than a generic prompt. It is a scoped, specialized working pattern.

## 4.5 What skills do not solve

Skills do not directly solve:

- how external systems connect
- how tools execute
- how multi-agent orchestration works
- how different agent systems communicate with each other

So a skill is not a tool, not a protocol, and not a scheduler.

## 4.6 Example: a technical writing skill

Suppose you define a technical writing skill with instructions like:

```text
Use cases:
- engineering deep-dives
- explanatory architecture articles

Requirements:
- start with the problem context, then explain the solution
- do not stop at definitions — explain why something is needed
- always include concrete examples
- avoid turning the article into a glossary
- default to Chinese unless requested otherwise
```

Now when an agent is asked to write about MCP, it behaves more like a consistent technical writer and less like a generic chatbot improvising on the spot.

# 5. A2A: then solve "how do agents talk to each other?"

## 5.1 Where it came from

Function calling, MCP, and skills solve a core set of problems:

> How does a single agent use tools, integrate capabilities, and execute tasks consistently?

But as agent systems mature, a new question emerges:

**How do different agents collaborate?**

Consider a real enterprise scenario:

- One agent handles code reviews (deployed next to the company GitLab)
- One agent handles ticket management (integrated with Jira)
- One agent handles documentation search (integrated with Confluence)
- One agent handles deployment coordination (integrated with CI/CD)

These agents may be built by different teams, using different frameworks, running on different servers. Now a user asks: "Investigate this 500 error — check recent code changes, related tickets, and deployment history."

A single agent cannot easily handle this — it may not have Jira permissions, and it may not understand deployment workflows. You could use MCP to connect all tools into one agent, but then:

- **You do not want one agent to have access keys to every sensitive system.** Security-wise, scoping each agent to its own domain is safer.
- **Internal tool implementations should not be directly callable by external agents.** The code review agent might use complex AST analysis toolchains that the development team does not want exposed.
- **What agents need from each other is not "tool calls" but "task delegation."** When you say "check the tickets related to this bug," you are not calling a function — you are delegating a subtask to another agent to think, search, and summarize.

This is what `A2A` (Agent-to-Agent Protocol) addresses.

## 5.2 What A2A is

A2A (Agent-to-Agent Protocol) is an open protocol originally proposed by Google and later contributed to the Linux Foundation. Its definition is clear:

> An open protocol enabling communication and interoperability between AI agents built on different frameworks, by different vendors, running on different servers — without requiring them to expose their internal state.

If MCP solves the *vertical* problem of agents connecting downward to tools, A2A solves the *horizontal* problem of agents collaborating with one another.

## 5.3 Core concepts

The A2A protocol revolves around several key design elements:

### 1. Agent Card

Every A2A server exposes an Agent Card — a JSON capability document describing:

- Who the agent is (name, description, provider)
- What it can do (skill listings, not tool listings)
- How to connect to it (URL, supported transport bindings)
- Authentication requirements (OAuth, API key, etc.)

This is like DNS for the internet, or `package.json` for the npm ecosystem — a standardized self-description that allows other agents to discover and understand it.

```json
{
  "name": "Code Review Agent",
  "description": "Reviews pull requests for code quality and security issues",
  "url": "https://code-review.internal.example.com",
  "skills": [
    { "id": "code_review", "name": "Code Review", "description": "..." },
    { "id": "security_scan", "name": "Security Scan", "description": "..." }
  ],
  "defaultInputModes": ["text", "file"],
  "defaultOutputModes": ["text", "file"]
}
```

Notice it describes "skills" (what task it can complete), not "tools" (what functions it has). This is intentional — A2A does not care how the other agent works internally, only what outcome it can deliver.

### 2. Task

The core unit of work in A2A is not a "function call" but a "Task." A task has its own lifecycle:

```text
pending → working → input-required → working → completed
                → failed
                → canceled
```

This matters because A2A natively supports **long-running tasks** and **multi-turn interactions**. One agent can delegate a task to another and come back later for the result. During execution, the delegated agent can even request more information (`input-required` state), enabling multi-turn dialogue.

### 3. Streaming and push notifications

A2A supports three interaction modes:

- **Synchronous request/response**: simple Q&A
- **Streaming SSE**: real-time progress updates (e.g., "code review 60% complete")
- **Async push notifications**: webhook callbacks when long-running tasks finish

### 4. Opaque execution

A core design principle of A2A: **agents collaborate without exposing internal state.** The other agent's prompts, toolchain, and reasoning process are all black boxes — you only need to know "what it can do" and "what it produced."

This solves a critical enterprise security concern: you do not expose your internal tool implementations, database schemas, or business logic to external agents.

## 5.4 How A2A relates to MCP

These two protocols are frequently compared. The key is understanding their **directionality**:

```text
        Agent ↔ Agent
            ↑
           A2A
            ↑
┌─────────────────────────┐
│         Agent           │
│  ┌───────────────────┐  │
│  │   LLM + Prompt    │  │
│  │   + Skills        │  │
│  └───────────────────┘  │
│           ↓             │
│      Function Call      │
│           ↓             │
│         MCP             │
│           ↓             │
│   Tools / Resources     │
└─────────────────────────┘
```

- **MCP is vertical**: agents call downward to tools, access resources, read data. It answers: "how does this agent integrate external capabilities?"
- **A2A is horizontal**: agents delegate tasks to each other, exchange information. It answers: "how do these agents form a collaborative network?"

MCP and A2A are not competitors — they are **complementary**. MCP gives agents "hands" to do concrete work. A2A gives agents "mouths and ears" to negotiate who does what.

A classic analogy:

- **MCP** = internal corporate tool standards (all employees use the same office software, same process systems)
- **A2A** = inter-company cooperation standards (how different companies place orders, sign contracts, and deliver results)

## 5.5 What it does not solve

A2A does not solve:

- task planning within a single agent
- tool invocation and execution
- multi-agent orchestration within a single system (that is what subagents do)
- what methodology an agent should use for a task (that is what skills do)

A2A solves exactly one thing: **letting agents discover each other, communicate securely, and collaborate on tasks at the network level.**

## 5.6 Example: cross-system incident investigation

Returning to the opening scenario. The user says:

> Investigate this production 500 error.

With A2A, the system can work like this:

```text
Main Agent (user conversation interface)
  ↓ via A2A delegation
  ├──→ Code Review Agent: check recent 24h of related code changes
  ├──→ Ticket Management Agent: find Jira tickets linked to this bug
  └──→ Deployment Coordination Agent: check recent deploy records and env changes

Each delegated agent runs independently:
  - uses MCP to connect to its own specialized tools
  - uses function calls for concrete operations
  - uses skills to maintain working method consistency

Finally, each agent returns results via A2A to the main agent, which summarizes for the user.
```

The key: each agent only exposes "what it can do" (via its Agent Card), not "how it does it" (internal tools and logic). Secure, controlled, auditable.

# 6. Subagents: solve "one agent cannot do everything well"

## 6.1 Where they came from

Once tasks get large enough, even a capable agent with good tools and good skills starts to hit limits.

Consider a task like:

> Refactor this repository's authentication flow, fix three API bugs, add tests, and write migration notes.

If one agent handles everything sequentially, several problems appear quickly:

- the context gets too large
- multiple lines of work compete for attention
- local details crowd out the main plan
- progress becomes harder to manage

That is where subagents enter the picture.

## 6.2 What a subagent is

A subagent is best understood as:

> a delegated agent that the main agent spins up to handle a scoped subproblem

It is not just a function call or a simple tool. It is closer to:

- an independent reasoning unit
- an executor with its own context budget
- a smaller agent that can inspect context, use tools, and return a result

## 6.3 How subagents differ from A2A

This is an easy point of confusion.

- **Subagents** are an **intra-system** task decomposition mechanism. They happen within a single agent framework, managed by the same host process, sharing the same tool registry and context management. Subagents need no protocol — the host directly manages their lifecycle.
- **A2A** is a **cross-system** collaboration protocol. It connects independently deployed, independently running agents — possibly built with different frameworks, in different languages, on different servers. They communicate through a standardized protocol and are mutually opaque.

An analogy:

- Subagents are like **task delegation within a single team** (a manager assigns work to team members who share tools and context)
- A2A is like **cross-company collaboration** (you place an order with an external vendor; they fulfill it in their own system; you do not need to know how)

The two can compose: a main agent might delegate via A2A to an external specialized agent, and that external agent might internally use subagents to decompose the work.

## 6.4 What subagents solve

### 1. Task decomposition

The main agent does not have to do everything itself.

For example:

- the main agent owns the plan
- subagent A analyzes the authentication module
- subagent B checks the failing tests
- subagent C gathers deployment history

### 2. Parallelism

Some work is naturally parallel:

- reading different code areas
- researching separate sources
- editing disjoint files
- running independent verification tasks

Subagents can reduce end-to-end latency significantly.

### 3. Context isolation

This is one of the most underrated benefits.

A single agent can get polluted by too much detail. Subagents let the system isolate local work and bring back only the result that matters.

For instance, the main agent may not need raw test output. It may only need:

- which tests failed
- why they failed
- whether the failures block delivery

## 6.5 What subagents do not solve

Subagents are not a substitute for the lower layers.

They do not solve:

- tool standardization
- tool schema design
- reusable task methodology
- cross-system agent communication

In other words, subagents solve an organizational problem, not a capability-definition problem.

## 6.6 Example: a repository-wide change

Suppose the main agent gets:

> Add idempotency protection to the payment flow and cover it with tests.

A good decomposition might be:

```text
Main agent:
- understand overall architecture
- design the change strategy

Subagent A:
- inspect API handlers and services
- identify where idempotency is missing

Subagent B:
- inspect the existing tests
- identify coverage gaps

Subagent C:
- run tests independently
- summarize failures
```

The main agent then integrates those results into the final implementation plan.

# 7. How these ideas fit together

At this point, the relationship should be clearer.

## 7.1 Function calling is the base execution interface

It answers:

> How does the model express a request to use an external capability?

Without it, the model can talk about actions but cannot request them reliably.

## 7.2 MCP is the integration standard

It answers:

> How are those external capabilities made available to model systems in a reusable, standardized way?

Function calling can invoke a tool. MCP helps make tool ecosystems portable and shareable. From v1.0 to v2.0, the protocol evolved from "can connect" to "can connect with governance."

## 7.3 Skills are the task-method layer

They answer:

> Given access to capabilities, how should the agent approach this class of work?

Skills turn agents from "tool-enabled" into "more consistently competent." Through context override, they establish a professional working framework inside the model's cognitive space.

## 7.4 A2A is the agent-to-agent collaboration protocol

It answers:

> How do different agents discover each other, communicate securely, and delegate tasks?

A2A moves the agent ecosystem from "solo performers" to "networked collaboration." It does not replace MCP or skills — it provides a common language for agents at a higher level.

## 7.5 Subagents are the task-organization layer

They answer:

> When the task becomes too large for one reasoning loop, how should the work be split and coordinated?

Subagents organize work within a single system; A2A organizes collaboration across systems. Both solve the "division of labor" problem, but at different scopes.

The five layers can be summarized as:

```text
User task
  ↓
Planning layer: subagents (decomposition), A2A (cross-agent delegation)
  ↓
Experience layer: skills (working methodology)
  ↓
Execution layer: function calls (concrete actions)
  ↓
Integration layer: MCP (standardized tool and resource exposure)
```

# 8. A complete scenario: an enterprise engineering assistant

Suppose you are building an enterprise engineering assistant that can:

- inspect code
- search documentation
- read tickets
- run tests
- generate change summaries
- call external specialized agents (e.g., a security audit agent)

Here is how the five layers might work together.

## 8.1 MCP provides the capability bus

You may have servers such as:

- `filesystem-mcp`
- `git-mcp`
- `jira-mcp`
- `ci-mcp`
- `docs-mcp`

They standardize how external systems are exposed. With MCP 2.0, these servers can:
- deploy in production over Streamable HTTP
- use unified OAuth authentication
- annotate tools for fine-grained permission control

## 8.2 Function calling performs concrete invocations

During reasoning, the agent decides to:

- call `search_code`
- call `get_ticket`
- call `run_tests`

Each of those actions is, at its core, a function call.

## 8.3 Skills define the way of working

For example, a code-fix skill might say:

- read related files first
- avoid broad refactors by default
- prefer the smallest effective fix
- verify changes after editing
- if verification cannot run, say so explicitly

Loaded with context override, this skill transforms the agent from "can modify code" into "knows how to fix bugs properly."

## 8.4 A2A handles external agent delegation

The main agent discovers that this fix involves security implications requiring an independent security audit — something beyond its own expertise. The company has a separate "Security Audit Agent" maintained by the security team on a different server.

Through A2A, the main agent:

1. Discovers the Security Audit Agent's Agent Card (via URL or registry)
2. Understands its capability: `security_audit` skill
3. Sends a task: "Audit the security of the following code change"
4. The Security Audit Agent executes in its own environment, using MCP to access its own security scanning tools
5. Returns audit results asynchronously or via streaming

Throughout this process, the main agent never sees the security agent's internal tools, prompts, or logic — it only needs to know "it can do security audits" and "here is the result."

## 8.5 Subagents handle internal decomposition

For work within its own MCP tools and skill scope, the main agent uses subagents:

- subagent A to analyze authentication flows
- subagent B to inspect failing tests
- subagent C to gather ticket context

## 8.6 The end-to-end flow looks something like this

```text
User: Fix duplicate payment settlement, run a security audit, and write a repair summary

Main agent:
1. Uses a skill to decide to read code first
2. Uses MCP-connected tooling to search the repository
3. Invokes concrete tools via function calling
4. Delegates analysis to subagents for parallel work
5. Delegates the security audit to an external agent via A2A
6. Integrates all results into an implementation plan
7. Edits code, verifies behavior, and writes the summary
```

Once you see the system this way, the roles are distinct:

- without MCP, integration becomes fragmented
- without function calling, execution requests are brittle
- without A2A, you cannot securely delegate to external specialized agents
- without skills, behavior drifts
- without subagents, complex tasks become slow and cognitively overloaded

# 9. The most common confusions

## 9.1 "Is MCP a replacement for function calling?"

No.

They solve different problems:

- `function calling` is about expressing the invocation
- `MCP` is about exposing the capability surface

In many real systems, MCP-exposed tools are still ultimately selected and invoked through function-calling-style mechanisms.

## 9.2 "Is A2A a competitor to MCP?"

This is one of the most common misunderstandings. They actually solve problems in different directions:

- `MCP`: Agent → Tools / Resources (vertical)
- `A2A`: Agent ↔ Agent (horizontal)

They are not either-or. A single agent can simultaneously be an MCP Client (connecting to various tools) and an A2A Server (exposing its skills for other agents to call).

## 9.3 "Is a skill just another word for a prompt?"

Not really. This is the easiest trap to fall into.

A prompt is "a piece of instructional text." A skill is "a complete task execution system." The difference:

- a prompt is one-off, temporary
- a skill is structured, reusable
- a prompt mainly affects a single response
- a skill, through **context override**, systematically changes the model's execution mode

Short version: a prompt is a "reminder." A skill is "training."

You can stuff a prompt into the conversation saying "think like a senior architect," or you can load a skill containing objectives, steps, constraints, and pitfall warnings. The latter almost always works better — because it does not "stick a note" onto the model's existing thought framework; it **swaps the framework entirely** within the context.

## 9.4 "Is a subagent an implementation of A2A?"

No.

- Subagents are an intra-system mechanism, typically managed directly by the host framework, with no protocol involved
- A2A is a cross-system open standard for connecting independently deployed agents

Think of it this way: subagents are created within the **same process** (sharing tool registries, memory space), while A2A connects agents in **different processes, different servers, different organizations.**

## 9.5 "If I give the agent many tools, will it automatically become better?"

Not necessarily. Often the opposite happens.

More tools can easily lead to:

- tool selection confusion
- misuse
- context clutter
- security risk

This is why mature systems usually combine:

- MCP for structured integration
- skills for execution discipline
- A2A for secure delegation to external expertise
- subagents for complexity management

# 10. Concrete examples

## 10.1 Example 1: a customer support assistant checking an order

The user says:

> Check why order `A1024` has not shipped yet.

The flow might be:

1. The model issues a `getOrder(orderId)` function call
2. The tool comes from an internal order MCP server
3. The result shows an inventory lock problem
4. The model calls `getInventoryStatus(sku)`
5. The system returns the data
6. The model produces a support-friendly explanation

Here:

- function calling handles the invocation
- MCP handles how order and inventory capabilities are exposed

If the system also has a customer-communication skill, that skill may further constrain the answer:

- lead with the conclusion
- then explain the cause
- avoid leaking internal field names

## 10.2 Example 2: modify code and fix tests

The user says:

> Add caching to this endpoint and fix the broken tests.

The system may work like this:

1. The main agent uses a code-modification skill and reads relevant files first
2. It searches the repository for dependency relationships
3. It spawns a subagent to analyze the failing tests
4. It spawns another subagent to inspect existing cache patterns
5. The main agent integrates the findings and edits the code
6. It runs verification tools

All four intrasystem layers appear here. If a security audit is also needed, the main agent would additionally delegate to an independent Security Audit Agent via A2A.

## 10.3 Example 3: a research agent

The user says:

> Compare three vector databases and recommend one for our use case.

If the system supports web research and A2A:

1. The main agent spawns three subagents, one per candidate
2. Each subagent uses search, browser, and extraction tools
3. Those tools may be exposed via MCP
4. If the main agent needs specialized benchmark data, it can delegate via A2A to a "Benchmark Agent"
5. The main agent aggregates the results and formats the final answer using a technology-evaluation skill

Here all five layers demonstrate their value: subagents for parallel decomposition, A2A for external expert delegation, skills for output quality, MCP for tool support, and function calls for concrete operations.

# 11. How to design these layers in practice

If you are building your own agent system, this layering is a good starting point.

## 11.1 Treat function calling as the execution entry point

In practice, that means:

- the model requests execution
- the host performs execution
- arguments are validated
- permissions are centralized
- timeout, idempotency, and auditability are system concerns

Do not let the model directly own business-side execution.

## 11.2 Treat MCP as the capability bus

Any external capability likely to be reused by multiple hosts is a good MCP candidate:

- filesystem
- Git
- docs and knowledge bases
- browser automation
- enterprise APIs

Prefer MCP 2.0 servers with Streamable HTTP support. The reasons are simple:
- your MCP servers will eventually need to support remote access (not everyone runs locally)
- Tool annotations enable fine-grained permission control
- OAuth standardization reduces duplicated security investment

That keeps the capability layer more stable even when models or hosts change.

## 11.3 Introduce A2A when you need cross-agent collaboration

If your system needs to:

- call agents maintained by other teams (security auditing, compliance checks, data analysis)
- have multiple independent agents collaborate on complex tasks
- protect each agent's internal implementation details and sensitive permissions

Then introducing A2A is a natural choice. Key design decisions:

- **What goes through A2A vs. MCP**: if your agent just needs to "call a function in another system" — use MCP. If your agent needs to "delegate a thinking-and-deciding task to another agent" — use A2A.
- **Agent Card granularity**: do not list tool functions like MCP does. A2A Agent Cards should describe "skills" (capabilities), not "tools" (functions). Describe "can do security audits," not "has sqlmap, nmap, OWASP ZAP."

## 11.4 Treat skills as team behavioral assets, not just prompt templates

Do not reduce skills to "prompt templates."

A stronger approach is to make each skill explicit about:

- name
- scope
- working steps
- examples
- constraints
- referenced files or assets

Understanding skills as "context override" gives you a better design compass: you are not writing a better prompt — you are building a professional working environment. Ask yourself:

- Which default behaviors should this skill override?
- Is the execution sequence clear enough?
- Are edge cases handled?
- Does the skill leave enough room for agent autonomy when unusual situations arise?

Good skill design balances "constraint (how to do it)" with "freedom (room to reason)" — too loose and it degrades to a plain prompt; too tight and it becomes a rigid script.

## 11.5 Use subagents only where they truly help

Not every task needs multiple agents.

Subagents are most useful when:

- exploration can happen in parallel
- information sources are independent
- write scopes are disjoint
- verification can be offloaded cleanly

They are less useful when:

- the task is tiny
- the next step depends immediately on one unresolved result
- the subproblem is poorly scoped
- coordination cost exceeds the gain

# 12. A simple framework for evaluating new agent products

When you encounter a new framework, SDK, or product claim, ask five questions:

## 1. Is it solving invocation or integration?

- invocation tends to point toward function calling
- integration tends to point toward MCP

## 2. Is it solving "can the agent do it" or "does the agent know how to do it well?"

- "can it do it" tends to be tools, function calling, and MCP
- "does it do it well" tends to be skills

## 3. Is it about point capabilities or agent collaboration?

- point capabilities tend to be tools and function calls
- agent collaboration tends to be A2A (cross-system) or subagents (within one system)

## 4. Is it increasing freedom or increasing stability?

- function calling and MCP usually expand capability access
- skills usually improve execution consistency — through context override, they channel "freedom" into a professional behavioral trajectory
- A2A and subagents usually improve the system's ability to handle scale

## 5. Does it operate within a system or across systems?

- within a system: function calling, MCP, skills, subagents
- across systems: A2A

This lens makes it much easier to avoid getting lost in terminology.

# 13. Final takeaway

Compressed to the shortest useful version:

- `function calling` lets a model request external actions in a structured way
- `MCP` lets external capabilities plug into model systems through a standard interface (from v1.0 tool sharing to v2.0 production-grade governance)
- `A2A` lets different agents discover each other, communicate, and collaborate through a standard protocol — without exposing internal implementations
- `skills` give agents reusable ways of working — through **context override**, they establish a professional working framework inside the model's cognitive space
- `subagents` let complex tasks be split, parallelized, and coordinated within a single system

These are not competing concepts. They are complementary layers.

A mature agent system often uses all five:

1. `MCP` to integrate the tool ecosystem
2. `function calling` to request concrete actions
3. `skills` to stabilize task execution
4. `subagents` to manage complexity within one system
5. `A2A` to connect with external specialized agents

If you collapse all of that into the vague idea that "the AI can use tools," you lose the architectural distinctions that actually matter.

The more useful way to think about them is:

- some solve execution interfaces
- some solve capability integration
- some solve reusable expertise
- some solve agent interoperability
- some solve collaboration and orchestration

And each layer keeps evolving: function calling is becoming more fine-grained (structured output, parallel calls), MCP is moving from "can integrate" to "can integrate with governance," A2A is moving from a Google proposal to a Linux Foundation open standard, skills are evolving from "complex prompts" to context engineering, and subagents are maturing from "helper functions" to autonomous collaboration units.

When these five layers come together, LLMs evolve from "good at chatting" into "a network of agents that can reliably do meaningful work."
