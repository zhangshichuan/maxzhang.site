> 写给不想被运维"卡脖子"的前端工程师

你可能觉得 Docker 和 Kubernetes 是运维的事，跟前端关系不大。但现实是：

- SSR 渲染需要稳定的 Node.js 环境
- 海报生成服务依赖底层的 `canvas` 或 `libvips`
- 微前端本地联调需要同时跑五六个项目

这时候如果你只会"本地 npm run dev"，就会陷入被动——代码在本地跑得好好的，一上生产就出问题。

别慌，这篇文章就是帮你补上这块短板。

---

## 1. 先说个故事：为什么本地和线上老是不一样？

做前端的你，一定遇到过这些糟心事：

**场景一：Node.js 版本诅咒**

本地开发用的是 Node.js 18，项目里有个 C++ 写的原生模块（比如 `canvas`）。结果服务器上是 Node.js 16，ABI 不兼容，部署上去直接崩溃。

**场景二：消失的系统依赖**

在 Mac 上 `npm install` 跑得溜得很。上了 Linux 服务器才发现：缺字体、缺 `libvips` 库，构建直接卡住。

**场景三："在我电脑上是好的"**

后端同事说接口没问题，你本地就是调不通。或者上线后才发现 Nginx 重写规则没配对，导致诡异的 404。

这些问题本质上都一样：**开发和生产的环境不一致**。

容器化要解决的就是这个问题——让你本地跑的环境，和线上跑的环境，一模一样。

## 2. 核心概念：镜像、容器、Pod 到底是啥？

### 2.1 镜像（Image）

镜像就像一个**已经装好所有软件的电脑模板**。你把这个模板复制到任何地方，它都长一个样。

比如你打包了一个 Next.js 应用镜像 `my-app:v1`，里面包含了：

- Ubuntu 系统
- Node.js 18
- 项目代码
- 依赖包
- 字体文件
- 配置文件

无论在谁电脑上、用什么操作系统，基于这个镜像跑起来的实例，行为都是一样的。

### 2.2 容器（Container）

容器就是**根据镜像跑起来的实例**。

类比一下：

- **镜像** = 菜谱（配方）
- **容器** = 按照菜谱做出来的菜

你可以用同一个镜像（比如 `node:18`），同时启动 10 个容器来扛并发。这 10 个容器互不影响。

### 2.3 Pod（K8s 专用）

Pod 是 Kubernetes 里的**最小调度单位**。

大多数情况下，一个 Pod 里面装一个容器。但有时候你会遇到"边车模式"（Sidecar）——一个 Pod 里有两个容器：

- 主容器：跑你的业务代码
- 副容器：收集日志、监控数据等

它们共享同一个 IP 地址和存储卷。

## 3. 技术演进：从 Docker 到 K8s

### 3.1 第一阶段：Dockerfile——单个服务的说明书

**Dockerfile** 是什么？

它是用来构建镜像的"配方文件"。就像你写菜谱告诉别人怎么做这道菜一样，Dockerfile 告诉 Docker 怎么构建你的应用环境。

**一个简单的例子：**

```dockerfile
# 基础镜像：Node.js 18
FROM node:18-alpine

# 设置工作目录
WORKDIR /app

# 复制依赖文件
COPY package*.json ./

# 安装依赖
RUN npm install

# 复制源代码
COPY . .

# 暴露端口
EXPOSE 3000

# 启动命令
CMD ["npm", "run", "start"]
```

**关键点：**

- `FROM node:18-alpine`：基于官方 Node.js 镜像，不用自己装 Node
- `RUN npm install`：把依赖装好
- `COPY . .`：把代码复制进去
- `CMD`：容器启动时执行什么命令

**Dockerfile 的定位：** 单个服务的打包文件。你有 10 个服务，就应该有 10 个 Dockerfile。

### 3.2 第二阶段：Docker Compose——本地联调的"指挥官"

当你有多个服务要同时跑的时候，比如：

- 前端（Next.js）
- BFF 层（接口聚合服务）
- 渲染服务（生成海报）
- Redis（缓存）
- 数据库

手动一个一个 `docker run` 启动，再配置网络互通，能把人逼疯。

`docker-compose.yml` 就是来解决这个问题的：

```yaml
version: '3.8'
services:
  frontend:
    build: ./apps/frontend
    ports:
      - '3000:3000'
    depends_on:
      - bff

  bff:
    build: ./apps/bff
    ports:
      - '8080:8080'
    environment:
      - REDIS_HOST=redis
    depends_on:
      - redis
      - render

  render:
    build: ./apps/render-service
    ports:
      - '9090:9090'

  redis:
    image: redis:7-alpine
    ports:
      - '6379:6379'
```

一行命令启动全部服务：

```bash
docker-compose up
```

**Docker Compose 的定位：** 本地开发和简单单机部署。**不适合生产环境。**

### 3.3 第三阶段：K8s——生产环境的"舰队司令"

Docker Compose 只能在单机上玩。生产环境是这样的：

- 服务器可能突然断电
- 流量可能遇到双十一级别的暴涨
- 需要在多台服务器之间调度资源

这时候 Docker Compose 就不够用了，需要 **Kubernetes（K8s）**。

**K8s 能干啥？**

- **自动调度**：把容器调度到合适的服务器上
- **故障自愈**：容器挂了？自动重启
- **动态扩缩容**：流量大了？自动多加几个容器
- **滚动更新**：更新版本时，先起新的，再停旧的，用户无感知

**但是 K8s 太重了？用 K3s 和 k3d**

标准 K8s 需要一堆配置，很麻烦。K3s 是轻量版，k3d 让你在 Docker 里跑 K3s——本地就能模拟完整的 K8s 集群。

```bash
# 一行命令创建 K3s 集群
k3d cluster create my-cluster

# 删除集群
k3d cluster delete my-cluster
```

## 4. 实战：用 K3d 搭建本地开发环境

### 4.1 创建集群

```bash
# 创建一个 2 节点的集群（本地 80 端口映射）
k3d cluster create my-dev -p "80:80@loadbalancer" --agents 2
```

### 4.2 部署应用

```bash
# 把本地镜像导入集群（重要！否则 K8s 会去公网拉取）
k3d image import my-app:latest -c my-dev

# 部署 K8s 配置
kubectl apply -f deploy/k8s-manifests/
```

### 4.3 本地开发的热更新

开发阶段总不能改一行代码就重新打包镜像吧？

解决方案：**用 Volume 挂载源代码**

```yaml
# 在 K8s Deployment 里添加
spec:
  containers:
    - name: web
      image: my-dev-image:latest
      volumeMounts:
        - name: source-code
          mountPath: /app
  volumes:
    - name: source-code
      hostPath:
        path: /Users/you/project/src # 本机代码路径
        type: Directory
```

这样容器内的 `/app` 目录就映射到了你本机的代码目录，改代码立刻生效。

## 5. 调试命令：kubectl 速查表

### 5.1 查看状态

```bash
# 看 Pod 列表
kubectl get pods

# 看所有资源
kubectl get all

# 看某个 Pod 详情
kubectl describe pod <pod-name>

# 看 Deployment 详情
kubectl describe deployment <deployment-name>
```

### 5.2 看日志

```bash
# 看日志
kubectl logs <pod-name>

# 实时跟踪日志（类似 tail -f）
kubectl logs -f <pod-name>

# 看上一个实例的日志（容器重启前）
kubectl logs --previous <pod-name>

# 看指定容器的日志（Pod 里有多个容器时）
kubectl logs <pod-name> -c <container-name>
```

### 5.3 进入容器

```bash
# 进去看看
kubectl exec -it <pod-name> -- /bin/sh

# 执行特定命令
kubectl exec <pod-name> -- ls -la /app

# 进指定容器
kubectl exec -it <pod-name> -c <container-name> -- /bin/sh
```

### 5.4 网络调试

```bash
# 端口转发到本地（调试内部服务）
kubectl port-forward <pod-name> 8080:80

# 查看 Service
kubectl get svc

# 查看 Ingress
kubectl get ingress
```

### 5.5 故障排查

```bash
# 查看事件（按时间排序）
kubectl get events --sort-by='.lastTimestamp'

# 查看节点
kubectl get nodes

# 看资源使用
kubectl top pods
kubectl top nodes
```

### 5.6 常用别名（提效）

```bash
# 放到 ~/.bashrc 或 ~/.zshrc 里
alias k='kubectl'
alias kg='kubectl get'
alias kd='kubectl describe'
alias kl='kubectl logs'
```

## 6. 项目结构：Monorepo + GitOps

一个成熟的大前端项目，目录结构大概是这样：

```
my-project/
├── .github/workflows/     # CI/CD：代码提交后自动构建、自动部署
├── apps/                 # 业务代码
│   ├── frontend/         # 前端（有自己的 Dockerfile）
│   ├── bff/              # BFF 层（有自己的 Dockerfile）
│   └── render/           # 渲染服务（有自己的 Dockerfile）
├── packages/             # 共享代码（TS 类型、工具函数等）
└── deploy/               # 基础设施配置
    ├── docker-compose.yml  # 本地开发用
    └── k8s/               # K8s 部署配置
        ├── deployment.yaml
        ├── service.yaml
        └── ingress.yaml
```

**工作流程变成这样：**

1. 你把代码 `git push` 到代码库
2. CI 自动跑测试、构建镜像、推送到镜像仓库
3. CI 自动触发部署，K8s 集群按照新配置平滑更新

**你不需要手动登录服务器敲命令，一切都是自动的。**

## 7. 常见问题

**Q：Docker 和虚拟机有什么区别？**

虚拟机是完整的一台电脑（包括操作系统），占用资源大、启动慢。容器共享宿主机的操作系统，更轻量、启动更快。

打个比方：

- **虚拟机** = 独立别墅（每栋都有自己的地基、水电系统）
- **容器** = 公寓大楼（共享大楼的水电，但每户是独立空间）

**Q：Docker Compose 和 K8s 怎么选？**

- 本地开发 + 单机部署 → Docker Compose
- 生产环境 + 多服务器集群 → K8s

**Q：学习 K8s 门槛高吗？**

刚开始会有些概念要学（Pod、Service、Deployment、Ingress 等），但只要理解了核心概念，上手并不难。K3d 让你在本地就能练手，不需要真实服务器。

**Q：前端学容器化有什么用？**

- SSR 项目本地调试
- 海报生成等依赖底层库的服务
- 本地模拟微前端联调环境
- 和后端/运维同事沟通更顺畅
- 面试加分项

---

## 总结

容器化本质上解决的是一个老问题：**本地和线上环境不一致**。

通过 Docker + K8s，你可以：

- 本地环境 1:1 还原生产
- 多个服务一键启动
- 自动扩缩容、故障自愈
- 不用再担心"在我的电脑上是好的"

学容器化不是为了转行做运维，而是为了让自己的工作更顺心。当你的 SSR 项目、海报服务、微前端能够在自己电脑上轻松跑起来的时候，你会感谢今天学的这些知识。
