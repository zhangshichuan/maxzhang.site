## 前言

搭过搜索引擎或 RAG 的人，都绕不开一句话：**向量召回 + BM25 兜底**。

第一次听到这个组合，可能会觉得它特别唬人——又是向量，又是算法，又是兜底。但把每个词拆开，它说的其实是三件各自独立的事。

下面我们就把这些东西一个个讲清楚。不讲公式推导，不讲论文里的 F1 分数——只讲工程上到底怎么用，为什么这么用，以及不用的话会怎样。

---

## 1. 一个搜索请求到底经历了什么

在你敲下回车之后，一次搜索大概走这四步：

```
用户输入 Query
    │
    ▼
┌─────────────────────────────┐
│  1. Query 向量化             │
│  把问题转成 768 维向量        │
└─────────────┬───────────────┘
              │
              ▼
┌─────────────────────────────┐
│  2. 向量召回（主力）          │
│  在向量库中找 Top-K 候选      │
│  用 HNSW 索引，毫秒级完成      │
└─────────────┬───────────────┘
              │
              ▼
      最高分 < 阈值？
      ├── 是 ──▶ BM25 兜底召回
      │         （倒排索引 + 关键词匹配）
      │
      └── 否 ──▶ 直接用向量结果
              │
              ▼
┌─────────────────────────────┐
│  3. 合并 + 去重              │
│  两路结果合并，同文档去重      │
└─────────────┬───────────────┘
              │
              ▼
┌─────────────────────────────┐
│  4. 重排（Rerank）           │
│  更精细的模型重新打分          │
│  候选从几百条精选到 Top 10     │
└─────────────┬───────────────┘
              │
              ▼
          返回结果
```

这里面有三个设计决策值得展开：

**召回和重排分开做**。召回管快，重排管准。让召回去追精度，延迟就炸了；让重排处理百万级文档，用户等不起。

**两套召回机制互补**。向量召回覆盖语义相近的场景，BM25 覆盖关键词精确匹配的场景。两条路一起走，基本不会出现「搜不到」的情况。

**阈值靠调，不靠算**。它不是从哪个公式推出来的——是在离线数据上看分布，上线以后看表现，来回磨出来的一个数。后面会细说。

## 2. 向量召回：把文字变成距离

### 2.1 它到底在干嘛

向量召回就是把一段文字映射成一组浮点数，然后用两个向量之间的距离来表示两段文字的「语义远近」。

举个例子：

> 「如何快速变瘦」和「减肥最高效方法」

这两句话从字面上看几乎没有共同词。传统的关键词搜索引擎看到它们，直接判定为无关——毕竟一个相同的词都没有。

但向量模型不这么看。它把这两句话分别编码以后，发现它们在 768 维空间里挨得很近。向量模型「感觉」到它们说的是同一件事。

这就是向量召回最有用的一点：**字面不一样但意思差不多的内容，它能抓到**。

### 2.2 怎么做到的

分两步走。

第一步，**Embedding**。用一个预训练的深度模型（BERT 的变体就行），把每篇文档和每个查询分别压成一个固定长度的向量。常见 768 维或 1024 维。

这组数字有个属性：语义相近的文本，向量在高维空间里距离就小；语义不相关的，距离就大。

第二步，**近似最近邻搜索（ANN）**。有了向量库之后，搜索就是「找离查询向量最近的 K 个文档向量」。问题是——如果文档有几百万条，一条条算距离不现实。

ANN 就是解决这个的。目前用得最多的算法是 **HNSW（Hierarchical Navigable Small World）**。可以把它想成一张路网：有高速公路让你快速跨越大片区域，有省道让你进入某个小区块，还有乡间小路让你精确定位。层数越高路越粗，层数越细找得越准。

这套方案的单次延迟一般在几毫秒到十几毫秒之间，在线服务完全够用。

### 2.3 向量召回的问题

向量召回最大的软肋，恰好就是因为它的语义感太强了。

搜「RTX 4090 显卡」，向量模型可能连「NVIDIA 旗舰 GPU」「高端游戏显卡」也一并给你。因为语义上这些确实相关——但用户想要的只是包含「RTX 4090」这几个字的文档。这种时候，语义泛化反而帮了倒忙。

这种场景下，BM25 就该上场了。

---

## 3. BM25：只认关键词，不讲语义

### 3.1 它是什么

BM25 是一个基于关键词匹配的打分算法，逻辑粗暴直接：**查询里的词在文档中出现得越多、这些词在整个文档集里越稀有，分数就越高**。

比如「RTX4090」这种稀有词，一旦命中，权重极高。「的」「是」「了」这种随处都是的词，命中再多也没分。这就是 TF-IDF 的思路，BM25 在它的基础上加了两样东西：对文档长度的惩罚（长文档不会天然占优），和对词频增长的饱和处理（一个词出现 100 次和 50 次的差距不大）。

### 3.2 它好在哪

看这个场景：

你在技术文档库里搜 **`OOM Killer`**。

向量模型大概率给你返回这些：

- 「内存不足错误」
- 「进程被系统杀死」
- 「资源耗尽处理」

语义上这些跟 OOM 确实沾边。但如果你要找的是 Linux 内核里那个叫 `OOM Killer` 的具体机制，上面这些结果全是噪声。

BM25 不会犯这个错。它严格匹配「OOM」和「Killer」这两个 token，优先返回同时包含这两个词的文档。如果文档里正好出现了完整词组「OOM Killer」，分数更高。

一句话总结：**精确匹配低频词和专有名词时，BM25 比向量召回清醒得多**。

### 3.3 BM25 和 Elasticsearch 的关系

一个特别容易搞混的地方：BM25 是算法，不是产品。

BM25 是 Stephen Robertson 在 1994 年提出的一个具体排名公式，属于概率检索模型家族。它就是个数学函数。

Elasticsearch 是一个基于 Lucene 的分布式搜索引擎产品。从 5.0 版本开始，ES 把 BM25 设为默认的相关性评分算法——但它底层跑的东西远不止这一个公式，还有分词、倒排索引、分布式检索等等。

所以日常说「我们用的 BM25」，99% 指的是「我们用的 Elasticsearch / Solr / Lucene 里内置的 BM25 评分」。把 BM25 单独拎出来用也行，Python 里装个 `rank-bm25` 就行，没几行代码。

同样常见的误会：「倒排索引是 BM25 的一部分」——不是。倒排索引是加速关键词查找的数据结构，BM25 是在这个数据结构上面跑的评分算法。它们是锤子和钉钉子的动作之间的关系，不是锤子和工具箱之间的关系。

## 4. 兜底：不是备胎，是安全带

### 4.1 兜底机制到底在兜什么

向量召回在两类情况下容易掉链子：

1. **Query 太短或太模糊**。用户就打了「bug」三个字母，向量模型猜不出他要的是哪种 bug：代码缺陷？昆虫？窃听器？这种时候相似度分数普遍不高。

2. **Query 里有具体到变态的专有名词**。「nginx 1.27.3 stream module proxy_bind 配置」——向量模型几乎没见过这种训练样本，召回质量多半拉胯。

兜底逻辑就一行伪代码的事：

```python
def search(query):
    vector_results = vector_search(query)
    if vector_results.top_score < THRESHOLD or len(vector_results) == 0:
        return bm25_search(query)
    return vector_results
```

向量的最高分低于阈值 → 切到 BM25 关键词检索。就这么简单。

### 4.2 阈值怎么定

问这个问题的人很多，因为直觉上会以为有什么「计算公式」。但真实答案是：**这个数就是反复试出来的**。

流程是这样的：

1. **准备标注数据**。找一批真实用户 Query，人工标注每个 Query 对应的相关文档。这步最累，但少了它后面都白搭。

2. **跑分布**。用向量模型对所有 Query 做召回，记录每个 Query 下相关文档的相似度分数，画成直方图。

   你大概会看到类似这样的分布（数字是我编的，示意用）：

   ```
   相似度范围      相关文档占比
   ─────────────────────────────
   0.8 - 1.0       ████████████████  40%
   0.7 - 0.8       ██████████████    35%
   0.6 - 0.7       ████████          15%
   0.5 - 0.6       ████              7%
   0.4 - 0.5       ██                3%
   ```

3. **选分位数**。如果上面这张图里 90% 的相关文档分数都超过 0.55，阈值搁在 0.5～0.55 这个区间就比较合理。实际经验中，余弦相似度阈值常落在 0.4～0.6。

4. **上线，接着调**。离线数据模拟不了真实用户。上线之后盯着兜底触发率、用户点击率、无结果率这些指标，来回微调。

还有个经验：**不同业务阈值不同**。电商搜商品，阈值可以低一点——搜不出来比搜不准更让用户跑。医疗搜文献，阈值得高一些——搜不准比搜不出来更危险。

### 4.3 兜底不是降级

很多人以为兜底是「向量召回挂了才启用」的后备方案。但实际上，很多系统里 BM25 和向量召回是**并行跑**的——两条路同时召回，合并去重后一起喂给重排。精确匹配和语义匹配的信息都进了最终决策环，不存在谁优先谁替补。

## 5. 重排：最后一道精密筛选

### 5.1 为什么不在前一步就追求精度

规模摆在那里。

一千万篇文档，用 Cross-Encoder 这种高精度模型逐篇算一遍——单次搜索可能要几分钟。所以不得不在架构上拆成两段：

|          | 召回                    | 重排                         |
| -------- | ----------------------- | ---------------------------- |
| 候选量   | 百万～亿级              | 几十～几百                   |
| 延迟要求 | 毫秒级                  | 百毫秒级                     |
| 模型     | 简单（双塔点积 / BM25） | 复杂（Cross-Encoder / GBDT） |
| 目标     | 别漏                    | 往准了搞                     |

海选不能标准太高，否则该过的被筛掉了；终面标准得严，因为人已经不多了，资源也撑得住。

### 5.2 重排模型有哪些

**Cross-Encoder**。效果最好，也最慢。做法是把 Query 和 Document 拼成一对，一起喂进 BERT，让两个文本在模型每一层都充分交叉。输出是一个分数。

它能把句子里那些微妙的否定词、条件词、语序全吃进去。代价是每条候选都要完整跑一遍模型，没法像双塔那样提前算好文档向量存着。所以只能用在几百条的候选集上。

**ColBERT 等延迟交互模型**。折中方案。文档和 Query 各自先独立编码（省计算），最后做一次轻量交互（补精度）。在很多 benchmark 上接近 Cross-Encoder 的效果，但快不少。

**GBDT / LambdaMART**。不走深度学习路线。输入不止向量相似度，还可以把 BM25 分数、文档发布时间、历史点击率、作者权威度这些拼在一起。可解释，好调参，适合需要人类理解和干预排序策略的业务。

实际做项目的话，**重排模型基本不需要从零训**。去 HuggingFace 下个 `cross-encoder/ms-marco-MiniLM-L-6-v2`，拿自己的标注数据微调一轮，大部分场景就够了。

## 6. 文档切分：地基打歪了，上面再高也没用

### 6.1 切分的质量决定天花板

太多人把力气花在 Embedding 模型和重排模型上，却不管最前面的切分。但一个 Bad Case 就能说明问题：

> 原文：`本系统使用 PostgreSQL 作为主数据库，因为其出色的并发控制能力。`

硬按固定长度切：

- 片段 A：「本系统使用 PostgreSQL 作为主数据库，因为」
- 片段 B：「其出色的并发控制能力。」

片段 A 的语义是「选了 PostgreSQL」但话没说完；片段 B 只有评价，缺了主语。两个片段的向量都是半吊子，下游模型再强也救不回来。

如果按完整句子切，这一个自然句就是一个片段，语义完整，向量准确。

### 6.2 几条实操经验

**按语义边界切，不要按固定字数硬砍**。至少得按句号、段落的自然边界来。用 `text-splitter` 这类库里的语义分割器效果更好。固定长度（比如 512 token）可以当上限兜底，但不能是唯一策略。

**片段之间加 overlap**。相邻片段留 10%～20% 的重叠，防止正好切在关键信息中间。

**保留上下文信息**。一条片段来自哪篇文档、文档标题是什么、属于哪个章节——这些信息重排的时候有大用。两条片段分数差不多时，来自更权威文档的那条应该排前面。

## 7. Embedding：挑模型就是挑性价比

### 7.1 通用模型还是领域模型

文档内容是 news、百科、通用问答这类，直接用 `text-embedding-3-large`、`bge-large-zh` 之类的通用模型就行，省心。

但如果是医学论文、法律文书、内部代码文档这类强领域数据——通用模型的语义空间未必对得准。要么在领域数据上微调一把，要么直接用领域特化的模型。

### 7.2 大就是好？

1024 维和 768 维的模型，精度的差距可能就 1%～2%，但存储和算力的开销能涨 30% 以上。文档量到百万级时，这 30% 是实打实的钱。挑维度的时候打开成本表，别只看论文里的指标。

### 7.3 后续维护

向量不是生成一次就完事了。文档更新，向量要重算；索引增量写入，也要考虑一致性。这是 Embedding 环节最容易被忽视的工程坑。

---

## 8. 倒排索引：凭什么能这么快

BM25 能做到毫秒级检索，骨子里靠的就是倒排索引。

### 8.1 正向索引的笨办法

你有一千本书，要找所有提到「量子力学」的书。

正向索引的思路：从第一本第一页，一行行扫过去，扫完一千本，告诉你答案。这显然没法用。

### 8.2 倒排索引反着来

倒排索引不记「每本书有哪些词」，它记的是「每个词出现在哪些书里」。

结构上两块：

**词项字典**：所有出现过的唯一词，按顺序排好。查一个词，二分查找，O(log N)。

**倒排记录表**：每个词下面挂一个列表，记着这个词在哪些文档的第几个位置出现过、出现了几次。

像这样：

```
"猫" → [(doc_id=5, tf=2, positions=[10, 205]),
        (doc_id=23, tf=1, positions=[67]),
        (doc_id=108, tf=3, positions=[...])]

"狗" → [(doc_id=3, tf=1, positions=[89]),
        (doc_id=5, tf=1, positions=[150])]
```

### 8.3 快的秘密

查「猫 狗」，过程是：

1. 字典里找「猫」→ 直接拿到所有含「猫」的文档 ID 列表
2. 同理找「狗」→ 拿到另一份列表
3. AND 逻辑 → 求两份列表的**交集**；OR 逻辑 → 求**并集**
4. 对结果用 BM25 打分排序

从头到尾没有「遍历文档」这步。就好像去图书馆，你不是书架上一本本翻开看，而是直接翻到书末的索引，找到关键词，跳去对应页码。

### 8.4 还能更快

倒排记录表里的文档 ID 列表，Lucene 还会在内部加**跳表**和**压缩编码**。跳表让两个大列表求交集更快（好比归并排序的加速版），压缩编码省内存。Lucene / Elasticsearch 在这块做到了工业极限，即使百亿级文档，单次关键词检索也就十几毫秒。

## 9. 离线干重活，在线只跑轻活

搜索引擎有两条独立的时间线：

**离线（用户看不到，但一直在后台跑）**：

1. 文档入库 → 切片段
2. 每个片段过 Embedding 模型 → 生成向量
3. 向量写入向量数据库，构建 HNSW 或 IVF 索引
4. 同步建倒排索引，给 BM25 用
5. 文档更新 → 增量同步以上所有索引

这些活计算量大，通常在 GPU 集群上批量跑。但不接触用户请求，延迟无所谓，重点是把吞吐量拉满，把一致性做好。

**在线（用户实时感知）**：

1. 收到 Query → 向量化
2. 向量召回（主力） + 可选 BM25 兜底
3. 合并去重
4. 重排模型精排
5. 返回 Top N

这里对延迟极度敏感。搜索响应超过 200ms，用户会觉得有点卡；超过 1s，用户开始烦躁。

两层架构说白了就一条原则：**能放在离线预计算的全放离线，在线链路瘦到最轻**。

---

## 10. 把各环节合并会怎样

把两个环节拼在一起，看起来好像能省一步。但实际算一下就清楚了：

**Embedding + 召回合并**。边向量化边搜索——BERT 一次前向传播就几十毫秒，几百万文档逐个跑，等出结果天都亮了。Embedding 必须放离线。

**召回 + 重排合并**。Cross-Encoder 一条 10～50ms，一百万条就是一万秒往上。搜一次等三个小时。

**切分 + Embedding 合并**。一个主要是规则操作（CPU），一个是神经网络推理（GPU），合在一起两边效率都打折。分开跑各用各的硬件，反而更快。

每层的分离不是架构师有洁癖，纯粹是因为**规模太大、延迟要求太严，不拆就跑不动**。

## 结语

整个搜索系统的架构，掰开来看就是一层漏斗：

```
全部文档（百万 / 亿级）
    │
    ▼ 召回（毫秒级，高召回）
几百条候选
    │
    ▼ 重排（百毫秒级，高精度）
Top 10
```

每一层要回应的都是同一个问题：**在这个时间预算里，怎么让结果最靠谱**。

向量召回和 BM25 不是谁替代谁的问题。一个认识语义，一个认识关键词，这俩是互补关系。那个兜底阈值也不是某个公式的产物——是你对着数据分布图，结合业务容忍度，一刀切下去定出来的。

打个比方，像是翻一张巨型卡片目录：

- **文档切分**——把一整本书拆成能独立检索的小卡片
- **Embedding**——给每张卡片打上一组只有机器能读懂的「理解分」
- **向量召回**——「把感觉最像我说的那几张卡片找出来」（语义匹配）
- **BM25**——「把字面上有我提到的那几个词的卡片找出来」（精确匹配）
- **重排**——两叠卡片合在一起，逐张精读，挑最好的 10 张

搜索引擎好不好，不看哪个 benchmark 上分最高。就看一件事：**在你的数据、你的用户、你的延迟预算这三个框里，它稳不稳**。

最后提一句 RAG。RAG 本质上就是把「召回 + 重排」吐出的文档列表，直接丢给大模型做总结、做生成。搜索搞懂了，RAG 就懂了一大半。剩下的那部分，是大模型自己的事。
