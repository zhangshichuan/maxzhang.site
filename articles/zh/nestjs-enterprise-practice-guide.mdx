## 一、为什么 TypeScript 全栈是未来

在聊 NestJS 之前，先回答一个根本问题：为什么要押注 TypeScript 全栈？

### 1.1 数据库到客户端的端到端类型安全

传统开发流程里，类型断层是 bug 的主要来源。后端改了某个字段的返回值类型，前端没人通知，上线就炸。

```typescript
// 后端改了返回类型
// 从 { userId: number } 变成 { userId: string }
@Get('/user')
getUser() {
  return { userId: 'abc-123' } // 原来是 123，现在变成字符串了
}
```

```typescript
// 前端还在用 number 类型接
const response: { userId: number } = await fetch('/api/user').then((r) => r.json())
// 💥 编译不报错，运行时却炸了
```

TypeScript 全栈的解法是：**把类型定义抽成共享包，前后端共同引用**。谁改了类型，另一端编译就直接报错，根本不会留到运行时。

### 1.2 tRPC：前后端共享类型的最佳实践

tRPC 把这个思路做到了极致——后端的类型定义自动推导到前端，你甚至不需要手动维护类型文件：

```typescript
// 后端定义
const appRouter = router({
  userById: publicProcedure.input(z.string()).query(({ input }) => {
    return { id: input, name: '张三', email: 'zhangsan@example.com' }
  }),
})

export type AppRouter = typeof appRouter
```

```typescript
// 前端直接推导出完整类型
const user = await trpc.userById.query('abc-123')
// user 的类型自动推导为 { id: string; name: string; email: string }
// 根本不需要手动写 interface
```

### 1.3 Zod：运行时类型校验的最后一道防线

TypeScript 的类型只在编译时存在，运行时它们全被擦除了。这意味着用户提交的数据、第三方 API 的返回值，编译时再严谨也拦不住。

Zod 解决了这个问题——它同时是 Type 定义和运行时校验器：

```typescript
import { z } from 'zod'

const CreateUserSchema = z.object({
  username: z.string().min(3).max(20),
  email: z.string().email(),
  age: z.number().min(0).max(150),
})

// 从 Schema 自动推导出 TypeScript 类型
type CreateUserDto = z.infer<typeof CreateUserSchema>

// 运行时校验
const result = CreateUserSchema.safeParse(req.body)
if (!result.success) {
  // 这里的错误信息可以直接返回给客户端
  return { code: 400, errors: result.error.flatten() }
}
// result.data 的类型自动就是 CreateUserDto
```

NestJS 生态里，`class-validator` 和 `class-transformer` 扮演了类似的角色。但 Zod 的优势在于——它不需要装饰器类，可以和 tRPC、OpenAPI 等任意框架组合使用，并且推导出的类型可以直接跨项目共享。后续我们会在认证章节详细对比这两种方案。

## 二、前置概念：NestJS 的"世界观"

NestJS 绕不开几个范式。不理解这些，你永远只能"照着文档抄"，改不动也排不了坑。

### 2.1 OOP、FP、FRP 在 NestJS 中的影子

**OOP（面向对象编程）**是 NestJS 的骨架。模块、控制器、服务全都是类——你可以用继承复用通用逻辑，用封装隐藏实现细节。

```typescript
// OOP 的经典模式：抽象基类
export abstract class BaseCrudService<T> {
  constructor(protected readonly repository: Repository<T>) {}

  async findAll(): Promise<T[]> {
    return this.repository.find()
  }

  abstract validateCreate(dto: unknown): T
}
```

**FP（函数式编程）**在 NestJS 里表现为管道和拦截器的组合模式——每个函数做一件事，通过 `pipe` 组合：

```typescript
// RxJS 的 pipe 就是典型的 FP 风格
this.userService.findById(id).pipe(
  map((user) => user.email),
  filter((email) => email.endsWith('@company.com')),
)
```

**FRP（函数响应式编程）**由 RxJS 承载。NestJS 大量使用 Observable 处理异步流——不仅仅是 HTTP 响应，还包括微服务消息、数据库查询重试、定时任务等。这个概念我们在第十章会深入讲。

### 2.2 AOP：切面编程与 NestJS 的拦截机制

AOP（Aspect-Oriented Programming）的核心思想是：**把横切关注点（日志、事务、权限）从业务代码中抽离出来**。

打个比方：你去餐厅吃饭，点单、上菜是"业务逻辑"。但你付钱时有个"记账"动作——每笔消费都要记到财务系统里。这个"记账"跟吃饭这个业务无关，但每桌客人都要触发，这就是横切关注点。

在 NestJS 中，AOP 通过四种机制实现：

| 机制         | 作用阶段         | 典型用途                 |
| ------------ | ---------------- | ------------------------ |
| Middleware   | 请求进入路由之前 | CORS、日志、body 解析    |
| Guards       | 确定是否放行请求 | 认证、权限               |
| Interceptors | 方法调用前后     | 响应脱敏、性能监控、事务 |
| Pipes        | 参数绑定与转换   | 数据校验、类型转换       |
| Filters      | 异常抛出后       | 统一错误格式、异常上报   |

```typescript
// 一个 Interceptor 实现"记账"功能——完全不影响业务代码
@Injectable()
export class AuditInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const request = context.switchToHttp().getRequest()
    const user = request.user?.username ?? 'anonymous'
    const path = request.url

    const now = Date.now()
    return next.handle().pipe(
      tap(() => {
        this.auditService.log(`${user} 访问了 ${path}，耗时 ${Date.now() - now}ms`)
      }),
    )
  }
}
```

### 2.3 DI 和 IoC：为什么到处都在"注入"

你刚开始写 NestJS 时，最困惑的可能是：为什么所有依赖都是通过构造函数传进来的？

```typescript
// 你在 Express 里可能是这样写的
app.get('/users', (req, res) => {
  const db = new Database() // 手动创建依赖
  const userService = new UserService(db) // 手动组装
  res.json(userService.findAll())
})
```

```typescript
// NestJS 里变成了这样
@Controller('users')
export class UserController {
  constructor(
    private readonly userService: UserService, // 自动注入
    private readonly auditService: AuditService, // 自动注入
  ) {}

  @Get()
  findAll() {
    return this.userService.findAll()
  }
}
```

这背后是 **IoC（控制反转）**和 **DI（依赖注入）**两个概念：

- **IoC（控制反转）**：谁创建对象？不是你——是容器。你把创建对象的"控制权"反交给了 NestJS 的 IoC 容器。
- **DI（依赖注入）**：`UserController` 需要的 `UserService` 不是它自己 new 的，而是容器"注入"进去的。

这样做有三个好处：

1. **方便测试**：测试时可以注入 Mock 实例，而不是真实的数据库连接
2. **解耦**：`UserController` 只依赖 `UserService` 的接口，不依赖具体实现
3. **生命周期管理**：容器自动处理单例、请求作用域等生命周期

### 2.4 装饰器：@Injectable、@Inject 和自定义装饰器

装饰器是 TypeScript 的实验性特性，NestJS 用它来声明元数据。理解装饰器的本质很重要——它就是一个**函数**，在类/方法/属性定义时被调用。

```typescript
// 看一个最简化的 @Injectable 是怎么工作的
function Injectable(): ClassDecorator {
  return (target: any) => {
    // 把类的设计时类型信息存到 Reflect 元数据中
    Reflect.defineMetadata('design:paramtypes', [UserRepository], target)
    // NestJS 容器读取这个元数据，就知道要注入 UserRepository
  }
}
```

NestJS 中常见的装饰器：

| 装饰器                                  | 作用                          | 使用位置     |
| --------------------------------------- | ----------------------------- | ------------ |
| `@Module()`                             | 声明模块及其依赖              | 类           |
| `@Controller()`                         | 声明控制器                    | 类           |
| `@Injectable()`                         | 标记可注入的服务              | 类           |
| `@Inject()`                             | 手动指定注入令牌              | 构造函数参数 |
| `@Optional()`                           | 依赖可选，不存在也不报错      | 构造函数参数 |
| `@InjectRepository()`                   | TypeORM 专用，注入 Repository | 构造函数参数 |
| `@Get()`, `@Post()` 等                  | 声明路由                      | 方法         |
| `@Param()`, `@Query()`, `@Body()`       | 提取请求参数                  | 方法参数     |
| `@Req()`, `@Res()`                      | 获取原生请求/响应对象         | 方法参数     |
| `@UseGuards()`, `@UseInterceptors()` 等 | 绑定守卫/拦截器               | 类或方法     |

你还可以自己写装饰器：

```typescript
// 自定义参数装饰器：从请求中提取当前用户
export const CurrentUser = createParamDecorator(
  (data: unknown, ctx: ExecutionContext) => {
    const request = ctx.switchToHttp().getRequest()
    return request.user
  },
)

// 用法
@Get('profile')
getProfile(@CurrentUser() user: User) {
  return user
}
```

### 2.5 控制器、服务、模块与常见装饰器速览

NestJS 应用本质上是一个"模块树"：

```
AppModule
├── AuthModule
│   ├── AuthController (路由层)
│   ├── AuthService (业务逻辑层)
│   └── UserModule (子模块)
├── ConfigModule (全局配置)
├── DatabaseModule (数据库连接)
└── CacheModule (缓存)
```

各层职责：

- **Controller**：接收 HTTP 请求、参数校验、返回响应。**绝不写业务逻辑。**
- **Service**：纯业务逻辑。可以被 Controller、其他 Service、甚至微服务调用。
- **Module**：组织代码的基本单元，声明该模块有哪些 Controller、Service，导入/导出了哪些依赖。

```typescript
@Module({
  imports: [TypeOrmModule.forFeature([User])], // 导入 TypeORM 实体
  controllers: [UserController], // 注册控制器
  providers: [UserService], // 注册服务
  exports: [UserService], // 导出给其他模块使用
})
export class UserModule {}
```

## 三、多环境配置：让应用在不同环境"活起来"

企业级项目不可能只有一套配置。开发环境连本地数据库，生产环境连 RDS；开发环境日志打控制台，生产环境打到 Elasticsearch。配置管理搞不好，生产事故就是迟早的。

### 3.1 ConfigModule.forRoot() 的正确用法

```bash
pnpm add @nestjs/config
```

```typescript
// app.module.ts
import { Module } from '@nestjs/common'
import { ConfigModule } from '@nestjs/config'

@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true, // ✅ 全局可用，不用在每个模块里重复 import
      envFilePath: ['.env.development', '.env'], // ✅ 后面的文件覆盖前面的
      validationSchema: validationSchema, // ✅ Joi 校验
    }),
  ],
})
export class AppModule {}
```

`isGlobal: true` 很重要——否则每个需要用配置的模块都得单独 `imports: [ConfigModule]`，时间长了你会疯。

### 3.2 环境文件优先级策略

```typescript
// 推荐的做法
const envFilePath = [
  `.env.${process.env.NODE_ENV || 'development'}`, // 优先级最高
  '.env', // 兜底
]

ConfigModule.forRoot({
  envFilePath,
  // ...
})
```

这个策略的含义是：

- `NODE_ENV=production` 时，优先读 `.env.production`，找不到再读 `.env`
- `NODE_ENV=development` 时，优先读 `.env.development`
- 变量名相同时，**排在数组前面的文件优先级更高**

```bash
# .env.development (优先)
DATABASE_HOST=localhost
DATABASE_PORT=5432

# .env (兜底)
DATABASE_HOST=prod-rds.xxx.com  # 这个值会被 .env.development 覆盖
REDIS_HOST=localhost             # .env.development 里没写，所以取这个
```

### 3.3 Joi 校验：环境变量出错了就早点报

最怕的场景：部署到生产环境，跑了一个小时才发现某个环境变量没配。应用不应该默默带着 undefined 继续跑——应该在启动时就炸掉。

```bash
pnpm add joi
```

```typescript
import * as Joi from 'joi'

const validationSchema = Joi.object({
  NODE_ENV: Joi.string().valid('development', 'production', 'test').default('development'),

  PORT: Joi.number().default(3000),

  DATABASE_HOST: Joi.string().required(),
  DATABASE_PORT: Joi.number().default(5432),
  DATABASE_USER: Joi.string().required(),
  DATABASE_PASSWORD: Joi.string().required(),
  DATABASE_NAME: Joi.string().required(),

  REDIS_HOST: Joi.string().required(),
  REDIS_PORT: Joi.number().default(6379),

  JWT_SECRET: Joi.string().min(32).required(),
  JWT_EXPIRES_IN: Joi.string().default('7d'),
})

export default validationSchema
```

如果启动时 `DATABASE_PASSWORD` 没有配，应用会直接抛异常：「ValidationError: "DATABASE_PASSWORD" is required」——而不是跑着跑着数据库连不上。

## 四、日志方案：生产环境的"黑匣子"

企业级应用上线后，你最依赖的东西就是日志。出 bug 了看日志，性能慢了看日志，被攻击了也看日志。

### 4.1 为什么推荐 Pino

日志库选型，三个核心维度：性能、结构化、生态。

| 方案               | 吞吐量 | 结构化    | 适用场景            |
| ------------------ | ------ | --------- | ------------------- |
| Pino               | 极高   | JSON 原生 | 生产环境首选        |
| Winston            | 中     | 需配置    | 需要复杂传输策略时  |
| NestJS 内置 Logger | 低     | 弱        | 开发调试、Demo 项目 |

Pino 快的原因很简单——它是异步的，JSON 序列化用的是优化的 schema 方案而不是 `JSON.stringify`。在高 QPS 场景下，这一点差异会被放大到不可忽视。

```bash
pnpm add nestjs-pino pino-http pino-pretty
```

```typescript
// main.ts
import { Logger } from 'nestjs-pino'

const app = await NestFactory.create(AppModule, {
  bufferLogs: true, // ✅ 启动阶段的日志先缓存，等 pino 初始化完再输出
})

app.useLogger(app.get(Logger))
```

```typescript
// app.module.ts - LoggerModule 的配置
LoggerModule.forRoot({
  pinoHttp: {
    // 开发环境：人类可读格式
    transport:
      process.env.NODE_ENV !== 'production' ? { target: 'pino-pretty', options: { colorize: true } } : undefined,
    // 生产环境：JSON 格式，方便 ELK 等日志系统解析
    level: process.env.NODE_ENV === 'production' ? 'info' : 'debug',
    // 自动记录每个请求的耗时和响应体大小
    autoLogging: false, // 配合拦截器手动控制，避免敏感信息进入日志
    serializers: {
      req: (req) => ({
        method: req.method,
        url: req.url,
        // ❌ 不记录 headers 和 body，避免日志里出现密码
      }),
    },
  },
})
```

### 4.2 业务日志的正确写法

```typescript
import { InjectPinoLogger, PinoLogger } from 'nestjs-pino'

@Injectable()
export class UserService {
  constructor(
    @InjectPinoLogger(UserService.name)
    private readonly logger: PinoLogger,
  ) {}

  async createUser(dto: CreateUserDto) {
    this.logger.info({ email: dto.email }, '开始创建用户')

    try {
      const user = await this.repository.save(dto)
      this.logger.info({ userId: user.id }, '用户创建成功')
      return user
    } catch (error) {
      // 第二个参数放上下文，不要拼到消息里
      this.logger.error({ err: error, email: dto.email }, '创建用户失败')
      throw error
    }
  }
}
```

Pino 日志的关键习惯：**把上下文数据作为第一个对象参数，消息字符串作为第二个参数**。这样日志里搜 `email: "xxx"` 就能精确匹配，而不是用正则去抠消息字符串。

### 4.3 Winston 的工程化用法（备选）

如果你的团队已经深度使用 Winston + Elasticsearch 等传输层，NestJS 也原生支持：

```bash
pnpm add nest-winston winston
```

```typescript
// Winston 的典型配置
import { transports, format } from 'winston'

WinstonModule.forRoot({
  transports: [
    // 控制台输出
    new transports.Console({
      format: format.combine(
        format.timestamp(),
        format.colorize(),
        format.printf(({ timestamp, level, message, context }) => {
          return `[${timestamp}] ${level} [${context || 'App'}]: ${message}`
        }),
      ),
    }),
    // 文件输出——按日期滚动
    new transports.DailyRotateFile({
      filename: 'logs/error-%DATE%.log',
      datePattern: 'YYYY-MM-DD',
      level: 'error',
      maxFiles: '30d', // 保留 30 天
    }),
  ],
})
```

## 五、过滤器、CORS、前缀、版本控制

这些是"地基"级别的配置——每个接口都会经过，必须在一开始就搞对。

### 5.1 异常过滤器：统一错误响应格式

前端最讨厌的事：同一个接口，成功时返回 `{ data: ... }`，失败时返回 `{ statusCode: 400, message: '...' }`——两种格式完全不一样，前端要写两套判断。

统一异常过滤器解决这个问题：

```typescript
// http-exception.filter.ts
@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
  catch(exception: HttpException, host: ArgumentsHost) {
    const ctx = host.switchToHttp()
    const response = ctx.getResponse<Response>()
    const request = ctx.getRequest<Request>()
    const status = exception.getStatus()

    const exceptionResponse = exception.getResponse()
    const message =
      typeof exceptionResponse === 'string' ? exceptionResponse : (exceptionResponse as any).message || '未知错误'

    response.status(status).json({
      code: status,
      message,
      timestamp: new Date().toISOString(),
      path: request.url,
    })
  }
}

// 所有未被 HttpException 捕获的异常——兜底
@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  constructor(private readonly logger: PinoLogger) {}

  catch(exception: unknown, host: ArgumentsHost) {
    const ctx = host.switchToHttp()
    const response = ctx.getResponse()
    const request = ctx.getRequest()

    this.logger.error(
      {
        err: exception,
        url: request.url,
        ip: request.ip,
      },
      '未捕获的异常',
    )

    response.status(500).json({
      code: 500,
      message: '服务器内部错误',
      timestamp: new Date().toISOString(),
      path: request.url,
    })
  }
}
```

### 5.2 CORS 与全局前缀

```typescript
// main.ts
const app = await NestFactory.create(AppModule)

// CORS 根据环境区别对待
app.enableCors({
  origin:
    process.env.NODE_ENV === 'production'
      ? ['https://yourdomain.com'] // ✅ 生产环境白名单
      : ['http://localhost:3000', 'http://localhost:5173'], // ✅ 开发环境
  credentials: true, // 允许携带 Cookie
})

// 全局前缀——所有接口都以 /api 开头
app.setGlobalPrefix('api')

// 排除健康检查接口，避免被前缀覆盖
// setGlobalPrefix 支持 exclude 方法
app.setGlobalPrefix('api', {
  exclude: ['health'], // /health 不加前缀
})
```

### 5.3 API 版本控制

业务升级时，你不可能要求所有客户端同时升级到新接口。版本控制是必经之路。

NestJS 内置了强大的版本控制方案：

```typescript
// main.ts
app.enableVersioning({
  type: VersioningType.URI, // 版本号在 URL 路径中: /api/v1/users
  defaultVersion: ['1'], // 不指定版本时默认用 v1
  // 也可以选 Header 模式: VersioningType.HEADER
  // 或 Media Type 模式: VersioningType.MEDIA_TYPE
})
```

```typescript
// 控制器指定版本
@Controller({ path: 'users', version: ['1', '2'] })
export class UserController {
  // 两个版本共用的接口
  @Get()
  findAll() { ... }

  // 仅 v2 新增的接口
  @Version('2')
  @Get('stats')
  getStats() { ... }
}
```

```typescript
// 或者控制器级别的版本隔离
@Controller({ path: 'users', version: '1' })
export class UserV1Controller { ... }

@Controller({ path: 'users', version: '2' })
export class UserV2Controller { ... }
```

访问效果：

- `GET /api/v1/users` → UserV1Controller
- `GET /api/v2/users` → UserV2Controller
- `GET /api/v2/users/stats` → UserV2Controller.getStats()

## 七、为什么需要高速缓存

一个没有缓存的企业级应用，就像一家餐馆没有冰箱——每次来客人都得现买食材。流量一大，数据库就扛不住。

### 7.1 Redis 客户端选型：ioredis 推荐

推荐 ioredis——不是因为 node-redis 不行，而是 ioredis 的 API 设计更贴近实际使用场景，特别是集群模式的配置简洁得多。

### 7.4 使用 @nestjs/cache-manager + LRU 做两级缓存

Redis 快，但毕竟是要走网络的。对于高频访问但不怎么变的数据（比如字典表、配置项），在内存里加一层 LRU 缓存，性能可以再提一个量级。

```bash
pnpm add @nestjs/cache-manager cache-manager lru-cache
```

```typescript
import { CacheModule } from '@nestjs/cache-manager'
import { createKeyv } from 'create-keyv'
import KeyvRedis from '@keyv/redis'

// 内存 LRU 缓存（进程内，零网络开销）
const memoryCache = createKeyv('cache-manager://store/memory', {
  max: 1000, // 最多缓存 1000 个 key
  ttl: 60000, // 60 秒过期
})

// Redis 缓存（跨进程共享）
const redisCache = createKeyv({
  store: new KeyvRedis({
    url: `redis://:${process.env.REDIS_PASSWORD}@${process.env.REDIS_HOST}:${process.env.REDIS_PORT}`,
  }),
})

CacheModule.register({
  stores: [memoryCache, redisCache], // ✅ 先查内存，未命中再查 Redis
  isGlobal: true,
})
```

### 7.5 通过标志位动态控制缓存

缓存很好，但在某些场景你必须能**动态关闭**缓存——比如数据刚更新、或者调试时：

```typescript
@Injectable()
export class UserService {
  constructor(
    @InjectRepository(User) private readonly userRepo: Repository<User>,
    @Inject(CACHE_MANAGER) private readonly cacheManager: Cache,
  ) {}

  async findById(id: number, useCache = true): Promise<User | null> {
    const cacheKey = `user:${id}`

    // ✅ 通过参数控制是否使用缓存
    if (useCache) {
      const cached = await this.cacheManager.get<User>(cacheKey)
      if (cached) return cached
    }

    const user = await this.userRepo.findOne({ where: { id } })
    if (user) {
      await this.cacheManager.set(cacheKey, user, 60000) // 60秒过期
    }
    return user
  }

  async updateUser(id: number, dto: UpdateUserDto) {
    const result = await this.userRepo.update(id, dto)
    // ✅ 更新后主动清除缓存
    await this.cacheManager.del(`user:${id}`)
    return result
  }
}
```

这种模式的关键习惯：**永远在写操作后主动 invalidate 缓存**，不要依赖 TTL 自然过期。否则数据不一致的时间窗口可能长达几十分钟。

## 九、数据库集成与 ORM：企业级应用的"心脏"

这是 NestJS 最有争议、也最重要的一章。选错了 ORM 或者搞错了数据库架构，后面改起来的成本是整个项目里最高的。

### 9.1 ORM 选型对比

| ORM      | 优势                                   | 劣势                            |
| -------- | -------------------------------------- | ------------------------------- |
| TypeORM  | NestJS 原生支持最好、装饰器风格、成熟  | 类型推导弱、部分 API 设计有争议 |
| Prisma   | 类型安全极好、Schema-First、迁移工具强 | 多一层抽象、生成代码不透明      |
| Mongoose | MongoDB 事实标准、Schema 定义直观      | 仅适用于 MongoDB                |
| MikroORM | 设计更现代、类型推导好                 | 社区比 TypeORM 小               |

**选型建议**：

- 用的是关系型数据库（PostgreSQL/MySQL）：新项目优先考虑 **Prisma**——它的类型安全和迁移体验是降维打击。但如果团队大部分人对 NestJS 装饰器风格更熟悉，**TypeORM** 也完全够用。
- 用的是 MongoDB：直接用 **Mongoose**，没有争议。
- 一个都不熟：先学 Prisma——它的学习曲线最平滑，Schema 定义即文档。

#### 9.2.3 多数据库连接（多租户场景）

这是企业级应用最常见的需求之一——同一个服务连接多个数据库。比如 SaaS 系统的每个租户有独立数据库。

```typescript
// multi-database.service.ts
@Injectable()
export class MultiDatabaseService implements OnApplicationShutdown {
  // ✅ 全局 Map 存放所有 DataSource 实例（这不是连接池，是连接管理器）
  private dataSources = new Map<string, DataSource>()

  async getDataSource(tenantId: string): Promise<DataSource> {
    if (this.dataSources.has(tenantId)) {
      const ds = this.dataSources.get(tenantId)!
      if (ds.isInitialized) return ds
    }

    // 从配置中心或元数据库读取该租户的数据库配置
    const tenantConfig = await this.loadTenantConfig(tenantId)

    const dataSource = new DataSource({
      type: 'postgres',
      host: tenantConfig.host,
      port: tenantConfig.port,
      username: tenantConfig.username,
      password: tenantConfig.password,
      database: tenantConfig.database,
      entities: [User, Order],
      synchronize: false,
    })

    await dataSource.initialize()
    this.dataSources.set(tenantId, dataSource)
    return dataSource
  }

  async getRepository<T>(tenantId: string, entity: EntityTarget<T>): Promise<Repository<T>> {
    const ds = await this.getDataSource(tenantId)
    return ds.getRepository(entity)
  }

  // ✅ 应用关闭时循环销毁所有 DataSource
  async onApplicationShutdown() {
    for (const [tenantId, ds] of this.dataSources) {
      if (ds.isInitialized) {
        await ds.destroy()
        console.log(`租户 ${tenantId} 数据库连接已关闭`)
      }
    }
  }

  private async loadTenantConfig(tenantId: string) {
    // 从元数据库或配置中心查询租户的 DB 连接信息
    return { host: '...', port: 5432, username: '...', password: '...', database: `tenant_${tenantId}` }
  }
}
```

你需要区分两个概念：

1. **ORM 的连接池**：TypeORM 内部的 pool，管理到同一个数据库的多个连接
2. **DataSource Map**：你手动管理的"多数据库连接集合"，不同租户连不同数据库

两者不是一个东西，一个是池化复用，一个是路由分发。

#### 9.2.4 TypeOrmConfigService 模式（推荐替代 useFactory）

当数据库配置逻辑比较复杂时，不要直接写在 `useFactory` 回调里——抽成一个专门的 Config Service：

```typescript

      port: this.configService.get('DATABASE_PORT'),
      // ... 其他配置
    }
  }
}

// 在 Module 中使用

  useClass: TypeOrmConfigService, // ✅ 代码更清晰，可注入、可测试
})
```

### 9.4 数据库连接池的正确理解

连接池不是你设置的越大越好。PostgreSQL 默认连接数上限是 100，如果你的服务实例有 5 个 Pod，每个 Pod 的 `max: 20` 刚好到上限。但如果你给每个 Pod 设了 `max: 50`，5 个 Pod 就是 250 个连接——超出 PostgreSQL 限制，新的连接会被拒绝。

连接池大小的经验公式：`max = (数据库最大连接数 / 服务实例数) * 0.8`，留 20% 的余量给运维操作和紧急查询。

## 十、RxJS：把异步当集合处理的利器

很多人觉得 NestJS 里的 RxJS 是多余的——"我回调/Promise 用得好好的，为什么要学这个？"

这就像你用 for 循环处理数组一样能干活，但遇到复杂的过滤、转换、合并操作时，没学过 map/filter/reduce 就很痛苦。RxJS 对异步事件的操控力，跟数组方法对数据的操控力是一个道理。

### 10.1 核心概念：把异步事件当作集合

```typescript
// 没有 RxJS——写一个"用户输入搜索"的防抖
let timer: NodeJS.Timeout
inputElement.addEventListener('input', (e) => {
  clearTimeout(timer)
  timer = setTimeout(() => {
    search(e.target.value)
  }, 300)
})
```

```typescript
// 用 RxJS——声明式，一眼看懂
fromEvent(inputElement, 'input')
  .pipe(
    map((e) => e.target.value),
    debounceTime(300), // 300ms 防抖
    distinctUntilChanged(), // 相同值不重复请求
    switchMap(
      (
        keyword, // ✅ 新搜索来了就取消旧的
      ) => this.searchService.search(keyword),
    ),
  )
  .subscribe((results) => {
    this.displayResults(results)
  })
```

### 10.2 数据库断连重试

生产环境数据库偶尔会断连——可能是网络抖动，可能是数据库主从切换。RxJS 的 `retry` 操作符能优雅地处理这类问题：

```typescript
import { from, throwError } from 'rxjs'
import { retry, catchError, delay, take } from 'rxjs/operators'

@Injectable()
export class ResilientUserService {
  constructor(@InjectRepository(User) private readonly userRepo: Repository<User>) {}

  findByIdWithRetry(id: number) {
    return from(this.userRepo.findOne({ where: { id } })).pipe(
      retry({
        count: 3, // 最多重试 3 次
        delay: (error, retryCount) => {
          console.log(`第 ${retryCount} 次重试，错误: ${error.message}`)
          // 指数退避: 1s, 2s, 4s
          return new Promise((resolve) => setTimeout(resolve, Math.pow(2, retryCount - 1) * 1000))
        },
      }),
      catchError((error) => {
        console.error('重试耗尽，查询失败', error)
        return throwError(() => new Error('服务暂时不可用，请稍后重试'))
      }),
    )
  }
}
```

### 11.4 中间件 vs 守卫：为什么要用守卫做认证？

中间件的问题：它不知道 `next()` 后面是什么。你在中间件里做了认证，但拦不住后面某个方法抛异常后绕过去。

守卫不同——守卫能拿到 `ExecutionContext`，它知道：

- 即将执行的是哪个 Controller 的哪个方法
- 该方法上有什么装饰器（比如 `@Public()`、`@Roles()`）
- 请求的完整上下文

```typescript
// jwt-auth.guard.ts
@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {
  constructor(private readonly reflector: Reflector) {
    super()
  }

  canActivate(context: ExecutionContext): boolean | Promise<boolean> | Observable<boolean> {
    // ✅ 检查是否有 @Public() 装饰器
    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
      context.getHandler(),
      context.getClass(),
    ])
    if (isPublic) return true

    return super.canActivate(context)
  }
}
```

```typescript
// 自定义装饰器：标记公开接口
import { SetMetadata } from '@nestjs/common'

export const IS_PUBLIC_KEY = 'isPublic'
export const Public = () => SetMetadata(IS_PUBLIC_KEY, true)

// 用法
@Public()
@Post('register')
async register(@Body() dto: RegisterDto) { ... }
```

```typescript

```

### 11.6 拦截器脱敏：接口不返回密码

```typescript
// serialize.interceptor.ts
@Injectable()
export class SerializeInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    return next.handle().pipe(
      map((data) => {
        if (Array.isArray(data)) {
          return data.map((item) => this.transform(item))
        }
        return this.transform(data)
      }),
    )
  }

  private transform(data: any) {
    if (!data) return data

    // ✅ 敏感字段自动剔除
    const sensitiveFields = ['password', 'passwordHash', 'refreshToken', 'secretAnswer']
    const result = { ...data }
    for (const field of sensitiveFields) {
      delete result[field]
    }
    return result
  }
}
```

```typescript
  @Column()
  name: string
}
```

## 十二、权限控制：RBAC 与 CASL 实战

认证回答"你是谁"，授权回答"你能做什么"。很多项目把这两个混在一起，结果是灾难性的——当你需要支持多角色、细粒度权限时，代码已经散落在几十个 if-else 里。

### 12.1 权限模型简介

| 模型 | 含义               | 粒度   | 复杂度 |
| ---- | ------------------ | ------ | ------ |
| ACL  | 访问控制列表       | 资源级 | 高     |
| DAC  | 自主访问控制       | 用户级 | 中     |
| MAC  | 强制访问控制       | 标签级 | 高     |
| ABAC | 基于属性的访问控制 | 属性级 | 很高   |
| RBAC | 基于角色的访问控制 | 角色级 | 中     |

企业级应用大多数场景用 **RBAC** 就够了——先确定角色，再给角色分配权限，最后给用户分配角色。

### 12.2 RBAC 实体设计

```typescript
// permission.entity.ts
```

### 12.3 @Permission 装饰器 + PermissionGuard

```typescript
// permission.decorator.ts
import { SetMetadata } from '@nestjs/common'

export const PERMISSIONS_KEY = 'permissions'
export const RequirePermissions = (...permissions: string[]) =>
  SetMetadata(PERMISSIONS_KEY, permissions)

// 用法
@RequirePermissions('user:create', 'user:read')
@Post()
createUser(@Body() dto: CreateUserDto) { ... }
```

```typescript
// permission.guard.ts
@Injectable()
export class PermissionGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const requiredPermissions = this.reflector.getAllAndOverride<string[]>(PERMISSIONS_KEY, [
      context.getHandler(),
      context.getClass(),
    ])

    // 没有 @RequirePermissions 装饰器 = 不需要权限
    if (!requiredPermissions || requiredPermissions.length === 0) {
      return true
    }

    const request = context.switchToHttp().getRequest()
    const user: User = request.user

    if (!user) return false

    // 查询用户的所有权限
    const userPermissions = await this.authService.getUserPermissionNames(user.id)

    // ✅ 任一所需权限满足即可（OR 逻辑）
    // 如果需要全部满足（AND 逻辑），改用 every
    return requiredPermissions.some((perm) => userPermissions.includes(perm))
  }
}
```

```typescript
// 在模块中注册为全局守卫——注意顺序：JWT 在前，权限在后
providers: [
  { provide: APP_GUARD, useClass: JwtAuthGuard },
  { provide: APP_GUARD, useClass: PermissionGuard },
]
```

### 12.4 前端权限：路由、菜单、按钮

权限控制不能只靠后端——用户能看到的界面也应该根据权限动态展示。通常做法是用户登录后，后端返回一个权限列表：

```typescript

{
  "user": { "id": 1, "name": "张三" },
  "roles": ["editor"],
  "permissions": ["post:read", "post:create", "post:update", "comment:read", "comment:create"]
}
```

前端根据这个列表：

- **路由权限**：没有 `user:manage` 权限的用户看不到用户管理页
- **菜单权限**：侧边栏动态渲染有权限的菜单项
- **按钮权限**：没有 `post:delete` 权限的用户看不到删除按钮

### 12.5 CASL：基于属性的权限策略库

RBAC 能覆盖大多数场景，但当权限逻辑变成"用户只能编辑自己创建的文章"或"部门领导只能看自己部门的报表"时，RBAC 的粒度就不够了。这时候需要 **CASL**——一个支持 ABAC 风格策略的权限库。

```bash
pnpm add @casl/ability
```

```typescript
import { AbilityBuilder, createMongoAbility, AbilityClass, ExtractSubjectType } from '@casl/ability'

type Actions = 'manage' | 'create' | 'read' | 'update' | 'delete'
type Subjects = 'Article' | 'User' | 'Comment' | Article | User

export type AppAbility = MongoAbility<[Actions, Subjects]>
export const AppAbility = MongoAbility as AbilityClass<AppAbility>

export function defineAbilityFor(user: User) {
  const { can, cannot, build } = new AbilityBuilder(AppAbility)

  if (user.roles?.some((r) => r.name === 'admin')) {
    can('manage', 'all') // 管理员可以做任何事
  }

  if (user.roles?.some((r) => r.name === 'editor')) {
    can(['create', 'read', 'update'], 'Article')
    can('delete', 'Article', { authorId: user.id }) // ✅ 只能删自己的文章
    can(['create', 'read'], 'Comment')
  }

  if (user.roles?.some((r) => r.name === 'viewer')) {
    can('read', 'Article', { status: 'published' }) // ✅ 只能看已发布的
    can('read', 'Comment')
  }

  return build()
}
```

```typescript
// 在 Service 中使用
const ability = defineAbilityFor(currentUser)
if (!ability.can('update', subject('Article', { authorId: 5 }))) {
  throw new ForbiddenException('你没有权限编辑此文章')
}
```

CASL 的精髓在于它的条件能力（Conditional Ability）——`{ authorId: user.id }` 这种基于资源属性的条件判断，这是纯 RBAC 做不到的。

```typescript
import { Processor, Process, OnQueueFailed } from '@nestjs/bull'
import { Job } from 'bull'

@Processor('email')
export class EmailProcessor {
  constructor(private readonly mailService: MailService) {}

  @Process('welcome')
  async handleWelcomeEmail(job: Job<{ to: string; username: string }>) {
    await this.mailService.sendWelcomeEmail(job.data.to, job.data.username)
  }

  @Process('resetPassword')
  async handleResetPasswordEmail(job: Job<{ to: string; token: string }>) {
    // ...发送重置密码邮件
  }

  @OnQueueFailed()
  onFailed(job: Job, error: Error) {
    console.error(`邮件任务失败: job ${job.id}, error: ${error.message}`)
    // 可以在这里写入重试队列或发送告警
  }

```

```typescript
// email.service.ts —— 生产者（在业务代码中添加任务）
@Injectable()
export class UserService {
  constructor(@InjectQueue('email') private readonly emailQueue: Queue) {}

  async register(dto: RegisterDto) {
    const user = await this.createUser(dto)

    // ✅ 异步任务，不阻塞注册流程
    await this.emailQueue.add(
      'welcome',
      {
        to: user.email,
        username: user.username,
      },
      {
        attempts: 3, // 失败重试 3 次
        backoff: { type: 'exponential', delay: 2000 }, // 指数退避
        removeOnComplete: true, // 成功自动清理
      },
    )

    return user
  }
}
```

Bull 的核心价值：

- **解耦**：用户注册和发邮件是两件事，不应该耦合在一个请求周期里
- **削峰**：促销活动时大量用户注册，邮件服务器撑不住——队列帮你排队处理
- **重试**：邮件发送失败了自动重试，不用人工介入

## 十四、微服务（重点）

前面十三章讲的都是单体应用。当你项目规模大到单体扛不住时，微服务是不可避免的路径。但微服务不是万能药——拆分不当比单体还糟糕。

### 14.1 微服务和分布式的区别

很多人把"微服务"和"分布式"混着用。但这俩不是一个概念：

- **分布式**是一个架构风格——一个系统被拆成多个节点，通过网络通信协作。这是"怎么部署"的问题。
- **微服务**是分布式的一种具体实现——按业务边界拆分，每个服务独立部署、独立数据库、独立团队。这是"怎么拆分"的问题。

你可以有分布式的单体（同个代码库部署多个实例），也可以有单机的微服务（一个进程里跑多个 NestJS 应用）。关键在于**业务边界**。

### 14.2 服务拆分：最难的决策

微服务最难的不是代码，而是**怎么拆**。拆错了比单体还难维护。

Martin Fowler 的《微服务架构模式》是必读书，但这里给你一个实操框架：

#### 按业务拆分

| 服务     | 职责                     | 示例接口          |
| -------- | ------------------------ | ----------------- |
| 用户服务 | 注册、登录、用户信息管理 | /users, /auth     |
| 内容服务 | 文章、评论、点赞         | /posts, /comments |
| 消息服务 | 站内信、推送、邮件       | /notifications    |
| 统计服务 | 用户行为分析、报表       | /analytics        |
| 订单服务 | 下单、支付、退款         | /orders           |

#### 按功能拆分

有些逻辑横向贯穿多个服务，需要抽成公共能力：

- **审计服务**：记录所有操作日志——任何服务的关键操作都写一条审计记录
- **通知服务**：聚合所有需要通知的场景——用户注册、订单完成、评论回复都能复用
- **文件服务**：统一管理文件上传、存储、CDN

#### 按资源特征拆分

| 特征     | 适合拆分出的独立服务                      |
| -------- | ----------------------------------------- |
| 高频访问 | 搜索服务（独立扩容、缓存策略不同）        |
| 低频批量 | 数据导出服务（独立资源调度）              |
| IO 密集  | 图片/视频处理服务（队列 + Worker）        |
| 计算密集 | AI 推理服务、报表生成（GPU/CPU 独立调度） |

### 14.3 服务治理全景

一套成熟的微服务体系，除了业务服务本身，还需要一套治理基础设施。推荐关注 [CNCF 全景图](https://cncf.io)：

| 功能           | 常用工具                  | 作用                               |
| -------------- | ------------------------- | ---------------------------------- |
| 服务注册与发现 | Consul / Etcd / Nacos     | "我的 IP 在哪？我能调到谁？"       |
| 配置中心       | Nacos / Consul KV         | 配置集中管理，支持热更新           |
| API 网关       | Kong / Traefik / Nginx    | 统一入口、限流、鉴权               |
| 负载均衡       | Nginx / Envoy / 云厂商 LB | 流量分发                           |
| 服务熔断       | Opossum / Resilience4j    | 下游挂了怎么办？快速失败不拖垮上游 |
| 链路追踪       | SkyWalking / Jaeger       | 一个请求经过了哪些服务，哪里慢了   |
| 日志采集       | ELK / Loki                | 分散在多个服务的日志如何统一查询   |
| 监控告警       | Prometheus + Grafana      | 服务健康状态、资源使用             |

#### 14.4.3 gRPC 通信（高性能，强类型）

gRPC 是微服务通信的黄金标准——基于 HTTP/2，使用 Protocol Buffers 做序列化，双向流支持，强类型契约。

```bash
pnpm add @nestjs/microservices @grpc/grpc-js @grpc/proto-loader
```

```protobuf
// proto/user.proto
syntax = "proto3";

package user;

service UserService {
  rpc FindOne (UserById) returns (User) {}
  rpc FindAll (Empty) returns (UserList) {}
}

message UserById {
  int32 id = 1;
}

message User {
  int32 id = 1;
  string email = 2;
  string name = 3;
}

message UserList {
  repeated User users = 1;
}

message Empty {}
```

```typescript
// 生成 TypeScript 类型
// npx grpc-tools -I ./proto --plugin=protoc-gen-ts=./node_modules/.bin/protoc-gen-ts --ts_out=./src/generated ./proto/*.proto
```

```typescript
// NestJS gRPC 服务端
@Controller()
export class UserGrpcController {
  constructor(private readonly userService: UserService) {}

  @GrpcMethod('UserService', 'FindOne')
  async findOne(data: { id: number }): Promise<User> {
    return this.userService.findById(data.id)
  }
}
```

```typescript
// NestJS gRPC 客户端
@Injectable()
export class UserGrpcClient implements OnModuleInit {
  @Client({
    transport: Transport.GRPC,
    options: {
      package: 'user',
      protoPath: join(__dirname, '../proto/user.proto'),
      url: 'localhost:50051',
      // ✅ 生产环境加 SSL
      // credentials: credentials.createSsl(),
    },
  })
  private client: ClientGrpc

  private userService: any

  onModuleInit() {
    this.userService = this.client.getService('UserService')
  }

  async findOne(id: number) {
    return this.userService.FindOne({ id }).toPromise()
  }
}
```

gRPC 的 proto 文件和证书（certs）需要在服务之间共享——通常的做法是把它抽成独立的 npm 包或 git submodule，避免到处拷贝导致版本不一致。

**gRPC 健康检查**也很重要——NestJS 内置支持：

```typescript
import { HealthCheckService, GRPCHealthIndicator } from '@nestjs/terminus'

@Get('health')
healthCheck() {
  return this.health.check([
    () => this.grpc.pingCheck('user-service', { service: 'user.UserService', url: 'localhost:50051' }),
  ])
}
```

### 14.7 流式消息（Event-Based）

事件驱动是微服务解耦的关键手段——一个服务发出事件，其他服务按需消费，完全解耦：

```typescript
// 发出事件
@Injectable()
export class UserService {
  constructor(@Inject('EVENT_BUS') private readonly eventBus: ClientProxy) {}

  async register(dto: RegisterDto) {
    const user = await this.createUser(dto)
    // ✅ 发射事件——谁关心谁处理，发送方不 care
    this.eventBus.emit('user.registered', {
      userId: user.id,
      email: user.email,
      timestamp: new Date().toISOString(),
    })
    return user
  }
}

// 消费者 A：发欢迎邮件
@EventPattern('user.registered')
async handleWelcomeEmail(data: { userId: number; email: string }) {
  await this.mailService.sendWelcome(data.email)
}

// 消费者 B：初始化用户配置
@EventPattern('user.registered')
async handleInitConfig(data: { userId: number }) {
  await this.configService.createDefaultConfig(data.userId)
}

// 消费者 C：写入审计日志
@EventPattern('user.registered')
async handleAuditLog(data: { userId: number; email: string }) {
  await this.auditService.log('user', 'register', data.userId)
}
```

### 14.8 超时逻辑与异常处理

微服务调用最怕"无响应"——下游挂了，上游傻等，等超时的时候上游自己也挂了。

```typescript
// 调用微服务时设置超时和重试
this.userServiceClient.send('user.findOne', { id: 5 }).pipe(
  timeout(3000), // ✅ 3 秒没响应就抛错
  retry({
    // ✅ 失败重试 2 次
    count: 2,
    delay: (error, retryCount) => {
      console.warn(`重试第 ${retryCount} 次: ${error.message}`)
      return timer(retryCount * 1000) // 线性退避
    },
  }),
  catchError((error) => {
    // ✅ 熔断后的降级逻辑
    if (error instanceof TimeoutError) {
      return of({ id: 5, name: '未知用户（缓存）', _fallback: true })
    }
    throw error
  }),
)
```

服务注册与发现是微服务最基础也最重要的能力。推荐 **Consul**——它同时提供了服务注册、健康检查、KV 配置存储。

### 14.10 Multipass + K3s：本地微服务集群

开发和测试微服务时，你不能每次都在集群上调试——本地搭建一个轻量级 K8s 环境是最佳实践。

[Multipass](https://multipass.run) 是 Canonical 出的轻量级虚拟机管理工具，几秒钟就能在本地启动一个 Ubuntu 实例。[K3s](https://k3s.io) 是 Rancher 出的精简版 Kubernetes——去掉了云厂商相关的功能，只保留核心，内存占用从 2GB 降到 512MB。

```bash
# 安装 multipass
brew install multipass # macOS
# 或 snap install multipass # Linux

# 创建一个 VM
multipass launch --name k3s-master --cpus 2 --memory 4G --disk 20G

# 在 VM 内安装 k3s
multipass exec k3s-master -- bash -c "curl -sfL https://get.k3s.io | sh -"

# 获取 kubeconfig
multipass exec k3s-master -- sudo cat /etc/rancher/k3s/k3s.yaml > ~/.kube/k3s-config.yaml
export KUBECONFIG=~/.kube/k3s-config.yaml

# 验证集群
kubectl get nodes
```

把 NestJS 微服务部署到 K3s：

```yaml
# k8s/user-service.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
spec:
  replicas: 3 # ✅ 3 个副本，保证高可用
  selector:
    matchLabels:
      app: user-service
  template:
    metadata:
      labels:
        app: user-service
    spec:
      containers:
        - name: user-service
          image: your-registry/user-service:latest
          ports:
            - containerPort: 3001
          env:
            - name: DATABASE_HOST
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: host
          livenessProbe: # ✅ 探活：进程是不是还活着
            httpGet:
              path: /health
              port: 3001
            initialDelaySeconds: 10
            periodSeconds: 15
          readinessProbe: # ✅ 就绪：能不能接流量
            httpGet:
              path: /health/ready
              port: 3001
            initialDelaySeconds: 5
            periodSeconds: 10
---
apiVersion: v1
kind: Service
metadata:
  name: user-service
spec:
  selector:
    app: user-service
  ports:
    - port: 3001
      targetPort: 3001
```

## 十五、总结：企业级 NestJS 架构的核心原则

### 15.1 配置与管理

- **多环境配置**必须通过 `envFilePath` 区分，`Joi` 做启动校验——环境变量不对就炸掉，不要默默带 bug 上线
- **日志**推荐 Pino（高性能结构化日志），生产环境输出 JSON 格式方便接入 ELK/Loki
- **全局过滤器**统一错误响应格式，`HttpExceptionFilter` + `AllExceptionsFilter` 兜底——不要让框架的默认错误格式暴露给前端

### 15.2 数据与缓存

- **缓存分层**：内存 LRU（进程内极快）+ Redis（跨进程共享），并**永远在写操作后主动 invalidate 缓存**
- **ORM 选型**：Prisma（类型安全优先）或 TypeORM（NestJS 原生生态），关系型数据库必须关掉生产环境的 `synchronize`
- **多数据库**场景用 `Map<string, DataSource>` 管理连接实例，`onApplicationShutdown` 中循环销毁

### 15.3 认证与授权

- **密码存储**：唯一推荐 Argon2，不要再问"bcrypt 够不够"
- **数据校验**：`ValidationPipe` + `whitelist: true` + DTO 的 `class-validator`——三层防护
- **接口脱敏**：`@Exclude()` 装饰器或 `SerializeInterceptor`——绝不让密码出现在任何接口响应里
- **权限控制**：RBAC 覆盖 80% 场景，CASL 解决剩下 20% 的属性级条件权限

### 15.4 异步与可靠性

- **RxJS** 处理数据库重试、防抖节流、异步流程编排——把它当成"异步事件的 Lodash"
- **Bull** 消息队列解耦重任务（邮件、图片处理、报表生成），失败自动重试
- **微服务超时**必须配置 `timeout` + `retry` + `catchError` 降级——下游挂了不能让上游也跟着死

### 15.5 微服务架构

- **服务拆分**从业务边界出发，辅以功能（审计、通知、文件）和资源特征（高频/低频/IO密集/计算密集）两个维度
- **服务治理**关注注册发现（Consul）、配置中心、网关、链路追踪（SkyWalking）、日志采集、监控告警
- **通信方式**：内部服务优先 gRPC（强类型 + 双向流），异步事件用 Redis Pub/Sub 或 Kafka
- **Monorepo 目录**用 `apps/` + `libs/` 结构，proto 和公共代码严格共享，不拷贝
- **本地开发**用 Multipass + K3s，生产部署关注 `livenessProbe` 和 `readinessProbe`

### 15.6 最后的建议

不要一上来就搞微服务。先写单体，当单体真的成为瓶颈（团队协作冲突、数据库扛不住、部署互相阻塞）时再拆。

NestJS 好就好在你先写成单体，后面拆微服务只需要把 Service 包成微服务端，把调用方改成 ClientProxy——业务代码几乎不用动。这才是真正的"为拆分而生"。

这篇文章涉及的技术栈很多，你不必一次性全掌握。我的建议是按优先级来：

1. 先搞定**配置 + 日志 + 异常处理**（项目地基）
2. 再搞定**数据库 + 缓存 + 认证授权**（业务核心）
3. 最后搞**消息队列 + 微服务**（架构扩展）

每搞定一层，验证它确实在生产环境跑得稳，再进下一层。
